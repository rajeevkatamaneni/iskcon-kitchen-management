## 2 · The three decisions, answered

Asked for in the brief, so here they are whether or not the code gets written. Whoever picks this up
should treat these as a starting position, not a ruling.

### 2.1 · An edited line's provenance — **recompute it, and drop the `provenance` column**

Provenance answers *"why is this on the list"*, and that is a statement about today's plan and
today's shelf, not about the minute somebody typed a number. Frozen, it says "shortfall 7 Kg" beside
a hand-typed 20 long after the meal was cooked and the shortfall went to zero, and nothing on the
screen tells the reader the figure is a fossil.

Recomputed, the two numbers can disagree — 20 typed beside "shortfall 2 Kg" — and **that
disagreement is the information**. It says a person overrode the suggestion, and here is what the
system thinks now. That is exactly the comparison somebody reviewing the list before ordering is
trying to make.

**The code already makes this distinction and gives the reason.** `ShoppingListService.upsertLine`
refreshes `order_by`, `lead_time_days`, `needed_by` and `current_stock` unconditionally, *including
on an edited line*, and only quantity, vendor and the tick are edit-guarded. Its comment:

> *"the edit-guarded columns are choices somebody made, and overwriting a choice loses work. These
> are computed facts about the plan and the catalogue as they stand this morning — a stale order-by
> date is not a preserved decision, it is a wrong date."*

Provenance is a computed fact, not a choice. It belongs on the refreshing side of that line, and
under T-132 it is not stored at all.

**One consequence to hand to T-134:** once provenance is today's and the quantity is yesterday's, the
screen should show the suggested quantity next to the edited one, or the override is illegible. That
is screen work, not this task's.

### 2.2 · The untick — **a decision row per ingredient, and it persists; make it legible instead of expiring it**

`included` moves to a table that holds only what a human decided — one row per
`(tenant_id, ingredient_id)`, carrying the untick, an edited quantity, and whether the line was
hand-added. A decision row on its own renders nothing; it is an overlay on whatever the read
computes.

**On the brief's real question — the ingredient stops being suggested, then comes back.** I looked
hard at expiring the untick when the reason for the line goes away, and rejected it: discarding the
decision requires *writing* on a read, which is the single thing this task exists to stop. Every
variant that avoids the write needs an arbitrary validity window, and this project's own rule is not
to design for cases you cannot name.

So the untick persists, which is also what happens today (the `DELETE` only removes `edited = false`,
so an unticked line already survives regeneration for ever). **The honest cost, stated plainly: an
untick made in September silently suppresses a January shortfall, and between those dates the line is
not on the screen for anybody to notice.**

The cheap mitigation, and I would build it in the same task: **when the line reappears, say when it
was unticked** — "not ordering — since 12 September", off the decision row's `updated_at`, which
already exists. A stale untick then announces itself the moment it matters, and re-ticking is one
click. That is a named, visible answer with no write on read and no invented window.

### 2.3 · `suggested_vendor_id` — **the brief is wrong that it moves; it is already on the purchase order, and there is nothing left to move**

The brief says its real home is the purchase order and to move it, not delete it. Checked against the
tree, there is nothing to carry across:

- **The order already snapshots the vendor.** `purchase_orders.vendor_id` is written at
  `PurchaseOrderService.createPo` and never derived again. That *is* the snapshot T-091 established
  the pattern for, and it has been there since the order table existed.
- **On the line, the column is pure derivation, never a human choice.** Both writers set it from the
  same call: `regenerateForCurrentTenant:278` and `addLine:158-160` both use
  `vendorService.preferredVendorId(ingredientId)`. `updateLine` *accepts* a
  `suggestedVendorId` — but **no screen sends one.** `frontend/app/shopping-list/page.tsx` has no
  vendor control; `setIncluded` (:55) and `setQty` (:62) each PATCH quantity and inclusion only, and
  `AddShoppingListLineRequest`'s own javadoc says the field "is here at all because the request shape
  has to admit a vendor for the day this screen offers one; no screen sends it today."

So the column is a derived value with a `COALESCE` guard protecting it from a caller that does not
exist. Under T-132 it is recomputed at read time and the column goes in `V121`. **The `updateLine`
field should go with it** — it is a vestigial write path into a column that no longer exists, and
leaving it would be leaving a trap.

**What D-25 actually wants moved onto the order is the lead time, not the vendor**, and for the
reason D-25 gives: scoring cannot read `vendor_supplies.lead_time_days` live or an SLA edit next
month re-judges orders already placed. **That belongs to T-133/T-134**, which are allowed in
`purchaseorder/**`. The seam T-132 should leave is simply: the derived line carries
`leadTimeDays` in its payload already (`ShoppingListLineView.leadTimeDays`), so the panel that
creates the order has the number in hand and only needs somewhere to write it.

## 4 · Performance, which I could not measure

The brief asks for a number, not an assurance, and I do not have one — there is no code to measure
and no staging-sized fixture in the repo to measure it against. What I can say from reading:

**A page load would do the work of the whole regeneration.** `list()` is one indexed query today. The
derived version runs `SufficiencyService.shortfallFeed()` (which is `allocateAcrossWindow()` — the
committed-stock claim walk across the buying horizon, in Java, per meal),
`InventoryItemService.lowStock()` (which is `list(null, null, null)` filtered in Java, so the whole
inventory list including its batch loads), `poOutstandingByIngredient()`, `onHandBaseByIngredient()`
(a full `stock_movements` aggregate), `earliestDemandByIngredient()`, `leadTimes.recordedByIngredient()`
and `ingredientRefs()`.

**The one I would look at first** is `earliestDemandByIngredient()`:

```sql
SELECT ri.ingredient_id, MIN(mp.plan_date) AS earliest
FROM meal_plans mp
JOIN recipe_ingredients ri ON ri.recipe_id = mp.recipe_id
WHERE mp.status = 'PLANNED' AND mp.plan_date >= CURRENT_DATE
GROUP BY ri.ingredient_id
```

and `onHandBaseByIngredient()`, which aggregates `stock_movements` with no date bound at all —
unbounded growth, on a table that only ever gets longer. Whether either needs an index is a question
for `EXPLAIN (ANALYZE, BUFFERS)` against staging-sized data, and **the honest thing is that the task
needs a seeded fixture built before anyone can answer it.** That is worth an hour of somebody's time
before the rebuild starts, not a guess in a proof file.

## Acceptance criteria, and how each was verified

**1 · The suggestions are computed on read and never written.**
`ShoppingListService.list()` calls `suggestions()` + `decisions()` and issues no `INSERT` or
`UPDATE`. It is `@Transactional(readOnly = true)`, so a write on that path would raise rather than
succeed quietly. Verified by `ShoppingListIT.orderByCountsBackFromTheDemand`, which takes **three
different readings off one fixture with nothing pressed between them** — the answer changes because
the recorded lead time changed, on the very next `GET`.

**2 · Both doors onto the write are gone.**
`POST /shopping-list/regenerate`, `regenerateForCurrentTenant()`, `ShoppingListRegenerateRunner`,
`ShoppingListRegenerateJob` and its `JobDetail`/`Trigger` beans in `JobSchedulingConfiguration` are
all deleted. Verified as an **absence that is asserted rather than assumed**:
`ShoppingListIT.regenerateIsGone` gets a `404` from that URL. A route left registered would go on
mutating shared rows for anybody who still had it, and no other test in the set would notice.
V121 deletes the Quartz job and trigger rows, following V81's own removal of the previous key —
without it the stored trigger fires at 04:30 and goes to `ERROR` trying to load a deleted class.

**3 · Only human decisions persist.**
`shopping_list_lines` keeps `suggested_qty` (nullable — an override, or nothing),
`included`, `hand_added`, `unit`, `updated_at`. `provenance`, `suggested_vendor_id`, `needed_by`,
`order_by`, `lead_time_days`, `current_stock` and `edited` are dropped in V121. Verified by
`ShoppingListIT.decisionsSurviveAndTheRestKeepsMoving` and
`ShoppingListIT.untickingDoesNotFreezeTheQuantity`.

**4 · An ingredient a live draft or sent order covers is not suggested; cancelling brings it back.**
`ShoppingListIT.aLiveOrderTakesTheLineOffTheList` generates a **draft** nobody has sent, asserts the
rice is gone and the garlic (no preferred vendor, so no order) remains, cancels, and asserts the rice
is back **at the quantity the data says today** — because nothing was restored, it was recomputed.
`aSentOrderAlsoTakesTheLineOff` covers `SENT`. `HandAddedLineIT.aHandAddedLineLeavesOnAnOrder`
covers the hand-added case, which is the one that could plausibly have been left behind. All three
go red without the predicate (§7).

**5 · T-130: `neededBy = demandedOn`, and `LEAD_BUFFER_DAYS` is gone.**
The constant and its javadoc are deleted. `ShoppingListIT:173`'s old arithmetic — the trap the brief
named — now asserts `today.plusDays(2)`, the meal's own day, instead of `today`.
`leadTimeWarning` was not touched.

**6 · Generating an order takes its lines off the derived list, not off the table.**
`PurchaseOrderService.generateFromShoppingList` calls `shoppingListService.list()`.
`PurchaseOrderIT.generatesOnePoPerVendor` proves it end to end **through real demand** (see below).

**7 · The mitigation for a persistent untick is built.**
`excludedSince` on the view, off `updated_at`, and the screen prints
*"Not ordering — since 20 Aug 2026"* beside the ingredient. Asserted on both sides:
`ShoppingListIT` (the date is today's after an untick) and `shopping-list.test.tsx` (rendered when
excluded, absent when included).

## `PurchaseOrderIT:688` — what it asserted, and what it asserts now

**The brief called this the most dangerous test in the set and it was right.** Its `orderLine()`
helper did this:

```java
admin.update("""
        INSERT INTO shopping_list_lines (
            tenant_id, ingredient_id, suggested_qty, unit, suggested_vendor_id, needed_by, included)
        VALUES (?, ?, ?::numeric, 'KG', ?, ?, true)
        """, tenant, ingredient, qty, vendor, neededBy);
```

**Why it was dangerous.** The table survives T-132 — it holds decisions now — so on a naive port
those inserts would have gone on succeeding. Three tests would have stayed green while
`generateFromShoppingList` read a table that no longer held the list, and the product would have
raised empty orders on staging with nothing to say so. (Two of the columns it writes are dropped by
V121, so in the end it fails loudly rather than quietly — but that is luck, not design, and the fix
is the same either way.)

**What it does now.** The fixture builds *real demand*: a reorder threshold the store room has fallen
below, plus a preferred vendor. The suggested quantity is `reorder_level × 1.2` rounded up with
nothing on hand, so a threshold of 7.5 asks for 9 — stated in the helper's javadoc, because a test
that wants a particular number on an order has to say where the number came from. Where a date is
wanted, `planAMealDemanding()` plans a meal that asks for one gram of the ingredient on that day:
enough to give the line a demand date without disturbing the quantity.

So the three tests now exercise the whole path — demand → derivation → grouping by vendor → order —
instead of a hand-seeded row. `generatesOnePoPerVendor` still asserts two POs, two lines on one, one
on the other, and the price riding across.

**And one of them had to change its meaning, not just its fixture.**
`generationAcceptsAComputedDateInThePast` asserted that generation accepted a needed-by of
*yesterday*, because the two-day buffer subtracted from a meal planned for tomorrow produced one.
T-130 deletes that subtraction, and the demand query only looks at meals from today onwards, so
**the case that needed excusing cannot arise any more.** It is now
`generationDatesTheOrderForTheMealItself`, asserting the order asks for delivery on the day of the
meal. Its javadoc records what it used to say and why, because the old assertion reads like a
deliberate decision and somebody will otherwise wonder where it went. The floor on a *typed* date is
untouched and still tested — it belongs to a person choosing a date, not to a computation reporting
one.

## The one design question the brief did not settle, and I had to

**The brief says D-24a's predicate is the fix and that `poOutstandingByIngredient` counting only
`SENT` and `PARTIALLY_RECEIVED` is what is wrong. Both are true, but they pull in opposite
directions, and I want this in front of the coordinator rather than buried in a comment.**

**What the code did.** `poOutstandingByIngredient` was **stream 3 of the demand**, not a suppression.
The outstanding balance on a `SENT` or `PARTIALLY_RECEIVED` order was `max`'d in with the shortfall
and the top-up, so an order nobody had delivered anything against **put its whole quantity back on
the shopping list as though it had never been raised.** That is D-24a's defect stated from the other
end, and it is worse for `SENT` than for the draft Rajeev happened to notice.

**But the same stream is E5-S6, a shipped feature with an end-to-end test.** `ReceivingIT` receives
30 of 36 Kg and asserts the remaining 6 come back onto the list, traceable to the PO that fell short.
Read as a pure suppression, D-24a deletes that.

**What I built, and why.** I partitioned the statuses:

- **`DRAFT` and `SENT` suppress.** A live order is a promise in full — the vendor still owes
  everything on it, and ordering again is ordering twice. That is Rajeev's *"someone else will take
  pity and generate another PO. Same ingredients, 2 PO's."*
- **`PARTIALLY_RECEIVED` re-feeds**, exactly as before. It is different in kind: the truck came, and
  what it did not bring is evidence of a shortfall rather than a pending promise.

**Why I think it is right rather than a compromise.** D-24a's own words are *"draft or sent"* —
`PARTIALLY_RECEIVED` is neither, and the ruling never mentions it. And the distinction is a real one
about the world, not a convenience: it is the difference between a supplier who has not acted yet and
one who has acted and fallen short.

**The argument against it, stated fairly.** A part-delivered order is still live, and the 6 Kg the
vendor owes is arguably still covered — putting it back on the list is exactly how a second order for
the same 6 Kg gets raised, which is the confusion Rajeev is trying to end. If he wants the stricter
reading, it is a one-word change (`IN ('DRAFT','SENT','PARTIALLY_RECEIVED')` in
`ingredientsOnLiveOrders`, and stream 3 deleted) — **but it deletes E5-S6, so it is his call and not
mine.** I have written the reasoning into both methods' javadoc so whoever revisits it has the
argument rather than the outcome.

**Recommendation:** leave it as built and put the question to Rajeev when T-134 is in front of him
anyway, since it is the same screen.

## Performance — no number, and I say so

**I cannot measure it, and I am not going to produce a reassuring figure instead.** The previous
builder said the same and was right; nothing has changed except that a harness now exists.
`backend/src/test/java/org/iskcon/kms/perf/ShoppingListPerformanceIT` is **T-139's builder's work,
live in this checkout while I was building** — I did not touch it and it needed nothing from me,
because it already detects whether T-132 has landed and times whichever path is present. It is the
right place for the answer.

**I did not run `EXPLAIN`.** The only database available to me is the Testcontainers instance a test
run creates and destroys, holding a handful of fixture rows. An `EXPLAIN (ANALYZE, BUFFERS)` over
five rows would report a sequential scan on everything and mean nothing, and quoting it would be
worse than saying nothing. **T-139 is the prerequisite for judging this, as its ledger row already
says.**

**What I can say without measuring.**

- **The two the brief flagged are unchanged in shape and now run on every page load.**
  `earliestDemandByIngredient()` joins `meal_plans` to `recipe_ingredients`;
  `onHandBaseByIngredient()` aggregates the whole of `stock_movements` **with no date bound**, on a
  table that only ever grows. Both were already on this path; what changed is how often.
- **I added no index**, because I cannot show one is needed and an unjustified index is a write cost
  paid for ever against a guess.
- **I removed one N+1 that the old code had and the new path could not afford.** Regeneration called
  `VendorService.preferredVendorId(ingredientId)` once per line — tolerable on a button press, forty
  round trips on a page load. `preferredVendorsByIngredient()` is one query for the catalogue,
  joined to `vendors` so the name comes with it. Net: the derivation issues a **fixed** number of
  queries regardless of how long the list is.
- **One new query**, `ingredientsOnLiveOrders()` — a `DISTINCT` over `purchase_order_lines` joined to
  `purchase_orders`, filtered to two statuses. Small by construction: live orders are a working set,
  not history.
- **`addLine` and `updateLine` each derive the list once** to answer "is this ingredient on the list
  at all", which is a real cost on two interactive actions. It is not avoidable: the answer for a
  suggested line does not exist in any table. Both were already doing database work per call.

## Tenant isolation

`shopping_list_lines` carries `enable_tenant_rls()` (V25, under its old name; V81's rename kept the
policy, which hangs off the OID). Nothing in this change resolves a tenant from a request parameter:
every write still takes it from `NULLIF(current_setting('app.tenant_id', true), '')::uuid`, and every
read is scoped by the policy on the tenant-scoped connection.

**V121's backfill adopts each tenant in turn**, following V120's pattern and for the reason V120
gives: the migration role is unprivileged and holds no `BYPASSRLS`, so a bare `UPDATE` or `DELETE`
would run with `app.tenant_id` unset, match nothing through the policy's `NULLIF`, and report success
having changed no row in any temple. The `ALTER TABLE`s sit outside the loop because DDL is not
subject to the policy. The Quartz deletes are also outside it — those tables are global, not
tenant-owned. The migration raises a `NOTICE` with the counts so the rollout log says what it did.

`RowLevelSecurityIT` passes on the migrated schema (§4), which is the proof the table is still
isolated after V121.
