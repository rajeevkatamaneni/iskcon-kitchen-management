## What was built

`GlobalExceptionHandler.handleValidation` chooses between two codes instead of always stamping one:

```java
ErrorCode code = isOnlyAboutAPhoneNumber(e.getBindingResult().getAllErrors())
        ? ErrorCode.INVALID_PHONE_NUMBER
        : ErrorCode.VALIDATION_FAILED;
```

**Which of the two rules this is.** Not "did a phone number fail" — that would hand KMS-400003 to a
half-empty form and hide the other four fields. It is "was the phone number the *only* thing that
failed", which is the acceptance criterion that defines the boundary, and it is asserted from both
sides in the test.

Two details worth stating because they are what makes the carve-out narrow rather than clever:

- It keys on **the constraint that failed**, never on the field's name — the error must be a
  `@Pattern` violation whose `regexp()` is the E.164 rule. Name-matching would have answered "that
  phone number isn't in a format we can use" to somebody who typed *nothing*, because `@NotBlank`
  on a `phone` field is also an error on a field called phone. A missing number is not a malformed
  one, and `"Enter a phone number."` is already right for it. Tested.
- It reads `getAllErrors()`, not `getFieldErrors()`. An object-level constraint failing at the same
  time is a second thing wrong with the form and does not appear among the field errors; testing
  only those would let it be dropped silently behind a code claiming the phone was the problem.

The E.164 literal is duplicated into the handler as `E164_PHONE_RULE`. That is a real cost and it is
written up in the code: a shared constant would need a home both a request record and the exception
handler can see, and a DTO importing the exception handler to describe its own field is worse
coupling than a repeated literal. `PhoneValidationIT` is what holds the two in step — it posts a
malformed number to every one of those endpoints, so drift fails a test rather than silently
switching the feature off.

## Which two DTOs actually lacked a format rule — the row is wrong, and here is the tree

The brief said two of the listed DTOs check only length. **Mechanically there are three**, and
**genuinely there is one.**

| DTO | Phone field | Constraint |
|---|---|---|
| `JoinTempleRequest` | `phone` | E.164 `@Pattern` |
| `ProvisionTenantRequest` | `adminPhone` | E.164 `@Pattern` |
| `CreateVendorRequest` | `phone` | E.164 `@Pattern` |
| `UpdateVendorRequest` | `phone` | E.164 `@Pattern` |
| `HireStaffRequest` | `phone`, `emergencyContactPhone` | E.164 `@Pattern` (both) |
| `CreateKitchenRequest` | `contactPhone` | **`@Size(30)` only** — deliberate |
| `UpdateKitchenRequest` | `contactPhone` | **`@Size(30)` only** — deliberate |
| `CreateRecurringRequest` | `phone` | **`@Size(20)` only** — the real gap |

**The kitchen pair is exempt by design, and I left it alone.** Its own Javadoc has said so since the
file was created (`5567280`, "a temple can record the kitchens it runs"): *"Not held to E.164 as a
vendor's is: this one is dialled by somebody standing in the temple, and an internal extension is a
legitimate answer."* That is not a stale comment — `KitchenIT`'s shared happy-path body posts
`"contactPhone":"204"` and asserts `isCreated()`, so **every kitchen created anywhere in that suite
uses an extension**. Applying E.164 there would break `KitchenIT`, which is not in my contract, to
enforce a rule the code explicitly argues against.

I also did not invent a lenient "looks like a phone" regex for those two fields. Nothing in the tree
says what a temple may legitimately type there — `"204"`, `"Ext. 204"`, `"204 / 9886230011"` are all
plausible — and narrowing an intentionally permissive free-text field on my own guess is designing
for cases I cannot name. **It stays a decision for Rajeev**, recorded below.

It follows that the kitchen endpoints keep KMS-400001, and that is deliberate rather than an
oversight: KMS-400003's permanent words are *"Include the country code, for example
+91 98765 43210."*, which on a field where `"204"` is a correct answer is **false advice** — a
Commandment 3 problem, not a nicety. I added a sentence to each kitchen DTO saying that the absence
of the constraint is load-bearing, so the next reader does not "fix" it.

**`CreateRecurringRequest.phone` is the genuine gap** and is the one I closed. It never had a format
check (`430267b`, E7-S3, and nothing since), so `"98450"` was accepted outright and stored against a
mandate that renews for years — the worst path in the application to accept one on, because a
recurring plan is precisely the donation the temple has to reach somebody about later. It now
carries the same E.164 `@Pattern` as everything else, still optional (`@Pattern` passes null).

**Why it is 5 of 9 and not 9 of 9 — the counting rule.** Four of these tests assert an *absence*:
that KMS-400003 is **not** used for a blank box, for a second bad field, for another `@Pattern`
field, or for a kitchen's extension. Remove the feature and there is no KMS-400003 anywhere, so all
four pass **vacuously**. That is not a hole; it is what an absence-assertion does under a control,
and it is why the failure count needs this paragraph rather than being read as four untested cases.
The five that fail are exactly the five that assert the specific code is reached.

**One false start, reported rather than dropped.** The control's first run came back **6** failures,
with a `DuplicateKeyException` on `tenants_slug_key` in the middle of it. That was an artefact of the
control itself, and an instructive one: with the recurring `@Pattern` stripped, `"98450"` is
*accepted*, a `recurring_plans` row is written, and its foreign key then holds the tenant down so my
`@AfterEach` fails and the next `setUp` collides. I added `DELETE FROM recurring_plans` to the
teardown and gave the class a slug of its own, re-ran both the verify and the control, and the
numbers above are from those clean runs. No assertion was touched — the tests are as written. The
incident is itself evidence that the new format rule is load-bearing: without it the rubbish number
does not merely get the wrong code, it gets *stored*.

**2. Deviation from the acceptance criterion, raised here rather than after the fact.** The brief
asks that *each* listed endpoint answer KMS-400003. The two kitchen endpoints do not, for the reason

held to a format after all, that is a real decision with three parts — what shape is legal, what the
message says, and updating `KitchenIT` — and it is not mine to take.

it: this change alters an API response code, and the frontend surface that would show it is
`frontend/` — T-082's contract this wave, so I stayed out. Worth checking when someone next drives
the deployed app that a bad phone on the vendor and join forms now shows the KMS-400003 wording
rather than the generic one, and that no screen keys off the literal string `KMS-400001` for a phone
field.
