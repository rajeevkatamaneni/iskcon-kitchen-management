# T-003 — a 401 from the security filter chain now carries its KMS code, and the web app reads it

Two codes existed with finished copy and were thrown nowhere: `ACCOUNT_DISABLED` (**KMS-400019**)
and `NO_ACCOUNT_AT_TEMPLE` (**KMS-400020**). `AuthenticationFilter` dropped silently at both sites
and `SecurityConfiguration` answered with a bare `HttpStatusEntryPoint` — a 401 with no body at all,
the only response in the product carrying no reference code. `GlobalExceptionHandler` cannot fix
this: it is a `@RestControllerAdvice`, and a request refused in the filter chain never reaches
`DispatcherServlet`.

The mechanism built, once: the filter **records** the reason as a request attribute where it used to
return silently, and a new entry point serialises the real `ErrorResponse` if — and only if — the
request went on to reach something that required an identity. Nothing is thrown, so the paths that
deliberately allow an unauthenticated request through (webhooks, unsubscribe, the temple list) are
untouched. The frontend then branches on the code rather than on the absence of a network error.

### How it works, in three lines

- `AuthenticationFilter` calls `recordFailure(request, ErrorCode…)` at the two sites named in the
  task (`!user.isActive()`, and the non-join-flow `return` in the no-membership branch). The
  private `authenticate(...)` now takes the `HttpServletRequest` instead of the temple header and
  path, which it derives itself.
- `AuthenticationFailureEntryPoint` reads that attribute, and writes
  `ErrorResponse.of(code)` as JSON at `code.httpStatus()` using the **application's own**
  `ObjectMapper` bean, so a body written from outside the dispatcher is byte-for-byte what the
  dispatcher would have produced. Attribute absent → today's bodyless 401, unchanged.
- `SecurityConfiguration` injects it in place of `new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)`.

## The `SESSION_EXPIRED` half was **held**, deliberately

`SESSION_EXPIRED` (**KMS-400018**) was not built and is not sent. `FirebaseTokenVerifier.java` and
`TokenVerifier.java` were not opened. The bad-token branch at `AuthenticationFilter` records no
attribute and still emits a bodyless 401, and there is a test asserting exactly that —
`a token that cannot be verified is still refused without saying why` checks the body is
null-or-empty, so a later change that starts explaining token failures will fail here rather than
slip through. Whether to carve "expired" out as the one safe disclosure, or delete the code as dead
copy, is Rajeev's open question and is untouched.

**The honest consequence, not fixed:** an expired token produces an uncoded 401, so it lands on the
frontend's fallback branch and is still reported to the user as `no-account`. That is unchanged from
today's behaviour, is known, and is the visible cost of holding this half. The comment in
`REFUSALS` in `auth-context.tsx` and the third frontend test both say so in place, so whoever
answers the question finds the note next to the code.
