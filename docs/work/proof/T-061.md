# T-061 — the operator's temple list showed 0 people at every temple; it now shows the true number

`/tenants` and `/tenants/{id}` counted members with `(SELECT count(*) FROM users u WHERE u.tenant_id = t.id)`.
`users` is tenant-owned and carries `FORCE ROW LEVEL SECURITY`; a platform operator is tenantless, so
the policy compared `tenant_id` against NULL, matched nothing, and `count(*)` over nothing returned a
perfectly ordinary **0** — no error, no log line, just a wrong number that looked like an answer.

Both call sites now go through a new `tenant_user_count(uuid)`: `SECURITY DEFINER`, pinned
`search_path`, which adopts one temple's context transaction-locally (the `delete_tenant_cascade`
move from V45), counts *inside* the policy rather than around it, and restores the caller's context
before returning. It returns a `bigint` and nothing else.

## I checked the brief's correction, and the brief is right

The task row originally asked for "a `SECURITY DEFINER` function with a pinned `search_path`, **not**
`BYPASSRLS`". The brief corrected that to say a `SECURITY DEFINER` function *on its own* would still
return 0, because `FORCE ROW LEVEL SECURITY` subjects the table's own owner to the policy.

**I agree, and I did not take it on trust.** `OperatorUserCountIT` builds precisely that naive
function — `SECURITY DEFINER`, pinned `search_path`, no borrowed context — as `kms_migrator` (the
schema owner, so it is owned by the schema owner exactly as a migration's function would be), and
calls it from a `kms_app` connection with `app.tenant_id` set to `''`. Same connection, same instant,
it then calls the real function. The database's verdict:

```
OperatorUserCountIT > a plain SECURITY DEFINER count still answers 0 — FORCE RLS binds the owner too PASSED
```

The assertions inside it are `assertThat(naive).isZero()` and `assertThat(scoped).isEqualTo(3)`. If
the simpler fix had been sufficient, the first assertion would have failed and I would be reporting
that instead. It did not. `SECURITY DEFINER` buys nothing here; the `set_config` is the whole fix.
This is now a standing test, so if a future PostgreSQL ever changes that behaviour the suite says so
rather than a deployment.

## Acceptance criteria, one by one

**The list and detail show the true number; a temple with none shows 0.**
`listShowsTheRealHeadcount` seeds two temples — one with a TEMPLE_ADMIN, a KITCHEN_STAFF and a
VOLUNTEER (the three accounts actually measured on staging), one with nobody — and asserts 3 and 0
from a single `/api/v1/tenants` response, matched by slug rather than by position because other
classes leave temples behind. `detailShowsTheRealHeadcount` asserts the same two numbers from
`/api/v1/tenants/{id}`. Seeding the empty temple is deliberate: without it, a "fix" that returned a
constant would pass.

**A tenant user's own screens are unchanged.**
Nothing a tenant user reaches was touched — the change is two SQL fragments inside two
`MANAGE_TENANTS` endpoints. `aTempleAdminStillCannotReachTheOperatorScreens` signs in as a real,
active TEMPLE_ADMIN of the seeded temple and gets **403** from both endpoints, so the fix widened
what an operator may count, not who may ask. The 15 `TenantUpdateIT` and 8 `MembershipIT` tests
covering tenant-side behaviour all pass.

**The caller's tenant context is unchanged after the count runs — asserted, not argued.**
Two tests, both on a raw `kms_app` connection with **autocommit off**. That second detail is what
makes them real: a transaction-local setting reverts at commit, so a test that looked after the
transaction would pass whether or not the function restored anything. Inside the transaction:

- `theOperatorsEmptyContextIsPutBack` — tenantless caller counts 3 at a temple, then
  `current_setting('app.tenant_id')` is asserted **equal to `''`** (not merely "not the temple": a
  restore to NULL would behave identically today and would be the one place in the system that
  writes "no tenant" differently), and `SELECT count(*) FROM users` is **0** — the operator still
  sees nothing, which is the property that actually matters.
- `aCallersOwnTenantContextIsPutBack` — a caller sitting in temple B sees 1 user, counts 3 at
  temple A, and afterwards the setting is temple B's again and they still see exactly 1. Not four,
  not three.

Delete the restore line from V102 and both fail; that is what makes them assertions rather than
decoration.

**A test proves the count is right when run as the unprivileged role.**
Every raw-connection test uses `DriverManager.getConnection(POSTGRES.getJdbcUrl(), APP_ROLE, APP_PASSWORD)`
— `kms_app`, which `AbstractIntegrationTest:79` sets `NOSUPERUSER NOBYPASSRLS`. The MockMvc tests go
through the application's own DataSource, which is the same role. The container superuser is used
only to seed fixtures, never to assert. I did not touch `AbstractIntegrationTest` or
`RowLevelSecurityIT`; the harness already arranged all of this.

**The function pins its `search_path` and returns a count and nothing else.**
`theFunctionIsShapedAsASecurityDefinerFunctionMustBe` reads `pg_proc` and asserts
`prosecdef = true`, `array_to_string(proconfig, ' | ') = 'search_path=pg_catalog, public'`,
return type `int8`, and `proretset = false`. A property of the deployed schema, not of the migration
text — so a later migration that redefined the function without the pin would fail this.
`theCountAnswersForOneTempleOnly` adds that it answers per-temple only, and that an unknown temple id
is 0 rather than an error or a leak.

**Both `list()` and `get()` are fixed.** Both, and the negative control proves both were broken —
each produced its own `expected 3 but was 0`.

has a `tenant_id` column needs a tenant context; a table without one is a platform table and needs
none. `last_export_at` sitting on the same row as the broken count is the cleanest possible statement
of it, and I left a comment saying so at both call sites.

## Two decisions I made that the brief did not ask for

**1. `REVOKE EXECUTE ... FROM PUBLIC`, then `GRANT` to `kms_app`.** PostgreSQL grants `EXECUTE` on a
new function to `PUBLIC`, which for a `SECURITY DEFINER` function hands the owner's reach to every
role in the cluster. Cheap to close, so I closed it, guarded by the same `IF EXISTS (kms_app)` test
V1 uses — and the guard deliberately covers the `REVOKE` as well, since revoking from PUBLIC without
a role to grant to would leave the function callable by nobody but its owner.

**2. I did *not* add a "caller must be tenantless" check inside the function, and I think that is
right.** It looks like hardening, and it is not. Every request arrives on the same `kms_app`
connection, so anyone able to call the function at all is able to `set_config('app.tenant_id', '')`
first and satisfy the check. It would buy nothing against the threat it appears to address, would add
a failure mode with no `KMS-nnnnnn` code behind it, and would break the very test that proves the
restore works. The real gate is `@PreAuthorize("hasAuthority('MANAGE_TENANTS')")`, which is where
this project has decided authorisation lives. Flagged rather than left silent — see below.
