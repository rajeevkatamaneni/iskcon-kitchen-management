## The table

`whatsapp_template_status_copy`: `tenant_id`, `template_name`, `our_category`, `meta_status`, `meta_category`, `held`, `wording_matches`, `meta_rejected_reason`, `lookup_problem`, `taken_at`. Primary key `(tenant_id, template_name)`. Calls `enable_tenant_rls()`.

- **Why it's tenant data.** Every row describes one temple's WhatsApp business account, read with that temple's secret. Two temples can hold different answers for the same template name.
- **Why a table, not columns on `tenant_settings`.** The copy has its own clock and is replaced on its own. Also, the webhook-lookup policy can read `tenant_settings`, which is no place for Meta's refusals.
- **Replaced whole, not append-only.** It's a cache of Meta's current answer. Who pressed Refresh is recorded in `audit_events`.
- **Checks.** A row Meta didn't answer for must carry a problem and claim nothing else. `wording_matches` is set exactly when `held` is true.
- **Tenant deletion: no change needed.** `delete_tenant_cascade` finds tables by their `tenant_id` column, so this one is purged automatically. It isn't append-only, and nothing references it. The foreign key is `ON DELETE CASCADE`, not RESTRICT: nobody made these rows, and the Submission, Test Send and Last Sent tests all tear down with `DELETE FROM tenants`. `TenantDeletionIT` passes, 9 of 9.
- **Migration under RLS.** DDL only, with nothing to seed or backfill.

## The two refresh paths and their audits

- **Operator Refresh:** `POST /api/v1/ops/tenants/{id}/whatsapp-templates/refresh`, behind `MANAGE_TENANTS`.
  1. `OpsService` checks the temple exists (otherwise `TENANT_NOT_FOUND`).
  2. It sets that temple's context and runs `compare()` in its own read-only transaction.
  3. `TemplateStatusCopy.replaceForOperator` then deletes, inserts and writes **one** `WHATSAPP_TEMPLATE_STATUS_REFRESHED` audit row on the temple, all in one transaction. The audit's before and after are both read from the table: `asOf`, and the counts of templates, approved, pending, refused, not held and not answered.
  4. It clears the context in `finally`.

  A temple that isn't connected is refused with `KMS-400001` before Meta or the audit log is touched.
- **The temple's own Reload:** at the end of `reloadTemplates`, `statusCopy.replace(comparison.compare())`. It runs inside Reload's transaction and writes no operator audit, because the temple acted and its Reload is already audited as `SETTINGS_UPDATED`.
- **Reading:** `GET /api/v1/ops/tenants/{id}/whatsapp-templates` and `GET /api/v1/ops/whatsapp-templates/status-counts`, both behind `VIEW_PLATFORM_OPERATIONS`. Reading never calls Meta.

## The token, used on the operator's behalf

Meta only answers about a temple's templates to that temple's own account. So on Refresh, `compare()` takes **that temple's own access token** from the secret store, inside that temple's context, and sends it to Meta for the operator. That is why Refresh needs `MANAGE_TENANTS` and is audited on the temple.

The token only travels in the Authorization header of 20 GETs. It is never logged, stored in the copy or audit row, or returned. The Refresh test's stub records every header and checks each one is `Bearer <that temple's token>` on `/waba-govinda/message_templates`. Every test's teardown searches every log line (4 classes at DEBUG) and every response body for both temples' tokens. The audit row's text is checked too.

## Status groupings

Meta's values, from https://developers.facebook.com/docs/graph-api/reference/whats-app-business-hsm/: APPROVED, IN_APPEAL, PENDING, REJECTED, PENDING_DELETION, DELETED, DISABLED, PAUSED, LIMIT_EXCEEDED.

- **Approved:** APPROVED.
- **Pending:** PENDING and IN_APPEAL.
- **Refused:** REJECTED, PAUSED and DISABLED. In each, Meta has decided the template isn't to be sent.
- **Everything else:** not held, not answered, and the other statuses count only toward `templesCounted`. The card shows the leftover as its own number.
- **`templesCounted`:** temples whose stored copy has a row for that template. A temple with no WhatsApp connection, or never refreshed, has no copy and isn't counted. Every card says so.
- **Marketing:** Meta's category is MARKETING, whatever the status.

## The formatting refusal, and where the reason comes from

Meta does give a readable reason.
- The template node has `rejected_reason`: "The reason the message template was rejected. enum {ABUSIVE_CONTENT, INVALID_FORMAT, NONE, PROMOTIONAL, TAG_CONTENT_MISMATCH, SCAM}". Source: https://developers.facebook.com/docs/graph-api/reference/whats-app-business-hsm/
- Meta's webhook reference describes `INVALID_FORMAT` as "Template has invalid formatting". The other values are about content or category, and `NONE` means paused. Source: https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/message_template_status_update
- Meta's template review page lists the formatting reasons as: variables missing or with mismatched braces, special characters in variables, variables out of sequence, too many variables for the length, and a template starting or ending with a variable. Source: https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-review

So `formattingRefusal` = any temple's copy has status REJECTED **and** `rejected_reason` INVALID_FORMAT. T-168's classifier is not used. It sorts Meta's answers at registration, not Meta's review decisions, and a template it refused isn't held, so it has no status to count.

## The counts loop

`TemplateStatusCopy.countsAcrossTemples()`: for each id in `tenants`, it calls `TenantContext.set(temple)`, reads that temple's rows with the same `READ` (`WHERE tenant_id = current_setting…`), and calls `TenantContext.clear()` in `finally`. This is the same shape as `OpsService.notificationMetrics`. It is deliberately not transactional, because the context reaches PostgreSQL when each connection is checked out. There is no cross-temple query: as `kms_app` there is none to write. `TemplateStatusCountsIT` shows the table reading 0 rows with no context, and one temple's 2 rows with that temple's context.

The response is one entry per template, in release order, with exactly the 7 `api.ts` keys. The test checks the body contains no temple's id, name or slug.
