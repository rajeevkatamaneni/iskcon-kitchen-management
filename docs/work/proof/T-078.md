## What was done

A `beforeAll`/`afterAll` pair around the `describe`:

```tsx
const TEMPLE_NOW = new Date("2026-09-01T12:00:00+05:30");
…
  beforeAll(() => {
    vi.useFakeTimers({ toFake: ["Date"] });
    vi.setSystemTime(TEMPLE_NOW);
  });

  afterAll(() => {
    vi.useRealTimers();
  });
```

plus a long comment above it, in the file's existing register, recording that the pin is a rule and
why; and one new assertion at the top of the failing test:

```tsx
expect(todayIso()).toBe("2026-09-01");
```

Three decisions worth stating, because each was a choice and not the only option:

- **`toFake: ["Date"]` only.** Faking the whole timer set breaks React Testing Library's `findBy*`,
  which polls on real timers. Only `Date` needs to move.
- **An explicit `+05:30` offset, not a bare literal.** This turned out to be load-bearing and is
  proved by control 3 below.
- **Today pinned *before* the window, at 1 September.** The two expected dates (the 8th and the
  16th) are then produced by the window arithmetic, not by the clamp — which is the rule this test
  is named for. The clamp has its own test three tests down, and that is the one the clamp control
  turns red. The new `expect(todayIso())` line exists so that if anybody moves the pin forward past
  the 8th, the test fails loudly instead of quietly starting to pass for the clamp's reason.

**Read this one carefully, because it is not quite what the brief predicted.** The file goes red

### Control 3 — is the explicit `+05:30` actually load-bearing?

The brief asserted that "a fake that pins a UTC instant without accounting for the temple's offset
will pass on your machine and fail somewhere else". That is a claim like any other, so it was
tested: `page.tsx` untouched, and the mutation applied to this task's own file — the pinned instant
loses its offset and becomes `new Date("2026-09-01T12:00:00")`.

```
RESTORE OK: reuse-plan.test.tsx byte-identical
```

The claim is true, and the direction is worth recording because I got it wrong first time and had to
correct the comment I had already written. `todayIso()` formats in the temple's zone, so the
**machine's** zone is irrelevant to `todayIso` itself — what it changes is how the offset-less
literal is *parsed*. A bare literal is midday on 1 September in Kolkata from a machine in UTC, but
**03:30 on the 2nd** from one at −10. It therefore breaks to the **west**, not the east:

```
UTC                 -> 2026-09-01T12:00:00.000Z  2026-09-01
Pacific/Kiritimati  -> 2026-08-31T22:00:00.000Z  2026-09-01
Pacific/Honolulu    -> 2026-09-01T22:00:00.000Z  2026-09-02
America/Los_Angeles -> 2026-09-01T19:00:00.000Z  2026-09-02
```

`America/Los_Angeles` is **this machine's own zone** — so an offset-less fake would have failed
here, not "somewhere else", and the brief's suggested `TZ=Pacific/Kiritimati` (+14) would have
missed it entirely. The comment in the file now states the ±direction rather than hand-waving at
"the zone", and the new `expect(todayIso()).toBe("2026-09-01")` line is what catches it.

## A false alarm I chased down rather than reporting either way

I added a leak check beyond what was asked, to satisfy "restore the clock": run the file in a
**shared** worker with isolation off, where a leaked global `Date` would show. It came back
spectacularly red — 24 failures across `calendar`, `equipment` and `reuse-plan` itself:

```
npx vitest run --no-isolate --pool=threads --poolOptions.threads.singleThread …
 Test Files  3 failed | 1 passed (4)
      Tests  24 failed | 40 passed (64)
```

That reads exactly like the defect the brief warned about, and I nearly wrote it up as one. It is
not. Three runs settle it — same command, three states of my file:

```
=== singleThread + no-isolate, with the FIXED file (fake clock) ===
 Test Files  3 failed | 1 passed (4)
      Tests  24 failed | 40 passed (64)
=== same command, with the UNFIXED HEAD file (no fake clock at all) ===
 Test Files  3 failed | 1 passed (4)
      Tests  24 failed | 40 passed (64)
=== and reuse-plan REMOVED entirely from the same command ===
 Test Files  2 failed | 1 passed (3)
      Tests  18 failed | 39 passed (57)
```

Identical with the fix, without the fix, and with my file not in the run at all. The failures are
role- and nav-shaped (`refuses a role the register is not for`, `is reachable from the menu`), not
date-shaped: these files each `vi.mock("next/navigation")` and `@/components/RequireRole`
differently and were never written to share one module registry. **`--no-isolate` is an invalid
instrument for this suite, not a finding.** Without isolation but with the default multi-thread
pool it is green three times running (`Tests 64 passed (64)` ×3), and under default isolation the
seven-file run above is green — so there is no clock leak.

I am recording it because a reader who saw only the red number would draw the opposite conclusion,
and because the general form is the one already in `docs/work/README.md`: *do not accept evidence
that would look identical if the thing were fine.* The way to tell was to run the instrument
against a tree that could not possibly contain the defect.

## The sweep — same shape elsewhere, reported not fixed

The question asked of each candidate was the one the brief set: **does the expected value depend on
when the test runs?** — not "does this file contain a date literal", which is worth nothing.

**Nothing else needs fixing that I could establish.** In particular:

- **`frontend/__tests__/calendar.test.tsx` already solves this**, by a different and arguably better
  route — it mocks the module rather than the clock:
  ```tsx
  // The screen anchors on the temple's today; pin it so the month under test never moves.
  vi.mock("@/lib/format", async (orig) => {
    const actual = await orig<typeof import("@/lib/format")>();
    return { ...actual, todayIso: () => "2026-08-15" };
  });
  ```
  Worth knowing about: it is file-scoped and touches no global, so it cannot leak at all. If a
  future task wants a house style for this, that is the candidate.
- **`equipment.test.tsx`** builds every fixture with an `isoIn(n)` helper relative to today, which is
  the other safe pattern — and it matters there, because `components/EquipmentWords.tsx:104`
  computes `wholeDaysBetween(todayIso(), item.nextServiceOn)` and renders *"Overdue by 12 days"*.
  An absolute `nextServiceOn` asserted against that phrasing would be exactly this bomb. It is not
  done anywhere: `equipment-edit.test.tsx` and `equipment-reinstate.test.tsx` do carry an absolute
  `nextServiceOn: "2026-07-01"`, but neither asserts the relative phrase (grep for
  `Overdue by|Due in|Due today` in those two files returns nothing).
- **`planner.test.tsx`, `manual-purchase-order.test.tsx`, `donations.test.tsx`** compute their
  expectations from `todayIso()` itself, so they move with the clock rather than against it.
- **`my-schedule.test.tsx`, `staff-schedule.test.tsx`, `recipes.test.tsx`** already call
  `useFakeTimers`.
- **Eight files hold an absolute date inside an assertion** — `calendar` ×3, `leave.test.tsx:103`,
  `planner.test.tsx:626`, `meal-recording.test.tsx:374/413/425`, `staff-schedule.test.tsx:312`,
  `today.test.tsx:280`. I opened each. Every one is an **echo of an input**: a route param, a
  fixture field, or a value the test itself typed into the form. None is derived from today.
- **Backend**: of the thirteen test classes mixing `LocalDate.of(20xx…)` with now-sensitive logic,
  only `MealPlanIT` uses `LocalDate.now()`, and it builds its fixtures as `today.plusDays(3)` /
  `today.minusDays(20)` — relative, so safe.

**Confidence, honestly stated.** High for the eight assertion sites and for the equipment wording
path, because I opened those and read the surrounding code. **Medium at best for the rest of the
~80 frontend test files.** My filter was "an assertion line containing a date literal", and that
filter has two known blind spots I did not close: an expected date built up through a helper or a
variable rather than written inline, and a *relative phrase* ("in 3 days", "overdue", "next week")
asserted against an absolute fixture date. I chased the second deliberately for the one component I
found that generates such phrasing (`EquipmentWords`), but I did not enumerate every component that
might. Telling those apart needs each file opened properly, which was outside this task's budget,
and I would rather say so than hand over a list that looks exhaustive and is not.
