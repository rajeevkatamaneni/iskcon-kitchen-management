# T-072 — a struck gift is no longer a permanent, unclearable reconciliation mismatch

`DonationReconciliationService` selected on `status = 'COMPLETED'` alone. V104 makes a void a
**mark**, not a status change, so every struck gift was still put to the gateway on every run — and
because a struck gift is by definition one recorded wrongly, it is the row least likely to have a
real payment behind it, so it came back UNKNOWN and was reported as a mismatch for ever, with a live
gateway API call per struck row per run to produce it.

**Files changed:** both inside the contract, nothing else touched.

- `backend/src/main/java/org/iskcon/kms/donation/DonationReconciliationService.java` — in contract
- `backend/src/test/java/org/iskcon/kms/donation/OneTimeDonationIT.java` — in contract (granted up front)
- `docs/work/proof/T-072.md` — in contract

`git status --porcelain` after the run shows exactly these two source files under my name; the other
dirty paths (`invoice/VendorInvoiceService.java`, `VendorInvoiceIT.java`, `frontend/lib/*`,
`docs/work/DISPATCH.md`, `frontend/app/settings/meal-kinds/`) belong to the other two builders in
this wave and to the work manager's reservations. I opened none of them.

## The fix

One clause, plus the javadoc the brief was right to say would otherwise start lying:

```
WHERE status = 'COMPLETED' AND voided_at IS NULL AND type <> 'IN_KIND'
```

I verified the brief's premises myself rather than taking them:

- `V104__donation_void.sql` adds `voided_at`, `voided_by`, `void_reason` and touches `status` not at
  all — and its own comment says so ("the row stays, stamped with who struck it, when, and why").
- `DonationVoidService:99` is `UPDATE donations SET voided_at = now(), voided_by = ?, void_reason = ?`
  — no status write anywhere in the method.
- `V38__monetary_donations.sql:23` — `status TEXT NOT NULL DEFAULT 'COMPLETED'`.
- The three other readers already carry the clause: `DonationLedgerService:186`,
  `MonetaryDonationService:379`, `MonetaryDonationService:463`. This one did not.

**I accepted the suggested approach rather than reporting the row separately, and the argument is
now in the javadoc so the next reader does not have to re-derive it.** Excluding struck rows loses
no signal at all: a struck gift that *did* capture was never reported anyway (the gateway answers
CAPTURED and the loop says nothing), so the only struck rows this report has ever named are the ones
the gateway could not confirm — which is precisely the case where striking the gift was correct.
There is no struck row whose reporting carries information, so "report but distinguish" would have
been a second display state for a set that is always noise.

That second failure is the **live defect reproduced on demand** — the unfixed tree really does name

**Why "three tests, two failures" is not a hole (the counting rule).** The third test in the control
selection, `reconciliationCatchesMismatch`, is the pre-existing one and it *should* pass in both
trees: it seeds no voided row, so the void clause cannot change its outcome. Its passing is the
acceptance criterion "a donation that stands and does not confirm is still reported, unchanged",
demonstrated on the unfixed tree and again on the fixed one.

**And on vacuity, which the brief was right to press.** Both new tests assert an absence, and an
absence passes for free if the whole feature stops working — so each carries a companion assertion
that goes red the other way:

- `reconciliationIgnoresAStruckGift` does not merely assert the struck id is missing; it asserts the
  list **equals** `[pay_bogus_standing]`. A reconcile that returned nothing at all fails it.
- `reconciliationDoesNotAskTheGatewayAboutAStruckGift` pairs `never()` on the struck id with
  `times(1)` on the standing id. A reconcile that asked nobody anything fails it.

Both went red without the fix, which is what the control shows, so neither is vacuous.

## Acceptance criteria

| Criterion | How it was verified |
|---|---|
| A voided donation in range is not reported as a mismatch | `reconciliationIgnoresAStruckGift` — passes fixed, fails on the unfixed tree with `was [pay_bogus_struck, pay_bogus_standing]` |
| No gateway call is made for it | `reconciliationDoesNotAskTheGatewayAboutAStruckGift` — Mockito `never()` on the spied `StubPaymentGateway`; fails unfixed with `NeverWantedButInvoked` naming `DonationReconciliationService.reconcile` |
| A standing, unconfirmable donation is still reported, unchanged | Pre-existing `reconciliationCatchesMismatch` passes in both trees, plus the standing row asserted present in `reconciliationIgnoresAStruckGift` |
| `./gradlew test` green for the tests touched | `OneTimeDonationIT` 10/10, `BUILD SUCCESSFUL in 8s` |

The seed strikes the row exactly as the product does — `voided_at`/`voided_by`/`void_reason` written
and `status` deliberately left at `COMPLETED` — so the test exercises a row `DonationVoidService`
can actually produce, rather than one invented to suit the fix. V104's two CHECK constraints
(`donations_void_attributed`, `donations_void_explained`) would have rejected a lazier seed anyway,
which is a small piece of evidence that the seed is faithful.

## Not done / needs Rajeev

**1. A second permanent unclearable mismatch of exactly the same shape, which I found and did NOT
fix, because fixing it would breach an explicit acceptance criterion and is an operator decision
rather than mine.**

Every **hand-recorded cash gift** is also reported as a mismatch on every run, for ever:

- `DonationRecorder:158` inserts a cash gift as `type = 'ONE_TIME'` with **no `provider` and no
  `provider_payment_id`** — its own comment says so: *"Neither sets `provider` — that is what tells
  the ledger a person, not a gateway, wrote this row."*
- `status` is not set, so it takes the `DEFAULT 'COMPLETED'` from V38:23.
- The reconciliation query excludes only `IN_KIND`, so it selects these rows and calls
  `fetchPaymentStatus(null)`.
- `StubPaymentGateway:40` returns `UNKNOWN` for a null id. `RazorpayPaymentGateway:149` is worse —
  it issues a real `client.payments.fetch(null)` over the network and returns `UNKNOWN` from the
  `catch`. So on a temple actually collecting through Razorpay, every cash gift ever recorded is one
  failed HTTP call and one permanent mismatch line per daily run.

I did not add `AND provider_payment_id IS NOT NULL`, though the file is in my contract, for two
reasons. It contradicts my brief's criterion *"a donation that stands and does not confirm at the
gateway is still reported, unchanged"* — a cash gift is exactly that. And it changes what an
operator's report says about money, which wants a decision, not a builder's guess: the honest
statement is probably that **reconciliation is a question about gateway-collected gifts and a gift
no gateway ever touched is not in its domain**, but that is a sentence for Rajeev to agree with
before it is code. It is a one-line change whenever he wants it, and it deserves its own task and
its own test.

**2. No hand smoke-test.** This surface has no screen of its own that I can drive — reconciliation
runs from a daily Quartz job and the super-admin ops page, against a tenant with real struck gifts
and real gateway credentials. I could not reproduce that by hand in this checkout, so the evidence
here is the integration test and the negative control only. What a human check would add, if wanted:
strike a gift on staging, run reconciliation from the ops page twice, and confirm the report stays
empty across both runs.
