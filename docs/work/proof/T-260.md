## Judgement calls (recorded as the task asked)

1. **When the client's quantity disagrees with the pack, the pack wins, silently.** The server stores `packCount × pack size` in the pack's unit and does not use the quantity sent with it. Why: the vendor is asked for "4 bags", so 100 Kg is what must be true. Refusing would need a new error code for a mistake the person never made (the screen did the sum). Trusting the client would let a stale box put 90 Kg into stock against an order for four bags. Test: `the pack decides the amount`.
2. **On a pack line, `unit` says what the expected price is per.** If the client's unit differs from the pack's (for example it sends gm and the pack is in Kg), the price is converted into the pack's unit. Example: ₹0.06/gm becomes ₹60/Kg. The client's unit still has to be in the ingredient's family (KMS-400013, as before). **Work manager:** send the line's price per the `unit` you send.
3. **A blank price is now filled from the list price converted into the line's unit.** Before this, `last_price` (per canonical unit) was copied as it stood, so tea kept in Kg at ₹400/Kg and ordered in gm got "₹400 per gm". Pack lines stored in the pack's unit make that common, so I fixed it for every line, not only pack lines. Test: `a pack line with no price takes the vendor's list price, converted into the pack's unit` (500 gm pack → ₹0.40/gm).
4. **A half-pair (a pack without a count, or a count without a pack) is `VALIDATION_FAILED` with a field error on "Line n".** No code was reserved for it, and this is a malformed request, not something a person does.
5. **`packLabel` is "Bag (25 Kg)", not the chip's "Bag = 25 Kg".** The document gives an order its own form ("4 × Bag (25 Kg)"). The existing chip helpers (`PackSizeService.label`, `VendorService.packLabel`) are package-private and write the chip form. So `PurchaseOrderService.packLabel` is a new three-line static built the same way, with the size through `Quantities.exact`. No unit word is written by hand, and UnitLabelAgreementTest passes.

## Defect found in V144 (outside my contract, not changed)

My own migration test caught a hole. A CHECK passes when it evaluates to NULL. With a pack and no count, `pack_size_id IS NOT NULL AND pack_count > 0 AND …` is NULL, so the row got in. V146 now spells out `pack_count IS NOT NULL`. **V144's `invoice_lines_pack_shape` on `vendor_invoice_lines` is written the old way and has the same hole:** a bill line with a pack and no count is accepted by the database. The fix needs a new migration (V144 is applied), so it needs a reserved version number. Reported here for the conductor.

## Acceptance criteria

1. **{packSizeId: Bag 25 Kg, packCount: 4} stores 100 Kg and reads back packLabel "Bag (25 Kg)", packCount 4.** Passes: `4 × Bag (25 Kg) is stored as 100 Kg with its pack, and reads back as the pack`. It checks the DB row (100, KG, pack, 4) and the API (`packLabel` "Bag (25 Kg)", `packCount` "4", `packQuantity` 25).
2. **Wrong-ingredient pack → 400 KMS-400162.** Passes: another ingredient's pack, another temple's pack, and a pack on a one-off line. Each also asserts that no order or line was written.
3. **0.0712 per gm round-trips with 4 places.** Passes: the DB reads `0.0712` and the API `expectedPrice` is 0.0712. The migration IT inserts 0.0712 as the app role and reads `0.0712`, and confirms the column is `14,4`.
4. **The sheet says "4 × Bag (25 Kg)" and the cooks' form rather than "2792 gm".** Passes, on the print HTML:
   - `>4 × Bag (25 Kg)<`, `>2 × 500 gm<` and `>3 Kg<` are present.
   - Neither "2792" nor "2,792" appears, and no rate ends "/ gm".
   - Rates read `>₹1500.00 / bag · ₹60.00 / Kg<`, `>₹200.00 / 500 gm · ₹400.00 / Kg<` and `>₹71.20 / Kg<`, with total `₹6598.79`.
   - The cook's form rounds 2.792 Kg to "3 Kg". The task allowed "or the cooks' form".
5. **Removing a pack used by a PO line → 409 KMS-400159.** Passes: PackSizeIT `a pack an order line was placed in cannot be removed`. The only thing referencing the bag is a draft order's line, and the pack is still there afterwards. The existing FK translation in `PackSizeService.remove` already maps any RESTRICT violation to KMS-400159, so the only code change there was its comments. The V146 FK is what makes the order line count.
6. **Existing data survives V146.** Passes: `ProcurementDataModelMigrationIT` `@Order(5)` snapshots `purchase_orders`, `purchase_order_lines` and `goods_receipt_lines` for both temples, migrates to V146, and compares:
   - every column byte for byte, except `expected_price`, which is compared by value (`trim_scale`, since 58.00 now prints 58.0000);
   - no existing line gets a pack.
