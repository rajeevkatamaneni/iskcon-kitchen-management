# T-064 and T-065 — the suite's context count and its "leak", both re-measured; one premise does not survive it

Both items were written weeks ago from a `jcmd` class histogram taken by hand. I measured both again
today before touching anything, and **neither reads the way the ledger has it**:

- **T-064's premise holds and its stated mechanism does not.** The suite builds **119** contexts, not
  106. But the `@Import` is not what splits the cache — Spring Boot detects the nested
  `@TestConfiguration` by itself. Doing the repair the ledger describes (re-point 99 `@Import` lines
  at one shared class) would collapse **nothing** and would look exactly like a fix.
- **T-065 does not reproduce as written.** The closed contexts are **softly** reachable, not held.
  With one JVM flag that tells the collector to treat soft references as expendable, the same run's
  retained contexts go from 12 to 2 and its live heap from 176 MB to 70 MB. Nothing is leaking them;
  the collector is keeping them because it has the room.

**I built neither repair.** T-064 is 99 test classes and it changes which classes share a context,
in a wave where every other task is verified by this suite. T-065 has no repair to build. What I
shipped is the instrument that produced these numbers, switched off by default, and a correction to
the forty lines of commentary in `build.gradle.kts` that state the old ones as fact.

### 3. T-064 — what actually splits the cache

The census computes each context's cache key three ways from the real `MergedContextConfiguration`:
as it is; with the `@Import` customizer removed; and with the nested `@TestConfiguration` classes
removed from `getClasses()` as well. On a 53-class subset (`meal`, `shift`, `donation`, `staff`,
`tenant`, `purchaseorder`):

```
  distinct cache keys:          53
  the same, ignoring @Import:   53   <- if every @Import named one shared class and nothing else changed
  ...and ignoring nested @TestConfiguration too: 8
```

And the keys themselves say why:

```
[org.iskcon.kms.KmsApplication, org.iskcon.kms.donation.DonationIntakeIT$StubVerifierConfiguration] | [] | [] | [spring.autoconfigure.exclude=...quartz.QuartzAutoConfiguration, ...SpringBootTestContextBootstrapper=true, server.port=0] | org.springframework.boot.test.context.SpringBootContextLoader | [...MockitoContextCustomizer#-208860145, ...]
[org.iskcon.kms.KmsApplication, org.iskcon.kms.donation.DonationLedgerIT$StubVerifierConfiguration] | ...
[org.iskcon.kms.KmsApplication, org.iskcon.kms.donation.DonationPeriodIT$StubVerifierConfiguration] | ...
```

The nested configuration is sitting in `getClasses()`, which is the *first* component of the key.
Spring Boot's `SpringBootTestContextBootstrapper` puts it there on its own: with no
`@ContextConfiguration(classes=…)` anywhere, Spring detects the leaf test class's nested
`@Configuration` classes, Boot sees they are all test components and appends the
`@SpringBootConfiguration` beside them. The `@Import` line next to it is redundant, and removing it
changes the key by nothing at all.

**This is the trap the brief asked me to watch for.** The ledger's plan — *"Hoist one shared
`StubVerifierConfiguration`/`StubTokenVerifier` and have the 87 import it"* — measured by a green
suite would look like a success and would have collapsed 53 contexts into 53.

Today's shape of the problem, counted:

```
$ grep -rl "extends AbstractIntegrationTest" backend/src/test/java/org/iskcon/kms | wc -l
     128
$ grep -rn "class StubVerifierConfiguration" backend/src/test/java/org/iskcon/kms | wc -l
      99
```

Of those 99 nested configurations, **97 are identical** once whitespace is normalised (the two that
are not: `tenant/MembershipIT` adds a stub `GeocodingProvider`, `shoppinglist/ShoppingListIT` adds a
statement recorder). Of the 99 nested `StubTokenVerifier` classes, **84 are identical**; the other 15
differ in ways that matter — a different phone number, an `acceptVerified`, a per-uid token, a
different rejection message.

### 5. T-065 — the retention, and why it is not one

The suspects were counted at every checkpoint. Three of them track the *live* context count exactly
and so are doing their job:

```
  Metrics.globalRegistry:            99 registries (67 of them already closed)
  SpringApplicationShutdownHook:     32 contexts held
  Quartz SchedulerRepository:        0 schedulers
  Hibernate SessionFactoryRegistry:  32 session factories
  live threads:                      47   (http-nio-auto x24, Catalina-utility x4, HikariPool x4)
  logback root appenders:            1 [ConsoleAppender], turbo filters: 0
```

Boot's shutdown hook, Hibernate's registry and Quartz's registry all release on close. Threads do not
accumulate. Logback does not accumulate. **Micrometer's global registry does** — it holds one closed
`MeterRegistry` per context ever built, 119 by the end of a full run, because Spring Boot closes a
registry on context close but never removes it from `Metrics.globalRegistry`. That is a real,
unbounded accumulation and it is worth fixing on its own — but it is not what holds the contexts,
which the route search settles below.

**The route search, with a control it must pass:**

```
  CONTROL — route from Spring's own cache to any context (must be found):
        Spring's own context cache (org.springframework.test.context.cache.DefaultContextCache)
        -> .DefaultContextCache#contextMap  (java.util.Collections$SynchronizedMap)
        -> .value[0]  (org.springframework.boot.web.servlet.context.AnnotationConfigServletWebServerApplicationContext)
        [9 objects examined; every link on this route is a strong reference]
  route from Metrics.globalRegistry to a closed context:
        no route found (11699 objects examined, graph exhausted)
  route from a live thread to a closed context:
        no route found (6000000 objects examined, budget spent)
  route from the logback LoggerContext to a closed context:
        no route found (9832 objects examined, graph exhausted)
```

The control is the part that makes the three "no route found" lines mean anything: a walker that
could not see would print exactly the same three lines. It finds a live context from Spring's own
cache in nine objects, so it can see.

**And then the experiment that settles it.** Same subset, same command, one JVM flag different,
with the context cache capped at 2 to make the closed ones cheap to weigh:

| after N contexts | default soft-reference policy | `-XX:SoftRefLRUPolicyMSPerMB=0` |
|---|---|---|
| 10 built — still reachable | 10 (2 running, **8 closed**) | **3** (2 running, 1 closed) |
| 10 built — live heap | **145 MB** | **73 MB** |
| 12 built — still reachable | 12 (0 running, **12 closed**) | **2** |
| 12 built — live heap | **176 MB** | **70 MB** |

`-XX:SoftRefLRUPolicyMSPerMB=0` changes one thing: it tells the collector to clear a soft reference
at every collection instead of keeping it in proportion to free heap. Under it, the closed contexts
go. **So they are softly reachable, not held** — which also explains, exactly, every other
observation in this investigation:

- `jcmd GC.class_histogram` compacts but does not clear soft references, so it shows them alive. That
  is where "81 live, 49 of them closed" came from.
- `System.gc()` does not clear them either, so the census sees them too.
- No *strong* route exists from any root, which is what the searches kept finding.
- T-062's own comment already recorded the other half of this without naming it: *"Squeezed into a
  smaller heap the same suite compacts to about 446 MB, because much of the rest is soft-referenced
  cache."* It is not just "much of the rest". It is the contexts as well.

**What holds them softly is still not named**, and I could not name it with what a Java program can
reach: the JVM hides `ClassLoader.classes` from reflection with or without `--add-opens`, so the
loaded classes cannot be enumerated without an instrumentation agent, and a walk from all live
threads runs past six million objects without exhausting the graph. Naming it needs a heap dump and
an analyser, which is what T-065 always said it needed. **What has changed is that naming it is no
longer the point:** a soft reference is the collector's memory-pressure valve working, not a defect,
and the way to stop the suite wanting a gigabyte is to stop it building 119 contexts.

### 7. Micrometer's accumulation, measured — and dropped on the number

The accumulation is real and I had not sized it, so I sized it. Same subset, same command, the
context cache capped at 2, run twice on each side; the only difference is
`-Dmanagement.metrics.use-global-registry=false`:

| run | live heap at JVM exit | registries retained |
|---|---|---|
| A1 — default | **167 MB** | 12 |
| A2 — default | **167 MB** | 12 |
| B1 — global registry off | **166 MB** | **0** |
| B2 — global registry off | **166 MB** | **0** |

```
--- mm-A1 (JVM exit) ---          --- mm-B1 (JVM exit) ---
  contexts built so far: 12         contexts built so far: 12
  live heap after that GC: 167 MB   live heap after that GC: 166 MB
  still reachable after a GC: 12    still reachable after a GC: 12
  Metrics.globalRegistry: 12 ...    Metrics.globalRegistry: 0 registries (0 of them already closed)
```

**The measurement checks itself**: the registry count going 12 → 0 is proof the property took
effect, so a "no difference" reading cannot be a flag that silently did nothing. And the retained
*context* count is 12 on both sides, which confirms what §5 found — the registry was never what held
them.

**So: 1 MB for 12 retained registries, about 85 KB each.** Extrapolated to a full run's 119
registries that is roughly **10 MB against a 1187 MB live set — under one percent.**

**Recommendation: drop it.** The leak is real, it is unbounded in principle, and it is immaterial
here. Shipping a one-line configuration change worth 0.8% would put a line in `AbstractIntegrationTest`
that nobody could later justify from its effect — and the way that ends is somebody copying
`management.metrics.use-global-registry=false` into production config a year from now because "it
helped in tests". If the suite ever builds thousands of contexts the arithmetic changes; at 119 it
does not.

**One near miss worth recording, because it is the same failure this task is about.** My first read
of the B2 number was **145 MB**, and I nearly reported a 21 MB spread. It was a mid-write value: the
census rewrites the whole report at every checkpoint, so I had read the ten-context checkpoint and
compared it against another run's exit figure. Reading the `at JVM exit` section explicitly gives
166 MB, twice. **Two numbers from the same file are not comparable unless they are the same
checkpoint**, and the tidy-looking difference was an artefact of how I read the file rather than
anything in the JVM.

## Not done, and why — this is the part that needs Rajeev

**T-064 was not built, deliberately.** Not because it is wrong — the payoff is real and measured, 9
contexts to 1 on one package, 53 to 8 on a six-package subset — but because of what it costs to do
safely:

1. It is **99 test classes**, and the edit is not the one in the ledger. The nested
   `StubVerifierConfiguration` and `StubTokenVerifier` have to be *deleted*, not merely re-imported.
2. It **changes which test classes share a context**. Eighty-odd classes that have each had a
   context to themselves would share one. Two application beans hold mutable in-memory state for the
   life of a context — `tenancy/InMemoryTenantSecretStore` and `payment/PaymentGatewayResolver`,
   both backed by a `ConcurrentHashMap` — and JUnit's class order is not fixed, so a cross-class
   effect would show up intermittently and somewhere different each run. **One green run would not be
   evidence**, and this is a wave in which every other task is being verified by this suite.
3. The 15 test classes whose stub verifier genuinely differs need reading, not scripting.

**My recommendation: schedule it as a wave of its own, alone**, with the transformation applied by
script, and accept it only on (a) the census showing 119 collapse to single figures and (b) three
consecutive full runs, not one. The control script here is a working version of that transformation
for one package, and the `staff/` result is what to expect per package.

**T-065 should be closed as "does not reproduce", not fixed.** There is nothing to repair: the
contexts are softly reachable and the collector releases them under pressure, which is what the
446 MB floor in `build.gradle.kts` already showed from the other side. The `2g` ceiling stays, for
the reason T-062 gave.

**Two things I am leaving, for a decision rather than because I ran out of time:**

- **Micrometer's global registry really does accumulate** — 119 closed `MeterRegistry` objects by
  the end of a full run — **and it is worth about 85 KB each, so I dropped it rather than shipping
  it.** §7 has the A/B: 167 MB against 166 MB, twice on each side, with the registry count going
  12 → 0 to prove the flag took effect. That is roughly 10 MB on a full run against a 1187 MB live
  set. Real, unbounded in principle, immaterial at this scale, and not worth a line of configuration
  nobody could later justify from its effect.
- **No hand smoke-test.** This task adds no user-facing surface — it is test infrastructure and a
  build comment — so Commandment 5's manual check does not apply and none was performed.
