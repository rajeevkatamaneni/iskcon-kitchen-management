# T-206 — voiding a vendor bill is refused while payments on it are not reversed

**Files changed:** (both inside the contract)

- `backend/src/main/java/org/iskcon/kms/invoice/VendorInvoiceService.java` — in the contract.
  `voidInvoice` now reads paid-to-date (the net sum of `invoice_payments`) straight after the
  already-voided check and before any write. If it is above zero it throws
  `ApplicationException(ErrorCode.INVOICE_HAS_UNREVERSED_PAYMENTS, {invoiceId, paidToDate})`. The
  figure it read is reused for the audit's before-state rather than read a second time. The javadoc
  paragraph that said payments are left in place is replaced with the reasoning for the refusal and
  for reading the net.
- `backend/src/test/java/org/iskcon/kms/invoice/InvoiceCorrectionIT.java` — in the contract. Four
  tests and two helpers (`invoiceJson`, `paymentsJson`); details below.
- `docs/work/proof/T-206.md` — this file.

Not changed, though in the contract: `VendorInvoiceIT.java` and `InvoicePaymentIT.java`. Neither
voids a bill that has payments, and both pass unchanged.

`ErrorCode.java` was not opened for editing. I read the reserved entry
(`INVOICE_HAS_UNREVERSED_PAYMENTS(400154, 409, ...)`) with grep/sed to confirm it was there, and used
it as given.

**How a reversal is recorded, and why the check reads the net.** `invoice_payments` is append-only
(V40, V49, V50). A reversal is a second row with the opposite sign whose `reverses` column names the
original (V103). A hand-entered compensating payment has the same negative shape without that link.
`SUM(amount)` treats both correctly, and it is the same `paidToDate` that `restateStatus` already
uses to decide PAID.

**Tests in InvoiceCorrectionIT**

- `voidRefusedWhilePaymentsStand` (new). It covers a bill paid in full and a part-paid bill. Each
  void gets 409 with `code` `KMS-400154`, and the `message` and `action` match the reserved text
  exactly. The whole `vendor_invoices` row (`row_to_json`) and every payment row (`json_agg`) are
  byte-identical before and after, and there is no `INVOICE_VOIDED` audit entry. The statuses stay
  PAID and PENDING. A third bill, paid twice with only one payment reversed, is still refused.
- `voidAllowedOnceEveryPaymentIsReversed` (new). Pay, void (409), reverse, void (204). The status is
  VOIDED, there is one audit entry, and the audit's `paidToDate` is `0.00`. A second bill paid ₹250
  and corrected with a hand-entered −₹250 also voids.
- `aStruckBillCannotBePaid` (reshaped from `aStruckBillStaysStruck`). The old test paid ₹200 and then
  voided, which is now refused, so it voids an unpaid bill and checks that a payment gets
  `KMS-400132`.
- `aReversalDoesNotBringAStruckBillBack` (the other half of the old test). The API can no longer set
  this state up, but bills struck before this change can still be in it on staging. So the test
  writes a voided bill with ₹200 paid directly, reverses through the API, and checks the bill stays
  VOIDED. That keeps the VOIDED guard in `restateStatus` tested.

**Frontend.** I checked, without editing, that the invoice screen already shows a server refusal's
sentence. In `frontend/app/invoices/[id]/page.tsx` the void dialog's `catch` calls
`toApiError(e, "We couldn’t void that invoice.")`. `toApiError` passes an `ApiError` from the server
straight through (`frontend/lib/api.ts`, its comment says so). `ErrorNotice` renders
`error.message`, `error.action` and `error.code`. So the Temple Admin will see "This bill has
payments that have not been reversed." / "Reverse the payments on this bill before voiding it." /
KMS-400154. No stop was needed.

Other callers checked: `VendorInvoiceController` only delegates. `GivingPageIT` voids with a direct
SQL UPDATE, not through the service, so this change does not reach it.

## After-UAT lines

- A payment recorded at the same moment as a void can still land on a voided bill, because neither
  `recordPayment` nor `voidInvoice` locks the invoice row. The fix is `SELECT ... FOR UPDATE` on
  `vendor_invoices` in both, and `InvoicePaymentService` was outside this contract.
- Bills already voided on staging with payments still standing are left as they are. Reversing
  those payments works and leaves the bill VOIDED (tested). Nothing lists them for anyone to find.
