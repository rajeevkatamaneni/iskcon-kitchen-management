# T-028 — Editing a shopping-list line stops nulling its vendor

`updateLine` wrote `suggested_vendor_id = ?` unconditionally on a `PATCH` whose two real callers
never send the field, so every include-box tick and every quantity edit nulled the line's suggested
vendor — silently, because the screen shows a blank vendor cell either way and the endpoint returns
`204`. The cost landed one step later: generation only picks up lines that have a vendor, so the
line quietly stopped being orderable.

One line in the service: `suggested_vendor_id = COALESCE(?, suggested_vendor_id)`, matching the
`suggested_qty` immediately beside it. `included = ?` was left unconditional deliberately — both
callers always send it and the column is `NOT NULL`, so an omission fails loudly rather than
destroying a value.

## The diff

```diff
-	/** A human edit — marks the line so a later regeneration leaves it alone. */
+	/**
+	 * A human edit — marks the line so a later regeneration leaves it alone.
+	 *
+	 * <p>This is a {@code PATCH}: a field the caller did not mention keeps the value it had. ...
+	 */
 	@Transactional
 	public void updateLine(UUID ingredientId, UpdateShoppingListLineRequest request) {
 		int updated = jdbc.update("""
 				UPDATE shopping_list_lines
-				SET suggested_qty = COALESCE(?, suggested_qty), suggested_vendor_id = ?, included = ?,
+				SET suggested_qty = COALESCE(?, suggested_qty),
+					suggested_vendor_id = COALESCE(?, suggested_vendor_id), included = ?,
 					edited = true, updated_at = now()
 				WHERE ingredient_id = ?
 				""", request.suggestedQty(), request.suggestedVendorId(), request.included(), ingredientId);
```

(The javadoc above the method was expanded to record *why* the coalesce is there and why `included`
is not; the elision above is only for brevity in this file. The SQL change is the two shown lines.)

regeneration writes vendors through its own `upsertLine` SQL, never through `updateLine`.

## Not done / needs Rajeev

- **No hand smoke-test.** The change has no visible surface — a correct `PATCH` looks identical to
  the broken one on screen (blank vendor cell, `204` back), which is exactly why the defect survived
  months in production. The only observable difference is downstream: after ticking an include box,
  the PO-generation count under the button no longer silently drops. Confirming that by hand needs a
  UAT deploy and a shopping list with a preferred vendor set; I did not deploy, and this wave's
  builders do not. Worth Rajeev checking on staging once this wave ships: regenerate the list, tick
  a box on a line that shows a vendor, and confirm the vendor name is still there and the generate
  count has not fallen.
- **The `included = ?` write is still unconditional**, deliberately and per the task. It is the same
  shape of bug in principle, but harmless in practice — the column is `NOT NULL`, so an omission
  raises rather than destroys. If a third caller ever PATCHes without it, it will fail loudly, which
  is the correct outcome. Left as-is; not a defect, recorded here only so nobody re-finds it and
  thinks it was missed.
- **The shopping-list screen was not opened.** It belongs to a later wave's task. It does not need a
  change for this fix — the point of putting the coalesce in the service is that the screen's
  existing partial `PATCH` becomes correct without touching it — but if that later task revisits the
  vendor cell, this is the behaviour it now inherits.
