# T-048 — the delivery events already pinned to the Gulf of Guinea are unpinned

V97 nulls `delivery_latitude`, `delivery_longitude` and `geocoded_at` on every row sitting at exactly
`0,0`, per tenant and under RLS, and leaves `delivery_place_id` standing so T-044's recovery path can
put the real pin back from Places by id.

## What the `WHERE` is, and how many rows it matched

```sql
WHERE tenant_id = t.id
  AND delivery_latitude  = 0
  AND delivery_longitude = 0
```

**Eight fixture rows were seeded across two temples. Three matched. Five did not.** Row by row, which
is the whole of the evidence I have for the predicate:

| Temple | Event | Seeded pin | Matched? | Why |
|---|---|---|---|---|
| gulf-temple | Poisoned pick | `0, 0`, place id `place-poisoned-a` | **yes** | both axes zero — the defect's exact signature |
| gulf-temple | Poisoned orphan | `0, 0`, **no** place id | **yes** | zeroes are false whether or not a place id sits beside them |
| gulf-temple | Genuine pick | `12.856230, 77.548110` | no | a real pin |
| gulf-temple | On the equator | `0.000000, 77.548110` | no | single zero — see the decision below |
| gulf-temple | On the meridian | `12.856230, 0.000000` | no | single zero |
| gulf-temple | Never located | `NULL, NULL` | no | `NULL` is not `0`; an unlocated event is not damage |
| second-temple | Poisoned pick | `0, 0`, place id `place-poisoned-b` | **yes** | the loop reaches the second temple too |
| second-temple | Genuine pick | `13.100000, 77.600000` | no | a real pin |

**Three of eight is a number about my own fixtures and nothing else.** I cannot count staging: its
database is on a private IP and reaching it needs a throwaway Cloud Run job on the VPC or Cloud SQL
Studio, which is not a builder's job — the coordinator is asking Rajeev for that figure. **The
migration is correct whatever the number turns out to be**, including zero: the `UPDATE` is
idempotent, matches on a value rather than a date or an id, and a run that clears nothing is a
successful run. Nobody should read "3" here as a claim about production.

Because that count is otherwise unrecoverable once the rows are repaired, the migration `RAISE
NOTICE`s its own total (`V97: unpinned N delivery event(s)...`). That is a best effort and the
comment says so — where a client notice ends up depends on `client_min_messages` and on what the
caller does with it, and I did not verify that Flyway surfaces it. It is one line and it beats losing
the number.

## The single-zero case — decided, not assumed

**A row with one zero axis and one real coordinate is deliberately left alone.** Argued at length in
V97's comment; the short form:

1. **It is not this defect.** The signature is both axes zero *together*, written as a pair by one
   line of client code. A repair migration should match rows it can account for.
2. **`0` is legal on each axis alone** — the equator, the Greenwich meridian. Only `0,0` *together* is
   provably not a delivery (a point in the Atlantic ~600 km south of Accra). We can prove the pair
   wrong; we cannot prove a single zero wrong.
3. **The decisive one: nulling it would change nothing the application does.** T-044's
   `isCoordinate()` already refuses zero on *either* axis, so a single-zero row is already unplaced,
   already stale, and already re-resolved on the next read — by place id where there is one, from the
   address otherwise. That is the identical behaviour it would have if V97 nulled it. The two options
   are indistinguishable to the running system and differ only in whether a stored datum is destroyed
   irreversibly. Given a tie, don't destroy evidence.

Two assertions pin that decision in place (`On the equator`, `On the meridian`), so a later tidy-up
of the `WHERE` into `latitude = 0 OR longitude = 0` fails the build rather than passing quietly.

**If Rajeev wants the other answer**, the change is one line and the test tells you exactly which two
assertions to flip. It is not a decision I would make on a builder's own authority in either
direction, which is why it is here.

## Acceptance criteria

1. **`0,0` cleared, place id untouched.** `pinOf("gulf-temple", "Poisoned pick")` reads
   `(none)|(none)|(none)|place-poisoned-a` — the two coordinates and `geocoded_at` gone, the place id
   standing. That pairing *is* the recovery: `isPlaced()` false → stale → re-resolved from Places by
   id, losslessly. Read straight off `meal_plans` through the superuser, never through an endpoint,
   so nothing can be surviving on a service re-resolving it on the way out. Also asserted: the
   address is unchanged and `updated_at` still equals the seeded `2026-09-05 09:15:00+05:30`, so the
   repair does not masquerade as somebody's edit.
   *And* `Poisoned orphan` — zeroes, no place id — is cleared too. That row is the one that shows
   which `WHERE` was written: the rejected "zeroes **and no** place id" filter would have cleared
   this one and left the recoverable one, precisely backwards.
2. **A real pin is untouched entirely.** `Genuine pick` reads
   `12.856230|77.548110|2026-09-05 09:15:00+05:30|place-real-a` in temple A and
   `13.100000|77.600000|…|place-real-b` in temple B — coordinates, timestamp and place id all as
   seeded.
3. **The single-zero case behaves as decided and the decision is justified in the migration
   comment.** `On the equator` (`0.000000|77.548110`) and `On the meridian` (`12.856230|0.000000`)
   both come through unchanged; V97's comment carries the three-point argument, including the one
   that decides it (T-044's `isCoordinate()` already makes them stale, so nulling changes nothing and
   only destroys a datum). A totals assertion — `count(*) WHERE latitude = 0 OR longitude = 0` — is
   exactly `2`.
4. **RLS and tenant boundaries, proved with more than one tenant.** Two temples, each with a poisoned
   row and a genuine one, following `TenantLoopMigrationIT` and `CateringMigrationIT`. The three
   failure modes this excludes all pass with a single temple in the database: a blanket `UPDATE`
   (fails closed under RLS, clears nothing, reports success), a loop that forgets `set_config`, and a
   loop that adopts only the first tenant. The test's own database is created with the schema owned
   by `kms_migrator` — unprivileged, `NOBYPASSRLS` — so a backfill that only works as a superuser
   fails here rather than on a temple.
5. **Applies cleanly on a fresh database and on one already at V96.** *At V96*: the test migrates a
   throwaway database with `target = "96"`, seeds it, then runs the rest — so V97's `DO` block is
   planned and executed against real rows at the schema version it was written for, which is the
   whole reason this class builds its own database (an empty one never plans a loop body; that cost a
   crash-looping deploy on V57). *Fresh*: every `AbstractIntegrationTest` boots a Spring context whose
   Flyway has just run the entire history, V97 included, against an empty database — all 19 tests
   above did so, and a broken migration would have failed at startup before any assertion ran.
