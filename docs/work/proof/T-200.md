## What Meta's docs say, as used

- **Resumable Upload** (https://developers.facebook.com/docs/graph-api/guides/upload)
  - Step 1 is `POST /<APP_ID>/uploads` with `file_name`, `file_length` and `file_type`, answering `{"id": "upload:<SESSION>"}`.
  - Step 2 is `POST /upload:<SESSION>` with `Authorization: OAuth <USER_ACCESS_TOKEN>`, `file_offset: 0` and the bytes, answering `{"h": "<HANDLE>"}`.
  - I send the token in the `Authorization: OAuth` header on step 1 too, not as the `access_token` query parameter the guide shows, so it never appears in a URL.
- **Template header** (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/components): `{"type":"HEADER","format":"DOCUMENT","example":{"header_handle":["4::YX..."]}}`.
- **Media upload** (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media): `POST /<PHONE_NUMBER_ID>/media`, multipart, with `file`, `type` and `messaging_product=whatsapp`, answering `{"id": ...}`.
- **Send**: the header component is `{"type":"header","parameters":[{"type":"document","document":{"id":<MEDIA_ID>,"filename":"PO-….pdf"}}]}`.
  - The T-182 ledger row quotes Meta's media object as taking "Either `id` or `link`".
  - I could not fetch Meta's send-template page (HTTP 500). The field names `id` and `filename` are from my own knowledge of the Cloud API. Staging will confirm them.

## Which sheet is sent

`latestReadySheet` sent the newest READY version whatever its language. Sheets are stored one row per version, each with a `language`: the vendor's preferred language by default, or one picked on the order screen for printing. `sheetToSend` picks, in order:

1. the newest READY sheet in the vendor's `preferred_language`;
2. otherwise the newest READY English sheet;
3. otherwise the newest READY sheet in any language;
4. otherwise, since the send-back, no sheet is READY, and one is rendered at the press, before the message is queued:
   - it renders the newest PENDING sheet, preferring the vendor's language, or asks for a new one with `DocumentService.requestPurchaseOrderPdf(poId, null)`, which uses the vendor's language;
   - it calls `DocumentGenerationService.generate(id)` synchronously, the same method the worker calls;
   - if the sheet is still not READY, or queueing or rendering threw, it throws `PO_SHEET_NOT_READY` (KMS-400155, 409).

FAILED is never chosen. The adapter still sends only a READY sheet, as the second line of defence.

**Why option 1 works inside the document design.**
- The PENDING row a draft transition inserts is uncommitted, so only the send's own transaction can render it before the message is queued.
- `generate` is written to run outside a transaction, because a read that throws inside one marks it rollback-only. Here that is the wanted outcome: any sheet that doesn't come out READY ends in the refusal, and the whole send rolls back. That covers the DRAFT transition, the queued sheet, the notification, the trail event and the audit entry.
- The worker's later job for the same row finds it READY and does nothing.
- Cost: pressing Send on WhatsApp with no READY sheet waits for one render. That includes translation of the sheet's labels for a non-English vendor.
- If the transaction rolls back after a successful render, the stored PDF object stays in storage with no row pointing at it.
