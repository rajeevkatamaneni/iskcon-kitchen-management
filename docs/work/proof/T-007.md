## Findings — reported, not fixed

### A. The cost-per-serving acceptance criterion is false, and I have pinned the true behaviour instead

`MealKindCostService:167` costs each dish at **`mp.target_yield`** — what was *planned* — and divides by the head count from `adults/children/seniors`. Its own comment at `:160` says so in as many words: *"The dish is costed at what was planned, not at what the returned job card said was cooked… a period of days must add up to the days in it."*

A correction moves `actual_servings` and `consumed_quantity`. It moves **neither** column that report reads. So "cost-per-serving recomputes from the corrected number" cannot be made true without changing a documented decision in a file outside this contract.

Rather than drop the criterion, I inverted it: `costPerServingIsUnmovedByACorrection` asserts the figure is **identical** before and after a 400→640 correction, with the reasoning in the test's Javadoc. If somebody later decides the report should follow the recorded figure, that test is what makes them notice they are making a deliberate change instead of hearing about it from a temple whose costs moved overnight.

### B. Who sums `actual_servings` / `consumed_quantity`, and what a correction actually moves

The brief asked for this as a finding. **Nothing in the product sums either column.** `grep -rn "actual_servings\|consumed_quantity"` over `backend/src/main/java` returns four hits: the `SELECT` and `MAPPER` in `MealPlanService`, and the `UPDATE` in `ServedMealService`. `TodayService:156` and two frontend files *display* `actualServings`; none aggregates it.

So a figure-only correction (400 → 640) changes **no aggregate anywhere in the application**. The only way a correction moves any computed figure is through **`status`**, when a dish's `notMade` flips — `COOKED ⇄ CANCELLED` — which moves it in or out of these six filters:

| Reader | Filter | Effect of a dish corrected to/from "not made" |
|---|---|---|
| `MealKindCostService:171` | `status <> 'CANCELLED'` | leaves/enters the cost report. Already true of recording; its `:155` comment anticipates it. |
| `MaterialsCostService:66` | `status <> 'CANCELLED'` | same, for the daily figure |
| `GivingPageController:101` | `status <> 'CANCELLED'` | today's plate count on the **public** page |
| `GivingPageController:190` | `status = 'COOKED'` | the 30-day **public cost-per-plate** denominator |
| `MealCrewService:147` | `status <> 'CANCELLED'` | the suggested-crew median |
| `MenuHistoryService:64,87` | `status <> 'CANCELLED'` | "what we cooked last Janmashtami" |

`SufficiencyService:166` and `ShoppingListService:398` filter `status = 'PLANNED'` and are untouched — a corrected dish is never `PLANNED`.

Each of those movements is *correct*: a dish that was never made did not feed anybody. I have changed none of them.

### C. A pre-existing defect in the public giving page — outside my contract, not fixed

`GivingPageController:190` computes the public cost-per-plate over the last 30 days with `mp.status = 'COOKED'`, and its denominator counts plates from `adults/children/seniors`, or `target_yield / per_head_qty` where no head count exists. **Both are planned figures. It never reads `actual_servings`.**

So a temple that recorded 400 and corrects to 640 has now formally stated that it fed 640 people, and the public figure — the one whose own comment says *"a made-up number here would be quoted back at them by a donor"* — will not move at all. This is not a defect I introduce; it predates the task. But shipping a correction feature makes it **visible in a new way**, because a Temple Admin who has just corrected a meal has a specific and reasonable expectation that the plate count follows. Worth its own task, and `donation/GivingPageController.java` belongs to nobody in this wave.

## Deviations worth naming

**A dish restated unchanged is left entirely alone.** The form restates the whole meal (a dish left out is refused, as when recording), but restating a figure is not changing it. The server compares with `compareTo`, not `equals` — `BigDecimal.equals` compares scale, so a form resending `400` against a column holding `400.000` would read as a change — and touches only the dishes that moved. Without this, every corrected meal would write a pair of ledger rows netting to nothing on each untouched dish, and would stamp `original_actual_servings` on dishes nobody corrected, so the planner would offer *"300 cooked, corrected from 300"*. `api.ts`'s comment on `originalActualServings` says "null on every dish of a meal nobody has corrected"; under this rule it is also null on an unmoved dish of a meal somebody **did** correct, which I believe is what that field is for but is a shade narrower than the sentence. Tested both ways (`anUnchangedDishIsLeftAlone`, and the frontend's "says nothing about a dish the correction did not move").

**A correction that changes nothing is refused** (`KMS-400001`), rather than recorded. Otherwise it badges the meal as corrected and puts a name and an hour against a change nobody made.

**Correcting a meal that was carded but never recorded returns `KMS-400030` (`RESOURCE_NOT_FOUND`), not a code of its own.** It is reachable — a `meal_services` row exists as soon as a job card is printed. `MEAL_NOT_RECORDABLE` was wrong (it says a *cancelled* meal never went to the kitchen). What is missing is the recording, so `RESOURCE_NOT_FOUND` with `{"mealServiceId": …, "missing": "recording"}` in the log detail. **If Rajeev wants a dedicated code with a next step that names the recording form, that is a reservation I did not have and did not take.**

**`corrected_by` is `ON DELETE SET NULL`, not `RESTRICT`.** It mirrors `recorded_by` on the same table rather than `donations.voided_by`: a struck donation is an 80G record whose author may have to be produced; a corrected meal is operational, and a temple removing a departed admin should not be blocked by a lunch from last March. The CHECK therefore pairs `corrected_at` with `correction_note` and deliberately **excludes** `corrected_by` — pairing it would make the foreign key's own UPDATE violate the constraint, and the user deletion would fail at a baffling distance.
