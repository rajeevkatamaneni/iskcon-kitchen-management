## Item 1 — the 114, fixed in one place

**Where.** `backend/src/test/java/org/iskcon/kms/testsupport/TestStaffRecords.java`, called from
`StubTokenVerifier.verify`.

**Why there.** There is no shared helper that makes a test user: I grepped, and **160 test files write their own
`INSERT INTO users`**, each with a private `insertUser`. The single place every one of them passes through is the
token verifier. So when a test signs somebody in and that account is Kitchen Staff or Kitchen Manager with no
employment record at all, the suite writes the record a real one would always have — ACTIVE, in a kitchen of that
temple that is open and uses the planner, `kitchen_needs_check = false`, and **no schedule template**, so the
person is rostered for no hours and appears in no crew figure.

**The rule is not weakened.** `PlannerKitchenGuard` and `KitchenOrder.mayPlan` are untouched, and
`PlannerKitchenAccessIT` — the class whose subject is exactly the people who should be refused — switches this
off for itself and still proves all nine cases.

**Three things it deliberately does not do**, each of which broke something when I tried it:

1. **It never creates a kitchen.** A temple with no open planner kitchen is left alone. Creating one changed what
   `OwnAccountsAtOtherTemplesIT` counts (`SELECT count(*) FROM kitchens` must be zero after a refused create).
2. **It never touches an existing employment record**, of any status, so "a former employee has no planner" still
   tests that.
3. **It takes its own rows away again**, after the test body and *before* the test class's own `@AfterEach`. This
   one is the load-bearing detail and it is why the cleanup is an `AfterTestExecutionCallback` registered on
   `AbstractIntegrationTest` rather than an `@AfterEach`: JUnit runs a **subclass's** `@AfterEach` first, so a
   teardown written in the base class would run *after* the test class's `DELETE FROM users` — and
   `staff_profiles.user_id` is `ON DELETE RESTRICT`. Measured, not reasoned about: without the callback,
   `MealPlanIT` failed 19 of 20 with
   `ERROR: update or delete on table "users" violates foreign key constraint "staff_profiles_user_id_fkey"`
   in its teardown, and the leaked tenant then failed the next test with `duplicate key value violates unique
   constraint "tenants_slug_key"`.

**Two per-file fixture lines were still needed, and both are honest gaps rather than exceptions to the rule:**

- `JobCardIT.setUp` now seeds the temple's kitchen (`MealFixture.plannerKitchen`). Its temple had no kitchen at
  all until a meal was planned, and the test *"a meal nobody planned has no card"* plans nothing — so there was no
  planner kitchen to put its cook in and the request was refused 403 instead of 404. Every real temple has a
  kitchen from the moment it is provisioned.
- `JobCardIT.rosterStaffOnTheDay` is now an upsert. That cook *is* the account the class signs in as, so on the
  tests that print a card before rostering anybody, the suite has already given them a bare record and the second
  insert hit `staff_profiles_one_per_user`.

**No assertion was changed for item 1.** The only assertions I changed anywhere are the three "Planned crew" →
"People needed" strings, which are the point of item 4.

## Not done / needs Rajeev

- **The leave line names the kitchen on every meal, including a meal cooked by one kitchen.** T-358 asked for it
  "only when the meal has more than one kitchen", and the screen cannot tell: `MealCrewService.crewIfAway` sends
  **one line per affected section** with only that section in `kitchens`, and the meal-level figures on that line
  are that same section's — so `kitchens.length` is always 1 and nothing in the payload counts the meal's
  kitchens. Adding a count would need a field on `MealCrewView` and on `frontend/lib/api.ts`, neither of which is
  mine, so I did not widen the contract. What ships: a one-kitchen temple reads "Lunch (Main kitchen) on 7 Sep at
  4 of 6", which is redundant but true; a two-kitchen temple reads the kitchen whose numbers those are, which is
  the case the change exists for. **Raising it rather than leaving it silent — if the redundancy is not wanted,
  the fix is one field.**
- **The job card's staff list is now narrower than it was, and that is deliberate.** Before, it printed everybody
  working that day; it now prints the people that kitchen's section counts, which excludes somebody whose hours
  end before the food is due. That is the same person the planner already leaves out of "4 of 6", and the whole
  point of item 4 was to make the sheet agree with the screen — but it is a visible change to a printed document
  and it is not only about kitchens, so it is called out here.
- **Volunteers are unchanged: every kitchen's card lists the day's volunteers.** A shift is posted for a meal or a
  stretch of the day, never for a kitchen, so there is nothing to filter on. T-358 flagged the matching assumption
  on the crew figures (volunteers counted once, in the main kitchen's section) as still waiting on Rajeev.
- **No hand smoke-test in a browser.** Everything here is backend plus one line of a React page; no server was
  started in this worktree and I did not drive Chrome. The nearest thing is the rendered HTML the job-card tests
  assert against, which is real output from the real endpoint. T-359 is the wave's live-measurement task.
- **A note for whoever reads the test suite next.** `StubTokenVerifier` now writes to the database on the first
  request of each test made with a given uid. It is documented at length in `TestStaffRecords`, but it is a new
  thing for a stub to do, and a test that needs a Kitchen Staff account with no employment record must say so with
  `withoutAutomaticStaffRecords()`.
