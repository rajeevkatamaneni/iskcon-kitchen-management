## The gap that was real

`README.md:46` told every developer to run `DB_MIGRATION_USER=kms DB_MIGRATION_PASSWORD=kms` — the
compose **superuser**. `FlywayMigrationRoleConfiguration` hands Flyway its own plain DataSource built
from those two values, so Flyway connected as a superuser locally while `./gradlew test` and Cloud SQL
migrated unprivileged. `grep -rn kms_migration` found the role in the init script, in Terraform and in
the test harness — and in no local workflow at all.

Two consequences, both demonstrated live below:

1. **A migration's seed or backfill sees every temple's rows locally and none of them anywhere else.**
   That is the divergence that would let a sweeping backfill pass locally and misbehave on staging.
2. **Ownership.** Flyway's connection decides who owns the 86 tables and the four `SECURITY DEFINER`
   functions. Locally that was the superuser `kms`; in tests and production it is `kms_migration`.

**The application itself was never affected either way** — it connects as `kms_app`, and `FORCE ROW
LEVEL SECURITY` applies to it regardless of who owns the table. I show that too, so the scope of the
defect is not overstated.

## The ownership questions the brief asked, answered

**Who owns the tables when Flyway runs as `kms_migration`?** `kms_migration`, all 86 of them, plus all
12 `public` functions. Measured, not assumed:

```
$ docker exec kms-t145-pg psql -U kms -d kms -c "
  SELECT DISTINCT pg_get_userbyid(relowner) AS owner, count(*)
  FROM pg_class WHERE relnamespace='public'::regnamespace AND relkind='r' GROUP BY 1;"
     owner     | count
---------------+-------
 kms_migration |    86
(1 row)
```

**Is `GRANT ALL ON SCHEMA public TO kms_migration` sufficient for all the migrations?** Yes. All 123
migration files, up to version 126, applied clean as the unprivileged role on an empty database:

```
$ docker run --rm --network kms-t145-net \
    -v .../db/migration:/flyway/sql:ro flyway/flyway:10-alpine \
    -url=jdbc:postgresql://kms-t145-pg:5432/kms \
    -user=kms_migration -password=kms_migration migrate
...
Migrating schema "public" to version "125 - the lead time the order went out under"
Migrating schema "public" to version "126 - closing a part delivered order"
Successfully applied 123 migrations to schema "public", now at version v126 (execution time 00:00.850s)
```

(The brief said 126 migrations; it is 123 files whose highest version is `V126`. Three numbers are
unused.)

**Does anything in the schema depend on the owner being a superuser?** No — and several migrations say
so in their own comments, which is why nothing had to be worked around. `V65:200` states *"the
migration role is not a superuser and holds no right to create one"*; `V107`, `V110` and `V124` each
carry a note about making sure *"a migration which only works as a superuser fails in the suite"*.
There is no `CREATE EXTENSION`, `ALTER SYSTEM`, `CREATE EVENT TRIGGER`, `CREATE ROLE` or server-side
`COPY FROM` anywhere in `db/migration`.

**What does change with the owner** are the four `SECURITY DEFINER` functions, since they run *as*
their owner:

```
 delete_tenant_cascade | kms_migration      vs.      delete_tenant_cascade | kms
 tenant_user_count     | kms_migration               tenant_user_count     | kms
 match_employment_bans | kms_migration               match_employment_bans | kms
 employment_ban_...    | kms_migration               employment_ban_...    | kms
```

Owned by a superuser they are exempt from RLS outright, so the lift that `V45`/`V46` exist for is
never exercised locally — `V45:10` already says as much: *"there the function runs as a superuser,
which never needs the lift at all."* Same for `tenant_user_count`, whose whole design (`V102:41`)
turns on it being *filtered* as the migration role. Fixing the migrator makes those local paths the
production ones.

On the FK point in the brief: `V49`'s comment is the authority here since it was written from a real
failure, and it says the `FOR KEY SHARE` check *"runs with the privileges of whoever issued the
delete"* — the caller, not the owner. That is why append-only is a trigger keyed on
`current_user <> 'kms_app'` rather than a revoke, and why it is unaffected by who owns the table. I
did not need to work around it.

## The live demonstration

Throwaway database `kms-t145-pg`, `postgres:16-alpine`, port **55433**, its own network
`kms-t145-net`, an anonymous volume. **Rajeev's `kms-postgres` container and its
`kitchen-management-system_kms-postgres-data` volume were not touched, and `docker compose down -v`
was never run.** Seeded with three temples; only Sri Mayapur has picked a theme, which is the shape
that produced the 2026-09-05 symptom. `tenant_settings` rows were inserted **per tenant**, with that
temple's id adopted on the session, because as `kms_migration` the insert is subject to RLS.

### A developer with an existing volume, plainly

Their tables are owned by `kms` and **changing the variable will not re-own them** — Postgres re-owns
nothing on a later connection. They must either drop the volume
(`docker compose down -v && docker compose up -d`, which loses their local data) or run the re-own
block above as `kms` once. Both are in `README.md`. Rajeev's own `kms-postgres` volume is in this
position: it was created before today, so his next `bootRun` with the new command will migrate fine
but leave his existing 86 tables owned by `kms` until he runs one of the two.
