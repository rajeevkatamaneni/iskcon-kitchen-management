## Sites 7, 9 and 10 in detail

**7, Take them back on.** The panel was `<div role="group" aria-label="Take them back on">` in
`app/staff/[id]/page.tsx`, and the button called `api.reinstateStaff` from `onClick`.

It now lives in its own component, `components/staff/Reinstate.tsx`, the same way `BanRecord` and
`ConductNotes` sit on that screen. The component holds the opener, the four fields and
`<Form aria-label="Take them back on">`. The page keeps the decision of whether it is offered (only
for someone who has left, and not while a ban stands) and makes the call:
`<Reinstate lastWorkingDay busy onReinstate={(input) => void run((t) => api.reinstateStaff(staff.id, input, t), …)} />`.
The input type is `Parameters<typeof api.reinstateStaff>[1]`, so no type was added to `lib/api.ts`.
The page lost its four reinstate state hooks, the `FIELD` constant and its `Form` and `SystemAccess`
imports, and holds no `type="submit"` or `onSubmit=` any more.

The button is `type="submit"` and `disabled={busy}`; "Leave it" stays a plain button. The date box already had `required`; now it is read. A blank press shows
"What day did they come back? is required" beside the date, with `aria-invalid` and
`aria-describedby`, and nothing is sent. The handler keeps `if (rejoinedOn === "") return` as the old
guard's twin. Side effect: Enter in the reason box now submits, as on every other form. The two
existing reinstate tests queried `getByRole("group")`; they now query `getByRole("form")`, with no
other change. Test: `staff-reinstate` "names a blank return date when Take them back on is pressed,
and sends nothing until it is given".

**9, Give.** What Enter did before the change: nothing, for a 0, negative or non-number amount. The
form's default button is Give (the preset buttons are `type="button"`), and the HTML spec says
implicit submission fires only if the default button "is not disabled", so a disabled Give meant
Enter did not submit. So Enter could not send a bad amount; the disabled button really was the only
guard, and it said nothing. I could not show this in a test: jsdom 25.0.1 does not implement implicit
submission (`grep -rn "implicit submission\|\"Enter\"" node_modules/jsdom/lib` finds nothing). No
real-browser check either.

The rule now on the box: `type="number" min="1" step="1"`, keeping `inputMode="numeric"`, still not
`required` (blank means the preset is the gift). Why: `type="number"` is what makes `min` work. The
box already opened a numeric keypad with no decimal point, and every preset is whole rupees, so
`step="1"` states what the page already assumed. The server refuses anything not above zero
(`AccountDonationRequest`: `@Positive`, "A gift has to be more than zero."), and the smallest whole
rupee above zero is 1. A 0 or -5 now shows "Or another amount must be at least 1" beside the box and
nothing is sent. Letters: a browser that allows typing them reports `badInput`, which `Form` names as
"must be a number". `submit` keeps `if (given <= 0) return`.

**10, Record this correction.** It was `<section aria-label="Correct …">` with a button calling
`save` from `onClick`, and the reason input had no `required`. It is now `<Form aria-label="Correct …">`,
the reason input has `required`, the button is `type="submit"` with `disabled={busy}`, and Cancel
stays a plain button. `save` takes the event and returns on a blank trimmed reason. A blank press
shows "Why the figures are being changed is required". Side effects, both from rules already on the
boxes: a Consumed figure above Cooked (`max={entry.cooked}`) or a negative figure (`min={0}`) is now
refused by name on submit, where before it was sent. Enter in a box now submits. No page wraps
`MealServices` in a form (checked `app/planner/page.tsx`, `app/planner/catch-up/page.tsx` and
`DayView.tsx`), so no forms are nested. Test: `meal-correction` "refuses to send until a reason has
been given, and names the blank reason when pressed".

## The two blockers, and how they were fixed

Both are fixed under the contract the dispatcher widened on 2026-09-13. It granted the slice D test
(Save note only) and a new `components/staff/Reinstate.tsx`, and it ruled that `design-system.test.ts`
and its design rule stay unchanged. What was found is kept below as written, then what was done.

**Done:** (1) the slice D test now presses Save note, see "Tests changed". (2) Option (a): the panel
moved to `Reinstate.tsx`, see site 7. `design-system.test.ts` went green through the move alone
(21/21 in the targeted run), with no change to it.

**1. `frontend/__tests__/blank-submit-slice-d.test.tsx:404-415` was not granted, and it asserts the
button this task enables.** Its own comment says so: *"Save stays disabled until something is typed…
T-172 owns that button; until then the form is submitted directly."* The fix is the same one made in
`staff-conduct-notes`: `toBeDisabled()` becomes `toBeEnabled()`, and `fireEvent.submit(form)` becomes
a click on Save note. Nothing else in that test changes. It is a one-line grant the task's list
missed. I did not touch the file.

**2. `frontend/__tests__/design-system.test.ts` fails on site 7 (Take them back on).** It reads
source text. On any file with `<FocusScreen`, every `type="submit"` must sit inside the `actions`
prop, and a file with `type="submit"` or `onSubmit=` must not say `Close`. The staff record screen
is read-only, so its header says Close. The reinstate panel is now a `Form` in the body of that same
file, so both rules fire. The page's other forms, the ban correction in `components/staff/Ban.tsx`
and the conduct note in `components/staff/ConductNotes.tsx`, don't trip them only because they live
in their own files.

I did not dodge the check, for example by spelling the button type another way, because that would
hide exactly what the rule looks for. The two honest fixes both need a path I don't have:
- **(a) Move the reinstate panel into its own component**, e.g. a new `components/staff/Reinstate.tsx`,
  mounted from the page as `BanRecord` and `ConductNotes` already are. The rules then hold as
  written, and this matches how the same screen already carries its other two forms. **Recommended.**
- (b) Change `design-system.test.ts` to allow a form inside a panel on a read-only record. That
  loosens a design rule, so it is Rajeev's call and not a builder's.

Until one of those is granted, site 7 stays in the tree as built and the full run stays red on these
two tests. Undoing site 7 would leave its required date unnamed again, which is the defect this task
exists to fix, so I did not undo it on my own.
