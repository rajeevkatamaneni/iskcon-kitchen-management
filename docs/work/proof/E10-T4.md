**What V160 creates**

- `assistant_conversations` (id, tenant_id, user_id → users, title nullable ≤ 200, created_at, updated_at).
- `assistant_runs` (id, tenant_id, conversation_id, user_id, model, status, started_at, finished_at,
  duration_ms, input_tokens, output_tokens, notional_cost_usd NUMERIC(12,6), tool_calls, error_code).
  Status `RUNNING | SUCCEEDED | FAILED | TIMED_OUT`; CHECK that RUNNING has no finish fields and every
  other status has finished_at and duration_ms; counts non-negative; error_code only on FAILED/TIMED_OUT
  and only in `KMS-nnnnnn` form.
- `assistant_messages` (id, tenant_id, conversation_id, role `USER | ASSISTANT`, content, run_id nullable,
  created_at). A USER message carries no run_id.
- `assistant_pending_actions` (id, tenant_id, conversation_id, run_id, kind `SHOPPING_LIST |
  STOCK_ADJUSTMENT`, payload jsonb, payload_sha256 (64 lowercase hex), idempotency_key UNIQUE per tenant,
  status `PROPOSED | CONFIRMED | REJECTED | EXPIRED`, expires_at > created_at, decided_by, decided_at,
  created_at). CHECK: PROPOSED undecided; CONFIRMED/REJECTED have decided_by and decided_at; EXPIRED has no
  decided_by.
- All four call `enable_tenant_rls()`. Links between them are composite keys on (tenant_id, id), the V149
  meal_series pattern, so a cross-temple link cannot be stored even though FK checks bypass RLS.
  user_id/decided_by are plain FKs to users, like every other table (users has no (tenant_id, id) key and
  adding one to a shared table is out of scope).
- Indexes: conversations (tenant_id, user_id, updated_at DESC); messages, runs and actions by
  (tenant_id, conversation_id, created/started_at); runs also (tenant_id, user_id, started_at) and
  (tenant_id, started_at) for the per-user and per-tenant daily budgets.
- No GRANT needed: V1's default privileges give kms_app SELECT/INSERT/UPDATE/DELETE on new tables.
- Tenant purge needs no entry: `delete_tenant_cascade` (V86) finds tables by tenant_id and retries; there
  is no FK cycle among the four. TenantDeletionIT still passes.
- Values are uppercase enum names, as in every other status column (plan writes them lower case).

**Append-only choice**

- `assistant_messages`: append-only via `make_append_only()` (the V49 trigger, not a revoke). A transcript
  is a record, and the assistant's reply is written once when its run finishes, so nothing in the planned
  flow edits a message.
- `assistant_runs`: not append-only. The row is written RUNNING at start so the daily budgets count runs
  still in flight (a row written only at the end would let simultaneous messages all pass a budget), and is
  finished in place. Consistency is held by CHECKs instead.
- `assistant_pending_actions`: not append-only; it moves PROPOSED → one decision. Its integrity comes from
  payload_sha256 being re-checked at confirm.
- `assistant_conversations`: not append-only; title and updated_at change.

**Acceptance criteria**

- Four tenant-owned tables, each with `enable_tenant_rls()`: `everyTenantOwnedTableIsProtected` (which
  discovers tables by their tenant_id column, so there is no list to add to) passes with the four present.
- Tenant A cannot see B's rows: `assistantTablesAreIsolated` seeds a conversation, run, two messages and a
  proposal per temple and asserts, through the unprivileged app connection, that each temple sees exactly
  its own ids, no context sees none, and A's unfiltered UPDATE/DELETE of B's rows affect zero rows.
- Cross-temple links refused: `assistantTablesRefuseCrossTempleLinks` asserts the composite-key constraint
  names in the error for a message → B's conversation, a reply → B's run, a proposal → B's run, and the RLS
  WITH CHECK for a conversation attributed to B.
- Append-only and run finishing: `assistantMessagesAreAppendOnlyAndRunsFinishInPlace` asserts kms_app's
  UPDATE and DELETE on a message are refused ("append-only"), a RUNNING run can be finished in place, and
  turning a finished run back to RUNNING is refused by `assistant_runs_finish_matches_status`.
- Migration replays with a temple present: `TenantLoopMigrationIT` passes (V160 writes no rows).

  migration. Deliberate, matching the rest of the schema.
- Messages being append-only means a conversation cannot be deleted by the app. If Rajeev wants people to
  be able to delete their chats (they may name people), that needs a deliberate path later.
- No user-facing surface, so no hand smoke test applies.
