## What `KMS-400020` already says, and why its words are not the words used

`ErrorCode.java` was **not opened for editing** — the declaration was read via `sed` on three lines
and nothing in the file was touched. It reads:

```java
NO_ACCOUNT_AT_TEMPLE(400020, 401,
        "You're signed in, but you don't have an account at this temple yet.",
        "Ask your temple administrator to add you."),
```

Two findings about it, and the second is why its wording was not reused verbatim:

1. **It is rendered nowhere.** `frontend/lib/auth-context.tsx:131` keeps the code only, maps it
   through `REFUSALS` to the status `no-account`, and drops the message and the action. So the
   sentence "may already exist and simply never be reached from the register screen" is true in a
   stronger form: it is never reached from **any** screen. Reusing it here would not be reuniting
   somebody with a wording they had already met.
2. **Its next step contradicts what this person will actually meet.** `KMS-400020` says *"Ask your
   temple administrator to add you."* But `no-account` lands on `/choose-temple`
   (`app/page.tsx:35`, `components/RequireRole.tsx:171`), which asks *"Which temple do you serve
   at?"* and carries `JoinTempleForm` — self-join, no administrator, no approval step
   (`components/JoinTempleForm.tsx` calls `api.joinTemple` directly). Telling the stranded person
   to go and ask an administrator would have replaced one dead end with a slower one.

**Flagged rather than fixed, because `ErrorCode.java` is reserved:** `KMS-400020`'s own action line
looks stale for the same reason — the product lets that person join themselves. If you want it
amended, the wording I would propose is *"Choose your temple to join it."* — but I have not touched
the file and this is a note, not a change.

## Ask the server, or make the sentence true for both? — the sentence, and why

**Chosen: make the sentence true for both readers. No server call, no new endpoint, no backend path
used.**

- **The screen has no token to ask with.** The branch is reached because
  `createUserWithEmailAndPassword` *failed*. There is no credential, so `/whoami` — the one call
  that knows about membership — cannot be made.
- **The only question askable from there is an enumeration oracle.** "Does this email have an
  account at this temple?", asked by anybody, about anybody, from a signed-out screen. That is
  precisely the answer this product already refuses to give: the comment above `SignInPage` says so
  in as many words — *"Saying 'no account with that email' tells anyone who asks which addresses are
  registered at a temple"* — and `EmailSignIn` deliberately does not distinguish a wrong password
  from an unknown account. Adding the oracle on the register screen would take back on one screen
  what the neighbouring screen refuses on purpose.
- **No such endpoint exists.** `grep -n "joinTemple" frontend/lib/api.ts` finds the join; there is
  no lookup-by-email anywhere in `api.ts`. So this would have been a new endpoint, and the contract
  says stop and report before adding one. It was not needed.
- **And the lookup buys less than it costs.** Both people's next action is the same — sign in. What
  differs is only what happens *after*, and the app already handles that correctly: `no-account`
  lands on the temple picker and they join themselves. The old sentence's fault was not that it
  gave wrong advice; it was that it **stopped one step early**, so the second person's screen looked
  like a rejection instead of a step.

## The copy

```
There is already an account with that email. Sign in instead. If you aren’t on ISKCON Mysore’s
list yet, signing in will ask which temple you serve at, and you can join from there without
registering again.
```

The temple is the one they picked at the top of this same form (`temple.name`, passed in; the
fallback "the temple’s list" covers a null that the disabled button makes unreachable).

- **Person A — registered here, forgot.** Reads their complete answer in the first two sentences,
  which are unchanged and come first. The rest is conditional on something they know is not their
  case.
- **Person B — Firebase identity, no membership.** Learns that signing in is not a return to the
  start: it asks which temple they serve at, and they can join there. Which is exactly what
  `/choose-temple` does.

No new `KMS-` code: this is a Firebase failure translated on the client, and the existing branch
carried no code. Nothing technical is shown — the test still asserts `auth/email-already-in-use`
never reaches the screen.

**The failure count needs its explanation, per lesson 4's counting rule: one, not two, is correct.**
Two tests were written for the two people, and only one of them *can* go red without the fix. The
other — *"still tells somebody who genuinely has an account already to sign in instead"* — asserts
the sentence that the **old** code also produced, deliberately: it is the invariant the fix must not
break, so it is green in both states by construction. That is what makes it useful. If a later
change answers the stranded person by deleting *"Sign in instead."*, the new test stays green and
**that** one goes red. The pair only works with both halves present, which is why the control's red
is one test and not two.

The received line also shows the control genuinely reverted the behaviour rather than merely
touching the file: the screen printed the **exact pre-T-114 sentence**.
