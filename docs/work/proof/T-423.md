# T-423 — A counted thing cannot be a fraction: the rule, and every server door

The rule lives in `ingredient/IngredientUnits.java` beside `requireSameFamily`, and is called at
**every server door across sixteen services**, plus the ledger's own last line of defence. Nothing measured in a
`Unit.Family.COUNT` unit can be entered as a fraction any more. No migration, no new error code, no
new permission, no frontend file.

**Scope note, decided mid-task and agreed with the coordinator:** a second brief arrived widening
T-423 to the *scaling* path — the fractions the application produces for itself (Banana 16.78,
Coconut 400.98). **I declined it and did the entry-doors half only.** Two reasons: the scaling half
is seven more consumer services plus a decision that moves money (cost per serving), and landing a
validation rule and a money change in one unreviewed tree means a red suite tells nobody which half
did it. The coordinator agreed and will dispatch it as its own task. Four findings handed over for
it are in **Not done / needs Rajeev** below.

## Where the rule lives, and why there

`IngredientUnits`, not `Quantities`. Three reasons, in order of weight:

1. **It is the same question the file already answers.** `requireSameFamily` is "may this quantity be
   said about this ingredient at all". "Is this number one the thing can be in" is the next sentence
   of the same paragraph, and both refuse a *write* and are silent on a *read*.
2. **`find()` is already there.** The ingredient-keyed form needs the ingredient's name and its
   canonical unit, which is exactly what `find()` returns. Anywhere else would be a second copy of
   that query.
3. **`UnitLabelAgreementTest` holds a fixed allow-list of every file that may read `Unit.label()`**,
   and `IngredientUnits.java` is already on it. Putting the message anywhere else adds a file to
   that list for no gain.

`Quantities` is display-only and says so in its own javadoc; a throwing validator in it would be a
second kind of thing in a file whose whole point is that it renders and never refuses.

### Two layers, and the layers ask about different numbers

The brief asked for the door and the ledger. That is what is built, but **the ledger's layer is
scoped, and this is the single most important design decision in the task.**

`StockMovementService.validate` is the choke point for eight write paths. Four of them hand it a
figure a person typed. **Three hand it a figure the application worked out**, and those are
legitimately fractional against a counted ingredient:

- `CONSUMPTION` and `USED_BEYOND_RECORDED_STOCK` — a recipe scaled to 12 L genuinely needs 2.4
  coconuts.
- `ISSUE` — FEFO splits a requirement across batches, so handing over **five whole aprons** out of
  lots holding 2.5 and 86 posts a **2.5** movement.

An unconditional check there would have refused both. Worse, it would have made the fractional rows
already on staging *undrawable* — the application unable to work around the data acceptance
criterion 7 says it must work around. So the ledger asks only of
`{PO_RECEIPT, DONATION_IN_KIND, RETURN_TO_VENDOR, ADJUSTMENT}`, and issuing, cooking and meal
recording are gated at their own doors on the figure the person actually typed. There is a test for
this (`theLedgerLeavesTheApplicationsOwnArithmeticAlone`).

`compensate` is untouched. It already goes straight to the insert past validation, and its own
comment says why: *"a movement written before the unit rule existed is exactly the one somebody
needs to reverse."* That is now also the escape hatch for the 0.2 of a cylinder left on an old row.

## Doors deliberately left alone, and why

**A reorder threshold** (`CreateInventoryItemRequest.reorderThreshold`, and the update). It is a
comparison level, not a quantity of anything that exists: nothing is ever received, issued, cooked
or counted against it, and it never reaches the ledger. "Reorder when we drop below 2.5 brooms" is
odd but harmless, and refusing it would push the rule out of "a thing you can hold" into "a number
you compare against". There is also a practical edge: with no migration, a temple that already has a
fractional threshold saved would be locked out of editing that item at all.

**Any price or rate** — `pricePerUnit`, `expectedPrice`, `amount`, the invoice's derived rate. Not a
count. ₹71.20 per piece is an ordinary price.

**`perHeadQty`**, on both the recipe form and the library form. A portion is explicitly *per one
person* — two and a half idlis a head is an ordinary, useful figure that nobody ever makes, buys or
holds. Multiply it by a head count and the answer is what gets cooked; **that** answer is the rule's
business and the ratio is not.

**`packCount`** ("4 × Bag"). Observed but out of remit: it is a number of packs, and a pack is not a
`Unit`. The pack's own contents *are* checked, which is where a fraction would actually do damage.

**`InventoryConsumptionService.preview`** — it is a read, and `IngredientUnits`' own rule is that
nothing here is consulted on a read, because a screen that throws is worse than one showing the
figure somebody needs in order to correct it. Only `consume` refuses.

**A shopping-list line's *computed* suggestion.** Only the override is checked on an edit. A request
carrying the suggestion back unchanged is the tick box saying "buy what you worked out", and the
computed figure is the application's own arithmetic. (Measured: `BuyingAmount` already rounds a
COUNT requirement up with `RoundingMode.CEILING`, so today it is whole anyway — see the sums section.)

**An approved request line the storekeeper did not touch.** It defaults to the approved figure, and
an approved figure written before this rule is exactly the one somebody has to be able to hand over
and close. Refusing it would strand the request with no way in the application to finish it.

### One door where the cost is real, and Rajeev may want to overturn it

**A recipe's ingredient line.** A recipe line is a ratio, and half a coconut is a thing a cook really
does halve. I checked it anyway — a line is the one place a fraction of a counted thing is
*authored* rather than mistyped, and from there it reaches the job card, the shopping list and the
stock draw at every scale the recipe is ever cooked at. A temple that genuinely halves a coconut
writes the recipe at the yield that makes it whole (one per 20 L rather than half per 10), which the
scaler then handles at any target.

**Measured before deciding, not assumed:** of 458 quantity strings in the three recipe books this
product ships (`recipe-library/karnataka.json`, `andhra_pradesh.json`, `prep-book/curated.json`), 35
are in a counted unit — `16 Pieces`, `150 Nos`, `25 pieces` — and **every one of the 35 is already a
whole number**. All 23 fractional quantities in the books are mass or volume. So nothing the temple
actually cooks is refused by this. It is still a judgement, it is the one I would most expect Rajeev
to disagree with, and it is a one-line change to lift if he does.

**An invoice's billed quantity** is the other sharp one. A bill records what somebody *else*
asserted, and this file argues elsewhere that storing a different quantity from the one typed "would
put words in the vendor's mouth". It is checked anyway because no delivery can be fractional from
today, so the only bills it can refuse are those against the 25 receipts written before the rule —
and R-INV-4 already allows billing *more* than was delivered, which is the way out of those. The rate
a vendor charged is Amount ÷ Billed qty, so a fraction here is the one that writes a nonsense
per-unit price into the history every later order reads.

## Who already reads or sums these columns?

The question the brief asked explicitly. Nothing stored moves, but what can *arrive* changes, so:
**is there code that depends on fractional counts being possible?** Three places were flagged; all
three were read.

**`shoppinglist/BuyingAmountTest` — yes, and it already agrees with the rule.**
`BuyingAmount.java` has, for a COUNT family, `return need.setScale(0, RoundingMode.CEILING);`, and
the test pins `2.1 PIECES → 3`, `0.2 PIECES → 1` and "never rounds down, at any quantity in any
band". So the shopping list's suggested figure for a counted thing is *already* a whole number. My
gate on `addLine` and on the `updateLine` override is consistent with what the derivation produces,
and carries no regression risk.

**`recipe/RecipeScalerTest` — yes, and this is why the scaling half is a separate task.** It
explicitly exercises fractional counts: `RecipeScaler.scale(10, PIECES, 0.4)`, and a `1.000`-from-JDBC
vector, and `0.999` / `1.004` / `1.005` boundaries. The scaler *depends* on a fractional count being
expressible. Changing that is T-425's decision, not a side effect of this one — and it is exactly the
work the widened brief describes.

**`ingredient/merge/IngredientMergeService.quantityIn` — reads two things, neither affected.** It
converts a `reorder_threshold` into the kept ingredient's unit (left alone here), and sums the
*typed* shopping-list quantities of a merged group. Two whole typed quantities sum to a whole one.
Two pre-existing fractional ones could sum to a fraction and would be written by the merge directly,
past every door — that is a derived write on legacy data, not a door, and it is noted rather than
gated.

**Nothing rounds or averages a count elsewhere.** `Quantities.cooks` rounds a COUNT unit HALF_UP for
display only, reads *stored* rows including the 88.5 apron, and is untouched — deliberately: a screen
that quietly rounded a stored 178.5 to 179 would hide exactly the damage this task exists to stop.
The IT asserts the stored figure comes back as 178.5.

## Acceptance criteria

**1 — every door refuses with `KMS-400191`, asserted by code.** `refusedNaming` asserts
`jsonPath("$.code").value("KMS-400191")` on every refusal, and the direct-ledger test asserts
`ErrorCode.PART_OF_A_COUNTED_THING` on the exception itself. No test in the file passes on status
alone.

**2 — the refusal names the thing and offers the whole numbers either side.** Asserted on
`fieldErrors` in the body: exactly one entry, its `field` the thing's name and its `message` the
exact sentence. Examples proven: `"Apron is counted in whole pieces. Enter 7 or 8."`,
`"Broom is counted in whole pieces. Enter 3 or 4."`, `"Idli is counted in whole pieces. Enter 200 or
201."` (a dish, which has no catalogue row at all), and `"Apron is counted in whole pieces. Enter -3
or -2."` on a negative adjustment. `FLOOR`/`CEILING`, not a rounding: which of the two they meant is
theirs to decide.

**3 — one good line and one fractional line writes nothing.** `twoLineOrderIsRefusedWhole` asserts
`purchase_orders` and `purchase_order_lines` are both empty, not even the header;
`twoLineGiftIsRefusedWhole` asserts no donation, no movement beyond the two seeded, and rice still at
100 Kg.

**4 — a whole count is accepted and a fractional KG/L is still accepted.** The most important
negative in the set, and it is covered four ways:
`adjustmentStillAcceptsAFractionalMass` (−0.5 Kg of rice → 99500 base grams),
`adjustmentStillAcceptsAFractionalVolume` (−1.75 L of ghee → 18250 base ml, so the rule is about the
*family* and not about one unit), `orderAcceptsAWholeCountBesideAFractionalMass` (12 aprons and 25.5
Kg on one order, the 25.5 stored untouched), and `giftAcceptsAWholeCountBesideAFractionalMass`.

**5 — `1.000` and `2.0` are whole numbers; the value, not the scale.**
`trailingZeroesAreStillWholeNumbers` posts both and expects 201 from each, ending at 87 aprons. Its
mirror `trailingZeroesDoNotHideAFraction` proves the other direction: `7.200` is still a fraction,
and `0.5` is a fraction with no whole part ("Enter 0 or 1"). The implementation is
`stripTrailingZeros().scale() <= 0`, with the reasoning written next to it.

**6 — the ledger's last line of defence refuses, reached directly.**
`theLedgerRefusesPartOfACountedThing` calls `StockMovementService.record` with 4.25 PIECES, past
every endpoint, and asserts the code and that nothing was appended.
`theLedgerLeavesTheApplicationsOwnArithmeticAlone` is its necessary companion.

**7 — existing fractional rows still read back, still sum, and are not rewritten.**
`theFractionalRowsAlreadyWrittenAreLeftAlone` inserts a `PO_RECEIPT` of **88.5 PIECES** exactly as
staging holds it, then: `GET /api/v1/inventory/items/{id}` returns `item.onHand` = **178.5** (asserted
on the figure, not on the field merely existing); the ledger sums to 178.5; a whole −2 adjustment on
top still succeeds and gives 176.5, so the half is carried and not swallowed; and the original row
still reads 88.5. `anOldFractionCanStillBeReversed` proves the way out — `compensate` takes a 1.5 row
back off the books past validation, which is why no "return exactly what was recorded" exception was
added to any door.

- **An invoice's billed quantity** is held to the rule, which means a bill against one of the 25

**One operational cost, stated plainly.** A goods-receipt line already sitting at 7.2 on staging can
