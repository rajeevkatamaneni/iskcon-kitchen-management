## Design decisions worth reading before this is signed off

**What was kept from the Nominatim provider, and what was dropped.**

| Kept | Why |
|---|---|
| the bounded LRU cache (500 entries), holding coordinates and description in one entry | a place does not move, and Google **bills every lookup** — the second devotee from Jayanagar costs nothing. Caching the two halves separately would ask twice for one lookup. |
| caching misses as well as hits | a typo retried in a loop should cost one request, not one per keystroke |
| `locate()` delegating to `describe()` | the two must never be able to disagree about where a place is |
| never raising; `Optional.empty()` for every failure | the port's contract, and both callers already fall back correctly |
| `Optional.empty()` on a blank query, before any I/O | nobody is billed for an empty box |

| Dropped | Why |
|---|---|
| the 1-request-per-second throttle | it existed to satisfy OSM's usage policy. Google's limits are orders of magnitude higher and enforced by billing, so keeping it would only make a devotee wait. |
| the `User-Agent` identity header, and its mandatory-with-no-default property | the free service demanded it; Google authenticates with the key. This is also what lets the deployment need exactly two variables. |
| **permanent** cache entries | this is the one thing that had to *change* rather than be kept. A permanent cache was right for OSM's licence. Google's terms allow geocoding content to be cached **temporarily**, so entries now expire at 25 days — inside their thirty with five to spare, and a long-lived Cloud Run instance cannot quietly turn a cache into a copy of their data. |

**Two guards the previous provider did not need.** The Geocoding API answers a refused key, an
exhausted quota and a disabled API with **HTTP 200** and a `status` field — unlike the Places API
(New), which 400s. So `status` is checked before anything is read, and the location node is checked
for `lat`/`lng` before they are taken. Control A above is what that guard is worth.

**`components=country:in`, a restriction rather than a bias.** Same shape as the Places provider's
`includedRegionCodes`, and the same behaviour the old `countrycodes=in` had. It is asserted on the
wire, from the server's `getRawQuery()`, not assumed.

**`GeocodingIT` lost its Spring context.** With the controller gone, everything left in the file is
about a provider, so it is now a plain JUnit class: no Testcontainers, no MockMvc, no `@Primary`
stubs standing in for the thing under test. It keeps the `IT` name (its own contract) and it is
still hermetic — a real socket on 127.0.0.1 and canned JSON, which is the technique that was already
in this file and the reason it was the right model.

## Not done / needs Rajeev

**1. `V93__validated_addresses_and_a_travel_allowance.sql:20` was NOT edited, and the brief's
reasoning for allowing it is wrong.** The contract listed it as comment-only and said *"changing
anything but a comment character is a checksum failure"*. **Flyway's checksum is a CRC32 over the
whole migration file, comments included.** Editing that comment on a migration already applied to
staging and production makes `flyway.validateOnMigrate` (on, by default, and not overridden in
`application.yml`) fail the next boot with a checksum mismatch, and the service does not start until
someone runs `flyway repair`. Independently, acceptance criterion 5 of my own brief says migration
comments are historical records and must not be edited to satisfy a text match — and `:20` is
exactly that: a dated account of why the address became a picked place. Two reasons pointing the
same way, so I left it. **If the coordinator still wants it changed, that is a decision about a
production boot and should be made deliberately, not by me.**

**2. `backend/src/test/java/org/iskcon/kms/geo/PlacesIT.java:52` still says "the technique
`GeocodingIT` uses for Nominatim".** It is outside my contract, it is untracked (created during this
wave), and its author is in the file now. It is a live comment, not history, so it wants correcting —
by them, or as **T-058**. The technique it points at is still there; only the name is stale.

**3. For T-058, noticed and deliberately left alone:** with `GeocodingController` gone, the port's
`describe()` / `Located` have no caller outside the geo package — `GoogleGeocodingProvider.locate()`
delegates to `describe()`, so nothing is dead, but the *reason* the split exists (a screen that had
to show a person the answer) no longer has a screen. Whether the port keeps the richer method is a
design question for a quiet moment, not for a wave where four people are in the tree. I did not
touch it; the brief was explicit that the signatures must not change.

**4. Sequencing, and it is an outage if it is got wrong.** Control B shows that an environment
carrying `GEOCODING_PROVIDER=nominatim` will now **fail to start the api and worker services** — no
`GeocodingProvider` bean, context load failure, not a degraded lookup. The Terraform change in this
same wave is what prevents that. This code must not reach a Cloud Run revision whose environment
still says `nominatim`.

**5. No hand smoke-test was performed.** This change adds no user-facing surface — it deletes one
(the `/api/v1/geocode` endpoint) and swaps the implementation behind an existing port — and the
provider cannot be exercised at all without a real `GEOCODING_API_KEY`, which I do not have and
would not spend. **The first real Google call this code makes will be on staging**, and it is worth
watching the api service's logs for `Geocoding … answered REQUEST_DENIED` the first time the devotee
temple search is used with a place name: that is precisely what a key not permitted for the
Geocoding API looks like, and it is a 200 in every metric.
