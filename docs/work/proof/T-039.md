# T-039 — a refused role change is recorded, on the door people actually use

The staff edit form now records a refused self role change before it throws the 403, and records a
successful access change as a `ROLE_CHANGED` event of its own beside the existing `STAFF_UPDATED`
one. Both go through `StaffEmploymentService.update`, which is the only door a temple role actually
changes through.

**Files changed:** (all three inside the contract, nothing else touched)

- `backend/src/main/java/org/iskcon/kms/staff/StaffEmploymentService.java` — in contract
- `backend/src/test/java/org/iskcon/kms/staff/StaffEmploymentIT.java` — in contract
- `docs/work/proof/T-039.md` — in contract (this file, new)

Nothing outside those was opened for writing. `audit/AuditAction.java`, `audit/AuditService.java`,
`user/RoleChangeService.java`, `frontend/app/audit/page.tsx` and the other `staff/` files were read
only.

## What was built

**1. The refusal is recorded.** `requireNotSelf(actor, before, ErrorCode.CANNOT_CHANGE_OWN_ROLE)` at
the old `:180` is replaced by a new private `requireNotChangingOwnAccess(actor, before, attempted)`,
which runs the same self-test and, when it fires, writes through
`AuditService.recordSeparately` — on its own transaction, so the record outlives the rollback the
throw causes — before throwing the identical `ApplicationException(CANNOT_CHANGE_OWN_ROLE,
Map.of("staffId", …))`. The error code, its detail map and the 403 are byte-for-byte what they were.

It mirrors `RoleChangeService:105-117`: same action `ROLE_CHANGE_REJECTED`, same entity type `USER`,
entity id the target's account, `{"role": …}` before and after, and a reason naming the act and the
staff record it was attempted on.

The guard is deliberately *not* folded into `requireNotSelf`, which stays as it was for its other
caller (see the finding below).

**2. The successful role change is recorded too.** `boolean accessChanged` is captured before the
branch that reassigns `userId`, and after the existing `STAFF_UPDATED` write a second, narrower
`ROLE_CHANGED` event is written against the account with before/after being the access level alone.
`STAFF_UPDATED` is unchanged and still covers the whole profile edit.

I checked the premise rather than taking it on trust. `frontend/app/audit/page.tsx:22-27` hardcodes
`ACTION_LABELS`, and the filter `<select>` is built from `Object.entries(ACTION_LABELS)` — so
`ROLE_CHANGED` is a selectable filter value fed by nothing but the backend's own rows. `grep -rn
"ROLE_CHANGED"` over `backend/src/main` finds it written in exactly one place,
`user/RoleChangeService.java:96`. Nothing else feeds that filter, so there is nothing to
double-count and the change stands as briefed.

A helper `accessRole(SystemAccess)` renders the access as the role name the rest of the log speaks
in, with `"NONE"` for no access — matching the existing `auditShape` convention rather than omitting
the key. `SystemAccess`'s constant names and `User.Role`'s coincide for the three grantable levels,
so a row written here reads identically to one written about a user account.

## Acceptance criteria

1. **A self role change through the staff path is refused and the audit row exists after the
   failure, on the real database, under RLS.** —
   `StaffEmploymentIT.refusedSelfAccessChangeIsRecorded`, PASSED. It goes through the endpoint
   (`PUT /api/v1/staff/members/{id}` via MockMvc), not the service, so there is a real transaction to
   roll back: the admin hires their own record at `TEMPLE_ADMIN`, then submits the form with
   `systemAccess` omitted. It asserts 403 with `KMS-400022`; that the role on `users` is untouched;
   that `STAFF_UPDATED` count is **zero** (proving the request's own transaction did roll back);
   and then that exactly one `ROLE_CHANGE_REJECTED` row survived, with
   `entity_type = 'USER'`, `entity_id` and `actor_user_id` both the admin,
   `before_state->>'role' = 'TEMPLE_ADMIN'`, `after_state->>'role' = 'NONE'`, and a reason
   containing both "their own access" and the staff record's id. The zero-versus-one pair is the
   proof: same transaction, one write gone and one write kept.
2. **A successful access change writes `ROLE_CHANGED` alongside `STAFF_UPDATED`.** —
   `StaffEmploymentIT.anAccessChangeIsAuditedAsARoleChange`, PASSED. A devotee hired at
   `KITCHEN_STAFF` is edited up to `KITCHEN_MANAGER`; asserts `users.role`, then `STAFF_UPDATED`
   count 1 **and** `ROLE_CHANGED` count 1, and reads the `ROLE_CHANGED` row for
   `entity_type = 'USER'`, `entity_id` = the devotee's account, and
   `KITCHEN_STAFF → KITCHEN_MANAGER`.
3. **A profile edit that does not change access writes no `ROLE_CHANGED`.** —
   `StaffEmploymentIT.anEditThatLeavesAccessAloneWritesNoRoleChange`, PASSED. Only the phone number
   moves; `STAFF_UPDATED` is 1 and `ROLE_CHANGED` is 0.
4. **Existing `StaffEmploymentIT` cases still pass.** — all 12 pre-existing cases PASSED in the run
   above, unmodified. 15 total, 15 passed, 0 failed.

## Finding, not built: the second `requireNotSelf` call site is still unaudited

`requireNotSelf` has a second caller — `StaffEmploymentService.endEmployment`, now at `:247` in the
edited file, with `ErrorCode.CANNOT_DISABLE_SELF` (**KMS-400024**), refusing somebody ending their
own employment. That refusal writes nothing at all. It is the same shape of gap this task closed on
the other call site: an admin trying to end their own employment and revoke their own sign-in is
exactly an act somebody reviewing the log would want to see attempted, and today it leaves no trace.

**I did not build it, deliberately.** It is a different act from a role change, there is no
`AuditAction` constant that fits it, and `ROLE_CHANGE_REJECTED` would file a resignation as an
attempted escalation. Minting an action constant is a reservation, not a tidy-up, and not mine to
take. It needs an action constant allocated (something like `EMPLOYMENT_END_REJECTED`) and a task of
its own. The `requireNotSelf` javadoc in the edited file now says this in as many words, so the next
person in the file does not have to rediscover it.

## For whoever takes this file next (T-014, staff reinstatement)

- `update()` now holds `boolean accessChanged`, captured **before** the branch that reassigns
  `userId`. If you add anything between that capture and the audit block at the end of `update()`,
  do not re-derive the answer from `userId` or from `before` — both have moved by then.
- `update()` now writes **two** audit events for one request when access changes. Any test that
  counts rows in `audit_events` after a staff edit has to count by `action`, not in total.
- `ROLE_CHANGED`'s `entity_id` is the **user account** id, not the staff profile id, and
  `audit_events.entity_id` is `NOT NULL` (`V3__audit_events.sql:85`). The code relies on `userId`
  being non-null on every path that reaches that write — prior access implies an account, and new
  access has just promoted or created one. A reinstatement path that restores access must keep that
  true or it will hit the constraint.
- `requireNotSelf` still takes an `ErrorCode` parameter although it now has one caller. That is on
  purpose; see the finding above. Do not "simplify" it away.
- `recordSeparately` needs the tenant on a **fresh** connection (`REQUIRES_NEW`), which works
  because the request's thread-local tenant context is applied on checkout. It would **not** work
  from a path whose tenant context is only transaction-local, e.g. provisioning. Reinstatement from
  an ordinary request is fine.
