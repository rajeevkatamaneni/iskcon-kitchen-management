## The endpoints

| | Permission | Answer |
|---|---|---|
| `POST /api/v1/vendor-invoices/bill-uploads` (multipart `file`) | MANAGE_PURCHASE_ORDERS | 201 AttachmentView, kind INVOICE_BILL |
| `POST /api/v1/vendor-invoices/payment-uploads?kind=…` (multipart `file`) | MANAGE_VENDOR_PAYMENTS | 201 AttachmentView. `kind` other than PAYMENT_PROOF / CASH_SIGNED_NOTE / CASH_RECEIVER_PHOTO (INVOICE_BILL included) is KMS-400001 with a field error on `kind` |
| `GET /api/v1/vendor-invoices/{invoiceId}/bill` | MANAGE_PURCHASE_ORDERS | the file, its stored Content-Type, `Content-Disposition: inline` with the original name; KMS-400030 when none |
| `GET /api/v1/vendor-invoices/{invoiceId}/payments/{paymentId}/attachments/{attachmentId}` | MANAGE_VENDOR_PAYMENTS | the file, only if it is on that payment and the payment on that invoice; else KMS-400030 |

No mapping clash: the two POSTs are single segments where `VendorInvoiceController` has only `POST /` and `POST /{id}/void|credit`, and the GETs are deeper than `GET /{id}` and `GET /{id}/payments`. The whole context booted in every IT run below, and Spring refuses to start on an ambiguous mapping.

AttachmentView JSON is exactly `{id, kind, contentType, sizeBytes, originalName, uploadedAt}` (asserted on the key set). No storage key leaves the server.

Type: decided from the bytes only (JPEG `FF D8 FF`, PNG signature, `RIFF….WEBP`, ISO `ftyp` with a HEIC brand → `image/heic` or `mif1`/`msf1` → `image/heif`, `%PDF-` at byte 0). AVIF is refused. The stored and served Content-Type is the detected one. Empty or missing `file` → KMS-400001, field `file`, "Choose a file to upload." (declared optional in the controller so a missing part is our answer, not Spring's unmapped exception → KMS-500001). Storage key `tenants/{tenantId}/attachments/{uuid}`, tenant from `TenantContext` (the verified token), `uploaded_by` = the signed-in user.

**Size, and which limit answers.** `spring.servlet.multipart.max-file-size` and `max-request-size` are **32MB**, the request size Cloud Run accepts (from Cloud Run's documented limit, not measured here). So every file from 10 MB + 1 byte up to 32 MB reaches `AttachmentService` and gets KMS-400166 from it (tested at 10 MB + 1 and at 20 MB over real HTTP). Past 32 MB the container stops the request and `GlobalExceptionHandler` answers the same KMS-400166 (tested with a raw socket). Why not "a little above 10 MB": my first version used 11 MB / 12 MB, and an 11.5 MB upload over real HTTP ended in a **broken pipe** on the client although the server logged KMS-400166. Tomcat stops reading when the container limit trips, so a client still sending never reads the answer. Raising the limit makes that case unreachable for anything Cloud Run lets through.

## The Java API for T-271 (invoices) and T-272 (payments)

All on `org.iskcon.kms.attachment.AttachmentService`, run inside the caller's request (temple from `TenantContext`), `@Transactional` so they join the caller's save transaction:

```java
AttachmentView claimBill(UUID attachmentId, UUID invoiceId)
AttachmentView claimForPayment(UUID attachmentId, AttachmentKind expectedKind, UUID paymentId)
Optional<AttachmentView> billOf(UUID invoiceId)
Map<UUID, List<AttachmentView>> ofPayments(Collection<UUID> paymentIds)
```

- Call a claim **after** inserting the invoice or payment row, in the same transaction, so a refusal rolls the save back.
- Refusals: KMS-400167 (ATTACHMENT_NOT_USABLE) for an upload that is null, missing, already claimed, of another kind, or another temple's (invisible under RLS). Also KMS-400167 for a second bill on one invoice or a second file of the same kind on one payment. KMS-400030 when the **parent** is not this temple's: a foreign key is checked past RLS, so each claim first reads the parent through RLS (`SELECT … FOR NO KEY UPDATE`, which also serialises concurrent claims on one parent). `claimForPayment` with `INVOICE_BILL` throws `IllegalArgumentException` (a coding mistake).
- The claim is one conditional `UPDATE … WHERE kind = ? AND invoice_id IS NULL AND payment_id IS NULL AND NOT EXISTS (same kind on this parent) RETURNING …`. A second claim of the same upload waits on the row lock and re-reads it as claimed.
- `ofPayments` returns every requested id as a key, with an empty list for none, files ordered proof, signed note, photo. One query (`payment_id = ANY(?)`).
- Also public, used by the controller: `upload(actor, kind, file)`, `openBill(invoiceId)`, `openPaymentFile(invoiceId, paymentId, attachmentId)`.

Grants and CHECKs: `kms_app` holds UPDATE and INSERT on `attachments` (asserted with `has_table_privilege`), and V144's `attachments_one_parent` and `attachments_parent_matches_kind` allow every claim the service makes: the claims succeed as `kms_app` in the tests.

## Frontend

`AttachmentUpload` props: `label`, `hint`, `required?`, `value: AttachmentView | null`, `onChange`, `upload: (file) => Promise<AttachmentView>`, `invalid?`, `loadStored?`. It follows the mock's `UploadBill`/`ChooseFile`: the same dashed box, the same filled box with thumbnail, name, "Photo"/"PDF", Replace and Remove. `accept="image/*,application/pdf"` and **no `capture`**, as the mock's comment says (capture would take away the PDF). The input is `sr-only` inside a `<label>` drawn with `BUTTON_CLASSES({variant:"ghost"})`, which is style E (`.btn-secondary`) with the `.btn` press. The focus ring is drawn on the label with the global ring's values. It uploads on choice, shows "Uploading…" at once, and ignores a stale upload overtaken by a replacement. It shows `formMessages.required(label)` ("Copy of the bill is required") in `FIELD_ERROR` under the box, turned red as the mock does. It does this when its enclosing form fires `submit` with no value, or when `invalid` is passed. It shows a server refusal with `ErrorNotice` (message, next step, KMS code).

`AttachmentThumb` props: `fileId`, `name`, `contentType`, `load: () => Promise<Blob>`, `small?`, `openable?`. A photo is fetched on mount and a PDF only when opened. The fetch is keyed on `fileId`, so an inline `load` does not refetch every render. Object URLs are revoked on change and unmount. HEIC that a browser cannot draw falls back to an icon and "This photo can’t be shown in the browser." with a Save link. Pressed, it opens the mock's viewing layer: `role="dialog"`, `aria-modal`, focus on Close, Tab kept inside, Escape and Close shut it, focus returns to the thumbnail.

**Deviation from the mock, raised here:** the mock's missing-bill sentence is "Upload a copy of the bill to save this invoice.". The brief (and R-INV-2, "using the standard required message") asked for `formMessages.required`, so it says "Copy of the bill is required". The mock's "Use the sample bill" button is mock-only and was left out. The "(required)" marker after the label is the brief's, not the mock's.

## Acceptance criteria

- Each endpoint refuses a user without its permission. A Volunteer gets 403 KMS NOT_PERMITTED on the bill upload and bill fetch. A Kitchen Manager gets 201 on a bill and 403 on payment proof and on a payment file. A Temple Admin gets 201 on all three payment kinds. **Met**, `AttachmentIT`.
- A PNG renamed `.pdf` with `application/pdf` is stored and served as `image/png`. **Met.**
- An EXE (`MZ`) is KMS-400165, and nothing is stored. **Met.**
- 10 MB + 1 byte is KMS-400166 (413), over real HTTP, from the service. Exactly 10 MB is stored. Past 32 MB it is KMS-400166 from the handler. **Met.**
- Claim twice → KMS-400167. Claim onto a second invoice → KMS-400167. Second bill on one invoice → KMS-400167. **Met.**
- Claim of the wrong kind → KMS-400167, in both directions and between payment kinds. **Met.**
- Another temple cannot fetch (404) or claim (KMS-400167). As `kms_app` with temple B set, `SELECT count(*)` of temple A's uploads is 0, and 2 with temple A set. Claiming onto another temple's invoice → KMS-400030, with the row unchanged. **Met.**
- The bill GET streams back byte-identical content, `application/pdf`, `inline`, with the original filename. **Met.**
- Frontend: choose → upload called with the file → shown with name and picture. Remove → value null, empty box back, object URL revoked. Required message on empty submit, with aria-invalid and describedby, cleared by a choice. Server error shown with its code. Thumbnail opens the blob (PDF iframe `src` = the object URL, fetched once, Escape closes, focus returns). A stale upload does not overwrite its replacement. **Met**, 10 vitest tests.
