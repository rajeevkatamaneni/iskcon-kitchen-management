## Design decisions made inside the brief (for the wave-2 builders)

- `meal_kitchens.meal_id` is **ON DELETE CASCADE**; `kitchen_id` RESTRICT everywhere. A meal with dishes still cannot be deleted (`meal_dishes.meal_id` and the composite key stay RESTRICT), and meals are cancelled, not deleted. The cascade meant fixtures deleting meals needed no change.
- Composite FK is named `meal_dishes_kitchen_on_meal`; unique target is `meal_kitchens_one_per_kitchen (meal_id, kitchen_id)`. Indexes: `meal_kitchens_by_kitchen`, `meal_dishes_by_meal_kitchen`, `staff_profiles_by_kitchen (tenant_id, kitchen_id)`.
- The migration's created kitchen gets a description saying why it exists. Creator is the earliest Temple Admin, else earliest user.
- **Interim lazy seeding.** Test temples (and in principle any temple provisioned before today with no planner kitchen after V150 — there are none, V150 creates one) have no kitchen. So the interim meal save and the interim hire call `KitchenService.seedMainKitchenForCurrentTenant(actor)`, which is idempotent: it returns the default planning kitchen if there is one and only creates when there is none, by V150's rules. T-354/T-357 should decide whether that stays or becomes an error.
- Interim hires are flagged `kitchen_needs_check = true`, because the system chose the kitchen.
