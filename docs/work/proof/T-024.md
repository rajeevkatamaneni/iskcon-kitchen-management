# T-024 — A purchase order line can name something that is not in the catalogue

`purchase_order_lines.ingredient_id` becomes nullable with an exclusive `description` beside it, and
the seven consumers that read a PO line were each taught what a null means. A described line is
**orderable and payable, never receivable**: `goods_receipt_lines.ingredient_id`,
`stock_movements.ingredient_id` and `vendor_supplies.ingredient_id` all stay `NOT NULL`.

## What I decided about `spendShares`, and why

**Decision: count it, in a bucket labelled "Other supplies".** `LEFT JOIN ingredients` plus
`COALESCE(i.category, 'Other supplies')` in both the `SELECT` and the `GROUP BY`.

The alternative was an explicit commented exclusion, and I rejected it for a reason specific to this
screen rather than as a general preference. Every figure `spendShares` returns is a **percentage of
a total the query itself computed**. Excluding ₹4,000 of furniture therefore leaves no visible gap
for a devotee to notice — it silently inflates every remaining slice by a few points. On a page
whose entire job is to tell somebody honestly where their donation went, quietly rounding the
awkward part out of the denominator is the one thing it must not do. A visible "Other supplies · 6%"
is both true and unremarkable.

Two details that made the label choice non-obvious:

- It is deliberately **not** "Everything else". That string already means something else in this
  method: the fourth-and-below categories, gathered up after the top three. Reusing it would have
  produced two rows reading "Everything else" whenever the described bucket ranked in the top three.
- `ingredients.category` is `NOT NULL` (verified at `V10__ingredients.sql:23`, not assumed), so the
  `COALESCE` fires only on the `LEFT JOIN` miss and can never merge a real category into the bucket.

`GivingPageIT` (4 tests) still passes. The bucket is not covered by a new test of its own — that
would need a described line and 30 days of PO history inside a donation IT, which is outside my
contract; `spendShares` is the only thing I changed in that file.

## Where the brief was wrong, and what I found that it did not

I opened every file before believing its description. Most of the brief held up exactly. These did
not:

**1. `ShoppingListService` line numbers.** The brief said `:220-241`. The method
`poOutstandingByIngredient` is at `:236-266` in the file as it stands. Same method, same defect.

**2. The `DocumentGenerationService` NPE is at `:263`, not `:311`.** `names.add(l.ingredientName())`
is at `:253` as stated, but the throw is
`glossary.get(names.get(i).toLowerCase())` at `:263` — the glossary *lookup*, not the line the brief
pointed at. It also matters that `:311` is inside `buildModel`, a different method about recipe
cards entirely.

**3. There is a second, quieter danger in that same method that the brief did not mention.** The NPE
only fires on a non-English sheet. On the **English** path a null name goes straight to the template,
which escapes null to `""` (`PurchaseOrderSheetTemplate.esc:199-204`, correctly) — so a vendor would
have been handed a printed sheet showing a quantity, a price, and a **blank** where the item should
be. Silent, and arguably the worse of the two. The fix (`l.subject()`) covers both.

**4. `ReceivingService` needs one guard, not five.** The brief asks for the null check at each of
`:120`, `:189`, `:224`, `:239-243` and `:327`. I put it at exactly one place — `validate()` — and
here is the evidence for why that is not a corner cut: `validate` runs over the whole submission
*before* `insertHeader`, so nothing is written when it refuses; and all five of those sites are
reachable only through the single loop in `receive()` that runs after `validate`. `receive()` is the
only caller. Repeating the check at the other four would be four pieces of unreachable code
pretending to be defence in depth. Control C confirms the single guard is load-bearing.

**5. `:327`'s inner join on `goods_receipt_lines` is correctly an inner join and I left it.**
`goods_receipt_lines.ingredient_id` is `NOT NULL` (verified at `V27__goods_receipts.sql:48`) and no
described line can produce a receipt line, so no row there can have a null to be dropped. I added a
comment saying so rather than leaving the reader to wonder. This is the far-side check the brief
asked for: a fact about the *receipt* table, not an assumption inherited from the PO table.

**6. The sixth consumer — `Collectors.joining` — your analysis is correct, and I checked it rather
than agreeing.** Compiled and ran it:

```java
List<String> xs = Arrays.asList("Rice", null, "Sugar");
System.out.println("[" + xs.stream().collect(Collectors.joining(", ")) + "]");
```
```
[Rice, null, Sugar]
```

`StringJoiner.add(CharSequence)` delegates to `StringBuilder.append(CharSequence)`, which calls
`appendNull()` for null. So `PurchaseOrderDeliveryService:121-124` would put the literal four
characters `null` into a WhatsApp body a vendor receives. **I did not touch that file.** Two
refinements for T-025:

- `.limit(SUMMARY_ITEMS)` is applied **before** the map, so the `"null"` appears only when a
  described line falls within the first `SUMMARY_ITEMS` lines of the order. `int extra =
  lines.size() - SUMMARY_ITEMS` is unaffected, so the "and N more" count stays correct.
- The fix is now one call: `PurchaseOrderLineView.subject()`, which I added to that record for
  exactly this. It is `@JsonIgnore`d, so it does not change the wire shape `frontend/lib/api.ts`
  declares.

## Two further consumers of `purchase_order_lines` that nobody's contract covers

`grep -rln "purchase_order_lines" backend/src/main/java` returns **eight** files, not six. Four are
outside the enumerated set. I read all four and did not touch any of them.

- **`BasketCostingService`** — mentions the table in a comment only. Safe.
- **`IngredientService.isReferenced:214`** — `EXISTS (... WHERE ingredient_id = ?)`. A null column
  never equals a supplied id, so no false positive. Safe. (Also T-023's file.)
- **`VendorPerformanceService.countLines:197-215`** — ⚠️ **a real defect, and it is silent.** It
  counts every PO line as "ordered" and joins `goods_receipt_lines` for "accepted". A described line
  is ordered and can never be accepted, so it contributes a permanent zero-fill line to that
  vendor's scorecard. Buy four stools from Govind Wholesale and their fill rate drops for ever. The
  fix is the same one-clause shape as the shopping list's: `AND pol.ingredient_id IS NOT NULL`, or a
  deliberate decision that an unreceivable line should be excluded from delivery performance. **This
  is a seventh consumer and needs its own task.** `vendor/` is explicitly forbidden to me and I have
  not widened my contract to reach it.
- **`VendorInvoiceService.expectedReceivedValue:130-146`** — a lesser note. The arithmetic is safe
  (a described line is never received, so it contributes 0 to `expected`), but `COUNT(pol.
  expected_price) AS priced` counts a *priced* described line, so a PO consisting only of priced
  described lines would show a variance measured against an expected value of 0. Cosmetic rather
  than wrong, and worth a look when somebody is next in that file.

## A second defect the shopping-list guard turned out to prevent

The brief describes the null-key collapse: `poOutstandingByIngredient` keys a `LinkedHashMap` by
`ingredient_id`, a null is a perfectly valid key, and every described line on every live order would
have collapsed into one bucket adding stools to extension cords in base units. That is correct.

There is a second consequence one step further on, which is why the IT asserts what it does.
`regenerateForCurrentTenant:141-180` seeds `merged` from `poOutstanding.keySet()`, then ends with:

```java
jdbc.update("DELETE FROM shopping_list_lines WHERE edited = false AND ingredient_id NOT IN ("
        + placeholders + ")", fresh.toArray());
```

With a `null` in `fresh`, SQL's `NOT IN` is never true for any row — so **the delete silently
matches nothing** and stale, unedited suggestions survive regeneration for ever, on every tenant with
a described line on a live order. `shoppingListIsUnaffected` is written around exactly that: an
order carrying only a described line, one stale unedited suggestion, regenerate, assert the stale
row is gone. Control B fails on that assertion.

## Decisions I made that were not spelled out, and that Rajeev may want to overrule

**1. I added a way to create a described line from the UI.** There is no purchase-order *creation*
screen anywhere in this application (`ls frontend/app/orders/` → `[id]/`, `page.tsx`,
`po-status.tsx`; `grep -rn createPurchaseOrder frontend` → no caller). The only surface that adds a
line to an order is `AddLine` inside `app/orders/[id]/page.tsx`, which is in my contract. Without
this, the feature would have had no way to be used or hand-tested at all.

So `AddLine` now has a second, separate control: a description box (max 200 chars), a "Counted in"
unit picker defaulting to `PIECES`, and its own "Add described line" button. Two controls rather
than one combined box, so a line naming *both* — which the server refuses with `KMS-400128` — cannot
be built from the form by accident; there is a test asserting the two adders do not offer each
other's fields. This is an addition beyond what the brief spelled out, not a deviation from an
approved mockup (there is none for this), but it is UI and it is Rajeev's to accept or change.

**2. `PurchaseOrderLineView.subject()`.** A `@JsonIgnore`d convenience over the two components, so
every display path reads `ingredientName ?? description` rather than the name alone. `@JsonIgnore`
because the wire shape is fixed by `frontend/lib/api.ts` — which I may not edit — and a derived
property appearing in JSON that the client's type does not declare is the exact drift the
required-and-nullable convention exists to prevent.

**3. `isFullyReceived` skips described lines.** Not stated in the brief, and the order would
otherwise stick at `PARTIALLY_RECEIVED` for ever — which is worse than a wrong status, because the
shopping list and the vendor scorecard both read that as "still outstanding".

**4. The visible skip is a `DESCRIBED_LINES_NOT_STOCKED` event on the PO trail**, recorded once per

# Appendix — sent back once, for the repo-wide unit-vocabulary guard

## What was wrong

The merged-tree run tripped `__tests__/design-system.test.ts`, which no targeted vitest run loads —
which is exactly why that step exists:

```
FAIL  __tests__/design-system.test.ts > E11 — one unit vocabulary, said one way > has no hand-typed unit array outside the one vocabulary
AssertionError: these hard-code a unit list — import FOOD_UNITS or YIELD_UNITS from lib/format instead: expected [ 'app/orders/[id]/page.tsx' ] to deeply equal []
```

The offender was mine, and the guard was right. The "Counted in" `<select>` on the described-line
form I added to `AddLine` typed the five unit names out as its own array — becoming a **seventh**
screen doing precisely the thing the guard was written in `design-system.test.ts:444-455` to stop:

> Six screens each carried their own `["KG","GM","L","ML","PIECES"]`. Adding a unit meant finding
> all six, and forgetting one meant a dropdown that silently offered less than the others.

This cuts with the grain of the brief rather than against it: the brief said `unit` stays `NOT NULL`
with its existing `CHECK (unit IN (...))` and needs no change, so a described line names a unit from
the same fixed vocabulary as every other line. There was never a reason for this screen to hold its
own copy.

## The fix

`FOOD_UNITS`, not `YIELD_UNITS`. Checked in `lib/format.ts` rather than guessed from the name — the
doc comment on `FOOD_UNITS:149` settles it explicitly:

> An ingredient, a stock level, a donation and **a purchase-order line** are all quantities of food,
> so they take the five physical units.

`YIELD_UNITS:158` is an alias of the same five, kept under its own name for recipe yields, which is
a different question. So:

- `frontend/app/orders/[id]/page.tsx:13` — `FOOD_UNITS` added to the existing `lib/format` import.
- `:726` — the select renders `{FOOD_UNITS.map(...)}`.

**One thing I dropped in the process, deliberately.** My original select reordered the five to put
pieces first, since that is where almost everything reaching that box lands. Rendering `FOOD_UNITS`
in its own order gives that up. I did not reorder a copy of it: the preference is expressed by the
field's initial value (`useState("PIECES")`) instead, which costs nothing and leaves the vocabulary
reading the same here as on the other six screens — which is the point of E11-S2. The comment in
the file says so.

**And a second-order trap worth recording.** My first attempt explained the fix in a comment that
quoted the offending array literally — and the guard reads raw file text, comments included, so the
comment itself re-tripped it:
