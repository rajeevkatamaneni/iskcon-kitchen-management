## Finding 1 — role and `systemAccess` are literally the same UPDATE

`backend/src/main/java/org/iskcon/kms/user/RoleChangeService.java:88-90` — the endpoint T-018
was to call:

```java
int updated = jdbc.update(
        "UPDATE users SET role = ?, updated_at = now() WHERE id = ?",
        newRole.name(), targetUserId);
```

`backend/src/main/java/org/iskcon/kms/staff/StaffEmploymentService.java:305-313` — what the staff
form's "App access" select already does:

```java
private UUID promote(UUID userId, SystemAccess access) {
    int updated = jdbc.update(
            "UPDATE users SET role = ?, status = 'ACTIVE', updated_at = now() WHERE id = ?",
            access.role().name(), userId);
```

…and `:316-320`, the demotion half:

```java
/** Takes a temple role away without taking the person away: they go back to being a devotee. */
private void demoteToDevotee(UUID userId) {
    if (userId != null) {
        jdbc.update("UPDATE users SET role = 'VOLUNTEER', updated_at = now() WHERE id = ?", userId);
    }
}
```

`SystemAccess` (`backend/.../staff/SystemAccess.java:15-17`) is a thin wrapper over `User.Role`:
`TEMPLE_ADMIN`, `KITCHEN_MANAGER`, `KITCHEN_STAFF` each carry a `User.Role`, and `none()` (null)
means VOLUNTEER via `demoteToDevotee`. Same column, same values, same table.

## Finding 2 — the control T-018 was to build is already on the screen T-018 named

The brief asked for "the promotion and demotion path there: promoting a volunteer to kitchen
staff, or demoting a manager, without going through hiring them again", on the staff record.

That control is `frontend/components/staff/StaffForm.tsx:170-195` — an **App access** select
offering *No login / Kitchen staff / Kitchen manager / Temple admin* — rendered on the edit path
by `frontend/app/staff/[id]/edit/page.tsx:98-107`, which submits it through
`api.updateStaffMember` at `:56`. Demoting a manager to devotee is "No login"; promoting is any of
the other three. Neither goes through hiring.

Building T-018 as briefed would put a **second control writing the same column on the same form**,
via a different endpoint, submitted by the same Save. Last-write-wins between the two, ordering
undefined. The edit page's own doc comment already rejects exactly this shape for a weaker case:
*"A fourth button on the row would be a second door to the same room."*

## Finding 4 — the brief's premise about reach does not hold

`UserController.java:62-64` states the rule: *"A temple's people arrive two ways… devotees register
themselves (E1-S17), and staff are hired (E6-S8), **which is also the only act that grants a temple
role**."* And `TenantProvisioningService.java:206-215` gives the founding admin a `staff_profiles`
row at provisioning, with a comment saying why — so they are not the one person on no screen.

Therefore **every user holding a non-VOLUNTEER role has a staff record**, and the existing App
access control reaches all of them. There is no population whose role is unchangeable today.
