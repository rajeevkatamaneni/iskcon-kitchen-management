## Defect 1 — `eventName` was never sent

`frontend/components/planner/MealServices.tsx`, in `RecordMeal.save()`, now sends the field the
server has always keyed on:

```ts
eventName: meal.eventName,
```

`meal` is the `MealServiceView` the block is already drawn from, and its `eventName` is populated —
the same value the job card two hundred lines above has always passed to
`api.requestJobCard(meal.planDate, meal.mealKind, meal.eventName, …)`. A main meal's is `null`, so
Breakfast/Lunch/Dinner keep sending `null`, which is what they always effectively sent by omission
and is now said out loud.

## The diagnosis of defect 2 — established, not assumed

The work manager's reading of the tree is **confirmed on all three consumers**. The refusal was
never discarded; it was rendered where nobody was looking.

`MealServices` did call `onError(toApiError(e, "We couldn't record that meal."))`, and every consumer
rendered it — but each renders it at the top of its screen, above the meals:

```
frontend/app/planner/catch-up/page.tsx:54:   const [error, setError] = useState<ApiError | null>(null);
frontend/app/planner/catch-up/page.tsx:100:  {error && <ErrorNotice error={error} />}
frontend/app/planner/catch-up/page.tsx:139:  onError={setError}          <- inside owing.map(...), one section per day

frontend/components/planner/DayView.tsx:38:   const [error, setError] = useState<ApiError | null>(null);
frontend/components/planner/DayView.tsx:57:   {error && <ErrorNotice error={error} />}
frontend/components/planner/DayView.tsx:77:   onError={setError}

frontend/app/planner/page.tsx:86:            const [error, setError] = useState<ApiError | null>(null);
frontend/app/planner/page.tsx:167:           {error && <ErrorNotice error={error} />}
frontend/app/planner/page.tsx:180:           onError={setError}          <- passed down through DayPanel
```

The three do **not** behave identically in how bad this is:

- **`catch-up`** is the worst, and is the screen Rajeev was on. The banner is above *every* day
  section (up to seven), so a refusal raised from the fourth day down renders far off-screen. No
  scroll, no focus move, nothing at the point of action. Four presses, no feedback — exactly what
  was observed.
- **`DayView`** and **`planner`** put the banner above one day's meals. Closer, but still above the
  day card and above every earlier meal on the day, so an Event block low on a long day is the same
  failure in a smaller way.

So the bug is *"the refusal is rendered where nobody is looking"*, not *"the refusal is discarded"*,
and the fix is the one that diagnosis calls for.

### The fix

The recording form shows its own refusal, in the product's existing shape for one — `ErrorNotice`,
which carries the server's message, the server's next step and the code to quote, with
`role="alert"` so it is announced. It sits immediately above the *Record this meal* button that
raised it. This is the pattern `components/VendorStatusDialog.tsx` already uses for a refusal inside
a form (its `{error && <ErrorNotice error={error} />}` sits directly above its submit row); nothing
new was invented.

**The `onError` prop contract is unchanged.** `MealServices` still takes it and still calls it for
the two acts on the meal header — the job card download and *Repeat it forward*. No consumer needed
editing and none can break.

**One deliberate decision to flag: the recording refusal is no longer *also* bubbled to `onError`.**
A page banner that has no way to clear itself would otherwise leave a red "we couldn't find that
meal" at the top of the screen contradicting the green "Lunch is recorded" after a successful retry.
A fresh attempt also clears the in-form refusal, so a refusal cannot outlive the thing it refused.
The test pins this so it is a decision and not a drift. If Rajeev would rather it appeared in both
places, that is a one-line change.

## Acceptance criteria

1. **Event meal carries its `eventName`.** ✅
   `"names the event it is recording, so the server can tell which meal is being written down"` —
   renders a meal with `mealKind: "Event"` and `eventName: "Bhagavad Gita Parayanam"` (the very
   event from the staging report), presses *Record actuals* then *Record this meal*, and asserts the
   object handed to `api.recordMeal` matches
   `{ planDate: "2026-08-21", mealKind: "Event", eventName: "Bhagavad Gita Parayanam" }`.
   It is not a Breakfast, and it is shown failing above without the fix.

2. **Everyday meal sends `eventName: null`.** ✅
   `"says null for an everyday meal, out loud rather than by leaving the field out"` asserts with
   `toHaveProperty("eventName", null)` rather than `toMatchObject`, deliberately: only
   `toHaveProperty` tells an absent field from one that is genuinely `null`, and an absent field is
   precisely what the defect was.

3. **A refusal reaches the person who pressed the button.** ✅
   `"shows the server's refusal inside the form that was submitted, beside the button pressed"`
   rejects `api.recordMeal` with the real `ApiError` from the staging capture (`KMS-400030`, 404),
   then asserts the `role="alert"` node carries the server's **message** ("We couldn't find what you
   were looking for."), its **next step** ("It may have been removed.") and the code, and that it is
   contained in the same `region` (`aria-label="Record Event"`) as the button that was pressed —
   i.e. at the point of action, not only at the top of a long page. It also asserts the form stays
   open on its figures so the attempt can be retried, and that the refusal was not additionally
   bubbled to `onError`.

4. **`npx tsc --noEmit` silent, targeted vitest green.** ✅ Output above: 53 passed, 3 files.

## Read-only findings you asked for

**Does `backend/.../meal/MealRecordingIT.java` cover recording an *event* meal? No — it contains
zero occurrences of `Event` or `eventName`.** Every one of its nine tests posts a main meal, and its
helper is `private MockHttpServletRequestBuilder record(String json)` at line 334 with the body
supplied per test — none of those bodies carries an event name. So the file the task named does not
cover it.

**But the server is correct, and is covered elsewhere.** `backend/.../meal/EventIdentityIT.java`
exercises exactly this seam:

- `recordingOneEventLeavesTheOtherOpen()` (line 184) POSTs
  `{"planDate":…,"mealKind":"Event","eventName":"Children's Bhagavad-gita Reading",…}` to
  `/api/v1/meal-services/record` and expects `200`, `$.recorded == true` and
  `$.eventName == "Children's Bhagavad-gita Reading"`, then asserts the *other* Saturday event is
  still waiting.
- `aMainMealsRecordingIsUntouchedByTheReKey()` (line 228), `recordingAnEventDoesNotLockTheOthers()`
  (line 268), `twoUnnamedEventsAreOneMeal()` (line 292) and
  `theSameNameInADifferentCaseIsTheSameEvent()` (line 318) cover the rest of the key's behaviour.

**So: the server was right, and was proved right, on the day the field was added.** The defect lived
entirely in the client type and the one caller, and no test on either side crossed the seam — which
is the identical shape of the V89 job-card defect that
`"names the event when it asks for that event's card"` in `meal-recording.test.tsx` was written for.
The same gap reopened one form lower down the same component.

**Other refusals shown where nobody would look, in the three consumer screens — reported, not
fixed:**

1. **`app/planner/catch-up/page.tsx:100` — the success notice has the same problem as the failure
   did.** `{cleared && <InlineNotice tone="success" …>}` sits at the top of the page, above every

   card it is about then vanishes from the queue — the person sees a section disappear with no

   of the screen contradicting whatever succeeded since. This is why the recording refusal is shown
   locally and not also bubbled (above); the other two acts that still bubble — job card download
   and *Repeat it forward* — remain exposed to it.

3. **`components/planner/DayView.tsx:57` vs `:64`** — `DayContextPanel`'s "Correct this date" form
   also reports to the page banner. The form is directly under the banner so it is usually visible,
   but a long correction form on a small screen can still push the submit button below it.

4. **`app/planner/page.tsx:167`** — the banner is inside the `Screen` above the view switch, so a
   failure raised in **day** view is still on screen after switching to **week** or **month**, where
