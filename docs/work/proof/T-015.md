# T-015 — A sent message can be sent again to the addresses it failed for, and to nobody else

`POST /api/v1/communications/{id}/retry` re-queues the message for the recipients whose
notification is `FAILED`, leaves every other recipient untouched, refuses with **KMS-400138** when
nothing failed, and cannot change a word of the letter. The control appears on the sent message's
record, in the card where the failures are already listed.

## The negative control

The strongest available statement: strip the fix back to the live defect — `DO UPDATE` → `DO
NOTHING` — and watch the retry report success while reaching nobody. Script:
`/private/tmp/…/scratchpad/control-T-015.sh`, log `control-T-015.log`. Named for this task, and its
first line says so, because the scratchpad is shared with the other two builders.

Guards, all four conditions:

- `grep -c -F` the anchor and **assert it equals 1** before patching (it did: `anchor occurrences
  in CommunicationService.java: 1`), so the patch cannot strip a neighbour's fix from the same file.
- `set -euo pipefail`, and the `perl` substitution `exit`s non-zero unless it replaced exactly one
  occurrence, so a control that fails to apply stops rather than passing vacuously.
- `git diff --stat` and a `grep -n DO NOTHING` **before** running anything, to prove the tree
  changed; plus `--rerun-tasks`, so Gradle could not answer `:test UP-TO-DATE`.
- Restore through an `EXIT` trap from a copy taken before the patch, then a byte-comparison.

## Acceptance criteria

**1. A retry re-queues only the failed recipients, proven by asserting the succeeded ones are
untouched.** `retryTouchesOnlyTheFailures` sets three distinct outcomes on one send — Nitai
`FAILED`, Gaura `DELIVERED`, Yamuna `SUPPRESSED/OPTED_OUT` — then after `{"retried":1}` asserts:
Nitai's recipient row points at a **different** notification and that notification is `PENDING`;
Gaura's and Yamuna's rows point at the **same uuids as before**; `count(*) FROM notifications` per
user is 1 for Gaura, 1 for Yamuna, 2 for Nitai; and `communication_recipients` still holds exactly
3 rows, so a retry re-points a row and never adds one. `SUPPRESSED` is deliberately not a failure —
a devotee who turned this kind off has made a decision, and a second attempt would be suppressed
identically anyway.

**2. Retrying a message every copy of which was delivered returns KMS-400138.**
`nothingToRetryIsRefused` — `409`, `$.code == "KMS-400138"`, and `count(*) FROM notifications`
still 3, so a refusal sends nothing at all. `aRetryInFlightIsNotRetriedAgain` covers the same code
for the second press, where the re-queued copy is `PENDING` rather than failed.

**3. The message body cannot be edited by this path.** `theLetterStaysFrozen` posts a full
newsletter payload (`"subject":"Rewritten"`) to `/retry` and asserts `subject`, `body_html`,
`body_text`, `status` and `audience_count` are byte-identical afterwards; that the copy the retry
queued carries `params->>'subject' = 'Janmashtami'`; and that `PUT /{id}` and `POST /{id}/send`
still answer **KMS-400086**. `requireDraft()` was not touched. On the client side, the test reads
`retryMock.mock.calls[0]` as a **list** and asserts `toHaveLength(2)` with the two values named —
an `objectContaining` would have passed just as happily against a call carrying the whole letter.

**4. The screen offers the retry where the failures are already listed, and says what it did.** In
the "Who it went to" card of `SentDetail`: *"2 copies didn't arrive."* with *Send it to them again*,
the singular *"1 copy didn't arrive."*, the reassurance that only those devotees are written to,
then *"On its way again to 2 devotees."* and a `deliveries.reload()`. A refusal renders through
`ErrorNotice` with its quotable code. Absence is asserted too: no control at all when everything
arrived (a `SUPPRESSED` recipient must not put a "something went wrong" button on a message that
went out perfectly), and no way to rewrite a sent message from this screen.

## Not done / needs Rajeev

**No hand smoke test, and I could not run one.** The control only appears once a real delivery has
failed, which needs a deployed environment and a genuine provider failure — there is no local
backend running and no honest way to manufacture a `FAILED` notification in a browser. `next build`
plus the screen suite is as far as this goes from here; the retry button, its wording and the
reload belong in the post-deploy verification pass on staging, against a message with a real
failure in it.

**No audit event, because no `AuditAction` was reserved.** `send` records `COMMUNICATION_SENT`;
`AuditAction.java` has no constant for a retry and it is not in my contract. Reusing
`COMMUNICATION_SENT` would have been wrong twice over — it would falsify `CommunicationIT`'s
assertion that one send produces exactly one such event, and it would record a retry as a send. The
retry currently logs (`Communication {} retried by {} for {} of its {} failed recipients`) and
nothing more. **If a retry should be on the audit trail, that is a `COMMUNICATION_RETRIED` constant
in `AuditAction.java` and a one-line call — a small follow-up task, not something to widen a
contract for.**

**A figure outside my contract that a retry makes stale — reported, not fixed.**
`OpsService.recentFailures()` (`backend/…/ops/OpsService.java:168`) lists the ten most recent
`notifications WHERE status = 'FAILED'`, and `todayCountsByStatus()` / `notificationMetrics()` count
by status. A retry leaves the original `FAILED` row exactly where it is — deliberately, since the
attempt genuinely did fail and the ops graph is a graph of attempts — so an operator's "recent
failures" list goes on showing a send that has since been retried successfully, with nothing to say
so. It is not a falsified sum in the wave-7 sense (nothing is double-counted), but it is a screen
that now has a state it cannot express. Whether it needs one is a judgement for the operator screen's
owner. **I did not touch `OpsService.java`.**

**One small honesty gap in the error text.** A **draft** has no recipients, so
`POST /{id}/retry` on one answers `KMS-400138` — *"Every copy of this message was delivered."* —
which is not quite true of a message that has never been sent. It is unreachable from the screen
(the control only renders on a sent message's record) and no second code was reserved, so I left it
and put `status` in the exception's context for the log. Say the word if it deserves its own code.

**`communications.audience_count` — the "Reached" column — is unchanged by a retry**, which is
correct: it records how many people the message was addressed to, not how many copies were sent.
Checked deliberately, since the wave-7 lesson is about exactly this question.
