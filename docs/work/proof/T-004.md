## What the backend actually does, having read it rather than assumed it

Two findings from `backend/src/main/java/org/iskcon/kms/occasion/OccasionService.java` that the
screen is built around:

1. **`seeded` changes nothing on update or delete.** `update()` and `delete()` look the row up by
   id and never read `seeded` — a seeded occasion is renamed and removed exactly like a temple's
   own. Seeding happens once, at provisioning, and `seedForCurrentTenant()` is not re-run. So the
   screen does **not** lock those rows: it badges them "Standard" and, in the removal dialog only,
   says that removing one removes it for this temple and that it does not come back on its own.
2. **Deleting an occasion the planner has already resolved against cannot fail.** The service's own
   comment says it: *"No hard reference from meal plans (they keep the occasion name as text,
   E4-S4), so removing an occasion never orphans historical plans."* There is no in-use refusal to
   catch, and no 500 to be had. What the task asked for — that this be handled visibly rather than
   left to a 500 — is therefore met in two parts, and both are tested: the confirmation states the
   consequence *before* the press ("the planner stops marking this day … meals already planned or
   cooked for it keep the name they were saved with"), and any refusal the server ever does give is
   rendered through `ErrorNotice` with the dialog left open, so nothing raw or blank can reach the
   reader. **Flagging this as a deliberate reading of the brief**: if Rajeev expected a server-side
   refusal on an in-use occasion, that is a backend change nobody has built and this task did not
   invent one.

The type is fixed at creation, matching `UpdateOccasionRequest` having no `type` field. The edit
dialog does not render the choice at all and instead says what to do instead — add it again as the
other kind and remove this one. A test asserts both halves.

## Acceptance criteria

**"Create, rename and delete each round-trip and are reflected in the list without a reload."**
Every mutation calls the reserved wrapper and then `reload()` from `useAuthedQuery`, which refetches
the list in place — no navigation, no `location.reload`, no full page load anywhere in the file.

The test proves the *effect* rather than the call, deliberately: `useAuthedQuery` is **not** mocked
in `occasions.test.tsx`, unlike most screen tests here. The real hook runs against a fake server
whose catalogue the mocked `createOccasion` / `updateOccasion` / `deleteOccasion` actually mutate,
so a screen that called the API and never refreshed would fail. Asserted three times:

- *"adds a fixed-date occasion and shows it in the list without a reload"* — asserts the exact call
  `({name: "Deity Installation Day", type: "MANUAL", matchText: null, fixedMonth: 11, fixedDay: 3,
  defaultServings: 600, notes: null}, "test-token")`, then that the row and its "3 November, every
  year" are on screen, then that the form has emptied itself.
- *"renames one, and never sends a type on the edit"* — asserts the id, `expect(input).not
  .toHaveProperty("type")`, the rest of the payload, and then the renamed cell on screen.
- *"says what a removal changes before it happens, then removes it"* — asserts the call, then that
  the row is **gone** from the table.

**"The screen is refused for every role but Temple Admin."**
`RequireRole roles={["TEMPLE_ADMIN"]}`, matching the reserved nav row's `roles: [ADMIN]` and the
server's `MANAGE_TEMPLE_SETTINGS` on all three writes. Test *"refuses every role but Temple Admin"*
renders the page as `KITCHEN_MANAGER`, `KITCHEN_STAFF`, `VOLUNTEER`, `ACCOUNTANT` and `SUPER_ADMIN`
in turn and asserts "Not your page", the absence of the add form, and — the part that matters more
— that `listOccasions` was never called for any of them, so the screen does not even ask.

**"Deleting an occasion that is in use fails readably."**
Covered in two places, per the backend reading above. *"says what a removal changes before it
happens"* asserts the consequence is on screen before the button is pressed. *"shows a refused
removal in the reader's own words, and keeps the dialog open"* makes the server refuse with a
409 `ApiError` and asserts the message, the next step, the visible code, that **no `409` reaches the
reader**, that the dialog is still open, and that the row is still there to try again on. A third,
*"says so readably when the list itself cannot be loaded"*, does the same for a 500 on the initial
read — an `ErrorNotice` rather than a blank screen.

**"`npx tsc --noEmit` clean; your new vitest file passes; `npm run build` succeeds."**
All three above: `tsc` silent and exit 0, 10/10 tests, build exit 0 with the route listed.

## Other things worth knowing

- **The occasion, not an event**, as the settled design says. Nothing here creates a meal, a plan or
  an event — it curates the recurring catalogue the planner resolves against.
- **The two types are asked about once, at the top of the add form**, because that is the one answer
  that cannot be changed afterwards. Choosing "the Vaishnava calendar decides" asks for the calendar
  wording to match; "the same date every year" asks for a month and a day. Only the pair belonging
  to the chosen kind is sent, and the other is sent as `null`, so a converted-looking record cannot
  be left half-populated.
- **29 February is accepted and explained.** The server takes any day 1–31 and `safeDate()` simply
  produces no occurrence in a year where the date does not exist, so the form says so in visible
  text under the field rather than silently taking a date that mostly will not happen.
