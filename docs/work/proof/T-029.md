# T-029 — "Continue with Google" now always asks which Google account

The two call sites built a bare `new GoogleAuthProvider()`. With no `prompt` parameter, Google's
OAuth endpoint skips the account chooser whenever exactly one Google session is live, so after
signing out of our app — which clears the Firebase session and leaves the Google one untouched —
the next press silently reused the previous person. Both sites now build the provider through a
single `googleProvider()` helper that sets `{ prompt: "select_account" }`.

**Cause confirmed before fixing.** Both call sites read exactly as diagnosed:
`lib/auth-context.tsx:208` and `app/register/page.tsx:83`, each `new GoogleAuthProvider()` with no
custom parameters anywhere in the file. `grep -rn "new GoogleAuthProvider" app lib components` now
returns one hit only — line 62, inside the helper itself. `app/sign-in/page.tsx` has no Firebase
call of its own; it goes through the context's `signInWithGoogle`, so fixing the context fixes that
screen.

**Files changed:** all three inside the contract.

- `frontend/lib/auth-context.tsx` — new exported `googleProvider()` with the reasoning comment;
  `signInWithGoogle` uses it.
- `frontend/app/register/page.tsx` — uses `googleProvider()`; the now-unused `GoogleAuthProvider`
  import dropped, `googleProvider` imported from `@/lib/auth-context` (which the file already
  imported `useAuth` from).
- `frontend/__tests__/google-account-chooser.test.tsx` — new. `session-failures.test.tsx` and
  `signin.test.tsx` were checked first as instructed: neither covers Google sign-in behaviourally
  (`session-failures` stubs `GoogleAuthProvider` as an empty class and never presses the button;
  `signin.test.tsx` only asserts the button is on screen), and the register call site needs a mock
  setup neither file has, so one new file covers both sites rather than splitting them.

One deviation from the literal instruction, raised here rather than after the fact: rather than
repeating `provider.setCustomParameters(...)` at two sites, both go through one exported
`googleProvider()`. Same behaviour at both, one place for the explanation, and a third call site
added later cannot quietly reintroduce the defect. If you would rather see the two lines inline,
say so and I will flatten it.

## Acceptance criteria

**After signing out, pressing Continue with Google offers the account chooser rather than reusing
the last session — on the sign-in screen.** Verified by test: `AuthProvider` is rendered, the
context's `signInWithGoogle` is invoked, and the assertion reaches into
`signInWithPopup.mock.calls[0][1]` — the provider object Firebase was actually handed, not merely
the last one constructed — and requires `setCustomParameters` to have been called on *that* object
with exactly `{ prompt: "select_account" }`. The mutation run above shows the assertion failing when
the parameter is absent.

**…and on the register screen.** Same assertion, reached by driving the real form: temple searched
and picked through `TemplePicker` (`api.temples` stubbed), name, email and phone filled, the Google
tab selected, "Create my account" pressed. So it covers the route a person actually takes, not a
direct call to the handler.

**`prompt: "consent"` not used.** Asserted explicitly:
`expect(handed.setCustomParameters).not.toHaveBeenCalledWith(expect.objectContaining({ prompt: "consent" }))`,
so a later change to `consent` fails the test rather than passing quietly.

**Nothing else regressed.** 906 tests across 87 files pass, including `session-failures.test.tsx`
(12) and `signin.test.tsx` (2), which mount the auth context I changed.
