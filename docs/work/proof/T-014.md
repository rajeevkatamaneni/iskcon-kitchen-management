# T-014 — Reinstating someone whose employment was ended

`POST /api/v1/staff/members/{id}/reinstate` — the one way out of a state that was otherwise
permanent. `requireStillEmployed` guards both `endEmployment` and `update`, so ending an employment
also locked the record, and a misclick on the termination form could not be corrected from anywhere.
The screen now offers reinstatement on the staff record, refusals are named, and both the act and
the refused attempt are audited.

**No migration was written. `V105` is unused** — see "Decisions" below.

## Decisions

### `V105` is unused, and `dateOfRejoining` is not stored

The end state is three columns that already exist (`V57__staff_employment.sql:67-69`):
`employment_status`, `last_working_day`, `end_reason`. The last two are nullable, so the inverse of
ending an employment is representable in the schema exactly as it stands.

The one thing that could have forced a column is `dateOfRejoining`. It does not, and this is the
decision the brief asked me to make and record. **It goes into the audit `after` map and nowhere
else**, for four reasons:

1. It cannot go on `date_of_joining` — that holds the day they *first* joined, and overwriting it
   destroys a fact about the person.
2. A `date_of_rejoining` column would hold only the **most recent** return and lose every earlier
   one — which is the same objection that rules out (1). Somebody can leave and come back more than
   once, so **this is an event, not an attribute**, and a single column is the wrong shape for it.
3. `audit_events` is append-only and already carries `lastWorkingDay` on `STAFF_EMPLOYMENT_ENDED`.
   The ENDED/REINSTATED pair is therefore the durable record of the whole cycle, each half with an
   actor, a timestamp and a reason — which is precisely what `equipment_state_changes` is for a
   machine in T-033.
4. **Nothing in the product computes anything from `date_of_joining`.** Checked rather than assumed:
   `grep -rn "date_of_joining\|dateOfJoining" backend/src/main/java frontend/lib frontend/components`
   returns only the insert, the update, the row mapper, the audit shape, the form field and
   `labels.ts:69` ("joined <date>"). No tenure, no accrual, no pay calculation. A stored rejoining
   date would have had no reader.

A gap at 105 is harmless. The number stays spent and mine. (Noted in passing: `V103` and `V104` were
taken by another builder mid-wave, so 105 was still free.)

### `staffProfilesWithARecord()` and retracted bans

The brief asked me to satisfy myself about this, and it is **the right predicate**. It is not
mine to edit and did not need to be:

```java
// EmploymentBanService.java:258-261
public Set<UUID> staffProfilesWithARecord() {
    return Set.copyOf(jdbc.queryForList(
            "SELECT staff_profile_id FROM employment_bans WHERE retracted_at IS NULL", UUID.class));
}
```

`retracted_at IS NULL` — retracted records are excluded, which is exactly what the brief was worried
about, and its own doc comment says so deliberately ("A retraction stops a record being shown at any
hire"). It is bounded by the row policy to this temple's own rows, so it is not a platform search.
**No new read was added to `ban/`.** The behaviour is proved from the side that could have been got
wrong, by `aRetractedRecordDoesNotRefuseTheReinstatement`.

### `KMS-400136` should be a distinct code — I agree with the allocation

Reusing `EMPLOYMENT_NOT_ENDED` would have told an admin "this person is still employed", which is
false and unactionable. The two refusals are different mistakes with different next steps: one is
"you are looking at the wrong person", the other is "retract the record first". Kept as allocated.

### Restoring access

`promote()` sets `role = ?, status = 'ACTIVE'`, which is what returns sign-in to a disabled account.
Asking for no access calls `demoteToDevotee` and deliberately does **not** re-enable a disabled
account — they came back without a login, and that is what that means.

That branch is doing real work rather than being defensive, and this was not obvious:
**`endEmployment` sets `status = 'DISABLED'` but leaves `role` alone**, so a dismissed administrator
still carries `TEMPLE_ADMIN` on their users row. Reinstating them with no login has to strip it, or
the temple keeps a row one status change away from an administrator nobody granted. Asserted by
`comingBackWithoutALoginRestoresNeither`.

### No self-guard

Unlike `endEmployment`, `reinstate` has no "not on yourself" guard, because self-reinstatement is
unreachable rather than permitted: a former employee holds either `VOLUNTEER` (no `MANAGE_STAFF`) or
a disabled account (cannot authenticate). Stated in a comment rather than guarded.

### The screen has no `<form>`, and that was forced

`frontend/__tests__/design-system.test.ts` has two guards over any file containing `<FocusScreen`:
a `type="submit"` outside the header `actions` prop is an offence, and so is `onSubmit=` on a screen
whose top-right action says **Close**. This screen is a read-only record whose action is Close — a
deliberate decision (Q1) that `staff-record.test.tsx` asserts — so a `<form onSubmit>` in its body
would have redded the repo-wide guard, and moving the submit into the header would have meant
changing Close to Cancel and contradicting that decision.

The panel therefore uses controlled inputs and a `type="button"` with `onClick`, inside a
`<div role="group" aria-label="Take them back on">`. The existing ban panel on this same screen
avoids the guard differently — its form lives in `components/staff/Ban.tsx`, which the guard skips
because it contains no `<FocusScreen`. **A `components/staff/Reinstate.tsx` would have been the
closer match to that precedent, but it is not in my path contract and I did not create it.** Flagging
it as a judgement call for review rather than widening the contract myself. The cost of the
in-contract version is that Enter does not submit; for a rare and consequential act that is arguably
right, but it was a constraint before it was a preference.

has existed, and this task is the actual answer. The right text is roughly *"Take them back on from
their record if they are returning."* **I did not change it** — `ErrorCode.java` is reserved and the
brief says to report rather than fix. One line, whoever holds that file next.
