# T-116 — the words written against a refusal code now reach the person refused, and a test keeps them there

## The scope question first, because the brief says answer it before touching anything

**`REFUSALS` has exactly two codes, and they were mute in two different ways. Neither was safe, and
only one of them looked broken.**

| Code | Status | Screen the reader reaches | What the reader was told |
|---|---|---|---|
| `KMS-400019` | `disabled` | `AccountDisabled` in `components/RequireRole.tsx` (rendered from `RequireRole` and from `app/page.tsx`) | The right words — **retyped by hand into the JSX**, not read from anywhere |
| `KMS-400020` | `no-account` | `app/choose-temple/page.tsx`, via `router.replace("/choose-temple")` | **Nothing.** Neither half had ever been on a screen |

So the brief's premise is half right, and the half it gets wrong is the more interesting one.
`KMS-400019` was not mute. Its message and its next step were on the screen — as two string
literals in `AccountDisabled` that happened to match `ErrorCode.java` exactly. That is not a
mechanism. It is a coincidence maintained by hand, and **the proof that it is only a coincidence is
one constant away in the same file**: T-114 reworded `KMS-400020`'s next step on 2026-09-10, from
*"Ask your temple administrator to add you."* to *"Choose your temple to join it."*, and not one
pixel of the application changed — because nothing in the application was reading it.

There is also a third case that is not a code at all and matters more than either:

**The fall-through.** `REFUSALS[error.code] ?? "no-account"` sends every unrecognised refusal to the
temple picker. A 401 with no body — an expired or unverifiable token, which `TokenVerifier`
deliberately refuses to explain — arrives as `api.ts`'s synthesised `KMS-0000 "We couldn't reach
the server."`, lands on `no-account`, and the picker tells that person *"Which temple do you serve
at?"* That is the same lie `unreachable` was split out of the status in August to stop, one screen
further along. It is not fixed here, because fixing it needs the server to say something it
currently refuses to say, but it **is** the reason the fix below is careful about which codes get
words. See "What I did not do" at the end.

**Verdict: the pattern, not the instance.** One code was silent and one was a hand-copy; a third
path had words that would have been actively wrong to print. Three different failure modes in a
two-row table, and none of them had anything watching.

## What was built

**One change of mechanism, two screens that use it, one guard.**

`auth-context.tsx` now keeps what the server said instead of reducing it to a routing decision. A
refusal carries a `Refusal { code, message, action }` on the context beside `status`: the status
says *where the reader goes*, the refusal says *what they are told when they get there*.

```ts
const known: AuthStatus | undefined = REFUSALS[error.code];
setRefusal(known ? { code: error.code, message: error.message, action: error.action } : null);
setStatus(known ?? "no-account");
```

**Only a code named in `REFUSALS` gets words, and that is the deliberate part.** An unexplained 401
carries `KMS-0000 "We couldn't reach the server."`, which is false about a refusal; printing it
would be worse than silence. So an unrecognised refusal keeps its old behaviour *exactly* — the
`no-account` status, and nothing said. Membership of that table is now what earns a code its
wording as well as its routing, which keeps "adding the next code is adding one line" true.

It is cleared on success, on sign-out, and on `unreachable`. The sign-out case is not tidiness: the
whole point of the sign-out button on the disabled screen is that somebody else can use the browser
next, and they must not be met by the last person's bad news.

### `AccountDisabled` — `components/RequireRole.tsx`

Reads `refusal.message`, `refusal.action` and `refusal.code` instead of three literals. The literals
survive as a fallback for a `disabled` status reached without a refusal, which no path produces
today — kept for the same reason `WrongRole` immediately below it falls back to `/`: this is the
last screen a broken session meets, and the last screen in the application is the one that must not
itself break.

**The screen was restructured rather than re-punctuated, and this is the part that changed on
review.** The first attempt rendered the catalogue's sentence *as* the `h1`, which meant the only
`h1` in the application ending in a full stop. The coordinator ruled — correctly — that the fix is
to move the sentence, not to trim it: trimming would make the rendered text differ from the stored
text, which is precisely the hand-copy problem this task exists to kill.

So the screen is now a short unpunctuated title with the catalogue's words as body copy beneath it,
the shape `ServerUnreachable` and `WrongRole` already use:

```
Account disabled                                    ← h1, the screen's own title, a literal
This account has been disabled.                     ← refusal.message, exactly as stored
Ask your temple administrator to restore access.    ← refusal.action, exactly as stored
…
If you need help, quote KMS-400019                  ← refusal.code
```

**One deviation from the letter of that instruction, flagged rather than buried.** The instruction
said to keep the `h1` as-is and put the sentence underneath. Done literally, the reader would have
met `This account has been disabled` as the title and `This account has been disabled.` as the line
directly below it — the same words twice, in two sizes. So the title is now the short label
**"Account disabled"**, which keeps every stated constraint (short, unpunctuated, house shape, the
catalogue's sentence rendered verbatim as body copy) and removes the stutter. **If you want the
longer title back, it is one string and the guard is indifferent to it.**

Message above next step, and the more prominent of the two: that is `ErrorNotice`'s order for every
other failure in the product.

### `/choose-temple` — `app/choose-temple/page.tsx`

`KMS-400020`'s **message** now appears as a quiet `InlineNotice tone="info"` above the heading:

> You're signed in, but you don't have an account at any temple yet.
> # Which temple do you serve at?

This screen already had the shape the disabled screen was corrected into, so it needed no change on
review: its `h1` is the screen's own question — *"Which temple do you serve at?"* — and the
catalogue's sentence is body copy above it. No heading here carries a catalogue sentence or a full
stop.

**Its next step does not, and that is the judgement the brief asked for.** `KMS-400020`'s next step
reads *"Choose your temple to join it."* The screen it would be printed on is headed *"Which temple
do you serve at?"* with the form that does it directly beneath. Printing it would be the same
instruction three times in four inches — this is precisely the "a sentence pasted onto a redirect is
noise" the brief warns about, and it is true of the next step and **not** true of the message. The
message is the reason the reader was sent, and the reason is the half nobody ever gave them: the
page's own comment records Rajeev losing ten minutes on 2026-08-30 to not knowing why he was being
asked.

`tone="info"` and not `danger`, and **no reference code shown**. For most people who read this line
it is the first screen of joining a temple; nothing has failed, nobody has anything to telephone
support about, and a red box with a KMS number stamped on it would be a poor way to meet a new
devotee. `AccountDisabled` keeps its code, because that reader genuinely does need to quote
something.

It renders only when the server actually said it. An expired session — `no-account` with no refusal
— sees the picker exactly as it is today, which is a real improvement on its own: the screen stops
asserting "you have no account here" to somebody nobody has said that about.

## The guard — `frontend/__tests__/refusal-words-reach-the-reader.test.tsx`

T-098's shape: **the scope rule is structural, not a list.** A code is in scope if and only if
`REFUSALS` in `lib/auth-context.tsx` names it. The test reads that table out of the source, resolves
each `[CONSTANT]` back to its `const CONSTANT = "KMS-nnnnnn"` literal, reads each code's message and
next step out of `ErrorCode.java`, then drives the real `AuthProvider` with that refusal and asserts
both halves are on the screen the reader actually reaches.

Nothing in it enumerates a code by hand, so **adding a line to `REFUSALS` puts the new code under
the guard in the same commit** — which is exactly how this defect arrived: a line was added to a
routing table and nobody asked what the reader would be told when they got there.

Why it reads source text, which this codebase otherwise avoids: the two things that have to agree
are a Java enum and a TypeScript screen, in different languages and different build systems, so no
compiler can hold them together. Precedents followed: `movement-labels.test.tsx` (T-125) and
`CommunicationSendGuardSourceTest.java` (T-104).

**Four things stop it passing vacuously.**

1. Both parses fail loudly with an instruction if the file's shape changes, rather than returning
   an empty set. `ErrorCode.java` must yield at least 50 constants or it throws; it currently yields
   well over a hundred, and a regex that matched nothing would otherwise leave every assertion
   comparing an empty string against an empty string and reporting success.
2. Every status `REFUSALS` routes to must be named in the test's `ARRIVALS` table. A new
   `AuthStatus` fails with *"this test does not know which screen that reader lands on"* rather than
   being skipped.
3. Every entry in the `NEXT_STEP_IS_THE_SCREEN` exemption must still be a code `REFUSALS` routes, so
   a stale exemption fails rather than sitting there excusing nothing.
4. **The sentinel case**, which is the one that catches a hand-copy: each code is refused a second
   time with words no catalogue would hold, and the screen must show *those*, and must no longer
   show the catalogue's. `AccountDisabled`'s old literals passed "the catalogue's words are on the
   screen" while never having read the catalogue; they do not pass this.

The one exemption is written down rather than left as an omission:

```ts
const NEXT_STEP_IS_THE_SCREEN: Record<string, string> = {
  "KMS-400020": "\"Choose your temple to join it.\" is /choose-temple's own heading asked as a " +
                "question, directly above the form that does it.",
};
```

An exempt code still has to render its **message**. The exemption is only ever about the next step.

**A fifth assertion was added on review**, once the heading question was settled: a catalogue
message must not be the accessible name of a heading. It keeps the rule from being quietly undone by
somebody promoting the sentence back into an `h1` and then finding they have to trim its full stop
to make it look right. It is a supporting assertion, not a load-bearing one — under the control it
passes vacuously, because a screen showing nothing has no heading to fail on.

### Three failures, nine tests — the counting, explained rather than left to a reader

**Six passed under the control, and every one of them should have.**

- The four "the two files were really read" cases only parse source. The parse is not what was
  broken, so they pass either way; they exist so the other five cannot pass against empty sets.
- "an unexplained 401 is given no words at all" asserts an **absence**, and the brief is right that
  an absence passes vacuously once the feature is gone. Under the control the picker says nothing
  because it can say nothing, so this passes for the wrong reason. It earns its place on the fixed
  tree, where it is the only thing keeping `KMS-0000`'s *"We couldn't reach the server."* off the
  temple picker.
- **The interesting one: `KMS-400019` → "says what ErrorCode.java says" passes under the control.**
  Not a weakness in the test — it is the scope finding, reproduced. `AccountDisabled`'s fallback
  literals are character-for-character the catalogue's, so with the plumbing ripped out the screen
  still shows the right words. That is the whole argument of this task in one test result: *the
  disabled screen was never mute, it was a hand-copy*, and only the sentinel case one line below can
  tell the difference. It fails.

## Open question — the unexplained 401 lands on the temple picker

**Named and carried forward as its own row. Not built here, and it should not be built without
Rajeev.**

**What the app does today.** Somebody whose session has expired opens the application. The server
answers `/whoami` with a 401 and an empty body, because `TokenVerifier` deliberately refuses to say
why a token failed. `api.ts` has no code to work with, so it synthesises the envelope it uses for a
dropped connection — `KMS-0000 "We couldn't reach the server."` `auth-context` finds no matching
entry in `REFUSALS`, falls through to `no-account`, and the person is redirected to
`/choose-temple`, which asks *"Which temple do you serve at?"* — of somebody who has served at one
for a year.

**Who it affects, by role name.** Everyone. Kitchen Staff, Temple Admin, Volunteer, Super Admin — a
session expires the same way for all of them, roughly hourly if the SDK cannot refresh.

**So in plain terms:** when your session times out, the app forgets you and asks which temple you
belong to, instead of asking you to sign in again.

**What T-116 changed about it, and what it did not.** It no longer *asserts* anything false: the
picker used to be the only thing on screen and now still is, but the fall-through explicitly
attaches no words, so `KMS-0000`'s *"We couldn't reach the server."* is not printed. That was the
right call and it is tested — `refusal-words-reach-the-reader.test.tsx` has a case for it. What is
unchanged is the destination. The person is still on the wrong screen, silently.

**What I found in the code.** `auth-context.tsx`'s own comment above `REFUSALS` calls this out in as
many words — *"an expired session still lands here and is still reported as having no account. That
is known, and it is the half of this held for Rajeev's decision."* The sentence that would be right
for these readers already exists in the catalogue: `SESSION_EXPIRED`, `KMS-400018`, *"Your session
has expired." / "Sign in again to continue."* Nothing raises it. The reason nothing raises it is
deliberate and is written above `SignInPage`: telling an anonymous caller *why* a token was refused
is a small oracle, and the sign-in screen already refuses to answer a related question — whether a
given email has an account — because that would tell whoever asks which addresses are registered at
a temple.

**The strongest argument against changing it.** An expired token and a forged one are refused by the
same code path. If a 401 may say "your session has expired", it is saying "this token was
well-formed and issued by us, and is merely old" — which is a signal an attacker does not have
today. It is a weak signal, but the current silence is a deliberate choice by somebody who thought
about it, not an oversight, and reversing a security decision to improve a redirect is the wrong
trade to make casually.

**Options, with costs.**

1. **Leave it.** Free. Every expired session keeps landing on the temple picker, which is the most
   common confusing state in the product and will be reported again by testers.
2. **Let the server distinguish expiry from invalidity, and send `KMS-400018` for expiry only.** A
   backend change in `TokenVerifier` plus one line in `REFUSALS` and one status. Costs the oracle
   described above — narrow, but real, and it is a security decision.
3. **Change nothing on the server; route the fall-through to the sign-in screen instead of the
   picker.** Frontend only. The app stops claiming anything about the person and sends them to the
   door. Costs: somebody who genuinely has no account is now sent to sign in rather than to join a
   temple, which is a worse outcome for the case the picker exists for — and the two are
   indistinguishable without option 2.

**My recommendation: option 2**, and it is not close on the user-facing side; hourly expiry affects
every role every day, the oracle it costs is one bit about a token the caller already holds, and the
frontend half is already built and would need one line. But it is Rajeev's to decide because it
moves a security boundary somebody set on purpose.

**Hard to reverse:** the security posture, not the code. Once a 401 explains itself, quietly
un-explaining it later is a regression somebody will have come to rely on. The code either way is a
few lines.
