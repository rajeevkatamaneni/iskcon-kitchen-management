## Part A — `API_BASE_URL` becomes a declared input

### The value, read from the running service rather than constructed

```

    --format='value(spec.template.spec.containers[0].env.filter("name:API_BASE_URL").extract(value))'
['https://kms-staging-api-bnpkv5hfrq-el.a.run.app']
```

The hash form, as the brief predicted. The project-number form
(`https://kms-staging-api-278207420486.asia-south1.run.app`) resolves to the same service but is a
different string, and writing it would have made `plan` propose a change to a running
configuration while looking, in the diff, exactly like a repair. That is the whole distinction
this part exists to hold.

The same query against the worker returned nothing (`grep -c` → `0`), so `API_BASE_URL` was added
to the api service only — matching what `deploy.sh` used to do.

### The shape chosen, and one decision the contract forced

Mirrors `cors_allowed_origins`, as the brief suggested: a plain `var` referenced by a plain `env`
block. No `ignore_changes`, no computed self-reference, no new mechanism.

One deviation worth naming. `cors_allowed_origins` is **required** (no default). I gave
`api_base_url` `default = ""`, for two reasons and one of them is a contract boundary:

- `infra/environment/terraform.tfvars.example` — the file Step 2 tells you to copy — is **not in
  my contract**. A required variable would make a fresh environment fail at plan with *No value
  for required variable*, and I could not add it to the example to fix that.
- It is also the honest translation of the behaviour being replaced. `deploy.sh` used
  `${API_URL:+…}`, i.e. it set nothing on the very first deploy. `application.yml:154` reads
  `api-base-url: ${API_BASE_URL:}` — read-only check, no edit — so an empty value and an unset one
  are the same thing to the application. Nothing changes for a brand-new environment.

## Part B — the geocoding swap

Written **after** Part A's plan was captured, so the two claims stay separable.

In **both** Cloud Run blocks (api and worker): `GEOCODING_PROVIDER` `"nominatim"` → `"google"`;
`NOMINATIM_USER_AGENT` deleted; `GEOCODING_API_KEY` added on
`data.google_secret_manager_secret.maps_api_key` by `value_source.secret_key_ref`, version
`latest` — copied from the `PLACES_API_KEY` block above it. **No key material is in the tree**;
`grep -n "GEOCODING_API_KEY" main.tf` returns only the two `name =` lines.

Placed with the other three key blocks rather than beside `GEOCODING_PROVIDER`, because that is
the convention already in the file: the four `*_PROVIDER` selectors are grouped, and the four
`*_API_KEY` secret mounts are grouped under the comment that explains why they share one secret.

## Not done / needs Rajeev

**1. Staging verification a human has to do, and the failure is silent.** The
`kms-staging-maps-api-key` key may have console API restrictions that do not include the
**Geocoding API**, and `geocoding-backend.googleapis.com` may not be enabled on the project. This
does **not** break the boot — the new provider returns an empty result rather than raising — so
the devotee temple search would fall back to name matching with **nothing on the screen to say
why**. I did not touch GCP project configuration, as instructed. After this wave deploys, someone
should confirm the key covers Geocoding and register a temple with a typed address to see
coordinates come back. `docs/DEPLOYMENT.md` now warns about this in two places.

**2. No hand smoke-test was possible from here, and none would have meant anything yet.** The
change is inert until `terraform apply` runs, which I am instructed not to do, and the geocoding
half depends on another builder's provider class that is not merged. The plans are the only
evidence available at this point in the wave.

**3. For T-058 — found, reported, deliberately not fixed.** Three things, all pre-existing:

  min_instance_count = 0 -> null }` on api, frontend **and** worker. This is exactly the
  never-converging diff the `lifecycle` comment at `main.tf:640` (and its twin at `:970`) predicts and says was
  suppressed once and then un-suppressed because "both services now run at a managed non-zero
  minimum". They evidently do not, from the API's point of view — the worker declares
  `min_instance_count = 1` in the file and the plan still shows `0 -> null` against it. So the

  proposes nothing". It deserves its own look, not a guess folded into this task.
- **`terraform fmt` has two standing violations**, `main.tf`'s `expression =` alignment and
  `terraform.tfvars`'s `api_min_instances` group. Both are one-character whitespace fixes and both
