## API

`GET /api/v1/meal-crew/at?date=YYYY-MM-DD&readyBy=HH:mm`, behind `hasAuthority('MANAGE_MEAL_PLANS')`. Both parameters are required. Response:

```json
{ "planDate": "2026-09-07", "readyBy": "12:00:00", "staffIn": 2, "volunteers": 0, "rostered": 2 }
```

This is a separate record, not a `MealCrewView` with nulls. That record promises a meal id to open and a crew target to be short of, and neither exists before the first save.

How it counts: `MealCrewService.crewAt` builds `new MealMoment(null, date, readyBy, null, null)` and asks `WorkforceService.countAt`. That is the same call `crewFor` makes for saved meals, so the figure before and after saving is the same arithmetic.

- **Staff:** anyone whose working window covers the ready-by (template, overrides, minus leave), exactly as for a saved meal.
- **Volunteers (the existing rule):** a shift not for a meal counts if it is OPEN on that date and its start–end window covers the ready-by, both ends inclusive. A shift for a meal counts only toward that meal's id (D-14/D-27). With no id, `MealMoment.isFor` is false, so no meal's shift counts here.
- **Why this equals the figure after the save:** the only shift that can newly point at the saved meal is the one drafted with it, and nobody has signed up for that yet.
- **Read-only:** `@Transactional(readOnly = true)`, and the service writes nothing.

Frontend rule in `MealComposer.tsx`:

- **When it asks:** only when the meal has no id, the day's crew rows have answered (or failed), and no row matched. That is a new event, or a new main meal with no meal of that kind that day. The existing `matchByKind` path still wins when it matches.
- **When it asks again:** whenever the date or the ready-by changes. It only asks once the ready-by is a valid time.
- **Which answer it uses:** only one whose `planDate` and `readyBy` match what is on screen, so a slow reply for an old time is never read out.
- **On failure or no ready-by yet:** "Not counted yet", and the old full-People-needed prefill.
