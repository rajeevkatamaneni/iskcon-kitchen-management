## Defect 1 — Save refused while the bill was still uploading

**What it was.** `AttachmentUpload` uploads the file the moment it is picked and hands the parent an
`AttachmentView` when the server answers. Until then `bill` is null, while the file's name, its
thumbnail and Replace/Remove are all on the screen. `savingProblems()` read `bill` alone, so a press
inside that window produced *"Upload a copy of the bill."* — telling the person to do the thing they
had just done. It needs the press to land inside the ~1.4 s the upload takes, which is why the
staging run could not reproduce it.

**What it is now.** The box reports its in-flight state up (`onUploadingChange`). While it is true:

- Save is `busy` — refused, `aria-busy="true"`, full weight — and reads **"Uploading the bill…"**.
- `save()` returns before `setTried`, so an Enter keypress in a box cannot run the check either.
- `savingProblems()` does not count a bill in flight as a missing bill.
- the box's own "Copy of the bill is required" was already suppressed while busy; `invalid` was
  tightened to match rather than rely on that.

## Defect 5 — `whatsappEverSent` on a never-sent draft: right value, misread name

**It is not a bug, and I have changed no behaviour.** The field is a fact about the *temple*, not
about the order, and it is deliberate. `PurchaseOrderDetailView.java:17-42` says so at length, and
the service reads it from tenant settings, not from the order:

```java
return new PurchaseOrderDetailView(
        header, lines, events, whatsappSettings.hasEverSentSuccessfully(),
```

It is derived from `tenant_settings.whatsapp_last_sent_at` (V123), written only by
`TenantWhatsAppSettingsService.markMessageSent` and only after Meta returns a message id. Staging's
temple had sent WhatsApp before — the same run's staging check 3 drove a send through Quartz to Meta
— so `true` on a fresh draft is correct. What says whether *this* order went out is
`order.sentAt`, which was null on the very same payload.

**Nothing on screen relies on a wrong value.** The only read anywhere:

```
$ grep -rn "whatsappEverSent" frontend/app frontend/components frontend/lib | grep -v lib/api.ts
frontend/app/orders/[id]/page.tsx:535:   * <p>`whatsappEverSent` is a fact about the temple that arrives on this order's own payload,
frontend/app/orders/[id]/page.tsx:543:  const whatsappWorks = data?.whatsappEverSent === true;
```

`whatsappWorks` gates whether "Send on WhatsApp" is offered at all, which is exactly Rajeev's ruling
of 2026-09-10 as the code records it: shown "only after a message has actually gone through it
successfully". Showing it on a draft is the intended behaviour.

**What I added instead of a fix:** a test pinning the meaning on the one case that reads as a defect
— a DRAFT that was never sent, on a temple that has sent — asserting `order.sentAt` absent and
`whatsappEverSent` true together, then clearing the temple's send and asserting the same untouched
draft reports false. The two existing tests both used an order that *had* been sent, which is why
neither could have shown the difference.

**What I did not do:** rename the field so the name stops inviting the misreading. A rename touches
`frontend/lib/api.ts`, which is a reserved shared file I was told not to open. It needs Rajeev.
