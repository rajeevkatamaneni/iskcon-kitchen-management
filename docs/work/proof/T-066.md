## Where the acknowledgement lives, and why

**`purchaseorder/`, not `receiving/`.**

Rajeev's ruling was "a **status transition, not a stock movement**", and receiving is nothing *but*
stock: a receipt header, a batch, a `PO_RECEIPT` movement, an expiry, a price written back to
`vendor_supplies`. An acknowledgement touches none of them. It is a purchase order's own lifecycle,
in the class that already owns every other transition on it (`send`, `cancel`,
`applyReceivedStatus`).

The dependency direction settled it too. `ReceivingService` depends on `PurchaseOrderService`; the
reverse would be a cycle. Closing an order needs the completion arithmetic, which both callers now
need — so it moved to `PurchaseOrderService.isFullyAccountedFor(poId)` and `ReceivingService` calls
it. `ReceivingService.isFullyReceived` is gone; its Java loop became one SQL `count(*)`.

**Surface:** `POST /api/v1/purchase-orders/{id}/arrivals`, body `{ "poLineIds": [...] }`, 204.
Behind `MANAGE_PURCHASE_ORDERS` — the same authority `ReceivingController` already carries, because
it is the same act by the same person at the same lorry. **No new permission constant was needed or
taken.**

**Per line, not per order.** An order from a hardware shop may carry four plastic stools that came on
Tuesday and "repair the mixer motor" that happens on Friday. One button claiming both is a statement
nobody made. The screen ticks every outstanding described line by default and lets you untick.

**No arrival date on the request — a deliberate omission, and the one thing I would add next.** The
arrival is recorded as the temple's today. Letting somebody backdate ("they actually came on
Tuesday") needs a refusal for a date in the future or behind the order date, which needs an error
code, and codes are allocated rather than taken. `arrived_on` is a `DATE` separate from
`arrived_recorded_at` precisely so backdating can be added later without re-interpreting a column
that already meant something else. Listed under "Needs Rajeev".

## What I did about on-time

`countOrders` judged an order at `MIN(goods_receipts.received_at)`. It now judges it at the **earlier
of two arrivals**: that receipt, or `MIN(purchase_order_lines.arrived_on)`. An order with neither
still scores late.

That last sentence is the whole reason for doing it this way rather than by excusing described orders
from judgement — **option (b), which Rajeev rejected**. A vendor who genuinely never delivered the
stools still scores zero, and is still distinguishable from one who delivered them on the day.
`VendorPerformanceIT.anOrderOfOnlyDescribedLinesIsJudgedOnItsArrival` is that pair of vendors, side
by side, and before T-066 both of them scored 0% with no way to tell them apart.

**Fill rate is untouched.** T-060's ruling — a described line is not judged on fill, because there is
no quantity the store room could have taken in — still stands, and
`aDescribedLineDoesNotDragTheFillRateDown` still passes unchanged. Counting an *acknowledged*
described line as 100% filled would be a second, separate ruling and it is not mine to take.

## Mixed orders — my decision, and it is a behaviour change

**An order closes when every line on it is accounted for: catalogue lines by receipts adding up, and
described lines by somebody recording that they arrived.**

So a mixed order whose rice has been received but whose stools nobody has confirmed now sits at
`PARTIALLY_RECEIVED` instead of going straight to `RECEIVED`. That is the assertion I changed in
`describedLineIsNeverReceivedIntoStock`.

Reasoning, since three places in the tree document the old rule (V100's migration comment,
`isFullyReceived`'s javadoc, and that test):

- The old rule had **one stated reason** — there was no way to account for a described line at all,
  so counting one would pin the order at `PARTIALLY_RECEIVED` for ever. **T-066 removes that reason.**
  There is now an action, it takes one press, and the storekeeper is standing at the lorry with the
  answer.
- The old behaviour is a silent claim that an order is complete while a line on it has never been
  confirmed by anybody. The new one is a truthful open order that is **visible and actionable** —
  it names exactly what is outstanding, on its own screen, unlike the old dead end.
- It removes an exception rather than adding one, which is the house preference.

**The risk I am accepting, stated plainly:** an order whose described lines nobody ever ticks stays
in the aging bucket. That is a different failure from the one T-066 fixes (it is fixable in one
click, and the screen says so), but it is a real one, and it is the argument for the other answer.
**If Rajeev prefers the old behaviour it is a one-line change** —
`PurchaseOrderService.isFullyAccountedFor`, `WHEN l.ingredient_id IS NULL THEN l.arrived_on IS NULL`
becomes `THEN false` — plus reverting two test assertions.

**No stored data is re-interpreted.** Orders already `RECEIVED` stay `RECEIVED`; status is only
recomputed when a receipt or an acknowledgement happens. Acknowledgement is refused on a `RECEIVED`
order, so a pre-T-066 order that closed with its described lines noted on the trail keeps the trail
as its record rather than being reopened to tidy up.
