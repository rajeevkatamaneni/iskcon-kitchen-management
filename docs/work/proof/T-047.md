## Half one — the 500

`update()` sent the `UPDATE meal_kinds` statement with no `catch`, so the unique-index violation came
back as a `DuplicateKeyException`, reached `GlobalExceptionHandler.handleUnexpected`, and the person
who had typed an existing name was shown `KMS-500001 UNEXPECTED_FAILURE` — *"Something went wrong at
our end."* That is a technical failure reaching the user for something that is not a failure at all:
it is a typo, and `create()` has always answered the identical typo with `MEAL_KIND_ALREADY_EXISTS`.

The fix is `create()`'s, verbatim in shape — caught off the database rather than pre-checked with a
SELECT, so two admins renaming at the same moment cannot slip between the check and the write:

```java
} catch (DuplicateKeyException e) {
	throw new ApplicationException(
			ErrorCode.MEAL_KIND_ALREADY_EXISTS, Map.of("name", request.name()), e);
}
```

**Only the `UPDATE meal_kinds` statement is inside the `try`, and that is deliberate.** The cascade
that follows it touches `meal_services`, which is unique on
`(tenant_id, plan_date, meal_kind, lower(COALESCE(event_name,'')))` and can in principle raise a
`DuplicateKeyException` of its own. That would be an entirely different fault, and reporting it to a
temple as *"That kind of meal already exists"* would be a wrong answer delivered confidently. It
stays outside the `try` and keeps falling through to the 500 it belongs in.

**Case-insensitivity is the index's, not Java's.** `meal_kinds_name_per_tenant` is over
`(tenant_id, lower(name))` — created in V22 as `meal_slots_name_per_tenant`, renamed by V48 — so
"DINNER" collides with "Dinner" in the database whether or not any Java code thinks so. A Java-side
exact-match pre-check would have passed that rename straight through into the same 500, which is why
there is no pre-check and why the case is a test of its own.

## Half two — V96, and what it can and cannot do

V64's `--` comment on `meal_services.meal_kind` says the kind is stored by name because *"a temple
may delete a kind, and the meals cooked under it must keep reading as what they were."* T-038 made
that false: deleting a used kind is now refused with `KMS-400126` **precisely because** those meals
would not keep reading as what they were — four read paths re-resolve the stored name through
`MealKindService.require()` and throw `KMS-400071` for history nobody touched.

V96 alters nothing but a comment, and says so in its first paragraph so a reviewer can stop reading
there. It does the two things a fix-forward can do:

1. `COMMENT ON COLUMN meal_services.meal_kind IS '…'` — the database's own comment, which is what
   `\d+` and every schema browser show, and what tooling reads. It keeps the true half of V64's
   reason (no FK is possible against an expression index), states that it **supersedes** V64's
   comment, quotes the false clause so a reader can match it to what they saw, and names T-038 and
   `KMS-400126` as what replaced it.
2. A `--` header carrying the same correction, so anybody grepping `meal_kind` across the migration
   tree meets it as well as meeting the error.

**And the honest limit, which is written into V96 itself rather than left to this file:** an applied
migration is immutable — editing V64 changes its Flyway checksum and the application refuses to boot
— so V64's `--` text cannot be removed and **a reader of V64 will still meet the false sentence
there.** V96 says that in as many words. Precedent for a comment-only `COMMENT ON COLUMN` migration:
V57, V65, V83, V95.

## Acceptance criteria, and how each was verified

**1. Renaming a kind onto an existing name returns `MEAL_KIND_ALREADY_EXISTS`, not a 500, case-
insensitively.** Two tests, both through the real `PUT /api/v1/meal-kinds/{id}`:

- `aRenameOntoAnExistingNameIsRefused` — Lunch → `Dinner`, the exact-match case. 409, and both
  `$.code == "KMS-400047"` and `$.message == "That kind of meal already exists."` asserted, because
  a status alone would not prove the person is being told anything useful.
- `aRenameOntoAnExistingNameInAnotherCaseIsRefused` — Lunch → **`DINNER`**, the case the expression
  index makes a collision and a Java exact-match check would not. 409, `KMS-400047`.

Both also assert the rollback: Lunch is still named `Lunch` afterwards, and the kind that was
collided with still reads `Dinner` — the refused rename did not half-apply or re-case its victim.
Both return 500 with the fix patched out, which is the negative control above.

**2. Renaming a kind to its own current name still succeeds.** `aKindMayKeepOrRecaseItsOwnName`
saves `Lunch` → `Lunch` (the settings screen's ordinary save, where somebody moved the ready-by
time and left the name alone) → 204, then `Lunch` → `LUNCH` → 204, and asserts the plan row moved to
`LUNCH` with it, so a case-only self-rename is still treated as the real rename T-038 made it rather
than being swallowed as a collision. `anEditThatIsNotARenameTouchesNothing` covers the same
no-collision path from the other side and still passes untouched.

**3. V96 applies cleanly on a fresh database and on one already at V95, and changes no data.**
Fresh: Testcontainers, every context load, twelve tests ran (a bad migration would stop the context
starting). Already at V95: the throwaway container above, V1..V95 replayed as the unprivileged
migration role and V96 applied alone on top. No data: `pg_dump --data-only` diffed before and after —
identical but for pg_dump's own random `\restrict` nonce. Both pasted in full above.

**4. The eight tests T-038 left green stay green.** All eight are named in the run above and all
eight PASSED; nothing in them was edited. The only change to the existing file besides the three new
tests is that `rename(...)` now delegates to a new `renameRequest(...)` builder so the refusal tests
can perform the identical request and expect a different status — behaviour identical, and the eight
prove it.
