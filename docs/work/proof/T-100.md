## How the exception was scoped to the retry path without widening the catch-all

**Not with an `@ExceptionHandler`.** `UnexpectedRollbackException` carries nothing about *which*
transaction rolled back, so a mapping in `GlobalExceptionHandler` is a mapping for every rollback in
the application, and the sentence "We couldn't send those copies just now" would then be told to
somebody whose stock adjustment failed. That is confidently wrong rather than merely unhelpful — a
worse defect than the one it fixes. Sniffing `request.getRequestURI()` for `/retry` inside a handler
would work and is the kind of coupling that rots the first time a path changes.

**It is handled in the service, and the honest reason is a mechanical one: a method cannot catch the
failure of its own commit.** With `@Transactional`, the `UnexpectedRollbackException` is raised by the
proxy *after* `retryFailed` has returned, so no code inside it can see it. So `retryFailed` now opens
its transaction explicitly through the `TransactionTemplate` the class already holds — the same field,
for a different reason, that `send` has used since T-094 — and the body moved to a private
`retryWithin`:

```java
public RetryResultView retryFailed(AuthenticatedUser actor, UUID id) {
    try {
        return transactions.execute(status -> retryWithin(actor, id));
    } catch (UnexpectedRollbackException e) {
        …
        throw new ApplicationException(
                ErrorCode.COMMUNICATION_RETRY_FAILED, Map.of("communicationId", id), e);
    }
}
```

That puts the commit inside a method that can see it, so the translation is scoped to this one path
**by construction**. `GlobalExceptionHandler`'s catch-all is unchanged in behaviour — the only edit to
that file is a javadoc on `handleUnexpected` saying why `UnexpectedRollbackException` is *deliberately*
left to fall into it, so the next reader who finds this and reaches for a handler reads the argument
before writing one.

**Why the catch is specific and not a general "a rollback happened" mapping wearing a specific
sentence:** the only thing in `retryWithin` that can mark the transaction rollback-only *without
throwing on its own account* is `queueFor`'s catch — `notify()` is `@Transactional`, so an exception
leaving it marks the caller rollback-only however politely `queueFor` logs it and returns `false`.
Every other step in the body (`find`, `nothingToRetry`, `failedRecipients`, `auditService.record`)
throws in its own name and never reaches the catch.

## Does KMS-500005's sentence survive contact with the code?

*"Nobody was written to, so nothing was sent twice."* — **yes, and here is the reading, because the
brief was right to ask.**

1. `queueFor` reaches a devotee only through `NotificationService.notify`, which does exactly two
   things: `INSERT INTO notifications …`, then `enqueueSend` → `quartz.scheduleJob`. There is no
   direct call to a relay anywhere on this path; the actual sending is `SendNotificationJob`, run
   later by the worker.
2. `spring.quartz.job-store-type: jdbc` (`application.yml:55`), so Spring Boot installs
   `LocalDataSourceJobStore`, which takes its connection through `DataSourceUtils` and **joins the
   surrounding transaction**. The trigger row is written in the same transaction as the notification
   row and is not visible to any scheduler instance until that transaction commits.
3. So the rollback takes back the notification rows, the re-pointed `communication_recipients` rows,
   the unsubscribe tokens and the Quartz triggers *together*. Nothing was handed to the relay, and
   pressing the button again cannot produce a second copy.
4. `auditService.record` is plain `@Transactional` (not `REQUIRES_NEW`), so the audit entry rolls back
   too — "nothing has been recorded that did not happen" is literally true, and is asserted below.

**It is tested rather than believed.** `aRetryRefusedPartWayUndoesTheCopiesItHadAccepted` makes the
relay accept the first of three retried copies, throw on the second, and accept the third, then
asserts `SELECT count(*) FROM notifications` is **zero** afterwards — two copies the relay genuinely
took, written down inside the transaction, gone with the rollback. That is the assertion the promise
rests on, and it is the one a stubbed `NotificationService` could never make, because a stubbed call
never enters the transaction whose rollback *is* the mechanism.

**One caveat, stated rather than hidden:** the promise is about *this* rollback, on *this*
configuration. If Quartz's job store were ever moved to `memory`, `scheduleJob` would stop joining the
transaction and the sentence would become false without a single test going red. That is a real
landmine and it is now written into the catch block's comment where somebody changing the job store
would meet it — but a comment is not a test, and I could not write one for it inside this contract.
Flagged below.

## What I did about the state the code cannot produce

**Documented, not collapsed — and the justification is that collapsing would make the record weaker,
not simpler.**

`retried` is *derived* from what `queueFor` actually reported, and today that derivation is correct by
construction: no committing execution can have `retried < failed.size()`. Replacing it with the
constant `failed.size()` would turn a number that is *computed and true* into a number that is
*asserted*. This repo has been bitten four times in a day by exactly that shape — a claim that goes on
compiling perfectly after the thing underneath it changes meaning (`SUM(amount)` over a table that
grew a `VOIDED` state; a config default read as a deployment). If the transaction shape here is ever
changed the way T-094 changed `send`'s, the counter tells the truth and the constant lies. Keeping a
counter that can only ever equal N is harmless; hardcoding N is a landmine.

So the invariant is written down instead, at the loop, and it says the asymmetry out loud because the
asymmetry is the confusing part:

> This path is total-or-nothing, and cannot be anything else (T-100). … That is the exact opposite of
> `send()`, where partial is genuine and is the point: `send()` hands the copies to the relay outside
> any transaction (T-094), so one devotee the relay refuses leaves the other three hundred and ninety
> queued, and its `queued < audience` is a real number about a real state.

The comment names all three places the phantom shows — the audit entry's `failed`/`retried`, and
`RetryResultView(retried)` — so the audit schema's reader is warned as well as the code's. The
part-way test also asserts **no `COMMUNICATION_RETRIED` audit row exists** after the refused retry,
which is the invariant proved rather than described: the one execution that ever held `retried == 2`
is precisely the one that did not commit.
