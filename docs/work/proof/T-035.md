## What was built

**1. The wrong-role branch gains chrome and a door.** `RequireRole`'s refusal is now a `WrongRole`
component: `<Sidebar activeHref="">` beside the same "Not your page" copy, plus a `ButtonLink` to
this reader's own home.

The link goes to `homeForRole(appUser.role)` — *not* a fixed `/today`. A volunteer is refused
`/today` exactly as a cook is refused `/donate`, so a hard-coded link would have landed a refused
reader on a second "Not your page" and reproduced T-002's defect inside T-002's fix. Its label is
that destination's own row label from `nav.ts` ("Go to Today", "Go to My shifts"), read through
`navForRole`, so the button and the menu row beside it cannot come to call one screen two things.
`activeHref` is deliberately empty: the reader is not on any menu row, and highlighting one would be
a small lie on a screen whose whole job is plainness.

**2. `AccountDisabled` gains a sign-out and nothing else.** "Signed in with the wrong account? →
Use a different account", the app's own `signOut` from `lib/auth-context.tsx`, worded as
`choose-temple` words it. Still no menu and still no retry.

**3. The note in the code about why the three branches differ.** A block comment on the file's guard
doc, so the next reader cannot tidy them into consistency without arguing with it:

> - **Wrong role — sidebar, and a link home.** Everything else in the application still works for
>   this reader; they are simply standing at one door that is not theirs.
> - **Disabled — no sidebar, but a sign-out.** A menu is a list of things to do, and there is nothing
>   this person can do here until access is given back; drawing it would offer twenty doors that all
>   refuse them. Signing out is the exception, and the reason is in the same sentence: the one useful
>   act left to somebody who cannot use this account is to stop using it.
> - **Unreachable — neither.** A working menu over a server that is not answering is decoration on a
>   dead app, and signing out of an app that cannot reach its server helps nobody.

## Two things I decided, that the row left open

**(a) The link's destination and label, above** — `homeForRole`, not `/today`.

**(b) A real defect the work uncovered: an unknown role blanked the refusal screen.** The first full
run failed one shipped test, `occasions.test.tsx > refuses every role but Temple Admin`, with:

```
 FAIL  __tests__/occasions.test.tsx > festival occasions > refuses every role but Temple Admin
Error: Failed prop type: The prop `href` expects a `string` or `object` in `<Link>`, but got `undefined` instead.
 ❯ key node_modules/next/src/client/link.tsx:338:7
```

That test loops over `["KITCHEN_MANAGER","KITCHEN_STAFF","VOLUNTEER","ACCOUNTANT","SUPER_ADMIN"]`,
and `ACCOUNTANT` is not in `PrincipalRole` — so `homeForRole` fell off its exhaustive switch and
returned `undefined`. It is an invented role in a test, but it is also exactly what a server that
starts sending a new role ahead of a frontend deploy looks like, and the screen it would break is the
one a mismatched reader lands on. So `WrongRole` falls back to `/` (the landing router, which knows
what to do with anybody) labelled "the home page", commented as to why, and the new test file asserts
it against that same invented role. `occasions.test.tsx` was not touched and passes.

**The mid-wave widening I was offered and declined.** Part-way through, the work manager granted me
`frontend/__tests__/occasions.test.tsx`, on the diagnosis that its wholesale `@/lib/auth-context`
mock supplies no `signOut` and so breaks against the new `AccountDisabled`. Recorded here because it
happened, and declined because the diagnosis does not hold: that test's status is `signed-in`, so
`AccountDisabled` — the only branch that reads `signOut` — never renders in it. The failure was the
`href` above, in my own file, and fixing it there left the granted file untouched and green. I have
replied to the work manager saying so. No shipped test needed repairing.

  it is the only one where the fix is a button that ends a session.
- **A correction to the row's survey, which the row asked not be redone.** It says 28 guarded pages
  "render no sidebar at all". They render one — `FocusScreen` draws it (rule 2 of the eight it
  enforces is *the sidebar stays*); the grep behind the number looked for `<Sidebar>` in the page
  file. Measured: 81 page components mount the guard — 54 with their own `<Sidebar>`, 24 with
  `FocusScreen` in the page file, 3 delegating to a component that uses it. The load-bearing half of
  the survey is exactly right and is what makes this safe: **not one of them draws chrome above the
  guard**, so no page can end up with two menus. The fix's shape is unaffected — a refused reader
  reached none of that chrome, because all of it sits below the guard — but the sentence "the 28
  chromeless ones strand a reader worst" is not true as written, and the same is now noted in the
  code so the next reader is not misled by it.
- **Not attempted, and arguably next:** the `AccountDisabled` doc comment still says it would be
  tidier in `components/` of its own. Left where it is — out of contract, and moving user-facing copy
