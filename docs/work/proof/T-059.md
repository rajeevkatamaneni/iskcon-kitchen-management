# T-059 — A picked coordinate is cut to six decimals where Google's number is read, and the screen prints what it is given

The provisioning screen filled Latitude with `12.285518000000001` for ISKCON - Mysuru and the
confirmation card above it printed the same string. The brief was right that this is not our
arithmetic: the fix is two call sites, both at the boundary where a Google reply becomes a
`GeocodingProvider.Coordinates`. **The frontend page needed no change**, and that is argued below
rather than assumed.

**Files changed:** all four inside the contract; nothing else in the tree is mine.

## Did the page need a change? No, and here is the reading that settled it

Both things the brief asked me to establish:

1. **The card and the input read from one value, not two.** `picked` is a single piece of state set
   once from the server's reply (`page.tsx:82-89`). The card renders `{picked.latitude}, {picked.longitude}`
   and the *Use these coordinates* button does `setLatitude(String(picked.latitude))`. React's number
   rendering and `String()` are the same conversion, so the two agree character for character by
   construction, not by coincidence.
2. **Nothing stores more precision than it displays.** Submit sends `Number(form.get("latitude"))` —
   the value in the visible box, not `picked`. There is no second, unrounded path. `AddressPicker`
   (`components/planner/AddressPicker.tsx:150-155`) copies `resolved.at.latitude` straight through,
   and `lib/api.ts` types it as a plain `number`.

So rounding at the provider is sufficient and the honest outcome is to leave the page alone. What I
added instead are two tests that *keep* it a pass-through, because the obvious wrong fix — a
`toFixed(6)` on the screen — would pad every honest coordinate and would put a different string in
the box from the one on the card. The negative control below shows that guard biting.

## The geocoder: it does have the defect, one decimal milder, and I have output for that

I did not take it on faith either way. Google's Geocoding API renders seven decimals, so it never
produced the seventeen-digit string Places did — but seven is still one more than anything stores.
The negative control makes this concrete: with the rounding patched out, the geocoding test failed
with `longitude=76.6340866`, i.e. the unrounded provider really does hand seven decimals to its
callers. Both providers answer with the same `Coordinates` record and both feed `NUMERIC(9,6)`
columns (`tenants.latitude` V1, `meal_plans.delivery_latitude` V88), so leaving one uncut would mean
the precision depended on which service answered. Cut in both.

## Acceptance criteria

| Criterion | How it was verified |
|---|---|
| A picked coordinate with float noise fills the field with six decimals | `aPickedPlaceIsCutToSixDecimals` and `theWireCarriesTheSixDecimalNumber` — the second asserts the serialised JSON the browser receives contains `"latitude":12.285518` and **not** `12.285518000000001`, against the Mysuru reply digit for digit. The field is that value stringified. |
| The card and the field agree character for character | Read: one `picked` state, rendered by React in the card and by `String()` into the box. Tested: `shows the coordinates exactly as the server sent them…` finds the text `12.285518, 76.634087` and then asserts both input values are `"12.285518"` / `"76.634087"`. |
| An already-short coordinate is not padded | `alreadyShortCoordinatesAreNotPaddedOut` (backend, asserted on the JSON as well as the double) and `leaves a coordinate that is already short exactly as short as it arrived` (frontend). Both stay green under the patch-out and both fail under `toFixed(6)` — which is the discrimination that matters. `BigDecimal.valueOf(...).setScale(6, HALF_UP).doubleValue()` rounds; the trailing zeros the scale introduces do not survive the return to `double`. |
| The geocoding path checked, and fixed with it if it has it | It has it — seven decimals, evidenced by the control's `longitude=76.6340866`. Fixed, with `geocodedCoordinatesAreCutToSixDecimals` and `shortGeocodedCoordinatesAreLeftAlone`. |

## Findings you asked me to check, and one you did not

**The audit trap is already handled, in both places, and I confirmed it rather than assuming.**
`TenantProvisioningService.snapshot()` records slug, name, timezone, currency, 80G and the first
admin — **it does not record latitude or longitude at all**, so nothing there can claim a coordinate
moved. `TenantUpdateService.loadSnapshot()` reads both halves from the row (`SELECT … latitude,
longitude …`, called before and after the write) and stringifies them precisely because the scale is
the value; its javadoc names the wave-4b defect by hand. Neither is affected by this change and
neither needed touching.

**The database was already doing this cut, silently.** `tenants.latitude` is `NUMERIC(9,6)` (V1) and
`meal_plans.delivery_latitude` is `NUMERIC(9,6)` (V88). `12.285518000000001` was never stored — the
column rounded it on insert. So this task did not change what any temple's row holds; it made the
number the operator is asked to confirm the same number the row was always going to keep. That is a
better argument for the change than "it looks untidy", and it is the reason no migration or backfill
is required: existing rows are already six decimals.

**One thing I could not avoid duplicating.** `sixDecimals` is a five-line private static in each
provider. The right home is a shared helper — most naturally a factory on
`GeocodingProvider.Coordinates`, so no provider behind that port can hand back a precision the port
does not promise. That file is a port interface and explicitly outside my contract, and creating a
new file in `geo/` is not on my list either, so I duplicated rather than widen the contract myself.
Each copy carries a comment pointing at the other. **If you want it deduplicated, grant
`GeocodingProvider.java` and it is a ten-minute follow-up.**
