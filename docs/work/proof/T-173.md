## The endpoint

`GET /api/v1/settings/whatsapp/templates/meta-comparison`, `@PreAuthorize("hasAuthority('MANAGE_TEMPLE_SETTINGS')")`.

Response record: **`WhatsAppTemplateComparison.Report`** `{wabaId, language, templates}`, where `templates` is a list of **`WhatsAppTemplateComparison.Entry`**, one per `NotificationTemplate` in declaration order:

- `name`, `ourCategory`, `metaCategory`, `metaStatus`
- `held`: true or false; **null** when Meta did not answer for that template, because then nobody knows
- `bodyMatchesExactly`: `String.equals`, character for character; null unless held
- `bodyMatchesAfterTrim`: `ours.strip().equals(theirs.strip())`, the exact test `bringUpToDate` makes before it edits (it uses `strip()`, not `trim()`); null unless held
- `metaBody`, `ourBody`: only where the exact match fails, otherwise null. `metaBody` is exactly as Meta sent it.
- `lookupProblem`: added so "Meta unreachable for one template" can say so. Null when Meta answered; otherwise one of two plain sentences ("Meta could not be reached for this message." or "Meta answered with an error when asked for this message. The reason is in the log."). Meta's own text goes to the WARN log only.

Nulls are serialised as explicit `null`, so every entry always has all ten keys (a test pins the key set).

Not connected: `KMS-400001` with context `field: phoneNumberId`, as Test and Reload. Connected with no stored token: `KMS-400001`, `field: accessToken`, as Reload. The field is in the log's context, not the response body, which is how `ApplicationException` works for Test and Reload too.

**Constructor note.** The controller now takes `WhatsAppTemplateComparison` in its `@Autowired` constructor. Three test classes build the controller by hand with two arguments, and two of them (`WhatsAppTemplateSubmissionIT`, `WhatsAppTestSendIT`) are not mine to edit. So I kept a **package-private** two-argument constructor that passes null. Nothing outside the package can use it, and Spring uses the `@Autowired` one. Once those tests pass a comparison, it can be deleted.

## Lookup versus list: lookup, and why

It calls `MetaWhatsAppClient.findTemplate` once per template (20 GETs). One list call would be one request, but it would be a different request from Reload's, parsed by new code, and paged by Meta. The question is what Reload reads when it compares. Only the same URL, the same name-and-language match and the same BODY parsing answer that honestly. 20 sequential GETs is a few seconds for a request made once by hand.

## Could `findTemplate`'s parsing hide a difference?

No, not towards a false match. It reads the BODY component's `text` with Jackson `asText()`. JSON escapes are decoded (that is what Meta holds), and nothing is trimmed, joined or normalised. The IT proves it: Meta sending `" " + body + "\n"` comes back in `metaBody` with the space and newline intact.

Three things it does that can make a template read as **not held** (never as matching), so worth knowing when reading staging's answer:

- It keeps only an entry whose name **and language** are exactly ours (`en`). If Meta stored the language as `en_US`, every template would read `held: false`.
- If Meta ever listed two BODY components, it takes the last.
- It reads only the first page of Meta's answer to the name filter.

So T-169a's comparison and this read cannot agree for the wrong reason. The only loosening in Reload is `strip()`, and this report shows both the exact result and the stripped one.

## Every "never", and the test that proves it

- **No `createTemplate`, no `editTemplate`, no POST to Meta.** The stub counts every request by method. `tearDown` asserts zero POSTs (and zero other non-GET requests) after every test. `@AfterAll noTestInThisClassPostedToMeta` asserts the sum across the class is zero. The counter is shown to be live: "all twenty held and identical" asserts exactly 20 lookups at the stub.
- **No write to `tenant_settings`.** "the tenant_settings row is identical before and after" reads every column (listed from `information_schema`, each cast to text) as `kms_app` through RLS, before and after, and compares the maps. The row is seeded by SQL, not by a Save (a Save would POST), with a value in every column a template send writes: fingerprints (one null), refused list, `whatsapp_templates_submitted_at`, both sent-account ids, `whatsapp_verified_at` and `updated_at`. The test asserts none is null or empty before it starts, so a write can't pass by writing what was already there. It also asserts no audit row. The status is asserted **last**, so a write PostgreSQL refuses still shows whether the row moved.
- **Structurally, no path to a write at the database.** `compare()` is `@Transactional(readOnly = true)`. "compare runs in a read-only transaction, which PostgreSQL itself refuses to write in" checks the annotation. Through the app's own transaction manager it also shows `SHOW transaction_read_only` = `on` and an UPDATE failing with "read-only transaction".
- **No `submitTemplates`, `bringUpToDate` or `reloadTemplates`.** The comparison doesn't hold `TenantWhatsAppSettingsService` at all. "the comparison holds only a JdbcTemplate, the secret store and the Meta client" pins its instance fields by reflection and checks no constructor takes the service. Every test's controller is built with the settings service as **null**, so a call to it would fail. And each of those three methods POSTs a registration for every template, which the zero-POST check would catch.
- **Token never logged or returned.** Every log event of every test is captured at the root logger, with `MetaWhatsAppClient` and the comparison raised to DEBUG. `tearDown` asserts no message or stack trace contains the token, and no response body does. The stub proves the token was really used: every `Authorization` header it saw is `Bearer <token>`.

The other acceptance cases, one test each: all twenty identical; outer whitespace only (exact false, after-trim true, `metaBody` as sent); differing inside (both false, both bodies exact, the other 19 still exact); not held (with `volunteer_shift_reminder` listed by the partial name filter, `shift_reminder` still reads `held: false`); held as MARKETING (both categories shown, body still compared); Meta drops the connection for one template and answers HTTP 500 for another (both entries say so, the other 18 answer); unconnected temple gets `KMS-400001`, with `context={field=phoneNumberId}` in the handler's log and zero requests to Meta; a Volunteer gets 403 `NOT_PERMITTED` through Spring Security's real `@PreAuthorize` interceptor with zero requests to Meta, while a Temple Admin through the same proxy gets 200.

## How to read the answer

**Safe to press Reload** looks like this:
- `language` is `en`, and `notAnswered` is 0.
- Every held template has `bodyMatchesAfterTrim: true`. Best case, `exact` is 20. `trimOnly` above 0 is also safe, because Reload strips before comparing and won't edit those. It does tell us Meta trims.
- `notHeld` entries are fine. Reload registers them as new templates, which is not an edit and uses no edit allowance.
- `metaCategory` differing from `ourCategory` (expected for `donation_thank_you` and `wishlist_gift_split`) is not a reason to stop. Reload can't change it and doesn't try.

**Don't press it** if any of these show:
- Any template in the second jq output whose `metaBody` and `ourBody` say the same thing and differ only in form: curly versus straight quotes, `{{ 1 }}` versus `{{1}}`, collapsed spaces or newlines, escaped characters. That means Meta normalises, and Reload would reword every such template and spend its edit for the day, every time it's pressed. That needs a fix to the comparison first.
- `notHeld` near 20 with `language` `en`. Likely Meta stores the language differently. The comparison, and Reload's own lookup, would then not find anything.
- `notAnswered` above 0. Run the comparison again before deciding; the WARN log names the reason.

**A genuine wording difference is not a reason to stop.** If `metaBody` is an older sentence (for example T-159's pre-rewording text) and `metaStatus` is APPROVED, that's the edit Reload exists to make. It uses that template's one edit for the day, as intended. A `PENDING` or `IN_APPEAL` template is never edited by Reload.
