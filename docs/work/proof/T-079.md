# T-079 — an attendance mark can be changed, one named volunteer at a time, on the audit trail

## The shape chosen, and why

**A separate per-volunteer endpoint — `PUT /api/v1/shifts/{id}/attendance/{userId}` with
`{"attended": true|false}` — and not the blanket `POST .../attendance` behaving differently the
second time.**

The existing refusal is load-bearing and I kept it exactly as it is. The blanket path is a screenful
of `defaultChecked` ticks committed in one press; if a second press overwrote the first, a
coordinator opening an already-marked roster days later and saving out of habit would replace every
considered answer with a remembered one, silently and for the whole crew. `KMS-400139` still refuses
that. The correction path cannot do it: it names one volunteer and one answer, so the smallest thing
it can get wrong is one person, and every use of it is a deliberate statement rather than a re-sweep.
`ShiftAttendanceIT.secondMarkingRefused` is untouched and still green.

PUT rather than POST because it *sets* one person's answer: asking twice leaves the same state, which
is what a second press on a slow connection should do. Asking for the answer the row already gives
writes nothing at all — no row change, no audit entry — so a double press is not filed as a
correction.

**No compensating entry, per ruling 15, and nothing in the implementation reaches for one.** A
corrected meal compensates because real goods left the store on the strength of the number and the
ledger is append-only. An attendance mark moves nothing: `shift_signups.attended` has exactly one
reader in the whole codebase (`ShiftService.roster`, live), and there is no stored reliability or
hours-contributed figure anywhere to go stale —

## How a coordinator who submitted a partial list recovers

Nothing about that case is special any more, which is the point.

1. The coordinator saves `marks` naming three of five. The other two keep `attended = NULL`.
2. Any later blanket marking is still `KMS-400139` — unchanged, and correctly so.
3. The roster screen now shows, on **every** active row of a marked shift, a button for each answer
   the row does not currently hold. The two omitted volunteers read "Not marked" and carry **both**
   buttons ("Mark as came" / "Mark as did not come"); the three already marked carry the single
   opposite one.
4. One press each and they are marked. The write takes `attendance_recorded_at` like any other first
   answer and leaves the correction columns null — **a first answer is not a correction of one** —
   while the act itself is on the audit trail either way.

Covered end to end by `ShiftAttendanceIT.aPartialMarkingIsRecoverable` (which reproduces the trap
first: partial save, then the `KMS-400139` refusal, then the recovery) and by
`shift-attendance.test.tsx` → *"offers both answers to somebody the marking left out, and marks
them"*. **I did not add the rule that `marks` must name every active signup**, as instructed.

## What the migration does

`V110` adds `attendance_corrected_at` + `attendance_corrected_by` to `shift_signups` (the pair the
dispatch reserved), a `shift_signups_correction_follows_recording` CHECK, and no backfill — NULL
already means "nobody has changed this mark", so there is no cross-tenant UPDATE to get wrong under
RLS. `attendance_corrected_by` is `ON DELETE SET NULL` and deliberately **not** in the CHECK, for the
reason V106 gives: the FK's own UPDATE would otherwise violate it and deleting a user would fail at a
baffling distance. `attendance_recorded_at` is never rewritten by a correction — it says when the
shift was marked, which is what the screen prints under the table.

### Why 4 of 6 and 3 of 5, and not 6 and 5 — the counting rule

**Two backend tests passed under the control on purpose, and neither is vacuous.** *"a correction
with no answer in it is refused"* (400) and *"a volunteer cannot change an attendance mark"* (403)
exercise the **controller** — the `@NotNull` boxed Boolean and the `@PreAuthorize` — which the
control deliberately left intact, since it patched out the service body only. They would have failed
had I stripped the endpoint instead, and they are the two tests that should keep passing if the
service is ever rewritten.

**Two frontend tests passed *vacuously*, and this is the absence-assertion case lesson 4 asks to be
declared.** *"offers no change while the marking itself is still to be done"* and *"offers no change
on a cancelled shift"* assert that the correction buttons are **not** there; with
`canCorrectAttendance` forced to `false` they are never there, so both pass for the wrong reason.
The first has a positive assertion beside it ("Save attendance" is still offered) which is why it
still says something; the second does not, and a reader should count it as one assertion of an
absence rather than as evidence.
