## What changed

**1. Nothing ticked when the panel opens.** `defaultChecked` is gone from the arrivals checkbox.
The comment above it that justified the old default has been replaced with one that records the
defect, because the old reasoning ("somebody opens this because the goods are in front of them")
reads as sound until you notice it makes the irreversible answer the default one.

**2. The empty case: the button stays enabled and the screen answers in words.** Not disabled.
Three reasons, in the order they weigh:

- *Nothing technical can reach the user either way.* `recordArrivals` already returned early on an
  empty selection before this task started — `if (poLineIds.length === 0) { setActionError(...)
  return; }` with the message *"Tick what arrived. Leave a line unticked if it hasn't."* So the
  endpoint's `@NotEmpty` was already unreachable from this screen. The choice here is not between
  a validation error and something better; it is between a sentence and silence.
- *A greyed button is silence.* A storekeeper who presses it is told neither what is wrong nor
  what to do, and there is nowhere on a disabled control to put the sentence that would tell them.
- *The receiving panel directly above does exactly this, for exactly this case* — an empty
  receiving form is refused with *"Enter what arrived on at least one line."* over an enabled
  button. Same screen, same mistake, same answer. Matching the surrounding code decided it.

Disabling would also have meant making the checkboxes controlled — React state per line, purely to
grey out a button — which is machinery bought for a worse outcome.

I did **not** build an undo path, and I did not want one. The write-once endpoint is now only ever
reached by a deliberate act, which is what makes it acceptable that it is write-once.

**3. The panel's wording — changed, and it is a proposal, not a decision.** The old third sentence
was reassurance aimed at a panel that had already ticked everything on the reader's behalf. With
nothing ticked, the panel had to *ask* for the tick and said nothing at all. Now:

> The store room doesn't track these, so they can't be received into stock — but the order isn't
> finished until somebody says whether they turned up. **Tick only what has arrived. Anything left
> unticked stays here for next time, and recording it changes nothing in the store.**

The first two sentences are untouched; they still orient. What is new is the instruction, and the
promise that unticking costs nothing — which is the fact that makes it safe to record the stools
today and the mixer repair on Friday, and it is true: the panel keeps offering a line until
`arrivedOn` is set (asserted by the existing "stops offering a line somebody has already recorded"
test). Rajeev judges copy; this is one line in one file and he can overrule it with an edit.

**4. Pluralisation.** There is **no** general pluralisation helper in this app. What exists is a
per-site inline conditional — `format.ts:289` `days === 1 ? "day" : "days"`,
`EquipmentWords.tsx:70`, `KitchenForm.tsx:35`, `SessionGuard.tsx:151` — five sites, five copies.

The actual defect is in `lib/format.ts`: `quantity()` names its unit from `UNIT_LABEL`, which holds
one label per unit, so `PIECES` is always `"pieces"`. `PIECES` is the only unit this can happen to;
the other four are a mass or a volume and "1 Kg" and "1 ml" are what a person says.

`lib/format.ts` is outside this contract, so I added `quantitySaid()` local to the page and pointed
every `quantity()` render site on the screen at it — all eight, not only the two named, because a
screen that says "1 piece" in the arrivals panel and "1 pieces" in the deliveries table two
sections down is worse than one that is consistently wrong. It compares the number and unit rather
than the rendered string, since `quantity()` promotes 0.6 Kg to 600 gm and its output is not this
file's to predict; `PIECES` is the one unit it can never promote.

**This is a local patch on a shared defect and should not stay one** — see *Needs Rajeev* below.

## Not done / needs Rajeev

**The pluralisation fix is local and the defect is not.** `UNIT_LABEL.PIECES` in
`frontend/lib/format.ts` makes "1 pieces" print on every screen that shows a count — stock,
receipts, recipes, the shopping list. `quantitySaid()` fixes this one page. The real fix is in
`format.ts` (either a singular column in `UNIT_LABEL` or the same test in `say()`), and it belongs
to a task that owns that file and can run the suites of everything that reads it. **I could not
take it: `lib/format.ts` is outside this contract.** Worth a ledger row.

**A rate still reads "per pieces".** On the same panel's neighbour, the receiving table, `unitLabel`
prints `optional, per pieces` and `expected ₹250 / pieces`. That is a different sentence from a
quantity — the right words are "per piece" — and it is the same shared table. I left it: it is not
in the brief, it is not on the arrivals panel, and it wants the same `format.ts` fix above rather
than a second local patch. Noting it rather than fixing it.

**The wording is a proposal.** I changed it rather than leaving it, per the brief, but Rajeev judges
copy and I have not seen it in a browser at the panel's real width.

**No hand smoke-test.** The change is not deployed — I do not deploy — and I did not stand the app
up locally against a purchase order carrying described lines, so nobody has yet pressed this button
with a mouse. The tests render the real component and assert the real DOM, which is not the same
thing. This is the Commandment 5 smoke test outstanding, and it should happen on the deployed
screen: open a SENT order with two or more described lines, confirm the boxes are empty, press
"Record as arrived" with nothing ticked and read the message, then tick one and confirm only that
line gains an "Arrived" date.

**I did not build an undo path** and do not think one is needed now. Recorded here because the
brief asked to be told if I wanted one.
