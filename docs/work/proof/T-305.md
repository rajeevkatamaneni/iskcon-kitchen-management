# T-305 — The first count on a new item no longer needs a Temple Admin

Rajeev, Decisions Desk Q-22, 2026-09-19: "The first count on a new item isn't an adjustment: anyone who manages
inventory can enter it. Later corrections keep the 20% rule."

**Files changed** (both inside the contract):
- `backend/src/main/java/org/iskcon/kms/inventory/InventoryItemService.java`. `adjust()` is now a thin public
  wrapper that calls a private `adjustStock(..., firstCountOfNewItem)`, always with `false`. `create()` passes `true` only when
  its ingredient has no row at all in `stock_movements` (new `hasAnyMovement`). When the flag is true, the Temple Admin check on a
  large adjustment is skipped. Nothing else changes: the value (KMS-400161), the unit family, the market rate set as STOCK_TAKE,
  one transaction, and the STOCK_ADJUSTED audit row are all as before. The decision is quoted and dated in the comment in `create()`.
- `backend/src/test/java/org/iskcon/kms/inventory/InventoryOpeningCountIT.java`. The old test "a first count kitchen staff may not
  make is refused" is replaced by 5 tests: Kitchen Staff and Kitchen Manager add with a first count (stock 40, note, market rate 62
  STOCK_TAKE, history row, audit row); Volunteer refused 403 with nothing written; an existing item at zero, counted +40 by Kitchen
  Staff, is refused KMS-400025; an ingredient that was tracked, written off, removed and re-added is still refused KMS-400025 with
  the re-added item rolled back.

The frontend is not touched, because no message changed.

**Movement reason:** still ADJUSTMENT / COUNT_CORRECTION with the existing note "Opening count, when the item was added to
inventory." `AdjustmentReason` has no opening value, and adding one would need a migration to widen the CHECK constraint. So no
migration and no new enum value.

**Acceptance criteria**
- Kitchen Manager and Kitchen Staff can add a new item with a first count, and stock, value and market rate are all set: covered by
  2 ITs, and by the Kitchen Manager drive above.
- An existing item at zero, adjusted by Kitchen Staff by a large amount, is still refused with KMS-400025: covered by an IT. Driven
  as Kitchen Manager through the API.
- Volunteer refused: covered by an IT (403, nothing written).
- The value is still required: the existing KMS-400161 ITs still pass.
- Still one transaction: the refusal ITs still assert that nothing is left behind.
- Negative controls: shown above.

- The first count is still recorded as COUNT_CORRECTION and still writes a STOCK_ADJUSTED audit row, so there is a record of who entered it.
