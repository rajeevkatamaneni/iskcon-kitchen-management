## Did I confirm the product is correct?

Yes, independently, before touching anything. Read `UnsubscribeTokens.java`
(`backend/src/main/java/org/iskcon/kms/communication/UnsubscribeTokens.java`): a token is
`base64url(payload) + "." + base64url(HMAC-SHA256(payload))`, both encoded with
`Base64.getUrlEncoder().withoutPadding()`. `verify()` decodes the tag and compares with
`MessageDigest.isEqual` against a freshly recomputed HMAC — constant-time, no early return, and it
never trusts anything from the request except the token string.

The tag is 32 bytes. Base64 processes 3-byte groups into 4 characters; 32 = 10×3 + 2, so the last
two bytes (16 bits) are encoded into the *final* 3 characters of the 43-character tag using 18
bits — 2 of which are padding zero-bits that a padding-less decoder simply discards. I worked out
the bit layout by hand: of those final 3 characters, only the very last one has any discarded
bits (its low 2 of 6); every other character position in the whole tag — including the
second-to-last — is fully load-bearing.

The old test forged a tamper as `token.substring(0, len-2) + "xy"`. For that forgery to
accidentally decode to the *same* tag as the original, two things both have to be true of the
*real* token's tail: its second-to-last character must already be `x` (probability 1/64, since the
substring drop only removes it if it differs, and it doesn't the literal `x` is reappended in the
same slot) and its last character must fall in the same 4-way group as `y` (bytes that share `y`'s
meaningful top-4 bits — the set is exactly `{w, x, y, z}`, since `y`'s alphabet index is 50 and the
group is `floor(50/4)*4 .. +3` = 48..51 = `w,x,y,z`; probability 4/64 = 1/16). Combined:
1/64 × 1/16 = **1/1024**, exactly the rate quoted in the dispatch, and it fell out of the
byte-layout math rather than being fitted to it — good sign the model is right.

I verified this with a standalone program (not part of the repo — see `control-T-093.log` below)
that reproduces the same base64url tag encoding, deliberately constructs a token whose tail hits
that exact triggering condition, and shows the old forgery decoding to **bit-for-bit identical**
bytes as the original, i.e. the forger's tag genuinely is the real signature — it has not broken
anything, it has just failed to change anything. **The product is correct; the test's forgery was
sometimes a no-op.**

## What I changed

In `CommunicationIT.java`:

1. Added a private static helper `tamperTag(String token)` that flips one character in the
   **middle** of the 43-character tag (`tag.length()/2`) rather than its tail — a position where,
   per the analysis above, every one of the six bits is load-bearing, so any change to it
   deterministically changes the decoded bytes. Javadoc on the helper explains why the last
   character specifically is unsafe to touch, citing T-093.
2. Added `decodeTag(String token)`, a one-line helper that base64url-decodes a token's tag half,
   used to assert on actual bytes rather than string equality.
3. In `unsubscribeNeedsNoSessionAndCannotBeForged` (the test named in the dispatch), replaced the
   old tail-splice forgery with `tamperTag(token)`, and — this is the actual fix, the character
   position is just the mechanism — added an assertion **before** the HTTP call that
   `decodeTag(tampered)` is not equal to `decodeTag(token)`, with an `.as(...)` message saying the
   test is vacuous otherwise. If a future change to the token format (different tag length, a
   padding change, a different split character) broke this premise again, this assertion fails
   loudly instead of the test silently passing for the wrong reason.
4. Added a new test, `tagTamperNeverCollidesAcrossManyTokens`, which loops 5,000 times issuing a
   real token from the real `UnsubscribeTokens` bean for a fresh random tenant/user/category each
   time, and asserts `tamperTag` never collides with the original. This is the "cheaper way"
   named in the acceptance criteria in place of literally re-running the full HTTP test 1,000
   times (see below for why, and what I ran instead).

## Why 5,000 in-process iterations instead of 1,000 full HTTP runs

The dispatch itself offers this as an acceptable substitute: "exercising the forgery function
directly over many generated tokens rather than the whole HTTP test." I took it because the
property being tested — that changing a fully-loaded base64 character always changes the decoded
bytes — is a **mathematical certainty**, not a statistical one: it doesn't need 1,000 trials to
become confident, it needs one trial per distinct code path, and there is only one path
(`tamperTag` always touches the same, middle, position). 5,000 iterations over independently
random tenant/user UUIDs (and alternating category/`null`) is overkill for a deterministic
property, but it costs milliseconds and it is honest: it doesn't claim to be a statistical
argument dressed as a large number.

I did **not** rely on that alone, though. I also ran the actual fixed HTTP test
(`unsubscribeNeedsNoSessionAndCannotBeForged`, inside the full `CommunicationIT` class, each run
booting a fresh Spring context and a fresh Testcontainers Postgres) **15 consecutive times**
end-to-end. 1,000 such runs would mean 1,000 full Testcontainers boots — impractical to do without
holding the shared `work-lock` for hours while three other builders (T-082, T-021, T-092) wait on
it — but 15 is a real, not hypothetical, repeated-execution check on top of the mathematical one.

## Negative control

`docs/work/proof/control-T-093.log` (standalone Java program, `ControlT093.java`, run outside the
repo in the scratchpad — not part of `backend`'s classpath or build, does not touch any file in
the path contract) does the honest control described in the task rather than the weak one:

- **Part 1** deliberately constructs a 32-byte tag whose base64 encoding hits the exact triggering
  tail condition (second-to-last char `x`, last char in `{w,x,y,z}`), then shows:
  - the **old** forgery (`substring(0,len-2)+"xy"`) decoding to **bit-for-bit identical** bytes as
    the original — `OLD forgery collides with original: true`
  - the **new** forgery (middle-character flip) on the same tag decoding to different bytes —
    `NEW forgery collides with original: false`
- **Part 2** sweeps 200,000 independently random 32-byte tags and tallies collisions for both
  forgeries:
  ```
  OLD forgery collisions: 199  (approx 1/1024 = 195 expected)
  NEW forgery collisions: 0  (expected 0, always)
  ```
  199 observed against 195 expected at 1/1024 over 200,000 trials confirms the probability model
  derived above, and 0/200,000 for the new forgery is exactly what a mathematical (not
  probabilistic) guarantee predicts.

This is the control the task asked for, not the "revert the fix and watch it still pass most of
the time" control, which the task correctly calls weak and which I did not use as evidence.
