## Decisions

- **Fields from the other method are ignored, not refused.** A proof id sent with cash, or a receiver name or cash photo sent with UPI, is neither stored nor claimed. The upload stays unclaimed, like any abandoned upload. Why: the form swaps these boxes when the method changes, so a stray field is a file picked before the method changed. Refusing it would put an error against a box no longer on screen. Tested both ways.
- **The required messages** follow `formMessages.required(label)`, using the mock's labels, plus the full stop that server-side field errors carry: "Proof of payment is required.", "Received by is required.", "Signed note is required.", "Photo of the person who took the cash is required.". Field names are the request's own. All missing fields are named in one answer (KMS-400001).
- **Proof is checked before the invoice is read**, so a missing file is reported in the same step as other form errors. Consequence: an unfinished form against an already-paid bill gets the field error first, then KMS-400070.
- **A negative amount (the hand-entered correction V40 allows) needs no proof**, the same as a reversal: no money moves. The form never sends one. Reversal is unchanged.
- **Order in the transaction:** insert the payment row, then claim each file, then restate status, then audit. The claim's FK and its `SELECT … FOR NO KEY UPDATE` on the payment need the row to exist. The append-only trigger is on UPDATE/DELETE and neither fires it. A refused claim rolls the payment back, and so does a refused *second* cash claim after the first had succeeded (tested).
- `/api/v1/payables` untouched. `recordedByName` keeps its name.

## Acceptance criteria

- UPI without proof: field error (also BANK_TRANSFER and CHEQUE). With proof: saved and claimed. Tested in `aNonCashPaymentWithoutProofIsRefused` ×3 and `aUpiPaymentWithProofIsSavedAndClaimsIt`.
- Cash without each of the three: one field error each (×3). All three missing, or a blank name: all named at once. Tested in `blankNameAndEverythingMissing`.
- Cash with all three: saved, `received_by_name` stored trimmed, both files claimed, invoice PAID, and the audit entry names the receiver and 2 file ids.
- A proof of the wrong kind, or one already claimed: 409 KMS-400167, and no payment row. A refused second cash claim also rolls back the first claim and the audit entry.
- The list returns 1 file for UPI and 2 for cash (the note first, even when the request sent the photo first). `receivedByName` is returned. A reversal returns `[]`, and so does a pre-stage-6 payment. JSON keys equal `api.ts`'s `InvoicePaymentView` and `AttachmentView`.
- Kitchen Manager and Kitchen Staff: 403 (KMS NOT_PERMITTED) on POST and GET, nothing saved, file unclaimed. `RolePermissions.has(role, MANAGE_VENDOR_PAYMENTS)` is true for TEMPLE_ADMIN only. `git diff` of RolePermissions.java has no `VENDOR_PAYMENTS` line.
- Another temple's upload: 409 KMS-400167. The row keeps templeB's tenant_id and stays unclaimed.
- Existing InvoicePaymentIT (5) and InvoiceCorrectionIT (15): green with proof added. Assertions unchanged.
