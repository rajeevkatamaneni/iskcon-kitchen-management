## Decisions I made that the brief left open, and one it got slightly wrong

**The brief said the delete refusal "carries `plannedMeals`, `recordedMeals` and `linkedShifts`
booleans in its details". Those never reach the browser.** `ApplicationException`'s details map is
not part of the wire contract: `ErrorResponse` is `(code, message, action, fieldErrors)` and
`GlobalExceptionHandler` builds it from the `ErrorCode` alone — the details go to the logs. So the
screen **cannot** say *which* of planned / recorded / rostered blocked the delete, and it does not
try. This is not a defect to fix here — surfacing them would mean changing the error contract, which
is `backend/` and forbidden — but it is worth Rajeev knowing, because "a kind used by nothing but a
linked volunteer shift" is exactly the case an admin will find hardest to explain to themselves, and
the message they get says "planned or recorded". If that turns out to matter on staging it is a
task of its own.

**`sortOrder` is exposed as a field rather than hidden.** `MealKindInput` requires it, so it has to
be sent, and the three options were: hide it and always append; expose move-up/move-down buttons; or
expose the number. I took the number, labelled "Order in the day" with a hint explaining that
smaller comes first and that the seeded kinds are numbered in tens so there is room between them.
Hiding it would have shipped an unfixable state — a temple adding "Evening prasadam" would get it
after Event in every planner picker with no way to move it. Move-up/move-down needs two sequential
`PUT`s per press and has a real half-applied window if the second fails; a single number has none.
Left blank on the add form it means "last", computed as the highest existing order + 10, and the
placeholder shows the reader what that will be.

**Both flags are on the edit dialog, and there is a test whose only job is to keep them there.**
`PUT` is a whole-record write, so an edit form that omitted `isEvent` would quietly turn the
temple's Event kind into an ordinary meal — the planner would stop asking for the event's name, and
nobody would connect that to a rename done on a settings screen a week earlier. The test inspects
`Object.keys(input).sort()` and *then* asserts `input.isEvent === true`, because per
`docs/work/README.md` a missing property and an explicit `false` read identically to
`objectContaining`.

**The rename warning appears only once the name has actually changed**, and compares
case-sensitively — the same comparison `MealKindService.update` makes before it cascades, so
correcting "lunch" to "Lunch" is a rename here as it is there. It names all three consequences
including volunteer shifts, which is the one a reader would not guess. No client-side guard of any
kind: no duplicate pre-check, no "has this been used?" pre-check. Both are facts about tables this
screen cannot see, and a browser-side guess would be wrong in precisely the case that matters.

**A kind with no default ready time reads "Asked every time", not an em dash.** `hhmm(null)` gives
"—", which is right for missing data and wrong here: no default time is a decision the temple made
and the planner behaves differently because of it.

**One test added to `nav.test.ts`** (the file granted up front): the Meal kinds row sits directly
after Festival occasions in the Temple group, is offered to TEMPLE_ADMIN, and is offered to none of
the other four roles. It was green before my change and is green after; nothing existing was edited.

*(Appended after the sections above were written and the work manager ran the merged tree.)*

The wave's merged-tree run reported `__tests__/design-system.test.ts:384` red against my file —

**Why my own run could not have caught it, and this is README lesson 3 rather than an excuse.**
`design-system.test.ts` is a repo-wide guard: it walks every file under `app/` and `components/`
itself and asserts over the copy it finds, so it is never *named* by a targeted run and a targeted
run never loads it. My verification ran `meal-kinds.test.tsx` and `nav.test.ts`, which is what the
brief asks a builder to run and what the verify lock's cost makes right — and no set of my own
files, however carefully chosen, would have included this one. That is exactly the gap the
merged-tree run exists to close, and it closed it.

**The offender was real and mine.** One straight apostrophe in the sort-order hint — the guard's
rule is that user-facing copy uses the typographic `’`, and every other apostrophe on the screen
already did (the three `couldn’t` strings pass). Fixed in
`frontend/app/settings/meal-kinds/page.tsx`, `temple's` → `temple’s`, in the `Order in the day`
hint. No other file was touched; `design-system.test.ts` is not in my contract, is correct, and was
left alone.

**No new negative control for this, and that is deliberate rather than an omission.** A control
exists to show that a test fails without the fix. Here the guard *is* that demonstration, already
performed: it went red on the unfixed character and green on the fixed one, which is the whole of
the evidence a one-character copy change can carry. Manufacturing a second control around it would
be theatre.
