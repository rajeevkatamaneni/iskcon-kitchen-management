## What was built

- `GET /api/v1/deliveries` → DeliveriesView. `today` is `TempleClock.zone()`'s today. `open` = every
  catalogue line on a SENT or PARTIALLY_RECEIVED order whose kept quantity is below ordered (same
  test as `PurchaseOrderService.isFullyAccountedFor`). `received` = receipts of the temple's today and
  the 29 days before it, newest first. `receivedLines` = every line those receipts touched, with its
  whole history (not cut to the window). `receivedFrom`, `hasOlder` per the ruling.
- `GET /api/v1/deliveries/received?before=YYYY-MM-DD` → OlderDeliveriesView: the 30 days ending the
  day before `before`. Date-bounded on the server: the window's two ends are the temple's midnights
  turned into instants and compared with `received_at`.
- `POST /api/v1/deliveries` → 201 `{receiptIds}`. Loads each line's order; groups by order; an order
  whose receipt already exists under the derived key is skipped from checking; every other line must
  be on a SENT/PARTIALLY_RECEIVED order of `vendorId`, or the whole request is refused with 409
  KMS-400164 before anything is written. Then `ReceivingService.receive` once per order in the one
  transaction. Derived key: `<request key>:<order id>` (the key index `goods_receipts_idempotency` is
  unique per tenant, V27, so the order id keeps two orders from one press apart).
- All three endpoints `@PreAuthorize("hasAuthority('RECEIVE_DELIVERIES')")`.
- `POST /purchase-orders/{poId}/receipts` moved to RECEIVE_DELIVERIES; `GET .../receipts` stays
  MANAGE_PURCHASE_ORDERS.
- R-DEL-5: `unitPrice` dropped from ReceiptLineInput. ReceivingService no longer writes
  `goods_receipt_lines.unit_price` (new rows store NULL) and no longer writes
  `vendor_supplies.last_price` (`recordPricePaid`, `pricePerUnit`, `canonicalUnit` removed). The
  column stays; old rows keep their values and are still read back on `GoodsReceiptLineView.unitPrice`.

**Q-1, stated plainly:** Kitchen Staff do not hold RECEIVE_DELIVERIES. From this change, anyone with
the Kitchen Staff role can no longer record a delivery, on either the order page or the Deliveries
screen, until Rajeev answers Q-1. I did not grant it. DeliveriesIT asserts their 403 on
`GET /deliveries`, `GET /deliveries/received`, `POST /deliveries` and `POST /purchase-orders/{id}/receipts`,
and their 200 on `GET .../receipts`.

## Judgement calls

- A part's date and a receipt's date are both the temple's date of `goods_receipts.received_at`,
  not `goods_receipt_lines.received_date`, so the two tabs can never date one delivery two ways. The
  new endpoint never sends a received date, and the order page doesn't send one either, so in
  practice they are the same day.
- `packLabel` is built in DeliveriesService with `Quantities.exact` in the same form as
  `PurchaseOrderService.packLabel`, which is package-private to another package outside my contract.
  The pack test asserts the two produce the same string for the same line.
- An unknown or other-tenant `poLineId` is refused with the same KMS-400164.
- `open` and `receivedLines` are ordered by vendor name, needed-by, order number, line order.
- A price a stale client still sends is ignored, not refused (as noted above).
