**2 — a no-match leaves the typed fields usable and says so plainly.** Met, backend and frontend.

## Negative control, round one — and the finding that stopped the task

One hold of the verify lock, five mutations, restored through `trap restore EXIT`. Script:
`scratchpad/control.sh`. Run **before** the contract was widened; this is what found the blocker.

### The brief's *mechanism*, tested — and falsified

The brief's ruling rests on a stated mechanism: *"Nominatim returns a normalised address string
alongside the coordinates. So when no map can be drawn, show 'We found: &lt;resolvedAddress&gt;'."*
I asserted that as a test rather than believing it. If the mechanism held, this would pass:

```java
@Test
@DisplayName("CONTROL: a hit carries the geocoder's normalised address, as the brief assumes")
void controlResolvedAddressIsCarried() throws Exception {
    staticMap.unconfigured();
    geocode("Bengaluru, Karnataka")
            .andExpect(jsonPath("$.found").value(true))
            .andExpect(jsonPath("$.resolvedAddress").exists());
}
```

```
GeocodingIT > CONTROL: a hit carries the geocoder's normalised address, as the brief assumes FAILED
    java.lang.AssertionError: No value at JSON path "$.resolvedAddress"
```

The claim is true of **Nominatim's HTTP response** and false of **this codebase's port**.
`GeocodingProvider.locate()` returned `Optional<Coordinates>` and nothing else, and
`NominatimGeocodingProvider` read `lat` and `lon` from the first result and discarded
`display_name`. No caller inside T-042's original contract could recover it. Finding that by test
rather than by argument is the point of the control: a test that only checked my own fix would have
passed, and the screen would have shipped permanently in its weakest state.

**This control is now a passing test rather than a deleted one.** It asserts the same thing it
asserted when it failed — see `findsAnAddressWithoutAKey` under acceptance criterion 3 — which is the
right end state for a control that falsified a premise: the premise is now true, and the assertion
that caught it stays in the suite.

### The fix patched out

**Backend** — `@PreAuthorize` removed, and the "don't call an unconfigured map service" guard removed:

```

    expected: null

```

**Frontend** — the confirm step short-circuited (fill the boxes straight from the reply), and the
empty-box guard removed from the lookup button:


`found:false` every time and the screen reads exactly as it did before, minus one extra button.

**1. ~~`resolvedAddress` is null in every deployment~~ — CLOSED, second pass.** Kept here because
the record is worth more than a clean-looking task. The brief asserted *"Nominatim returns a
normalised address string alongside the coordinates"*; that is true of Nominatim's HTTP response and
was false of this codebase's port. `GeocodingProvider.locate()` carried coordinates only, and

The work manager then widened the contract by exactly the two files I had scoped, and the second
pass built exactly the patch I had scoped and nothing beyond it:

- `GeocodingProvider` — a `Located(Coordinates, String)` record and a **defaulted** `describe()`
  beside `locate()`. Defaulted is what keeps `NoGeocodingProvider`, `MembershipService` and
  `MealPlanService` untouched and unbroken, and what keeps the interface functional so the
  lambda-shaped test stubs still compile. Both properties are now asserted by
  `theDefaultDescriptionIsAPositionWithNoLabel` and by `MembershipIT` continuing to compile and pass.
- `NominatimGeocodingProvider` — `describe()` overridden to read `display_name`, with `locate()`
  delegating to it so the two can never disagree about where a place is. The cache now holds the
  whole answer, so it is still one request and one entry per place: nothing extra is asked of
  Nominatim. The existing contract is intact — a missing or blank `display_name` is an absent
  description, never an exception and never a failed geocode, and the broad catch still returns
  empty for everything.
- `GeocodingController` — the one line that was marked `TODO(T-042, blocked)`.

Endpoint shape, the `api.ts` reservation, the screen and its three states are all exactly as they
were. `kms.geocoding.provider` stays at `none`, so the suite still cannot reach OpenStreetMap by
construction even though the provider now does more.

**2. The pin itself is unproven, and no test in any unkeyed environment can prove it.** Stated
plainly as asked, and this one is still open. `GoogleStaticMapProvider` has never been exercised against Google by anything —
`GeocodingIT` stubs `StaticMapProvider`, so what is proved is that a `byte[]` becomes a correct
`data:image/png;base64,…` and reaches the `<img>`. Whether Google returns a usable greyscale map
centred where we asked is unknown until a key exists. It is the one part of this task neither an
automated test nor any environment we have can demonstrate.

**3. Not hand smoke-tested, and Commandment 5 wants it.** I could not: the feature is dark in every
environment (`GEOCODING_PROVIDER` unset), so a click on staging would show the no-match path and
nothing else, and I do not deploy. What a human should do once the env var is set, in under a
minute: open `/tenants/new` as the operator, type *Hare Krishna Hill, Bengaluru*, press **Find the
coordinates from the address**, check the address that comes back reads like the right place and
that the coordinates are ~12.91 / 77.51, press **Use these coordinates**, then type over the
latitude and confirm the typed value is what saves. The *resolved address is the real live
question*: every automated test here feeds it from a stub or from a loopback server, so what nobody
has yet seen is what OpenStreetMap actually writes for a real temple address.

**4. The wording of the no-match line is a deliberate compromise worth a second opinion — still
open.** It reads
*"No coordinates came back for that address."* rather than *"We couldn't find that address"*, because
the endpoint cannot tell a geocoder that looked and missed from a deployment that has no geocoder —
the reservation in `api.ts` has no field for it and I could not add one. `GeocodingProvider`'s own
javadoc calls reporting the second as the first a lie, so the copy says only what is true of both. If
a sharper message is wanted, the clean way is an availability endpoint beside this one, the way

line in `api.ts`, which is a reserved file.
