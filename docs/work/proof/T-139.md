# T-139 — a fixture big enough to measure the shopping list on, and the first real numbers off it

**The headline, before anything else.** On a temple with five years of history behind it —
146,150 stock movements, 16,963 meal plans, 150 ingredients — the derived shopping list takes
**425 ms** to load. At ten years it takes **795 ms**. And the reason is not either of the two
queries the brief named: **one page load scans `stock_movements` nine times and reads 1,315,350
rows out of it.** The aggregate with no date bound is not run once per page load. It is run nine
times.

## How somebody runs this

**It does not run in the default suite, and `./gradlew test` is unaffected.** Both classes are
gated on an environment variable and tagged `perf`:

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home

# the measurement, at the default five-year scale
tools/work-lock.sh run verify 'cd backend && KMS_PERF=1 ./gradlew --no-daemon \
    test --tests "*ShoppingListPerformanceIT*"'

# the control
tools/work-lock.sh run verify 'cd backend && KMS_PERF=1 ./gradlew --no-daemon \
    test --tests "*TempleScaleFixtureControlIT*"'

# turn the size up — every field of TempleScale has an override
KMS_PERF=1 KMS_PERF_YEARS=10 ./gradlew --no-daemon --rerun-tasks test --tests "*ShoppingListPerformanceIT*"
```

Without `KMS_PERF` the classes are disabled and JUnit never instantiates them.

**Why an environment variable and not `-Dkms.perf=true`.** `backend/build.gradle.kts` does not
forward system properties to the test worker, and this task may not edit that file. A Gradle worker
does inherit its parent's environment, so this needs no build change at all. The `@Tag("perf")` sits
beside it so a future build script can exclude the package by tag if it would rather.

**One trap, and it caught me — say it out loud, because it produces a false green.** An environment
variable is not a Gradle build input. My first ten-year run reported `BUILD SUCCESSFUL in 4s` with
`Total: 1, Passed: 1` **and never ran the test at all** — the `:test` task was `UP-TO-DATE` from the
one-year run before it, and my script cheerfully copied the one-year report into a file named
`10y`. I caught it because the report carries its own timestamp and row counts, and both said one
year. **Pass `--rerun-tasks` when changing scale between runs**, and read the numbers in the
artefact rather than the exit code.

**The report lands in a file** — `backend/build/reports/perf/T-139-shopping-list.txt`, path printed
at the end of the run. `build.gradle.kts` sets `testLogging` for PASSED/FAILED/SKIPPED and does not
set `showStandardStreams`, so a `System.out.println` from a test never reaches the console.

## What the fixture builds, and why those numbers

Grounded in staging rather than rounded: **150 ingredients, 116 inventory items, 26 recipes** are
the live counts. On top of that, **three meals a day with three dishes in each** (9 meal plans a
day) plus **a named event every fortnight**, **8 ingredients per recipe** (the median line count in
the temple's own `RM 2019_v2.xlsx`), and **80 stock movements a day** — 72 consumption rows for the
day's dishes, a delivery every few days, and an adjustment most days.

**Generated as `kms_app`, under Row-Level Security, one tenant at a time.** Not as the superuser.
That is the difference between measuring the plan the application gets and measuring a plan nobody
will ever run: every `EXPLAIN` below carries
`Index Cond: (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid)`,
which is the RLS policy folded into the query, and it would simply be absent from a superuser's
plan. The `tenants` row and its user are made as the superuser, as every other integration class
here does — a tenant is not tenant-owned data and the application never creates one from inside a
tenant context.

At the default scale, counted with `count(*)` through that same unprivileged connection:

```
  ingredients                   150   (staging holds about 150)
  inventory_items               116   (staging holds about 116)
  recipes                        26   (staging holds about 26)
  recipe_ingredients            208   (8 lines per recipe)
  meal_plans  COOKED         16,555   (9 dishes a day for 5.0 years, plus events)
  meal_plans  PLANNED           408   (45 days ahead — the ordering horizon is 14, 30 for a festival)
  stock_movements           146,150   ← the table that only ever grows
  vendors                         8
  vendor_supplies               150   (one preferred vendor per ingredient)
  purchase_orders               260   (one in ten still SENT, so outstanding in full)
  purchase_order_lines        1,560
```

Building that takes **4.1 seconds**. Ten years takes 8.3 s. **No memory or disk limit was hit** —
the container peaked around 105 MB and the test JVM never went near its 2 GB ceiling.

## The numbers

Every row below is a real run. Median of 7 measured calls after 2 discarded warm-ups, real HTTP to
the embedded server, signed in as Kitchen Staff. **The five-year row, both `EXPLAIN`s and the read
counts all come from one run** — the last one, taken after the read-counting was added — so they
can be read against each other.

| History | `stock_movements` | `meal_plans` | **GET /api/v1/shopping-list** | `earliestDemandByIngredient()` | `onHandBaseByIngredient()` |
|---|---|---|---|---|---|
| 1 year | 29,350 | 3,719 | **141 ms** | 2.0 ms | 17.3 ms |
| 5 years | 146,150 | 16,963 | **425 ms** | 3.4 ms | 71.1 ms |
| 10 years | 292,150 | 33,518 | **795 ms** | 2.1 ms | 136.6 ms |

Read across: **the page load grows roughly in step with the ledger.** Ten times the history is not
ten times the page, but 5.6 times it, and there is no flattening in sight — the temple's operating
life is being re-read on every page load.

Raw, from the five-year run:

```
──────────────────────────────────────────────────────────────────────
  Timings
──────────────────────────────────────────────────────────────────────
  GET  /api/v1/shopping-list                      fastest    418.2 ms   median    424.6 ms   slowest    434.2 ms   (7 samples)

```

**Nothing here asserts a duration.** The only assertions in the whole harness are that the fixture
contains what it claims and that the endpoint answered 200. A build that goes red on a millisecond
count flakes on a loaded machine and teaches people to re-run rather than read. **If a gate is
wanted later, it should compare two runs of this harness rather than name an absolute ceiling** —
and I would not add one until the nine scans below are dealt with, because right now it would gate
on a number everybody already knows is wrong.

## The finding: the ledger is read nine times per page load

The two timings above do not add up on their own. If the page costs 425 ms and the aggregate the
brief singled out costs 71, something has to account for the other 350. So I asked the database how
many times one request reads each table — `pg_stat_all_tables`, snapshotted either side of a single
`GET`. This needs no source reading and names no private method; it counts the reads the running
application actually performs.

```
──────────────────────────────────────────────────────────────────────
  How many times ONE page load reads each table (pg_stat_all_tables delta)
──────────────────────────────────────────────────────────────────────
  table                   seq scans  idx scans  seq rows read  idx rows read
  stock_movements                 0          9              0        1315350
  meal_plans                      0          9              0           1986
  recipe_ingredients              0       1746              0          13968
  inventory_items                 0          3              0            348
  purchase_order_lines            0         78              0            468
  ingredients                     0       4185              0         294636
  vendor_supplies                 0         27              0           4050
```

Two things in that table, and the first is the important one.

**`stock_movements`: 9 scans, 1,315,350 rows read — which is exactly 9 × 146,150.** The whole
ledger, nine times over, for one person opening one screen. That is why the page costs 425 ms and
the query costs 71. Bounding the aggregate by date would help; **running it once instead of nine
times would help six times more.**

**`ingredients`: 4,185 index scans reading 294,636 rows.** 4,185 scans of a 150-row catalogue is an
N+1 read, and it is reading two thousand times the number of rows the table contains. Cheap per
scan, and it will stay cheap, but it is a lot of round trips for a table that could be read once.

I am reporting both rather than fixing either: `shoppinglist/**` belongs to T-132's builder, and
these numbers are for whoever judges that work.

## `EXPLAIN (ANALYZE, BUFFERS)` — the baseline

Both run as `kms_app` with `app.tenant_id` set. **The SQL is a verbatim copy taken from
`ShoppingListService` on 2026-09-10** — copied because the methods are private and that file is not
mine to open. That makes this a snapshot with an expiry date: **whoever takes the after-reading has
to re-take the SQL from the file first.**

### `earliestDemandByIngredient()` — 2.2 ms, and not the problem

```sql
SELECT ri.ingredient_id, MIN(mp.plan_date) AS earliest
FROM meal_plans mp
JOIN recipe_ingredients ri ON ri.recipe_id = mp.recipe_id
WHERE mp.status = 'PLANNED' AND mp.plan_date >= CURRENT_DATE
GROUP BY ri.ingredient_id
```

**This one is fine and needs no index.** `meal_plans_tenant_status` already keeps the 16,555 cooked
plans out of it, and what it costs does not move between one year of history and ten — 2.0 ms, 3.4 ms
and 2.1 ms across the three scales, which is noise, not a trend — because the query is bounded by `plan_date >= CURRENT_DATE`
and the forward plan does not grow with the temple's age. **The brief named it as the first thing to
look at; the measurement says look elsewhere.**

One thing to note anyway: the planner estimates `rows=1` and gets 3,264. The plan it picks is a good
one, so this costs nothing today, but an estimate off by three orders of magnitude is the sort of
thing that picks a bad join order once the shape changes.

**Every row of the ledger, every call.** 146,150 rows, 2,975 buffers, and the cost tracks the row
count almost exactly across the three scales — 17.3 ms at 29,350 rows, 71.1 ms at 146,150, 136.6 ms

`GroupAggregate`; at five it switches to `HashAggregate`. Anyone comparing a before and an after has
to compare at the same scale or they will be comparing two different plans.

## Acceptance criteria

**1 — a data fixture that generates a temple at realistic scale, parameterised.** `TempleScale` +
`TempleScaleFixture`. Defaults are the staging counts and a five-year projection; every field is
overridable from the environment, and `KMS_PERF_YEARS` is offered beside `KMS_PERF_HISTORY_DAYS`
because years is how the question actually gets asked. **Verified** by building at 30 days, 60 days,
1 year, 5 years and 10 years and counting the result each time.

**2 — a repeatable measurement, with the fixture's size printed beside it.** The report prints the
size block first, the timings second, and repeats the size in one line at the bottom, so the two can
never be separated by a copy-paste. **Verified** — five runs, reproduced above.

**3 — `EXPLAIN (ANALYZE, BUFFERS)` on the two queries as they stand today.** Both above, run as the
unprivileged role with the tenant set. **Verified.**

## Not done / needs Rajeev

**The pre-T-132 baseline could not be taken, and this is the one real gap.** The brief assumed
`POST /shopping-list/regenerate` would still be there, so that today's button-press cost could
stand in as the forecast of tomorrow's page load. **T-132's rewrite is already in the working tree**
— the endpoint and the nightly job are gone and `GET` is derived. So the harness probes for the
endpoint and says which shape it measured, and every number above is the **post-T-132** figure. That
is the more useful number, but it means there is **no "before" to compare it with**. Anybody wanting
one has to run the harness against `git archive HEAD`.

**The 350 ms I have not attributed.** I have shown that the ledger is scanned nine times and that
the catalogue is read 4,185 times. I have *not* shown which callers do it — that needs
`shoppinglist/**` and `meal/SufficiencyService`, and those belong to T-132's builder. **The nine
scans are worth a task of their own**, and they are worth more than an index would be.

**No hand smoke-test, and none is possible.** T-139 adds no user-facing surface — it is a test
harness. Nothing was deployed and there is nothing to press.

**No error code was needed**, so none is named. `ErrorCode.java` was not opened.

**Twice I could not compile, and neither time was mine.** First
`purchaseorder/PurchaseOrderIT.java` (3 errors, a missing `java.math.BigDecimal` import) and later
`equipment/ServiceIntervalTest.java` (15 errors, a changed `EquipmentService.derive` signature) —
both other builders' files, mid-edit, and both fixed by their owners while I waited. Recording it
because it is the wave-8 lesson exactly: **a path contract isolates edits, not the shared compile.**
The signature is the same both times — every error in one file that is not yours, at compile time
rather than at an assertion — and the right move is `git status` and a wait, not a hunt for what you
broke.

**One thing I would put to Rajeev before the harness is used to judge anything.** These numbers are
from a Testcontainers PostgreSQL on this laptop, with everything in shared buffers
(`Buffers: shared hit=2975`, no `read=`) — a warm cache and no network between the application and
the database. Cloud SQL in `asia-south1` behind Cloud Run will be slower for the same work, not
faster. **425 ms is the optimistic figure, not the pessimistic one.**

**And one caveat on comparing runs.** The `EXPLAIN` SQL in the harness is a copy taken on
2026-09-10 and will go stale the moment T-132 lands properly. It is labelled as such in the report
itself, but somebody will still paste an old baseline next to a new reading. Re-take the SQL first.
