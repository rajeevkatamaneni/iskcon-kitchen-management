# T-131 — a supply row can be edited in place, so a lead time can be recorded on a supply a vendor already has

The reported defect, restated in one line: **T-090's lead time box lived on the *Add supply* form,
and that form's picker deliberately offers only ingredients the vendor does *not* already supply —
so on every supply that already exists, which is every supply a real temple has, the box could not
be reached.** The only route left was Remove and add again, which starts from an empty form and so
throws away the last price and the preferred flag to change a lead time. The escalation T-090 built
could never fire on anything.

**Fixed by making the row editable**, following the Edit/Save/Cancel pattern `/ingredients` already
uses, and **the server needed no change at all** — see the next section, because that was the first
question the brief asked.

## The server already upserts. No backend change was made.

`VendorController.setSupply` is a `PUT /api/v1/vendors/{id}/supplies`, and `VendorService.setSupply`
(`:206`) ends in:

```sql
INSERT INTO vendor_supplies (
    id, tenant_id, vendor_id, ingredient_id, last_price, lead_time_days, preferred)
VALUES (gen_random_uuid(), NULLIF(current_setting('app.tenant_id', true), '')::uuid, ?, ?, ?, ?, ?)
ON CONFLICT (vendor_id, ingredient_id) DO UPDATE
SET last_price = EXCLUDED.last_price, lead_time_days = EXCLUDED.lead_time_days,
    preferred = EXCLUDED.preferred, updated_at = now()
```

So a PUT for a pair the vendor already supplies **updates that row**. No new endpoint, no new
method, and nothing in `backend/src/main/java/org/iskcon/kms/vendor/` changed:
`git diff --numstat` returns **nothing at all** for `VendorService.java`. What the backend got was
**two tests**, because the claim the whole screen rests on had never been exercised from a screen —
the screen had no way to send the request.

**And the `preferred` clash is already handled on the server, in the same transaction, three lines
above that statement:**

```java
if (request.preferred()) {
    jdbc.update("UPDATE vendor_supplies SET preferred = false, updated_at = now() "
            + "WHERE ingredient_id = ? AND preferred", request.ingredientId());
}
```

`vendor_supplies_one_preferred` (`V24__vendors.sql:63`) is `UNIQUE (tenant_id, ingredient_id) WHERE
preferred`. Because the other vendor's preference is cleared *before* this row is written, ticking
the box **moves** the preference and cannot collide with the index. Stage 4 of the control proves
that this is the line doing it, and not luck.

**So `preferred` is offered in the inline edit rather than left out**, which the brief allowed either
way. The reasoning: it is one of the three facts Remove-and-add was throwing away, so leaving it out
would fix two thirds of the defect and leave the third needing the destructive route. What the screen
owes the person is therefore not a refusal but a sentence, and there is one above the table:

> Only one vendor can be preferred for an ingredient, so ticking Preferred here takes it from
> whichever vendor holds it now.

It sits over the table and the Add form both, because both offer the tick and neither can name the
other vendor — that vendor is not on this screen. **No new error code is wanted; `ErrorCode.java` was
not opened.**

## What was built

**The row gets an Edit beside its Remove, and Edit swaps it for the same row as inputs**, exactly as
`/ingredients` does — that screen's `EditRow` was read first and this is the same shape, not a second
pattern for the same interaction. Five cells, matching the header; the row's own values seeded into
the controls; Save and Cancel at the end; nothing committed until Save. The `Remove` column heading
becomes `Actions`, since the column no longer holds one control.

**The ingredient itself is not editable, and that is the one departure from the precedent.** On
`/ingredients` the name is a field because the name is a property of the thing. Here the ingredient
is what the row *is* — the server addresses a supply by `(vendor, ingredient)` — so changing it in
the box would not correct this supply, it would create a different one and leave this one behind.

**All three values are sent on every Save.** Not defensiveness: the upsert writes the whole row, so
a save that omitted one would *erase* it rather than leave it alone. Seeding each control from the
row is what makes sending all three safe, and it is why the price box opens holding the price.

**Clearing a lead time lands as null, not 0**, and that is guarded in one named place rather than
four inline ternaries:

```ts
function numberOrNull(raw: string): number | null {
  const t = raw.trim();
  return t === "" ? null : Number(t);
}
```

The blank is tested as a *string*, before anything is coerced. `Number("")` is `0`, so the obvious
coercion turns "nobody has recorded this" into "arrives the same day"; and the reflex guard
`Number(t) || null` fixes that direction and breaks the other, quietly discarding the real `0` a
cash-and-carry shop has. Both are one character from correct, which is why it is a named function
used by the Add form and the edit row alike. Its mirror, `boxValue`, has the same trap on the way
back in: `n === null ? "" : String(n)` and never `n ? … : ""`, or a recorded 0 would open as blank
and save back as unknown.

## The one change to `frontend/lib/api.ts`, and why it is not churn

`setVendorSupply`'s input had `lastPrice?: number | null` and `leadTimeDays?: number | null`. Both are
now **required-and-nullable**. The server writes all three columns on every call, so an *optional*
key lets `tsc` wave through a caller that forgets one — and forgetting one does not leave it alone,
it erases it. That is precisely the data loss this task exists to stop, arriving by a different door.
Required-and-nullable makes it a compile error. The javadoc on the method says so.

**This is a guard, not the fix**, and stage 1 of the control proves the distinction: with the type
change in place and the screen reverted to `HEAD`, **`tsc` was silent** — `control-T-131: tsc silent
on HEAD's screen` — and the ten editing tests failed anyway. The types stop a future omission; they
are not what makes today's tests pass.
