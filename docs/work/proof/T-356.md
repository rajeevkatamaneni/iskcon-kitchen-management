## What was built

1. **Whose card.** `JobCardService.kitchenFor` requires the meal first (so another temple's meal is the same 404 it
   always was), then reads the meal's sections. Named: it must be one of them, else `KMS-400187`
   (`KITCHEN_NOT_ON_THIS_MEAL`, 404) — another temple's kitchen is hidden by RLS and reads as the same refusal.
   Not named: the only kitchen where there is one, `KMS-400186` (`JOB_CARD_NEEDS_A_KITCHEN`, 400) where there are
   two or more. A meal with no section at all is an `IllegalStateException` (an incident id, not a refusal that
   would tell the person something untrue) — V150 and the meal save make it unreachable.
2. **The sheet.** Only that kitchen's dishes, and because the food items, the recipes appendix, its translations
   and the serving sheet are all built from that one list, all four narrow together. The identity line reads
   `Lunch · Sweets kitchen` in the corner over the date, and `Lunch · Sweets kitchen · Monday 17 March 2025` on
   the head of the appendix, serving and delivery sheets; the `<title>` carries the kitchen too, because that is
   the name a browser offers when the print view is saved. "Planned crew" is the section's `crew_required`.
   `meals.crew_required` is read nowhere (V151 drops it).
3. **Versions.** `meal_kitchens.card_version` / `card_fingerprint`, locked `FOR UPDATE` per section. The card
   **number** is untouched: one per meal, `ServedMealService.issueCardNumber`, printed on every kitchen's sheet.
   The fingerprint now includes the kitchen's name; `withVersion` recognises the two older forms (no kitchen, and
   pre-2026-09-14 with equipment) and rewrites them in place, so no card in any kitchen jumps a version because
   the name went on the sheet.
4. **V152.** Drops `meals.card_version`, `meals.card_fingerprint` and their CHECK. Adds
   `documents.kitchen_id UUID REFERENCES kitchens(id) ON DELETE SET NULL` plus
   `documents_kitchen_only_on_job_cards`, so the kitchen travels to the worker the way the language does. No
   backfill and so no per-tenant loop: existing job-card rows keep NULL, which means "the meal's only kitchen" and
   is exactly right for every card requested before this release. SET NULL rather than V150's RESTRICT is argued
   in the migration's header: `KitchenService.delete` decides deletability from what it knows references a
   kitchen, and a key it does not know about would surface as an unexplained failure in the Settings screen.

**Grep before dropping the columns** (Commandment: check nothing else reads them). `grep -rn -e card_version -e
card_fingerprint -e cardVersion -e cardFingerprint backend/src/main/java frontend/lib frontend/app
frontend/components` returned `JobCardService.java` only (plus `JobCardTemplate`'s own `cardVersion` field, which
