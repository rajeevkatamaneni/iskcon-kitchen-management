# T-105 — an unreadable request body now names the field it could not read, and lists the values it would have taken

## What was actually wrong when I started, not what the ledger says

The ledger row (2026-09-09, revision `api-00133`) says posting a purchase order line with
`"unit": "EACH"` answers **KMS-500001 / HTTP 500**. **That is no longer true**, and I checked the
tree rather than taking either the ledger's word or the brief's. `bed58c8` added two handlers:

- `GlobalExceptionHandler:189` `HttpMessageNotReadableException` → `VALIDATION_FAILED`, **KMS-400001, HTTP 400**
- `GlobalExceptionHandler:208` `MethodArgumentTypeMismatchException` → `RESOURCE_NOT_FOUND`, HTTP 404

So one third of the original complaint was already fixed. **What was still wrong is the sharp
third**: both handlers called `ErrorResponse.of(code)` — the one-argument overload, which hard-codes
`List.of()` for `fieldErrors`. Reproduced verbatim over real HTTP in the negative control below:

```
{"code":"KMS-400001","message":"Some of the information entered isn't valid.",
 "action":"Check the highlighted fields and try again.","fieldErrors":[]}
```

"Check the highlighted fields" with nothing highlighted. Meanwhile a Bean Validation failure on the
same endpoint returns the same KMS-400001 *with* the field named — so the request that is most
obviously the caller's own typo got the least useful answer in the product, because an unparseable
body fails in Jackson before the validator is ever reached.

## What it does now

`{"unit":"EACH"}` →

```
{"code":"KMS-400001","message":"Some of the information entered isn't valid.",
 "action":"Check the highlighted fields and try again.",
 "fieldErrors":[{"field":"unit","message":"Choose one of KG, GM, L, ML, PIECES."}]}
```

Nested and indexed paths are named the way the caller wrote them: `lines[1].unit`.

**A value in the request that cannot be what it claims is now split two ways** (coordinator's call
mid-task; see "The split" below):

| request | answer |
|---|---|
| `/vendor-invoices/undefined/payments` — names no resource | **404 KMS-400030**, now naming the segment |
| `/orders?status=SNET` — names a real collection and one misspelt word | **400 KMS-400001**, naming the field and its values |

## Where the line between "name the field" and "paste the exception" was drawn

Jackson's own sentence for this case is:

> Cannot deserialize value of type `org.iskcon.kms.ingredient.Unit` from String "EACH": not one of
> the values accepted for Enum class: [KG, GM, L, ML, PIECES]

Everything in it is useful and almost none of it may be shown. What I took, and why each is safe:

- **the field name**, from `MismatchedInputException.getPath()` — a list of
  `JsonMappingException.Reference`, each carrying either a JSON property name or an array index.
  Both are the caller's own vocabulary: they are literally what the caller typed. **A Java type name
  cannot appear here**, which is the property that makes echoing it back safe at all.
- **the enum constants**, from `getTargetType().getEnumConstants()` — the names, not the labels
  (`KG`, not "Kg"), because the name is what has to be sent on the wire.

What I refused:

- **the message string**, never read, never scraped. `getMostSpecificCause().toString()` still goes
  to the log at WARN, which is where the existing javadoc already said it belongs, and it still does.
- **the Java type**, never named in any user-facing string.
- **per-type format advice** for non-enums ("use a date like 2026-09-30"). Tempting and rejected: the
  format a field accepts is a fact about that field's configuration, and a sentence generated here
  would be asserting it on behalf of every date and decimal field in the product at once. Non-enums
  get the field name and "That isn't a value we can use here." Naming the field was the defect.
- **long enum lists.** `AuditAction` has 108 constants and `ErrorCode` has 148. Past
  `MOST_VALUES_WORTH_LISTING = 12` the field is still named and the list is left to the docs — a
  wall of constants next to a box is not help. Tested against `JobTitle` (17 members).

The catch-all was **not** widened, and nothing is scoped to a request path — the T-100 note at the
bottom of `GlobalExceptionHandler` is intact and untouched. The scoping is to the exception types
that already had handlers.

## The split: a misspelt filter is a bad field, not a missing order

`MethodArgumentTypeMismatchException` carries two different failures, and until now both were
answered 404. The existing argument in the javadoc — *"a path that identifies nothing is a 404 —
which is what it is"* — is **sound for a path and unsound for a filter**:

- `/vendor-invoices/undefined/payments` names no resource. Nothing is there and nothing could be.
  404 is the truth, and that half is unchanged.
- `/orders?status=SNET` names a real collection and one misspelt word. The resource is fine; the
  field is wrong. "We couldn't find what you were looking for" sends the reader hunting for a
  missing order **that exists** — which is the same defect T-105 is about, one layer along.

The test is `isPartOfTheAddress(e)`: whether the parameter that failed to convert is a
`@PathVariable`. That is the whole rule. It is deliberately a property of the parameter and **not of
the URL** — scoping a handler to a request path is exactly the mistake the T-100 note at the bottom
of the file exists to prevent, and it is untouched. Anything not part of the address takes the 400,
because only the address can name something that does not exist. A parameter we cannot see at all
(a null `MethodParameter`) takes the 400 too: it names the parameter the caller supplied and asserts
nothing about what exists, whereas a 404 guessed at in the dark tells somebody their order is missing
when it is not. That fallback is tested, so it is a decision rather than an accident.

**The risk check I was asked to run before changing it, and what it found:** no test in the tree
asserts a 404 on a query parameter. All fourteen places asserting `KMS-400030` are
`ApplicationException` raised by service code — a withdrawn endpoint (`UserManagementIT:77`), a row
another tenant's RLS policy hides (`InventoryStockIT:190`), a business rule
(`DescribedPurchaseLineIT:428`) — and none is a type mismatch. Separately: every `@RequestHeader` in
the tree is a `String` (three of them, all webhook signatures), and a String never fails to convert,
so no typed header can reach this handler today. The reasoning above is in the handler's javadoc,
not only here.

## Error codes

**No new code, which is the point of the task.** `VALIDATION_FAILED` (KMS-400001) is already what a
field error arrives under, and making the unreadable-body answer arrive the same way *is* the
consistency being asked for. The split reuses the same two codes that were already in the file —
`VALIDATION_FAILED` and `RESOURCE_NOT_FOUND` — and adds none. `ErrorCode.java` was not opened.
400148 was not taken.
