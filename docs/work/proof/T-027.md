# T-027 — A shopping-list line can be added by hand, and it survives the nightly regeneration

`POST /api/v1/shopping-list` plus `ShoppingListService.addLine`, and a picker on
`/shopping-list` that calls it. The line is written `edited = true`, so the 04:30 regeneration's
`DELETE ... WHERE edited = false` leaves it alone; a duplicate is refused with `KMS-400131` rather
than silently overwriting the existing line.

## Negative control — `edited = true` patched out

The script is `control-edited-false.sh` in the session scratchpad. It backs the file up to a
`mktemp`, installs an `EXIT` trap that restores it whatever happens, patches the fix out with a
Python step that **exits non-zero unless it matches exactly once**, prints the diff to prove the
tree changed, and runs the test with `--rerun-tasks` so no incremental shortcut is available. Tests
were **not** adjusted; the control ran against them as written.

## Acceptance criteria

**A hand-added line survives `POST /regenerate`, asserted against a real regeneration.**
`handAddedLineSurvivesARealRegeneration` adds a gas cylinder — no inventory row, no recipe, no meal
plan, so no demand stream can ever suggest it — then calls the real `POST /regenerate`, which does
genuine work (`{"lines":1}` for rice) and runs its `DELETE ... WHERE edited = false`. The list still
has both. The negative control above proves the assertion is load-bearing.

**Adding an ingredient already on the list returns KMS-400131.** `alreadyOnTheListIsRefused`
regenerates so rice is on the list at 9 KG, adds rice at 4, gets 409 / `KMS-400131`, and then
asserts the existing line is *still* 9 KG and still `edited: false` — the refusal changed nothing,
which is the whole argument for refusing rather than upserting. `handAddedLineCannotBeAddedTwice`
covers the same refusal against a line that was itself added by hand. Implemented as
`ON CONFLICT DO NOTHING` and a zero-rows check, so two people adding the same thing at once get one
line and one readable refusal instead of a constraint violation.

**Quantity zero is refused.** `zeroQuantityIsRefused` → 400, and the list is still empty afterwards.
`@NotNull @Positive` on the request, with `shopping_list_lines_qty_positive` behind it. The screen
also disables the button (`refuses to add without an item, or with a quantity of zero`), but the
server decides.

**An unknown ingredient is refused.** `unknownIngredientIsRefused` → 404. The lookup goes through
`IngredientUnits.canonicalUnit`, which reads on the tenant-scoped connection — so another temple's
id is not "forbidden", it is simply not found, and the tenant still comes only from the token.

**A supply can be added exactly as food can.** The defining test's subject *is* a supply
(`is_supply = true`, T-023 / D-1) rather than a case bolted on at the end, and on the screen
`offers a supply exactly as it offers food` asserts the cylinder is in the picker and posts. No code
distinguishes the two, which is the point of D-1's flag.

**The `unit` decision, honoured and tested.** No `unit` field on the request;
`takesTheCanonicalUnitAndThePreferredVendor` adds jaggery and gets `GM` back without having said so,
and the frontend test asserts the POST body is exactly `{ ingredientId, suggestedQty }`. I agree
with the decision as briefed and did not re-derive it: the CHECK admits all five names, so a caller
free to choose would have had nothing downstream to stop it. The dropped criterion ("an unknown unit
is refused") is correspondingly gone — there is no unit to refuse.

**Screen.** A picker, not an id box, copying `AddLine` on the order detail (read via `git show`;
`app/orders/**` was never opened for editing). It filters out what is already on the list, offers
itself under the empty state as well as under the table, states the chosen ingredient's unit beside
the quantity rather than offering to change it, and leaves what was typed in place on a refusal.
The catalogue query's own failure is deliberately not raised as the page's error — losing the picker
should not replace the list somebody came to read.
