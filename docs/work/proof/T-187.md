## Approach and why

Java decides. SQL only narrows the candidates.

1. Read the looked-at gift's stored phone and email (unchanged). `phone = CounterPhone.normalise(storedPhone)`.
2. If `phone == null && email == null`, return nothing. Before, this checked the stored phone. It now checks the normalised one because otherwise a gift whose phone was saved as spaces would match every contactless gift in the temple, since those normalise to null too. Tested.
3. Candidates: `SELECT d.id, d.donor_phone FROM donations d WHERE d.is_anonymous = false AND d.donor_email IS NOT DISTINCT FROM ? AND <net(d.donor_phone)> = <net(?)>`. The email clause is character-for-character the old one.
4. In Java, keep a candidate only if `Objects.equals(CounterPhone.normalise(candidatePhone), phone)`.
5. Fetch the ledger rows for the kept ids with the existing `SELECT`/`MAPPER` (`WHERE d.id = ANY(?)`, same pattern as `RecipeService`). This leaves the shared `SELECT` alone, so `donor_phone` never enters the ledger list or export query.

Why not the brief's plain-Java suggestion (fetch every non-anonymous gift with the same email, then filter)? For a gift with no email, which is most counter gifts, that fetches every contactless named gift the temple has ever recorded, on every donor-history open, and it grows forever. So the database applies a net: `PHONE_NET = right(regexp_replace(coalesce(%s, ''), '[^0-9]', '', 'g'), 10)`, meaning the last ten ASCII digits.

The net is not the rule. It is a superset of it. Any two phones `normalise` makes equal have equal keys: both recognised means the same ten digits come last, and no separator or trimmed character is a digit; both kept as typed means the same string after trimming, and trimming removes no digit. One recognised and one kept can't be equal. Blank and null both key as `''`. The reverse does not hold, on purpose: `+44 98765 43210` and `0091 98765 43210` pass the net and Java rejects them (tested).

So the SQL is not a second copy of the rule, but it must stay wider than it. `phoneNetIsWiderThanTheCounterRule` pins that on CounterPhoneTest's own `recognised()` and `keptAsTyped()` lists (plus the Bengaluru landline, null/blank, and two inputs these tests use). Every pair the rule makes equal must get equal keys from PostgreSQL. Control B shows it goes red when the net is narrowed.

## Acceptance criteria

1. **Old and new group, from either id.** `DonationLedgerIT.oldTypedGiftsAndNewPlusNinetyOneGiftsGroupTogether`: `98765 43210`, `+91 98765-43210`, `normalise("98765 43210")` (asserted stored as `+919876543210`) and `normalise("09876543210")`, email null. The history opened from each of the four returns all four. Same email on both: `sameEmailGroupsAndTheEmailHalfIsUnchanged` (older/newer with `govind@example.com` group).
2. **Different numbers stay apart.** `phonesTheRuleDoesNotEquateStayApart`: `+919876543210`, `+44 98765 43210`, `0091 98765 43210`, `98765 43211`. Each returns only itself. The first two foreign ones share the last ten digits, so they pass the SQL net and are rejected by the Java rule.
3. **Landline.** `landlineKeptAsTypedGroupsOnlyWithItself`: `022 2345 6789` groups with another `022 2345 6789` only. `022-2345-6789` and a mobile each return only themselves.
4. **Anonymous and email unchanged.** `anonymousAndContactlessGiftsNeverJoin`: an anonymous gift and a contactless walk-in never appear; a gift whose phone is `"   "` returns an empty history rather than gathering contactless gifts. `sameEmailGroupsAndTheEmailHalfIsUnchanged`: the same phone under `someone@example.com`, under no email, and under `Govind@Example.com` (case differs) each return only themselves. Honest note: V38's `donations_anonymous_has_no_pii` CHECK means an anonymous row has no phone or email, so the `is_anonymous = false` clause cannot be shown red on its own. The phone comparison already excludes those rows. The clause is kept anyway.
5. **My donations exact.** `MyDonationsIT.typedGiftStaysOffMyDonationsThoughTheOfficeHistoryGroupsIt`: two gifts, `98765 43210` and `+919876543210`. The Temple Admin's donor history returns both (proving normalisation is live on this data), and Gopal, verified as `+919876543210`, gets only the `+91` one on `/api/v1/my-donations`.
6. **DonationLedgerIT's split assertion changed.** The T-186 test `newPlusNinetyOneGiftDoesNotGroupWithOlderTypedGift` asserted `older` grouped only with `alsoOlder`, and `newer` only with `newerTypedWithZero`. It is replaced by `oldTypedGiftsAndNewPlusNinetyOneGiftsGroupTogether`, which asserts all four group from each of them. Its comment records what it used to assert.
