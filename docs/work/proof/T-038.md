## The two things the brief asked me to settle with evidence

### 1. Is any of the three tables append-only? No.

Checked rather than assumed, because `make_append_only()` refuses an UPDATE with a
**BEFORE UPDATE OR DELETE trigger** (V49/V50 — not a rule and not a privilege revoke, both of
which V50's header explains were tried and abandoned), so an UPDATE against such a table raises
from somewhere a reviewer of this method would never look.

The complete registered set is: `audit_events`, `platform_audit_events`, `stock_movements`,
`equipment_state_changes`, `po_events`, `goods_receipts`, `goods_receipt_lines`,
`invoice_payments`, `shift_broadcasts`, `staff_conduct_notes`, `equipment_services`,
`vendor_status_changes`.

`meal_plans`, `meal_services` and `shifts` are **not** among them. The work manager's read was
correct and the design stands. (The tests below are the second half of this proof: the cascade
actually changes rows, which a trigger-blocked UPDATE would not.)

### 2. How is the old name matched? Case-insensitively — `lower(meal_kind) = lower(?)`.

An exact match is what the stored data *ought* to allow, and for two of the three columns it
would: `meal_plans.meal_kind` is written `ps.setString(3, kind.name())` from
`require(...).name()` (`MealPlanService.java:429`), and `meal_services.meal_kind` likewise
(V64's own column comment says so). The third column breaks it:

```java
// ShiftService.java:157 — the INSERT, and :177 the UPDATE
request.mealDate(), trimToNull(request.mealKind()), trimToNull(request.mealEventName())
```

`shifts.meal_kind` stores **what the caller typed**, never routed through `MealKindService`. It
is read back through `staff/MealMoment.java`, whose canonical constructor folds both sides to
lower case — deliberately, and its javadoc argues the point at length:

> "it removes the one remaining way a caller can post `"lunch"` against a temple that stores
> `"Lunch"` and be quietly counted nowhere"

`ShiftMealLinkIT.anEventNameIsFoldedTheSameWayTheMealKeyFoldsIt` proves a lower-cased link is a
working, supported row today. So an exact-match cascade would rename the meals around such a
shift and leave the shift itself pointing at a kind that no longer exists — silently, because a
broken link reads as zero volunteers, which looks exactly like a shift nobody joined.

Folding matches everything an exact comparison would match and nothing it would not, which is
the same argument `MealMoment` makes. **The case I did not choose is tested**: both
`aRenameCarriesEverythingRecordedUnderTheOldName` and `aLinkedShiftHoldsItsKind` link their
shift as `"lunch"` / `"dinner"` in lower case against a temple that stores `Lunch` / `Dinner`.
Under exact matching the first fails on the crew count and the second deletes a kind that is in
use.

One collision risk considered and dismissed: `meal_services` is unique on
`(tenant_id, plan_date, meal_kind, lower(COALESCE(event_name,'')))` — the **exact** kind — so a
case-insensitive rewrite could in principle collapse two rows into one key. It cannot happen:
that would require two service rows for one date and event differing only in the case of
`meal_kind`, and every write to that column goes through `require(...).name()`. Noted in the
code comment rather than defended against.

Transitive, as the brief noted: `document/JobCardService.java:239` reaches site 4, and
`:305` reaches site 6 with a **stored** name off an already-served meal.

**My verification agrees with the ruling, and I did not have to soften it.** The stored name is
neither a snapshot nor a reference: it is read raw and unresolved on the plain listing
(`MealPlanService` `SELECT`), the menu history (`MenuHistoryService:63` and `:89`), the
sufficiency read (`SufficiencyService:162`), the costing report (`costing/MealKindCostService:167`)
and the giving page (`donation/GivingPageController:143`) — and **re-resolved** on the four
read-shaped paths above. Deleting a used kind therefore arms `KMS-400071` in history nobody
touched, to go off later on a job card or a reuse preview, far from the settings screen that
caused it. V64's own column comment carries the same false premise the old `delete()` comment
did — *"a temple may delete a kind, and the meals cooked under it must keep reading as what
they were"* — and it is now wrong in the schema as well as in the service. I left it alone;
`meal_services`'s migration is outside the contract.

Refuse-when-in-use built as specified. Deactivation was not built and remains a strict superset
available later.

## Acceptance criteria, and how each was verified

**1. A rename leaves every plan, recorded meal and linked shift readable — on the real database,
under RLS, with more than one tenant present, through a path that resolves the name.**
`aRenameCarriesEverythingRecordedUnderTheOldName`. Two tenants exist for the whole class
(`setUp` provisions `rename-temple` and `other-temple`, both seeded with the same six kinds).
`Lunch` → `Prasadam lunch`, then three resolving reads, none of them a `SELECT` of the column:

- `POST /api/v1/meal-plans/reuse/preview` → 200, `$.kinds[0].mealKind == "Prasadam lunch"`,
  `$.totals.meals == 1` (site 1, resolving the **stored historical** name — the strongest of the
  three, and the one that returns 409 without the fix);
- `GET /api/v1/job-cards/languages?mealKind=Prasadam lunch` → 200 (site 4 → `ServedMealService.find`),
  and the same call with `mealKind=Lunch` → 409 `KMS-400071`, i.e. the old name really is gone
  rather than both working;
- `GET /api/v1/meal-crew` → the volunteer still lands on the meal, now called `Prasadam lunch`,
  `volunteers == 1` — the only read in the product that resolves a shift's link.

The `meal_services` and `shifts` rows are additionally asserted by id to hold the new name, so
all three tables are covered explicitly as well as behaviourally.

**2. The other tenant's identically-named kind and its rows are untouched.**
`theRenameStopsAtTheTenantBoundary`. Mysuru holds a `Lunch` kind plus a `meal_plans`, a
`meal_services` and a `shifts` row all reading `Lunch`; after Bengaluru renames, all four are
asserted still `Lunch` through the privileged connection (the only one that can see across), and
Bengaluru's own plan is asserted to have moved. The cascade carries no `tenant_id` at all — RLS
is what confines it, which is why this assertion is the one that matters. It fails on `HEAD`
(`expected: 1 but was: 0`) for the opposite reason — no cascade ran anywhere.

**3. A rename that does not change the name writes nothing to the three tables.**
`anEditThatIsNotARenameTouchesNothing`. The `updated_at` of the plan, the service row and the
shift are captured, the ready-by time is moved 12:00 → 12:30 with the name left alone, and all
three timestamps are asserted **identical** afterwards. Since the cascade sets
`updated_at = now()`, an unchanged timestamp is positive proof no UPDATE ran. The kind's own
`default_ready_time` is asserted to have changed, so the request was not a no-op overall.

**4. `delete()` refuses with KMS-400126, each of the three tables independently.**

- `aPlannedMealHoldsItsKind` — only a `meal_plans` row → 409 `KMS-400126`;
- `aRecordedMealHoldsItsKind` — only a `meal_services` row, no plan beside it → 409;
- `aLinkedShiftHoldsItsKind` — **nothing planned at all**, only a shift linked to `"dinner"`
  → 409. This is the case a planner-shaped check misses.

Each also asserts the message text and that the kind row survives. The last two go through a
shared helper that checks `$.code`, `$.message` and the surviving row.

**5. `delete()` still removes a kind that has never been used.** `anUnusedKindGoes` — a kind is
created through `POST /api/v1/meal-kinds` and deleted → 204, row gone. Plus
`useIsCountedPerTemple`: Mysuru having planned a lunch does **not** hold Bengaluru's `Lunch`,
because the in-use check runs inside the request's tenant and RLS scopes it.

**6. The eight `require()` sites enumerated with READ/WRITE and the endpoint reaching each.**

brief on all eight.

## Not done / needs Rajeev

- **No hand smoke test.** The contract is backend-only — the whole frontend is forbidden to me,
  and I did not open or run it. Commandment 5 wants the new user-facing behaviour driven by
  hand: on the temple-settings meal-kinds screen, rename a kind the temple has used and confirm
  the planner, an existing job card and a linked shift all still read; then try to delete a used
  kind and confirm the screen shows **KMS-400126** with *"Rename it instead."* rather than a raw
  failure. I could not do that here.
- **The frontend has not been told about the new 409.** `MEAL_KIND_IN_USE` is a code the delete
  button never used to be able to receive. Whatever generic error surface the settings screen
  uses will show the code, the message and the action, so it degrades honestly — but nobody has
  looked at it. Worth a glance when someone is next in that screen.
- **A pre-existing gap I deliberately did not fix.** `update()` does not catch
  `DuplicateKeyException`, so renaming a kind onto a name another kind already has (case-
  insensitively) returns a 500 rather than `MEAL_KIND_ALREADY_EXISTS`, which `create()` does
  handle. That is untouched by this task and one line to fix, but it changes behaviour nobody
  asked about and has no test, so I left it and am reporting it instead.
- **Deactivation was not built,** as ruled. If a temple later needs to retire a kind it has used
  for a year, that is the column-and-migration answer, and refusing here forecloses none of it.
- **V64's column comment is now wrong.** `meal_services.meal_kind` still carries *"a temple may
  delete a kind, and the meals cooked under it must keep reading as what they were"* — the same
  premise this task disproved. The migration directory is outside my contract, and an applied
  migration is not edited in this project anyway; the correction would have to be a comment-only
  fix-forward if anyone thinks it worth one.
