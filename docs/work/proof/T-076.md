# T-076 — the frontend has a linter that runs, and CI runs it

`"lint": "next lint"` had been in `frontend/package.json` since the first commit with no ESLint
config and no ESLint dependency anywhere in the tree. It is now `eslint . --max-warnings=0`, with a
flat config of **twelve Testing Library rules and nothing else**, and a `Lint` step in the frontend
CI job. Two real findings came out of it; both are fixed. No style rule is enabled and no
formatting was touched.

**The command is `npm run lint`, and yes, the `"lint"` script changed.** It could not stay as
`next lint`: Next 14's wrapper looks for an `.eslintrc*` and does not read flat config, so pointing
it at this config would have produced a linter that exits 0 having checked nothing — the exact
failure this task exists to end.

## The rule set, rule by rule

All twelve are `error`. Each one is here because switching it off lets a test pass while proving
nothing, or fail for a reason other than the one it names. The full argument, with the same wording,
is in `frontend/eslint.config.mjs` where the next person will actually read it.

**The async group — the T-075 defect shape**

1. `await-async-queries` — an unawaited `findBy*` returns a pending promise, and every matcher
   passes against a promise object. The test is green whether the element ever appears or not.
2. `await-async-utils` — unawaited `waitFor` / `waitForElementToBeRemoved`: the test ends before
   the condition is evaluated, and the rejection lands inside some unrelated later test.
3. `await-async-events` — `userEvent`'s methods are async in v14; unawaited, the assertions below
   the click run against the screen as it was before the click.
4. `no-await-sync-queries` — `await screen.getByText(...)` resolves to the element, so it reads
   like a wait and is not one. The author believed there was a wait on that line; there is not.
5. `no-promise-in-fire-event` — the real shape is `fireEvent.click(screen.findByRole(...))`: a
   promise is dispatched as the element and the interaction never happens.
6. `no-wait-for-side-effects` — anything non-assertive inside a retried `waitFor` callback runs
   several times; a click in there fires twice on a slow machine and once on a fast one.
7. `no-wait-for-multiple-assertions` — read what it does in 7.16.2 before judging it: it fires on a
   *second assertion against the same subject* inside one `waitFor`, not on any two assertions.
   That second one is retried for the whole timeout when it fails, so a broken expectation is
   reported as "waitFor timed out" instead of as the assertion that failed. (Verified against the
   rule's source in `node_modules`, because its name says something broader than it does.)
8. `no-wait-for-snapshot` — a snapshot inside a retried callback captures whichever intermediate
   render the retry landed on, and writes it to disk as the settled state.
9. `prefer-query-by-disappearance` — `waitForElementToBeRemoved(() => getBy...)` throws the moment
   the element is gone, which is the condition being waited for; success and error are
   indistinguishable.

**Assertions that can never run, and queries that lie**

10. `prefer-presence-queries` — `expect(getBy...).not.toBeInTheDocument()` never reaches the
    matcher, because the query throws first. It does fail when the element is absent, but it fails
    saying it could not find the element it was asserting was absent.
11. `no-global-regexp-flag-in-query` — a `/g` regexp keeps `lastIndex` between calls, so the same
    query against the same DOM matches and then does not, depending on call order.
12. `no-dom-import` — `render`/`fireEvent` from `@testing-library/dom` rather than `/react` are the
    unwrapped versions: no `act()` around the event, so React state is not flushed before the next
    line reads the DOM, and no auto-cleanup, so the previous test's markup is still mounted.

**Deliberately off.** From a diagnostic pass with every non-deprecated rule the plugin ships turned
on at once — **2,261 problems**, of which 2,257 were preference:

```
  930 prefer-implicit-assert      898 prefer-user-event        231 no-node-access
   80 prefer-explicit-assert       36 prefer-find-by            32 prefer-screen-queries
   27 no-unnecessary-act           17 no-container               3 render-result-naming-convention
    2 no-manual-cleanup             1 no-test-id-queries
```

`prefer-implicit-assert` and `prefer-explicit-assert` are each other's opposite and the plugin ships
both — which is on its own the argument against "turn on what's recommended". `prefer-find-by` (36
sites) is the one a reader might want back: `waitFor` + `getBy` is correct, just longer than
`findBy`, so it is style by Rajeev's line and it would have put a 36-site diff through files three
other builders are in. `no-manual-cleanup` is **wrong here both times it fires** —
`calendar.test.tsx` and `shift-attendance.test.tsx` call `cleanup()` mid-test to unmount before
rendering again, without which every `getBy*` afterwards throws "found multiple elements"; the rule
flags the import and cannot tell that from a redundant `afterEach`. `no-debugging-utils` (0 hits) is
excluded on principle: it catches a left-behind `screen.debug()`, which is tidiness, not correctness.

**Scope: test files only** (`__tests__/**/*.{ts,tsx}`). Every enabled rule is a Testing Library rule
and is meaningless outside a test, so `app/`, `components/` and `lib/` match no config block. See
"Needs Rajeev" for the one thing that leaves on the table.

## CI

Added to the existing `frontend` job in `.github/workflows/ci.yml`, before the type check, so it
runs on every push and pull request to `main` (the workflow's existing triggers):

```yaml
      # Before the type check, because it is the cheaper of the two and because what it catches is
      # a test that passes without proving anything — which makes every green result below it
      # worth less. The rule set is deliberately tiny and argued for, rule by rule, in
      # frontend/eslint.config.mjs. `npm run lint` is `eslint . --max-warnings=0`; it is not
      # `next lint`, which needs an .eslintrc this project does not have and would lint nothing.
      - name: Lint
        working-directory: frontend
        run: npm run lint
```

It sits after `npm ci` and before `npx tsc --noEmit`, `npm test` and `npm run build`, all unchanged.
No other job was touched.

   it rather than widening. **It wants a task of its own.**
