# T-040 — the role-change endpoint is deleted: dead code that read as a feature

`PATCH /api/v1/users/{id}/role` and everything behind it are gone. **No screen ever called it and no
client wrapper survived** — this is the removal of dead machinery, not the removal of a feature, and
it is worth saying plainly because the machinery was convincing. It had four documented guards, full
before/after auditing, an integration test per guard, and a class javadoc describing it as "the
exemplar of before/after auditing". It looked exactly like a working feature, and that appearance is
what produced docket item **B10**: a task was raised to build a screen for an endpoint nobody was
calling. Leaving a second endpoint in that condition while naming the pattern would have been the
worse outcome.

What actually happened: it was written as the *seed* of user management (E1-S12) before hiring
existed. Hiring (E6-S8) then became the only act that grants a temple role, and the seed was never
pulled up. So it sat as a second door onto a decision the staff register owns — and, being unused, a
door nobody was watching.

## What the deletion costs, and what it does not

`RoleChangeIT` was the only test of four guards. Three of them go away with the code they guarded.
The fourth is the one that mattered and it was rebuilt first, which is why this task waited:

- **Guard 1, no self-change** — rebuilt on the staff path by T-039 and green above.
- **Guard 4, refusals are audited** — same, and the gate on this task.
- **Guard 3, no cross-tenant change** — the endpoint is gone; RLS itself is still covered by
  `RowLevelSecurityIT`, and `UserManagementIT > an admin cannot disable a user in another temple`
  (green above) still exercises the same RLS-as-not-found behaviour on the surviving endpoint.
- **Guard 2, no promotion to SUPER_ADMIN** — worth stating precisely, because this is the one that
  sounds alarming. The property now holds **structurally rather than by a guard**:
  `staff/SystemAccess.java:13-17` has exactly three constants — `TEMPLE_ADMIN`, `KITCHEN_MANAGER`,
  `KITCHEN_STAFF` — so the only remaining path that assigns a role cannot express `SUPER_ADMIN` at
  all. An unrepresentable value needs no runtime guard. (This also matches the standing decision
  that super-admin creation is out-of-band.) I verified this by reading the enum; I did not change
  it, and `staff/` is another builder's this wave.

Deleting `RoleChangeService` leaves **`ErrorCode.CANNOT_ASSIGN_SUPER_ADMIN` (KMS-400023) with no
writer anywhere** — it was thrown only from the deleted guard 2. It stays in `ErrorCode.java`
untouched, which is correct on both counts: codes are never reused or renumbered, and `ErrorCode.java`
is reserved. `ErrorCodeTest` iterates `ErrorCode.values()` for uniqueness and tone only, never for
"is this code thrown somewhere", so an unwritten code does not fail the build. `CANNOT_CHANGE_OWN_ROLE`
(KMS-400022) is **not** orphaned — `StaffEmploymentService:435` still throws it.
