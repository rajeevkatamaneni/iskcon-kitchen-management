# T-098 — field errors are now part of the product's voice, and a test keeps them there

## The policy question first, because the ledger says to answer it before touching anything

**Yes. Field errors are part of the product's voice.**

The reader of `"must not be blank"` is the same person, on the same screen, in the same second, as
the reader of `KMS-400001`. The two arrive in one JSON body. `CLAUDE.md` states the rule as
*"nothing technical reaches the user"* with no carve-out, and there is no argument for one: the
only reason field errors escaped it is that `ErrorCodeTest` walks an enum, and an annotation is not
in the enum. So this was never a second policy — it was one policy with an unpoliced channel.

What that implies, and what was built:

1. Every constraint reachable from a request body carries a message written for a person.
   **558 sites, 383 of which had none.**
2. A test enforces it — `FieldErrorMessageTest`, sitting beside `ErrorCodeTest` and reusing its
   jargon and tone lists verbatim, so one product keeps one register.
3. The scope rule is **structural, not a list**: a constraint is in scope if and only if it is
   reachable from a `@RequestBody` parameter of a `@RestController`. Entities, projections and
   internal service types are excluded *by that rule*, not by a hand-written exclusion list, so
   nothing starts or stops being checked because somebody edited an array of class names.

`ErrorCode.java` was **not needed and not opened for editing**. Every message here is field text; no
new code was required and none was allocated. (Its message strings were read, read-only, via
`grep -rhoE 'message = "[^"]*"'` across `src/main/java`, to match the house style — that grep hits
the 175 constraints that already had messages, which is where the style actually lives.)

## The rule the test enforces, and what it walks

1. Scan the classpath for `@RestController`.
2. Every `@RequestBody` parameter of every method on one is a root.
3. Walk fields transitively from each root — through `List<X>`, `Map<K,V>`, arrays and generic
   arguments — following only types under `org.iskcon.kms`.
4. Every constraint annotation (`@Constraint`-meta-annotated, so custom ones count too) on those
   fields *and on their type arguments* is a site.

`List<@Size(max = 100) String> tags` is a real shape in this tree — ten of them — and those
messages reach a user exactly as directly, so the walk reads `AnnotatedParameterizedType`
arguments as well as the field's own annotations.

**"Has no message" is tested exactly, not by guessing at English.** An unset `message` is not
empty; it is the literal `"{jakarta.validation.constraints.NotBlank.message}"`, a bundle key the
validator resolves out of the library's own properties file. The test looks for the braces.

Four checks on the words themselves, on top of that:
- not Jakarta's sentence retyped by hand (`"must not be blank"`, `"size must be between"`, … as
  fragments, so `"Name must not be blank."` is caught too);
- a capital and a full stop, so it reads as a sentence beside a `KMS-nnnnnn` one;
- `ErrorCodeTest`'s jargon list, verbatim;
- `ErrorCodeTest`'s tone list, verbatim.

The bare word "must" is **not** banned. `"Latitude must be between -90 and 90."` was written by a
person, is about the temple's data, and already ships. Only the library's specific sentences are.

The walk's number is **383 without a message out of 558 inspected**. The difference is that grep
counts javadoc mentions of `{@code @NotBlank}` and cannot see the 175 that already had one; the
walk reads the loaded classes. Both numbers are now zero-without-a-message.

## Acceptance criteria

**The policy question answered explicitly, at the top of the proof, before building.** Done —
first section. Yes, with the reasoning.

**Every constraint that can reach a user has a message in the product's voice.** 558 of 558, from
the test's own report. Verified by `everyConstraintCarriesAMessage` (no bundle key survives),
`noMessageIsJakartasPhrasing`, `everyMessageReadsAsASentence`, `noMessageContainsJargon` and
`toneIsNeutral`. The style was taken from the 175 that already had one plus `ErrorCode`'s own
sentences, not invented: "That name is too long.", "Choose a unit.", "Enter the date they joined."
are all pre-existing strings reused, and new ones are built on the same three shapes.

**A message is not a translation of the constraint.** `@NotBlank` on a vendor's name is
`"Enter the vendor's name."`, not `"Name must not be blank."`; `@Digits(integer = 10, fraction = 2)`
on a purchase cost is `"Enter a cost in rupees and paise, for example 4500."`, following the phone
field's what-is-wanted-plus-an-example standard and the salary message already in `HireStaffRequest`.

**Something enforces it, `ErrorCodeTest`-shaped, over the DTOs.** `FieldErrorMessageTest`, six
tests, in the same package, reusing `ErrorCodeTest`'s jargon and tone lists so the two channels
cannot drift apart.

**Out of scope is named as a rule the test enforces, not a list.** Reachability from a
`@RequestBody` on a `@RestController`. Entities and internal types are excluded by construction. No
exclusion list exists anywhere in the test.

**No vacuous pass.** `theWalkActuallyReachedTheProduct` asserts 60/90/90/500 floors and prints the
actual figure in every failure message. It walked **70 controllers, 108 request bodies, 110 types
and 558 constraints**, and writes all of it to `backend/build/reports/field-error-messages.txt`.

**Negative control.** Above, all five conditions, artefact at `docs/work/proof/control-T-098.log`.

## Not done / needs Rajeev

**No hand smoke-test.** T-098 changes no screen and adds no surface; it changes the words in an
existing `fieldErrors` payload. The payload is exercised by the six Testcontainers ITs above against
a real PostgreSQL and a real Spring MVC stack. **I did not drive the deployed staging app to post a
blank vendor name and read the new sentence back**, and that is the one thing not proven here. It
is a one-line check for whoever deploys this: post a vendor with an empty name and a bad phone, and
the reply should read `"Enter the vendor's name."` where it used to read `"must not be blank"`.

**Two request bodies are never validated at all, and both are outside this contract.** The test
reports them rather than asserting on them, because the fix is a controller signature and not a
message:

- `EmploymentBanController#retract(RetractEmploymentBanRequest)` — `@RequestBody(required = false)`
  with **no `@Valid`**. Its `@Size(max = 1000)` on `reason` has never run. I gave it a message; the
  message still cannot reach anybody until `@Valid` is added.
- `PurchaseOrderController#generate(GeneratePosRequest)` — same shape. `GeneratePosRequest` declares
  no constraints today, so nothing is lost yet; it will be the day somebody adds one.

  (The other four the report lists — three `byte[]` webhook bodies and one `Map<String,String>` —
  are correct as they are. There is nothing on a `byte[]` to validate.)

  **Worth a task**, because it is the same class of defect as T-098 itself: a check that looks like
  it is running and is not.

**Three pre-existing messages sit slightly outside the register but were left alone**, because
changing text already on staging is a product decision and not mine to take:
`"Yield must be greater than zero."`, `"Quantity must be greater than zero."` and
`"The yield must be more than zero."` read fine and are three different phrasings of one idea,
where a sibling field says `"A portion must be more than zero."`. The test deliberately permits all
four. If Rajeev wants one phrasing, it is a four-line change.

**`ErrorCode.java` was not needed.** Stated because the contract asked to be told if it was.
