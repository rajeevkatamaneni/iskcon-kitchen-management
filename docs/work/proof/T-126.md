## What was built

**Backend.** `PurchaseOrderView` gains `boolean vendorAbandoned` beside `cancelReason`;
`HEADER_SELECT` gains `po.vendor_abandoned` and `HEADER_MAPPER` reads it with `getBoolean` — the
column is `NOT NULL DEFAULT FALSE`, so there is no third state and every order raised before V118
reads false, which is the reading that blames nobody. One mapper serves both the detail endpoint and
the list, so the list carries it too.

**Client type.** `vendorAbandoned: boolean` on `PurchaseOrderView` in `api.ts` — **required, never
optional**, per the convention `PurchaseOrderLineView.ingredientId` documents. That is load-bearing
here rather than stylistic, and section 6 of the control tests it.

**The screen.** Under `Cancelled: {reason}`, guarded on `po.vendorAbandoned`:

```
<Badge tone="warning">Never delivered</Badge>
The vendor never delivered this order. It counts against their delivery record.
```

Three deliberate choices, all argued in a comment at the site:

- **A sentence, not a bare badge.** "Never delivered" next to a line that already says *Cancelled*
  is ambiguous — it could as easily mean the goods never came *because* we called it off. The
  sentence names who we are holding responsible, which is the entire difference between the two
  kinds of cancellation.
- **No new badge style.** `<Badge tone="warning">` is the marker this application already uses for
  this exact fact: `frontend/app/vendor-performance/page.tsx:196` renders the same component in the
  same tone for *"1 order never delivered"*.
- **The second sentence is the tick's own hint, said back.** The cancel form promises *"This counts
  against the vendor's delivery record."* on the way in; the order says the same thing on the way
  out, so a reader is not told two different things about one tick.
