## The dispatcher fix, and retries confirmed from the code

`NotificationDispatcher.dispatch` used to call `NotificationTemplate.valueOf(n.template())` bare. It now calls `templateNamed`, which returns null for an unknown or null name. For such a row the dispatcher:
- logs at WARN with the row's id and the stored name
- writes one `notification_attempts` row: FAILED, on the row's preferred channel, with `detail` = "This message's template no longer exists, so it could not be sent." That table is the only place a notification keeps a reason, and its channel column is required. Nothing reads `detail` on a screen today (grepped: only the dispatcher touches `notification_attempts`).
- marks the notification FAILED, which also bumps `kms.notifications.failed`
- returns normally

**Retries, from the code:**
- `SendNotificationJob.retryPolicy()` is `RetryPolicy.of(3, 5s)`.
- `KmsJob.execute` retries only when `run` throws. It schedules a fresh trigger while `attempt < maxAttempts`, then logs "parked as failed" and stops. A normal return is "completed", with no retry.
- `NotificationDispatcher.isTerminal` treats anything other than PENDING as terminal, and `dispatch` returns before touching a terminal row.

So a row failed this way is never retried: the job completes on its first attempt, and any later dispatch of the row, whether a duplicate enqueue or a retry, returns at `isTerminal`. With the old bare `valueOf` it threw, ran 3 attempts, parked, and stayed PENDING for ever, so it never showed in ops' failure list. `UnknownTemplateDispatchIT.failedThatWayIsTerminalAndListedAsItIs` dispatches it twice and finds 1 attempt.

**Ops' failure list:** `OpsService.recentFailures` reads `template` as text and has no reason column. The test calls `opsService.tenantOperations(temple)` and gets `failedToday` 1, with the failure listed under its stored name `SHIFT_REMINDER`. The plain reason lives in the attempt row, not in the ops list. Showing it there would need an `OpsService` change, which is not in my contract.

## Flattening: where, and its tests

It lives in `WhatsAppChannelAdapter.whatsappParameters`, used only for the Meta send.
- **Why the adapter:** it is the one place a notification becomes a WhatsApp send. SMS and email never pass through it, so they keep the line breaks as typed.
- **Why every parameter and not only `message`:** Meta's refusal applies to any parameter, and the temple announcement's intro is typed text too. Each run of whitespace becomes one space, and the ends are stripped. A value without a line break or double space comes out unchanged, which a test checks on the purchase-order fixture.

The other direct Meta send, `TenantWhatsAppSettingsService.sendTestMessage`, passes only the temple name and is not in my contract.

Tests in `WhatsAppChannelAdapterTest`, using the message `"Please arrive at 5am.\r\n\r\nBring  an apron."`:
- `aTwoLineBroadcastIsFlattenedForWhatsApp`: Meta receives `["Kitchen seva", "Please arrive at 5am. Bring an apron."]`, with no `\n`, `\r` or double space.
- `emailAndSmsKeepTheLineBreaks`: after the WhatsApp send, the same message's rendered body and parameters still hold the original text. A real `SmtpEmailAdapter` around a mocked relay then sends a MIME body containing it exactly. SMS has no provider and sends nothing, so what it is handed, the rendered body, is what the test checks.
