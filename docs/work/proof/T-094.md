## The finding that changed the fix, and it contradicts the brief

The brief said a devotee the relay throws on leaves `audience_count` saying forty against
thirty-nine rows. **That is not what happens.** `NotificationService.notify` is itself
`@Transactional`, so an exception leaving it does not merely get caught by `queueFor` — Spring's
transaction interceptor marks the *whole surrounding transaction* rollback-only on the way out
(`globalRollbackOnParticipationFailure` is true by default and nothing in this project changes it).
`send`'s commit then fails whatever `queueFor` did with the exception.

So the live behaviour on staging is worse than the brief describes: **one devotee the relay refuses
takes the entire send down with a 500 and nothing is recorded at all** — no recipient rows, no SENT
status, no audit entry. `queueFor`'s comment — *"One unreachable devotee is not a reason to abandon
the other three hundred and ninety"* — described behaviour the code has never had.

This is proved, not reasoned: the negative control's own test report contains

```
org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back
because it has been marked as rollback-only
```

sitting directly under three swallowed per-devotee warnings

```
Could not queue communication 3c106e6e-… for 12ccd46e-…: org.iskcon.kms.error.ApplicationException: KMS-500001 Someth…
```

which is exactly the shape lesson 4 asks for — the brief's stated mechanism tested as a claim, and
found wrong in a direction that mattered. **A single transaction around the whole send cannot keep
the promise the brief asks for**, however the recipient row is written inside it: the row rolls
back with everything else. Writing the row before the notify, or after it with a null notification,
would both have produced a green-looking fix that still lost the row.

## How every intended recipient was made durable

`send` is now two steps with a transaction boundary between them, which is the shape
`BroadcastService.plan`/`deliver` has used since E6-S7 against `shift_broadcast_recipients` — the
table `communication_recipients` was explicitly modelled on (`V59__communications.sql:26`), and
whose own class comment already states this reason: *"delivery is a best-effort loop outside it, so
a message that can't be queued to one volunteer neither rolls back the record nor stops the rest."*

1. `recordSend(...)`, inside one transaction that touches nobody: guards, audience, **one recipient
   row per intended recipient** (`notification_id` null, plain INSERT — a draft is sent once and
   `requireDraft` in the same transaction says so, so a conflict here would be news), the SENT
   status with `audience_count`, and the audit entry. The count and the rows are written from the
   same list in the same transaction and can no longer disagree.
2. The copies go to the relay afterwards, outside any transaction. `queueFor` no longer creates the
   row; it points the existing row at the copy that stands (`UPDATE … SET notification_id`). When
   the relay throws there is no copy to name and the row stays exactly as the send wrote it.

**Why an UPDATE and not "insert the row carrying whatever the attempt produced":** both leave the
same durable state, but only this one survives the rollback finding above — the record of intent has
to be written by the step that knows the audience, not by the step that may not survive. It also
means a failed *retry* leaves the failure it was retrying in place rather than erasing which copy it
was; null already means failed, and the old notification still says which channel and when.

Reading the null through:

- `failedRecipients` was an **inner** join and could never see a row with no notification. It is now
  a LEFT JOIN with `(n.status = 'FAILED' OR r.notification_id IS NULL)`. Nothing else can produce a
  null there: the column's `ON DELETE SET NULL` is never triggered, because nothing in the
  application deletes a notification (checked — no `DELETE FROM notifications` outside test teardown,
  and no retention job).
- `deliveries` mapped a null status to `"UNKNOWN"`, which `DeliveryOutcome` in
  `frontend/app/communications/page.tsx` renders through its fallback as **"Queued"** — a devotee
  nobody had written to appearing as one whose letter was on its way. It now reads `FAILED`, which
  that component already renders in red as "Failed", and which the page's `failed` counter (it
  filters `d.status === "FAILED"`) counts, so the retry offer appears for them. **No frontend change
  was needed and none was made.**

**Declared loudly, because it is a real behaviour change: a partial send is now durable.** If the
process dies between the two steps, or the relay refuses every copy, the message stays SENT with a
row for every intended recipient naming no notification — read as *Failed*, and reached by *Send it
to them again*. The failure that is not recoverable is the other one: rolling the record back while
copies are already on their way, after which pressing Send again writes to those devotees twice.

## How the empty case was branched

`nothingToRetry` now branches on the status as well as the count: `recipients == 0 && DRAFT` keeps
KMS-400143; `recipients == 0 && SENT` gets `ErrorCode.COMMUNICATION_REACHED_NOBODY` (KMS-400146,
used exactly as reserved, `ErrorCode.java` not edited). The test asserts both the new code and that
the door the old sentence sent the reader to is still shut (KMS-400086) — which is why "Send it
first" was a contradiction rather than a next step.

## Defect 3 — declined, with the reasoning

**I did not narrow the catch and did not add `REQUIRES_NEW` per recipient. Neither is now the right
change, and the split has already fixed the defect on the path that mattered.**

- On the **send** path there is no longer an ambient transaction, so a per-recipient failure really
  is per-recipient — including a JDBC one, which now rolls back only `notify`'s own transaction.
  `queueFor`'s promise is true for the first time. Narrowing the catch here would make it *worse*:
  it would abandon the remaining 399 for one recoverable database blip.
- On the **retry** path a database failure still dooms the transaction, and I left it that way. The
  outcome is identical with or without a narrowed catch (rollback and a 500); narrowing would only
  remove some misleading warnings, and a retry loops over the failures alone, so it is a handful of
  lines rather than 390. Rolling a retry back whole costs nothing: the recipients it was retrying
  are left saying FAILED, the button is still there, and nothing was recorded that did not happen.
- **`REQUIRES_NEW` per recipient is the wrong shape here and I would argue against it in its own
  task too.** It commits each notification independently while the recipient rows and the SENT
  status stay in the outer transaction — so an outer rollback leaves devotees holding a letter for a
  communication still marked DRAFT, which can then be sent again. That is a double-send, the one
  failure mode this feature cannot recover from. The plan/deliver split gets the durability without
  it, and gets the safe failure mode instead.

## Not done / needs Rajeev

**1. KMS-400146's wording does not survive contact with the code, and I recommend amending the next
step before commit.** The message is right; the next step names the wrong cause.

> `"This message was sent, but it reached nobody."` / `"Check who is set to receive this category
> before writing another."`

Once every intended recipient gets a row, this error can only fire for messages sent by the code
that did not — i.e. the rows on staging right now, which is exactly what Rajeev will press the
button on. And an empty audience is *not* how they got there: `send` refuses an empty audience with
KMS-400087 before it ever writes SENT, so a SENT message always had an audience. (The brief's line
that 400146 "protects an audience that was genuinely empty" is wrong for the same reason —
KMS-400087 already does that, at send time.) What actually happened is that the relay refused every
copy. So "check who is set to receive this category" sends the reader to audit a list that was
fine. Suggested, for the reserving session to accept or reject:

> `"This message was sent, but no copy of it ever reached anybody."` / `"There is nothing here to
> send again. Write the message again and send it."`

That names a door the reader can open — Write a message — and is true of every case that can reach
this code. I have **not** edited `ErrorCode.java`; the code as reserved is what the tests assert, so
amending the text means updating the one `$.message` assertion in
`CommunicationRetryIT.aSentMessageWithNoRecipientsSaysItReachedNobody`.

**2. A pre-existing double-send race in `send`, found while working and deliberately not fixed.**
`send` reads the status and writes it in one transaction but takes **no row lock**, so under READ
COMMITTED two admins pressing *Send* at the same moment can both see DRAFT and both send the whole
letter to the whole audience. It is the same hole `lockForRetry` was added for in T-084, on the
louder path. My change neither widens nor narrows that window. Fixing it is one line
(`lockForRetry(id)` at the top of `recordSend`, renamed), but it is a behaviour change nobody asked
for in a wave with four other builders in the tree, so it should be its own task with its own
concurrency test.

**3. `templeName()` is still queried once per recipient** inside `queueFor`, which now costs a
connection checkout each (the tenant `set_config` runs on checkout). It was already per-recipient
before this change and hoisting it changes a signature `sendTest` and `retryFailed` share, so I left
it. Worth a line in a tidying task if a 400-person send is ever timed.

**4. Not smoke-tested by hand, and it cannot honestly be.** Commandment 5 wants the user-facing
surface driven, but the surface here only differs when the relay refuses a copy, which cannot be
made to happen in a browser against UAT — the relay either takes the message or it does not. What
*can* be checked on staging after deploy, and is the reason this task exists: open the sent message
Rajeev is going to retry, confirm the recipient list now shows those devotees as **Failed** rather
than as missing or "Queued", press *Send it to them again*, and confirm it reports the number it
reached rather than bouncing between KMS-400143 and KMS-400086. **Note that the rows already on
staging cannot be repaired by this fix** — a recipient row that was never written is not created
retroactively, so a message sent before this deploys still has no rows and will answer KMS-400146
(see item 1 for what it should then say). Messages sent after it will behave.
