# T-060 — A described line no longer drags a vendor's fill rate down for ever

`VendorPerformanceService.countLines` counted every purchase-order line as *ordered* and
left-joined `goods_receipt_lines` for *accepted*. A described line (T-024: no `ingredient_id`, a
description instead) is orderable and payable but can never be received — `ReceivingService`
refuses it with `KMS-400129` and `goods_receipt_lines.ingredient_id` is NOT NULL — so its accepted
quantity is permanently zero. Four plastic stools bought from a wholesaler therefore became a
zero-fill entry on that wholesaler's scorecard that no later delivery could ever clear.

The fix is one clause, `AND pol.ingredient_id IS NOT NULL`, and a comment that says it is a ruling
rather than a filter, so the next reader does not delete it as dead weight.

**Files changed** — all three inside the contract, nothing else touched:

- `backend/src/main/java/org/iskcon/kms/vendor/VendorPerformanceService.java` — the clause, plus two
  paragraphs on `countLines`'s doc comment (why a described line is not judged, and what happens at
  the boundary).
- `backend/src/test/java/org/iskcon/kms/vendor/VendorPerformanceIT.java` — two new tests and a
  `describedLine(...)` helper.
- `docs/work/proof/T-060.md` — this file.

No migration, no error code, no permission, no change to the scorecard's response shape.

## The judgement, and the boundary cases

**Why exclusion is the right ruling, not just the cheap one.** A fill rate is "the fraction of what
was asked for that turned up". For a described line that question has no answer the vendor can
affect: the schema forbids anyone from ever recording that the stools arrived. Scoring it 0% is not
a judgement about the supplier, it is a judgement about our own schema, published on a page whose
entire purpose is to be evidence about suppliers. Excluding it is the same one-clause shape T-024
already used for the shopping list's outstanding map
(`ShoppingListService:260`, `AND pol.ingredient_id IS NOT NULL`), so the two consumers now ask the
discriminator the same question.

**A PO with only described lines.** The vendor is *present* on the report — `countOrders` still
counts the order placed, and the open columns still age it — but contributes **no judged lines**,
so `Totals.fillRate()` returns null on a zero denominator and the fill-rate cell is **blank beside
a lines-judged count of 0, not 0%**. That is the choice the class comment already makes for an
order with no needed-by date ("counted aside rather than scored a silent hundred per cent"), and
the existing `anOrderWithTimeLeftIsNotJudged` test already expects a blank `fillRatePercent`, so
nothing new has to be learned to read the column. The second new test pins this.

**`countRejections` does not inherit the defect.** It starts from `goods_receipt_lines` and joins
outward. A described line can never have a receipt line, so it can never appear there; there is
nothing to exclude and adding a clause would be noise.

**The on-time calculation does inherit a version of it — reported, not fixed. See "Needs Rajeev".**

## Acceptance criteria

1. **"A vendor whose PO carries a described line alongside an ingredient line has the same fill
   rate as if the described line were not there, and a test proves it with real rows."** —
   `aDescribedLineDoesNotDragTheFillRateDown` builds both vendors as real rows (PO, PO lines,
   goods receipt, receipt line) and asserts 75% for each, and 75% over 2 lines in the report
   totals. The control shows it reading 38% without the clause.
2. **"A vendor whose only lines are described is handled deliberately, and the code says which way
   and why."** — Blank fill rate, `linesJudged` 0, vendor still on the report.
   `anOrderOfOnlyDescribedLinesIsNotJudgedOnFill` asserts it; the second new paragraph on
   `countLines` states the ruling and ties it to the existing needed-by precedent.
3. **"The existing `VendorPerformanceIT` assertions all still pass."** — 14 pre-existing tests,
   all PASSED above, unmodified.
4. **"The exclusion carries a comment that survives the next reader."** — A doc paragraph on
   `countLines` in the file's own voice, plus two SQL comment lines immediately above the clause
   pointing back to it. Both explain *why*, not *what*.

## Not done / needs Rajeev

**1. The same defect exists on the on-time half, and it is worse than the fill rate was. Not
fixed — it is a product decision, and it is bigger than this file.**

`countOrders` judges on-time per order at its first goods receipt. An order of *nothing but*
described lines can never have a receipt at all: `ReceivingService.validate` refuses any receipt
line pointing at a described PO line, so there is no way to record that the stools arrived. That
order therefore scores **late for ever**, and its status never leaves `SENT`, so it also sits in
the open-orders aging bucket for ever, ageing past 31 days and appearing as a supplier sitting on
an order since last year. `anOrderOfOnlyDescribedLinesIsNotJudgedOnFill` pins this as today's
behaviour (`onTimePercent` 0) with a comment saying it is pinned, not endorsed.

I did not fix it inside `countLines`'s neighbour because the honest fix is not a `WHERE` clause: it
is the missing lifecycle step — how does an order of four plastic stools ever get closed? Either
described lines get a "these arrived" acknowledgement (a status transition, not a stock movement),
or such orders are excluded from on-time judgement entirely, which would also let a genuinely
undelivered stool order score nothing at all. That is a decision about the product, it touches the
purchase-order lifecycle and probably the receiving screen, and it is outside my contract in every
direction. **Suggest it be filed as its own task.**

**2. Out of contract and deliberately untouched, as briefed:** the `VendorInvoiceService` variance
count, and the compile break I found in another builder's `ShoppingListController.java` (which had
resolved itself by my next run).

**3. No hand smoke test.** This is a backend query change with no new user-facing surface and no
change to the response shape, and the deployed staging environment has no described-line purchase
order on it to look at. The vendor-performance screen renders `fillRatePercent`/`linesJudged`
exactly as before; a blank fill-rate cell is a path that screen already handles, because an order
still inside its needed-by date produces one today. Worth a look on staging once T-024's described
lines can actually be created there.

**4. Not committed, not pushed, not deployed.** Working tree left dirty with the three files above.
