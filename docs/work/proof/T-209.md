**How the legacy match works**

- `fingerprint(model)` is now `fingerprint(model, null)`: the old material minus the equipment segment (segment and its separator both gone).
- `fingerprint(model, legacyEquipment)` rebuilds the old material exactly, with the equipment segment where it used to sit.
- In `withVersion`: if the new fingerprint matches, keep the version (unchanged path). Otherwise, if a version exists and the stored value equals the legacy fingerprint of the meal as it is now (equipment read with the old query and old wording, now a private `legacyEquipment()`), keep the version and overwrite the stored value with the new fingerprint, so that meal never takes this path again. `updated_at` is not touched, because the meal did not change. Otherwise bump as before.
- The equipment query therefore still exists, but only for this comparison, and it only runs when the current fingerprint does not match. The brief said to remove the `equipment_items` query; it cannot go entirely while the legacy match needs the old material. Its comment says when it can be deleted.
- Proof that the legacy material is byte-for-byte what the old code stored: before editing anything, a temporary test on the unmodified tree printed the fixture's Lunch and read `meals.card_fingerprint`. It was `816f33912b82d6342d9c80d873e6f5419bc6e5c696cd972b2b1c2c329c435487`. After the change, the new reprint test's legacy value was asserted equal to that constant for one run (see below), and the assertion was then taken out, so a later change to the card's wording does not break an unrelated test.
