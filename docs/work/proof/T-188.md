## The cause, proven before any main code changed

The count is `TenantWhatsAppSettingsService.pending`. Before T-188, a temple whose `whatsapp_template_fingerprints` is `{}` skipped the loop entirely (`if (!fingerprints.isEmpty())`), and a null fingerprint counted nothing. A temple that last sent before V129 therefore always read `{changed:0, refused:0, accountChanged:false}`, whatever Meta held.

Reproduction test `aPreV129TempleWithOlderWordingAtMetaIsNotShownAsNothingWaiting`:
- The temple is set up exactly as the existing `aTempleThatSentBeforeV129` fixture does: submitted date set, fingerprints `'{}'`, no account recorded.
- Meta (the local HTTP fake) holds older wording for 11 templates.
- The real `WhatsAppTemplateComparison` is asserted to find exactly those 11 not matching. That is the staging symptom.
- The view is then read, and the test asserts Meta was asked nothing and that something is waiting. "Something is waiting" is read generically over the JSON fields, so it compiled against the old shape.

The 11 names are templates whose code changed in 651bdbd. They stand in for staging's 11 and are not claimed to be the same set. The count never looks at Meta, so which 11 it is cannot change the result.

## Option chosen: (b), a distinct `unchecked` count

- **(a) would print a false number.** Counting an unknown as changed would make South Bengaluru read "19 templates changed since they were last sent" when 11 did. T-169a's objection to that still holds.
- **(c) was rejected.** The stored Meta copy is taken only at a Reload, which already records fingerprints, or at an operator's Refresh, so it would help only a temple an operator refreshed since the release. Its freshness also cannot be proven from `whatsapp_template_wording_seen`. V130 adds no row when a template returns to an earlier wording, so after a rollback `taken_at > first_seen_at` holds for a copy that compared a different wording. It would need (b) as its fallback anyway.
- **(b) says what is true.** It adds no call to Meta, because the count stays a pure function of the row.

**The rule.** Every template in this release not already counted in `refused` lands in exactly one place:
- `unchecked` when the temple has no fingerprints at all, or this template's fingerprint is null;
- `changed` when the stored fingerprint differs, or when a temple that has fingerprints has no key for this template;
- nowhere when it matches.

JSON is `{"changed":…,"refused":…,"accountChanged":…,"unchecked":…}`. The audit entry on a Reload also records `whatsappTemplatesUnchecked`.

**Behaviour change, stated for review.** A first connection to an account that already held templates now reads as unchecked. Before, it read as nothing waiting, because a first connection records null for every template Meta already held. It is pinned by `aFirstConnectionToAnAccountThatAlreadyHeldTemplatesIsUnchecked`, and the Reload that follows clears it. A null written by a Reload that could not reword always comes with a REFUSED or NOT_REACHED list entry, so that template stays in `refused` and is not double-counted.

**T-169a's rule is reversed.** The test that asserted it, `aTempleThatSentBeforeV129ClaimsNothing`, is now `aTempleThatSentBeforeV129IsUncheckedNotChanged`, and its comment says why. It asserts 19 unchecked and 0 changed, and 0 unchecked after the Reload.

**Button order** (`templatesButtonLabel`): changed account, then unchecked, then today's counts, then the date. With unchecked above zero and nothing ever sent, it keeps "Templates not yet sent to Meta". `waiting` includes `unchecked ?? 0`, so the button is `btn-primary`. The page reads `pending.unchecked ?? 0` everywhere, so it compiles whether the field is optional or required.
