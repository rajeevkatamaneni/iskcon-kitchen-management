## The name, and why

**`templeWhatsappEverSent`.**

The defect in the old name was positional, not lexical. The field sits on a purchase-order payload
next to `order.sentAt`, `order.status` and `order.cancelledAt` — every neighbour is a fact about
the order — so a reader supplies "this order" as the subject and reads it as *have we sent this
one*. Putting `temple` first fixes the subject in the first word, before the reader reaches
`EverSent` and guesses. That is the ux-writing rule about front-loading the information that is
actually being lost, applied to an identifier.

It also has the property that made it cheap: every sentence already written about this field stays
true, so the doc comment's substance survives a rename rather than needing re-argued.

Rejected, and why:

- **`templeWhatsappWorks`** — "works" is not what is stored. A temple with valid, verified
  credentials that has never sent a message also "works" in the ordinary sense of the word, and
  that is precisely the state the 2026-09-10 ruling says must *not* show the button. The name
  would trade one misreading for a worse one, because this one would mislead about behaviour.
- **`whatsappEverSentByTemple`** — the misleading word is still first. Someone scanning a field
  list reads `whatsappEverSent…` and stops before the correction arrives.
- **`tenantWhatsappEverSent`** — "tenant" is our word for it, not the product's. The application
  says temple everywhere a person can see, the Java doc comment on this very field already says
  "this temple", and CLAUDE.md asks for the same label in every view.

### `hasEverSentSuccessfully()` — I agree, no rename

It should stay as it is. The ambiguity was caused by the field's neighbours, and this method has
none of them: it hangs off `TenantWhatsAppSettingsService`, whose own type name supplies the
subject, and at its single call site there is no order in scope to confuse it with —

```java
header, lines, events, whatsappSettings.hasEverSentSuccessfully(),
```

Renaming it would also mean opening `TenantWhatsAppSettingsService.java` and `WhatsAppLastSentIT`,
both outside this contract, for no reader who is currently being misled.

## `deliveryScore` — it comes too, and here is the argument

`deliveryScore?: OrderDeliveryScore | null` is now `deliveryScore: OrderDeliveryScore | null`.

**For.** The stated reason for its optionality is spent: the comment says it is optional because
"existing fixtures construct this interface", and every construction site in the repository is
inside this contract and now updated — `grep -rln PurchaseOrderDetailView frontend` returns eight
files, of which six construct one (the six fixtures); the other two are `page.tsx`, which only
reads it, and `api.ts`, which declares it. Beyond that, `undefined` is not a state the wire can
produce: the Java record component
is `OrderDeliveryScore deliveryScore`, non-optional, and the server always sends it. The `?` was
modelling something that cannot happen. And the `| null` arm already says "nothing to show"
explicitly, so optionality adds no expressive power at all — it only removes the compiler's
requirement that a fixture state which case it is, which is exactly the hazard this same file cites
`PurchaseOrderLineView.ingredientId` for.

**The strongest argument against, stated fairly.** The `undefined`-reads-as-safe claim genuinely
does hold for `deliveryScore`: an absent score renders as "nothing to show", the same benign
outcome as null, so nothing bad happens at runtime if a payload omits it. That means requiredness
buys no runtime safety here — and it has a real cost, five fixtures that care nothing about
delivery scores now each carry a `deliveryScore: null` line and a comment explaining it. On a
narrow reading, tightening a field that cannot hurt anyone is churn.

**Why I moved it anyway.** The benefit was never runtime safety; it is that a fixture can no longer
differ silently from the payload the screen actually receives. A test that omits the score is
exercising a shape the server never sends, and that is the specific failure this file's convention
exists to prevent. It applies word for word to both fields. Leaving one of a pair fixed also leaves
a live counter-example sitting two lines below the fixed one, and the next person copies whichever
they see first.

`page.tsx:109` keeps `deliveryScoreLine(score: OrderDeliveryScore | null | undefined, …)`. That
`| undefined` is still correct and was deliberately left: it comes from `data?.deliveryScore`, and
`data` itself is undefined while the query loads.
