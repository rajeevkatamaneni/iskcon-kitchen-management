# T-009 — An edit screen for an equipment record, and a confirmation before a machine is scrapped

Both halves are client-side only. The `PUT` behind the edit screen has existed since the register
did and had no caller, so a transposed digit in a serial number was permanent; and `SCRAPPED` sat in
a plain dropdown next to three reversible values while being the one the service refuses to move off
again. No migration, no error code, no permission: nothing about either fault was on the server.

**`SCRAPPED` is still terminal.** Nothing was added that un-scraps, reverses or restores. The
dialog says so in the words the acceptance asked for and offers exactly two buttons, and there is a
test asserting there is no third.

## Acceptance criteria

| Criterion | How it was verified |
|---|---|
| A serial number corrected on the edit screen persists and shows on the detail page | `corrects a serial number and sends it back to the record` — asserts `updateEquipment("eq-1", {...serialNumber: "WG-4417"...})` is called with the **whole** field set, then that the screen returns to `/equipment/eq-1?saved=…`. The detail page reads that record back from `getEquipment` and prints `serialNumber` in its *Serial number* fact, which `equipment.test.tsx` already covers as an item-page field. Not verified against a live server — see below. |
| Choosing `SCRAPPED` requires an explicit confirmation naming that it cannot be undone | `asks before scrapping, and names the consequence` — asserts `changeEquipmentCondition` has **not** been called when the commit button is pressed, that a `role="dialog"`/`aria-modal` element appears, and that it contains `/cannot be undone/i` and `/condition can never be changed again/i`. `sends the change only once it has been confirmed` covers the confirm path; `sends nothing at all when the question is answered no` covers Cancel (and that the typed reason survives it). |
| No other condition change gains a confirmation | `asks nothing before a condition that can be taken back` — loops `GOOD`, `NEEDS_REPAIR`, `IN_REPAIR`, asserting for each that no dialog appears and the request goes on the single press. |
| `SCRAPPED` stays terminal — no undo added | `offers no way back from scrapped, because there is not one` — the dialog's buttons are exactly `["Cancel", "Scrap it"]`, and it carries no `/un-?scrap\|restore\|bring it back\|reverse/i` wording. No un-scrap path exists anywhere in either file. |
| Edit screen behind the same roles as the register's writes | `RequireRole roles={["TEMPLE_ADMIN", "KITCHEN_MANAGER", "KITCHEN_STAFF"]}` — copied verbatim from `/equipment/new`, not invented. Test: `refuses a role the register is not for` (VOLUNTEER gets *not your page*). |
| `tsc --noEmit` clean; new vitest file passes; `npm run build` succeeds | All three above, exit 0. |

Beyond the acceptance list, and worth naming because it is where this screen could have gone wrong:
`offers neither condition nor the service schedule, because the endpoint refuses both` asserts the
edit form has no condition control, no interval count, no interval unit and no service company.
`UpdateEquipmentRequest` refuses all of them, so offering any would have been offering a request the
server throws away.

## Design decisions worth a second pair of eyes

- **Where the confirmation lives.** Inside `ChangeConditionForm`, as a modal over the form it
  interrupts — the same shape as `app/kitchens/page.tsx`'s delete and `VendorStatusDialog`. Escape
  cancels, and `autoFocus` puts the keyboard on **Cancel**, so nothing destructive is one Enter away
  from a dialog somebody has not finished reading. (`Button` is not a `forwardRef` component, so
  focus is set with `autoFocus` rather than a ref; `components/ds/Button.tsx` is outside my
  contract and was not changed.)
- **It asks whenever `SCRAPPED` is chosen**, including on a machine already scrapped, rather than
  only on a transition. One rule with no exception, and the server refuses the already-scrapped case
  anyway.
- **Returning to the record, not the list.** Design system rule 8 wants the confirmation waiting on
  the list you came from; for a correction that list is the record itself, because it is the one
  place the correction can be seen to have landed. So `/equipment/[id]?saved=<name>`, captured
  behind a `useRef` and `router.replace`d out of the URL — the exact ref-guard the Ingredients flash
  loop needed — with an auto-dismissing `InlineNotice`. That required wrapping the detail view in
  `<Suspense>` for `useSearchParams`, as `/equipment` already does.
- **The way in is *Edit details*, a ghost `ButtonLink`** in the detail page's header, before *Change
  condition*. Named "details" so it does not read as a way to change state.

## Not done / needs Rajeev

- **No hand smoke-test.** Commandment 5 wants a new user-facing surface walked by hand. I did not
  run the app or drive a browser: the phase is serialised behind a shared checkout and lock, and
  starting a dev server or deploying from a builder is outside what this task may do. Both screens
  are proven only by vitest and `next build`. **The serial-number round trip has never touched a
  real server** — the `PUT` is exercised against a mock, so the acceptance criterion "persists and
  shows on the detail page" is proven up to the API boundary and no further. It wants one walk on
  UAT: edit a serial number, save, confirm the item page shows the new one after a reload.
- **The dialog is not focus-trapped.** It sets initial focus and closes on Escape, matching the two
  dialogs already in the codebase, but Tab can still reach the form behind it — a pre-existing
  pattern-level gap, not something I introduced, and not something I could fix inside this contract
  since it belongs in a shared component.
- **Scrapping stays one-way, deliberately.** Question 13 (whether it should ever be reversible) is
  still open with Rajeev. Nothing here answers it.
