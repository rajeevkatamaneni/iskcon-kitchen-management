## What changed at each of the three sites

Removed `private static final String FUTURE = "2026-12-01";` (line 53) entirely — no absolute
future date remains anywhere in the file. All three call sites now use the file's own
`tomorrowAtTheTemple()` helper (added by T-085, unchanged by me), exactly as instructed.

I did not assume the three sites wanted the same thing — I read `SignupService.java` (read-only,
not in my contract, not modified) to find out what each one actually depends on:

1. **`coordinatorReleasesNamedVolunteer` (was :319, now :318).** Calls the coordinator's release
   endpoint, which runs `SignupService.releaseSignup`. That method's guard is
   `if (!start.isAfter(LocalDateTime.now(clock.zone()))) throw SHIFT_ALREADY_STARTED;` — literally
   "is the shift's start still ahead of now." `tomorrowAtTheTemple()` (tomorrow at the temple's
   zone, shift starts 08:00 by the 3-arg `shift()` overload) always satisfies this, regardless of
   what time of day the suite runs. **Genuinely depends on a future date**, for the guard to let
   the release through at all.

2. **`releasingSomebodyNotOnTheShift` (was :346, now :345).** Same endpoint, same guard, run
   first — before the "not on shift" check that the test is actually about. With a past or
   already-started date the guard fires first and the test gets `SHIFT_ALREADY_STARTED` where it
   expects the not-on-shift code. **Also genuinely depends on a future date**, for an unrelated
   reason to the test's own name: the guard sits in front of the behaviour under test.

3. **`volunteerCannotReleaseSomebodyElse` (was :357, now :356).** This one is different, and I
   checked it separately rather than assuming it matched the other two. The release itself is
   blocked by `@PreAuthorize("hasAuthority('MANAGE_VOLUNTEER_SHIFTS')")` on the controller, which
   Spring evaluates *before* the service method (and its date guard) ever runs — so the 403 this
   test asserts does not depend on the shift's date at all. But the test's second assertion reads
   `vol2`'s own `/api/v1/my-shifts`, and `SignupService.myShifts` filters
   `s.shift_date >= CURRENT_DATE`. With a past date, vol2's still-active signup simply drops out
   of that list and the "vol2 is still on the roster" assertion fails on a length mismatch — not
   because anything about the release logic changed, but because the read-side listing hides past
   shifts. So this site does need a future date too, just not for the reason its name suggests.
   The control run below is what surfaced this; the previous two sites' dependence I could read
   straight off `SignupService`, but this one I would have gotten wrong by code-reading alone.

All three genuinely wanted "future," and `tomorrowAtTheTemple()` covers all three identically —
there was no site that needed a different offset once I understood why it was failing.

## The acceptance test: does this actually survive the clock passing 1 December 2026?

I did not set the machine clock forward. `SignupService` and `TempleClock` call
`LocalDateTime.now(...)` / `LocalDate.now(...)` directly — there is no injectable `Clock` bean —
so faking "now" for the JVM without editing product code would mean either changing the real OS
clock (out of the question: this checkout has three other builders and Docker/Testcontainers
running concurrently right now — a global clock jump would corrupt their runs, TLS validation,
container timestamps, and the lock's own staleness check, for no gain I could reliably attribute
to only my test) or `DYLD_INSERT_LIBRARIES`-based JVM time-faking (`libfaketime`), which is
well-documented as unreliable against the JVM specifically (cached boot time, per-thread syscall
paths) and would have risked producing a result that *looked* like proof without being one.

Instead I used the structure the task hinted at: the guard in question,
`start.isAfter(LocalDateTime.now(clock.zone()))`, is a pure comparison between a shift's dated
timestamp and "now." Its outcome depends only on whether that timestamp is *before* or *after*
now — not on which specific date "now" or the deadline is. So rather than moving "now" forward
past `2026-12-01`, I moved the shift's date backward past "now," using the file's own existing
`PAST` constant (`"2020-01-01"`) — which is already, today, in exactly the state `FUTURE` will be
in once 1 December 2026 has passed. This exercises the identical branch of identical code that
would fire on that date, today, with no clock manipulation of any kind.
