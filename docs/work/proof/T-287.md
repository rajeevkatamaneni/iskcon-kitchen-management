## What it does

Server:
- **GET close-matches** lists one `ImportCloseMatchView` per distinct base name that the matcher calls CLOSE (not EXACT) against the temple's catalogue as it stood before the import. It writes nothing.
  - Two lines with the same normalised base ("Tomatos, chopped" and "Tomatos") get one row, carrying the first line's note.
  - Close matches against an ingredient this same import creates are not asked about. That can't be listed in advance, and "Use" can't name a row that doesn't exist yet. Those lines keep the old behaviour: exact re-use, otherwise create.
- **POST** plans the lines and checks the answers before anything is written.
  - Exact match: mapped silently, as before.
  - "Use": the line goes on the listed ingredient, with its note kept. Nothing is created.
  - "Different" (`useIngredientId: null`, `confirmDifferent: true`): the ingredient is created as an unmatched one would be (library_derived). It is audited in the same shape as R-DUP-2's `IngredientService.create`:
    - `INGREDIENT_ADDED` on the new ingredient
    - reason: `Added although it looks like “Tomato, ripe”: confirmed as a different ingredient.`
    - `after_state.confirmedDifferentFrom` = {id, name, matchedName, kind}
  - `RECIPE_IMPORTED.after_state` also gets `closeMatches: [{libraryName, lookedLike, answer: USED_EXISTING|DIFFERENT_INGREDIENT}]`, but only when there were close matches.
- **Refusals.** Every one writes nothing (tests assert zero recipes, categories, lines and audit rows, and the ingredient count unchanged).
  - **Unanswered → 409 KMS-400156.** `ErrorResponse` can only carry `{field, message}` pairs, so `closeMatches` is flattened. Per match i it sends `closeMatches[i].libraryName`, `closeMatches[i].note` (left out when null), `closeMatches[i].existingIngredientId` and `closeMatches[i].existingIngredientName`, listing every match, not only the unanswered ones. `closeMatchesFrom()` rebuilds `ImportCloseMatchView[]` from them.
  - `{useIngredientId: null, confirmDifferent: false}` counts as unanswered, the same as on the ingredient form.
  - **Bad answers → 400 KMS-400001, one field error.** The first problem found is the one reported:
    - `decisions[i]`: a null entry.
    - `decisions[i].libraryName`: blank; or no close match by that name (compared as the matcher normalises, so "tomatoes" answers "Tomatos"); or a repeat answer.
    - `decisions[i].useIngredientId`: not the listed ingredient.
    - `decisions[i].confirmDifferent`: both an id and `confirmDifferent: true`.
  - With no body, a recipe with no close match copies exactly as before.

Screen, on both copy actions:
- **The flow.** Pressing Add calls `importCloseMatches` first. If the list is empty, it copies at once, with no body. If not, `ImportCloseMatches` opens. A KMS-400156 from the POST also opens it, using the parsed list.
- **Each row:**
  - It shows "Tomatos · chopped" and asks "Did you mean Tomato, ripe?".
  - The buttons are "Use Tomato, ripe" and "It’s a different ingredient".
  - "Different" opens the R-DUP-2 confirmation, in its words: "Keep “Tomatos” separate from Tomato, ripe?", "It will have its own stock, prices and orders. Your choice is recorded in the audit log.", then "Go back" and "Keep it separate".
  - An answered row reads "Using Tomato, ripe." or "Kept separate. “Tomatos” will be added as a new ingredient.", with a "Change" button.
- **The dialog itself:**
  - Heading: "Did you mean these ingredients?" (or "this ingredient").
  - Footer: "Cancel" and "Add to my recipes". "Add to my recipes" stays enabled. Pressed with a row unanswered, it says "Choose an answer for every ingredient first." and focuses that row.
- **Accessibility:**
  - `role="dialog"`, `aria-modal`, labelled and described. It is portalled to `body`, and every other body child is made `inert`.
  - Focus goes to the first "Use" on open. It moves to the next unanswered row after each answer, then to "Add to my recipes", and returns to the opener on close.
  - Escape backs out of a confirmation first, then cancels. Tab wraps inside the dialog.

## Acceptance criteria

- **"Tomatos" with "Tomato, ripe" and no answer → 400156 with closeMatches, nothing written.** Checked by IT `noAnswerIsRefusedAndWritesNothing`. It asserts 409, the code, the 4 flattened fields and their values, and that nothing was written. The negative control fails it.
- **"Use" → no new ingredient; the line is on the existing one with its note.** Checked by IT `useMapsTheLineToTheExistingIngredient` (ingredientsCreated 0; lines on Tomato, ripe and Green chilli; notes "chopped", "slit"). The control fails it.
- **"Different" + confirm → new ingredient + audit row.** Checked by IT `differentCreatesAndAudits`: library_derived row; `INGREDIENT_ADDED` with entity_id, reason text, `confirmedDifferentFrom` id, name and kind CLOSE, and tenant_id templeA.
- **Exact match silent.** Checked by IT `exactMatchIsSilent`: GET returns [], the no-body POST gives 201, nothing is created, and there is no `closeMatches` key in the audit.
- **Answers validated.** Checked by IT `answersAreValidated`: unknown name, wrong id, both answers at once, a repeat by normalised name, and a blank name, each checked for its field path, then nothing written. Also `differentWithoutConfirmationIsNoAnswer`, which returns 400156.
- **Other checks, beyond the ACs:**
  - RLS: another temple's "Tomato, ripe" is never listed.
  - A VOLUNTEER gets 403 on both GET and POST.
  - One question per repeated name.
- **Screen:**
  - lists every close match
  - Use answers the row
  - different needs a confirmation, and Go back undoes it
  - nothing is sent until every row is answered
  - keyboard focus order, Escape, the Tab wrap, inert background and focus restore
