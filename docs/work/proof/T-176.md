## Mechanism, and why

A class-level constraint `@NotAtZeroZero` on `ProvisionTenantRequest`. Its validator,
`NotAtZeroZeroValidator`, refuses when both coordinates compare equal to zero (`compareTo`, so `0`,
`0.0` and `0.000000` all count). It files the violation on the `latitude` property node, so Spring
reports it as an ordinary field error for `latitude`. In `GlobalExceptionHandler`, a new check
`isOnlyATempleAtZeroZero` sits beside the phone one. When every error is this constraint the answer
is `KMS-400002`, otherwise the codes are chosen exactly as before.

Why this route. It is the one that gives both requirements from one place. A service throw would give
the code but no field error. An `@AssertTrue` would give neither the field name nor a way to tell it
from other object errors. A constraint on the `latitude` field alone cannot see longitude. If either
coordinate is null the validator passes, so a missing value keeps `@NotNull`'s own words.

The handler now imports `tenant.NotAtZeroZero`. That is the same kind of knowledge the handler
already holds about the phone rule. The request record still imports nothing from `error`.

## The exact JSON answer for 0,0

Asserted character for character in `refusesZeroZero`:

```json
{"code":"KMS-400002","message":"Those coordinates don't look right.","action":"Choose the temple's place, or type its real latitude and longitude.","fieldErrors":[{"field":"latitude","message":"That puts the temple at 0, 0. Choose its real place."}]}
```

The status is 400 and `SELECT count(*) FROM tenants` is 0 afterwards.

## The sentence, and why

"That puts the temple at 0, 0. Choose its real place." Ten words, two short sentences, sentence
case, no semicolons. The first sentence says what went wrong in the operator's own terms: the numbers
they sent put the temple somewhere. The second gives the next step. "Its real place" matches the next
step in KMS-400002 ("Choose the temple's place…"), so the banner and the box say the same thing. It
avoids "coordinates" because the banner already says that, and avoids "Atlantic", because
this text shows under the box and a word about geography is a detail nobody needs.

`FieldErrorMessageTest` walks field annotations only, so it does not check this message (it sits on
the class). It was held to that test's rules by hand anyway: capital, full stop, no jargon, no banned
tone.

## Latitude only, not both fields

Only latitude gets an entry. The refusal is about the pair, so putting the same sentence under both
boxes would say one thing twice. Latitude comes first on the form, so it is what a person reads first. The test checks the
whole `fieldErrors` map, so a second copy under longitude would fail it.

## When 0,0 comes with other errors

The answer is `KMS-400001` with every error listed, the same rule as the phone check. Both narrow codes need
*every* error to be their own kind, so neither can claim a mixed form.

- 0,0 and a blank name: `KMS-400001`, `latitude` with the 0,0 sentence and `name` with "Enter the temple's name.". Tested.
- 0,0 and a malformed phone: `KMS-400001`, not `KMS-400003` and not `KMS-400002`, with `latitude` and `adminPhone` listed. Tested.

A blank or missing coordinate keeps its existing answer, `KMS-400001` with "Enter the temple's
latitude.". Tested three ways, each with longitude 0 beside it: key left out, `null`, and `""`.
Jackson turns `""` into null for a `BigDecimal`, so all three reach `@NotNull`.

## Follow-ups (not done, not in contract)

- Add a temple's screen still sends a blank box as `Number("")`, which is 0. After this, a temple with *both* boxes blank
  gets KMS-400002 and the 0,0 sentence, which is correct but less direct than "Latitude is required". With only one box
  blank, the other real coordinate still slips a 0 through, for example latitude 0 and longitude 77.55 (a real place, so the
  server accepts it). T-174 phase 2 adds `required` to both boxes, which closes that on the client.
  Worth a check after phase 2 lands that a blank box never reaches the server as 0.
- A class-level constraint's message is not walked by `FieldErrorMessageTest`. This is the first custom
  constraint in the tree, so that is one message the test does not check. Widening the walk
  is a change to that test, which was run-only here.
- Not smoke-tested by hand on a running app. There is no UI change, and the screen reading above is from code only.
