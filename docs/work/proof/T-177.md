## The table

`whatsapp_template_wording_seen (template_name, fingerprint, first_seen_at)`, primary key `(template_name, fingerprint)`, `first_seen_at DEFAULT now()`.

- **The name.** Each row is one wording of one template, and when a running app first saw it. "Versions" would suggest someone authored and numbered releases. "History" would suggest a log of edits. "Created" is the word the screen must not use. "Seen" is the word the screen's label uses.
- **Not temple data.** No `tenant_id`, so no RLS and no policy. The wording is the app's own and the same for every temple. The migration comment says so, beside V9 and V66. It also explains why there's no identity policy either: the only writer runs at start-up, with no request and no identity.
- **Append-only.** `SELECT make_append_only('whatsapp_template_wording_seen');`. A first-seen time is never edited. The default privileges from V1 grant `kms_app` UPDATE and DELETE, so without this line both would succeed, which control 2 shows.
- **Checks:** the name isn't empty, and the fingerprint starts `sha256:`.
- **Time on the database clock,** so the api and the worker write on one clock.

## The recorder, and why it cannot race

`TemplateWordingRecorder` is an `ApplicationRunner`, so it runs at every start of the api and the worker. It makes one statement:

```sql
INSERT INTO whatsapp_template_wording_seen (template_name, fingerprint)
SELECT seen.name, seen.fingerprint
FROM unnest(?::text[], ?::text[]) AS seen(name, fingerprint)
ORDER BY seen.name
ON CONFLICT (template_name, fingerprint) DO NOTHING
```

- **No read before the write.** The primary key decides inside the one statement. A second process whose insert meets the first one's uncommitted row waits, then inserts nothing and succeeds.
- **Name order,** so two releases running side by side during a rolling deploy can't deadlock on each other's rows.
- **Fingerprint** is `NotificationTemplate.whatsappFingerprint(LANGUAGE)`. `LANGUAGE` is taken from `WhatsAppTemplateComparison.TEMPLATE_LANGUAGE`. A test checks it equals `TenantWhatsAppSettingsService`'s private `"en"`, so it can't drift from what Save and Reload fingerprint.
- **A failure is logged at WARN, and start-up carries on.** It returns false; it never throws. This only dates an operator's screen. Nothing sends, bills or guards anything based on it, so failing the api over it would turn a missing date into an outage for every temple.

**One thing to know about "earliest time kept".** A later start never moves a time; tested. When two starts race within the same few milliseconds, the row keeps the time of whichever insert reached the table first. Keeping the other one's time would mean an UPDATE, which append-only forbids. The concurrent test asserts one row per wording, both starts succeeding, and every time falling inside that start's window.

## The dates

Per template name, as briefed:
- `wordingFirstSeenAt`: earliest first-seen time of any fingerprint recorded for the name.
- `wordingLastChangedAt`: first-seen time of the current fingerprint, if more than one fingerprint is recorded for the name; otherwise null.
- `trackingSince`: earliest first-seen time in the table.

**One case the brief's definitions don't cover. I filled it; I did not change the definitions.** If the wording running now was never recorded, both dates come back null, so the screen says "Not recorded" twice. That happens only when this process's start-up write failed. Taken literally, the definitions would give a first-seen date and a null change. The screen would then say "Not changed since tracking began" about a wording nobody recorded, which would be false. It's one `if` in `WhatsAppTemplateCatalogue.build`, easy to reverse. Pinned by the `leave_revoked` case in `WhatsAppTemplateCatalogueIT`.

## Acceptance criteria

- **Recorder, concurrent:** "two processes starting at once…", shown by control 1 to be deterministic. "A later start with unchanged wording adds nothing and keeps the earlier time." "A changed wording for one template adds exactly one row, and the catalogue then shows when it changed." All on two raw `kms_app` connections inside the shared context. No extra Spring context and no `@Import`. The catalogue IT reuses OpsIT's exact configuration, so it shares OpsIT's cached context.
- **Not temple data, as `kms_app`:** it inserts and selects; UPDATE and DELETE are refused with PostgreSQL's "it is append-only" (control 2); no `tenant_id`; no RLS. The test asserts `current_user` is `kms_app`.
- **Endpoint:** an operator gets 200 with every template in enum order, body, examples and usedBy equal to the enum, and dates as defined across five cases: changed, changed where the older wording is the earliest row, unchanged, nothing recorded, current not recorded. An empty table returns null dates. A Temple Admin gets 403. Reads no temple table: shown above.
- **Screen:** the operator sees every template's name, category and language as words, body, examples, used-by, both labels, formatted dates, and the tracking line with the `templeDay` date. Nulls are words, no "created" anywhere, and a Temple Admin sees "Not your page". Control 3 shows the tracking-line assertion is live.
- **Recorder runs at start-up:** the Spring bean is an `ApplicationRunner`, and running it writes the current wordings through the app's own connection. A write on a closed connection returns false and `run()` does not throw.
