## What was built

- "Fixed when the order was sent" removed.
- The "What was ordered" table and the per-delivery "Deliveries received" tables replaced by one
  table, "Items": Item · Ordered · Delivered · Rejected on delivery · Returned · (actions).
  Delivered = kept, summed; Rejected on delivery = rejected, summed; Returned = returnedQty,
  summed. Nothing rejected/returned shows "—", as the mock does.
- Each item with at least one delivery has a row under it, spanning the table, holding the shared
  `DeliveryHistory` ("▸ N deliveries"). Parts are built from the receipts (date = the receipt
  line's `receivedDate`, or the receipt's `receivedAt` as a temple-zone date), and `completedOn` is
  the date of the part that brought the kept total up to the ordered amount.
- "Rejected at the gate" is gone from the page.
- The old "Receive delivery" button and the whole record-a-delivery form, including "Price paid",
  removed. The page has no recording path and does not call `receiveDelivery`.
- Link "Record a delivery on the Deliveries screen →" to `/deliveries?order=<po id>`, beside the
  "Items" heading, for Temple Admin and Kitchen Manager only, and only on a Sent / Partially
  received order with at least one catalogue line.
- A pack line's Ordered reads "4 × Bag (25 Kg)" with "100 Kg" under it. Quantities go through
  `quantity()` (1500 gm reads "1.5 Kg").
- "Return to vendor" kept: one per item row (conductor's ruling), asking which delivery when there
  is more than one; the quantity box carries `max` = that delivery's received − returned.
- "These arrived", draft editing, send, WhatsApp, close and cancel unchanged.

## Judgement calls

1. **History in a spanning row under the item, not inside the Item cell.** My first build put it
   in the Item cell (as the Deliveries mock does). Measured at 1280 with histories open: lines
   wrapped to 3 in a 305px column while four figure columns stood empty beside them (rows 207–259px
   tall). Mock E draws history as spanning rows, so I followed it. After: every history line is one
   line (878px wide) at 1280.
2. **The link sits right of the "Items" heading**, where mock E has "Record the whole delivery".
3. **The link is also hidden on a Draft/Received/Closed/Cancelled order and on an order of only
   one-off lines**: there is nothing the Deliveries screen could record there.
4. **Role check, not permission**: the browser knows the role, not the policy. Admin + Manager
   match the nav item's roles for /deliveries.
5. **Card holds the table edge to edge with an `overflow-x-auto` wrapper**, the planner's pattern.
   Heading padded `px-6 lg:px-5` so "Items" lines up with the item names (21px = 21px at 1280,
   25px = 25px at 390; before the fix 25 vs 21 at 1280).
6. **Status chip: now a neutral "Part delivered"** (conductor's ruling, 2026-09-19: the mock wins
   where the document is silent, and one label in every view). I first left it as "Partially
   received" in amber and flagged it; the conductor then widened the contract. Changed once in
   `po-status.tsx`, so the order page, the orders list (label and filter option) and the invoice's
   order picker all read "Part delivered". No other file uses the old words (grep of app,
   components, lib, __tests__). Tested: new test in `po-merged-table` (chip text, `bg-sunken`, no
   warning class, no "partially received" on the page) and `invoice-order-picker` now expects
   "PO-2026-0043 · Part delivered".
7. **Return button's accessible name** is "Return to vendor: <item>" (visible text + sr-only item),
   so a screen reader's button list tells the rows apart.
8. **Parts are computed on this page from the receipts**, not from the Deliveries endpoint: that one
   needs RECEIVE_DELIVERIES and Kitchen Staff can open this page without it.
