## Why two boxes were named and six were not

The markup was the difference, not the words.

- Title, Date, Start time, End time, Location and Description were each wrapped in a `<label>`, with
  the words in a `<span>` inside it and no `for`/`id`.
- "Reminder hours before" comes from `HintedField`: a separate `<label htmlFor={id}>` holding its
  words directly, beside the box and not around it.

A spec-following browser names a box from a label wrapped around it. But the accessibility tree the
browser test was driven through (the Chrome extension's `read_page`) does not. I checked this in
Chrome on a scratch page (example.com with the DOM replaced), reading the tree for each shape:

```
 label [ref_2]
  generic "WrapText" [ref_3]
  textbox [ref_4]                          <- wrapped, no for: unnamed
 label [ref_8]
  generic "WrapNumber" [ref_9]
  textbox [ref_10] type="number"           <- wrapped number: unnamed too
 label [ref_14]
  generic "ForText" [ref_15]
  textbox [ref_16]                         <- wrapped WITH for/id: still unnamed
 label [ref_17]
  generic "ForTime" [ref_18]
  textbox [ref_19] type="time"             <- same
 label "SeparateText" [ref_23]
 textbox "SeparateText" [ref_24]           <- separate label with for: named
```

Then the shape I built, in the same tab:

```
 label "Title" [ref_26]
 textbox "Title" [ref_27]
 label "Date" [ref_28]
 textbox "Date" [ref_29] type="date"
 generic "The day of the meal. It cannot be changed here." [ref_30]
 label "Start time" [ref_31]
 textbox "Start time" [ref_32] type="time"
 label "Volunteers requested" [ref_33]
 textbox "Volunteers requested" [ref_34] type="number"
 label "Reminder hours before" [ref_35]
 button "More about Reminder hours before" [ref_36] type="button"
 textbox "Reminder hours before" [ref_37]
```

So adding `htmlFor` to the wrapping labels, as the brief's wording allowed, would have left the form
reading exactly as the defect describes. I tried that first and threw it away. Every field is now a
`<div>` carrying the old label's classes, with a separate `<label htmlFor>` holding the words and an
`<input id>` beside it. That is the same shape as the field that already worked.

One thing I could not reconcile: the defect lists "Volunteers requested" as named, but it was wrapped
exactly like Title, and a wrapped number box was unnamed in my Chrome check. I could not re-read the
live page (Chrome's debugging port 9222 was not listening and the staging page needs a sign-in), so
either the defect note is off on that one field or something on the live page differs. It is fixed
either way.

Ids come from `useId`, one base per form, so two forms on one page cannot collide. The planner's
read-only date carries the same id scheme, and its "cannot be changed here" line's id is now
`useId`-based too (it was the fixed string `shift-date-fixed`, which two forms would have shared).
For a meal shift on the edit page there is no date box, so "Date" stays a plain `<span>`, not a label
pointing at nothing.

## Acceptance criteria

1. **New test covers all three uses.** `shift-form-labels.test.tsx` renders Post a shift (blank),
   editing a plain shift (filled in, overnight times) and the planner's fixed date. Title, Location,
   Description and Reminder hours before are found with `getByRole("textbox", { name })`, and
   Volunteers requested with `getByRole("spinbutton", { name })`. **One deviation:** Date, Start time
   and End time cannot be found by role in jsdom, because a date box and a time box have no ARIA role
   in the mapping testing-library uses (aria-query 5.3.0 lists roles for `number` → spinbutton but
   none for `date`/`time`). For those three the box is found by its `name` attribute and checked with
   `toHaveAccessibleName`, which is the same name computation `getByRole` runs. Every box is also
   checked to have an id, exactly one `<label for>` pointing at it with the label's words, and a label
   that does not wrap it. The planner's date is checked read-only, named "Date", and described by
   "The day of the meal. It cannot be changed here." (`toHaveAccessibleDescription`). Two forms
   rendered together give no duplicate ids, and each form's boxes are still named inside that form.
   A fifth case covers a meal shift on the edit page: no date box, and no label pointing at nothing.
2. **Negative control.** Shown above: removing Title's `htmlFor`/`id` fails all 5 tests on the role
   query, and the file was restored identical. The second control shows the pre-fix form fails too.
3. **Full checks.** Green on the third run: tsc silent, 139 files and 1871 tests passed, eslint silent, next build exit 0. The first run failed on T-215's files mid-edit. The second failed on mine (the design-system scan) and was fixed.
4. **Hand smoke test:** I did not drive the real Post a shift, Edit a shift or planner screens. I had
   no signed-in session I could use and no local app running. The Chrome check above ran on a scratch
   page with the same markup, not on the app.

## Not done / needs Rajeev

- **The duplicate-id test leaves out the `<form>`'s own id.** Every `ShiftFields` form carries the
  fixed id `shift-form`, which the page's header button submits through (`form="shift-form"`).
  Changing that means touching the pages and `ShiftLayer.tsx`, which is outside this task and belongs
  to T-215 this wave. Two shift forms on one page would still share that one id. Today the planner
  layer and the Volunteer shifts pages are never on screen together, so it does not bite.
- **The markup changed shape**, which the brief did not spell out. The wording, classes and grid
  columns are the same, so the page should look identical, but I have not compared it on screen. One
  small behaviour change: the old wrapping label made the 4px gap between the words and the box
  clickable, and now only the words and the box are. The reason is above: `htmlFor` on the wrapping
  label did not fix what the browser test reads.
- **One real naming fix came with it.** A wrapping label's name is all of its text, so End time was
  named "End time Ends the next day — this shift runs through midnight" whenever the overnight line
  showed. It is now just "End time", and the line stays visible under the box.
- Could not confirm the "Volunteers requested was already named" observation (see above).

## After-UAT lines

- Many other forms use the same wrapped-label shape (the `closest("label")` assertions in 20-odd test files show it), so they will read as unnamed in the same tool; worth one sweep once the shape here is accepted.
- The End time sentences ("Ends the next day", the same-time refusal) are not tied to the box with `aria-describedby`, so a screen reader on the box does not hear them.
- The planner layer's date box and the edit page's meal date differ in shape (a read-only box and plain words); fine as ruled, noting only that tests of one do not cover the other.
