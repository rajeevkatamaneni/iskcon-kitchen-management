## The migration, and why columns

Three columns on `tenant_settings`, which has had RLS since V36:
- `whatsapp_template_fingerprints JSONB NOT NULL DEFAULT '{}'`, with a CHECK that it is an object;
- `whatsapp_templates_sent_waba_id TEXT` and `whatsapp_templates_sent_phone_number_id TEXT`.

Columns, not a table, for V128's reason: always read and written whole, for one temple, next to the other WhatsApp facts, twenty entries, never queried per template. A table would add a policy and a tenant loop for nothing. DDL only, no backfill, so nothing runs into RLS. The webhook-lookup policy can now also read these columns; they hold hashes of wording that is the same for every temple, and two ids already on the row.

## The fingerprint

`NotificationTemplate.whatsappFingerprint("en")` = `"sha256:" + hex(SHA-256(name ␟ category ␟ language ␟ body))`, joined with U+001F (written as the `\u001F` escape). Example values are left out: they only go to Meta's reviewer, and a better sample must not make every temple's screen say "changed".

Stored per template name:
- `"sha256:…"`: Meta holds exactly this wording on the recorded account.
- `null`: the app sent it last time but we don't know what Meta holds (refused, not reached, or already held and not compared).
- no key: the app didn't have this template at the last send, so it is new.

## templatesPending

- `refused`: stored entries of kind REFUSED or NOT_REACHED, as the contract says. HELD_UNDER_ANOTHER_CATEGORY is not counted, because Reload can't move a category and the button would stay primary forever.
- `changed`: templates not already counted in `refused` whose stored fingerprint differs, or which have no key on a temple that has fingerprints. The two numbers never count one template twice.
- `accountChanged`: recorded account differs from the saved WABA id or phone number id. Never recorded reads as false.

## The pre-V129 decision

**An empty fingerprint record means unknown, and nothing is counted as changed.** A `null` entry is also unknown. South Bengaluru after deploy reads `changed 0, refused 0, accountChanged false`, not "20" or "6". Its account reads as not changed too, since there's nothing recorded to differ from.

The first Reload fixes it: every template comes back "already held", its fingerprint isn't known, so Meta is asked what it holds; wording that matches is recorded without an edit. Pinned by "a temple that sent before V129 is claimed to have nothing changed…" (20 lookups, 0 edits, 20 fingerprints recorded, nothing waiting after).

Cost of this choice: on such a temple, a template added in a later release also shows as 0 until its first Reload, because "new" can't be told from "never recorded".

## Finding a template id, and edit versus new name

**Finding the id:** `GET /{WABA_ID}/message_templates?name=<name>&fields=id,name,language,status,category,components`. Meta's Graph API reference lists `name` as a filter and the answer as a `data` array of templates with these fields: https://developers.facebook.com/docs/graph-api/reference/whats-app-business-account/message_templates/ . The management guide shows the same listing with `fields=`: https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-management . Meta doesn't say whether `name` matches whole names, so the client keeps only the entry whose name and language are exactly ours. The test fake matches part of a name on purpose, and the test asserts that only `id-shift_reminder` is edited, never `volunteer_shift_reminder`.

**Chosen: Meta's edit route**, `POST /{TEMPLATE_ID}` with the new BODY component and no category. Why not a new name: the name lives in code and is the same for every temple. Renaming is a release-wide change, so every temple's messages would fall back to SMS until each temple's Meta approved the new name, and a temple that hadn't pressed Reload would be sending a name its account doesn't hold. An edit changes one temple's copy under the name the code already sends, and Meta says it "automatically re-approves the template unless it fails template review". Renaming is still the tool for what an edit can't do, such as an approved template's category.

**Reload, per template:** register it as today (T-168's classifier unchanged). Then:
- Created: record the fingerprint.
- Refused or not reached: `null`, with an entry.
- Already held, or held under another category: if the same account last recorded this exact fingerprint, trust it. Otherwise look it up:
  - body matches ours: record it;
  - status PENDING or IN_APPEAL: no edit attempted (Meta: "Only templates with an APPROVED, REJECTED, or PAUSED status can be edited");
  - any other status outside those three: no edit;
  - else edit. Meta's documented 2388039 "Message template status can't be changed" covers both "still in review" and "daily limit on the number of edits" (https://developers.facebook.com/documentation/business-messaging/whatsapp/support/error-codes). On an APPROVED template it can only be the limit; on a status Meta didn't name, the reason gives both causes.

Every template is registered on every Reload, not only the counted ones, so a template deleted in Meta's manager gets recreated and "last sent on" is true after a press. The date is stamped by T-159's rule (Meta holds at least one). The list is replaced whole, as T-168 does.

## What "first connection" means

Save sends templates only when the row has **no recorded sent account and no `templates_submitted_at`**. The account alone would make every pre-V129 temple "first" again. The date alone would make a temple whose first Save was all refused "first" again, forever. A pre-V129 temple has the date, so its Save sends nothing. A changed account is saved, nothing is sent, and the view reports `accountChanged` until Reload.

## Stored reasons added or changed

New (all kind REFUSED unless noted):
- Lookup failed or no match (kind NOT_REACHED): "Meta did not say which wording it holds for this message. Press Reload to try again."
- In review: "Meta is still reviewing this message, so its new wording has to wait. Press Reload again once the review is over."
- Edit limit (APPROVED + 2388039): "Meta allows a message to be reworded only once a day and ten times a month. Press Reload again tomorrow."
- 2388039, status not named: "Meta is not taking new wording for this message yet, because of a review or a recent change. Press Reload again tomorrow."
- Status can't be edited (e.g. DISABLED): "Meta holds this message in a state that cannot be reworded. Report it with the message name shown here."
- Edit refused for a rule: T-159's `plainReason`, unchanged.

**Changed, a deviation I'm flagging:** T-159's two reasons said "Press Save to try again". After this task Save sends nothing, so that advice would be false. Both now say "Press Reload". T-168's classifier, kinds, date rule and typed timestamp read are unchanged. Entries already stored on staging keep the old text until the next Reload replaces them.

## Known limits

- **Synchronous.** Reload is 20 registrations plus a lookup and maybe an edit for each template not known to be current, in one request and one transaction. That's about Save's 34 to 60 seconds for a fingerprinted temple, and more for South Bengaluru's first Reload (20 extra lookups). Not built around, by instruction.
- **Body comparison assumes Meta returns the body verbatim** (compared after trimming outer whitespace). If Meta normalises text, the first Reload on a temple would edit templates that didn't need it, and use up that day's one edit each. Nobody has checked this against real Meta.
- A pre-V129 temple counts a template added in a later release as 0 until its first Reload.
- Review status isn't tracked. A template Meta rejected after review, whose wording matches ours, is recorded as current, as it was never surfaced before either.
- A template both held under another category and failing an edit shows only the edit problem until it's resolved.
- No hand smoke test: backend only, and the screen is T-169b.

## Follow-ups for T-169b

- Make `refusedTemplates` and `templatesPending` required in `api.ts`. The JSON always carries both.
- `changed` and `refused` never overlap, so the button can add them. HELD entries are in `refusedTemplates` but not in `refused`; show them as a note, not as waiting.
- Reload can take a minute or more; the button needs a working state and must not double-submit.
- Reload on an unconnected temple answers `KMS-400001` (VALIDATION_FAILED) with `field: phoneNumberId`, the same as Test. Hide the button when not connected.
- Button date: `templatesSubmittedAt`.
- Before pressing Reload on staging, have someone confirm with one real `GET …/message_templates?name=shift_reminder` that Meta returns the body text exactly as registered (see known limits).
