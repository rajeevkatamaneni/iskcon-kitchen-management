## What was built

**Backend.** `CORRECT_RECORDED_ATTENDANCE` added to `Permission.java` directly beneath
`MANAGE_VOLUNTEER_SHIFTS`, with the why-comment the task asked for: the person running the shift is
the one who actually knows who turned up so they must be able to fix a mark; a cook should not be
able to change a record about a colleague they work alongside; and it starts narrow because widening
a permission later is one line in a diff while narrowing one after temples have built a habit around
it is a conversation with every one of them. Granted to `TEMPLE_ADMIN` and `KITCHEN_MANAGER` only,
each with its own reason at the grant site, and a comment in the `KITCHEN_STAFF` block saying what is
*absent* there and why — the file is meant to read as a document, and an absence with no note is
indistinguishable from an oversight.

`PUT /api/v1/shifts/{id}/attendance/{userId}` now carries
`@PreAuthorize("hasAuthority('CORRECT_RECORDED_ATTENDANCE')")`. **`MANAGE_VOLUNTEER_SHIFTS` is
untouched** — same three role blocks, same members — and `POST /{id}/attendance` (the marking) is
still on it, along with every other endpoint in the controller.

**Frontend — what I found, since the brief asked.** The roster screen is
`frontend/app/volunteers/[id]/page.tsx`. It uses `RequireRole` only at the page level, with
`roles={["TEMPLE_ADMIN", "KITCHEN_MANAGER", "KITCHEN_STAFF"]}` — that guards *the screen*, and it is
correct as it stands: a cook still marks the roster, so they must reach the page. The correction
buttons themselves were gated on **no role check at all**: a single `canCorrectAttendance` constant
computed purely from state (`attendanceRecordedAt !== null && shift.status === "OPEN" &&
shiftHasStarted`). So after the backend change every Kitchen Staff reader would have been shown
"Mark as came" / "Mark as did not come" buttons that 403 on click — exactly the failure the brief
called out.

Fixed the way `MealServices.tsx` does it for `CORRECT_RECORDED_MEAL` — the same precedent, and the
same caveat written down beside it: there is no permission list on the client (`appUser` carries a
role and nothing finer), so this reads the two roles the grant was given to, and if the grant widens
this line must widen with it. The state condition is now split from the permission condition
(`attendanceIsCorrectable` vs `mayCorrectAttendance`) so the copy under the table can tell a cook
that a correction is possible and who makes it:

- marking hint, cook: "…the whole roster is saved in one go, and **a kitchen manager can change a
  mark afterwards**." (it used to promise "*you* can change a mark afterwards", which stopped being
  true for them);
- after recording, cook: "Attendance recorded … **Ask a kitchen manager if a mark is wrong.**"
- after recording, admin/manager: unchanged — "Change any mark that is wrong."

**Role tests found by grep.** Backend: `RolePermissionsTest.java` (the parameterised "the
authorisation policy is exactly as documented" table) and `AccessControlEnforcementIT.java` (which
turns out to test the mechanism on a stub controller, not this endpoint — it needed no change and was
run anyway). Frontend: `role-refusals.test.tsx` — it covers four *other* screens from T-002 and has
no roster case; it needed no change, and was run to prove it still passes. The roster's own case went
into `shift-attendance.test.tsx`, which is where the screen's other role-shaped assertions live.
