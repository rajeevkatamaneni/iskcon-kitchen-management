Rajeev's ruling of 2026-09-10, built as he described it: *"They should be two different things. Maybe
a check box for equipment that don't need service like a ladder. When checked, the Service interval
box is cleared out and uneditable."*

servicing, every six months" unrepresentable, a fifth `ServiceStatus` value `NOT_SERVICED`, and a

**This is also T-089's second tier, finally in the schema.** T-089 shipped with no migration, so the
flag its ruling described — *"owned, not serviced"* — has never existed. This is it.

## The four things the brief asked me to get right

### 1. The two nulls are distinguishable in the database, and I took the CHECK

**I read both precedents and this one is V118's kind, not T-129's.** The reasoning is written into
V122's header so the next reader finds it beside the code rather than in a proof file:

- V118's `purchase_orders_abandoned_is_a_cancellation` is a **coherence rule about a row's state** —
  two columns written by one `UPDATE`, and no product decision could make the forbidden pairing mean
  anything.
- T-129 refused its constraint because that rule is a **policy about what a person may assert**,
  chosen from three options on one day, with the two columns written minutes or days apart by
  different people. Its proof: *"Policy that may be revisited belongs where reverting it costs an
  edit to one method."*

Mine is the first kind on every count. *"This never needs servicing, and it needs servicing every six
months"* is not a policy anybody could revisit into meaning something — it is a contradiction, in any
product, for ever. Both columns are written by the same single `UPDATE` in `setServiceSchedule`, so
there is no legitimate half-applied intermediate state. And `derive` reads the flag **first**, so a
row carrying both would hold an interval that nothing on earth ever reads — a stored fact with no
reader, which is how a register starts lying.

```sql
ALTER TABLE equipment_items
    ADD CONSTRAINT equipment_never_serviced_has_no_interval
    CHECK (never_needs_servicing = FALSE OR service_interval_days IS NULL);
```

Proved by behaviour, not by grepping the SQL: `theDatabaseRefusesThePairingToo` opens **two real
unprivileged connections as the application role** and tries the pairing by `UPDATE` and by `INSERT`.
Both are refused by name.

**Two smaller decisions inside that one.** The column is `NOT NULL DEFAULT FALSE` and not a nullable
boolean — the ledger's design note suggested nullable, and a nullable boolean is three-valued logic
standing in for exactly the ambiguity this task exists to remove. And the CHECK names only
`service_interval_days`, not the unit, because `equipment_service_interval_paired` (V87) already ties
the unit to the day count; a second statement of a rule that is already true is a rule that can
drift.

### 2. Existing rows are left unflagged, and the migration says why

V122 flags nothing and touches no rows. Every ladder in the database is currently null-interval and
unflagged, and so is every unscheduled boiler; **nothing stored anywhere can tell them apart**, and a
migration that matched on the name would write a permanent claim about the temple's own equipment on
the strength of a string. `DEFAULT FALSE` leaves them all saying *"nobody has said"*, which is the
true statement about all of them.

Asserted, not just written: `v122FlagsNothing` inserts a row the way an existing row exists — through
the API and directly through the unprivileged role — and asserts `bool_and(never_needs_servicing =
false)` over the whole table.

**No tenant loop, and that is deliberate.** `equipment_items` carries `enable_tenant_rls()` (V16) and
migrations run unprivileged, so any `UPDATE` here would match nothing through the policy's `NULLIF`
and report success. This one touches no rows; `ADD COLUMN` and `ADD CONSTRAINT` are DDL and run as the
table owner, so `ADD CONSTRAINT` genuinely validates every tenant's rows rather than silently
validating none. Same shape as V118, and `TenantLoopMigrationIT` was run against it (green).

### 3. What the screen says when the box is ticked

I read the neighbouring strings first — *"Not scheduled"*, *"Nobody has recorded a service against
this yet"*, *"Nobody has said where it lives"*, *"This order was never sent, so there is nothing to
hold the vendor to"*. The voice is a plain fact plus what it means for you. So:

- **The box:** *This never needs servicing*, with *"A ladder, a trestle table, a stack of stools — the
  temple owns it and nobody will ever service it. Leave it un-ticked for anything that just has not
  been scheduled yet."* The second sentence is doing real work: it is what stops the box being ticked

- **Under the disabled interval:** *This equipment does not need servicing, so there is no interval
  to set.*
- **In the record above the form:** *Serviced every* reads **"It does not need servicing"** instead of
  an em-dash, and *Next service* reads **"Not needed"** instead of *Not scheduled*.
- **In the list's Next service column:** **"Does not need servicing"**.

The box is **disabled and still visible**, not removed, because the ruling says *"cleared out and
uneditable"* and because a field that vanishes makes the reader wonder what they broke. The count is
cleared in the form state as well as in what is sent — a number sitting greyed out in a dead field
reads as a value still in force.

## Two judgement calls worth naming

**I took the ledger's `NOT_SERVICED` status value rather than reading the boolean alone.** The
DISPATCH row itself warns why not to: *"Adding a state to a derived enum is exactly that shape"* — the
project's standing lesson that a count goes on compiling when a row's meaning changes. I checked every
reader before deciding (the table above) and took it anyway, because the boolean alone leaves the next
person to write a "which machines has nobody scheduled?" list needing to remember `&&
!neverNeedsServicing`, and forgetting it puts sixty stools back on the chase list. The tier is the
distinction; putting it only in a sidecar boolean is the same mistake one layer up from the one being
fixed. `tsc` confirms nothing in the frontend exhaustively maps the union.

**The flag is asked before `SCRAPPED` in `derive`.** Both are invisible to every warning count either
way, so this is about words. A scrapped ladder reading *"Not scheduled"* is an invitation to go and
schedule a thing that has been thrown away, and the flag is a statement about what the thing **is**
that stays true after it is scrapped. `theFlagOutranksScrapping` pins it. A scrapped machine that is
**not** flagged reads `NOT_SCHEDULED` exactly as before — no existing behaviour moved.

## Acceptance criteria

**1. A flag on the equipment item meaning "this never needs servicing".** Done —
`equipment_items.never_needs_servicing`, `NOT NULL DEFAULT FALSE`, V122.
`theDistinctionIsStoredAndNotDerived` reads it straight off the table for a flagged and an unflagged
row, so a view that computed the answer from a name would pass every other assertion and fail this one.

**2. On the screen it is a tick box; ticked, the interval is cleared and not editable.** Done.
`clears the interval and makes it uneditable when ticked, and says why` asserts all three halves —
value emptied, `disabled` true on both controls, and the sentence present — and goes red in arm C.
`comes back ticked on a thing already marked` proves the state survives a reload.

**3. Unticked, the interval works as it does now.** Done. `still says not scheduled for a machine
nobody has got round to` and `gives the interval back when the box is un-ticked` on the screen;
`theFlagCanBeTakenBack` end-to-end, which un-ticks and then schedules properly; and every pre-existing
servicing test (`EquipmentServicingIT`, 81 total green) is unedited except for the new nested class.

**4. The two nulls stay distinguishable in the database, not just on the screen.** Done, with a CHECK.
Reasoning above and in V122's header, against both precedents by name.

**5. Existing rows are left unflagged, and the migration says so.** Done, asserted by
`v122FlagsNothing`.

**6. A flagged thing drops out of the servicing views rather than sitting there for ever.** Done.
`aFlaggedThingIsOutOfScope` takes a ladder that is genuinely OVERDUE, flags it, and asserts it is gone
from both list filters **and** that the interval is cleared in the row — not merely ignored. Every
reader is enumerated in the table above.

**7. Nothing reports a flagged item as infinitely overdue.** Done, structurally: the CHECK forbids the
interval and `derive` returns before any arithmetic. `aFlaggedThingIsNeverOverdue` asserts it against
seven-year-old dates.

**8. The audit trail can tell the two acts apart.** Done — `scheduleSnapshot` carries
`neverNeedsServicing` in both before- and after-state, asserted by `theTrailSaysWhichActItWas`. Not in
the brief; added because "the interval was cleared" and "this was declared never to need one" are the
same two facts this whole task exists to separate, one table along.
