**Decisions and deviations from the mock (Rajeev should see these):**

1. **The purchase-order table is two columns, not three.** This was the sanctioned fix, and it was measured. With the mock's layout in the real panel at 1280 the table was 380px wide, and Quantity and Amount took 102 and 98px of it. Their headings and the 20px row inset set those widths, not the figures. That left the item name 148px of text: 3 of 4 names wrapped and rows were 127px tall. Now "50 Kg at ₹132/Kg" is the third line of the item cell, and Amount is the only number column, the same shape as the meal draft. Result: 1 of 4 names wraps (the 36-character rice name, to 2 lines), and the other rows are 100px.
2. **Reject and Confirm stay beside the sentence at 1280.** The mock gave the sentence a 240px basis, which pushed the buttons to their own row. It now has a 160px basis. At 1280 it gets 165px and two lines, with the buttons on the same row. At 375 it would get 77px and six lines, so there it takes the row above and the buttons sit side by side at the trailing edge below it. It also uses `text-wrap: pretty`. The sentence itself comes from the server (`confirmSays`). The mock's "Confirm saves this as a draft order. It is not sent." took three lines with "sent." alone, so the type's comment asks S4 for 45 characters or fewer, for example "Confirm saves a draft order. Nothing is sent."
3. **The empty state offers what the assistant can do today.** The heading is "Ask about stock" and there are two suggestions: the Toor dal stock question and "What is running low?". The mock offered "Plan lunch for Sunday" and "Make a purchase order", but no tool can do either until S4, and a suggestion it cannot do is the first thing somebody would press. The comment says to add them back when S4 lands.
4. **Daily limit placeholder:** "Available again tomorrow", not the mock's "Back at midnight", because the real KMS-400192/400193 text says "tomorrow".
5. **No microphone**, as the mock itself recommended.
6. **The draft card is wired to nothing yet.** No `proposal` shape existed, so I defined `AssistantProposal` / `AssistantProposalLine` in the api.ts section, shaped from the mock's two cards. Without `onConfirm` / `onReject` the buttons are disabled, so they never sit there doing nothing. The api does not emit `proposal` yet, so nobody can see the card. The confirmed state shows only "Saved."; S4 adds the link from its confirm response.
7. **Tool names are put into words:** `get_inventory` shows as "Checking stock…" and then "Checked stock: toor dal". `list_low_stock` shows as "Checking what is running low…". Unknown tools show as "Looking it up…". The tool's own name never reaches the screen. The api sends no "finished" event for a tool, so a lookup line is marked finished when the next event arrives, and "stopped" if the next event is an error or Stop.
8. **The conversation persists** across navigation, because the panel lives in the root layout. It also survives a reload: the conversation id is kept in sessionStorage, keyed by person and temple, and read back with GET on the next open. After a reload only the questions and answers come back, because tool lines and errors are not saved. "New" forgets the id.
9. **Accessibility:** focus goes to the box when the panel opens and back to the button when it closes. Escape closes the panel. The message list is `role="log"` with `aria-busy` while an answer streams. **Not done:** on a phone the full-screen panel does not make the page behind it `inert`, so Tab can reach the covered page.
10. The design-system tests forced three conventions: the shared `Form` in place of `<form>`, `quantity()` in place of a number followed by a bare `unitLabel()`, and a literal ’. The box is named with `aria-label`, because the mock gives it no visible label.
