## Defect found, and deliberately not fixed

### D1 — a refused join leaves an orphan Firebase account, and the retry advice is wrong

**Where:** `frontend/app/register/page.tsx`, `createAccount()` (roughly lines 71–129).

**What happens.** The function creates the Firebase credential first and calls `api.joinTemple`
second. If the join is refused — server down, temple closed to new devotees, any validation the form
did not anticipate — the Firebase account has already been made, and nothing removes it, signs out
of it, or remembers that it exists. The `catch` reports the join failure honestly (correct) and
resets `busy` so the button is pressable again (also correct).

The second press then calls `createUserWithEmailAndPassword` with the same email, which Firebase
refuses with `auth/email-already-in-use`, and the screen answers:

> There is already an account with that email. Sign in instead.

That advice is wrong for this person. They have a Firebase identity and **no membership of any
temple**, so signing in is not the thing that helps. The registration flow itself is a dead end from
that point: every subsequent press gives the same sentence, and the join is never retried.

**Severity, honestly stated.** It is recoverable, but only by accident: signing in as instructed
gives `whoami` a 401, which `RequireRole` turns into a redirect to `/choose-temple`, where they can
finish joining. Nobody tells them that, and the sentence on screen points the other way. The same
shape exists for the Google and phone branches — the credential is made, the join fails, and the
person is left signed in with no membership — though those two recover more gracefully on a reload
because the identity already exists.

**How it was found.** Writing the characterisation test for the "credential made, join refused"
path. It is now asserted as-is in `register.test.tsx` →
`"leaves a Firebase account behind that the second attempt cannot get past"`, with a comment block
saying explicitly that it documents a defect rather than endorsing it. **Whoever fixes this must
come to that test and change what it says** — which is the point of writing it that way.

**Product code was not touched.** The fix is a different task in a different contract, and it is not
obvious which shape is wanted (compensating delete of the Firebase user; remembering the credential
across attempts and skipping straight to the join; or reordering so the temple is reserved before
the credential exists). That is a decision for Rajeev, not for a test-writing task.

## Observations — smaller, not raised as defects

Not defects, and not fixed; noted here because the tests walked past them.

1. **`app/library`** — the take-down is a bare `×` with no confirmation step. One click permanently
   removes a recipe from the **shared, cross-tenant** library, which is the most consequential
   destructive action in the app that has no "are you sure". The `aria-label` is good
   (`Take <name> out of the library`); the lack of a confirm is a design question worth putting to
   Rajeev rather than a bug.
2. **`app/choose-temple`** — a user whose `status` is already `signed-in` renders the full "Which
   temple do you serve at?" form for one paint before the effect redirects them to `/`. The guard is
   `status === "loading" || !user`, and a signed-in user satisfies neither. Cosmetic, and only
   reachable by navigating to the URL directly.
3. **`app/unsubscribe`** — with no `?token=` in the URL the page sends `describeUnsubscribe("")` and
   lets the server judge it. That is defensible (the server is the authority) and is asserted as the
   shipped behaviour, but it is a wasted round trip for a case the page can see for itself.
4. **The docket's superlative (P9) is confirmed wrong**, which the task already said: `app/library`,
   `app/choose-temple`, `app/register` and `app/c/[token]` had no tests either. `app/register` was
   the nearest miss — `google-account-chooser.test.tsx` renders it, but for one assertion about one
   OAuth parameter on one of its three methods; the form and everything after "Create my account"
   were uncovered.
