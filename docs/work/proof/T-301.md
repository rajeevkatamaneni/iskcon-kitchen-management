## The mechanism, and why

A Spring MVC `HandlerInterceptor` does the work, registered once for every path. `preHandle` runs
after the request has been matched to its controller method and before Spring builds that method's
arguments. Building the arguments is when Spring parses the JSON, converts path ids and runs
`@Valid`. So `preHandle` is the one point that knows which permission to check and has not yet read
the body.

- **Same check as method security.** The interceptor reads the method's own `@PreAuthorize`, or the
  class's if the method has none. It evaluates that with a `MethodSecurityExpressionHandler`: the
  app's own if it ever declares one, otherwise a `DefaultMethodSecurityExpressionHandler` built the
  same way `@EnableMethodSecurity` builds its own. There is no endpoint list or permission list in
  this code, so every endpoint is covered, including ones added later.
- **Expressions that read a method argument are skipped.** Any expression containing `#` (such as
  `#id`) is left to method security. No expression in the product does this today; every one is a
  plain authority test.
- **Method security stays on**, so the question is asked twice. Refusals go through the existing
  `AccessDeniedException` → `GlobalExceptionHandler` path, so the body is the same 403 KMS-400021
  with the same log line.
- **401 is unchanged.** The filter chain answers a caller with no sign-in before any controller is
  matched.

**Rejected alternatives:**
- Editing each controller (a raw String body validated by hand after the check). That has to be
  remembered for every new endpoint, and some future endpoint will forget.
- A servlet filter. It runs before Spring MVC has picked a controller, so it would need its own copy
  of the permission map.

**One side effect:** this applies app-wide, not only to procurement. Every `@PreAuthorize` endpoint
now refuses an unpermitted person before reading their body, path ids or query parameters. Before,
an unpermitted person could get 400 or 404 for a malformed request. The fix reveals nothing
to them that the old order didn't. None of the 2,098 tests I ran relied on the old order.

## Endpoints covered

These are all the write endpoints of the procurement controllers, plus the recipe import pair.
`everyProcurementWriteEndpointIsListed` compares this list against the app's own request mappings,
and fails if any controller below gains a write endpoint the list doesn't name.

- Purchase orders: POST `/purchase-orders`; PUT `/{id}`; POST `/{id}/send`, `/close`, `/cancel`, `/arrivals`, `/whatsapp`
- Shopping list: POST `/shopping-list`; PATCH `/shopping-list/{ingredientId}`
- Deliveries/receipts/returns: POST `/deliveries`; POST `/purchase-orders/{poId}/receipts`; POST `/goods-receipts/{receiptId}/returns`
- Invoices: POST `/vendor-invoices`, `/{id}/void`, `/{id}/credit`
- Invoice payments: POST `/vendor-invoices/{id}/payments`, `/{invoiceId}/payments/{paymentId}/reverse`
- Uploads: POST `/vendor-invoices/bill-uploads`, `/vendor-invoices/payment-uploads`
- Vendors: POST `/vendors`; PUT `/{id}`; POST `/{id}/deactivate`, `/{id}/reactivate`; PUT `/{id}/supplies`; POST `/{id}/supplies/bulk`; DELETE `/{id}/supplies/{ingredientId}`
- Ingredients: POST `/ingredients`; PUT `/{id}`; PATCH `/{id}/ekadashi-flag`; DELETE `/{id}`; POST `/{id}/pack-sizes`; DELETE `/{id}/pack-sizes/{packSizeId}`; PUT `/{id}/market-rate`
- Ingredient merge: POST `/ingredients/merges/preview`, `/ingredients/merges`
- Recipe import: POST `/recipes/import/{masterRecipeId}`; GET `/recipes/import/{masterRecipeId}/close-matches`
- Inventory items (with opening count): POST `/inventory/items`; PUT `/{id}`; DELETE `/{id}`; POST `/{id}/adjustments`

That is 41 endpoints. Each one gets a request that is wrong in the way that used to beat the
permission check:
- `{}` that fails `@Valid`;
- the verifier's `{"lines": []}`;
- JSON cut off halfway, where the body is optional or not validated, or where `{}` turned out to be
  valid (ekadashi-flag, inventory PUT, merges);
- a multipart form with no file and no `kind`;
- or, for an endpoint with no body, an id in the address that isn't an id.

## Acceptance criteria

- **Unpermitted role with a malformed body gets 403 KMS-400021 on every listed endpoint.** Verified
  in `PermissionBeforeValidationIT`: 41 Volunteer probes, each asserting 403, code KMS-400021, no
  field errors, and no permission name in the body. All green with the fix (run 1); 40 red without
  it (run 2). The live API gives the same answers (run 4).
- **Nothing is written.** The same test counts rows in every table in the `public` schema, as the
  superuser, before and after each request, and asserts the counts are equal. Green on all 41.
- **Permitted role with a malformed body still gets 400.** 41 probes run as the first role that holds
  the permission (Temple Admin, Kitchen Manager, Kitchen Staff), all green. Seven of the 41 have no
  body, only a bad id in the address, and those assert the 404 KMS-400030 the product already gives
  for that. Also checked on the live API as Kitchen Staff.
- **Control run red without the fix, restored byte-identical.** Run 2: 41 failures, with the file
  hashes matching the pre-move hashes.
- **401 for no sign-in is kept.** `AccessControlEnforcementIT`'s existing test plus the new
  `unauthenticatedWithInvalidBodyIsUnauthorized` test, and live (HTTP 401).
- **403 body shape unchanged, method security still in place.** The 403 body is identical to the one
  method security gives. `argumentExpressionIsLeftToMethodSecurity` has an endpoint whose
  expression reads an argument: the interceptor skips it and method security still refuses it (403).
