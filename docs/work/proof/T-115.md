# T-115 — the phantom `scaling` diff was a block the config never declared, and `terraform plan` is now empty

**Nothing was applied.** Only `terraform plan`, `fmt`, `validate`, `show` and `providers schema`
were run. State serial was **31** before and **31** after (`terraform state pull`), and the plan was
run with `-lock=false` because it is read-only.

---

## The mechanism

`google_cloud_run_v2_service` has **two** `scaling` blocks, and the config only ever declared one.

- `template { scaling { min_instance_count } }` — the **revision's** floor. This is the one
  `main.tf` sets (`api_min_instances`, `web_min_instances`, and the worker's literal `1`).
- `scaling { min_instance_count }` at the **top level of the resource** — the **service's** floor,
  divided among revisions taking traffic, plus `manual_instance_count` / `scaling_mode`.
  **No service declared this one.**

Cloud Run returns the service-level block on every service whether or not anyone set it. The
provider reads it into state; none of its attributes is `Computed`; so a config with no `scaling`
block does not mean *leave it alone*, it means *this block should not exist* — and Terraform
proposed to delete it on every plan, forever, because the next refresh read it straight back.

That is exactly why the worker diffed `0 -> null` while declaring `min_instance_count = 1`:
**the diff was never about the number the worker sets.**

### Evidence, not inference

Provider schema, read from the pinned provider itself (`terraform providers schema -json`,
hashicorp/google **6.50.0**, the version in `.terraform.lock.hcl`):

```
TOP-LEVEL block types: ['binary_authorization', 'build_config', 'scaling', 'template', 'timeouts', 'traffic']
service-level scaling attrs:
  manual_instance_count {'type': 'number', 'optional': True}
  min_instance_count    {'type': 'number', 'optional': True}
  scaling_mode          {'type': 'string', 'optional': True}
template.scaling attrs:
  max_instance_count {'type': 'number', 'optional': True}
  min_instance_count {'type': 'number', 'optional': True}
```

`"description": "Scaling settings that apply to the whole service"` on the top-level block —
optional, and **not computed**, which is the part that makes omission a deletion.

What the deployed services actually report, from state (`terraform show -json`):

```
api      -> top-level scaling: [{"manual_instance_count": 0, "min_instance_count": 0, "scaling_mode": ""}] | template.scaling: {"max_instance_count": 10, "min_instance_count": 1}
frontend -> top-level scaling: [{"manual_instance_count": 0, "min_instance_count": 0, "scaling_mode": ""}] | template.scaling: {"max_instance_count": 10, "min_instance_count": 0}
worker   -> top-level scaling: [{"manual_instance_count": 0, "min_instance_count": 0, "scaling_mode": ""}] | template.scaling: {"max_instance_count":  1, "min_instance_count": 1}
```

Two things fall out of that table:

1. The service-level floor is **0 on all three** — including the worker. The pinned instance the
   worker relies on is the *revision* floor, a different field.
2. **The frontend runs at zero**, so the old comment's "both services now run at a managed
   non-zero minimum" was false on its own terms as well as diagnosing the wrong block.

### Why the diff renders as `min_instance_count = 0 -> null`

It is a **block removal**, not an attribute change; Terraform renders every attribute of a
disappearing block as `<value> -> null`. Read quickly it looks like the revision attribute, which
is how the wrong explanation survived. The baseline at `HEAD` (`git stash`-clean tree), verbatim:

```
  # google_cloud_run_v2_service.worker will be updated in-place
  ~ resource "google_cloud_run_v2_service" "worker" {
        id                      = "projects/iskcon-kms-2026/locations/asia-south1/services/kms-staging-worker"
        name                    = "kms-staging-worker"
        # (33 unchanged attributes hidden)

      - scaling {
          - manual_instance_count = 0 -> null
          - min_instance_count    = 0 -> null
            # (1 unchanged attribute hidden)
        }

        # (2 unchanged blocks hidden)
    }

Plan: 0 to add, 3 to change, 0 to destroy.
```

Note `- scaling {` sits at resource level, and `template` is among the "2 unchanged blocks hidden".
Identical stanzas for `.api` and `.frontend`.

### What was done instead of suppressing it

`lifecycle { ignore_changes = [scaling] }` would have silenced this in one line. It was
**deliberately not used**: it hides the block rather than recording it, and this file already lost
a suppression once on a false premise. The block is now **declared** with the value the running
services report (`min_instance_count = 0`), so the file describes what is deployed — which is what
the rule asks for. `manual_instance_count` and `scaling_mode` are left undeclared: this resource is
SDKv2, where an omitted number inside a block that *is* present reads back as `0` and an omitted
string as `""`, matching state exactly. The empty plan below is the proof that holds.

## Judgement: `api_base_url` stays `default = ""`

**Left as it is, deliberately, and `variables.tf` was not touched.**

The argument for making it required is that an environment silently missing it hands a temple
administrator a webhook URL with no host on the Settings screen, and a required variable makes that
impossible to forget. The argument against is stronger: **the value does not exist yet at the moment
it would first be demanded.** Cloud Run only issues the URL when the service is created, and the
variable's own description says to copy the string the deployed service reports rather than
construct it. Required, the first `apply` of a new environment could not be filled in honestly — it
would be satisfied by typing `""`, which is strictness that changes nothing except adding a step
that teaches people to type a placeholder past a guard. `cors_allowed_origins` is required and has
the same shape, but its blank failure mode is an app that visibly does not work; this one's is a
single field on one screen.

So the real risk is *forgetting on the second apply*, and the fix for that is visibility, not a
type error. The example file now gives `api_base_url` its own section, the exact
`gcloud run services describe` command, and a sentence saying it is empty until the environment has
been deployed once and should be filled in on the second apply.

**If Rajeev would rather have the guard, it is a two-line change** — drop `default = ""` from
`variables.tf` and the environment must name it — and I will take it; I am not attached to the call,
only to it being made on the bootstrap ordering rather than by default.

## Not done / needs Rajeev

- **No hand smoke-test, and none is possible for this task.** There is no user-facing surface here;
  Commandment 5's smoke test does not apply. The equivalent — running `apply` and seeing the
  services unchanged — is **explicitly forbidden by this task** and is the release agent's step.
- **The empty plan is proved against staging only** (`iskcon-kms-2026`, `environment = "staging"`).
  There is one deployed environment, so there is nowhere else to prove it.
- **`terraform.tfvars.example` is not checked by anything.** `terraform fmt` refuses the `.example`
  extension and nothing in CI compares it to `variables.tf`, which is how it drifted far enough to
  name a variable deleted some time ago. The set-difference check in this proof is six lines of
  Python and would catch the next drift on every push; **worth a small task, not taken here** —
  it would mean touching CI config, which is outside this contract.
- **Not run through `tools/work-lock.sh`.** Terraform touches neither Gradle nor `.next/` nor
  `build/`; it serialises on its own GCS state lock, and a read-only plan was run with
  `-lock=false` so as not to block anyone. Flagging it because the brief asks for the lock by
  default.
- **One thing noticed and deliberately left alone:** the `min_instance_count = var.x > 0 ? var.x :
  null` ternary on the API and frontend is, on this SDKv2 resource, indistinguishable from passing
  the number directly — `null` and `0` both read back as `0`. It is harmless, it becomes correct
  again if the resource ever moves to the plugin framework, and removing it is a behaviour-neutral
  edit nobody asked for. The comment above it now says this instead of claiming it prevents a
  perpetual diff, which it does not.
