## Decisions and how things work

**How proposals are grouped.** Ingredients whose `IngredientNameMatcher.normalise(name)` is equal (preparations, plurals, case, punctuation removed). EXACT only; the matcher's CLOSE matches ("Rice" / "Rice, basmati") are varieties, not duplicates, so they are not proposed. The admin can still build any group by hand. Names only, not aliases.

**How the kept ingredient is chosen** (clarifier: the document's examples keep the base name; the rest is left to the admin): 1) a name with no preparation word; 2) the most recipe lines; 3) the oldest; 4) by name.

**Preparation note in the input.** `preparationNote` null or missing means the proposed note (the matcher's split). A blank string means no note. T-276 should send the proposal's note back, or `""` when the admin clears it.

**Clarifier and conductor rulings used.** A line that already has a note gets the moved note first, then its own, with no repeated part ("sour" onto "whisked" gives "sour, whisked"). A recipe with lines for two members keeps two lines, and quantities are never added. No unique constraint on `recipe_ingredients` gets in the way.

**Units** (conductor's ruling). Figures that carry their own unit are left as recorded: stock movements, PO lines, receipt lines, invoice lines, recipe lines and pack sizes. On-hand sums already go through `to_base_qty`, so nothing is lost. Figures stored per one canonical unit with no unit beside them are converted with `Unit.baseFactor()`/`InventoryUnits`: vendor list price, price history, market rate and its history, and reorder level. Shopping-list decisions are converted too, because they fold into the kept line. Across families the merge is refused with 400171, and the details name both ingredients and both units.

**Folding one-row-per-ingredient tables:**
- **Vendor supplies**, per vendor:
  - Price comes from the chosen ingredient, else the kept one, else the first priced row. The pack and pack price come with it.
  - Lead time is the winner's, else the first one that vendor gave for any member.
  - The kept ingredient's preferred vendor stays preferred; if it had none, the first merged member's preferred vendor does.
- **Pack sizes:** a pack of the same base size folds into the kept pack, and the PO, invoice and supply rows that named it follow. Other packs move across as entered.
- **Inventory item:** the kept row, with any blank filled from the others.
- **Shopping-list decisions:** one row. Typed quantities are summed in the kept unit. It is ticked if any was ticked, and hand-added if any was.
- **Market rate:** the newest of the group, converted.

**Aliases.** Merged-away names, and their own aliases, go onto the kept ingredient's `aliases` array and into `ingredient_aliases`. They have to go in both. `IngredientService.update` rebuilds alias rows from the array and deletes the rest, so a name held only in the table would vanish on the next edit of the kept ingredient. Names that normalise alike ("Curd, fresh" and "Curd, sour" are both `curd`) share one table row. A key another ingredient already holds is left with that ingredient; the name is still on the array, which search reads.

**Merged-away rows are deleted.** I found no reason to keep them, since every reference is moved and the names live on as aliases. Before the delete, the service counts references from the catalogue and refuses if any remain. That matters because `ingredient_pack_sizes` and `ingredient_aliases` are ON DELETE CASCADE and would otherwise lose rows silently.

**Audit.** One `INGREDIENT_MERGED` on the kept ingredient. Before-state is each member's snapshot. After-state is read back from the rows: the kept row, alias rows, on hand, supplies, packs, and `stillPointingAtMerged` from the catalogue, which reads 0 everywhere. The reason reads "Merged Curd, fresh, Curd, sour, Curd, whisked into Curd." It also writes one `INGREDIENT_DELETED` per merged-away ingredient, reason "Merged into Curd.", so that ingredient's own history says where it went.

**Recipe versions are bumped** on every recipe whose lines changed. Otherwise cached translations would keep printing "Curd, sour".

**Append-only mechanism (V147).**
- One SECURITY DEFINER function, `merge_ingredient_ledger_rows(table, from, to)`, with `search_path` pinned, EXECUTE revoked from PUBLIC and granted to `kms_app`.
- It runs as the table owner, which `reject_append_only_change()` already lets through, so that trigger is unchanged.
- It can only set `ingredient_id` from one ingredient to another, on four named ledgers: `stock_movements`, `goods_receipt_lines`, `vendor_price_history`, `ingredient_market_rate_history`.
- It works in the session's temple only: RLS is FORCEd on the owner, and there is an explicit `tenant_id` predicate as well.
- It needs both ingredients visible and in the same unit family.
- It converts only the two per-unit rate columns, with the factor worked out from the two units itself, never passed in.
- It refuses unknown tables, the same id twice, another temple's id, and a session with no temple.
- A flag honoured by the trigger (the way the purge gets through) was rejected. While the flag is on, it would let every UPDATE and DELETE through on every append-only table, including `audit_events`.

**Foreign keys to `ingredients` found in the catalogue (13):**
- recipe_ingredients
- stock_movements, goods_receipt_lines, vendor_price_history, ingredient_market_rate_history (append-only)
- vendor_supplies
- inventory_items
- shopping_list_lines
- ingredient_pack_sizes, ingredient_aliases (CASCADE)
- purchase_order_lines
- vendor_invoice_lines
- ingredient_request_lines

**Foreign keys to packs:** `purchase_order_lines`, `vendor_invoice_lines` and `vendor_supplies`, each on `pack_size_id`.

**Anything stored by NAME rather than id (README lesson 1):**
- **`recipe_translations.content`**: cached translations with ingredient names in them. Handled by the recipe version bump.
- **`master_recipes.ingredient_names`**: the library's own names, not the temple's catalogue. The import now resolves them through aliases (T-250), so a re-import of "Curd, sour" finds Curd.
- **`translation_glossary.source_term`**: a temple's term for translation. It is not a reference, so it was left alone. A glossary entry for "Curd, sour" simply goes unused.
- **Left as history, correctly:** `vendor_price_history.pack_description`, job-card/document snapshots, and audit JSON.
- **Not ingredients:** `purchase_order_lines.description` and invoice-line descriptions are free text for lines outside the catalogue.

## Not done / needs Rajeev

- **No hand smoke-test.** This task has no screen (T-276 builds it), and the local API is down and was not touched. Everything above is Testcontainers only.
- **Production ownership, not verified.** V147's function must be owned by the table owner (the migration role). If a deployment ever ran migrations as `kms_app`, the function would run as `kms_app` and the append-only trigger would refuse it. The merge would then fail safe, rolled back with a 500. I have not checked who owns the tables on staging.
- **Rounding.** Converting a Kg price to gm keeps 4 places, the column's scale: ₹71.23/Kg becomes ₹0.0712/gm, 0.04% out. An absurdly small per-Kg market rate (below ₹0.00005/gm) would round to 0, fail its CHECK and roll the merge back with a 500.
- **Pack limit.** The kept ingredient can end up with more than 8 pack sizes. The limit is enforced only when a person adds a pack.
- **My own judgement calls, open to Rajeev:**
  - Shopping-list decisions are summed and ORed.
  - The newest market rate wins.
  - Supply lead time is inherited from another row when the winning row has none.
  - Proposals use exact normalised matches only.
- **For T-276:** send `preparationNote` null to use the proposed note, and `""` for no note. The preview returns 200 with `unitProblem` and `conflicts` rather than refusing.
- The preparation-word list behind the proposals is still T-249's provisional list (Desk Q-12).
