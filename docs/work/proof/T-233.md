## Part 1c — caps are caps

CSS cannot make a table column "min(content, 40%)". I tested it in Chrome on a scratch table before
writing code: `max-width` on a cell was ignored (identical widths with and without); px `max-width` still
grew past the cap; `width:1px` + cap pinned every column at its longest word; `min-width`,
`fit-content`, `max-content`, container units: nothing, or pinned. So `table.ts` measures. Each column's
widest cell is read unwrapped, each flexible column gets min(need, cap). Spare width is then shared
evenly among the flexible columns still short, never past their need, and anything left sits between
the groups. It runs just before paint after any content change or width change. It writes only inline
widths on header cells. It does nothing below 1024 or in jsdom.

Interpretation to check: I read the brief's "leftover to flexible columns in proportion" as letting a
column go past its cap when nothing else needs the room. §5's rule 3 says longer-than-cap content
wraps. Taken literally, /users at 1280 would keep Email at 141px, three lines per address, next to 315px
of blank Phone column. That is the state I measured with the strict version. One place in `table.ts`
switches between the two.

Before/after (column px; table 934 at 1280, 1198 at 1920; "wrapped" = cells where a text node takes
two or more lines):

- /users 1280: Name 347→**159** (names ≤126px), Email 132→**263**, every email 2–3 lines→**one line**.
  1920: Name 479→159, Email 180→263, one line.
- /staff 1280: Name 265→150, Contact 134→248. Contact still wraps in all 6 rows: the row needs 936px in
  a 934px table (Actions alone is 259). 1920: Name 479→150, Contact 180→257, nothing wraps.
- /invoices 1280: Invoice 147→139, Vendor 157→**216**, vendor names 3 lines (7 of 8)→none wrap. 1920:
  Vendor 275→216.
