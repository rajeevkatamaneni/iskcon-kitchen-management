# T-103 — the fill rate stops counting goods that went back because the vendor got them wrong

`VendorPerformanceService.countLines` summed `goods_receipt_lines.received_qty` and nothing else. A
return writes its own negative `RETURN_TO_VENDOR` movement and never touches that column, so a
vendor whose fifty kilos of rice all went back for weevils scored exactly as one whose rice was
fine. The fill rate now measures what the temple **kept**: received quantity less every return whose
reason blames the vendor — `DAMAGED`, `SPOILED`, `WRONG_ITEM`, `NOT_DELIVERED`. `OTHER` is
deliberately outside it, per Rajeev's ruling of 2026-09-10.

## The three judgements this task had to make

**On-time is not touched, and that is a decision.** The goods in a return *did* arrive on the day;
they were sent back later. The class comment already says the two figures are deliberately a pair —
on-time asks whether the lorry turned up, fill asks how much of the order the temple kept — and that
measuring on-time at completion would collapse them into one number. A return reversing an on-time
score does the same thing, and does it on a clock the vendor does not control: a return can be
booked six weeks later, so a percentage already read off the screen would silently change. The
weevil test asserts `onTimePercent` **100** alongside `fillRatePercent` **0**, so the decision is
pinned rather than merely stated. **The one case that is genuinely arguable is left for Rajeev** —
see *Needs Rajeev* below.

**A partial return subtracts the quantity; it does not disqualify the line.** Forty-five kilos back
out of fifty received, against fifty ordered, leaves five kept — a fill of 10%, not 0%. Returns are
cumulative and the subquery sums them, so two returns against one receipt line both count.

**A line is floored at zero fill and still capped at one.** `GoodsReturnService` already caps
cumulative returns at the receipt line's `received_qty` (`KMS-400140`), so the arithmetic should
never go negative; the clamp is there because a report is the wrong place to discover otherwise. A
negative fraction would drag down that vendor's *other* deliveries through the average, producing a
figure nobody could reconcile against the counts printed beside it. Tested with returns written past
the service's cap, straight to the table.

**Two smaller things, recorded because they were chosen rather than fallen into.** The four reasons
are named one by one instead of "everything except `OTHER`", so a sixth reason added later is left
out until somebody rules on it rather than enrolled against every vendor silently. And a return is
counted against the order it came in on **whenever it was made** — the period picks orders by
`order_date`, exactly as the rejection counts do, so weevils found in November move October's
figure and the same October report does not read differently depending on the day it is run.

## Acceptance criteria

| Criterion | How it was verified |
|---|---|
| A fully returned delivery scores as not delivered | `aFullyReturnedDeliveryIsNotFilled` — 50 ordered, 50 received, 50 back as `SPOILED`, `fillRatePercent` **0** with `linesJudged` 1 (0%, not blank: there *was* something to fill) |
| A partial return subtracts the returned quantity and no more | `aPartialReturnSubtractsOnlyTheQuantityReturned` — 50 ordered, 50 received, 45 back as `DAMAGED`, `fillRatePercent` **10** |
| A return with reason `OTHER` does not change the score | `aReturnForOtherDoesNotCountAgainstTheVendor` — two vendors, same delivery, same 50 kg back, only the reason differs: `OTHER` **100**, `SPOILED` **0**, totals **50** |
| Fill rate cannot go negative | `aFillRateCannotGoNegative` — 40 received, 30 + 20 back (written past `KMS-400140`'s cap), **0** rather than the −25 an unclamped line would give |
| Existing vendor performance tests pass, T-060's included | 18 of 18 green in the real run **and** in the control, `aDescribedLineDoesNotDragTheFillRateDown` untouched |
| `VendorInvoiceService.expectedReceivedValue` untouched | Not opened. A return is settled by a credit note this product has no concept of |
| No migration, no `ErrorCode.java` | Neither opened; `ReturnReason`'s five values already existed and the CHECK in `V111` already mirrors them |

**T-060's pinned test is unaffected, and the reason is structural rather than lucky.** A described
line has `ingredient_id IS NULL`, so the `AND pol.ingredient_id IS NOT NULL` clause still excludes it
before any return is looked at, and a described line can never take a receipt line for a return to
point at. The clause was not moved, weakened, or worked around.

## What a temple admin will see change

**One column, on one screen: "Fill rate" on `/vendor-performance`, per vendor and in the totals
row.** Nothing else moves — on time, orders judged, orders placed, rejections by reason and the
open-order aging buckets are all computed from untouched queries.

- **Historic figures move, because the report is computed on read.** A period from three months ago
  can show a lower fill rate today than the same period showed yesterday. Nobody's data changed; the
  question changed.
- **Only vendors with a recorded return move.** A vendor with no `goods_returns` row against a
  vendor-fault reason reads identically to the digit. A return recorded as `OTHER` also changes
  nothing, which is the ruling.
- **How far it moves:** the drop on one line is the returned quantity over the ordered quantity, and
  the vendor's figure is the average over judged lines. One fully returned line out of five judged
  lines takes twenty points off. One fully returned line where that is the vendor's only judged line
  takes it from 100% to 0%.
- **The realistic blast radius is small, and worth saying in the release note.** Returning goods only
  became recordable at T-013 (`V111`, 2026-09-09), so the only deliveries whose scores can move are
  ones somebody has recorded a return against since then. "Months-old deliveries can drop" is true of
  the mechanism; in practice it is bounded by however much returning has actually been keyed in.

## Wording proposed for the screen — for Rajeev to judge, not adopted

The screen already carries an "What these figures count" notice built by `caveat()` in
`frontend/app/vendor-performance/page.tsx`. Two things could be said, and they are separable.

**A. A permanent fourth line in that notice**, in the voice of the three already there:

> "The fill rate counts what the kitchen kept. Goods sent back to a supplier as damaged, spoiled,
> the wrong item, or never actually delivered come off it; goods sent back for our own reasons do
> not."

**B. A dated, temporary note**, because a figure that drops overnight otherwise reads as the vendor
getting worse:

> "From <date>, goods sent back as the supplier's fault come off their fill rate — including for
> deliveries made before that date. A figure lower than you remember may be this change rather than
> a change in the supplier."

My recommendation: **both, and B removed after a few weeks**, since its whole value is that it
explains a discontinuity nobody else can see. A alone leaves the drop unexplained; B alone leaves
the column undefined once the note is gone. Neither is written — this is a proposal.

## Not done / needs Rajeev

- **No hand smoke test.** The change is backend-only and is not deployed — builders do not deploy —
  so nothing was pressed on the running application. The screen renders whatever the API returns and
  its own code was not touched, but **the changed column has not been seen by a human on a real
  screen**, and Commandment 5 wants it seen before this is considered closed.
- **The one on-time case that is genuinely arguable, deliberately left alone.** A `NOT_DELIVERED`
  return says the receipt itself was a keying error — fifty entered when five arrived, or nothing at
  all. Where that reverses the *entire* first receipt of an order, the order currently still scores
  on-time on a delivery that never happened. Reversing it is a judgement at **order** grain while
  this ruling is at **line** grain, it needs its own rule for partial cases, and Rajeev has not been
  asked. Smuggling it in beside a ruling about fill would have been the wrong way to raise it. **It
  is a real hole and it is his to rule on.**
- **The copy above is a proposal.** Nothing was written to the frontend.
- **The purchase-order balance is still untouched**, as the ledger row says: a return does not
  re-raise `poOutstandingByIngredient`, so a re-buy shows as a fresh shortfall rather than as a
  balance the vendor still owes. Defensible as it stands, unruled, and out of this contract. (The
  shopping list itself needs nothing — on-hand sums `stock_movements` with no type filter, so the
  goods do come back on the list. The struck claim in an earlier version of the ledger row was
  wrong and was not acted on.)
- **A defect in this change was caught before the first test run, not by it.** The `sent_back`
  subquery is a Java text block concatenated into another, and the first version produced
  `… AS sent_backFROM purchase_order_lines` — a missing newline that would have failed as a SQL
  syntax error. It was found by assembling the query outside Java and reading it. Noted because the
  neighbouring `LIVE_ORDER` concatenation has the same shape and gets away with it (`)AND` still
  tokenises), so the trap is live in this file for whoever edits it next.
