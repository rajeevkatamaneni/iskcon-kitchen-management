# T-082 — the invoice form chooses a vendor, then picks that vendor's own open order from a dropdown; the server refuses a pair that disagrees

Three problems with one cause, fixed by construction rather than by validation: the vendor is asked
first, the purchase order is a dropdown of **that vendor's open orders**, and the endpoint refuses a
mismatched pair with `KMS-400145` because it is reachable without the screen.

## What I found before building (the two questions the brief asked)

**1. `GET /api/v1/purchase-orders` did NOT filter by vendor, and had no notion of "open".** It took
one optional `status` and nothing else:

```java
// PurchaseOrderController.java:37, before
public List<PurchaseOrderView> list(@RequestParam(required = false) PoStatus status) {
```
```java
// PurchaseOrderService.java:56, before — the whole of the filtering
if (status != null) { sql.append(" AND po.status = ?"); args.add(status.name()); }
```

So I added the narrowest thing that answers the question: two more query parameters, `vendorId` and
`openOnly`, on the list that already exists — not a second endpoint returning the same view from a
second copy of the join. `PurchaseOrderService.list(PoStatus)` is **kept as an overload** delegating
to the new three-argument one, because `TodayService.java:215` calls it and that file is not in my
contract.

**2. What "open" means, decided from the code and not from instinct.** Offered: `SENT`,
`PARTIALLY_RECEIVED`, `RECEIVED`. Excluded: `DRAFT` and `CANCELLED`. The reasoning is in the
javadoc on `list` and in short:

- **DRAFT is excluded** because `send()` is the only path out of DRAFT and it is what puts the order
  in front of the vendor — a vendor cannot have billed for an order it has never seen.
- **CANCELLED is excluded** because a bill against a withdrawn order is a dispute, not a payable, and
  must not be capturable with one dropdown pick.
- **PARTIALLY_RECEIVED is offered deliberately**, as the brief expected: vendors bill for what they
  have delivered so far, and hiding a part-delivered order pushes exactly that invoice down the
  direct path, where it loses its order and its variance.
- **RECEIVED is offered** because it is the ordinary case — the bill usually arrives after the goods.

**"Already fully invoiced" is NOT filtered, and that is a decision I want on the record rather than an
omission.** The schema cannot express it. `vendor_invoices.po_id` carries no unique constraint
(`V28__vendor_invoices.sql:52` is a plain index, and the file's own comment says the duplicate-number
index is "an index for the lookup, not a unique constraint"), several invoices against one order is
the supported part-billing case, and there is no invoiced-to-date total anywhere to compare an
order's value against. Dropping an order the moment it has one invoice would silently block the
second legitimate bill. **If a fully-invoiced notion is wanted it needs a definition first, and that
is a decision for Rajeev, not a filter I should bolt on here.** Listed under "needs Rajeev" below.

**3. `frontend/lib/api.ts` had no wrapper for this.** It had `listPurchaseOrders(status?, token?)`
and eleven other PO calls; nothing vendor-filtered. I added
`listOpenPurchaseOrdersForVendor(vendorId, token?)` rather than more optional arguments on
`listPurchaseOrders`, because the two answer different questions and `listPurchaseOrders` has a live
caller in `frontend/app/orders/page.tsx:33` whose signature I did not want to churn.

**4. Existing tests covering this screen and this service — grepped, found, and granted to myself as
the contract instructs:** `frontend/__tests__/invoices.test.tsx` (it asserted
`input[name="purchaseOrderId"]`, so it **had** to change — this is exactly the case the standing rule
exists for), `backend/.../invoice/VendorInvoiceIT.java`, and, not modified but run as neighbours,
`InvoicePaymentIT`, `InvoiceCorrectionIT`, `GivingPageIT`, `PurchaseOrderIT`.

### The substance of the change

**Server (`VendorInvoiceService`).** The two bare `count(*)` checks were independent, so no version of
them could ever notice the pair disagreeing. Folded into one query, as the brief preferred — this is
one query where there used to be one, not a third:

```java
private void requirePurchaseOrderForVendor(UUID poId, UUID vendorId) {
    List<UUID> owner = jdbc.queryForList(
            "SELECT vendor_id FROM purchase_orders WHERE id = ?", UUID.class, poId);
    if (owner.isEmpty()) { throw ... RESOURCE_NOT_FOUND ... }
    if (!owner.get(0).equals(vendorId)) { throw ... INVOICE_ORDER_NOT_FOR_VENDOR ... }
}
```

A cross-tenant order is invisible under RLS, so it reads as absent and returns 404 — deliberate, and
tested, so a probe cannot tell "no such order" from "somebody else's order".

**Screen.** Vendor select is now controlled state; choosing one resets the chosen order and re-fetches
through `useAuthedQuery`, whose effect keys on the fetcher, so the list re-filters. The order field is
a `<select>` labelled **"Purchase order"** (the word "id" went with the text box), options read
`PO-2026-0042 · Received · needed 20 Aug`, and it is disabled until a vendor is chosen. The direct
tick is unchanged in size and behaviour — one checkbox swapping the dropdown for the description.

**One incidental fix inside my own file, declared:** the vendors query was
`useAuthedQuery((t) => api.listVendors(true, t))` — an inline arrow, which `use-authed-query.ts`'s own
doc warns "would re-fetch in a loop" because the fetcher is in the effect's dependency list. Wrapped
in `useCallback`. Same file, same screen, and I would rather say it here than leave it.

## Not done / needs Rajeev

1. **No hand smoke-test.** The change is not deployed — I do not commit, push or deploy — so I could
   not drive the real screen in Chrome. Commandment 5 wants this surface tried by hand; **it still
   needs doing after release**, and the two things worth pressing are the vendor→order re-filter with
   a vendor that has several orders, and a vendor with none (the hint should appear and point at the
   direct tick).
2. **"Fully invoiced" is undefined in this product, and I did not invent it.** Reasoning above under
   finding 2. If Rajeev wants an order to drop off the list once it has been billed in full, that
   needs a rule — invoiced-to-date against the order's line value, presumably, netting credits and
   ignoring voided bills — and it is a task, not a filter.
3. **The guard is on the record path only.** Nothing else in the product re-points an existing invoice
   at a different order (there is no such endpoint), so there is no second door to close today. If one
   is ever added it must call the same check.
4. **`KITCHEN_STAFF` reaching the order list.** The dropdown calls
   `GET /api/v1/purchase-orders`, which is behind `MANAGE_PURCHASE_ORDERS` — the *same* authority the
   invoice-recording endpoint already requires, so anyone who can reach this screen can already fill
   the dropdown. Checked rather than assumed; no permission change was needed, and I did not open
   `RolePermissions.java` to edit it.
