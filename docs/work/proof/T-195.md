## What was built, for the next builder

**V135, the reset**, runs per temple with `set_config('app.tenant_id', id, true)`, the same way V64 and V89 do it.

1. It deletes the Quartz jobs for shift reminders (group `shiftrem-<shift>`) and queued job-card renders (`generate-document-<doc>`). Both are matched with V86's `quartz_job_is_orphaned` for that temple and removed child-first, in V86's order.
2. It deletes the `JOB_CARD_PDF` documents.
3. It balances stock. The meal-connected set is every `MEAL_PLAN` movement plus every `CORRECTION` that points into the set, followed recursively. For each (ingredient, batch, storage_location) in that set it inserts one `ADJUSTMENT`:
   - quantity is `SUM(to_on_hand_qty)` of the rows being deleted, so the used-beyond-stock memorandum rows count zero;
   - the unit is the smallest one those rows used, found and divided by `to_base_qty(1, unit)`, so no conversion is written by hand and the result is exact to 3 decimals;
   - reason `COUNT_CORRECTION`, no reference, note starting `Meal data reset:`;
   - actor is whoever made the latest deleted movement in that batch;
   - a net of zero writes nothing.
4. It deletes those movements, then shift_reminders, broadcast recipients, broadcasts, waitlist, signups (attendance and its corrections are columns on this row), all shifts, meal_services, meal_plans, and the meal_card_sequence row. The next card is number 1.

**Roles.** Flyway runs as `kms_migrator` in tests (AbstractIntegrationTest) and as `kms_migration` on staging (FlywayMigrationRoleConfiguration, `DB_MIGRATION_USER`; memory note uat-environment). Neither is `kms_app`, so the V49 append-only trigger lets the deletes through unchanged. `app.purging_tenant` is not used.

**Other things pointing at these rows** (checked on a V134 schema dump):
- The only foreign keys are documents→meal_services and the shift children→shifts, all CASCADE.
- No function, view, trigger or policy names meal_plans, meal_services or the dropped columns.
- audit_events, notifications and ingredient_request_dishes have no foreign key. They are kept.

**V136, the schema.** Names are as the ledger fixed them.
- **`meal_plan_days`:** id, tenant_id, plan_date, day_type, created_at/updated_at. Unique `(tenant_id, plan_date)`, named `meal_plan_days_one_per_date`.
- **`meals`:** `meal_plan_day_id`, `meal_kind_id` (FK to meal_kinds.id, RESTRICT), event_name, occasion_name, and every per-meal field with its old CHECK restated under a `meals_` name.
  - Unique index `meals_one_per_meal` on `(meal_plan_day_id, meal_kind_id, lower(COALESCE(event_name, '')))`. It is not partial and does not include tenant_id. Any ON CONFLICT must name exactly that expression.
  - The event-name CHECK is meal_services' stricter one: not blank, at most 200 characters.
  - No `created_by` column on meals. Dishes keep theirs.
- **`meal_dishes`:** `meal_plans` renamed, so dish ids are unchanged. Adds `meal_id uuid NOT NULL REFERENCES meals ON DELETE RESTRICT`. Drops plan_date, meal_kind, event_name, day_type, occasion_name and all per-meal columns. Constraint and index names are renamed `meal_plans_*` → `meal_dishes_*`, as V81 did for the shopping list. The RLS policy is called `tenant_isolation` and has no table name in it, so nothing to rename there.
- **`documents`:** `meal_service_id` dropped; `meal_id` added (FK meals, CASCADE, as before). `documents_target_shape` is restated from V117. Index `documents_tenant_meal`.
- **`shifts`:** meal_date, meal_kind, meal_event_name and the V95 CHECK are dropped. `meal_id` added (FK meals, RESTRICT). Partial unique index `shifts_one_per_meal ON shifts (meal_id) WHERE meal_id IS NOT NULL AND status <> 'CANCELLED'`.
- **Dropped:** `meal_services`. V96 was only a column comment; its in-use check lives in Java (MealKindService), which the service wave removes. The foreign key replaces it.
- **RLS:** `enable_tenant_rls()` on both new tables. The renamed table keeps its policy.

**V137, the reseed.** Per temple with `app.tenant_id` set. It runs only where the temple has ACTIVE rows in `recipes`. Library copies count: V69 calls them wholly the temple's. The shared library (`master_recipes`) is never used. The planner is the Temple Admin, else a Kitchen Manager; a temple with neither is skipped with a notice.

Dates are the temple's own (`now() AT TIME ZONE tenants.timezone`). It writes:
- **Days:** today-2 through today+6, with B/L/D looked up by name then written by id, and 3 or 4 distinct dishes alternating from the temple's recipes. Target yield is the recipe's base yield.
- **Day type:** worked out as MealPlanService.dayContext does it, including occasion resolution.
- **Ekadashi:** recipes with a prohibited ingredient are left out on an Ekadashi day, so no acknowledgement is ever faked.
- **The event:** "Children's Bhagavad-gita Reading" at today+3, on the first `is_event` kind.
- **The meal shift:** "Kitchen help for Lunch" tomorrow, three hours up to ready-by, signed up by `ikms.volunteer.1@trading4good.org` if that account exists in the temple.
- **Plain shifts:** "Garland making" and "Crowd control".
- **Recorded days:** today-2 and today-1. Dishes COOKED, actual = consumed = target. The meal is recorded, and card numbers come from the reset counter using ServedMealService's prefix rule (BC/LC/DC-YYYY-0001…).
- **Not written:** stock movements, PDFs, reminders or audit rows. Each one's reason is in the migration header.

## Acceptance criteria

1. **Reset keeps on hand and removes meals and shifts, per temple.** MealRebuildMigrationIT builds a throwaway database as `kms_migrator` at V134. It seeds two temples with deliveries, meal plans with cooked draws, a correction, a used-beyond-stock row, a served and corrected meal, a job card, plain and meal shifts, signups with attendance, waitlist, reminder, broadcast and Quartz jobs; plus a third temple with none of that. It captures on hand per temple, ingredient and batch, then migrates one version at a time.
   - Tests: `onHandIsUnchanged`, `mealAndShiftRowsAreGone`, `everythingElseIsKept` (deliveries, POs, audit, notifications, recipes, users, kinds, the spoilage adjustment and its correction, the send job, a global job), `adjustmentsAreLabelledAndPerTemple`.
   - Temple B draws double, so the expected adjustment figures differ by temple and were worked out by hand.
   - The card counter row is gone (`card counters` = 0). The reseed then numbers from 0001.
2. **New rules refuse.** `aMealIsUniquePerDayKindAndEventName` covers a case-only difference and a second unnamed Lunch; a differently named event is accepted. `oneLiveShiftPerMeal`: a second OPEN is refused; a CANCELLED one is accepted, and an OPEN one is accepted after cancelling the first. `theNewTablesAreIsolated` is run as `kms_app`: another temple and no temple both read zero, and a cross-temple insert is refused by row-level security.
3. **Reseed.** `theReseedPlansAWeek`:
   - 9 days, 7 ahead, 27 B/L/D meals and 1 named event, 3–4 distinct dishes each;
   - the meal shift with the volunteer's signup, and the two plain shifts;
   - recorded days at -2 and -1, card numbers 0001–0006, counter 6;
   - no new stock movements.

   `theReseedWithoutTheVolunteer` checks the meal shift has no signup. `theReseedLeavesATempleWithoutRecipesAlone` checks nothing was written. TenantLoopMigrationIT asserts the same for its fixture temple.
4. **Negative control:** section 2. It applied (`cmp -s`, anchor count 1), failed 2 of 10 on the on-hand and adjustment assertions, and restored byte-for-byte.
5. **Green:** section 1. All nine named classes passed; CateringMigrationIT and DeliveryPinBackfillIT are pinned, not retired.
6. **Full suite:** section 3, with the worklist above. Every class failing that does not obviously read meals or shifts was rerun in isolation. What still fails traces to main code reading the old schema (section 4).

## Not done / needs Rajeev

- **No hand smoke test.** This task has no user-facing surface. The seeded data can only be seen once the services and screens are rebuilt.
- **The wipe is irreversible on staging.** D-27 says a full backup of the staging database must come first. Nothing in the migration enforces that; the release agent must take the backup.
- **Production condition.** V135 loops over every temple. D-27 records that production holds no temple data, and that the purge must not ship as written if that changes.
- **Document pipeline scope.** The D27-2 wave must include DocumentService and DocumentGenerationService. Until then no PDF of any kind renders: recipe, PO, work order, donation receipt.
- **Reading of "the temple's own recipes":** any ACTIVE row in the temple's `recipes`, library copies included. Stated in V137's header.
- **Timing.** V137's dates are the migration's run date. Deployed days after this proof, the week starts on deploy day, which is intended.

## After-UAT lines

- Job-card PDF files stay in object storage after V135 deletes their document rows; nothing references them.
- Notifications already queued for a deleted shift (a reminder created before the reset) will still send. V135 deletes reminder jobs, not notification send jobs.
- The seeded signup has no reminder job. SQL cannot write Quartz's serialized job data.
- `meals` has no tenant-consistency check on `meal_plan_day_id` / `meal_kind_id`: an FK can point at another temple's row if application code passes a foreign id. Same as every other FK in the schema today.
- A meal-reading test's failing `@AfterEach` leaves shared fixtures behind and fails ~90 unrelated classes. A cleanup that deletes the temple first, or `@Sql` cleanup, would stop one red class turning the suite red.
