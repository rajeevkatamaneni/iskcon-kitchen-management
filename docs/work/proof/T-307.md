## The API as built (for api.ts) — exact shapes, copied from the live responses below

`POST /api/v1/meals/{id}/repeat` body `{"everyWeeks": int, "until": "YYYY-MM-DD"}` (both required; missing → 400 KMS-400001 with a field error).
`GET /api/v1/meals/{id}/repeat-preview?everyWeeks=&until=` — same walk, writes nothing. Both answer `RepeatEventResult`:

```json
{"copies":6,"preparations":6,"dates":["2026-10-10","2026-10-24","2026-11-07","2026-11-21","2026-12-05","2026-12-19"],"skippedFasting":[],"skippedAlreadyPlanned":[],"lastDate":"2026-12-19","series":{"seriesId":"b2414699-2c16-4c63-8cf1-d33babfe0a17","everyWeeks":2,"until":"2026-12-31","position":1,"count":7}}
```
Preview of a new series has `"seriesId":null`. `lastDate` is null when no copy is made. `series` is null only when nothing is made and the source is in no series.

`ServedMeal.series` (list `GET /meals` and `GET /meals/{id}`), always present, null for a meal never repeated:
```json
"series":{"seriesId":"b2414699-...","everyWeeks":2,"until":"2026-12-31","position":4,"count":7}
```
`position` is null on a cancelled occurrence.

`GET /api/v1/meals/{id}/later-in-series`:
```json
{"seriesId":"b2414699-...","later":[{"mealId":"e2e50f7c-...","planDate":"2026-11-21","edited":false,"volunteersSignedUp":0}],"lastDate":"2026-12-19","volunteersToTell":0}
```

`POST /api/v1/meals/{id}/cancel` body (optional) `{"reason"?: string, "scope"?: "THIS"|"THIS_AND_LATER", "expectedMealIds"?: uuid[]}` → `{"volunteersTold":0,"mealsCancelled":4,"lastDate":"2026-10-24"}`.

Refusals: KMS-400175 (400) gap outside 1..12; KMS-400176 (400) until after temple-today + 1 year; KMS-400177 (400) no date fits; KMS-400178 (409) not in a series (later-in-series, or cancel THIS_AND_LATER); KMS-400179 (409) later set ≠ expectedMealIds, nothing cancelled; KMS-400045 (409) this meal cooked/recorded. All four endpoints are `MANAGE_MEAL_PLANS`.

### Deviations and decisions the contract did not fix (each is small; say if any is wrong)

1. **Cancel answers the same shape for both scopes.** `THIS` (and no body) now answers `{volunteersTold, mealsCancelled, lastDate}` instead of `{volunteersTold}`. A superset: the old key is unchanged. `lastDate` is null for a meal in no series.
2. **Repeating a meal that is fully cancelled is refused with the existing KMS-400046 MEAL_PLAN_NOT_OPEN** ("This meal can't be changed. It is already cooked or cancelled."). The old code quietly made nothing; the contract did not cover it, and I did not take a new code.
3. **Every date skipped is a 200 with `copies: 0`, not a refusal**, so the preview can still show which dates were skipped and why. Nothing is written in that case, not even a series of one.
4. **"Already planned" also covers a recorded meal on that date** (even one whose dishes were all "not made"), because `create()` would throw MEAL_ALREADY_RECORDED and roll back the whole repeat.
5. **Planning onto an existing series member through "Save this meal" marks it edited**, as `update()` does. A copy the repeat makes (including a cancelled meal it revives) has `series_edited_at` cleared.
6. **`volunteersToTell`** = people signed up or waitlisted on this meal's shift plus every later one's — the same people `cancelForMeal` messages. `volunteersSignedUp` per row counts signups only. `lastDate` in later-in-series is the last of `later`.
7. **When a THIS_AND_LATER cancel leaves nothing standing, `until_date` is left as it was** (the column is NOT NULL) and `lastDate` is null.
8. **Composite foreign key** `(tenant_id, series_id) → meal_series (tenant_id, id)`, so the database refuses a meal joining another temple's series even though FK checks bypass RLS. Needs `UNIQUE (tenant_id, id)` on `meal_series`. No cycle: meal_series points at no meal; TenantDeletionIT green.
9. **Series summary** is two correlated subqueries in `ServedMealService.MEAL_SELECT`, run only for meals with a `series_id` — no extra statement. ShoppingListStatementCountIT green.
10. **Later-in-series counts volunteers in SQL**, using the same two predicates as `ShiftService.rosterToTellOfCancellation` (ShiftService is outside the contract). If that method's rule changes, this has to change too; the javadoc on `laterRows` says so.
