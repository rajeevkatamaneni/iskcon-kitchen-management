# T-205 — voiding the gift behind a FULFILLED wish-list item reopens the wish

Rajeev's ruling on the question T-069 left open (option B in `docs/work/proof/T-069.md`, "Deferred to
Rajeev"). Built as ruled; not reopened for discussion.

## What was built

`DonationVoidService.voidDonation` now reads the struck gift's `wishlist_item_id` with the row it
already locks. After the mark, the stock reversal and the `DONATION_VOIDED` entry, still in the same
transaction, it calls `WishlistService.reopenIfNoLongerCovered(itemId)`:

1. Locks the item row `FOR UPDATE`. If it is not FULFILLED (ACTIVE, ARCHIVED, or gone), nothing.
2. Reads the item through `findItem`, i.e. the existing `SELECT` whose `paid_inr` is the giving page's
   figure (non-voided, COMPLETED, split gifts counted at `wishlist_applied_inr`). **No second sum was
   written.** The struck gift is already out of it because the mark was written earlier in the same
   transaction.
3. If `paid_inr >= price_inr * quantity_wanted`, nothing (jointly funded and still covered).
4. Otherwise `UPDATE ... SET status = 'ACTIVE', fulfilled_at = NULL, updated_at = now() WHERE id = ? AND
   status = 'FULFILLED'`, and returns before/after maps, both built from rows the database returned
   (before: the locked row; after: re-selected after the UPDATE).

The void then writes one audit entry: action `WISHLIST_ITEM_REOPENED`, entity type `WISHLIST_ITEM`,
entity id the item, before/after `{status, fulfilledAt, updatedAt, costInr, standingInr}` plus
`voidedDonationId` on the after side (not item state; it links the entry to the donation), reason
"A gift towards it was voided: <the void reason>".

Why the audit is written in the void and not in `WishlistService`: the entry needs the actor and the
reason, which only the void has. The wish-list service decides and reports; the void records.

Concurrency: the item row lock is the same one the gateway capture path takes in
`MonetaryDonationService.owedOnHeldItem` before it counts what is owed, so a settling payment and a
void cannot both judge the item on a figure the other is changing.

A later gift that covers the item again goes through `markFulfilledIfComplete` unchanged, which sets a
fresh `fulfilled_at` (tested in WishlistIT).

  The service-level `WishlistIT.onlyAnUncoveredFulfilledItemReopens` also covers this case, along

## Who reads `wishlist_items.status`, and what each does with a reopened item

Found by `grep -rn "wishlist_items" backend/src/main/java` and reading each hit.

- **Giving list, `WishlistService.forGiving`** (served by `GivingPageController GET
  /api/v1/donations/wishlist`): `status IN ('ACTIVE','FULFILLED')`. A reopened item is ACTIVE, so it
  stays listed. The screen, `frontend/components/give/DonatePage.tsx`, hides only ARCHIVED and decides
  "Fully covered" vs "₹N to go" from `paidInr` against cost, not from status, so it shows "₹15,000 to
  go". Correct. (WishlistIT asserts the item is still in `forGiving` after reopening.)
- **Checkout guard, `MonetaryDonationService.startWishlistCheckout`** (KMS-400068,
  `WISHLIST_ITEM_UNAVAILABLE`): refuses when status is not ACTIVE, then when owed (cost less
  `completedAmount`, which also excludes voided gifts) is not positive. A reopened item is ACTIVE and
  owed its shortfall, so checkout is taken. Correct. (DonationVoidIT asserts `201 Created` for the same
  checkout.)
- **Office cash guard, `DonationRecorder.validate`**: same status rule, refuses non-ACTIVE. A reopened
  item accepts hand-recorded cash again. Correct.
- **Payment capture, `MonetaryDonationService.settle` / `owedOnHeldItem`**: does not read status; it
  locks the row and compares against money owed, then calls `markFulfilledIfComplete`. A payment
  settling on a reopened item is applied (or split) and re-fulfils it. Correct.
- **Archive sweep, `WishlistService.archiveFulfilledForCurrentTenant`** (run by
  `WishlistArchiveRunner`): only `status = 'FULFILLED' AND fulfilled_at IS NOT NULL` past the window.
  A reopened item is ACTIVE with `fulfilled_at` NULL, so it is never swept while it is asking for money.
  Correct. (WishlistIT runs the sweep on a reopened item and asserts it stays ACTIVE.)
- **Admin list, `WishlistService.list`**, and `frontend/app/wishlist/page.tsx`: hides ARCHIVED unless
  asked; the pill shows "Active". Correct.
- **Office "record a donation" picker, `frontend/app/donations/new/page.tsx`**: offers items with
  `status === "ACTIVE"`, so the reopened item can be chosen again. Correct.
- `MyDonationsService`, `DonationLedgerService`, `DonationReceiptService` and
  `MonetaryDonationService:582` join `wishlist_items` for the title only and do not read status.
