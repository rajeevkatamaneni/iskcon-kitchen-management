## Two defects this found in my own work, both fixed before reporting

**Focus went to the top of the document after Add group.** The playground focuses the new element
inside a `requestAnimationFrame`, and measured in a real browser it does not work: React had not
committed the new group by the time the frame ran, so `getElementById` returned null and the
keyboard landed on `document.body`. Replaced with a ref plus an effect with no dependency list,
which runs after the commit. Re-measured: Add group → "Heading for Evening seva"; Delete →
"new-group-button"; Move to group across a boundary → the select it was pressed on.

**The screen contradicted itself when the save worked and the refresh did not.** Saving is two acts
— store the arrangement, then refresh the session so the menu repaints — and only the first can
fail in a way worth reporting. It used to report a refresh failure as "We couldn’t save your menu
arrangement", which is false and would have an administrator save a thing that is already saved. Now
the two are separate: a refused save shows the server's own words, and a save the refresh did not
follow says "Saved. The menu on the left catches up the next time you open a page." The unsaved
marker is measured against what this screen knows it saved, so "Saved." and "Not saved yet" can no
longer appear together. Observed in the harness, where the refresh genuinely fails.

## Layout: where a rule could not be met literally

`components/ds/table.ts` states intent, and this screen is a list of cards rather than a table, so
two rules needed a judgement. Both are built, neither was escalated.

**1. "No dead block" (§5 rule 3), against a 271.8–376.5px gap in the middle of every item row.**
Read the row as the two-column table it is — what the destination is, and what you can do to it —
and rule 3 says spare width is shared out *between the gaps*. With two columns there is one gap, and
it gets all of it: the labels start at one edge, the controls end at the other. That is also what
the rule's own phone layout does, `.kms-actions { margin-inline-start: auto }`. The alternative,
each row's buttons starting wherever its label happens to end, is ragged and slower to use — Move up
pressed twice would move under the finger. The gap between a content edge and its *container's*,
which is the number the dead-space rule is stated as, is **0px on every card and 52px from `main` to
the column either side**.

**2. The page is `max-w-4xl` (896px), the same as the Settings page it is reached from.** Narrowing
the board to its content would shrink that internal gap and grow the empty margins either side
instead — 164px rather than 52px — which fails the 120px test the internal gap passes. Total
emptiness is the same either way, and this way it is where the rest of the application already puts
it.

**3. Two things were changed after measuring, because the first build looked wrong.** The group's
heading box stretched the full width of the card, so the header row was the one line in the card
that did not read as "content left, controls right"; it is capped at 384px now. And the group's
three buttons were 157px out of line with the item rows' — the trash icon sat over the selects, not
the arrows. The delete control is a 192px labelled button now, matching the select's width, and the
header row carries the same 9px inset an item row gets from its own border and padding. Measured
after: 870–914, 918–962, 966–1158 in both, grips both at 402.

## Not done, or for Rajeev to look at

- **The real menu repainting after Save was not seen in a browser.** The harness has no Firebase, so
  `refresh()` throws in it. The unit test asserts the save and then the refresh, in that order. This
  is the one thing worth pressing on staging: arrange something, save, and watch the column on the
  left change without a reload.
- **No server was involved anywhere.** `KMS-400189`, `KMS-400190` and the field errors for a blank
  heading, an over-long heading and more than 20 groups were exercised against a mock. The screen
  stops two of those before they can happen (`maxLength={40}` on both heading boxes, and New group
  is disabled with a sentence at 20 groups), which means those two server messages should never be
  seen — worth one deliberate try on staging all the same.
- **Dragging is untested, by decision (D-M10).** It is offered on a pointer and nothing depends on
  it. It is the part most likely to have a rough edge on his machine.
- **One consequence of D-M7 that nobody has ruled on.** An administrator can delete the first group
  — the unheaded one — by moving its five items elsewhere. The nine destinations that are not on
  this board (a volunteer's four, the operator's five) all belong to that group, so for a volunteer
  at that temple they would then appear at the bottom under a heading reading "New". Nothing is
  lost and nothing is hidden, and an operator is unaffected because they belong to no temple. It is
  the only way anything a volunteer sees can change, and it is reversible by Reset. Worth a yes or
  a no from him rather than a guess from me: should the first group be undeletable?
- **A group made here is keyed on a generated id** (`g-<base36>-<random>`, lower case, never the
  reserved `new`). Two administrators arranging at the same time each overwrite the whole
  arrangement — the server takes it whole and replaces it whole, by design — so the last Save wins.
  That is T-420's decision and is recorded there; this screen does nothing to soften it.
