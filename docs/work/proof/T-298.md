## What was wrong and what changed

**N-1.** The option text for an item with no list price used the ingredient's stock unit (`unitLabel(i.unit)` in `everyone`, and `unitLabel(s.unit)` in `vendorOffers`). `catalogueLine` builds the line in `readableUnit(stockUnit)`, or in the vendor's pack where the ingredient has one. So "Curry leaves · gm" became a Kg line.
- `everyone` now says `unitLabel(readableUnit(i.unit))`. These are never in the vendor's pack, so the line always starts plain.
- `vendorOffers` now takes the catalogue. A no-price option says `startsIn(...)`, which uses `catalogueLine`'s own rules: the vendor's pack label if the ingredient has that pack ("Bag (25 Kg)"), otherwise the readable unit.
- Priced options are unchanged ("₹60/Kg", R-PO-3). The verifier already passed them.
- The pack wording is a builder decision. The clarifier (ae4684d1c214adbd1) said the requirements settle only the priced option. R-SL-3 gives the line's wording but not the dropdown's, and nothing contradicts "Bag (25 Kg)". Reason for choosing it: the option promises what the line will be, and the line starts at "× Bag (25 Kg)".
- Other places on the page that name a unit, checked: the Unit select's plain option and the fixed Unit cell use `l.unit`, which is already readable. The rate note uses `readableRate`. The one-off select lists `FOOD_UNITS` and creates what it shows. None of these can differ from the line.

**N-2.** Both local refusals (no items; needed-by date in the past) went through `toApiError(null, …)`. That wrapper is for a request that never reached the server, so it added "Check your connection and try again." and "KMS-0000".
- They now set a separate `refusal` state. It renders as ErrorNotice's red box with only the one sentence: no next-step line, no code.
- The no-items refusal clears when an item is added. Both refusals clear on the next submit.
- `toApiError` is still used for the real create failure.
