### Assertions of an absence, and why they pass vacuously

Two acceptance criteria assert that something is *not* there. Under the control both are inside a
test that has already failed on an earlier line, so **neither contributes to the failure count**, and
that is expected of an absence test rather than a hole:

- **`"Vendor null"` notification row** — `assertNoVendorNullNotification()` inspects
  `SELECT recipient_label FROM notifications` and asserts the list does not contain the string, plus
  `count(*) = 0`. It is not a `LIKE`, and not an `objectContaining`-style "does it have this shape".
- **the string `null` in the message body** — asserted on `params ->> 'summary'` and on
  `params::text`.

**A correction to the dispatch on the first of these.** The brief says the null "persists the literal
`Vendor null`" at `NotificationService:162` and only then fails at `:171-174`. Reading the file, the
label at `:162` is *built* but never *written*: `insert()` throws its `VALIDATION_FAILED` at the very
top, before any `jdbc.update`, so no row is inserted even before the `@Transactional` rollback is
considered. So the row this criterion forbids was never actually written by the old code either, and
the assertion would pass with or without the fix. I have kept it because it is cheap and it locks the
property in against a future change to `insert()`'s ordering — but it should not be read as evidence
the fix works. **The evidence that the fix works is the KMS-400130 code and the `status = 'DRAFT'`
assertion**, which do fail without it.

Likewise the JSON-key assertions do not use `objectContaining`: the frontend tests read
`Object.keys(body)` and then the value separately, and the audit-trail test asks
`jsonb_exists(before_state, 'phone')` and `before_state -> 'phone' = 'null'::jsonb` as two questions,
because `->` returns Java `null` both for an absent key and for a JSON null.

## Acceptance criteria

**1. A vendor saves with no phone; a malformed phone is still refused.**
`VendorWithoutPhoneIT > a vendor saves with no phone at all, and stores a real NULL rather than a
blank` posts `{"name":"Corner Hardware"}`, gets 201, and asserts `phone IS NULL` in the row — a real
NULL, not `""`. It also asserts the wire shape by inspecting the response body for the literal
`"phone":null`, rather than JsonPath's `doesNotExist()`, which answers the same for an absent key and
a null one (this is the exact reason `api.ts` makes `VendorView.phone` required-and-nullable).
`> a malformed phone is still refused` covers `98450` **and** `""` — both `KMS-400001` — and then
asserts neither left a row behind. Both fail/pass as set out in the control table.

**2. Sending a PO to a phoneless vendor returns KMS-400130 and leaves the order in DRAFT.**
`> sending to a phoneless vendor is KMS-400130 and leaves the order in DRAFT` asserts 409 +
`$.code == "KMS-400130"`, then **explicitly** `SELECT status FROM purchase_orders` is `DRAFT`, and
that `po_events` for that order is empty. FAILED under the control.

The fix is a restructure, not an inserted `if`. `sendViaWhatsApp` now asks all three refusable
questions above the one mutating statement: closed order → vendor lookup and phone guard →
`guardRate` → *then* the DRAFT→SENT transition. **I moved `guardRate` up too**, which the brief did
not ask for: it is a pure read, and a DRAFT PO cannot carry a recent `WHATSAPP_SENT` event (that
event is only written on the line after the transition), so the move is behaviour-preserving and
makes "everything that can refuse, refuses before anything changes" true rather than nearly true.
`PurchaseOrderWhatsAppIT > an immediate resend is rate-limited` still passes.

**3. No notification row is written with a `"Vendor null"` label.** Asserted against the table, and
additionally `count(*) FROM notifications = 0` for a refused send. See the vacuity note above — this
one passes with or without the fix, and the dispatch's claim that the old code persisted the row is
wrong.

**4. A described line renders its description in the summary, and `null` appears nowhere in the body.**
`> a described line names itself in the message` builds PO-2026-0061 in the shape of staging's
PO-2026-0030 — one ingredient line and one described line — sends it, and reads
`params ->> 'summary'` back off the notification: it must contain `Plastic stool`, must contain
`Rice`, and must not contain `null`. The whole `params::text` is checked for `null` as well.
FAILED under the control (the summary read `2 item(s): Rice, null`).

**5. An existing vendor with a phone is completely unaffected.**
`> a vendor with a phone is completely unaffected` sends and asserts 202, status `SENT`,
`recipient_label = 'Vendor +919845012303'` and `to_phone` intact. Plus the 30 pre-existing tests in
`VendorIT`, `PurchaseOrderWhatsAppIT` and `DescribedPurchaseLineIT`, and all 9 in
`frontend/__tests__/vendors.test.tsx`, unchanged and green.

## What I checked in the dispatch, and what I found

All three of the extra findings were real. One claim in the brief was not.

**Confirmed — `Map.of` and the audit snapshots (finding 1).** `VendorService:126`, `:148` and `:149`
all used `Map.of`, which throws NPE on a null *value*, and `:148` snapshots `before.phone()` — so a
phoneless vendor was a 500 on the way in *and* on every later edit, on top of the `.trim()` NPEs at
`:113` and `:140`. Now a `LinkedHashMap`. On the standing rule that the trail records what was
**stored**, never what was **asked for**: both sides now come from a `VendorView` read back through
`findById`, so the after-snapshot cannot agree with the caller by construction. That is one extra
`SELECT` on a rare staff action, which I judged worth it; say if you would rather I reused the
locals.

**Confirmed — `whatsapp_reachable` is stored, not derived (finding 2).** `VendorService:250`/`:300`.
It is not used as the guard, and `savesWithNoPhone` asserts a phoneless vendor reads
`whatsapp_reachable = true`, so the two facts stay distinct and any future conflation fails a test.
Both the migration and the error-code comment spell out the difference.

**Confirmed — `vendors/page.tsx:123` rendered `{v.phone}` bare (finding 3).** Now `?? "—"`. I matched
`staff/page.tsx:218`'s `??` rather than `users/page.tsx:140`'s `||`, because with the E.164 check the
only falsy value possible is `null` and `??` says exactly that.

**Confirmed — `vendors/new/page.tsx` bypassed `emptyToNull` on phone.** Fixed, and both forms lost
`required`.

**Corrected — the `"Vendor null"` row is never persisted.** Set out in full above. It changes nothing
about the fix (the guard still has to move, and the user-visible failure was still a meaningless 400

**Corrected, mildly — the CHECK already permitted null.** SQL treats a CHECK whose expression
evaluates to NULL as satisfied, so `phone ~ '…'` passes for a null phone and `DROP NOT NULL` alone
would have worked. I replaced the constraint anyway, with the null branch spelled out, so a reader of
`\d vendors` sees "null, or E.164" without having to recall three-valued logic. The migration says so
in as many words, so nobody later mistakes it for a behavioural change.

**Refuted a worry of my own — the vendor sheet was already safe.** `DocumentGenerationService:190`
also reads `vendors.phone` and is outside my contract, so I read it rather than touched it:
`PurchaseOrderSheetTemplate:123` guards with `notBlank(...)` before printing, so a phoneless vendor
prints a sheet with no phone line and does not NPE. `DescribedPurchaseLineIT > the vendor sheet prints
the described line's words` still passes. **No change needed there.**

**Reservations used exactly as issued.** `V101` (confirmed `V99`/`V100` are the highest on disk);
