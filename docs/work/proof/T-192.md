## Legitimate write paths, checked before writing

- **Bans** (`ban/EmploymentBanService`): `raise` (from `StaffEmploymentService.endEmployment`), `amend`, `retract`, `recordAbandoned`, and `check` → `recordCheckOnPlatformLog` (from `StaffScheduleController.hire`). Every one is behind `MANAGE_STAFF`, which SUPER_ADMIN does not hold (`RolePermissions`). So they are always temple requests. `AuthenticationFilter` sets `TenantContext.set(user.getTenantId())` from the selected membership, and `recordPlatform` passes `actor.getUserId()`, which is that same membership. The check runs in its own transaction, and `TenantAwareDataSource` sets `app.tenant_id` from the thread-local on every checkout, so it is set there too. EmploymentBanIT (14 tests, green below) drives all of these through MockMvc as a temple admin.
- **Notices** (`notice/NoticeService`): `raise` and `withdraw`. A temple admin has the temple set, which is covered as above. **An operator raising or withdrawing a notice has no temple set** (the filter sets a tenant only when `user.getTenantId() != null`). That write gets through V9's `platform_audit_superadmin_insert`, not V66's. Proved directly by `platformAuditOperatorWritesAreUnchanged` (PLATFORM_NOTICE admitted, no temple), and end to end by PlatformNoticeIT's operator tests: `operatorMayWithdrawAnyone` and "every raise and every withdrawal lands on the platform audit log", which signs in `uid-operator`.
- **Automation** (`NoticeService.raiseFromPlatform`) writes no platform audit row at all, by design (its Javadoc says so). Nothing to admit.
- **Other `recordPlatform` callers** (TenantExportService, TenantDeletionService, PendingAccountClaim, MasterRecipeService) are operator acts with entity types other than these three, so they always went through V9. Their ITs are green in run 3.

Nothing legitimate is refused. No decision needed.

## Acceptance criteria

All tests run as `kms_app` through the application's tenant-aware DataSource. Temple and uid are set exactly as `AuthenticationFilter` leaves them, and inserts are written without RETURNING (a RETURNING insert would be refused by the SELECT policy and prove nothing about the write).

- **(a) Cross-temple author refused, each entity type on its own.** `platformAuditRefusesTheCallersAccountAtAnotherTemple(String)`, one invocation each for EMPLOYMENT_BAN, EMPLOYMENT_BAN_CHECK and PLATFORM_NOTICE. Setup: same uid at A and B, temple A set, `actor_user_id` = the B account. Each asserts that the B account is visible to the request (the precondition that made the hole real), that the insert is refused with "row-level security", and that nothing was written. Green in run 4. **All three red without V133 in run 2, notice included.**
- **(b) Own active account at A admitted.** `platformAuditAdmitsTheCallersActiveAccountHere`: all three types insert 1 row each. Also, entity type `USER` is still refused for a temple user, so nothing widened. Green in runs 2 and 4. This one still loops, deliberately: it asserts admission, so a failure there is already the red.
- **(c) Disabled A account refused, each entity type on its own.** `platformAuditRefusesADisabledAccountHere(String)`, one invocation per type. Green in run 4. Without V133 (run 2), red for EMPLOYMENT_BAN and EMPLOYMENT_BAN_CHECK, which is new, and green for PLATFORM_NOTICE, which V66 already refused.
- **(d) Operators unchanged.** `platformAuditOperatorWritesAreUnchanged`: SUPER_ADMIN with tenant NULL, no temple set, own id. USER, PLATFORM_NOTICE and EMPLOYMENT_BAN_CHECK are all admitted and read back (3 rows). Operators really do write PLATFORM_NOTICE today. They do not write the ban types (no MANAGE_STAFF), and the test comment says so. Green in runs 2 and 4. PlatformNoticeIT (runs 3 and 4), plus TenantDeletionIT, TenantExportIT, PendingAccountClaimIT and RecipeLibraryIT (run 3), cover the real operator paths end to end.
- **(e) Reading stays operator-only.** `platformAuditStaysUnreadableToATempleUser`: the temple admin writes a notice row and reads count 0, while the admin connection sees 1. The existing `platformAuditIsSuperAdminOnly` still passes. Green in runs 2 and 4.
- **Negative control:** file move, run 2.
- **AuditService comment:** corrected to say that operators may write any entity type (V9), that temple users may write only bans, ban checks (V65) and notices (V66), and that since V133 the author must be the caller's active account at this request's temple. Code unchanged.

## Staging

The policies govern new writes only. PostgreSQL checks a policy when a row is written and never re-checks rows already stored, so no stored `platform_audit_events` row can "violate" V133 and nothing needs backfilling. Staging has one temple (checked by the main session), so no stored row names another temple's account anyway.
