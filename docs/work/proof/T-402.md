## The migration, and why RLS needed nothing

```sql
ALTER TABLE ingredients
    ADD COLUMN is_not_bought BOOLEAN NOT NULL DEFAULT false;
```

plus a `COMMENT ON COLUMN` in V99's register — quoting Rajeev, saying what the shopping list does
with it, and distinguishing it from `is_supply` beside it (a supply *is* bought; this says the thing
is never bought at all).

**No policy, no GRANT, no new table, and that is the reason rather than an omission.**
`ingredients` has called `enable_tenant_rls()` since V10. A policy is a *row* predicate, not a
column list, so a column added to that table is covered by the policy already there. The flag is
per tenant because the rows are.

**No backfill and no per-tenant loop.** `ADD COLUMN ... NOT NULL DEFAULT false` is DDL executed as
the table owner; PostgreSQL fills the default into every existing row itself, in one catalogue-only
operation, without a row-level policy ever being consulted. Migrations here *are* subject to RLS
(V97 and V98 both adopt each tenant in turn) — this one runs no DML, so there is nothing to adopt
into. `NotBoughtIngredientIT.everyExistingIngredientIsBought` asserts the fact that criterion
reaches for: a row written before the column existed reads as bought, **including a row belonging to
a temple nobody signed in as**, which is precisely the row a DML backfill would have missed.
`NotBoughtIngredientIT.theFlagIsConfinedByRls` drives the PATCH at another temple's ingredient over
HTTP and gets KMS-400030.

`RowLevelSecurityIT` (30 tests) and `TenantLoopMigrationIT` (1) were run unchanged and pass — see
the counts below. Nothing new to assert there, confirmed by running them rather than by reasoning.

## Where the shopping-list filter went, and what happens to each kind of line

`ingredientRefs()` (`ShoppingListService.java:698`) now reads the flag with the name and unit it
already read:

```java
jdbc.query("SELECT id, name, canonical_unit, is_not_bought FROM ingredients", rs -> {
```

and the filter is one named predicate in the merge loop of `suggestions()`, at
`ShoppingListService.java:463`, immediately below the live-order check:

```java
if (ref.notBought()) {
    continue;
}
```

**Why there and not in the query.** Filtering the rows out of `ingredientRefs()` would have been
one character shorter and worse: `refs.get(id) == null` already means "there is no such ingredient",
and making it quietly mean two things is how the next reader gets it wrong. It is also not a second
statement — that map is read once per page load and `ShoppingListStatementCountIT` exists because a
per-line read crept back in before, so the boolean rides along on the statement already being run.

**Why that loop and nowhere else.** It is the one place a line is born. All four routes onto the
list pass through it, so one predicate covers all four and a fifth stream added later is covered
without anybody remembering:

- **Meal-plan shortfall** — dropped. The demand is real; the answer to being short of water is a tap.
- **Below-threshold top-up** — dropped, same reasoning.
- **A closed order's undelivered balance** — dropped, and this is the one worth stating because
  money had already changed hands. The flag can be set *after* an order was raised, so a temple that
  bought bottled water last month and has since decided it never buys water gets no re-fed line for
  the balance. **The order itself is untouched** — it keeps its lines, its receipts and its history,
  asserted in `aClosedOrdersBalanceIsNotReFed` — and the audit trail says who marked the ingredient.
  Re-feeding it would ask the temple to chase a delivery of something it has just said it does not buy.
- **A line added by hand** — refused at `addLine` (`ShoppingListService.java:177`) before anything is
  written, because a picker is not a guard and a raw POST never meets the picker. A row added
  *before* the flag was set stays in `shopping_list_lines` and renders nothing, which is exactly what
  a live purchase order already does to a hand-added line, and it comes back by itself when the mark
  is cleared (`anExistingHandAddedLineDropsOutAndComesBack`).

**Out of the list entirely, never on it unticked** — an untick is already possible and is the thing
Rajeev's instruction rejects: it is a decision about one list, and in the meantime it is still a line
somebody has to read and think about.

**One thing I decided without a code and flag for you:** the refused hand-add answers
`KMS-400030 RESOURCE_NOT_FOUND` ("We couldn't find what you were looking for"), because the brief
says to mint no new error code. That is honest — the thing cannot be on a shopping list — but it is
not the sentence you would write. Without the guard the outcome is the same 404 by accident (insert,
derivation drops it, `added == null` throws, transaction rolls back), so the guard makes it
deliberate and writes nothing. Say the word and it gets a code of its own.

## The wording, and where it came from

Written with the installed `ux-writing` skill (purposeful / concise / conversational / clear;
sentence case; front-loaded; the button and label patterns). The same words on every screen, in one
exported constant each (`NOT_BOUGHT`, `NOT_BOUGHT_LABEL` in `IngredientFacts.tsx`), so a reword is
one edit:

| where | words |
|---|---|
| The mark, everywhere it is shown | **Not bought** |
| Detail page, facts row | label **Buying**; values **Not bought** / **Bought when needed** |
| Checkbox, create form and detail page | **Not bought (water, ice — never on a shopping list)** |
| Shopping-list picker hint, appended | **Anything marked "not bought" isn't here.** |

Two calls worth your eye. The checkbox says the **consequence** rather than restating the flag,
because what a person needs to predict is that the thing will never be suggested for buying again.
And I rejected a **Mark as bought** button for clearing it: on a procurement screen that reads as
"record that it has been bought", which is a different and expensive act. A checkbox has no such
pair.

**Colour:** both states are plain ink, neutral. Amber is low/wrong/overdue, red is act-now, green is
the success of the reader's own action; a temple that has decided it does not buy water has nothing
wrong with it. The Ekadashi cell beside it stays badged blue, which is that flag's own colour across
the product — a consistency argument, not a severity one, so it does not carry over.
