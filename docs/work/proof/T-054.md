# T-054 — Provisioning picks the temple from Places instead of geocoding a typed string

`/tenants/new` now uses the same autocomplete picker the planner's delivery address uses. The
operator names one building and the server answers with where that building is; the confirm step
stays, and confirms the *server's* address and coordinates rather than anything typed. The typed
latitude/longitude fallback is untouched. `PlacesController`'s three endpoints were widened from
`hasAuthority('MANAGE_MEAL_PLANS')` to `hasAnyAuthority('MANAGE_MEAL_PLANS','MANAGE_TENANTS')`.
`AddressLookup.tsx` and the `geocodeAddress`/`GeocodedAddress` pair in `lib/api.ts` are gone.

Coordinates only — no `placeId` is stored, no column, no migration, exactly as briefed. The
`place_id` is the *means* of getting an accurate coordinate; once the pin is captured its job is
done, and D-17 froze the coordinate deliberately, so an identifier whose purpose is later
re-resolution would be a column written and never read.

### The one prop added to `AddressPicker`, and why `MealComposer` is unaffected

`AddressPicker` is also imported by `components/planner/MealComposer.tsx`, which is **not** in my
contract, so its props could not change incompatibly. One **optional** prop was added:

```ts
inputProps?: InputHTMLAttributes<HTMLInputElement>;
```

It is spread onto the box *before* the component's own `value`, `onChange`, `role="combobox"` and
`aria-*` wiring, so nothing passed in can take the picker apart, and the class falls back to the
existing literal when the prop is absent:

```tsx
className={
  inputProps?.className ?? "min-h-touch w-full rounded-control border border-hairline px-3"
}
```

`MealComposer` passes nothing, so it renders byte-identically to before. It exists because
`/tenants/new` builds its fields with `<Field>`, whose render prop supplies the class every other
control on that form wears plus the `aria-invalid` / `aria-describedby` that wire the field's error
message to its input — without it the address box would be the only control on the page not wearing
the form's own styling, and a server-side "That address is too long." (`@Size(max = 500)` on
`ProvisionTenantRequest.address`) would be red text no screen reader announced. Declared here as the
contract requires.

### The one thing I decided rather than was told

The brief said to configure `PlacesIT` "through a test property source, the way `GeocodingIT` already
does". `GeocodingIT` does not use one — it uses `@Import`ed `@Primary` stub beans plus **direct
construction** of the `@ConditionalOnProperty` provider. I followed what the file actually does
rather than what the brief said it does, which reaches the same end (`application.yml` untouched)
with less machinery: a `@Primary` `StubPlaces` bean for the controller tests, and
`new GooglePlaceSuggestionProvider(...)` pointed at a loopback `HttpServer` for the parse test.

### Why "8 new tests, 3 failures" is not a hole — the counting rule

Three of the eight frontend tests assert an **absence**, and an absence passes vacuously once the
feature it guards is gone. Under FE-2 the survivors are exactly those three plus the two tests that
never touch the address at all:

- *"a place that cannot be resolved never becomes a confirmation"* asserts the panel is **not**
  there. FE-2 removes the panel in every case, so it passes — vacuously.
- *"a deployment with no Places key… is not told off"* asserts no lookup is made and no scolding text
  appears. FE-2 does not change the unkeyed path.
- *"never spends a lookup on two characters"* asserts `placeSuggestions` was **not** called.
- The slug/phone test and the duplicate-name test do not go near the address.

Where a test had to prove an absence rather than a presence I inspected the value rather than
matching a shape: `expect((screen.getByLabelText(/^latitude/i) as HTMLInputElement).value).toBe("")`
reads the actual value, and the "never from what was typed" assertions are
`expect(screen.queryByText(TYPED)).not.toBeInTheDocument()` on the literal typed string and on the
suggestion's own description — not an `objectContaining`, which cannot tell a missing property from
an explicit `false`.

## Acceptance criteria

**1. `/tenants/new` offers Places autocomplete; picking fills the coordinates from the server's
answer, never from what was typed.** — `AddressPicker` replaces `AddressLookup`; `onPick` fires only
from `api.resolvePlace`'s reply. The test types `"hare krishna"`, the suggestion row reads
`"ISKCON Sri Radha Krishna Temple, Hare Krishna Hill, Bengaluru"` and the server answers a **third,
different** string with `13.0098, 77.5511` — the test asserts the panel shows the server's string and
that neither the typed text nor the suggestion's description appears. Proved by FE-1 and FE-2 going
red, and on the server by BE-2's `expected:<ISKCON …> but was:<ChIJhare-krishna-hill>`.

**2. The typed latitude/longitude fallback still works and provisioning is never blocked; nothing
tells anybody off about a missing key.** — three tests: *"declining what came back leaves the
coordinates empty and the boxes typeable"*, *"a coordinate the operator would rather type wins over
the one that was picked"* and *"a deployment with no Places key gets the plain box it always had, and
is not told off"* (asserts `placeSuggestions` is never called, no `listbox`, and that no text matching
`/suggestion|not available|unavailable|no map/i` is on the page, then provisions with typed numbers).
A fourth — *"a place that cannot be resolved never becomes a confirmation, and blocks nothing"* —
covers a keyed deployment whose lookup fails: no panel, no `role="alert"`, no `KMS-` code, and the
form still provisions.

**3. `SUPER_ADMIN` reaches all three endpoints, `MANAGE_MEAL_PLANS` still does, someone with neither
does not.** — `superAdminMayAskSinceProvisioningPicksAPlace`, `kitchenManagerStillMayAsk`,
`volunteerIsRefused` (403 on all three **and** `places.asked()` empty, so a refused caller spends no
paid lookup), plus `anonymousIsRefused` (401). `KITCHEN_MANAGER` holds `MANAGE_MEAL_PLANS`
(`RolePermissionsTest.java:70`) and `VOLUNTEER` holds neither.

**4. `PlacesIT` exists and covers the parse, the 204, and the authorization change.** — 12 tests.
The parse runs the real `GooglePlaceSuggestionProvider` against a loopback `HttpServer` and covers:
Google's `suggestions[].placePrediction` shape including `structuredFormat`; a prediction with no
place id being skipped; the `X-Goog-Api-Key` staying server-side and the `X-Goog-FieldMask` being
sent; the request body's `input`/`includedRegionCodes`/`sessionToken`; the three-character floor; the
details reply's `displayName` prefix rule in both directions; a details reply with **no `location`**
returning empty (which is what stops Jackson's `asDouble()` default putting a temple at 0,0 in the
Gulf of Guinea); a 429 returning empty rather than raising; and an unkeyed provider calling nobody.
The 204 is covered twice — a place that cannot be resolved, and no provider configured at all.

**5. `AddressLookup.tsx`, the `api.ts` wrapper and the interface are gone with no live reference.** —
greps above; `tsc` exit 0.

**6. Both suites green.** — outputs above. `tsc` exit 0, the **full** frontend suite 1093/1093
across 98 files, `PlacesIT` 12/12. The full `npm test` was run once, at the work manager's request,
