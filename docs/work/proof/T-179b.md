## What BaseQuantityIT flagged

`noHandWrittenConversionRemains` fails on any `.java` file containing `CASE unit` or `CASE m.unit`. T-179's main query built the food half of a goods gift's description in SQL:

```
(SELECT string_agg(i.name || ', ' || trim_scale(m.quantity) || ' ' ||
        CASE m.unit WHEN 'KG' THEN 'Kg' WHEN 'GM' THEN 'gm' WHEN 'ML' THEN 'ml'
                    WHEN 'PIECES' THEN 'pieces' ELSE m.unit END,
        '; ' ORDER BY i.name) ...) AS food
```

What that produced, shown by the control below: `Coconut, 1 pieces; Milk, 1.5 L; Rice, 1500 Kg`.

A correction to the brief: `L` passing through `ELSE m.unit` prints "L", which is exactly `Unit.L`'s label. So the litre case was fragile, not visibly wrong. The visible defects were "1 pieces" and the missing Indian digit grouping.

## The Java replacement

- The `food` subquery and its CASE are gone from `candidates()`. The main query no longer touches units at all.
- `list()` first filters rows through `owns()`, exactly as before. It then passes the ids of the owned `IN_KIND` gifts to a new `foodGiven(ids)`. That makes one query: `stock_movements` joined to `ingredients`, with `reference_id = ANY(?)` and the same `DONATION` / `DONATION_IN_KIND` / `quantity > 0` filter, `ORDER BY i.name`. The uuid array is passed the same way `RecipeService` passes one.
- It returns the raw `name`, `quantity` and `unit`. Java writes each line as `name + ", " + Quantities.exact(quantity, unit)` and joins the lines with "; ".
- `toView` and `goodsDescription` take that string, so the wording is unchanged: "Rice, 25 Kg; Wet grinder".
- `requireOwnReceiptNumber` is unchanged, apart from no longer computing a description it never used.

**Privacy logic is unchanged.** Same candidate WHERE clause, same `owns()`, same `VerifiedContacts`, same 404. The food lookup runs only on gifts `owns()` has already accepted, so it cannot widen what anyone sees. It also carries the same explicit tenant predicate as the main query; RLS is still the boundary.

One slip, caught by the first run. My first javadoc quoted the old phrase literally, and `BaseQuantityIT` (a plain text search) went red on the fixed file. I reworded the comment, and a tree-wide grep now matches only `BaseQuantityIT.java` itself.

## Rounding rule and where it comes from

`Quantities.exact`, the ledger form, never rounded. Its TypeScript twin is `quantity()` in `frontend/lib/format.ts`. Both are held to one vector table by `QuantitiesTest` and `quantities.test.ts`.

Why not `Quantities.cooks`: a gift of goods is stock received. The same donation already shows as a `DONATION_IN_KIND` movement row on the inventory item screen, and that row is written with `quantity(m.quantity, m.unit)` (`app/inventory/[id]/page.tsx:570`). `Quantities`' own class comment lists goods receipts and movement rows under the exact form.

`exact` has three effects:
- it chooses the word through `Unit.label(BigDecimal)` with the figure as shown, so "1 piece" but "2 pieces"
- it promotes between gm and Kg, and between ml and L
- it groups digits en-IN, at up to 3 decimals

No donations screen or receipt prints a goods quantity anywhere else, so there was no other rule to match.
