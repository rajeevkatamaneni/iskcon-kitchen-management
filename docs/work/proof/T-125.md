## What was built, item by item

**1. The raw enum constant.** `TYPE_LABEL` was missing **three** constants, not two: `ISSUE` as well
as `RETURN_TO_VENDOR` and `USED_BEYOND_RECORDED_STOCK`. All three now have entries — "Issued",
"Sent back", "Used beyond the books". The three `TYPE_LABEL[x] ?? x` lookups (lines 504, 521, 638)
are now one function, `movementTypeLabel`, whose fallback humanises the constant
(`SPILLED_IN_TRANSIT` → "Spilled in transit") rather than printing it. Two of those three call sites
lower-case the result mid-sentence, so the labels were chosen to survive that.

The new test is `frontend/__tests__/movement-labels.test.tsx`. It reads `MovementType.java` and the
screen as text — `StockMovement.type` is `string` in `api.ts`, so no type-check can do it — and
asserts both directions: every constant has a label, and no label names a constant that does not
exist. Following T-104's proof, three of its six cases exist only to stop it passing vacuously: the
enum parse strips comments first (that file names its own constants a dozen times in javadoc), and
both parses are checked against known anchors and a minimum count, so a regex that matched nothing
cannot report success by comparing two empty sets. It also asserts the label map read is
`TYPE_LABEL` and not `REASON_LABEL`, which sits a few lines above it with the same shape. Two
further cases render the screen with all seven kinds and assert no stored constant appears anywhere
in the DOM — the defect as it was actually seen.

`app/inventory/[id]/page.tsx` is the only consumer of `api.listMovements` in the tree, so the Type
column is the whole surface.

**2. Zero in the wrong unit.** `render()` now picks the item's own unit when the value is zero, and
the step-down rule applies to everything else exactly as before. The em-dash rule above it is
untouched. `quantity(0, "L")` is `"0 L"`; `quantity(0, "KG")` is `"0 Kg"`.

**3. The receipt that never arrives.** The receipt card polls `api.donationReceipt` every 4 seconds
while `issued && !ready && !voided`, through a new `recheckDocument` prop so the poll re-reads the
document alone rather than the gift as well. It stops on the two conditions the brief asked for and
no third: it stops the moment the document is `READY`, and it does not run while the tab is hidden
(`visibilitychange`, both directions). `recheckDocument` is held in a ref and kept out of the effect
deps — the parent rebuilds that callback every render, so depending on it would tear down and
rebuild the interval several times a second.

**4. The banner that promised a thank-you.** The reachability test is the server's own, from
`DonationIntakeService.sendThankYou`: anonymous, or neither phone nor email. It is decided on the
record screen (the only place that has those values) and carried in the URL as `&thanked=no`
alongside the donor's name. The ledger now says one of three things, and the anonymous case is
decided from the empty name rather than the parameter, so a hand-edited URL cannot put the old
sentence back:

- reachable — unchanged: "It is in the ledger below, and a thank-you is on its way to the donor."
- named, no contact — "It is in the ledger below. No thank-you was sent: this gift carries no phone
  number and no email address, so anything the temple wants to say has to be said in person."
- anonymous — "It is in the ledger below. No thank-you was sent, because an anonymous gift leaves
  nobody to send one to."

I did **not** reproduce this on staging — see "Not done" below. It was reproduced in the tests
instead: with the fix patched out, the two new cases fail on the old sentence being present.

**5. The duplicate-invoice warning.** `countByVendorAndNumber` now carries `AND status <> 'VOIDED'`.
Read the T-073 row first, as instructed; the ruling is Question 1 only, and Question 2 (donor
history) is already built and is not touched here. The invoice still saves either way — this is the
flag on `RecordInvoiceResponse`, never a block, and the javadoc on both the method and the record
now says so. Nothing on staging was touched; `VERIFY-T068` was not read, written or tidied.

### Three things the control got wrong first, recorded rather than dropped

The protocol asks for these to be written down rather than quietly re-run, so:

**Leg 1 truncated its own evidence.** The gradle leg was piped through `tail -45`. The summary said
`Failed: 2` and only **one** `FAILED` line survived into the log — the other was above the window.
A reader would have been left to take the second failure on trust. **Leg 2** re-runs the backend
control alone with nothing truncated, and both failures are named above.

**Leg 1's "the tree changed" proof was the wrong baseline, and would have looked identical had the
patch matched nothing.** It used `git diff` against `HEAD`. For a control that patches a fix *back
out*, that is exactly wrong: reverting the invoice SQL restores it to what `HEAD` already holds, so
the diff correctly showed nothing for the one line that mattered. **Leg 3c** re-applies the identical
patch and diffs against a copy of the *verified working tree* instead, printing the real before/after
for all six files. What actually carried condition 3 in legs 1 and 2 was the other guard — the patch
step asserts each anchor matches exactly once and exits non-zero otherwise under `set -e` — and the
observable flip of two tests from PASSED to FAILED on the identical command. That is sound, but the
`git diff` line was not evidence and should not be read as any.

**Leg 3 printed a false "NO CHANGE — the patch did not apply to this file" after every diff it had
just correctly printed.** `diff` exits 1 when files differ and `set -o pipefail` promoted that to the
pipeline's status, so the `|| echo` branch fired every time. Left alone it would have been a *false
red* in an artefact — the failure mode wave 7b's T-069 warns is worse than a false green, because it
looks like the control working. Leg 3b was a second try that broke on an apostrophe inside a
single-quoted `printf` and silently skipped its own patch step, which is how the mistake was caught:
it reported NO CHANGE for all six files, correctly, because nothing had been patched. Leg 3c is the
correct run. **All three legs are in the log in the order they happened.**
