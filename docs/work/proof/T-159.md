## Part 3 first: why `templatesSubmittedAt` was null

**Cause, proven: the write landed and the read threw it away.** `read()` used `queryForMap`, which asks the PostgreSQL driver for each column with a plain `getObject(int)`. For `timestamptz` the driver answers `java.sql.Timestamp`. The old `instant()` accepted only `OffsetDateTime` and returned null for anything else. So **all three dates on the WhatsApp settings answer** (`verifiedAt`, `webhookSeenAt`, `templatesSubmittedAt`) have read null for every temple since the feature was written (ccc9635, 2026-08-16), whatever the table held. The transaction, `app.tenant_id` and the pool were never involved. The cause is inside `notification/`, not `tenancy/`.

The payment settings service beside it, written a day earlier, already accepts both types, with the comment "A timestamptz comes back as one of two types depending on the driver's mood". The WhatsApp one copied only half of that.

**Prediction the main session can check on staging without a database:** in the same GET that returned `templatesSubmittedAt: null`, `verifiedAt` was null too, and the Settings screen has never shown "Last checked …" for WhatsApp.

**Evidence, from `WhatsAppTemplateSubmissionIT`:**
- The service is wrapped in the application's own `TransactionInterceptor`, so it runs in one transaction on one connection as it does on staging. The test asserts `TransactionSynchronizationManager.isActualTransactionActive()` was true while Meta was being called.
- After a save where Meta refuses the six staging refusals and accepts the rest, `whatsapp_templates_submitted_at`, read straight from `tenant_settings` through the context's `JdbcTemplate` (the unprivileged `kms_app` role, under RLS, with no WHERE of our own), **is set**. That assertion passed on the unfixed code.
- The GET through the controller then answered null. That is staging's symptom, reproduced.
- A pinning test asserts `queryForMap(...)` hands back a `java.sql.Timestamp` for that column. That is the explanation, tested.

I did not need to reproduce the 64-second elapsed time. An instant stub reproduced the symptom, and the table read shows the write was never lost.

## The rules test (`MetaTemplateRulesTest`)

It runs over every `NotificationTemplate`. Its sources:

**(a) Not only parameters, no more than two newlines in a row, no more than 10 emoji.** Source: Meta's own staging refusal of `temple_communication`, quoted in the brief. Meta's review page says only that "The number of emojis allowed in the body component may also be limited". Emoji are counted with Java 21's `\p{IsExtended_Pictographic}`, and a test checks that digits, `₹` and `—` are not counted.

**(b) No variable at the start or end.** Source: Meta's review page, https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-review, which says: "The message template cannot start or end with a parameter (dangling parameters are not allowed)." Staging's `low_stock_digest` refusal said the same. Meta does not say whether `{{3}}.` counts as the end, so the test treats trailing punctuation as the end. That is the conservative choice.

**(c) Length per variable.** **Meta publishes no threshold.** Its review page says only "too many variable parameters relative to the message length". The components page, https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/components, gives just "Maximum of 1024 characters", and the template management guide says nothing on it.

Two messaging providers publish a figure they found by testing, neither citing Meta: words plus parameters must be at least 3n + 1. Sources: Syniverse, https://sdcsupport.syniverse.com/hc/en-us/articles/30569685832471-How-to-avoid-too-many-parameters-rejection-in-WhatsApp-Templates, and Mercuri, https://docs.mercuri.cx/features/templates/whatsapp-templates/whatsapp-template-minimum-words-parameters-ratio.

I checked that figure against staging:
- It refuses exactly the four Meta refused for length.
- It passes all fourteen Meta accepted. `low_stock_digest` sits exactly on the line, and Meta did not complain about its length.

Two tests pin that calibration: `stagingOutcomes` and `acceptedOnStagingPassTheRatio`.

**My margin: at least 3 fixed words per variable**, which means words plus parameters of at least 4n. It is a round rule a person can apply while writing, and it is stricter than the published figure. Every template Meta accepted already meets it, so no approved template needed rewording. A "word" is a run of non-space characters containing a letter or digit, counted with the placeholders removed.

## Part 2: the connection test message

- **New name:** `whatsapp_connection_check`. The enum constant is still `WHATSAPP_TEST`. The category is UTILITY, as before.
- **New wording:** "Connection check for {{1}}: this WhatsApp number can send messages. A temple administrator asked for this check in the app's settings, and no reply is needed."
- **Old wording:** "Hare Krishna. This is a test message from {{1}}. If it has reached you, the temple can send WhatsApp messages."

What read as marketing: Meta's categorization guide says a template whose "contents are unclear" is categorized as marketing, and that a utility template must be "specific to or requested by the user" or "essential or critical to the user". A greeting followed by "this is a test message" states no specific fact and no request. The new wording states the one fact confirmed and who asked for it. Source: https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-categorization.

What Meta's documentation says:
- **Edit while in review: no.** "Only templates with an APPROVED, REJECTED, or PAUSED status can be edited." Source: https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-management
- **Change the category once approved: no.** "You cannot edit the category of an approved template." Same page.
- **What review will do with it:** "If you selected UTILITY as the template's category and WhatsApp determined it should be MARKETING, the template is approved as MARKETING." A review can be requested within 60 days. Source: the categorization page above.
- **Reusing the name:** "If you delete an approved template, you cannot create a new template with the same name for 30 days." Source: the template management page. Separately, our Save treats "already exists" as done, so a new body under `connection_test` would never reach Meta.
- **So a new name is required.** The old `connection_test` stays in each temple's Meta account, unused, until someone deletes it in Meta's manager. Nothing sends it.

Editing does have an endpoint: `POST /{TEMPLATE_ID}`, limited to "10 times in a 30-day window, or 1 time in a 24-hour window", and only for APPROVED, REJECTED or PAUSED templates. It needs the template's id, which we never store or look up. So it is not a one-call fix, and I did not build it.

`WhatsAppTestSendIT` passes with the new name, 8 of 8.

## Part 4: refusals stored

**Migration `V128`.** It adds `tenant_settings.whatsapp_refused_templates JSONB NOT NULL DEFAULT '[]'`, plus a CHECK that the value is an array. It is DDL only, with no backfill: the constant default rewrites no rows. The table already has RLS since V36, so no new policy is needed.

**Written on every save.** The whole list is replaced by an unconditional UPDATE in `submitTemplates`, so a clean save leaves `[]`.
- Refused templates get a plain sentence chosen from Meta's phrase. Meta's own text goes to the log only.
- A template Meta could not be reached for is also stored, with "Meta could not be reached … Press Save to try again." To an admin the consequence is the same.

**View.** `TenantWhatsAppSettings.refusedTemplates` is a `List<RefusedTemplate(name, reason)>`, and never null. `api.ts` is not touched.

**Reasons stored:**
- "too many variable" → "Meta found too little fixed wording around the details the app fills in. This needs a change to the app, not to your WhatsApp account."
- "start or end" → "Meta will not accept a message that begins or ends with a detail the app fills in. This needs a change to the app, not to your WhatsApp account."
- newline, only parameters or emoji → "Meta found no fixed wording of its own, too many blank lines or too many emoji. This needs a change to the app, not to your WhatsApp account."
- anything else → "Meta did not accept this message. Press Save to try again, and if it is refused again, report it with the message name shown here."
