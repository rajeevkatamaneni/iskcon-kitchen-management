### The missing `type` — the mechanism, and how many others there are

Spelled out because it is a defect **class**, not one button.

**The mechanism.** HTML's default for `<button>` is `type="submit"`. A `<button>` written inside a
`<form>` with no `type` is therefore a submit button, whatever its label says and whatever its
`onClick` does. On this screen the Remove button sat inside `<form onSubmit={saveLines}>` with an
`onClick` that filtered the line out of `draftLines` and no `preventDefault`. So one press did two
things:

1. `onClick` ran and queued a state update removing the line;
2. the form submitted, running `saveLines` — **in the same event, before React had applied that
   update**, so `saveLines` read the *old* `draftLines`.

The order was saved to the server with the removed line still on it. The row then vanished from the
screen on the re-render, so it looked like it had worked. It had not: the next load brought the line
back. Nothing threw, nothing logged, and every test in the suite was green over it — the existing
test only asserted the button was *disabled* on a one-line draft, which is the one case where
pressing it does nothing at all.

**The sweep, over the files this task touched.** Every `<button>` and every `<Button>` counted, with
JS/JSX comments stripped first (one of my own new comments contains the words "`<button>` inside a
`<form>`" and a naive scan reads it as a form):

| File | `<form>`s | buttons | inside a form | **typeless inside a form** | typeless outside |
|---|---|---|---|---|---|
| `frontend/app/orders/[id]/page.tsx` | 5 | 17 | 8 | **0** | 1 |
| `frontend/app/orders/new/lines/page.tsx` | 1 | 4 | 1 | **0** | 0 |

**Zero remain**, after fixing the one. The single typeless button left is `<Button variant="secondary">
Return to vendor</Button>` at `frontend/app/orders/[id]/page.tsx:986`, and it is **harmless**: it
sits in the deliveries table between the form that closes at line 890 and the one that opens at
1018, so it is inside no form and there is nothing for its default `submit` to submit. I left it
alone — it is not a bug, and changing it would be noise.

The test files in my contract render no JSX buttons of their own, so there is nothing to count
there.

**Worth knowing for the wider sweep:** `components/ds/Button.tsx` does **not** default the `type`.
It spreads `...rest` onto a bare `<button>`, so every caller that omits `type` inherits HTML's
submit default. That is the reason this class exists at all, and one line in that component would
close it everywhere at once — but `components/ds/Button.tsx` is outside my contract and is read by
most of the application, so I have not touched it. Naming it here for whoever runs the sweep.

WhatsApp message has gone out — and on a temple that uses WhatsApp *only* for purchase orders, no
message ever goes out, so the button never appears. It is not fatal: shift reminders, broadcasts and

WhatsApp earns the button within a day. But a brand-new temple that has connected WhatsApp and sent
nothing sees a settings screen saying "connected" and a purchase order with no WhatsApp button, and
nothing on either screen explains the gap.

The fix is for the Test button on the WhatsApp settings screen to *send a real message* instead of
reading the number's description — that stamps the column honestly, gives an administrator a way to
prove the connection, and makes the gap self-closing.

when Rajeev was told the button should appear only after a real send, **he asked whether a test-send
