# T-081 — a wish-list gift that no longer fully fits is split, not diverted whole

A ₹14,000 grinder given ₹10,000 by one devotee and then ₹14,000 by a second, while the first is
still landing, now puts **₹4,000 into the grinder — finishing it — and ₹10,000 into general funds**,
in **one donation row**, and tells the donor exactly that. It used to divert the whole ₹14,000 and
leave the grinder ₹4,000 short.

- **"only ₹4,000 of it was still needed there"** rather than your "we were only able to apply ₹4,000".

  the only thing to swap.
- **"that is not second best"** is the load-bearing sentence for point 3 and the one most likely to
  read as too blunt to you. The alternative was to leave it implied; I judged implied was exactly
  how it would come across as a consolation prize.

## The schema, and why I would be content to live with it

`V113__a_gift_that_no_longer_fits_is_split.sql` adds **one nullable column** to `donations`:

```sql
ALTER TABLE donations
    ADD COLUMN wishlist_applied_inr NUMERIC(12, 2),
    ADD CONSTRAINT donations_wishlist_split_shape CHECK (
        wishlist_applied_inr IS NULL
        OR (amount_inr IS NOT NULL
            AND wishlist_applied_inr > 0
            AND wishlist_applied_inr < amount_inr));
```

**`amount_inr` keeps its meaning exactly: what the donor paid, in one payment.** That is the whole
design. Everything that reads a donation *as a payment* — the Form 10BD dataset, the period tiles,
the ledger amount, and **T-020's 80G receipt when it is built** — is untouched and correct, because
one card payment is still one row with one total. T-020 reads `amount_inr` and gets ₹14,000, which
is what the donor is entitled to deduct and what the tax authority expects to see against that
payment reference. If T-020 wants to *describe* the split it reads one more column and subtracts;
if it does not, it produces a correct document knowing nothing about any of this.

**Three states, one representation each** — the strict bounds in the CHECK are what buy that:

| `wishlist_item_id` | `wishlist_applied_inr` | what the row says |
|---|---|---|
| NULL | NULL | a general gift, or one wholly converted because the item was already paid for |
| set | NULL | the whole gift went to that item |
| set | X, `0 < X < amount_inr` | X to that item, `amount_inr − X` to general funds |

`X = amount_inr` is not a split, it is row 2 and must be written NULL; `X = 0` is not a split, it is
row 1. A shape that can state one fact two ways is a shape whose sums eventually disagree.

**What I considered and rejected:**

- **Two rows sharing one payment.** Your ruling, and I agree with the reason: one payment, one 80G
  receipt, and an accountant reconciling a bank statement should not find two rows against one
  payment reference and have to know to pair them.
- **Making the column NOT NULL for every earmarked gift** (so no `COALESCE` anywhere, and a writer
  that forgets it fails loudly). I wanted this — the repo's worst recurring bug is a silently wrong
  `SUM` — and dropped it on two grounds. It needs a per-tenant RLS backfill of live rows for no
  behavioural gain; and worse, the row is **written PENDING, before anyone knows how much will be
  applied**, so a NOT NULL column would have to be filled with a provisional lie at insert time. A
  column named "how much was applied" holding a number for a payment that has not settled is exactly
  the sort of thing that gets summed by someone in a year's time.
- **Naming the column for the diverted half** (`general_fund_inr`) instead. Rejected because the
  *applied* half is the quantity that gets summed (the wish-list progress figure); the general half
  is summed nowhere, since "general" means "not earmarked". Store the number you sum.

**Deliberately not in the CHECK: `AND wishlist_item_id IS NOT NULL`.** V41:43 declares that FK
`ON DELETE SET NULL`, so deleting a wish-list item nulls the earmark on every gift towards it — and
with that clause the delete would fail on a constraint about *donations*, which is a baffling way to
tell a temple it may not delete an item. Left off, an orphaned applied amount is inert: every sum is
keyed on `wishlist_item_id = i.id`, so it counts towards nothing.

**No backfill.** NULL already means "the whole gift went to the item", which is true of every
existing row by construction — no other outcome could be recorded before V113. Same argument V104
made for `voided_at`, and it avoids a cross-tenant `UPDATE` that under RLS matches nothing and
reports success.

### Who already sums this table — asked before writing, per README lesson 1

Three sums meant "money towards the item" and all three now read
`COALESCE(wishlist_applied_inr, amount_inr)`:

1. `WishlistService` `paid_inr` — the progress bar and the remaining figure;
2. `WishlistService.markFulfilledIfComplete` — whether the item is bought;
3. `MonetaryDonationService.completedAmount` — the checkout cap **and** the capture-time decision
   this task exists for.

Everything else that sums `donations` sums whole payments (period tiles, Form 10BD, ledger totals)
and is correct unchanged.

### The race

Untouched and still the mechanism: `settle()` runs in one transaction opened after the tenant is
set, and the room-left read takes `SELECT … FROM wishlist_items WHERE id = ? FOR UPDATE`. Two
payments landing at once are serialised on that row lock, so the second reads a figure that already
includes the first. What changed is only that the read now returns **how much** is owed instead of a
boolean "does it fit" — the boolean was the defect, because it threw away the one number the answer
needed. `WishlistContributionIT` drives both payments through the real webhook endpoint.

## What happens when a split gift is voided — and it is not ambiguous

**A void strikes the whole row, and the item loses exactly the ₹4,000 that reached it.** Not the
₹14,000 that was charged, and not nothing.

I looked for the ambiguity you were right to expect and it is not there, because **the unit of a
void is the payment**: there is no way to strike half a card charge, and `DonationVoidService` marks
one row. The ₹10,000 in general funds was never counted towards the item, so nothing has to be
decided about it — every wish-list sum already carries `voided_at IS NULL` and drops the whole row,
which removes exactly the applied ₹4,000. `wishlist_applied_inr` itself is left in place: it is a
record of what happened, and V104's argument is that a struck row stays readable rather than being
rewritten.

Test: *"striking a split gift takes back the part that reached the item, and only that part"* —
₹14,000 on the giving page before the strike, ₹10,000 after, and the split column still reading
₹4,000.

One pre-existing wrinkle this does **not** fix and does not make worse: an item already flipped
FULFILLED does not un-flip when a gift behind it is struck (`WishlistSponsorshipIT`'s
*"an already FULFILLED item stays closed to giving"*, left to you in T-069). A voided split gift
behaves the same way as a voided whole one there.

## Not done / needs Rajeev

- **The copy is yours to judge.** It is quoted in full at the top. The two clauses I would expect
  you to want to move are named there.
- **The message is not smoke-tested by hand.** Commandment 5 wants a user-facing surface driven in a
  browser, and this one cannot be: it only fires when two payments land against the same item within
  the same window, which needs two real gateway captures on a deployed environment, and Mailgun's
  sandbox on UAT only delivers to pre-authorised addresses anyway. What is proven is that the message
  is queued with the right template and the right stored figures, and that rendering those figures
  produces the text above. **Somebody should read it on a real phone before a temple does.**
- **The Meta WhatsApp template `wishlist_gift_split` is not registered.** Six parameters, sample
  values supplied in `whatsappExampleValues()`. Until Meta approves it, a WhatsApp send of this
  message fails as an unapproved template and cascades to SMS — which renders the same body locally,
  so the donor is still told, just not on WhatsApp. Same situation `PO_DELIVERY` documents.
- **Hand-recorded cash can still over-fund an item.** `DonationRecorder` writes a cash gift against
  a wish-list item with no cap and no split — a staff member entering ₹14,000 against a grinder that
  is owed ₹4,000 records all ₹14,000 against it. That was true before this task and is unchanged by
  it; T-081 is about the online race. It is a real hole and probably wants its own row.
- **`git` reports this checkout clean under the sandbox.** See the deviation note above. Nothing to
  fix here, but the release agent should not trust a clean `git status` from this session.
