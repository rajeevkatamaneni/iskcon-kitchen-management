## What was built, and why in this shape

**Step one asks one question.** `FocusScreen`, a native `<select>` of vendors, an "Add a vendor"
`ButtonLink` beside it, `[Cancel] [Continue]` in the header. Choosing pushes to
`/orders/new/lines?vendor=<id>`, so step two is linkable and survives a reload. D-7's premise — that
routing out to `/vendors/new` costs nothing — is asserted rather than assumed: a test fails the
moment a second field appears on that screen.

**Step two is the lines**, needed-by, deliver-to and notes. A line is an ingredient from the
catalogue **or** a description of something that is not in it (T-024), never both, because the two
adders are separate controls with separate buttons. Every line sends both `ingredientId` and
`description` explicitly, one of them null, which is what keeps the server's KMS-400128 from firing
on an omitted-optional-field `undefined`.

**Three server rules the form respects.**

1. `neededBy` earlier than today (`NEEDED_BY_BEFORE_ORDER_DATE`) — the date box carries
   `min={todayIso()}`, so the browser refuses it first, and the same refusal is said in words for
   anything that gets past the box. `todayIso()` is the temple's day, which is the clock
   `PurchaseOrderService` measures against.
2. `requireVendor` accepts an **inactive** vendor, so the picker must not offer one. It asks
   `api.listVendors(true, …)` — active-only — and the lines screen re-resolves the id from that same
   list, so a vendor typed into the address bar, or dropped between the two screens, lands on "No
   vendor chosen" with a link back to the question rather than on a form.
3. The inverted flag: `listVendors(true)` is active-only and `listVendors(false)` asks for the
   inactive ones as well. A test asserts the argument, not the rendering, because the rendering
   looks identical either way.

**The flash on `/orders`** is the `/vendors/new` → `/vendors` pair copied line for line —
`useSearchParams`, a `useRef` guard, `setFlash`, `router.replace` to strip the parameter, an
`InlineNotice`, and a `<Suspense>` boundary around the view.

## The negative control — the ref guard

The guard is the thing this codebase has actually got wrong before, so it is what the control
removes: the two lines of `captured` come out of the flash effect in `app/orders/page.tsx`, and the
tests are run **as written**, unmodified.

`scratchpad/negative-control.sh`, and the three conditions it had to meet:

- **The restore is trapped, not trusted** — `trap restore EXIT INT TERM`, restoring from a `mktemp`
  copy taken before anything was edited, so a death mid-control cannot leave the tree broken for the
  three other builders in this checkout.
- **The patch step fails loudly** — `set -euo pipefail`, and the edit is a python `assert old in s`,
  so a patch that matched nothing aborts the script instead of reporting a green that controlled
  nothing (which is what wave 5-2's first control did).
- **The tree is shown to have changed** before anything is run against it.


**Read the `git diff --stat` honestly:** the file is uncommitted, so that stat is this whole task's

stronger things stand behind it: the `assert` above would have aborted the run had the guard not
been where the script expected, and the behaviour changed unmistakably — **the same 13 tests that
pass in 200ms with the guard never finished at all without it.** `ps` during the run showed the
worker at 104% CPU with memory climbing 4.3% → 4.9% → 6.1% of the machine: the effect re-running on
every render, each run setting a fresh flash object and causing the next. That is the shape this
project's own memory records as OOM-looping vitest, and it is why the assertion in the test is
`replaceMock` having been called exactly once rather than anything about the banner, which looks
identical either way.

## Not done, deviated, or needs Rajeev

1. **`frontend/__tests__/orders.test.tsx` is red and I did not fix it — it is outside my contract.**
   `/orders` now calls `useSearchParams`, and that file's `next/navigation` mock (line 16) supplies
   only `useRouter`. Three tests fail on the mock, not on behaviour. The whole fix is one line:

   ```
   vi.mock("next/navigation", () => ({
     useRouter: () => ({ replace: vi.fn(), push: vi.fn() }),
     useSearchParams: () => new URLSearchParams(),     // ← add this
   }));
   ```

   `vendors.test.tsx` already carries exactly that line for exactly this reason. **This must be
   applied by whoever holds that file before the tree is merged**, or CI goes red.

2. **"Comes back with the new vendor selected" is not built, and cannot be from inside this
   contract.** `/vendors/new` ends with `router.push("/vendors?added=…")` unconditionally, so the
   return leg needs one line in a file this task may not open — and the obvious mechanism, a
   `returnTo` parameter, is the very thing D-7 rejected as an invention. What is built is the half
   D-7 argued actually matters: leaving costs nothing, and the new vendor is in the picker when you
   come back to `/orders/new`. Selecting it automatically would need either that one line in
   `/vendors/new` (`?then=order` → push to `/orders/new?vendor=<id>`) or a decision from Rajeev that
   a `returnTo` is worth having after all. **Neither taken here.**

3. **Deviation from the vendors flash, deliberately: the confirmation on `/orders` does not
   auto-dismiss, and it carries a link.** `/vendors` uses `autoDismiss`. This one does not, because
   `InlineNotice`'s own rule is that a notice fades only when there is nothing left in it to act on
   — and a purchase order is a DRAFT until somebody sends it, which happens on `/orders/[id]`. So
   the banner stands and offers "Open the order", which is also how "lands on it" was honoured
   without abandoning the flash the task asked for. The mechanism is copied exactly; the
   presentation is this one judgement. Reversible in two lines if it is the wrong call.

4. **`AddLine` is now written twice** — here and in `/orders/[id]/page.tsx`, about sixty lines.
   Sharing it means a new file under `components/`, which is outside this contract, and `[id]` is
   explicitly forbidden to this task. It is a real extraction for whoever next holds both files.

5. `deliveryLocation` and `notes` are plain single-line inputs at the server's `@Size` limits (300
   and 1000). A textarea for notes would be kinder and is not what the surrounding screens do.
