## Did this need a schema change? No — and here is the justification, because the brief asked for one

**The boolean already carries this information exactly, and Rajeev asked for a menu item.** A menu
item is a fact about navigation. Turning `is_supply` into a type or an enum would have been a
migration whose only content is `CASE is_supply WHEN true THEN 'SUPPLY' ELSE 'FOOD' END` — a rewrite
of every row in `ingredients` in every tenant, under RLS, per tenant, to end up knowing precisely
what the column already knows. Four reasons it would have been worse, not just larger:

1. **It rewrites rows it should not touch.** The brief's own third acceptance criterion asks for an
   existing supply-marked ingredient to appear on the new screen "without a migration that rewrites
   rows it should not touch". The strongest possible form of that is **no migration at all**, which
   is what this is.
2. **V99 already argued the shape and nothing in the ruling reopens it.** V99 rejected a parallel
   `supply_items` table because a leaf plate is bought, received, stored, issued and reordered
   exactly as rice is, and a second table duplicates the whole inventory chain to express one
   boolean. Rajeev's ruling changes where a person *goes*, not what a supply *is*.
3. **A two-valued enum is a boolean with ceremony**, and this repo has a fresh scar from exactly the
   opposite direction: V91 removed equipment's three-value `category` four days ago because a closed
   vocabulary the temple cannot extend "has to be either complete or wrong". A third value is not
   coming — the third thing (equipment) already has its own table.
4. **It would have forced `frontend/lib/api.ts`**, which is reserved and was not allocated to me. The
   design that fits the contract is also the smaller one, which is a good sign rather than a
   coincidence.

So the split is **two screens over one endpoint**: `/ingredients` takes `!supply`, `/supplies` takes
`supply`. Both filter on the client, which is not a shortcut — it is what `/equipment` already does
with its three filters and what `/ingredients` already did with `libraryDerived`, and it is required
here: **every other picker in the app must keep offering supplies**, so a server-side split would
have had to be undone in five places to get back to where D-1 already is.

**`V116` was reserved and is NOT used. It should go back to the pool.** Staging is on V114 and T-087
holds V115; I added no migration file, so nothing of mine can collide with either.

**No new error code and no new permission.** Nothing here can fail in a new way — the screens call
`GET /api/v1/ingredients`, `POST /api/v1/ingredients` and `PUT /api/v1/ingredients/{id}`, all of
which already have their codes. And D-1's argument against a permission stands: saying a thing is a
mop is a fact about the thing, not the religious ruling `MANAGE_DIETARY_POLICY` guards, so anybody
who may catalogue rice may catalogue soap.

## The Equipment second tier — NOT built, and why. This is the part to read.

**Equipment servicing already exists.** V87 (2026-09-04) built it: `equipment_services` append-only,
`service_interval_days` + `service_interval_unit`, `tenant_settings.equipment_service_warning_days`,
a derived `ServiceStatus`, and `/equipment` (E3-S11) with Overdue / Due soon filters and a Today
nudge that links into them.

**The harm the ruling names is already prevented today.** `ServiceStatus.NOT_SCHEDULED` is
documented as *"No interval, or no date to count from, or scrapped. Reads 'not scheduled' and
appears in no warning count — a machine nobody has decided about is not a machine that is late
(D6)."* Sixty plastic stools with no interval are already invisible to the servicing view: not in
Overdue, not in Due soon, not in the Today count. **The servicing view already stays about the mixer
and the boiler.**

**What the tier would genuinely add** is a different and narrower thing than the ruling's stated
motive: today, *"nobody has set an interval yet"* and *"this will never need servicing"* are the
same state. With sixty stools in the register, an admin auditing which machines still need an
interval set cannot tell the boiler nobody got round to from the stool that never needs one. That is
real. It is not what the ruling says it is for, and it is not urgent.

**Three reasons I stopped rather than half-building it**, in the order that decides it:

1. **It cannot be done inside my contract.** `EquipmentServiceStatus` is a union type in
   `frontend/lib/api.ts`, and a `NOT_SERVICED` state has to be added there, along with `serviced` on
   `EquipmentView`, `CreateEquipmentInput` and `UpdateEquipmentInput`. **`frontend/lib/api.ts` is
   RESERVED and no reservation for it was allocated to me.** That is decisive on its own; widening
   the contract myself is the one thing the brief forbids.
2. **It adds a state to a derived enum with ten readers** — `EquipmentService`, `EquipmentController`,
   `EquipmentView`, **`TodayService`** (which counts overdue for the dashboard), `EquipmentServicingIT`,
   `ServiceIntervalTest`, and on the client `app/equipment/page.tsx`, `components/EquipmentWords.tsx`,
   `lib/api.ts`, `__tests__/equipment.test.tsx`. This repo's own standing lesson is that a new state
   goes on compiling perfectly while an aggregate somewhere else quietly changes meaning, and
   `TodayService` is exactly such an aggregate.
3. **There is a live design argument to put to Rajeev first, not to settle in a builder.** **V91
   removed equipment's `category` on 2026-09-04**, in his words, because a closed vocabulary the
   temple cannot extend "has to be either complete or wrong" and "people will come up with weird
   shit they want us to add and it will never end". A two-value tier is a closed vocabulary on the
   same table, four days later. I think it survives that objection — it answers one operational
   question rather than classifying a thing — but he is the one who threw the last one out, and he
   should hear the parallel before it is built rather than after.

**What I would dispatch it as**, with the design already done so the next builder need not rediscover it:

- **`serviced BOOLEAN` nullable**, not `NOT NULL DEFAULT`. `NULL` = nobody has said, which is the
  true state of every existing row and reaches them by DDL alone with no backfill and no per-tenant
  loop — V99's shape, and the reason it is right here is the same. `FALSE` = owned, not serviced.
  `TRUE` = serviced, and an interval is then expected. A `NOT NULL DEFAULT` in either direction makes
  every existing row claim an answer nobody gave.
- **`ServiceStatus.NOT_SERVICED`** beside `NOT_SCHEDULED`, so the two states stop being one word.
- **Reservations it needs:** `frontend/lib/api.ts` (four edits, listed above) and **a migration
  version — `V116` is free, since I did not use it.**
