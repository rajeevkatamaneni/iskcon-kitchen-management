# T-155 — The planner's "Ask for volunteers" opens the real shift form in a layer

## What was built

**The layer now renders `ShiftFields`, the volunteers' own form, not a copy.** `ShiftLayer.tsx`
imports `ShiftFields`, `SHIFT_FORM` and `readShiftForm` from `app/volunteers/shift-form.tsx`, the
same three things `/volunteers/new` and `/volunteers/[id]/edit` use. T-019's three-field form and
its "Location, notes and reminders" link are gone.

The layer copies the volunteers screen's header: the task as heading ("Post a shift" or "Edit a
shift"), one line under it ("For Lunch · Tuesday, 1 September 2026"), and `[Cancel] [Post shift]`
or `[Cancel] [Save changes]` top right. The commit button reaches the form with `form="shift-form"`,
as on the screen, and there is no second copy at the foot. Escape closes it and a backdrop click does
not, as before. Width is `max-w-prose` (40rem), the same as the old layer.

- **New shift:** the form opens on the derived title, the planner's date, capacity = shortfall
  (floored at 1) and end time = the meal's ready-by, as T-019 did. Start, location and description
  are empty, and reminders are "24", the form's own default.
- **Save:** `readShiftForm(form)` plus `mealDate`, `mealKind` and `mealEventName`, sent on both
  create **and** update. That matters: `ShiftMealLinkIT.anEditCanUnlinkAShift` shows an update
  without the link takes it off. The layer closes and the day's nonce bumps, so the crew and shift
  lists re-read. Nothing navigates.
- **After saving,** the button disappears because a linked shift now exists, and the shift shows as
  `ShiftPebble` ("0 of 3 signed up"). **I kept `ShiftPebble` rather than adding a link**: it already
  was a button that opens the shift, and it carries the sign-up figure. The one change is
  `aria-haspopup="dialog"` (also added to "Ask for volunteers"). Pressing it opens the same layer on
  the full form, as an edit.
- **An existing shift** linked to the meal shows the same way, instead of the button, full or not.
  "Covers" means linked to the meal (D-14), not overlapping it by the clock, as T-019 had it.
- **Kept:** `canRaiseShift` (admin, manager, kitchen staff) and `readOnly` both still hide the
  button and make the pebble plain text.

## The three defects

1. **Next day.** Fixed by reusing the form. For 20:00 → 02:00 the layer now shows the form's line
   "Ends the next day — this shift runs through midnight". I did not change that wording to add the
   literal "(next day)", which is `shiftWindow`'s wording for a read-only time range. The test
   asserts the form's line.
2. **Button on a full meal.** New rule: `canRaiseShift && !readOnly && shifts.length === 0 &&
   shortOfCrew(meal.crewRequired, crew)`. `shortOfCrew` is `required != null && (crew?.rostered ?? 0)
   < required`, now a single function that `CrewPebble` also calls for its warning tone, so the
   button and the number cannot disagree. "6 of 6" shows no button, and "7 of 8" does.
3. **Label.** `ShiftFields` now takes a required `editing: boolean`, separate from `shift`, which now
   means "what the boxes open on" (type `ShiftFormValues`, which a `ShiftView` still fits). The label
   is `editing ? "Edit a shift" : "Post a shift"`. `new/page.tsx` passes `editing={false}`,
   `[id]/edit/page.tsx` passes `editing`, and the layer passes `editing={shift !== null}`. Required
   so no caller can forget. Those two page lines are the only change to either page.

### Change 1: the date is fixed in the layer

`ShiftFields` takes a new optional `fixedDate?: string`, and only `ShiftLayer` passes it
(`fixedDate={date}`, the meal's day, for a new shift and an edit alike). The volunteers screens don't
pass it, so their date stays editable. `new/page.tsx` is unchanged (`cmp` identical to its `.pre`).

How a person can tell it is fixed:
- **Screen reader:** the input is `readOnly`, not `disabled`, so it is announced as read-only. Its
  `aria-describedby` points at the line under it: "The day of the meal. It cannot be changed here."
- **Keyboard:** a read-only input stays in the tab order, so it can be reached and read.
- **Sighted:** the box has the recessed `bg-sunken` fill, secondary text colour and a default
  cursor, and a lock icon beside that line.
- **Saving:** a read-only input still submits its value, so `readShiftForm` sends the meal's day as
  `shiftDate`. A disabled input would drop out of the form data. Tests assert `readOnly` is true,
  `disabled` is false, and the posted `shiftDate` equals the meal's day even after trying to change it.

The wording of that line is mine, and is Rajeev's to change.

### Change 2: the layer warns when a save moves a shift people signed up for

- **One rule:** `movedUnderRoster(before, after)` in `shift-form.tsx`, next to `moved()`, defined as
  `moved(before, after) && before.signedUpCount > 0`. The edit screen's `warn` line now calls it.
  The layer calls it on update.
- **One banner:** new `app/volunteers/moved-notice.tsx`, `MovedNotice`, holding the list page's JSX
  moved verbatim. Same text, same `/volunteers/<id>` link. The list page renders it in place of its
  inline copy, and the planner renders it too.
- **Path:** the layer calls `onSaved(shift && movedUnderRoster(shift, input) ? shift.id : null)`.
  MealServices keeps that id. The meal whose shifts include it shows `MovedNotice`, using the shift as
  re-read after the save, which is how the list page gets its count. The next save replaces it.
- **Where it shows:** inside the meal's own card, directly under its header row, where the
  shift button is. The layer closes back onto that spot, which is where the person just pressed. It
  also shows which meal is affected without new words. It does not clear itself (a warning,
  per §4).
- **Concern for Rajeev, wording kept exact as instructed:** "That shift moved" reads fine inside the
  meal's card. But on the planner the only change possible is the times, and "moved" may read as
  "moved to another day". I did not reword it.
