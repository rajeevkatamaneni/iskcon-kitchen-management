## Each form and its test (all in `blank-submit-slice-c.test.tsx`)

Every test clicks the real submit button, then checks four things: the exact sentence, the red class,
that the sentence sits straight after the box (or after its wrapping label), and that the box has
`aria-invalid` and the sentence as its description. It also checks that no API call was made.

1. Add a vendor (`vendors/new`, button outside the form via `form=`): "Name is required".
2. Edit vendor (`vendors/[id]`): cleared Name, "Name is required".
3. Add a supply (`vendors/[id]`): "Ingredient is required". Out of range: lead time 400 gives "Lead time (days) can be at most 365".
4. Vendor status dialog: see the nested-forms section. "Why are they being dropped?Whoever considers … is required".
5. Register equipment (`EquipmentForm`, button outside): "Name is required". Out of range: cost 12.345 gives "What it cost (₹) can have at most 2 decimal places".
6. Edit equipment: cleared Name, "Name is required". Out of range: cost -1 gives "What it cost (₹) must be at least 0".
7. Change condition (`equipment/[id]`): "Why is required". A second test chooses Scrapped with a blank reason and checks the scrap question never opens.
8. Bring it back (`equipment/[id]`, scrapped machine): "Why it is coming back is required".
9. Record a service (`equipment/[id]`): cleared date gives "Serviced onA service dated next Tuesday has not happened yet. is required". Out of range: 2099-01-01 gives "… must be on or before 12 Sept 2026" (built from `dateWithYear(todayIso())`).
10. Kitchen form (`kitchens/new`, button outside): "Name is required".

The edit-kitchen page mounts the same `KitchenForm`, so it has no separate test.

## Tests changed, and why

- `vendor-without-phone.test.tsx`: 7 × `fireEvent.submit(form)` became a click on "Add vendor" (3) or "Save changes" (4).
- `vendor-lead-time.test.tsx`: 3 × `fireEvent.submit(form)` became a click on "Add supply".

These tests were green both before and after the switch, because every form they submit is valid. The
switch is on the brief's instruction. A dispatched submit event skips the browser's check entirely,
while a click goes through it, which is how a person submits. No assertion, value or fixture changed.
A vendor with no phone still saves: both no-phone tests, on add and on edit, pass through a real click.

## Nested forms

- **Vendor status dialog.** In the DOM and in React it is a sibling of the page's forms, never inside
  one. On both `vendors/[id]` and `vendors` it is mounted after `<main>`. Tests: a written reason
  submitted from `vendors/[id]` calls `deactivateVendor` once, with `updateVendor` and
  `setVendorSupply` not called. The same submit from the vendor list calls it once. Bring back with
  no reason calls `reactivateVendor(…, null)` and shows no sentence, because `required` is only set
  when dropping.
- **Blank reason in the dialog cannot be reached by a click.** The commit button is disabled while the
  reason is blank. So that test dispatches `submit` on the dialog's form, the one place in this file
  that does. It still proves `Form` is there: with a plain `<form>`, the dispatched event would reach
  the handler and post an empty reason.
- **Equipment page.** Only one of its three forms is open at a time, since they share one `open`
  state. The scrap confirmation has no form of its own. Nothing nests.
- **KitchenForm.** Its "Save these changes" confirmation button is `type="button"` inside the form. It
  calls `onSubmit` with the input captured at the submit that already passed `Form`. It never submits
  the form, so `Form` does not see it.

## Hand-rolled checks and disabled Save buttons

None of the forms shows a second message beside `Form`'s.

- `VendorStatusDialog`: the commit button is `disabled={dropping && written === ""}`. That is a
  hand-rolled copy of `required` (it also treats spaces as blank). It is the disabled-Save issue, left as it was.
- `vendors/[id]` Add supply: `disabled={busy || available.length === 0}`. That is not a copy of
  `required`: it means there is no ingredient left to add.
- `equipment/[id]/edit`: Save is `disabled={busy || !item}`. That covers loading only.
- All other submit buttons are `disabled={busy}` while a request is in flight.

## Labels that read badly (not renamed, for Rajeev)

- **Record a service, Serviced on:** "Serviced onA service dated next Tuesday has not happened yet. is
  required". The hint sentence sits inside the `<label>`, so it becomes part of the name, run
  together. A person sees this whenever they clear the date or pick a future one. This is the one worth fixing.
- **Vendor status dialog:** the reason's label also wraps its hint, giving the same run-together
  name. Nobody sees it today because the button is disabled.
- **Change condition:** "Why is required". Correct, but terse.
- **Kitchen Name:** the label also wraps the duplicate-name error (KMS-400106). If someone clears the
  box while that error shows, the name would read "NameAnother kitchen here already goes by this name."
  Rare, and not tested.
- "What it cost (₹) …" and "Lead time (days) …" carry their bracketed units into the sentence. That is a matter of taste.

## Boxes with rules that `Form` cannot check (outside any form)

Checks were never applied to any of these, before or after this change:

- `EquipmentForm` servicing block: "How often" has `min=1 max=100` but sits outside the `<Form>`
  element, on purpose, and has no `form=` attribute. So 0 or 500 goes to the server unchecked.
- `equipment/[id]` Change the schedule: not a form at all. "How often" `min=1 max=100` is unchecked,
  and Save is `type="button"`.
- `vendors/[id]` supply edit row: not a form. Last price `min=0` and Lead time `0–365, step 1` are
  unchecked, and Save is `type="button"`.
- A Name of only spaces passes `required` on every form here, and the server is left to refuse it.
