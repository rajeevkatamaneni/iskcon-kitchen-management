## How comments are excluded

The guard does not use a regex. It parses each file with the TypeScript compiler
(`ts.createSourceFile(..., ts.ScriptKind.TSX)`, typescript 5.6.3, already a frontend dependency). It
then walks the tree for `JsxOpeningElement` / `JsxSelfClosingElement` nodes whose tag name is the
identifier `form`. Comments are trivia to the parser, never nodes, so no comment shape can match. A
string containing `"<form>"` is a string literal, not an element. `<Form`, `<FormRow` and `<formatted>`
have different tag names. `<form>`, `<form ...>`, `<form\n...>` and `<form/>` all parse to a node
tagged `form`, which is the "followed by whitespace, `>` or `/`" rule from the brief.

Why not the brief's regex-over-stripped-comments: `prose()` in the same file strips comments with
`/\/\*[\s\S]*?\*\//`. A `/*` inside a string, such as `accept="image/*"` on a file input, would start
a fake comment running to the next `*/` and hide any real `<form>` in between. The parser has no such
hole. The test file's doc comment records this.

The file list is the file's existing `FILES` (git cached + untracked, `.tsx` under `app` and
`components`), so a new, uncommitted screen is scanned too. The control relies on that.

A second test, "still finds the one <form> it exempts", asserts the parser finds exactly one `form`
element in Form.tsx. It fails if the parse ever silently stops seeing JSX (for example, a wrong
ScriptKind), which would otherwise leave the main guard green over any tree.
