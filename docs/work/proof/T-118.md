# T-118 — the temple somebody chose while registering is carried to the screen that asks for it

Somebody fills in the register form, temple first, and Firebase says their email already has an
account. The screen tells them to sign in instead and promises the sign-in will ask which temple
they serve at. It did — as though they had never said. The answer is now carried across and the
picker opens with it chosen, still waiting to be told to join.

**Not touched:** `frontend/app/sign-in/page.tsx`. It is in the contract and it turned out to need
nothing: the note is not in the URL, so the sign-in screen is a pass-through and the query parameter
it already carries (`?registered=`) is untouched.

**`lib/auth-context.tsx`, and why it is not avoidable or merely convenient.** The note has to be
forgotten on sign-out, for the same reason the refusal is: the way off the picker for somebody who
chose the wrong Google account is "Use a different account", and the next person to use that browser
must not be handed the last one's temple. `signOut` lives in `auth-context`, so a note it cannot
reach is a note that outlives the person who left it. The two screens also need one definition of
the key and the shape between them, and the natural home — `api.ts`, where `setActiveTempleId`
lives — is held exclusively by another builder this wave. If you would rather it were its own
`lib/chosen-temple.ts`, it is a move of three functions and an import.

**`JoinTempleForm.tsx`.** `/choose-temple` renders the picker through it, and its temple is internal
state. Opening with one chosen means telling it so. The prop is optional, read once at mount, and
never re-asserted — so the picker's "Change" stays the last word, which is the point of
pre-selecting rather than pre-deciding. No other caller passes it and none changed.

## The design questions

**Where it lives, and for how long.** `sessionStorage`, key `kms.templeChosenWhileRegistering`,
holding `{ id, name, at }`. Not a query parameter: the hop is register → sign-in → `/` →
`/choose-temple`, and the last leg is a `router.replace` from the session layer that carries no
query, so a parameter would have to be threaded through three screens and would survive being
pasted, bookmarked or shared. Not `localStorage`: that is shared between tabs and outlives the
browser, and this belongs to one journey in one tab. Lifetime is therefore the tab, and on top of
that **half an hour** and **one read**. Half an hour because the gap is a sign-in and a sign-in can
turn into finding a password, resetting it and waiting for the email; read-once because a note still
sitting there on the second visit is explaining a journey that finished. It is also written narrowly
— only on `auth/email-already-in-use`, the one failure that ends with the person leaving the screen.
A temple picked on a form somebody then abandoned is not an answer anybody gave us.

**What happens when it is stale — and the answer is that nothing stale is ever shown.** The note
holds an id; the name in it is a search term and is never rendered. On arrival the picker looks the
id up in the same list it offers (`api.temples({ q: name })`) and uses **the record that comes
back**. So a temple renamed since they picked it is not found and the question is asked plainly; one
closed to new devotees or withdrawn is not in the list and is not offered; a lookup that fails at all
falls back to asking. A person who reached the picker by any other road finds it exactly as it was,
and no request is made for them at all.

**Pre-selected, never pre-joined.** Your ruling on the neighbouring register defect was to remember
the credential and resume at the join; the same shape here stops one step short, because joining a
temple is a real act. Arriving calls nothing. The button is still theirs to press, "Change" sits
beside the choice, and one line above the form says where it came from: *"This is the temple you
chose when you registered."* — a box that fills itself in is a small mystery on a screen somebody
has arrived at confused.

**The finding you asked for: the two screens cannot disagree about what is selectable.** They are
the same component (`components/TemplePicker.tsx`) calling the same function (`api.temples`) with
the same token (none — both pass `token={undefined}`). The only difference is the label. So a temple
choosable on the register form is choosable on the picker *at that moment*; the only way they can
diverge is time, which is exactly what the lookup above re-checks.

## Acceptance criteria

- **The temple chosen on the register form reaches the picker.** `temple-carried-from-register.test.tsx`
  drives the real register screen to `auth/email-already-in-use`, then reads the note with the real
  `takeChosenTemple` and finds `{ id: "t1", name: "ISKCON Mysore" }`. Nothing in that file mocks
  `lib/auth-context`; both ends use the real storage, or it would prove only that a fake agrees with
  itself.
- **The picker opens with it chosen, and joining is still the person's act.** Asserted together: the
  temple's card is on screen, "Change" is beside it, the explaining sentence is above it, and
  `joinTemple` has not been called. A second test presses the button and checks the join goes to
  `t1`.
- **Nothing stale is shown.** Four tests: a renamed temple shows the server's name and *not* the
  remembered one; an id the list no longer holds falls back to the plain question; a lookup that
  throws falls back to the plain question; a note older than half an hour is not even looked up.
- **Everyone else is unaffected.** A test asserts that an arrival with no note makes no lookup at
  all and sees the screen as it was; `choose-temple.test.tsx` (11 tests, all its existing ones) is
  that same claim from the other side.
- **The note belongs to one person.** Signing out clears it, driven through the real `AuthProvider`.
- **T-116's work is intact.** Its guard is green, and no refusal message or next step is hardcoded
  anywhere in this change.
- **The stale comment is fixed**, with the before-and-after above and a grep count either side.
