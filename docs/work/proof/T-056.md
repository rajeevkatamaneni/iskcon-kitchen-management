## Acceptance 3 — the runtime proof, and the negative control that makes it mean something

The criterion is a Temple Admin reaching `PATCH /api/v1/ingredients/{id}/ekadashi-flag` and **not**
getting 403. `IngredientIT.onlyAdminChangesEkadashiFlag` already does exactly that, through the real
security filter chain (`@AutoConfigureMockMvc` over the full context, a stubbed token verifier and a
real `TEMPLE_ADMIN` row in Postgres), and it asserts `isNoContent()` on the admin's PATCH — line 119.

**Demonstrated, not asserted.** Inside one hold of the verify lock, the `@PreAuthorize` string alone
was patched back to `MANAGE_SATTVIC_POLICY` — the enum, the grant and the service left correct, so
the only thing wrong was the one line the compiler does not read:

```
=== PATCHING THE ANNOTATION BACK TO THE OLD NAME ===
90:	@PreAuthorize("hasAuthority('MANAGE_SATTVIC_POLICY')")

=== IT STILL COMPILES AND RUNS — that is the whole danger. Running IngredientIT: ===
IngredientIT > kitchen staff may add an ordinary ingredient but not mark one prohibited PASSED
IngredientIT > only a Temple Admin can change the Ekadashi-prohibited flag, and it is audited FAILED
    java.lang.AssertionError: Status expected:<204> but was:<403>
        at org.iskcon.kms.ingredient.IngredientIT.onlyAdminChangesEkadashiFlag(IngredientIT.java:119)

  Total:    9
  Passed:   8
  Failed:   1

```

Three things worth reading off that output.

**It compiled.** The build reached the test phase and ran nine tests. That is the entire trap the
brief named: a rename that misses this line is not a build error, it is a 403 in production for
every Temple Admin, against a permission nobody holds.

**Only one test could see it — and the count needs its own explanation.** Eight of nine passed under
the broken string, and that is not a hole. `staffCannotMarkProhibited` and the staff half of
`onlyAdminChangesEkadashiFlag` both assert a **denial**, and a permission nobody holds denies
everybody: they pass vacuously whether the string is right or wrong. `sattvicFlagEndpointIsGone`
asserts a 404 and is likewise indifferent. **The admin's 204 is the only assertion in the codebase
that distinguishes a working authority string from a dead one** — which is why the comment added at
the annotation names that test by name and says to keep it.

**The restore was trapped, not trusted.** An `EXIT` trap copied back a pre-patch snapshot and
`cmp`-ed it, so a death mid-control could not have left the shared tree broken for the rest of the
wave:

## It is a rename, not a migration — checked, not assumed

D-21 asks this to be established rather than inferred, and the answer comes from the far side of the
boundary rather than from the absence of a grep hit:

- **The mechanism.** `AuthenticatedUser.getAuthorities()` (`:108`, `:117`) builds every authority at
  request time from `RolePermissions.forRole(role)` and `permission.name()`. What is persisted is
  `users.role` — a *role* name — and the permission names never leave the JVM.
- **The schema agrees, out loud.** `V61__kitchen_manager_role.sql:26` comments the `users.role`
  column: *"The policy itself lives in RolePermissions.java, deliberately in code rather than in rows
  somebody can edit in production."*
- **No row anywhere holds one.** Every occurrence of a `Permission` enum name across all migrations
  was listed and inspected line by line (21 lines, across V10, V16, V26, V44, V61, V66, V68, V83,
  V84, V86, V90). **Every one is either a `--` comment or the text of a `COMMENT ON`** — documentation
  attached to the schema, never data. No `CREATE TABLE` column, no `INSERT`, no `CHECK` constraint
  names a permission.

So there is no backfill to write and no stored value to rewrite. The two `V10__ingredients.sql`
lines were deliberately left as they are: a shipped migration is never edited, and a migration
comment that has aged is history, not a defect.

## The four apologies, removed

Each said some version of *"a historical name, kept because renaming the authority string is wider
than D-18 ruled"*. That was good discipline — it is the reason the misnomer was findable at all —
and it is now false. Removed from `IngredientService.java:34`, `CreateIngredientRequest.java:10`,
`IngredientController.java:26` and `IngredientIT.java:93`.

In their place, one comment was **added**, at the `@PreAuthorize` in `IngredientController.java` —
the single site with no compiler behind it — recording that the authority is a string, what a missed
rename costs, and which test would catch it. The explanation of the *misnomer* goes; the explanation
of the *hazard* stays, because the hazard is still there for whoever renames a permission next.
