### 5. The import label clears only on a real change — DONE, SERVER-SIDE

**I put the comparison on the server, and the brief's lean was right.** Three reasons:

1. **A client that scores its own save is a client handing the server a verdict to trust.** A raw
   POST could then clear the label off every imported row in the catalogue without changing a
   value. The project's standing rule, in `RecipeService`'s own comment guarding this same
   catalogue: *"a picker is not a guard: a raw POST, an import, or a screen built later never goes
   through it."*
2. **The stored row is where the truth about what changed lives.** The client knows what it
   displayed; the server knows what is there.
3. **It is the only place the comparison can be made in its stored form.** The service trims the
   name and category and runs aliases through `normalizeAliases` before writing. A client
   comparing raw form values counts `" Rice"` against `"Rice"` as a change — and the row comes
   back from the database identical. There is a test for exactly this.

The comparison is written out field by field rather than looped, because it *is* the definition of
"a modification" and should read as one. Alias order counts (the array is stored and displayed in
the order given, so re-ordering is a change a person can see).

**One consequence I have named in the code rather than left to be discovered:** the comparison is
against the row as it stands *now*, not against what the client was shown. If somebody else edited
the ingredient in between, a save that looks unchanged on this screen genuinely does change the
stored row, and the mark clears. That is the right answer — the row moved, and it moved because of
this request.

**Ticking Ekadashi counts, and clears the mark.** As the brief says, that is a change from today
and it is right, because it now happens inside a deliberate edit. The old one-click toggle still
clears nothing (`ekadashiFlagLeavesTheMarkAlone` still passes) — setting a flag is not reviewing a
row, because it never shows anybody the category and unit an import guessed.

#### The security hole this could have opened, closed and asserted

`PUT /api/v1/ingredients/{id}` is behind `MANAGE_RECIPES`. **Kitchen staff reach it.** Putting the
Ekadashi flag on that body means the endpoint annotation no longer guards it, so
`IngredientService.update` checks `MANAGE_DIETARY_POLICY` itself — the same rule, the same
`NOT_PERMITTED` / KMS-400021 and the same reason `create()` has always applied. Commandment: a
permission, never a role, and the guard is not the checkbox.

The check compares against the **stored value**, not against the key's presence. A "the key is
present" check would have 403'd every Kitchen Manager who renamed a prohibited ingredient while
the admin's own form echoed the flag back. Both cases have tests.

**And the field is a boxed `Boolean`, which is load-bearing.** `null` means "leave it alone" — the
only honest thing a client without the permission can say. A primitive would have deserialised
their absent key to `false` and quietly un-prohibited the row. On the client this is a spread, not
`x ? v : undefined`, because the latter still *creates* the key holding `undefined`: the wire would
look right and every payload assertion would see a field that person was never offered.
