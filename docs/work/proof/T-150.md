# T-150 — stock adjustment, gift of goods and ingredient request refuse a wrong-family unit with KMS-400013

**Files changed:** all six are inside the contract. Nothing else was touched: no `IngredientUnits.java`, no frontend, no UAT doc.

- `backend/src/main/java/org/iskcon/kms/inventory/InventoryItemService.java`
  - Injects `IngredientUnits`.
  - `adjust` calls `requireSameFamily(item.ingredientId(), unit)` where the inline check was.
- `backend/src/main/java/org/iskcon/kms/donation/DonationRecorder.java`
  - Injects `IngredientUnits`.
  - Every ingredient line is now parsed and checked **before** the donation row is inserted.
  - Removed the now-unused `findIngredient`, `IngredientRef` and the `Optional` import.
- `backend/src/main/java/org/iskcon/kms/ingredientrequest/IngredientRequestService.java`
  - Injects `IngredientUnits`.
  - `validateLines` keeps its own "ingredient not found" check, then calls `requireSameFamily` per line.
- `backend/src/test/java/org/iskcon/kms/inventory/StockAdjustmentIT.java`
  - `unitMustMatchFamily` asserted KMS-400001.
  - It now asserts KMS-400013, `fieldErrors[0].field` "Toor Dal", and that the batch still holds 100.
- `backend/src/test/java/org/iskcon/kms/ingredientrequest/IngredientRequestIT.java`
  - `refusesACrossFamilyUnit` asserted KMS-400001.
  - It now asserts KMS-400013 and `fieldErrors[0].field` "Rice".
- `backend/src/test/java/org/iskcon/kms/ingredient/UnitFamilyRefusalIT.java` is new, with 9 tests.

DonationIntakeIT, DonorCaptureIT and DonationVoidIT needed no change. None of them tested the family refusal. Their KMS-400001 assertions cover other rules, such as cash and goods on one form or a missing donor name.

No constructor is called by hand anywhere in `backend/src`: `grep "new InventoryItemService(\|new DonationRecorder(\|new IngredientRequestService("` found nothing.

## Things the brief asked me to check

**Which ingredient id `adjust` passes.** It passes `item.ingredientId()`, which is `ii.ingredient_id` from `ITEM_SELECT`. The old code compared against `i.canonical_unit` from `JOIN ingredients i ON i.id = ii.ingredient_id`. `requireSameFamily` runs `SELECT name, canonical_unit FROM ingredients WHERE id = ?` with that same id, so it reads the same row and the same canonical unit.

**Order of refusals.**

- **Adjustment: unchanged.** Unknown item (not found), then an unreadable unit name (400001), then wrong family (now 400013), then zero quantity, then OTHER without a note, then batch, negative stock and the large-adjustment gate.
  - The ledger (`StockMovementService.record`) also checks the family, but only after the negative-stock and large-adjustment guards.
  - Keeping the early call means "-150 L of dal" is told the unit is wrong, not that it needs an admin.
- **Gift of goods: moved, in two small ways.** Before, the donation row was inserted, then each line was checked in turn and its movement written. Now `validate()` runs first as before, then every line is checked, and only then is anything inserted.
  1. Nothing is written before a refusal. The transaction used to roll back the donation row and any earlier line's movement, so what a person sees is the same, but nothing is left waiting to be undone.
  2. Within one line, the unit name is now read before the ingredient is looked up. A line with both an unknown ingredient and an unreadable unit name now answers 400001 (bad unit) instead of not-found. Line 2's wrong unit is also now reported before any ledger refusal on line 1.
- **Ingredient request: unchanged.** Kitchen, then for each line in order: unknown or other temple's ingredient (still 400001, `lines[i].ingredientId`), then wrong family (now 400013), then dishes. All of it runs before any insert, on both create and edit.

**The extra lookup.** Each is one primary-key read on `ingredients`, on a form a person typed.

- Adjustment: one extra read per adjustment.
- Gift: none extra. `requireSameFamily` replaces the `findIngredient` read that was there.
- Request: one extra read per line, on top of the existing existence read.

It does not matter on these paths.

**Frontend screens that read the old field error: none.** I read these files and changed nothing:

- `frontend/app/inventory/[id]/page.tsx` shows the adjust failure through `ErrorNotice` (line 171, fed by `run(...)` at line 322).
- `frontend/app/donations/new/page.tsx` uses `ErrorNotice` at line 152.
- `frontend/components/IngredientRequestForm.tsx` uses `ErrorNotice` at line 244.
- `frontend/components/ErrorNotice.tsx` renders only `message`, `action` and `code`.

None of the three screens reads `fieldErrors`, `field`, `lines[` or `expectedFamily`, or checks for `400001`. The old `field`/`expectedFamily` values were in the exception's log details, which never reached the client: `ErrorResponse` carries only code, message, action and fieldErrors. So no screen stops highlighting anything.

**The gap this leaves:** the new field error naming the ingredient ("Ghee is measured in L, and there is no way to turn Kg into L.") is sent, but none of these three screens shows it. UAT-081 step 17 expects the two-line gift refusal to name Ghee. Today it will show the general KMS-400013 message only, and the UAT doc rates a refusal that names no line as Major. `frontend/app/orders/[id]/page.tsx` lines 815–819 already render `fieldErrors` and are the pattern to copy. That needs a frontend task; it is outside this contract.

## Acceptance criteria

1. **Each path answers 400, KMS-400013, a field error naming the ingredient, and writes nothing.** Covered by the refusal tests in UnitFamilyRefusalIT. Each asserts status 400, `code` KMS-400013, exactly one field error, its `field` as the ingredient name, and the full message.
   - Adjustment, L and PIECES on Rice: stock_movements count still 1, on-hand still 100,000 g.
   - Gift, Rice in L: donations 0, movements still 1.
   - Request, Rice in L: requests, lines and dishes all 0.
   - Edit of an existing draft adding a nonsense line: the draft keeps 1 line, still 40, not the 60 the refused edit carried.
   - Verified by the targeted run (86/86) and the control (all fail with 400001 under the old checks).
2. **The two-line gift, one good line and one bad, writes neither line.** Covered by `twoLineGiftIsRefusedWhole`: Rice 5 Kg plus Ghee 2 Kg is refused naming Ghee, with donations 0, movements still 1, Rice on hand unchanged, and no new inventory item for Ghee. The same is proved for a two-line request (`twoLineRequestIsRefusedWhole`).
3. **A different unit of the same family is still accepted on all three.**
   - `adjustmentAcceptsTheSameFamily`: -500 gm gives 201 and 99,500 g.
   - `giftAcceptsTheSameFamily`: 5000 gm gives 201, one donation, 105,000 g.
   - `requestAcceptsTheSameFamily`: 500 gm gives 201, line stored as GM.
   - IngredientRequestIT's existing `acceptsAnotherUnitOfTheSameFamily` also still passes.
4. **Existing tests that asserted KMS-400001 for this case are updated.** Two: `StockAdjustmentIT.unitMustMatchFamily` and `IngredientRequestIT.refusesACrossFamilyUnit`. There was no family test in DonationIntakeIT, DonorCaptureIT or DonationVoidIT.
