## The brief's claimed mechanism, checked rather than trusted

The brief asserted the select paints before its options. Confirmed from the source, not inferred:

- `frontend/components/IngredientRequestForm.tsx:103` — `const kitchens = useAuthedQuery(fetchKitchens);`
- `:136` — `const kitchenOptions = (kitchens.data ?? []).filter((k) => !k.usesMealPlanner);`
- `:263-264` — `<option value="">Choose…</option>` then `{kitchenOptions.map(...)}`
- `frontend/lib/use-authed-query.ts` — `useState<T|null>(null)` seeded null, filled in an effect.

**And the part that makes it fatal: there is no loading gate.** `IngredientRequestForm` renders its
form unconditionally — no `if (loading) return <Loading/>` anywhere in it. So the `<select>` exists
on the very first paint carrying one option, and `findByLabelText` resolves on exactly that paint.

That is the difference from every other site in this sweep, and it is worth stating as the general
test: **the sweep's pattern is not the diagnostic; the loading gate is.** A container behind a gate
on the same query as its content cannot race. A container rendered unconditionally and *filled* by a
query can. Every verdict below turns on that one question.

Nor is `:218`'s negative (`queryByRole("textbox")` is null) vacuous — `:217` immediately above is a

**:258 and :310 — RACY, a different fault, and NOT the same patch shape. Fixed** (now both at
`:283` / `:334`).
The brief flagged these and asked me to diagnose them on their own terms rather than assume. Doing
so: `app/orders/new/lines/page.tsx:86-87` runs **two** queries — `activeVendors` and
`allIngredients` — and `:220` gates the form on `loadingVendors` **only**. So the "Add an ingredient"
select appears when *vendors* land, and is filled when *ingredients* land. Two sources again, but
the consequence is different in kind:

> `fireEvent.change(picker, { target: { value: "ing1" } })` against a `<select>` that has no such
> `<option>` **neither throws nor warns**. The DOM silently declines it, the value stays `""`,
> "Add line" stays disabled, the click does nothing — and the run dies a dozen lines later at
> `getByLabelText("Quantity of Rice")`, a field that was never created, on a screen with nothing
> wrong with it.

So: a `within` race is an *assertion* reading too early, and it names the thing it could not find. This
is an *action* landing too early, and an innocent later line takes the blame. That is why the patch
shape differs — you cannot wrap `fireEvent.change` in `waitFor` (it would re-fire on every poll).
The fix waits for the option to exist, *then* selects it. The control below shows the displaced
blame exactly: the reported failure is at line 315, six lines past the actual fault.

## What was changed

### `ingredient-request-new.test.tsx` — and how I know `:127` is now a *real* absence

```js
const picker = await screen.findByLabelText(/^kitchen$/i);
// …why the race exists…
await waitFor(() => expect(within(picker).getAllByRole("option")).toHaveLength(2));

expect(within(picker).getByText("Prasadam kitchen")).toBeInTheDocument();
// It draws its stock through the planner, … KMS-400110.
expect(within(picker).queryByText("Restaurant kitchen")).not.toBeInTheDocument();
```

I first wrote this as `library.test.tsx`'s shape — `await waitFor(presence)` then the synchronous
absence — and the non-vacuity was then an *argument*: both kitchens come back in one array from one
promise and are rendered by one `.map` in one commit, so an established presence proves the array
rendered. That argument is correct, but it is an argument, and the brief's whole standard is not to
accept evidence that would look the same if the thing were broken.

So I made it **mechanical instead**. The `waitFor` asserts the option *count*, which is the one thing
that separates all three states:

| picker state | options |
|---|---|
| nothing loaded | 1 (`Choose…`) |
| loaded, filter working | 2 |
| loaded, filter broken | 3 |

The clock cannot satisfy `toHaveLength(2)`, and neither can a broken filter. By the time the two
named assertions run, "loaded, **and** filtered" is established rather than assumed. `toEqual` on an
option-text array is an idiom this very file's neighbour already uses (`manual-purchase-order:231`),
so this is not a new shape in the repo.

**And I proved the hazard was real rather than theoretical** — control C below.

### `manual-purchase-order.test.tsx`

Added `waitFor` to the testing-library import, and a helper beside the file's existing
`vendor()` / `tomorrow()` / `yesterday()` helpers:

```js
async function chooseRiceFromTheCatalogue() {
  const picker = await screen.findByLabelText(/add an ingredient/i);
  await waitFor(() =>
    expect(within(picker).getByRole("option", { name: "Rice" })).toBeInTheDocument()
  );
  fireEvent.change(picker, { target: { value: "ing1" } });
}
```

A helper rather than two inline patches because the reason is long and belongs in one place, and
because the next test in this file that needs a catalogue ingredient now does the right thing
without knowing why. Both call sites (`:283`, `:334`) became one line each; `picker` was not
referenced after the `fireEvent.change` at either site, so nothing was lost.

## Not done / needs Rajeev

**1. I declined the brief's suggested approach — permanently deferred mocks — and here is why.**
The suggestion was to make every mock resolve on a macrotask so the race is always lost, turning the
suite into a standing guard. I think it is the wrong trade, on four counts, and the third is the one
that decided it:

- *It cannot be scoped.* "The suite" is 106 files; my contract is 5. There is no version of this that
  is not a repo-wide edit, and a repo-wide edit to test timing is exactly the change you do not want
  landing on a red `main` whose deploy is blocked.
- *It changes what some tests assert.* Several tests here are deliberately synchronous — e.g.
  `ingredient-request-new`'s "refuses a volunteer the page" does `render` then `getByText` with no
  await, because the guard is a first-paint fact. Under permanent deferral those tests keep passing
  but are now asserting against a screen that is permanently mid-load, which is a different claim
  from the one they were written to make. That is worse than a flake: it is a green test about
  nothing, which is the failure mode this project's own lesson 4 exists to prevent.
- *It would not have made this bug diagnosable.* The `manual-purchase-order` fault would still have
  surfaced at `Quantity of Rice` — see control B/BEFORE. Deferral makes such failures *deterministic*,
  which is real value, but not *legible*; you would trade twelve latent flakes for a pile of hard reds
  landing at once, each pointing at the wrong line.
- *It removes a real signal.* A test that must assert something appears *before* a load — a skeleton,
  a disabled control, a guard — would go green for the wrong reason under permanent deferral.

**What I would do instead, and it is out of my contract so I am recommending rather than doing it:**
lint for it. `eslint-plugin-testing-library`'s `await-async-query` / `prefer-find-by` family catches
exactly this shape, and it catches it at author time on all 106 files rather than at CI time on one.
I checked: **`frontend/` has no ESLint config or plugin at all** (`ls -a | grep -i eslint` returns
nothing; `package.json` names no eslint dependency). So this is a real piece of work — add the
toolchain, add the config, fix whatever else it turns up — and it deserves its own task rather than
being smuggled into a hygiene fix. I would rank it above re-sweeping by hand, because the sweep that
produced my twelve sites has a false-positive rate of 10 in 12 and a false-*negative* rate that let
`:258`/`:310` through entirely.

**2. A latent fragility in `LanguageSection`, correct today, one refactor from being a bug.**
`app/settings/page.tsx:1391` seeds `useState((initial ?? "en-IN").split("-")[0])` from a prop.
`useState` ignores later prop changes, so if that section were ever mounted before `locale` arrived
— by removing the `!settings` gate at `:116`, by splitting the `Promise.all` into independent
queries, or by adding a suspense boundary — the picker would show English **permanently**, and no
test would notice, because `settings-payments:460` would then be reading an early paint. It is safe
as written and I changed nothing. Worth a `useEffect` re-seed or a `key={locale}` if anyone touches
that page's loading shape. **Not raised as a component change**, per the brief: the test is not wrong
about timing today, and I am not going to edit a component on a hypothetical.

**3. No hand smoke-test, and none was warranted.** Commandment 5 wants a user-facing surface driven
by hand. This task adds no surface and changes no product code — the only files changed are two test
files. There is nothing to press. Saying so explicitly rather than leaving the line blank.

**4. One thing I did not widen my contract for.** `manual-purchase-order.test.tsx:231` (formerly
`:206`) is a sibling of a listed site and is *safe* by the same gate argument, so it needed nothing.
But had it needed a fix I would have had it, since it is in a granted file. There is no widening to
ask for — the contract as written was sufficient, including the read-only grants, which is what let
me confirm the `ErrorNotice` and `BanFindings` verdicts from the source instead of guessing.
