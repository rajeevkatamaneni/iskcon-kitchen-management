# T-096 — the send path takes the communication's row lock before it reads the status

**Files changed:**

- `backend/src/main/java/org/iskcon/kms/communication/CommunicationService.java` — in contract
- `backend/src/test/java/org/iskcon/kms/communication/CommunicationRetryIT.java` — in contract

Nothing else. `ErrorCode.java` was not opened: `COMMUNICATION_ALREADY_SENT` (KMS-400086) already says
exactly the right sentence and `requireDraft` already throws it, so no new code was needed.
`CommunicationIT.java` was **read but not edited** (it is `@Import`ed by the test class for its stub
verifier); it is untouched in `git status`.

## Where the lock went, and why that half

Inside **`recordSend`**, as its first statement — before `find(id)` reads the status.

`recordSend` is the body of the first of the two transactions T-094 split `send` into. That
transaction is the one that reads the status, takes a decision on it (`requireDraft`) and writes it
(`UPDATE … SET status = 'SENT'`); it touches no devotee. The relay run is the second half, outside
any transaction.

The two wrong places, both of which look right in a diff:

- **Top of `send()`.** `send` is deliberately **not** `@Transactional` — it calls
  `transactions.execute(...)` and then loops. A `SELECT … FOR UPDATE` there would run in its own
  auto-commit transaction and be released on the spot. It would close nothing at all.
- **Around both halves.** That holds one row for the entire relay run — a four-hundred-copy send —
  which is precisely the arrangement T-094 broke apart.

Ordering matters as much as the half: the lock is taken **before** `find`, not after it. A lock taken
after the status has been read leaves the decision standing on a snapshot the lock does not cover,
which reads as a fix and is not one. (`retryFailed` orders it the other way round for a reason of its
own — its decision is `failedRecipients`, read *after* the lock — and was left alone.)

`lockForRetry` was renamed `lockCommunication`, since it now has two callers, and its javadoc grew the
T-096 paragraphs. It is the same one-line query, unchanged.

## What the second admin now gets — and what the negative control actually proved

**The brief's stated mechanism is no longer reachable, and the negative control is what says so.**
"Both send the whole letter to the whole audience" was true before T-094. It is not true today: since
T-094, `recordSend` writes a recipient row per audience member up front with a plain INSERT, and
`communication_recipients_once` is a unique index on `(tenant_id, communication_id, recipient_user_id)`.
So the second transaction cannot write its rows. Removing the lock and re-running the new test gives,
verbatim from the control log:

```
CommunicationRetryIT > two admins pressing Send at once send one copy each, not two FAILED
    org.opentest4j.AssertionFailedError: [the second send is refused in words, not by a constraint]
    expected: 409
     but was: 500
```

and from that run's own test report:

```
duplicate key value violates unique constraint "communication_recipients_once"
KMS-500001
```

The copy-count assertions above it **passed without the lock** — nobody got the letter twice. So the
live defect is not a duplicate send; it is that **the second admin is stopped by a constraint instead
of by a sentence**: a `KMS-500001` "something went wrong" for the entirely ordinary act of pressing a
button that was already pressed, where the true and plain answer — *this message has already been
sent* — was already written and already reachable. With the lock the second transaction waits, reads
the `SENT` the first one committed, and is refused **409 / KMS-400086**.

Two things worth saying out loud, because they change how this task should be read:

1. **It no longer outranks T-084's race.** T-084's was a real duplicate delivery to real people.
   This one is a bad error message on a rare double-press. It is still worth fixing — nothing
   technical reaches the user is a commandment, and this is a technical failure reaching the user —
   but if it is competing for a slot with anything that duplicates or loses a message, it should
   lose.
2. **The index is a backstop, not an answer, and it disarms silently.** The moment anyone gives that
   INSERT an `ON CONFLICT` clause — which is the obvious way to make the 500 go away — the whole
   letter goes twice with nothing anywhere saying so. The lock is what makes that safe, and the
   copy-count assertions in the test are what would fail the day it is not. This is the same shape as
   the wave-7 lesson about `SUM` over a table whose rows changed meaning: the guard is real, and
   nothing names it as a guard.

The second sender is **refused**, not silently no-oped: 409 with a code and a next step, the record
admin A wrote is the one that stands (`status = SENT`, `audience_count = 3`), and B changed nothing.

| The second is refused rather than silently no-oping | Asserted `409` and `KMS-400086` on admin B's response body. This is the assertion the negative control fails on (`but was: 500`). |

## Where the test lives, and why

In `CommunicationRetryIT` rather than a new class. Three reasons, and the class comment now says them:
a reader comparing the send race with the retry race should find them side by side; the held-connection
harness (`appConnection`, `lockCommunication`, `notificationCount`, `recipientCount`) is the same
harness and a new class would have to copy it; and a second class means a second Spring test context,
because `@Import` is part of the context cache key — the cache explosion this repo has already been
bitten by.

## Not done / needs Rajeev

- **No hand smoke-test.** This is a two-browser race on a deployed environment: it needs two admins
  pressing *Send* on the same draft within the same transaction window, which I cannot stage by hand
  from here, and the change is not deployed. What a person *can* check once it ships is the ordinary
  case, which is already covered by `CommunicationIT`: sending a draft twice from one browser shows
  *"This message has already been sent."* rather than a generic failure.
- **A judgement call worth your eye, not a blocker:** T-096's row in `DISPATCH.md` says this defect
  duplicates the letter for everybody and outranks T-084. Post-T-094 it does not — see above. The
  fix is still right; the priority claim in the ledger is stale, and I did not edit `DISPATCH.md`
  (not in my contract).
- `retryFailed` reads the communication *before* it takes the lock, and `nothingToRetry` branches on
  that possibly-stale status. Harmless today (worst case it picks the wrong one of two refusal
  sentences in a race) and it is T-084's line, so I left it. Noted, not fixed.
