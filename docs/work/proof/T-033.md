# T-033 — a scrapped machine can be brought back, once, by name, with a reason (D-15)

Terminality is not loosened. `POST /{id}/condition` goes on refusing every post-scrap edit with
`EQUIPMENT_SCRAPPED` **KMS-400043**, and the guard in `EquipmentService.changeCondition` is
unchanged and unconditional. The way back is a second endpoint,
`POST /api/v1/equipment/{id}/reinstate`, behind `REINSTATE_SCRAPPED_EQUIPMENT` (Temple Admin
alone), auditing under `AuditAction.EQUIPMENT_REINSTATED`, writing through the same
`recordStateChange` the condition path uses. **No migration** — `equipment_state_changes` already
permits `from_condition = 'SCRAPPED'` and already carries a mandatory reason, actor and timestamp
(`V16__equipment.sql:54-70`), confirmed by reading the CHECK constraints before writing anything.

## The copy that became false, and what replaced it

The confirmation Rajeev triggered on staging read *"Scrapping cannot be undone. Its condition can
never be changed again, and it drops off the equipment list."* Both of those claims stop being true
the day this ships. Replaced with:

> Scrapping takes it off the equipment list, and its condition can no longer be changed here. Only
> a Temple Admin can bring it back, and they must record why.

The second paragraph — the record staying readable, and the *Needs repair* steer — is **unchanged,
word for word**, because both sentences are still true and the steer is what stops most wrong
scrappings before they happen.

The same claim was made three more times in the file's own prose, and all three were rewritten:

| Where | Was | Now |
|---|---|---|
| File doc comment (`:49-52`) | "it is the only one that cannot… names that consequence in the words the reader needs — 'cannot be undone'" | says the dropdown is what closes, and adds a paragraph on the one way back and why the confirmation is not weakened by it |
| `ChangeConditionForm` doc (`:398`) | "`SCRAPPED` is terminal by design in `EquipmentService`" | "`SCRAPPED` closes this form for good… since D-15 a scrapped machine can be brought back, but not from here and not by everybody" |
| `ConfirmScrap` doc (`:499-502`) | "It does not offer a way back, because there is not one. Whether scrapping should ever become reversible is a question outstanding with Rajeev" | records that the sentence was rewritten by the task that made it false, on the `MEAL_ALREADY_RECORDED` precedent, and why it now names the friction rather than an impossibility |
| Form sub-text (`:430`) | "Scrapped is the end of the road" | "Scrapped is the end of this form — the item stays on the register, drops out of the list, and only a Temple Admin can bring it back" |

The confirmation itself is **not weakened**: it still fires before anything is sent, still offers
exactly two buttons (Cancel, Scrap it), still keyboard-focuses Cancel, and offers no undo control
of its own. All four properties are asserted.

The only remaining occurrence of the string "cannot be undone" in the file is inside the
`ConfirmScrap` doc comment, quoting the old wording to explain why it changed. It is a historical
note, not a claim, and it never renders — the test asserts against `document.body`, not the source.

## Acceptance criteria, one by one

1. **Reinstating a scrapped item moves it to the condition given, writes a state-change row with
   `from_condition = 'SCRAPPED'` and the reason, and returns it to the default listing — on the
   real database.**
   `reinstatementBringsItBack` scraps an item, asserts the default `GET /equipment` returns 0 rows,
   reinstates to `NEEDS_REPAIR`, then asserts the default listing returns it at `NEEDS_REPAIR` and
   the item's history has 3 rows with `fromCondition = SCRAPPED`, the reason, and the actor's name.
   `reinstatementIsOneStateChangeRowFromScrapped` reads `equipment_state_changes` through the

   `from_condition = SCRAPPED`, `to_condition = GOOD`, reason intact. Both run against

## Design choices I made that were not specified

Named because the contract left them to me and a reviewer should be able to disagree:

- **On a scrapped item the header now offers *Bring it back* in place of *Change condition*, rather
  than alongside it.** The server refuses a condition change on a scrapped item with KMS-400043, and
  a button that can only ever produce that refusal is the pattern commit 81fd72f ("four screens stop
  offering what the server is right to refuse") went through the app removing. For a kitchen
  manager or cook on a scrapped item this means the header offers neither control, which is correct:
  they may not undo a disposal.
- **The condition picker opens on *Needs repair*, not *Good*.** A machine that was written off is
  rarely in good order the day it comes back, and a default of *Good* would let somebody return a
  broken machine as working on one press.
- **No second confirmation in front of the reinstatement.** D-15 puts the friction in getting there
  — the register hides scrapped items until the filter asks for them — and reinstating is itself
  reversible by scrapping again through the existing confirmation. A dialog in front of an act
  somebody has already worked to reach is one they learn to click past, which is the argument the
  file already makes for not confirming the three reversible conditions.
- **The form's submit reads *Put it back on the register*, not *Bring it back*,** so it does not
  duplicate the header button's label on the same screen.

### Why it belonged to this task and not to a follow-up

Same defect as the dialog copy, one file along. `SCRAPPED is terminal — a scrapped item drops out
of the default views but keeps its history` became a false statement in the codebase the moment
`reinstate` shipped, and this is the change that made it false. The project's rule, the same D-4 /
`MEAL_ALREADY_RECORDED` precedent this task already applied to the confirmation dialog, is that the
task which makes a sentence untrue is the task that rewrites it. The specific risk here is concrete
rather than tidiness: a javadoc on the condition enum is what the next person reads when deciding
whether reinstatement is possible at all, and one that says only "terminal" is how somebody later
re-adds the guard I deliberately kept *out* of `changeCondition` — or, worse, "simplifies" the two
mechanisms into one and removes the guard while believing they are tidying it.

### What it now says

Both halves, and in that order, so neither can be read without the other:

- **The ordinary path stays closed.** `changeCondition` refuses every condition change made after a
  scrapping, unconditionally, with `EQUIPMENT_SCRAPPED` — "there is no flag, no request field and
  no caller that reaches past that guard, and it must stay that way."
- **There is exactly one way back**, `EquipmentService.reinstate`, behind
  `REINSTATE_SCRAPPED_EQUIPMENT` (Temple Admin alone), insisting on a reason and auditing as
  `EQUIPMENT_REINSTATED` rather than as an ordinary condition change (D-15).
- **And it does not read as though scrapping is now casual.** The way back is described as "not
  this enum's business to make easy" and as "a deliberate, named, recorded act", with the two
  frictions named explicitly: the register still hides scrapped items until asked, and the screen
  still asks before it scraps anything.
- A closing paragraph states why the refusal and the way back are separate mechanisms that must not
  be merged, addressed to the future reader most likely to merge them.

The `SCRAPPED` constant's own one-line comment was extended to match, so a reader who jumps
straight to the constant is not left with the old claim.
