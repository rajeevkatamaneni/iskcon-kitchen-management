## The question the brief asked: does a re-enqueue *correct* stale rows, or only add to them?

**It corrects them.** No stop needed. `CalendarService.upsertDays` writes

```sql
ON CONFLICT (tenant_id, cal_date) DO UPDATE SET
    tithi = EXCLUDED.tithi, ... sunrise = EXCLUDED.sunrise, sunset = EXCLUDED.sunset,
    festivals = EXCLUDED.festivals, computed_at = now()
```

so each recomputed day overwrites the row already there rather than duplicating it — and the whole
row is recomputed under the new zone, because `precompute` resolves `offsetHours(timezone, start)`
and passes it into both `engine.computeRange` and `degToLocalTime`.

**One limit, which I have documented in the service rather than silently relied on.**
`precomputeForCurrentTenant()` starts its horizon at `LocalDate.now(zone).withDayOfMonth(1)` and runs
550 days forward. So **days before the first of the current month keep the tithi and sunrise they
were computed with under the old zone.** I judged that correct rather than a gap: what a temple
cooked last March is history, and rewriting the calendar underneath a meal already planned and
served would change the record of what happened. Everything the temple will plan against is
corrected. If Rajeev wants past days corrected too, that is a separate change to
`CalendarService`'s horizon and was not in this contract.

## Resolved since the first pass

### 1. `TENANT_UPDATED` was allocated, and is now used

I originally shipped this under `SETTINGS_UPDATED` and flagged that it should not stay there,
because that action is what a *temple admin* does to its own settings and this is the *operator*
changing what a temple is — the same reasoning that split `EQUIPMENT_REINSTATED` out from an
ordinary condition change. The work manager allocated `AuditAction.TENANT_UPDATED` and confirmed no
migration is needed (`V3__audit_events.sql:98` constrains `action` only by `length(action) > 0`, with
no enumerated CHECK). `TenantUpdateService` now records it and `TenantUpdateIT` asserts it by name.
`AuditAction.java` was written by the work manager and remains read-only to me.

### 2. `TenantDetail` carries the coordinates, and the local alias is gone

`latitude` and `longitude` are now on `TenantDetail` as **required** fields. The
`TenantForEditing = TenantDetail & {…}` alias I had declared in the edit page is deleted, the page
uses `TenantDetail` directly, and `String(temple.latitude)` is gone with it since the value is typed
`number`. My own vitest fixture dropped its `as unknown as TenantDetail` cast for a real
`(over: Partial<TenantDetail> = {}): TenantDetail` signature.

Making them required rather than optional immediately earned its keep: it stopped
`tenant-detail.test.tsx` compiling until its fixture carried them, which is exactly the failure mode
an optional pair would have hidden — a form posting a silently relocated temple.

The natural pattern is `?saved=…` plus the ref-guarded flash `/tenants` already uses. It needs

`useParams` and `useRouter`. My contract was later widened to that file for the fixture fields

corrected name is in the heading and the new 80G status in the details. Recorded as a finding.

### 2. Not smoke-tested by hand

I cannot drive a browser from here, so Commandment 5's manual check on a new user-facing surface has
**not** been done. What a human should check on staging: open a temple, press *Edit details*, change
the name and tick 80G, confirm the detail page reads back "Approved"; then change the timezone and
confirm the calendar rebuilds for that temple rather than staying on the old tithi.

### 3. The precompute horizon leaves past days on the old zone

Recorded above and in `TenantUpdateService.reprecomputeCalendar` rather than fixed. Accepted by the
work manager as a decision: rewriting the calendar underneath a meal already planned and served
would change the record of what happened. If Rajeev wants past days corrected too, that is a change
to `CalendarService`'s horizon and a task of its own.

### 4. No new error code, no new permission, no migration

As reserved. The slug refusal reuses `VALIDATION_FAILED` (`KMS-400001`) with a field-level message —
the same code `TenantProvisioningService` already uses for a bad timezone — so nothing was minted. If
a dedicated "this field is fixed at creation" code is wanted, that is the work manager's to allocate.

### 5. Two hardcoded timezone lists that must agree, and nothing makes them

`/tenants/new` and `/tenants/[id]/edit` each hold their own copy of the four offered zones (and the
three currencies). If one gains a zone the other will not, and the failure is silent: the screen
that lacks it appends the stored value as a bare option via `optionsFor`, so it still works but
reads differently. The fix is a shared module and it means editing `/tenants/new`, which nothing
this wave owns. Warned about in the `TIMEZONES` doc comment on the edit page and in the guard's
exemption comment, so both copies point at each other.
