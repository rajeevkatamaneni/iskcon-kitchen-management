`"type": "http"`, url `<api>/mcp`.

## The thread hop (the thing most likely to go wrong)

SDK 1.1.4 wraps every sync tool handler in `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`
(`McpStatelessServerFeatures.AsyncToolSpecification.fromSync`). The servlet transport then `block()`s the
request thread. So the handler runs on a Reactor worker, where neither `TenantContext` nor
`SecurityContextHolder` is set. Left alone, RLS would fail closed and the tool would report "no stock".

The fix is `AgentCallScope`. The transport's `contextExtractor` runs on the request thread after the
filter chain. It copies the tenant and the `Authentication`, never anything from the request itself,
into the `McpTransportContext`. The handler then sets both on whatever thread it runs on, and restores
the previous values afterwards, which is a clear on a pooled worker. A call that carries no tenant is
refused in words rather than run unscoped. I deliberately did not rely on `immediateExecution(true)`,
because that only works while the SDK's internals stay synchronous. Two tests cover this: one runs the
handler on another thread and checks the worker is clean afterwards, and the transport test goes
through the real SDK hop.

## Mounting

`/mcp` is a Spring MVC controller (`McpEndpoint`) that calls `transport.service(req, res)`. It is not a
`ServletRegistrationBean`, because a second servlet makes Spring Security reject the plain-string
`requestMatchers(...)` in `SecurityConfiguration`. POST goes to the transport. GET returns **405** from the
controller itself: the transport's own `sendError(405)` re-dispatches to `/error`, the Firebase chain
handles that dispatch, and the client got **401**. The first run measured this; see below. Both methods
declare `@PreAuthorize("hasAuthority('agent:read')")`.

## Acceptance criteria

- **Transport mounted at `/mcp`, server name `ikms`, Streamable HTTP.** McpTransportIT checks
  `serverInfo.name == "ikms"` and a `tools` capability, then gets 202 for `notifications/initialized`.
- **Two tools, neither takes `tenant_id`.** tools/list returns exactly `get_inventory` and `list_low_stock`,
  and the test asserts that `get_inventory`'s input schema has `item_name` and no `tenant_id`.
- **Reuse services, do not re-query tables.** Both tools call `InventoryItemService.list()` /
  `lowStock()`, plus `GlossaryService.lookup("kn")`. No SQL in `assistant/mcp`. (Deviation, see below.)
- **JSON, capped at 50, with English and Kannada name, on hand, unit, reorder level, cover.**
  InventoryToolsIT: 55 items gives returned 50, total 55, truncated; low stock gives 50 of 54. The Kannada
  name comes from that temple's glossary and is absent where there is none. Each row has `on_hand`,
  `available`, `unit` (Kg/gm/L/ml/pieces), `reorder_level`, `low`, `on_order` and `cover` (`{known:false}` when
  there is not enough history).
- **Only the caller's temple's rows.** Both temples have a "Toor Dal" with different stock and different
  Kannada. Tested at handler level and over HTTP: each gets only its own figure and its own Kannada.
- **Tenant context visible where the handler runs.** See "The thread hop". Tested on a separate thread
  and through the real SDK.
- **Descriptions written as API docs.** They are in `McpServerConfiguration` and cover when to use each
  tool, what comes back, every field, units, the 50 cap and what an empty result means.
- **Hand smoke test (Commandment 5).** Not done. This surface is for a model, not a person, and no
  `claude -p` run was made against it. That is T8.

## Not done / needs Rajeev

1. **Deviation in which services back the tools, raised here.** `LowStockAlertService`'s only public
   method, `sendDailyDigest()`, sends WhatsApp and email and writes a claim row. A read tool cannot call
   it. The tool calls `InventoryItemService.lowStock()` instead, which is the same list the digest reads.
   `StockFactsService` has no on-hand or reorder figure, so `get_inventory` calls
   `InventoryItemService.list()`, which is where `StockFactsService` is combined with them.
2. **Extra permission check.** Both tools need `MANAGE_INVENTORY`, the same permission the stock screen
   endpoints use. They depend on T5 adding the person's own permissions to the token's authorities, as
   the contract says.
3. **For T5 / conductor:** `AuthenticationFilter` is a `@Component`, so Boot also registers it as a plain
   servlet filter on `/*`, including `/mcp`. It will try to verify the agent JWT as a Firebase token, fail
   quietly, and clear `TenantContext` in its `finally`, which runs after the servlet. That looks harmless,
   but it is wasted work, and T5 should know.
4. Error-dispatch 401s: apart from GET, the transport's remaining `sendError` cases (body over 16 MB,
   shutting down) still come out as 401 through `/error`. I left these alone.
5. `McpTransportIT` has a nested `@TestConfiguration`, a stand-in for T5's chain, so it costs one extra
   test context. T7 should replace that with the real token.
6. Item search matches the English name, its spoken form and the Kannada glossary name. It does not
   match the `ingredient_aliases` table, because `StockItemView` does not carry aliases.
