## What changed

In `MealComposer.tsx`:

- **A corrected meal is never touched.** `adultsTouched = useRef(editing)` starts true for an
  existing meal, so its stored figure is never replaced.
- **Typing claims the box.** `setCount` marks Adults touched when the planner types it, marks the
  form changed, then calls `applyCount`, which holds the old rescaling body.
- **When the day is asked.** The day-context effect now runs when a feast still needs its occasion
  (as before), or when Adults is untouched, whatever the kind. Its deps are unchanged:
  `[date, kind?.needsOccasion]`.
- **What happens when the reply arrives:**
  - The occasion name is set exactly as before, on a kind that needs one.
  - If Adults is still untouched and `suggestedServings` is not null, the value goes through
    `applyCount("adults", n)`. That call goes through a ref refreshed on every render, so ticked
    preparations rescale against the current recipes and counters.
  - The form is not marked changed. A default is not an edit, so leaving straight afterwards asks
    nothing.
- **Hooks.** No hook is conditional. `exhaustive-deps` is off in `eslint.config.mjs`.

## Which meal kinds this reaches on the reseeded data (V137)

**Every kind the temple has.** On staging that is Breakfast, Lunch, Dinner, Festival feast, Deity
Offering if the temple still has it, and Event. The default does not check the kind.

It only shows on a date where one of the temple's occasions resolves **and that occasion has
`default_servings` set**.

**No seeded occasion carries default servings.** No migration or provisioning code sets
`default_servings`; `OccasionService` writes it only from a create or update request. So on
freshly reseeded data every date returns null and Adults opens at 0. The browser test needs a
Temple Admin to give an occasion a default servings figure first.
