## What each fix does

**(1) The work order.** `{(approved || status === "ISSUED") && mayIssue && <WorkOrder …/>}` —
`mayIssue` is the boolean the file already computes at `:109`. Gating the *card* rather than its
buttons is what stops the `/api/v1/work-orders/languages` call, because that query lives inside
`WorkOrder` and fires on mount. The `InlineNotice` a non-issuer already had ("Approved, and waiting
on the store.") is untouched. The card's own doc comment now says it is rendered for an issuer only,
so the next reader does not restore the unconditional render from the component's side.

**(2) The tile.** `href={maySeeSchedule ? "/staff-schedule" : undefined}`, with
`maySeeSchedule` = `TEMPLE_ADMIN || KITCHEN_MANAGER`, matching `staff-schedule/page.tsx:62`. The
tile, the count and the per-meal note are unchanged for everyone. `StatTile` was not opened — its
`href` was already optional.

**(3) The `/my-shifts` empty state.** Role-conditional copy. A volunteer still reads *"Browse
available shifts to offer seva."* — that is true for them, `SIGN_UP_FOR_SHIFTS` is theirs, and
"Available shifts" is in their sidebar. A manager or a cook now reads *"Shifts are signed up for by
volunteers, so this list stays empty for you. Who is covering which shift is on the Volunteer shifts
screen."* No link was added; it is still plain `<p>` text.

> **A deliberate reading of the acceptance criterion, please check it.** The criterion says "the
> `/my-shifts` empty state contains no instruction to browse shifts", flatly. I made it conditional
> instead, because the task text says "reword it so it does not offer *what the role cannot do*",
> and a volunteer *can* do it — `/shifts` exists and is in their nav. Removing the line for
> everybody would take a correct affordance away from the only role that has it. If you want it
> gone unconditionally, it is a one-line change to `app/my-shifts/page.tsx` and one assertion in
> `role-refusals.test.tsx`.

**(4) The staff-schedule empty state.** The `<Link href="/staff">` is gone; the sentence now reads
"Nobody is on the temple's staff register yet. An administrator adds them, and they will appear
here." That is what the file's doc comment at `:22-25` has claimed since A11. Removed for every
role, not just the manager, which is what the comment says. `Link` is still imported and still used
for the staff-name cells.

## What changed in it

Inverted rather than deleted, as asked, so the detail screen's own suite still answers "what does
the work-order card do for a non-issuer?" without a reader having to find `role-refusals.test.tsx`.
In "keeps the issue form away from somebody with no issuing rights":

```js
    // Nor the work order. It reads like a reading act — somebody walks the store room with the
    // sheet — but it is not one in the API: every endpoint behind that card is guarded by
    // ISSUE_INGREDIENTS, the language list it asks for on mount first of all, so offered to a cook
    // it 403s before a button is pressed. This screen follows the API rather than the intention
    // (T-002). role-refusals.test.tsx holds the other half: the same card, for a manager, with the
    // language list actually requested.
    expect(screen.queryByRole("button", { name: /download work order/i })).not.toBeInTheDocument();
    expect(screen.queryByRole("button", { name: /^print$/i })).not.toBeInTheDocument();
```

The old comment — "The work order is a reading act, so it is offered to whoever is looking." — is
gone with the assertion it justified. Print is now asserted too; the old test only named Download,
which would have let half the card come back unnoticed.
