## What was changed

- `testsupport/StubTokenVerifier` + `testsupport/StubVerifierConfiguration`: one shared verifier.
  Its overloads are the union of the 14 private variants; each call site was rewritten to produce
  the exact subject its old private copy produced (phone, email, emailVerified, token).
- `AbstractIntegrationTest`: `@Import(StubVerifierConfiguration.class)`, `@AutoConfigureMockMvc`
  (it is part of the key; 25 classes without it were a separate context), and a `@BeforeEach` that
  resets the shared verifier.
- 99+ nested `StubVerifierConfiguration`/`Stubs`/`StubTokenVerifier` classes deleted, their
  `@Import` lines removed, per-class `stubVerifier.reset()` in setup removed (the base does it).
- `perf/PerfStubVerifierConfiguration` deleted; its statement-recorder bean is now
  `perf/StatementRecordingConfiguration`, imported by ShoppingListIT and the perf classes only.
- Perf classes with `@TestInstance(PER_CLASS)` signed in from `@BeforeAll`; moved to `@BeforeEach`
  because the base resets before every test.
- `testsupport/SharedStubVerifierResetIT`: three new tests holding the base class to its reset (see
  "Why a guard test was added").
- Payment key ids in PaymentGatewayResolverIT, TenantPaymentSettingsIT and TenantPaymentWebhookIT made
  unique per test (see the mutable-state list).

## Mutable state shared by a context, and how each is handled

- **StubTokenVerifier** (test): reset before every test by `AbstractIntegrationTest`.
- **InMemoryTenantSecretStore** (production, unchanged): keyed by temple id. Every test creates its
  temples with database-generated ids (grep for fixed UUID literals in test sources: none), so a
  leftover secret belongs to a temple id that never recurs. Classes that write secrets already call
  `deleteAll` for their temples in `@AfterEach` (TenantPaymentSettingsIT, PaymentGatewayResolverIT).
- **PaymentGatewayResolver.built** (production, unchanged, no reset): every key id a test stores is
  now unique per test instance (`name + "_" + UUID`), in PaymentGatewayResolverIT,
  TenantPaymentSettingsIT and TenantPaymentWebhookIT. No fixed `rzp_` key id remains in test sources.
- **@MockBean / @SpyBean** (Scheduler, NotificationService, StockMovementService, StubPaymentGateway):
  Spring Boot's MockitoTestExecutionListener resets them after every test (MockReset.AFTER default).
- **StatementRecorder** (test, static): already JVM-wide before; `start()` clears it.
- **RecordingProbe, TestPaymentHandler, StubPlaces, StubGeocoder, StubRouter, MembershipIT's map
  stub, RecordingFactory**: each still lives in its own class's configuration, so its context is not
  shared with any other class.

## Why a guard test was added, and why that restarts the count

Looking for a reader for the negative control, no existing test turns red when the verifier reset is
removed. The tests that expect a 401 either send no token at all (ProfileIT, PlacesIT, TenantUpdateIT),
send a made-up token (AuthenticationFilterIT, AuthenticationFailureIT), or send `valid-token` only
when somebody is signed in (TenantProvisioningIT, AccessControlEnforcementIT), and in that last case a
leaked sign-in is still refused, because every one of those classes deletes its users after each test
and a known token with no account gets 401. So the leak is real but invisible to the suite as it was.

`testsupport/SharedStubVerifierResetIT` states the promise directly: test 1 asserts nobody is signed
in (catches a sign-in left by any earlier class in the shared context), test 2 signs someone in and
leaves them, test 3 asserts nobody is signed in again (catches it inside the class on every run). Three
tests added, none removed: the expected total on the final tree is 2629.
