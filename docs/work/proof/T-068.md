# T-068 — the giving page's cost per plate stops counting struck bills, and counts reduced ones at what is left

The one number in this product a stranger reads was summing every invoice in the last thirty days at
its face value. Wave 7's V103 gave an invoice two ways of being corrected, and it honoured neither: a
bill struck as *never owed* still counted as kitchen spend, and a bill the vendor had *reduced* still
counted at its full original amount. Both overstate what a plate costs.

## The change

`costPerPlate()`, before:

```sql
SELECT COALESCE(SUM(amount), 0) FROM vendor_invoices
WHERE invoice_date >= CURRENT_DATE - INTERVAL '30 days'
```

after:

```sql
SELECT COALESCE(SUM(amount - credited_amount), 0) FROM vendor_invoices
WHERE status <> 'VOIDED'
  AND invoice_date >= CURRENT_DATE - INTERVAL '30 days'
```

No tenant filter was added: RLS scopes this table, and a hand-rolled one would be the mistake the
project commandments name. `credited_amount` is `NOT NULL DEFAULT 0` (V103), so the subtraction needs
no COALESCE and an uncredited bill still contributes its whole amount. No API shape changed, so no
frontend test moves; none was run and none was touched.

## The judgment call: `status <> 'VOIDED'`, not `status IN ('PENDING','PAID')`

V103's CHECK admits exactly `PENDING`, `PAID`, `VOIDED`, so the two are the same query today. They
diverge the day a fourth status is added: the exclusion silently counts it, the inclusion silently
drops it. I chose the exclusion, on three grounds.

**1. Spend is the default state of an invoice row.** Money leaving the temple is what an invoice
*is*; a bill counts unless something positively says it was never owed, and "never owed" is the one
thing VOID means and the only concept in the product that means it. V103's own header states the rule
in that direction — a void "leaves the pay cycle entirely and every figure that sums invoices must
skip it". It names what to skip, not what to keep. A plausible fourth status (a DISPUTED bill, a
PARTIALLY_PAID one) is still real money and would want counting; the exclusion gets that right by
default and the inclusion gets it wrong by default.

**2. Which mistake is findable.** Counting one status too many overstates a total, and a total is
checkable — a treasurer can add up the invoice list and see it. Dropping a status understates it
invisibly, and this figure is a *division*, so the gap never shows as a gap; it shows as a plausible,
slightly cheaper plate that nobody has any reason to question. This file already made that exact call
once, in `spendShares` for T-024, and said why: quietly rounding awkward money out of a donor-facing
figure is the one thing this page must not do.

**3. Direction of harm.** Understating spend understates the cost of a plate, so a donor paying for
"one plate" is quoted less than a plate costs and the temple silently carries the difference — the
"made-up number quoted back at them by a donor" this method's own doc comment exists to prevent.

The honest cost of the choice, recorded so nobody has to rediscover it: a future `DRAFT` status — a
bill not yet real — *would* be wrongly counted by this query, and nothing would fail to say so. The
reasoning above is written into the method's doc comment, so whoever adds a fourth status finds it at
the line they would have to change.

## Acceptance criteria

1. **`costPerPlate()` excludes voided invoices and subtracts credited amounts.** The query above; the
   control proves both halves are load-bearing, separately.
2. **A test that asserts the figure *moves*.** Both new tests read the cost per plate, correct one
   bill, and read it again, asserting the new value:
   - `voidingABillDropsTheCostPerPlate` — ₹64,000 + ₹20,000 over 2,000 plates cooked reads **42**;
     the ₹20,000 bill is struck as never owed; the same page then reads **32**. The plates never
     move, so the whole of the ₹10 is the struck bill leaving the spend.
   - `creditingABillLowersButDoesNotRemoveTheSpend` — ₹64,000 over 2,000 plates reads **32**; the
     vendor credits ₹20,000 of it; the page then reads **22**. Not 32 (credit ignored) and not
     absent or zero (the bill treated as though it had been voided) — a credited bill still counts,
     at what is left of it. That second assertion is the one that makes VOID and CREDIT different
     behaviours here rather than one behaviour with two names.
   A shape-only test would have passed against the broken code in both cases — the old query returned
   a perfectly well-formed number, it was simply the wrong one — which is exactly what the control
   demonstrates.
3. **Backend suite green on my files.** Only two test classes in the tree touch this endpoint
   (`grep -rln "costPerPlate\|donations/page" backend/src/test/java/` → `GivingPageIT`,
   `TenantUpdateIT`), and both were run: 21 of 21 passed. Per the brief I did not run the full suite;
   that is the release agent's job on the merged tree.
4. **Negative control.** Above: named for this task, anchored, proved applied, `--rerun-tasks`,
   restored through an `EXIT` trap, failures read and confirmed as mine.
