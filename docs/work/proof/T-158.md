# T-158 — Saving a shift on the volunteers edit screen keeps its meal link

## Who legitimately unlinks

Nobody on a screen. The only unlink is the API one: a `PUT /api/v1/shifts/{id}` that leaves the
three link fields out (or sends them null). I kept that exactly as it is.

Evidence:

- **Server.** `ShiftService.update` writes `meal_date`, `meal_kind`, `meal_event_name` from the
  request every time. Its comment says why: *"An edit rewrites every field, the link included … That
  is the only way to undo a link that was made in error."* `requireWholeMealLink` only refuses half a
  link (date without kind, kind without date, or an event name without a date); all three null passes.
  `UpdateShiftRequest` documents the link as "or nothing at all where it is not posted for one".
- **The test.** `ShiftMealLinkIT.anEditCanUnlinkAShift` does a raw PUT with no link fields and asserts
  the shift reads back unlinked and counts by its hours again. It is an API-level test; no screen is
  involved. Unchanged, and green below.
- **Every caller of `api.updateShift`.** Two in the tree:
  `frontend/app/volunteers/[id]/edit/page.tsx` (this fix) and
  `frontend/components/planner/ShiftLayer.tsx`, which always sends the planner meal's link on update.
  Neither offers "unlink". Searched the whole repo for `/shifts/` and `api/v1/shifts`: the only other
  hits are `lib/api.ts`, tests, backend controllers and docs. No other API client exists.
  `VolunteerShiftController` has no update route.
- **Docs.** D-14 in `docs/work/DECISIONS.md` defines linked versus unlinked shifts but says nothing
  about a user removing a link. `grep -rni unlink docs` finds only D-14's, the CHANGELOG's and T-034's
  descriptions of unlinked shifts, and T-155's proof reporting this defect. No doc describes an unlink
  control.

So the server comment's "undo a link made in error" has no screen today. The planner can only link to
the meal it is opened on, and this screen now keeps whatever is stored.

## The fix

`save` in the edit page now builds `{ ...readShiftForm(form), mealDate: shift.mealDate ?? null,
mealKind: shift.mealKind ?? null, mealEventName: shift.mealEventName ?? null }`, with the loaded shift
as the source. `ShiftView` already carries the three fields back from `GET /shifts/{id}` (`api.ts`
~:3240, backend `ShiftService.SELECT` selects them), so no change outside the contract was needed.

I left `shift-form.tsx` alone. `readShiftForm` reads a form, and the form has no link box. The planner
layer takes its link from the meal it was opened on; this page takes it from the stored shift. One
helper would have to know about both.

## Both behaviours, each with its test

New file `frontend/__tests__/shift-edit-keeps-meal-link.test.tsx`, 5 tests. Each checks
`Object.keys(input)` for the three keys before checking values.

- **Keeps:** "keeps a meal link through a change of title and capacity" (Lunch, event null) and
  "keeps an event's link, event name included" (`mealEventName: "Janmashtami"`).
- **Unlinked stays unlinked:** "leaves an unlinked shift unlinked, sending the three fields as null",
  and "treats a shift whose view carries no link fields at all as unlinked" (the three keys deleted
  from the fixture, since `ShiftView` types them optional). **Nulls, not absent keys.** The server's
  request record reads both as null. All three null is the one "no link" shape `requireWholeMealLink`
  accepts, and `?? null` on each field means `undefined` can never turn into a mix it would refuse
  with KMS-400125.

## Date change: matter of taste for Rajeev

If the date is moved on the edit screen, the shift stays linked to its original meal. This matches
T-155's layer, which says a moved shift stays linked to its meal. So the two screens agree. Test: "keeps
the shift on its original meal when the date is moved". The downside T-155 already noted: the planner
only lists shifts for the day shown, so a shift moved off its meal's day does not appear under that
meal.
