### One judgement call: the secret is a `data` source, not a `resource`

The brief said the secret is referenced nowhere in `infra/` today and that I would be adding
the wiring. I added it as:

```hcl
data "google_secret_manager_secret" "maps_api_key" {
  secret_id = "kms-${var.environment}-maps-api-key"
}
```

The repo's own precedent (`google_secret_manager_secret.smtp_password`) is a **resource**
created without a version, and that is the better long-term shape — it makes a fresh
environment work with no new prerequisite. I did not use it, for one reason: the secret
already exists outside state, so a `resource` block makes `plan` propose **creating** it
(`1 to add`, and an apply that 409s), and the only way to a no-op plan would be
`terraform import` — a **write to the shared remote state**, invisible in the git diff, during
a wave with other agents in the tree. That is not a repair to make unilaterally, so it is
listed under *Needs Rajeev* instead.

A data source was chosen over a bare `"kms-${var.environment}-maps-api-key"` string because
either way a fresh environment now needs the secret to pre-exist (Cloud Run validates a secret
mount at deploy time), and the data source fails at **plan** time with *secret not found*
rather than ten minutes into an apply. `DEPLOYMENT.md` Step 2 now documents that prerequisite.

## 4. Two things `plan` still proposes, neither of them the six

### (a) `API_BASE_URL` — a seventh drifted variable, and it is **not fixable inside this contract**

Found by doing the verification the brief asked for. It is on the API service, absent from
`main.tf`, and `terraform apply` deletes it exactly like the six. Consequence, from
`infra/deploy.sh:110-113`: it is the only way the Settings screen can show a temple
administrator where their payment provider should send webhooks — without it they are handed a
bare path with no host.

It is different in kind from the six, which is why I did not simply add it. `deploy.sh:118` sets
it **deliberately**, with a reason that is correct as far as it goes: Terraform cannot reference a
service from inside that service's own definition, so `google_cloud_run_v2_service.api.uri`
is a dependency cycle.

Why I stopped rather than fixing it:

- The live value is the hash-form URL `https://kms-staging-api-bnpkv5hfrq-el.a.run.app`. The
  constructible form (`...-278207420486.asia-south1.run.app`) is a *different string*, so
  building it in `main.tf` produces a plan **change**, not a no-op — and changes a live value.
- Hardcoding the hash URL in `main.tf` is wrong: that file is environment-generic and
  environment-specific values live in `terraform.tfvars`.
- `lifecycle.ignore_changes` cannot name one element of a list of `env` blocks. Ignoring
  `template[0].containers[0].env` wholesale would ignore *all* env drift and destroy the very
  property this task exists to restore.

The clean fix is the one `cors_allowed_origins` already uses for the identical chicken-and-egg
problem: a `variable "api_base_url"` defaulted to `""`, set in `terraform.tfvars` after the
first deploy, and the `--update-env-vars` flag dropped from `deploy.sh`. That needs
`infra/environment/variables.tf`, `infra/environment/terraform.tfvars` and `infra/deploy.sh`
— **three files outside my contract**, so I have not touched them. See *Needs Rajeev*.

**Consequence for the acceptance criterion, stated plainly:** the criterion as written — no
change to any environment variable on either service — is **met in full on the worker and met
for all six named variables on the API**, and **not met on the API for `API_BASE_URL`**, which
was not in the task and cannot be closed without widening the contract. I did not adjust the
file until the plan looked tidy.

### (b) The `scaling` block — pre-existing, not an environment variable, not mine

`- scaling { manual_instance_count = 0 -> null; min_instance_count = 0 -> null }` appears on all
three services **including `frontend`**, which this task never touches, and it is present in the
`HEAD` baseline plan above. It is **not** the `template.scaling` the config sets. `terraform state show`
proves there are two different blocks:

So the config's scaling is correct and clean; the diff is the provider's newer service-level

changes deployed behaviour.
