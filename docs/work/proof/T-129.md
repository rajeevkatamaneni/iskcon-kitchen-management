sent."* The screen hides it and says why, the endpoint refuses it (`KMS-400147`), the scorecard's

on staging, which is what gave Heritage Fresh Dairy 0%.

**Two judgement calls are written up below rather than buried:** why the rule is *not* a schema
CHECK, and what happens to PO-2026-0036's activity trail.

## The two judgement calls

### 1. The rule is enforced in the service, not by a CHECK constraint

The brief left this open. I did not add `CHECK (vendor_abandoned = FALSE OR sent_at IS NOT NULL)`,
and the reasoning is written into V120's own header so the next reader finds it beside the code.

**Why V118's CHECK belongs in the schema and this one does not.**
`purchase_orders_abandoned_is_a_cancellation` ties two columns written by a single `UPDATE`, and no
decision about the product could ever make a no-show on a live order meaningful — it is a coherence
rule about a row's state. Today's rule is a different kind of thing. It is a **policy about what a
person is allowed to assert**, chosen from three defensible options on one day, *against* the
coordinator's own recommendation to leave it alone — and the losing option has a real case behind
it, an order placed over the telephone and never marked sent. Policy that may be revisited belongs
where reverting it costs an edit to one method, not a second migration and a second rewrite of
stored rows.

A smaller second reason: a CHECK here would constrain a row's **history** rather than its state.
`sent_at` is written by *Mark sent* and `vendor_abandoned` by *Cancel*, minutes or days apart and
possibly by different people, so the pairing is not atomically coherent the way V118's is.

**And one concrete cost it would have carried, worth recording because it is invisible from inside
this task's contract.** `VendorPerformanceIT.abandoned()` (`backend/.../vendor/VendorPerformanceIT.java:834-837`)
builds its fixture by inserting a cancelled order with **no `sent_at`** and then setting
`vendor_abandoned = true`. A CHECK would break that file — which is **outside my contract and held by
T-091 right now**. That is not why I decided as I did, but it means: *if the constraint is ever
added, that fixture has to gain a `sent_at` first.* Flagging it for the ledger rather than acting on it.

### 2. PO-2026-0036 is corrected; its activity trail is not rewritten

V120 clears `vendor_abandoned` on every cancelled order with `sent_at IS NULL`. Two reasons it has
to be a migration and not a note to the coordinator: the scorecard reads the column directly, so
leaving the row keeps scoring a supplier 0% forever; and there is **no in-app route to untick it**
— `CANCELLED` is terminal in `PurchaseOrderService` and nothing transitions out of it.

**The trail line is deliberately left alone.** PO-2026-0036 carries a `po_events` row reading
*"… — recorded as never delivered by the vendor."* `po_events` is append-only by design (`V26:85`)
and that line is the honest record of what the coordinator actually did on 10 September. What was
wrong was never that the act happened; it was that the act **scored somebody**. So the scoring input
is corrected and the history of the act is not. `cancel_reason` is untouched too — it only ever held
the operator's own words, never the appended sentence.

**Consequence to expect on staging, said plainly:** after the deploy, PO-2026-0036's screen shows no
*Never delivered* badge, and its activity trail still says the vendor never delivered it. That is
intended, not a bug.

**The migration runs its correction per tenant**, because `purchase_orders` carries
`enable_tenant_rls()` and the migration role is unprivileged — a bare cross-tenant `UPDATE` would
match nothing through the policy's `NULLIF`, report success, and correct nothing anywhere. That
exact silence is what `AbandonedWithoutSendingMigrationIT` exists to catch.

### And the two things the brief asked me to confirm rather than assume

**`sent_at` is stamped in exactly one place.** Still true.
`grep -rn "sent_at" backend/src/main` returns three hits in `PurchaseOrderService` — the write at
`:263` (the *Mark sent* action), and two reads at `:647` / `:667`. The other `sent_at` in the
application belongs to the `communications` table (`CommunicationService:266`), a different table
entirely. So "was this order sent?" has one answer, and both the screen and the service read it.

**`sentAt` is already on `PurchaseOrderView` in `api.ts`.** Confirmed by reading it (line 2082). No
`api.ts` change was made or needed.

## What was built

**Server.** `PurchaseOrderService.cancel` refuses the pairing, after the transition check and before
the `UPDATE`, so a refused request leaves no half-applied cancellation:

```java
if (vendorAbandoned && po.sentAt() == null) {
    throw new ApplicationException(ErrorCode.PO_NEVER_SENT_TO_VENDOR, Map.of("purchaseOrderId", id));
}
```

It reads `sentAt` and not the status, because a cancelled order's status no longer says whether it
was ever sent — which is precisely the case being refused.

**Screen.** `const wasSent = po?.sentAt != null;` gates the tick box. When it is false the box is
replaced, not removed, by:

> This order was never sent, so there is nothing to hold the vendor to. Cancelling it counts against
> nobody's delivery record.

The cancellation itself is unchanged: the reason is still required, the button is still there. The
submit also sends `wasSent && vendorAbandoned` — not because the state can be true there today (the
box is not rendered), but so the screen cannot post a request it knows the server will refuse.

**Scorecard sentence.** Was: *"Drafts are left out, and so is a cancellation nobody has marked
against the vendor. An order cancelled because the vendor never delivered it does count, and scores
nothing."* The first half became true again under the ruling, but the second half was now loose — it
implied any cancellation could carry the mark. Now:

> Drafts are left out, and so is a cancellation nobody has marked against the vendor. An order that
> was sent and then cancelled because the vendor never delivered it does count, and scores nothing;
> an order that was never sent cannot be marked that way at all, so nothing a vendor was never told
> about reaches these figures.

## Acceptance criteria

**1. The box is hidden on an unsent order, and its absence is explained.** Done.
`does not offer the never-delivered box on an order that was never sent, and says why` asserts both
halves — the input gone, and *"This order was never sent, so there is nothing to hold the vendor
to."* present — and fails when the gate is removed (control, above). No `api.ts` change was needed;
verified by reading `PurchaseOrderView` at `frontend/lib/api.ts:2082` rather than assuming.

**2. The server refuses it.** Done. `PurchaseOrderService.cancel` throws before the `UPDATE`;
`an order nobody sent cannot be cancelled as one the vendor never delivered` asserts `409` +
`KMS-400147` **and** that the order is still `DRAFT` with `vendorAbandoned` false and no cancel
reason, so the refusal is total. `marking an order sent is what opens the never-delivered box`
sends the identical request twice, differing only in whether *Mark sent* was pressed in between —
without it, "the endpoint always refuses this" would explain a green run just as well.

**3. `PO_NEVER_SENT_TO_VENDOR(400147, 409)` used as given.** Done, and `ErrorCode.java` was not
opened. Asserted by code in the test above, not by string.

**4. The scorecard sentence.** Done — reworded as quoted above.
`vendor-performance.test.tsx` (15 tests, unedited) stays green.

**5. The CHECK-constraint question, answered explicitly.** No constraint; a service guard plus a V120
data correction. Reasoning above and in V120's header.

**6. Existing rows do not break the migration, and PO-2026-0036 is decided.** Nothing can break: the
migration adds no constraint and only clears a flag. `AbandonedWithoutSendingMigrationIT` migrates a
throwaway database to V119, seeds **two** temples each with an unsent-abandoned order and a
sent-abandoned one, then runs the rest — and asserts the unsent claims are gone, the sent ones
survive, and the trail lines are untouched. Two temples on purpose: one would pass against a
migration that adopted the first tenant and stopped.
