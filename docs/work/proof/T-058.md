## The twelve items

### Built

**6b — the removal form was off the screen. Fixed.** `frontend/app/volunteers/[id]/page.tsx`.

The form shipped inside the row's Actions `<td>`, and a cell is the one place on this screen that
cannot hold a form. Every column carries `whitespace-nowrap` from `components/ds/table.ts`, so a
column is never squeezed below what its contents ask for — right for a date or a status, fatal for
a form. The cell took the width its widest control wanted, the table outgrew the page, and the
`overflow-x-auto` wrapper turned that into sideways scrolling *inside* the table. The note is the
field the coordinator is required to fill in, so the mandatory half of the form was the half off
the screen.

It is now a row of its own spanning all four columns, directly beneath the volunteer it is about,
capped at `max-w-prose`. A full-width row cannot widen one column, so it cannot do this again.
T-080's reason for putting the form on the row rather than in a dialog is unchanged and still right
— the note only means anything if it was written about this particular person — and a row directly
under the name keeps that rather than trading it for a modal.

Verified by measurement above, and guarded by a new test that asserts the structure rather than
pretending to assert pixels: the controls sit in a cell whose `colSpan` equals the table's rendered
column count, and in a different `<tr>` from either volunteer's row. It fails against the markup as
it shipped.

**5 — `ShoppingListService.updateLine`. Real, and worse than recorded. Fixed.**

The item said it was harmless because `included` is `NOT NULL`, so an omission fails loudly. **It
did not.** The field was a primitive `boolean`, Jackson gives a missing primitive its Java default,
and `false` is a perfectly good value for a `NOT NULL` column. A `PATCH` that said nothing about
whether to buy something quietly unticked it. The column never saw a null and so never had the
chance to refuse. That is the same shape as the `suggested_vendor_id` defect that opened this batch:
a value nobody sent, written as though they had. The control above proves it — 204, not a refusal.

No screen can reach it: `updateShoppingListLine` in `lib/api.ts` types `included` as a required
boolean, so the only client always sends it. So this is a latch, not a bug anyone met. `Boolean`
and `@NotNull` — an omission is now KMS-400001 naming the field, on the existing validation
handler, and **no request that succeeds today behaves any differently**. New test covers both
halves: the refusal, and the line being untouched by it.

**12 — `PeriodNav`'s `@param children`. Fixed.** It offered "the planner's 'Duplicate last week'",
deleted 2026-09-05. Checked all five callers: the calendar's `<Legend />` is the only one that
passes children at all; the planner, the issue log, vendor performance and cost per serving pass
none. The docblock now says that.

**13 — `PlacesController` said "Both endpoints". Fixed.** There are three
(`grep -c "@GetMapping"` → `3`). Changing "Both" to "All three" would have been wrong, though: the
sentence claims they "answer with an empty result rather than an error", and `/available` does not
— it answers `false`, which is its entire job. The javadoc now names the three and draws that
distinction.

### Needs Rajeev — three parks and one item I am refusing to guess at

**6 — the native validation bubble. This is not five instances. It is how the whole app works.**

I checked the premise before acting on it, and the premise does not hold against today's tree.

*What the app does today.* Every mandatory field in the application is enforced by the browser's
`required` attribute, and the browser's grey bubble — "Please fill out this field." — is what a
person sees when they leave one blank. **83 of them, across 39 files.** Not a corner: `app/settings`,
`app/donations`, `app/invoices`, `app/vendors`, `components/staff/*`, `components/planner/*`,
`components/RecipeForm.tsx`, and the five sightings already named.

*The convention the brief says to match does not exist for this case.* `fieldErrors` appears in four
files. In every one of them it is fed from `ApiError.byField()` — errors the **server** sent back
after a submission. Not one line of the app sets a field error for a blank box before submitting.
So there is no "error styling every other missing field uses" to copy; there is no other missing
field doing anything else.

*Who it affects.* Everyone who fills in a form: Temple Admin, Kitchen Manager, Kitchen Staff,
Volunteer Coordinator, and the platform operator provisioning a temple.

*So in plain terms:* the browser's own pop-up is the app's only way of saying "you left this blank",
everywhere, and changing that is a decision about all 39 form files rather than a fix to the four or
five screens where it has been noticed.

*The strongest argument against my own position.* The coordinator's point is a good one and I think
it is right: two of the five sightings shipped in the last twenty-four hours, which means people are
still writing new ones, and a fix that leaves the sixth just as easy to write has not fixed
anything. That argues for doing something now rather than filing it. My answer is that it argues
for doing it **once, properly, everywhere** — not for converting the handful inside this task's
paths and leaving the app with two conventions and no rule saying which is which.

*Options.*

1. **Leave it.** Costs nothing, changes nothing. The bubble is consistent, accessible, and
   translated by the browser — which the product's own error text is not. But it is plainly not what
   you want, or you would not have flagged it twice in a day.
2. **Fix only what is inside this task's paths** (volunteers, equipment, components — about 35 of
   the 83). Cheap, and I think wrong: it would leave `app/settings`, `app/donations`,
   `app/invoices`, `app/orders` and the rest on the bubble, with nothing recording which screens got
   which treatment.
3. **One shared mechanism, adopted across all 39 files, as its own task.** A small helper beside
   `components/Field.tsx` — which already owns `FIELD_ERROR`, `aria-invalid` and `aria-describedby`
   — that checks a form's required controls on submit, returns a `Record<string, string>`, and lets
   every form render it the way the four `fieldErrors` screens already do. Plus one line in the
   design-system guard so the 40th file cannot go back to the bubble. That is the only version where
   "the sixth instance is no longer easy to write" is true.

*My recommendation: option 3, as a task of its own, not folded into this wave.* It needs two things
from you that a cleanup wave has no business inventing: **the sentence a blank required field
shows** (the browser says "Please fill out this field."; the product would want something in its own
voice, and that is copy you own), and **a decision on whether `required` stays on the element as
well** — it should, because it is what a screen reader announces, but it also means the browser will
still refuse the submit before our code runs, so the helper has to be wired to `noValidate` forms to
be reached at all. That last point is not a detail; it changes every one of the 39 files.

*Hard to reverse?* No. Each form can be moved independently and moved back.

Two things I did **not** do, deliberately: I did not touch `app/orders/[id]/page.tsx` — it is
outside this task's paths, and the `closeNote` rule there is correct and I would not have changed
it anyway. And I did not take error code `400151`: nothing here needs one, because the four
existing `fieldErrors` screens carry plain sentences with no `KMS-` code at all.
