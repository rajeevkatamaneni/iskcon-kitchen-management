**Deviations from the brief, decided inside the contract:**
- **No JPA entities.** The app has two entities in total (Tenant, User). Every module uses JdbcTemplate, and so does this one. That leaves nothing for `ddl-auto=validate` to check. The boot below still validated Flyway against V161 and started. `assistant_pending_actions` is not touched: that is S4.
- **"10 turns" = 10 question+answer pairs**, as `chat.py` counts them. The prompt has the same shape as `chat.py`'s, and unanswered questions are left out.
- **SSE written by hand on the request thread**, not `SseEmitter`. `TenantContext`/RLS live on the request thread, and an executor thread would save the reply with no temple set. The cost is that one servlet thread is held per run, for up to about 60 s.
- **Accept header:** the frontend must send `Accept: text/event-stream, application/json`. Otherwise Spring answers a refusal with a body-less 406 instead of the JSON error with its code. This is stated in the controller javadoc, for T13.
- **Events.** Before any event, a first comment frame `: run <id>` is sent. The events are:
  - `text {text}`
  - `tool_call {tool, summary}`: the name without `mcp__ikms__`, and `key=value` arguments cut at 120 characters. No tool results are relayed.
  - `done {messageId, runId}`
  - `error {code, message, action, runId}`
  - `proposal` is not emitted.
- **How each failure is mapped:**

  | Failure | Run status | Code |
  |---|---|---|
  | Runner refused, unreachable, 503 busy, non-200, `exit_nonzero` / `spawn_failed`, CLI `is_error` result, stream ended with no result | FAILED | KMS-500008 |
  | Runner `timeout` line, or the api's own deadline (`kms.assistant.runner.timeout`, default 75 s, past the runner's 60 s) | TIMED_OUT | KMS-500009 |
  | Browser left | FAILED | none (nobody was shown one) |

  In every one of these cases no reply is saved. Input tokens are input + cache writes + cache reads. The run row's model is updated to the one named in the CLI's init event.
- **Budgets:**
  - They count every run started today in the temple's timezone, including RUNNING, FAILED and TIMED_OUT runs.
  - They are checked under a per-temple `pg_advisory_xact_lock`, so two requests sent together cannot both pass.
  - The temple's limit is checked before the person's.
  - Tests change limits, runner URL and deadline through package-private setters on `AssistantSettings`, so the IT adds no new Spring context.

**Acceptance criteria and how each was verified** (all in `AssistantApiIT` against Testcontainers Postgres as the unprivileged role, with a fake runner on a real port):
- SSE order and content: `text, text, tool_call, text, text, done`. The tool call is `get_inventory` / `item_name=toor dal`, and no tool result is relayed. The runner was sent the profile, the bare prompt, `…/mcp` and an agent token that verifies as this user, temple and conversation with scopes `agent:read`/`agent:propose` (`oneMessage`).
- Messages and run row saved: USER then ASSISTANT (with run_id). The run is SUCCEEDED with model, input 18012, output 95, cost 0.041235, tool_calls 1, finished_at and duration. An `ASSISTANT_RUN` audit row exists whose after-state holds no question text. The `assistant.runs{status=SUCCEEDED}` counter went up by 1. The list shows a title and the detail shows both messages (`oneMessage`).
- History window: with 12 answered turns plus one failed question, the prompt holds turns 3–12, oldest first, and leaves out the failed one (`historyWindow`).
- Kitchen Staff and Volunteer: 403 on all four endpoints, and the runner is never called (`refusedWithoutPermission`).
- Another person at the same temple gets 404 KMS-400030 on read and on send, and their list is empty (`anotherPersonsConversation`). Another temple gets 404, and its list is empty (`anotherTemplesConversation`).
- Budgets:
  - Person limit: 429 KMS-400192 as JSON, with a RUNNING row counted. The runner is not called, the refused question is not saved, and the `budget_refusals{scope=person}` counter goes up by 1. A colleague can still use the assistant (`personalLimit`).
  - Temple limit: 429 KMS-400193 for a second person. Another temple is unaffected (`templeLimit`).
- Runner down (closed port) and runner busy (503) both end with an `error` event carrying KMS-500008, a FAILED row and no reply.
- Timeouts:
  - The api's own deadline (1 s against a runner that pauses 3 s per line) gives KMS-500009, TIMED_OUT, a return in under 2.9 s, and the fake runner sees its caller leave.
  - The runner's own `timeout` line gives the text so far, then KMS-500009, then TIMED_OUT.
- Browser disconnect mid-answer: the run is closed FAILED with no code and no reply, and the fake runner sees the connection dropped (`browserLeaves`).
- Blank message: 400 KMS-400001, and no run row is written.
- Stream parsing: unit-tested on the recorded stream and on edge cases, including no partial messages, an `is_error` result, junk lines and summary truncation (`RunStreamReaderTest`).
