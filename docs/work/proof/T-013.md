# T-013 — Goods accepted into stock can be sent back to the vendor, through the ledger

Rejection only ever worked at the gate. `goods_receipt_lines.rejected_qty` is a field of the
receiving submission, so weevils found the next morning, or 50 kg keyed when 5 arrived, had no path
at all. This adds a sixth movement type, the migration that lets the database accept it, an endpoint
behind `MANAGE_INVENTORY`, and the screen to use it.

## The model: partial, cumulative returns — and KMS-400141 cannot happen

**Decided deliberately: a receipt line can be returned against many times, each time up to what is
left of it.** The docket's own two examples settle it. Weevils are found in two sacks of a
twenty-sack delivery, not in the delivery; and "50 kg keyed instead of 5" needs a return of 45 out of
50, not of 50. A whole-receipt model cannot express either. The rule the row states — *you cannot
return more than was received* — is also only meaningful in a partial world: in a whole-return model
the quantity is never chosen, so it can never be wrong.

The cap is therefore cumulative across every return already recorded against that line: 20 kg back
today and 11 kg back tomorrow is 31 against a 30 kg line, and each request on its own is under the
received quantity. That is `ReturnToVendorIT.theCapCountsEveryReturnAlreadyMade`.

**So `ALREADY_RETURNED` (KMS-400141) describes a state that cannot exist, and I have not used it.**
There is no "these goods have been returned" flag anywhere — there is a quantity, and a remaining
quantity, and returning more than remains is `RETURN_EXCEEDS_RECEIVED` (KMS-400140) whether the line
was returned against before or not. Nothing else is a candidate for it either: a double-submitted
return is answered by the idempotency key with the return already recorded, which is a success and
not a conflict.

**Recommendation for Rajeev: retire KMS-400141 before it ships.** I have not touched `ErrorCode.java`
— it is a shared file and the code is yours to amend. Codes are permanent once released, so a number
that means a case that cannot occur is worth removing now rather than carrying for ever.

## Who sums `stock_movements`, and what I did about each

Grepped `FROM stock_movements` and `movement_type` across `backend/src/main`. Nine readers, in three
groups.

**Sum everything, no type filter — a negative `RETURN_TO_VENDOR` row correctly reduces them, which is
the whole point.** No change needed or made:

| Reader | What it computes | Effect |
|---|---|---|
| `InventoryItemService.onHandBase`, `batchStockBase`, batch aggregation | the Inventory screen | returned goods leave on-hand |
| `ShoppingListService.onHandBase` | what to buy | returned goods become buyable again |
| `SufficiencyService` | can we cook this meal | correct |
| `FefoAllocator.loadPositiveBatches` | `HAVING SUM(...) > 0` per batch | a batch returned to zero drops out of allocation — correct |
| `WorkOrderService` | `MAX(received_date) GROUP BY batch_id` | safe: the return movement leaves `received_date` NULL and `MAX` ignores NULLs, so a batch's arrival date is untouched |

**Filter by type or reference — checked and unaffected:**

- `IssuedFromStoreService` filters `movement_type = 'ISSUE'`. Untouched.
- `StockMovementService.list` takes an optional `MovementType` filter; the new value simply becomes
  selectable, which is right.
- `DonationVoidService` and `StockMovementService.compensateAllFor` select by
  `reference_type`/`reference_id`. A return is stamped `PURCHASE_ORDER` + the PO id.
  **One thing to know:** `compensateAllFor` today is only ever called with `MEAL_PLAN`
  (`InventoryConsumptionService:120`), so nothing reverses PO movements as a set. If a "undo this
  order's receipts" path is ever added, it would also reverse returns booked against that PO. Noted,
  not guarded — guarding a caller that does not exist is the wrong shape.
- `IngredientService` uses `EXISTS` to refuse deleting an ingredient with history. More rows, same
  answer.

**And the group whose meaning genuinely changes — three readers of `goods_receipt_lines.received_qty`,
all outside my path contract, all left alone deliberately.** These are the "a SUM goes on compiling
when the meaning of a row changes underneath it" case, and each is a separate judgement rather than
one fix:

1. `VendorPerformanceService.countLines` — the **fill rate** is `SUM(received_qty) / ordered`. A
   quantity received and then returned still counts as filled. Arguably wrong for `SPOILED` and
   `NOT_DELIVERED`: the vendor did not, in the end, deliver it.
2. `VendorInvoiceService.expectedReceivedValue` — the value the invoice is checked against.
   Arguably right as it stands: the vendor billed for what they delivered, and a return is settled by
   a credit note, which this application has no concept of.
3. `ShoppingListService` PO-outstanding — `ordered − received` on live orders. A return does not put
   the quantity back on the list. Arguably wrong for `NOT_DELIVERED` (the order really is short) and
   right for the rest (whether to re-buy is a decision, possibly from a different vendor).

**These need Rajeev**, and 1 and 3 in particular. Fixing them means editing `vendor/` and
`shoppinglist/` and changing the meaning of two reports, which is not a thing to do inside a
contract that names neither.

## The negative control

Full log: `docs/work/proof/control-T-013.log`. Script:
`<scratchpad>/control-T-013.sh`.

**What it patched, and why that and not the Java.** The defect this row exists to prevent is a
runtime one: the enum is mirrored in a database CHECK, and a value added on one side alone compiles
perfectly. So the control removes **only** the `'RETURN_TO_VENDOR'` literal from V108's CHECK and
leaves every line of Java, every test and the whole frontend exactly as written. That reproduces the
precise failure mode on demand, rather than merely showing that deleting the feature breaks tests of
the feature.

All five conditions: `set -e` at the top; `grep -c` of the anchor with the count asserted
(`expected exactly 1`, aborting otherwise); the tree proved changed before anything ran; `--rerun-tasks`
so no up-to-date shortcut could hand back the earlier green; restore through an `EXIT` trap **and**
an explicit `cmp` afterwards; and the artefact named `control-T-013.log`, read from the top rather
than by its exit code.

**The first attempt aborted on its own guard, and that is in this proof rather than dropped.** It
used `git diff --stat` to prove the tree had changed — but V108 is a *new* file and therefore
untracked, so git reported nothing however well the patch applied:

```

CONTROL: patch applied

CONTROL: ABORT — the tree did not change; V108 is untracked or unmodified
```

## Not done / needs Rajeev

1. **KMS-400141 `ALREADY_RETURNED` is unused and, under this model, unreachable.** Retire it before
   release. I did not edit `ErrorCode.java`. (Section 1 above has the reasoning.)
2. **Three readers of `goods_receipt_lines.received_qty` now mean something slightly different and
   were left alone** — the vendor fill rate, the invoice expected value, and the shopping list's
   PO-outstanding. All three are outside the contract, and two of them are report-semantics decisions
   rather than bugs. Details in "Who sums `stock_movements`" above.
3. **A return does not change the purchase order's status and does not re-raise the quantity on the
   shopping list.** Chosen deliberately — flipping `RECEIVED` back to `PARTIALLY_RECEIVED` would mean
   mutating the order on the strength of a later, separate event, and whether to re-buy is a decision
   (possibly from another vendor) rather than an arithmetic consequence. Flagging it because the
   `NOT_DELIVERED` case is the one where the opposite is arguable: the order genuinely is short.
4. **No hand smoke test.** Commandment 5 wants a new user-facing surface driven by hand, and this adds
   one ("Deliveries received" plus the return form on the order screen). I cannot do it: builders do
   not deploy, and the change is not on staging. It needs driving on UAT as a storekeeper once it
   ships — record a delivery, return part of it, confirm the Inventory screen falls by exactly that
   much and the delivery row still reads what it read before.
5. **The endpoint is `POST /api/v1/goods-receipts/{receiptId}/returns` behind `MANAGE_INVENTORY`,
   which is a different permission from the receiving endpoints beside it** (`MANAGE_PURCHASE_ORDERS`).
   That is what the row reserved and I think it is right — taking stock off the books is the store
   room's job — but it means a person who can record a delivery cannot necessarily undo it, and vice
   versa. Worth a look at the role table before release. I did not open `RolePermissions.java`.
