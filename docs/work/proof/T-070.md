## The one thing built — a draft and a cancellation are not spend

**What was wrong.** `GivingPageController.spendShares` builds the donor-facing *"where last month's
money went"* breakdown by summing every purchase order line raised in the last thirty days. Its only
filter was the date. An order typed up and never sent, and one sent and then withdrawn, both counted
as money the temple spent on that category.

**Why it stopped being dormant.** I originally filed this as a question rather than a change, on the
grounds that it was invisible because unpriced lines fell out at the `HAVING ... > 0`. **That ceased
to be true on 2026-09-11**, when T-134 made `createPo` fill a blank `expected_price` from
`vendor_supplies.last_price` for every line naming a catalogue ingredient. Drafts raised through the
new shopping-list panel have carried prices since this morning, so the suppression is gone and the
defect is live on a page volunteers read. `PO-2026-0045` on staging carries ₹62 a litre.

**The change.** One clause:

```sql
WHERE po.status NOT IN ('DRAFT', 'CANCELLED')
  AND po.created_at >= CURRENT_DATE - INTERVAL '30 days'
```

**Both DRAFT and CANCELLED, on the coordinator's ruling, with the reasoning on the record so it can
be reversed in one line.** The sentence on the screen is *"where last month's money went"*. An order
nobody has sent is money that has not gone anywhere; a cancelled one is money that never will. If
committed-but-undelivered spend is ever wanted here, that is a different sentence on the page rather
than a different `WHERE` — and the javadoc says so, so the next reader finds the option rather than
guessing at the omission.

**The two things carried into the comment, both as asked.**

- The precedent was already written down twice. `PurchaseOrderService:117-123` spells out the
  identical habit at length for the invoice order picker — *"DRAFT is excluded. A draft has not been
  sent … CANCELLED is excluded. The order was withdrawn"* — and `VendorPerformanceService:241` keeps
  the very clause under the name `LIVE_ORDER`. The comment cites both, so nobody re-derives it.
- **Its own neighbour knew.** `costPerPlate()`, forty lines above in the same file and on the same
  screen, filters `status <> 'VOIDED'` correctly (T-010). One reader of a table knowing about a
  state and its neighbour not knowing is the cleanest instance of this defect class in the codebase,
  and the comment now says that in those words so it is findable.

**And a second finding that came out of writing the test, which is worth more than the fix.** The
`purchaseOrder(...)` fixture helper in `GivingPageIT` inserted no `status`, so it took V26's column
default — **`DRAFT`**. Both existing spend-share tests were therefore asserting their percentages
against orders nobody had sent, and passing, *because the production query counted drafts too*. The
fixture was wrong in exactly the way the query was, the two agreed, and nothing went red. That is
the same defect seen from the test side, and it is why a green suite could never have found this.
The helper now takes a status and defaults to `RECEIVED`; the reason is in its javadoc.

### 1. The donor-facing spend figure — BUILT, and here is what you are being asked to ratify

This was written up as a question and then authorised mid-task, so it is no longer a decision you
need to take before anything happens. It is one you can **reverse in one line** if you disagree, and
you should see the reasoning either way.

**What the app did until tonight.** The giving page at `/donate` shows *"where last month's money
went"* as a percentage breakdown — Dairy 40%, Vegetables 30%, and so on. It built those percentages
from every purchase order line raised in the last thirty days, whatever became of the order.

**Who it affects.** Every **Volunteer** — they are the only role that can open `/donate` — and
through them, anybody a volunteer repeats the figure to.

**So in plain terms:** an order the temple typed up and never sent, and an order it sent and then
cancelled, both counted on a donor's screen as money spent on that category.

**What changed.** Both are now excluded: `WHERE po.status NOT IN ('DRAFT', 'CANCELLED')`.

**The argument for it,** in the coordinator's words on the record: the page's own sentence is *"where
last month's money went"*, and an order nobody has sent is money that has not gone anywhere, while a
cancelled one is money that never will.

**The strongest argument against, stated fairly.** `CANCELLED` is uncontroversial. **`DRAFT` is
arguable**, and I said so before being overruled: a draft raised this morning is often a real order
a day from being sent, so excluding it makes the thirty-day window lag reality slightly, and the
page is a percentage breakdown in which everything is relative anyway. If you want committed-but-
undelivered spend counted, the honest fix is to change the **sentence on the page**, not the `WHERE`
clause — and the javadoc says exactly that, so whoever picks it up next finds the option rather than
re-deriving the omission.

**How to reverse it:** delete `'DRAFT', ` from one clause in `GivingPageController.spendShares`, and
change the two assertions in `draftsAndCancellationsAreNotSpend` that cover the draft half.

**Nothing about it is hard to undo.** No migration, no stored data, no shape change on the wire.
