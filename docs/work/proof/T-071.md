# T-071 — a credit note settles a variance, and the variance stops showing the full discrepancy

`withVariance` computed the informational price variance against the **gross** invoiced amount. It
now computes it against what is actually owed — `amount - credited_amount - expectedReceivedValue` —
which is the same arithmetic `restateStatus` (`:220`) and `InvoicePaymentService` (`:62`, `:208`)
already use to answer "how much does this bill come to".

**Files changed:** all three inside the contract.

| `backend/src/test/java/org/iskcon/kms/invoice/VendorInvoiceIT.java` | yes (granted up front) |
| `docs/work/proof/T-071.md` | yes |

`InvoiceCorrectionIT.java` was granted and **not** modified — its invoices are all direct (no PO), so

already existed.

## The diagnosis, and the two parts of the brief I declined to change

The brief offered `v.amount().subtract(v.creditedAmount()).subtract(expected)` as a suggestion and
invited a different answer. I agree with the suggestion, and record why the two obvious alternatives
are wrong:

- **`expectedValue` must not move.** It is the worth of the goods *actually received* at the PO's
  line prices — a fact about the delivery. A credit note does not change what arrived; it changes
  what the temple is being asked to pay. The credit belongs on the invoice side of the subtraction
  and nowhere else.
- **The client does not need a second figure.** `amount` and `creditedAmount` are both already on
  `VendorInvoiceView`, so any screen that ever wants the gross variance back can compute it. Adding
  a `grossVariance` field would put a second account of one fact on the wire for no present reader.

**Nullability checked in the schema, not inferred from the record type**, as asked:
`V103__invoice_void_and_payment_reversal.sql:69` — `ADD COLUMN credited_amount NUMERIC(12, 2) NOT
NULL DEFAULT 0`, with `:74` `CHECK (credited_amount >= 0 AND credited_amount <= amount)`. It is
never null, so no null guard is needed and none was added; a comment in the code says so and cites
the migration, because the next reader will ask.

The check constraint also means the netted variance can never be driven below `-expected` by a
credit, so no new lower bound is introduced.

## Acceptance criteria

| Criterion | How it was verified |
|---|---|
| A credited invoice shows a variance on what is owed, not on the gross | `varianceIsNetOfCreditNotes`: PO of 30 kg received @ ₹45 (expected ₹1350), invoiced ₹1400, credited ₹50 → `variance` is `0.0`, and `expectedValue` is still `1350.0`. Fails with `50.0` when the fix is removed. |
| A partial credit still shows what is left in dispute | `aPartialCreditLeavesTheRemainingVariance`: same fixture, credit ₹20 → `variance` `30.0`. This is the test that distinguishes *netting* from *clearing the variance whenever any credit exists*. Fails with `50.0` without the fix. |
| The uncredited case is unchanged | `varianceSurfacesWhenPricesDiffer` (pre-existing, unmodified) still `50.0`; and `varianceIsNetOfCreditNotes` asserts `creditedAmount: 0.00` with `variance: 50.0` **before** recording the credit, so the same fixture proves both states. Both pass with and without the fix. |
| Both `list()` and `get()` covered | Each of the two new tests asserts on `GET /api/v1/vendor-invoices/{id}` (`get()`, `:116`) **and** on `GET /api/v1/vendor-invoices` (`list()`, `:107`). Both call sites of `withVariance` are exercised. |
| `./gradlew test` green for the tests touched | 21/21, output above. |

The credit is recorded through the real `POST /api/v1/vendor-invoices/{id}/credit` endpoint, not by
writing `credited_amount` directly, so the test exercises the flow a temple admin would actually
take. That needed a `TEMPLE_ADMIN` user in `setUp` alongside the existing staff and volunteer; the
class's `tearDown` already deletes `users`, and a credit writes no `invoice_payments` row, so no
teardown change was needed.

## Not done / needs Rajeev

- **No hand smoke-test.** Commandment 5 wants a user-facing surface driven by hand. I did not do
  that and could not: this is a backend read-path change with no screen of its own, the invoice
  screen that renders `variance` is under another builder's contract in this same wave, and driving
  staging would mean testing a revision that does not contain this fix. **The netted figure has not
  been seen in a browser.** Worth one look on the invoice detail and payables screens after the wave
  deploys — credit a PO-backed bill and confirm the variance moves.
- **A voided invoice still gets a variance computed.** `withVariance` does not special-case
  `VOIDED`, so a struck bill shows a variance for a debt that is no longer owed at all. It is
  arguably harmless — the void mark is on the face of the row and the screen shows it — and it is a
  different question from this one, so I left it. Flagging it rather than fixing it, because deciding
  whether a struck bill should show a variance, a zero, or nothing is a product call.
- **Nothing outside the contract was touched.** In particular `backend/src/test/java/org/iskcon/kms/donation/GivingPageIT.java`, which mentions `VendorInvoiceService`, was neither opened nor run — it is T-010's and it does not call `withVariance`.
