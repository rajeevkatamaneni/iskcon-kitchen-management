## 1. Does `concurrentSendsDeliverOneCopyEach` already discriminate? Yes — proved, not argued

The coordinator's mid-task message closed this question in favour of Rajeev's reading and told me
not to referee it. The control settles it empirically anyway, because condition C2 is exactly the
experiment, so it is recorded here as evidence rather than as an opinion.

C2 puts the code into the dangerous future state — lock gone, `ON CONFLICT DO NOTHING` on the
recipients INSERT, compare-and-swap removed — and runs the test **as written**:

```
FAILING TEST: two admins pressing Send at once send one copy each, not two
org.opentest4j.AssertionFailedError: [one letter, one copy — never the whole letter to the whole audience twice]
expected: 1
 but was: 2
	at app//org.iskcon.kms.communication.CommunicationRetryIT.concurrentSendsDeliverOneCopyEach(CommunicationRetryIT.java:405)
```

Line 405 is `notificationCount(unreachable)`. The test fails on the **copy count**, before it ever
reaches the status assertion — admin B notified the whole audience a second time. So the
notification assertions are sensitive to the letter going twice; they were merely never given the
chance to observe it, because the unique index killed B first. Whoever said they were insensitive to
this race was wrong.

The test's own comment claimed the 409 assertion "is the assertion that would fail the day it does
not" stay free of `ON CONFLICT`. **Both fail, and the count fails first.** I corrected the comment in
that direction, as instructed, and left every assertion and the anchoring untouched.

## 2. The strong control: lock removed *and* the index neutralised

Per the coordinator's amendment I did **not** drop the index — that needs DDL the app role does not
have, and would have proved something about a database rather than about this code. `ON CONFLICT DO
NOTHING` neutralises it from the application side instead, which is both privilege-free and the
exact edit the change exists to make safe.

| Condition | Patches to the service | Result |
|---|---|---|
| baseline | none | **14/14 SUCCESS** |
| **C1** | lock removed from `recordSend` + `ON CONFLICT DO NOTHING` | **14/14 SUCCESS** — the compare-and-swap alone refuses the second send |
| **C2** | C1's patches **+ compare-and-swap removed** | **13/14, 1 FAILED** — the letter goes twice |
| **C3** | compare-and-swap removed, lock and index intact | **14/14 SUCCESS** — see §4, this is a finding |

C1 is the claim in the brief, and it holds: with `lockCommunication` gone from `recordSend` and the
unique index unable to stop anybody, `two admins pressing Send at once send one copy each, not two`
still passes — 409, `KMS-400086`, one notification per devotee, three recipient rows. C2 removes
only the compare-and-swap from that same state and the test fails, so C1's green is the
compare-and-swap's doing and nothing else's.

**Consequence, and it is the point of the task:** an `ON CONFLICT DO NOTHING` on the recipients
INSERT is now harmless. C1 ran with that clause in place. B's UPDATE matches nothing, B is refused,
B never reaches `queueFor`, and the copy counts stay at one — the end-to-end test stays green *for
the right reason instead of for the index's reason*. This was checked, not predicted.

## 3. The new test

`theSendStatementItselfRefusesASecondTransition` — two connections on the unprivileged app role,
both running `recordSend`'s UPDATE verbatim, no lock, no INSERT, no index anywhere near it. The
second is asserted to **block** on the row first (otherwise the zero would be satisfied by a
transaction that never raced), then returns **0 rows**. It also asserts the row is **visible** to
that connection, because under RLS an invisible row updates zero rows just as convincingly and would
prove nothing about `status`. Same shape as `RowLevelSecurityIT`.

## 4. What I could not do, stated plainly

**No end-to-end test can be sensitive to the compare-and-swap while the lock stands, and C3 proves
it.** Removing the predicate with `lockCommunication` still in front of it leaves all 14 tests green.
That is not a gap in the control — it is the mechanism working, and it is *why* the small
statement-level test exists.

The honest limit that follows: **deleting the predicate from the service does not fail the new test
either**, because that test runs its own copy of the statement. It proves the mechanism the service
now relies on is real (a compare-and-swap on the app role under READ COMMITTED with RLS refuses the
second transition); it does not prove the service still contains it. The two are tied by the copied
statement and by review, not by execution. Anyone who deletes the predicate is caught by C2's
arrangement, not by CI. I would rather say that than let the test's name imply more than it does.

## 7. Not done / needs Rajeev

- **No hand smoke-test.** Commandment 5 wants a user-facing surface driven by hand, and I could not
  do it: this is a two-admin race that needs two simultaneous sessions and a held transaction, which
  is not reproducible by pressing a button. The user-visible behaviour it protects — a second press
  of *Send* answering "this has already been sent" rather than a 500 — is unchanged from T-096 and
  already covered end to end. There is no new screen and no new copy.
- **The new test does not fail if the predicate is deleted from the service.** Stated in full in §4.
  If that is not acceptable, the only thing that would close it is a seam in `recordSend` that lets a
  test interpose between the read and the UPDATE, and I did not add one on my own authority — it
  would mean weakening the lock or adding a test-only hook to a method whose whole subject is
  atomicity.
- **`ON CONFLICT DO NOTHING` was not left in the recipients INSERT.** C1 shows it would now be safe,
  but it was not in the brief and it changes what a genuine conflict does — today one is still a
  fact worth hearing about. Worth a task of its own if the 500 in that path is ever seen in the wild.
- **Wave hygiene noted, nothing acted on:** T-013's files are in the tree (`receiving/`,
  `MovementType.java`, `V108__return_to_vendor.sql`, `frontend/lib/api.ts`). Every backend run here
  booted Flyway cleanly, so V108 was syntactically valid throughout. `ErrorCode.java` and
