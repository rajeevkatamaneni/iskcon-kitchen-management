No main notification code changed. The mechanism is in how the test contexts share Quartz, and production behaves correctly (see below). NotificationIT, NotificationFallbackIT and the other granted tests were therefore not needed and not run. The cascade is untouched.

## The mechanism

There is one cause, and it produced both failure modes.

1. **Two clustered Quartz nodes with the same name, in two different Spring contexts.** The E2E class's comment said its property set matched `BackgroundJobIT`'s, so the two shared a context. That was never true. `@MockBean JavaMailSender` and `kms.notifications.email.from` are both part of Spring's context cache key, so the E2E class always built its own context. Both contexts started a clustered scheduler named `kms-scheduler` against the same `qrtz_` tables. Clustered Quartz lets any node with that name run any trigger. The other node is `BackgroundJobIT` and `RecipeDocumentE2EIT`'s context, which has no mocked mail sender and no from address.
2. **The trigger is written inside the caller's transaction, but Quartz nudges its thread before the commit.** `notify()` is `@Transactional`. Spring's `LocalDataSourceJobStore` gets its connection through `DataSourceUtils.doGetConnection`, which I checked with javap on spring-context-support 6.1.13, so the trigger insert joins that transaction. `QuartzScheduler.scheduleJob` signals the local scheduler thread immediately. The thread wakes, queries, sees no committed trigger, and sleeps for its idle wait: 30s by default, randomised to between 24 and 30s. Nothing signals again after the commit.
3. So **whichever node's sleep ends first runs the send**:
   - If it is the E2E node, the send happens 24 to 30s later. That broke the old 20s await (failure mode 1). fc03d6a raised the await to 30s, which only moved it to the edge of the same window.
   - If it is the other context's node, the cascade runs with that context's beans. WhatsApp fails (no settings), SMS fails (no provider), and email fails (no sender or from address), so the notification ends FAILED (failure mode 2).

### Suspects ruled out, with evidence

- **Cascade order or stop condition.** `NotificationDispatcher.dispatch` tries every channel and marks FAILED only after all three fail. The attempts above show all three tried in order. The cascade did what it should with the beans it had.
- **SMS treated as terminal.** No. SMS FAILED, then EMAIL was attempted.
- **The `@MockBean` stubbed in `@BeforeEach` while a scheduler thread is already sending.** No. The E2E context's email adapter reports "mail sender present"; the failing send reported "from address unset", which is a different context. The stub is also set before `notify()` runs.
- **Another class's teardown deleting rows mid-send.** No. The row existed, was read by the dispatcher, and was FAILED when asserted, with three attempts recorded. Classes run one after another in one JVM.
- **The retry policy marking FAILED after N attempts.** No. `KmsJob` logged "completed on attempt 1". `dispatch` does not throw on channel failures, and FAILED is written by `markFailed` after one pass through the cascade.

## The fix

Two properties on the E2E class, one for each half, plus a forced reproduction in the test itself:

- `spring.quartz.scheduler-name=kms-scheduler-notification-e2e`. Quartz partitions every `qrtz_` table by scheduler name, so no other context's node can see these triggers. It also stops this node running `BackgroundJobIT`'s probe jobs, whose parked and abandoned counters are read from that context's meter registry only. The lock rows for the new name are created by Quartz itself: `StdRowLockSemaphore` carries `INSERT INTO {0}LOCKS(SCHED_NAME, LOCK_NAME) VALUES ({1}, ?)` (checked with javap on quartz-2.3.2), and `kms_app` has INSERT on `qrtz_locks` through V1's default grants. Nothing else hardcodes `kms-scheduler`: the only occurrence in main sources and migrations is V6's seed.
- `spring.quartz.properties.org.quartz.scheduler.idleWaitTime=1000`. The node that owns the trigger finds it within a second of commit, not after half a minute.
- The test now holds the caller's transaction open for one second after `notify()`. That forces the nudge-before-commit ordering on every run, so a regression fails every time rather than one run in a few thousand.
- The await came down from 30s to 10s, because time was never the cause. The assertion now prints the attempts, so any future failure names its channel and reason.

Why not change `NotificationService` instead, for example scheduling after commit? In production the API process runs no scheduler at all (`auto-startup: ${KMS_WORKER_ENABLED:false}`). Its sends are always found by the worker's poll, never by a nudge, so the race does not cost production anything. Scheduling after commit would give up the atomicity the code has today: a notification committed with no job behind it, stuck PENDING if the process died in between.

## Acceptance criteria

- **The proof names the mechanism, with far-side evidence.** See the mechanism section: the failing CI run's captured log ("from address unset", 20s after queueing, a second `kms-scheduler` instance), plus a local reproduction reading back `notifications`, `notification_attempts`, `qrtz_triggers` visibility before and after commit, and `qrtz_scheduler_state`.
- **The fix addresses that mechanism, and the 30s await is not raised.** A separate scheduler name removes the other node; a 1s idle wait removes the missed nudge. The await is lowered to 10s.
- **At least 5 consecutive green runs of both classes together, with `--rerun-tasks`, through the lock.** 5 of 5, outputs above.
- **NotificationIT and NotificationFallbackIT still pass if the cascade was touched.** The cascade was not touched and no main notification logic changed (two comments only), so they were not run.
- **Negative control with every condition.** Snapshot plus `trap EXIT` restore; whole-line anchors counted exactly once under `set -e`; `cmp -s` proved the patch applied; `--rerun-tasks`; task-named artefacts, with the log's first line checked; real failing output pasted; restore proved with `cmp`.

## Not done / needs Rajeev

- **The control shows the idle-wait half deterministically. The separate-name half shows as FAILED only in the diagnostic run and the CI log, not in a control of the final test.** With a 1s idle wait kept and only the name removed, the E2E node almost always wins, so the other node would steal the send only occasionally. A control of that variant would be a rare flake, not a deterministic failure, so I did not run it.
- **`RecipeDocumentE2EIT` (outside my contract) probably has the same late-pickup exposure,** if its document request also schedules inside a transaction. It shares `BackgroundJobIT`'s context and scheduler name, so it cannot be stolen from by the E2E node any more, but a nudge before commit would still leave its send waiting for that node's 24 to 30s idle wait. I did not check it. `DocumentGenerationService.java` is also being edited by someone else right now (per `git status`).
- **Production note, not a defect:** a send queued by a request is picked up by the worker's poll, so it can take up to about 30s after the request to go out. That is how it was designed, and nothing here changes it.
- No user-facing surface was added, so there is nothing to smoke-test by hand.
