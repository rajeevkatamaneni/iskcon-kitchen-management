## The policy

```
WITH CHECK (EXISTS (SELECT 1 FROM users u
  WHERE u.id = platform_audit_events.actor_user_id
    AND u.firebase_uid = NULLIF(current_setting('app.auth_uid', true), '')
    AND u.role = 'SUPER_ADMIN'
    AND u.tenant_id IS NULL))
```

This is the brief's version, unchanged. The caller is identified by `app.auth_uid`, which only the authentication filter sets, from the verified token. Nothing comes from a request parameter. `u.tenant_id IS NULL` repeats `users_tenant_matches_role` (V2), which already makes every SUPER_ADMIN row tenantless. It is written out so the policy reads on its own, since the same uid can also hold temple accounts (V52).

## Every writer of platform_audit_events, and who it names as the author

The only INSERT in main code is `AuditService.PLATFORM_INSERT`, reached only through `recordPlatform`. It binds `actor.getUserId()`. No SQL function or trigger inserts into the table: `grep platform_audit_events` over the migrations finds only V9's DDL, V49/V50's `make_append_only`, V65/V66/V133's policies and V66's FK change, plus comments. `delete_tenant_cascade` does not touch the table. The only thing that changes existing rows is V66's `ON DELETE SET NULL` foreign key, which is an update, not an insert, so this policy does not apply to it. No test writes a platform audit row through the application's own database connection naming anyone else.

The `recordPlatform` callers:

- **`NoticeService.raise` / `withdraw`** (`NoticeController`, behind `RAISE_PLATFORM_NOTICE` / `WITHDRAW_ANY_PLATFORM_NOTICE`). The author is the signed-in person. For an operator that is their own SUPER_ADMIN row, and they write through this policy. For a temple admin it is their account at this temple, written through V133's notice escape.
- **`TenantExportService.export`** (`TenantController`, `DELETE_TENANT`), entity `TENANT`. The author is the signed-in operator.
- **`TenantDeletionService.delete`** (`TenantController`, `DELETE_TENANT`), entity `TENANT`. The author is the signed-in operator.
- **`MasterRecipeService.create` / `update` / `delete`** (`MasterRecipeController`, `MANAGE_RECIPE_LIBRARY`), entity `MASTER_RECIPE`. The author is the signed-in person. `LibraryLoader.load` and `RecipeImportService` do not call `recordPlatform`.
- **`PendingAccountClaim.adopt`**, the operator's first sign-in, entity `USER`. The author is the pending SUPER_ADMIN row that was just bound to the verified uid in the same request, so it already carries `app.auth_uid` when the audit row is written. That is the operator's own row. `PendingAccountClaimIT` "the platform super-admin signs in for the first time" is green below.
- **`EmploymentBanService`** (raise, amend, retract, check). Always a temple user, behind `MANAGE_STAFF`, written through V133's ban escape, never through this policy.
- **`NoticeService.raiseFromPlatform`** (automation) writes no platform audit row, by design.

Nothing legitimate names an author other than the connected person, so the rule did not need widening and no stop was needed. No existing operator IT asserts a mis-authored write.

## Status decision: `u.status = 'ACTIVE'` left out

- A disabled operator cannot be signed in. `AuthenticationFilter` refuses `!user.isActive()` with ACCOUNT_DISABLED before any endpoint runs.
- Nothing in the application disables or re-enables an operator. `UserManagementService.setStatus` only finds rows at the admin's own temple (`tenant_id = app.tenant_id`), and a SUPER_ADMIN row has no temple. Operators are created outside the application. So no operator audit write happens as part of disabling or re-enabling one.
- **The one path it would change:** the filter calls `pendingAccountClaim.attemptClaim` before its `isActive` check, and `findClaimablePending` does not filter on status. So a pending operator row seeded as DISABLED today binds its uid, writes the claim's audit row, and is then refused with ACCOUNT_DISABLED. With the ACTIVE condition, that audit insert would raise inside the filter, and the person would get a failure instead of the plain "account disabled" answer.
- It adds nothing on the paths that can be reached and breaks one that can, so it is left out. The migration header says so.

## Acceptance criteria

All cases run as the unprivileged `kms_app` role through the application's tenant-aware DataSource. `app.auth_uid` is the operator's uid and no temple is set, exactly as the filter leaves an operator request. Inserts are written without RETURNING (T-192's helper). Each method makes one assertion.

- **(1) Operator, own id, PLATFORM_NOTICE admitted.** `platformAuditOperatorAsThemselvesWritesANotice`. Green in runs 1 and 3, and green in the control. PlatformNoticeIT's operator tests are green in run 3.
- **(2) Operator, own id, an entity type operators write today, admitted.** Operators write no ban row today: every ban write is behind `MANAGE_STAFF`, which SUPER_ADMIN lacks, as T-192 found. So this uses **`TENANT`**, which `TenantExportService.export` (TENANT_EXPORTED) and `TenantDeletionService.delete` (TENANT_DELETED) write. `platformAuditOperatorAsThemselvesRecordsATempleAction`. Green in runs 1 and 3, and green in the control. TenantExportIT and TenantDeletionIT are green in run 3.
- **(3) Another Super Admin as author: refused.** `platformAuditOperatorCannotNameAnotherOperator`, one invocation for `TENANT` and one for `PLATFORM_NOTICE`. `PLATFORM_NOTICE` shows V133's notice escape does not let the row back in. Green in run 1, each red in the control.
- **(4) A temple user as author: refused.** `platformAuditOperatorCannotNameATempleUser` (a different person), and `platformAuditOperatorCannotNameTheirOwnTempleAccount` (the operator's own account at a temple, same uid), each for `TENANT` and `PLATFORM_NOTICE`. Green in run 1, all four red in the control.
- **(5) Random UUID: refused.** `platformAuditOperatorCannotNameAnIdThatIsNobody`. Before V134 the foreign key refused it, and now the policy does. It is included because it shows the change of refusing layer. Also added: `platformAuditOperatorCannotNameNobody`, a NULL author, which was a real hole that no foreign key covers. Green in run 1, admitted (red) in the control.
- **T-192's cases unchanged and passing.** Green in runs 1 and 3. Under the control they stay green, because V133 is still applied.
- **Negative control:** run 2 above.
- **`platform_audit_superadmin_read` untouched:** V134 contains no statement naming it. `platformAuditIsSuperAdminOnly` and T-192's operator read-back are green.
