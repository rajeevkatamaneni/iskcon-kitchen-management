## What was built

**Migration `V107__shift_attendance.sql`** adds two nullable columns to `shift_signups` —
`attended BOOLEAN`, `attendance_recorded_at TIMESTAMPTZ` — with a CHECK that they move together
(`shift_signups_attendance_whole`), in the shape of V95's meal link. **No backfill statement at all,
and the file says why:** the table is tenant-owned under FORCE RLS and Flyway runs unprivileged here,
so a cross-tenant `UPDATE` would match nothing and report success. Every existing signup is unmarked,
NULL is the honest reading of every one of them, and two nullable columns defaulting to NULL *are*
the backfill. `ALTER TABLE` is DDL and runs as the table's owner; the policy governs the DML this
migration does not do.

`attendance_recorded_by` was deliberately **not** added — nothing would read it, and this repo
refuses columns nothing reads (`IngredientRequestStatus.java:29-32`, in those words). Noted below as
something to design with the correction endpoint rather than half-guess now.

**Server.** `POST /shifts/{id}/attendance` and `DELETE /shifts/{id}/signups/{userId}`, both on
`ShiftController`, both `@PreAuthorize("hasAuthority('MANAGE_VOLUNTEER_SHIFTS')")`. `SignupService`
gained `recordAttendance` and `releaseVolunteer`; the existing `release(volunteerUserId, shiftId)`
keeps its signature and behaviour and now delegates to the same private `releaseSignup`, so the
coordinator's removal frees the spot, promotes the waitlist head, cancels the pending reminders and
shows on the roster exactly as a volunteer's own release does. `VolunteerShiftController` is
**unchanged** — not one line.

**Screen.** `/volunteers/[id]` (`ShiftRosterPage`) gained an *Attendance* column — a ticked-by-default
checkbox per active volunteer and one *Save attendance* submit — and a per-row *Remove*. Once
recorded the column reads `Came` / `Did not come` / `Not marked`, and the Released list now carries
the release time.

## Findings

### Who already counts `shift_signups`, and does any of this change a figure they compute?

Every reader was enumerated (`grep -rn shift_signups backend/src/main`). **Answer: no figure moves,
and the reason is structural** — the coordinator's release writes the same `released_at` column
through the same code path as the volunteer's, so every counter that already handled a release
handles this one; and attendance adds a column nothing sums yet.

| Counter | Reads | Effect |
|---|---|---|
| `SignupService.signedUpCount` (capacity guard), `availableShifts`, `myShifts`, `overlaps` | `released_at IS NULL` | correct: a coordinator release frees the spot, as intended |
| `ShiftService`'s `SELECT … AS signed_up` (feeds `ShiftView.signedUpCount`) | `released_at IS NULL` | same |
| `ShiftService.notifyCancellation`, `BroadcastService` recipients | `released_at IS NULL` | someone removed stops being messaged, which is right |
| `ShiftReminderScheduler` / `ShiftReminderService` | active signups | reminders for a removed volunteer are cancelled by the shared `releaseSignup` |
| `staff/WorkforceService:115,200,211` → `MealCrewService` crew count | `ShiftView.signedUpCount` | unchanged in value |

**One thing to raise rather than fix, outside my contract.** `WorkforceService` is now the only place
where the *meaning* of the number has drifted: `signedUpCount` is "hands expected", and for a shift in
the past that is now knowably different from "hands that came", because attendance exists. Nothing is
wrong today — no sum is falsified, and the crew count is a planning figure — but when the reliability
and hours-contributed figures this task unblocks get built, `staff/WorkforceService.java` is the file
that should decide whether a past date reports signups or attendance. Reported, not touched.

### A correction to the brief (small, and it stands in the builder's favour)

The contract grants `frontend/__tests__/volunteer-shifts.test.tsx` as *"the only frontend test
referencing `shiftRoster`"*. **No frontend test references `shiftRoster` at all** —
`grep -rn "shiftRoster" frontend/__tests__` returns nothing, and that file covers `/volunteers`,
`/volunteers/new` and `/volunteers/[id]/edit`. The grant was still the right call (it is the nearest
neighbour and cost nothing), and the roster page had **no** test before this task; it has one now.
The rest of the brief's correction was confirmed against the tree: there is no `[id]` segment under
`shifts`, and `/volunteers/[id]` is `ShiftRosterPage`, so no route and no nav entry were needed.

### Judgement calls, each of which could be overruled

1. **Marking is not gated on the shift having started**, on either side. A coordinator can mark a
   future shift, and because marking is once-only that mistake is currently uncorrectable. Gating it
   needs either a new error code (none is reserved) or client-side clock reasoning across the
   temple's timezone, so I left it and am raising it instead.
2. **The real gap behind that: there is no correction endpoint.** `KMS-400139`'s next step says
   *"Change it on the shift's roster"*, and today the roster cannot change it — `api.ts` reserves no
   wrapper for a correction, so building one would have been an endpoint no client calls. It wants a
   task, and `attendance_recorded_by` plus a correction history should be designed with it.
3. **A struck-off volunteer is not notified.** Every notification template in
   `notification/NotificationTemplate.java` is wrong for it and adding one is outside this contract.
   A volunteer removed by a coordinator will otherwise turn up. Worth a task; the promoted waitlister
   *is* notified, as on any other release.
4. **The coordinator's release keeps the started-shift guard** (`KMS-400059`). Removing somebody from
   a shift that has already run would rewrite what the roster said when it mattered; attendance is
   the right way to record that a person on the roster did not come.
5. **No audit event.** `SHIFT_BROADCAST_SENT` is the only shift action in `AuditAction`, and adding
   `SHIFT_ATTENDANCE_RECORDED` / `VOLUNTEER_RELEASED_BY_COORDINATOR` means editing `audit/`, outside
   the contract. Taking a named person off a roster is arguably the most audit-worthy act on this
   screen; raising it rather than doing it.
6. **No confirmation before *Remove*.** No screen in `frontend/app` uses `window.confirm`, and the
   act is reversible (the volunteer can sign up again and the release stays on the roster), so I
   matched the surrounding code. `Cancel` on the shifts list prompts only because it needs a reason.
7. **Ticked-by-default checkboxes.** Submitting untouched records everyone as present; the
   coordinator unticks the absentees. The reverse default makes a distracted save record a roster of
   no-shows, and the no-show is the mark that costs somebody something.
