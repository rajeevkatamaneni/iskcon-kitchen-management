# T-110 — one donation page: the 80G receipt, and what else this donor has given

`/donations/[id]` now exists. It carries the gift, the receipt (issue, download, send again), and the
donor's other gifts — good ones by default, everything on a toggle. The receipt goes through the
existing documents pipeline as a fifth kind, not beside it.

---

## ⚠ Read this first — one thing needs Rajeev, and one is a judgement call

**1. I need one error code, and I did not take a number.** `ErrorCode.java` was reserved, so the
refusal *"a voided donation cannot have a receipt issued"* is thrown with the existing
**`DONATION_ALREADY_VOIDED` (KMS-400134)** — *"This donation has already been voided." / "Record it
again if it was actually received."* That reads correctly in this context and its next step is
reachable (recording is `MANAGE_INVENTORY`, which the Temple Admin has — T-095's own test), and the
screen withholds the control anyway so a person only meets it from a stale tab. **But it is a reused
code, chosen because I could not mint one.** If a code of its own is wanted, it is one constant and
one line in `DonationReceiptService.issueNumber`. Nothing else needs touching.

**2. I extended the scope by one thing: a permanent receipt number.** The acceptance did not ask for
one. I judged that a receipt with no number is a letter about a donation rather than a receipt — a
donor quoting it back in March has nothing to quote — and that it is also the cleanest proof that
re-sending changes nothing. It follows the pattern already in the tree (`po_sequence`,
`meal_card_sequence`): a per-tenant counter, issued once, stored on the donation, never reissued.
**Raising it here rather than after, per Commandment on deviations.** If it is unwanted it is one
column, one table and one method.

**3. And one deliberate refusal to over-claim, which is also a scope call.** A gift *in kind* does
not qualify for deduction under 80G — only money does. Rather than refuse a receipt for one (which
would have needed a second error code I also do not have), the receipt states honestly which of
three things is true: eligible under 80G; an acknowledgement of goods that is not an 80G receipt; or
a temple with no 80G registration, supporting no deduction. This is what satisfies *"renders with the
temple's 80G status"* precisely rather than printing "80G" regardless.

## What `donorHistory` actually returns, and whether its shape needed changing

**It returns `List<LedgerRow>` — the same row type the ledger list uses — and its shape did NOT need
changing.** It had never been rendered by anything, so this is the first review of it.

Two findings worth having on the record:

- **It applies no status filter at all.** `ledger()` appends `AND d.status = ?` defaulting to
  `COMPLETED`; `donorHistory` does not. So it already returns PENDING, FAILED and EXPIRED gifts and
  struck ones, each carrying `status` and a separate `voided` boolean. **That is exactly what the
  toggle needs**, and it is why the toggle is a client-side filter over rows already in hand rather
  than a second request: instant, and honest that the hiding is only on the screen.
- **It matches by account, else PAN fingerprint, else exact phone-and-email**, first match wins, and
  an anonymous or contactless gift matches nothing and returns `List.of()`. It also includes the
  donation being viewed — correct, and the screen marks that row "This one".

Two things I did **not** change but that a reader should know: it is **unbounded** (no limit, no
paging — a large donor could return hundreds of rows), and `donorDisplay` is anonymity-safe, so the
history table shows amounts and dates rather than names. Neither is in scope; both are named here
rather than left to be discovered.

## How the receipt reuses the existing document path

No parallel path. `documents` gains a fifth `kind`:

- **`DocumentService.requestDonationReceiptPdf`** sits beside `requestRecipePdf`,
  `requestPurchaseOrderPdf`, `requestJobCardPdf` and `requestWorkOrderPdf` — same PENDING row, same
  `enqueue()`, same Quartz `GenerateDocumentJob`.
- **`DocumentGenerationService.generate`** gains one `else if ("DONATION_RECEIPT_PDF")` arm beside
  the other four, rendering to `generated/donation-receipts/<id>.pdf` through the same
  `PdfRenderer` and `DocumentStorage`.
- **`DonationReceiptTemplate`** is the fifth template in `document/`, built the same way as
  `WorkOrderTemplate` and `PurchaseOrderSheetTemplate` — StringBuilder, self-contained A4, every
  value escaped. `DonationReceiptService.render()` builds its model, exactly as
  `WorkOrderService.render()` does for the work order.
- **Download** streams through the same authorised proxy shape as
  `PurchaseOrderDocumentController` — no public URL.

**The one deliberate difference from all four:** three of them are *versioned* and the recipe card
*overwrites in place*. A receipt is neither — it is **issued once**. A receipt already `READY` is
returned untouched rather than re-rendered, because re-rendering would silently reissue the donor's
April receipt with whatever the row says today. V117's unique partial index makes a second row
impossible whatever the service does.

**The receipt reads `amount_inr` and nothing else.** It never touches `wishlist_applied_inr`.

## Acceptance criteria, and how each was verified

| Criterion | How |
|---|---|
| The receipt renders with the temple's 80G status and the donor's details, and downloads | `DonationReceiptIT.issuesRendersAndDownloads` — asserts the temple name, its address, the donor's name, the decrypted PAN, `₹5,000`, the receipt number and *"Eligible for deduction under Section 80G"* in the rendered HTML, then drives the worker to READY and downloads bytes starting `%PDF`. `unapprovedTempleClaimsNothing` proves the other status. `DonationReceiptTemplateTest` covers all three statuses in isolation. |
| Re-sending does not create a second document | `DonationReceiptIT.reSendingReusesTheOneDocument` — issue, generate, issue again, send twice; asserts the same document id, the same receipt number, `count(*) = 1`, and that the READY bytes were not remade. `theUniqueIndexIsTheRealGuard` inserts a second row **as the superuser, past the service entirely**, and asserts `DuplicateKeyException` — so the rule is proven to live in the database, not only in a method. |
| A voided donation cannot have a receipt issued | `DonationReceiptIT.aStruckGiftGetsNoReceipt` — 409, **and** zero document rows, **and** `receipt_number` still null (nothing queued, no number spent), **and** the detail endpoint reports `canBeReceipted: false` so the screen can withhold. Frontend: *"withholds the receipt from a struck gift and says what to do instead"*. |
| History defaults to good gifts; the toggle reveals failed, expired and struck | Server half: `historyCarriesEverythingTheToggleReveals` — four gifts (completed, FAILED, EXPIRED, struck), all four returned, one marked voided. Screen half: *"opens on the good gifts alone, and the toggle reveals the rest"* — ₹2,500 visible, ₹1,000/₹2,000/₹3,000 absent, then all three present after the click, with the struck one badged. |
| A split gift shows one receipt for the whole payment | `DonationReceiptIT.aSplitGiftIsOnePayment` — ₹14,000 paid with ₹4,000 applied to a wish-list item; the receipt contains `₹14,000` and **neither** `₹4,000` **nor** `₹10,000`, and still names the grinder. `DonationReceiptTemplateTest.oneFigureAndOneOnly` asserts the same at the template layer. |
| Existing donation and document tests pass | 820/820 across `DonationVoidIT`, `DonationLedgerIT`, `DonorCaptureIT`, `DocumentGenerationIT`, `WorkOrderIT`, `JobCardIT`, `ErrorCodeTest`, plus the whole 1293-test frontend suite. |

**Permissions — checked, not assumed.** Reading a donation is `VIEW_DONATIONS`; recording is
`MANAGE_INVENTORY`; striking is `VOID_DONATION`. Issuing a receipt puts the donor's decrypted PAN on
paper, which is the same act as the existing `GET /donations/{id}/pan` — already `VIEW_DONATIONS` —
so every endpoint here is `VIEW_DONATIONS` and **`RolePermissions.java` needed no change**. Proved by
`aCookCannotReadOrReceiptOne`: a `KITCHEN_STAFF` gets 403 on the detail, the issue and the send.
`RequireRole` on the page is `TEMPLE_ADMIN` alone, matching `RolePermissions`.

**Audit.** `issuingIsAudited` — issuing files one `DONATION_RECEIPT_ISSUED`, and pressing again files
none (the number is issued once, and re-pressing is not a second act). It also files one
`DONOR_PAN_VIEWED`, because a receipt is a second way to see a PAN and a reader auditing PII access
should not have to know that.

**Read the two assertion messages, because they are the whole point:**

- `expected:<409> but was:<200>` is **C2**. With the voided guard gone, the temple happily issues an
  80G receipt for a gift it has told the tax authority it never received. That is the defect

  the control distinguishes them.

`DonationReceiptTemplateTest` cases are pure template rendering and neither patch can reach them.

statuses, the split gift, the unreachable donor, the permission check, and the unique index tested

would satisfy — `aStruckGiftGetsNoReceipt` asserts a **409 first**, and its zero-document and
null-number assertions are never reached.

## Not done / needs Rajeev

1. **One error code, as above.** `DONATION_ALREADY_VOIDED` is doing a second job. Say the word and
   it becomes its own constant.
2. **The receipt number is scope I added.** Named at the top; reversible in one migration.
3. **No browser print view.** The other four document kinds each have a `/print` endpoint rendering
   the same HTML with no worker. The receipt has download only, because nothing in the acceptance
   asked for print and the template is already the same object either way — adding it later is one
   controller method.
4. **No amount in words.** Indian receipts conventionally carry *"Rupees Fourteen Thousand only"*.
   Not in the acceptance, and a number-to-words routine for the Indian system is real code with real
   bugs, so I did not invent one. Worth a decision before a temple files one of these.
5. **`donorHistory` is unbounded** — no limit, no paging. Fine for the temples on staging; it is a
   full table scan of one donor's history on every open.
6. **I could not hand-smoke-test it.** Commandment 5 wants a new user-facing surface driven by hand.
   This is a builder agent in a shared checkout with no deploy and no session; the screen has been
   exercised only through vitest and the API only through MockMvc against real PostgreSQL. **The
   whole `/donations/[id]` screen is unverified by a human.** The first things worth pressing on
   staging: Open on a ledger row, Issue the receipt, wait for READY, Download, and read the PDF for
   the 80G sentence; then Send it to the donor twice and confirm the office is not holding two
   receipts.
7. **Mailgun's sandbox blocks email on UAT** (existing, known), so the "Send it to the donor" path
   will only reach pre-authorised addresses there. Not caused by this task; it will look like a
   failure of it.
