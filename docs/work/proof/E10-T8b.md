**Overall: 12 of 28 items had more than one spelling.**

What the table shows:

- The common words are stable: ghee, jaggery, curd, toor dal and rice. Most of them are in the
  prompt's word list. The drift is in the less common spices (mace, ajwain) and in descriptive
  variants (chopped, diced small, grated). Those are exactly the names a cook would need to match
  against the sack.
- **The English name was alongside the Kannada every time.** Every one of the 220 mentions carried the
  store's English name. 20 of them (9%) gave no Kannada at all, mostly in the long rice list for kn08.
- Two different items get one Kannada name. "Broken rice" and "Rice, broken" are separate store items,
  and both came out as ನುಚ್ಚಕ್ಕಿ. One stored name per item would not fix that by itself, because the
  glossary is keyed on the name, and two English names would still map to whatever the temple types.
  This is noted, not fixed.
- Some renderings are transliterations of the English, not Kannada words (ರಾ ರೈಸ್, ಬ್ರೋಕನ್ ರೈಸ್).

How it was measured: the extractor finds "ಕನ್ನಡ (English)" and "English (ಕನ್ನಡ)" next to the tool's own
English name, its read-aloud form ("Curd, sour" → "Sour curd"), or the name without its bracket. I
checked that every item in every tool result was attributed. After the fixes listed next, all 28 items
in all 50 runs were found. I read every multi-word capture by hand. The capture could pick up sentence
words in front of a name ("ಸ್ಟೋರ್‌ನಲ್ಲಿ ಎರಡು ರೀತಿಯ ತುಪ್ಪ (Ghee)", "in the store, two kinds of ghee"), so
nine such prose words are stripped from the front. Each one is listed in the script. Normalisation
collapses runs of whitespace and punctuation to one space and removes the invisible ZWJ/ZWNJ
joiners; nothing else. A space between words is kept, so "ಓಂಕಾಳು" and "ಓಂ ಕಾಳು" count as two
spellings, because that is a real difference in what the person reads.

## How the app stores and produces Kannada names today (read-only)

- **`translation_glossary` (V13)** is the only per-tenant Kannada name there is. It holds
  `(tenant_id, language, source_term, target_term)`, with RLS and a unique key on
  `(tenant, language, lower(source_term))`. A Temple Admin edits it on `/glossary`, under
  `MANAGE_RECIPES`. `GlossaryService.lookup(lang)` returns the whole language as a map. No ingredient
  or stock table has a Kannada column. The local copy has 0 rows; I did not check staging.
- **`Translatable`** is the shared rule: look the glossary up on the name as the temple filed it, and
  hand the machine the read-aloud form (`IngredientNames.readable`). Three paths use it: recipe
  translation, the purchase-order sheet and the work order. `InventoryTools.toRow` uses it too, but
  only its glossary half. `name_kn` is the glossary hit or nothing, and on purpose there is no
  machine translation (its class comment says so).
- **`GoogleCloudTranslationProvider`** is stateless. One `translateText` call per batch, nothing kept.
  Locally `TRANSLATION_PROVIDER=stub`.
- **Caching:** the translation is stored per document, never per name. `recipe_translations` caches a
  whole recipe per (recipe, version, language) and is invalidated by an edit. V94 emptied it once.
  `po_label_translations` and `document_label_translations` cache fixed labels only. The PO sheet and
  the work order translate ingredient names fresh on every render. **So a machine-translated
  ingredient name is never stored anywhere on its own.** The same ingredient can read differently
  on a recipe card, a PO and a work order, and can change whenever Google changes its model.

### The smallest change that gives every item one stable Kannada name (not built)

Make the glossary the store. When a Kannada name is needed for an ingredient that has no `kn`
glossary row, translate it once (`Translatable.forMachine()` through the `TranslationProvider`) and
**insert it into `translation_glossary`** with an `ON CONFLICT DO NOTHING` insert, so it is never
re-translated or changed. Then every caller reads the same row from then on. The Temple Admin can
still correct it on `/glossary`, and a correction overwrites it.

Concretely:

1. Add one method to `GlossaryService`, `namesFor(language, filedNames)`. It returns the stored names,
   translates only the misses in one batch, and inserts them. It needs a `source` column
   (`'temple'`/`'machine'`), added in a migration with no backfill, so that the glossary screen can show
   which names nobody has checked. Without that column the machine's words are indistinguishable from
   the temple's.
2. Have `InventoryTools` call it instead of `lookup`, so `name_kn` is always present, and drop the
   "absent when the glossary has none" wording from the tool description.
3. Prompt: "use `name_kn` exactly as given".

Two things to settle first. Should the 119 stock items be translated up front by a one-off job, or
lazily on first use? Lazy means the first Kannada question pays one translate call. And writing to the
glossary from a read path means a `@Transactional` write inside the `/mcp` tool call, which today is
read-only. A one-off "fill the glossary" action on `/glossary` avoids that, and it is my preference.
