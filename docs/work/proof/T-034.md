## Where the event-name normalisation lives, and why there

**`MealMoment`'s canonical constructor**, in `backend/.../staff/MealMoment.java`, with a private
`fold(String)` — `null` or blank → `""`, otherwise `trim().toLowerCase(Locale.ROOT)` — applied to
both `mealKind` and `eventName` on the way in, plus a `MealMoment#isFor(date, kind, eventName)` that
folds the *link* it is handed before comparing.

That is the one place because it is the only place both sides of the comparison must pass through.
The meal side is built by `MealCrewService.momentOf`; the shift side arrives raw from the column in
`WorkforceService.volunteersAt`. Both go through the record, so there is no call site at which the
rule can be forgotten, and none at which a second copy can drift from `ServedMealService.Key.of`.
`Key` is private to `ServedMealService`, which is out of this contract, so the rule is **replicated,
not imported** — deliberately, and in exactly one method.

**One deliberate addition to `Key.of`'s rule:** the *kind* is folded too, which `Key.of` does not do.
This is strictly safe — folding both sides matches everything an exact comparison matches and nothing
it does not — and it closes the remaining way a caller posts `"lunch"` against a temple that stores
`"Lunch"` and is silently counted nowhere. `ShiftMealLinkIT` exercises it: the event test posts
`"mealKind":"event"` against a kind stored as `"Event"`. Nothing displays these two components (the
readout takes its labels from the meal record), so folding costs no legibility.

## Two design decisions worth flagging to Rajeev

**1. `meal_kind` has no foreign key, and this was checked rather than assumed.** `meal_kinds` is
unique per tenant on `(tenant_id, lower(name))` — an *expression* index (`V22__meal_plans.sql:23`,
renamed by `V48`). PostgreSQL will not accept an expression index as the target of a foreign key, so
no FK is possible. `meal_plans.meal_kind` is plain `TEXT` for the same reason, so the new column is
consistent with the one it has to match. Recorded in `V95`'s header.

**2. `ShiftService.listCountingTowardMeals(from, to)` is new, and it is not cosmetic.**
`WorkforceService.countAt` used to fetch `shiftService.list(from, to, false)`, a range built from the
*meals'* dates. A linked shift counts toward its meal whatever the clock says — and the clock includes
the calendar. "Grind the masala on Thursday for Sunday's feast" is a shift on Thursday committed to
Sunday lunch, and the old fetch would never have loaded it: the count would have read **zero on
precisely the shift somebody took the trouble to link**, which is the silent-failure mode D-14 warns
about. The new query fetches on `shift_date IN range OR meal_date IN range`. Widening by a fixed
number of days was the alternative and was rejected — any number is a guess about how far ahead a
temple prepares, and the one time it is too small the count is quietly short. Covered by
`a shift posted days ahead of the meal it is for still counts toward it`.

Two smaller ones: the `CHECK` also refuses an event name with no date and kind beside it (a name
alone names nothing), and `KMS-400125` is raised for that case too. And `momentsOf`'s de-duplication
narrowed from `(date, readyBy)` to the meal's full identity — two meals due at the same minute used
to collapse into one question, which was harmless while the answer depended only on the clock and is
wrong now that a shift can be posted for one of them and not the other. That is asserted by
`two events on one day are two meals, and a link reaches only the one it names`.

## Acceptance criteria, one at a time

**"A shift posted with a meal date and kind saves and reads back with them; one posted with a kind
and no date returns `KMS-400125` and writes nothing."**
`ShiftMealLinkIT > a shift posted for a meal saves and reads back with the meal it was posted for` —
POSTs date + kind + event name, GETs all three back on `/shifts/{id}` and on the list, with the event
name in the case the temple typed it (folding happens at match time, not on the way in).
`ShiftMealLinkIT > half a link is refused by name and nothing is written` asserts `400` with
`$.code == "KMS-400125"` on all three half-links — kind with no date, date with no kind, and an event
name with neither — then `SELECT count(*) FROM shifts` = 0.
`ShiftMealLinkIT > an unlinked shift reads back as unlinked, on every one of the three fields` closes
the other half: a reader can tell "not linked" from "this endpoint does not say".

**"A linked shift counts toward its own meal and toward no other, asserted against a day carrying at
least two meals — including the breakfast case above, asserted as a deliberate decrease."**
`ShiftMealLinkIT > a lunch-prep shift stops inflating breakfast once it says it is for lunch`. Written
in the order the mistake actually happens, so the difference is the evidence:

| | Breakfast (07:30) | Lunch (12:00) |
|---|---|---|
| shift 06:00–10:00, **unlinked** — today's behaviour, asserted | volunteers **1** | volunteers **0** |
| same shift, same hours, same volunteer, **linked to Lunch** | volunteers **0** | volunteers **1** |

Breakfast goes **down**, on purpose, in a passing assertion. Those hands were never coming to
breakfast. `a linked shift counts toward its meal even where its hours cover no meal at all`
(14:00–16:00, linked to lunch) proves the clock is not consulted at all for a linked shift, and
`two events on one day are two meals, and a link reaches only the one it names` proves "and no other"
where the clock would have credited both.

**"An unlinked shift counts exactly as it does today. Every existing crew test still passes on its
original numbers, or a changed number is explained."**
No existing test was edited and **no number changed.** `MealCrewIT` (8), `CrewCoverageIT` (9),
`ShiftIT` (6), `MealCrewDefaultTest` (4), `TodayIT` (15), `StaffScheduleIT` (8) and
`VolunteerSignupIT` (6) all pass as they stood. New coverage of the unlinked rule:
`a shift left unlinked still counts toward every meal its hours span` posts the 06:00–22:00 festival
all-dayer and asserts it counts toward breakfast, lunch **and** dinner.

**"The event-name normalisation matches `Key.of` — a test links a shift to an event meal whose name
differs only in case and surrounding whitespace and asserts it still matches."**
`ShiftMealLinkIT > an event link matches on a name differing only in case and surrounding space`.
The meal is planned as `"Janmashtami Feast"`; the shift is linked with
`"mealKind":"event","mealEventName":"  janmashtami feast  "` — different case on both, stray space at
each end — and its two volunteers land on the event, while the day's Lunch gets none of them.

**"`./gradlew test` green, including a boot that applies `V95`."**
Green as above. `V95` demonstrably applied, twice over: every `ShiftMealLinkIT` case writes and reads
`meal_date` / `meal_kind` / `meal_event_name` through real SQL against Testcontainers PostgreSQL, and
`the database refuses half a link too, whatever route the row comes in by` inserts a half-link with
raw SQL through the admin `JdbcTemplate` — bypassing the service entirely — and asserts the failure
names `shifts_meal_link_complete`, a constraint that exists only because `V95` ran.
`RowLevelSecurityIT > every table with a tenant_id is covered by row-level security` and
`TenantLoopMigrationIT > every migration runs against a database that already has a temple in it`
both pass, so `shifts` keeps its RLS and the migration is clean against a populated database.
Migrations here run as the unprivileged `kms_migrator`, so an RLS-blind migration would have failed —
this one adds three nullable columns and a constraint and backfills nothing, because every existing
shift is unlinked and that is the correct reading of it.

  explicitly, and editing a second test file for a display name was not worth the collision risk.
  Worth folding in whenever `ShiftIT` is next opened.

  neither the `CHECK` nor the service requires the meal to exist. It starts counting the moment the
  meal is planned (asserted in `an edit can take the link off again`, whose first assertion is a
  link to an unplanned lunch reading zero). If Rajeev would rather the planner *warned* about a link
  that currently matches no meal, that is a real product question and it belongs to the planner task,
  not here.
- **`AvailableShiftView` (what a volunteer sees) does not carry the link.** Out of contract and, I
  think, correct — a volunteer signs up for hours, not for a planning artefact — but flagging it
  rather than deciding it.
