## What was changed

One line became three, at `Quantities.java:121`:

```java
boolean empty = inBase.signum() == 0;
Unit display = empty ? unit
        : inBase.abs().compareTo(BigDecimal.valueOf(1000)) >= 0 ? large : small;
```

This is `frontend/lib/format.ts`'s `const empty = inBase === 0;` line for line — same condition, same
consequence, same placement between the base conversion and the divide, so the `forCooking` promotion
below it is reached in exactly the same states on both sides. The em-dash rule above is untouched: a
null is "we have no figure", a zero is "we have none of it", and they still read differently.

`signum()` rather than `equals(BigDecimal.ZERO)`, and this is the one place the two implementations
could not be literally identical. TypeScript has one number type; here a quantity comes back through
JDBC carrying its column's scale, so a genuine nothing arrives as `0.000` and `equals` would answer
false on the scale alone — the fix would then work in a unit test and not in the application. There is
a test for that specifically, `zeroAtAnyScale`, and it is the reason it exists.

The class javadoc claimed *"Changing one without the other fails the build."* That sentence was false
when it was written and this defect is what it cost, so it now says what actually holds: the vector
tables are the whole mechanism and they only cover the cases they list.

### The tests added — the frontend's zero vectors, word for word, plus two Java-side guards

`zeroKeepsItsOwnUnit` is the mirrored table: the same seven assertions T-125 added to
`quantities.test.ts`, in the same order, with the same expected strings — `0 L`, `0 Kg`, `0 ml`,
`0 gm`, `0 pieces`, then the cook's form for `L` and `KG`. **The frontend's zero case was confirmed
present and correct at `frontend/__tests__/quantities.test.ts:51-66` and needed no change**, which is
the half of the brief that turned out to be already done.

Two more, and they are not in the frontend table because they answer questions only this side has:

- `zeroAtAnyScale` — `0.000`, `0.00000`, `BigDecimal.ZERO.setScale(6)`. The JDBC hazard above.
- `nearlyZeroStillStepsDown` — `0.0001 L` is still `0.1 ml`, `0.000001 KG` is still `0.001 gm`. This
  one **passes with the fix patched out**, deliberately, and the count below explains why: it guards
  against the fix having been written as *"small numbers keep their unit"*, which is a different and
  wrong rule that would have silently stopped the step-down working for every fraction on a job card.

### The baseline, which is the thing T-125's control got wrong

T-125's builder reported that it proved "the tree changed" with `git diff` against `HEAD`, and that
this told it nothing. It is worth spelling out why, because the trap is not obvious and this task had
exactly the same shape: **this fix is not in `HEAD`.** It is an uncommitted working-tree change. So
patching it back out restores precisely what `HEAD` already holds, and `git diff HEAD` falls *silent*
at the moment the control is doing its job and *speaks* when it has failed to apply. The signal is not
merely absent, it is inverted.
