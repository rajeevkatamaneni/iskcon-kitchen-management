# T-403 — the book's "the temple never buys this" reaches the temple's ingredient

T-402 made `ingredients.is_not_bought` real; nothing set it from the book. Rajeev's curated recipes
mark fifteen lines, every one of them water, and the library path dropped the key before anything
could read it — so loading his catalogue created water as an ordinary bought ingredient and put it
on every shopping list. The mark now travels from the book, through `master_recipes.ingredients`,
onto the ingredient the import creates. **Measured end to end on his real 44 recipes: 15 marks and
83 preparations into `master_recipes`, and a shopping list for a meal cooking Akki Rotti with no
water line on it.**

## The judgement call: create marks, match does not, and the disagreement is recorded

**What I built.** An ingredient the import *creates* from a marked line is created marked. An
ingredient the temple *already holds* is left exactly as the temple has it, whether it was matched
exactly or chosen through the close-match answer. Where the book marks a line and the temple's own
row says it buys the thing, the names go into the import's `RECIPE_IMPORTED` audit entry under
`notBoughtNotApplied`.

**Why a match must not be marked silently — the permission.** Copying a library recipe is
`@PreAuthorize("hasAuthority('MANAGE_RECIPES'))")` on `RecipeController.importFromLibrary`, and
`RolePermissions.java` grants `MANAGE_RECIPES` to three roles (lines 45, 117, 148).
`MANAGE_BUYING_POLICY` is granted at line 94 to one role only, the Temple Admin, and T-402 put it
behind `PATCH /api/v1/ingredients/{id}/not-bought` with an audit entry on every move. If the import
flipped the flag on a row the temple owns, a Kitchen Manager copying a recipe would set a flag they
are refused at that endpoint — silently, and the effect is that the temple stops buying something
with nothing on the order to say so. `IngredientService.create` already refuses `notBought: true`
without the permission, and its comment gives this exact reason.

**Why creating a marked row is not the same objection.** The temple held no opinion about a row that
did not exist a moment ago, so nothing of theirs is overruled. The authority behind the mark is the
platform operator who curated the book — writing the library is `MANAGE_RECIPE_LIBRARY`. And the
mistake it can make is reversible in the safe direction: an ingredient wrongly marked shows up as
something missing from an order, which a store keeper notices, and one click on the ingredient
clears it; the opposite mistake is water quietly back on every list, which is the fault T-402 exists
to fix.

**Why this is not the Ekadashi precedent.** `RecipeImportService.create`'s existing comment says an
imported ingredient arrives with no Ekadashi flag because "the flag is a Temple Admin's to set, and
the import cannot tell a grain from a spice". The second half is the operative one: the import has
no information. Here it does — the book states it outright on the line. I have left that comment
standing and said next to it why this case differs, rather than quietly contradicting it.

**I am flagging the asymmetry rather than hiding it.** A Kitchen Manager importing a recipe ends up
with a marked ingredient they could not have created by hand through `POST /ingredients`. I think
that is right for the reasons above, and it is the kind of thing a reviewer should get to disagree
with. `RecipeImportNotBoughtIT.aKitchenManagerCopiesWithoutMakingPolicy` pins both halves: the copy
goes through, the temple's own Water is untouched, and the same person is refused 403 at the flag's
own endpoint in the same test.

**Where the disagreement is reported, and why not in the response.** The brief suggested the
import's response. **The response body is not built in `RecipeImportService` — it is built in
`RecipeController.importFromLibrary:75-79`, which is outside my path contract** — and
`frontend/lib/api.ts`, which I am forbidden to edit, declares that response as
`{ id; name; ingredientsCreated; categoryCreated }`. A field added to the `Imported` record alone
would be sent and typed by nobody: a surface that looks built and is not. So it goes in the audit
entry, beside `closeMatches`, which is already where this import records the decisions it made and
did not make, is durable, and needs no reserved file. **If Rajeev wants the copy screen to say
"this recipe says the temple doesn't buy Water, but your Water is set as bought — change it?", that
is an `api.ts` field plus screen work and it is his call.** Noted again at the end.

**The mark is per ingredient, not per line.** The marked keys are collected across the whole recipe
before anything is resolved, so a book that marks water on one line and forgets it on another marks
it either way — a mark is a statement about water, not about a line — and the answer does not depend
on which line came first. `aMarkOnEitherLineMarksTheIngredient` asserts it with the *unmarked* line
first, which is the order a per-line implementation gets wrong.

**Created-marked is audited like the form.** T-402's `IngredientService.create` writes a second
`INGREDIENT_NOT_BOUGHT_CHANGED` entry when a row is created already marked, and its comment says why:
*"so that 'who said we never buy this' has one action to grep for whether the decision was made at
creation or afterwards. An ingredient created already marked is the ordinary case — a recipe import
that knows the line is water creates it this way — and it would otherwise be the one route that left
no findable trace."* The import was that route. It now writes the same action with the same two maps,
and `creatingOneMarkedIsAuditedLikeTheForm` asserts the exact JSON so the two shapes cannot drift.

## Two things I decided differently from the brief, and why

**1. No frontend change — the mark is deliberately not shown on the library screens.** The brief left
it to me. I looked at both screens and decided against, on a consistency argument rather than a
scope one.

`RecipePeek` draws a temple's own recipe and a library recipe through one flattening step, and
`api.ts`'s `RecipeIngredientView` (the temple's own line) carries no `notBought` — stock, price and
buying policy sit on the ingredient, not the line. So a mark on the library branch would show on a
dish before it is added and vanish the moment it is added, which is exactly the fault Rajeev raised
on 2026-09-18 and which the library page's own comment records: *"the same dish read two different
ways depending on whether the temple had added it yet"*. The library detail page has the same
asymmetry against `app/recipes/[id]`.

T-402 already shows "Not bought" in the three places the flag acts — the ingredients list, the
ingredient's own page, and the shopping-list picker's hint — and that is where a person can also
change it. Adding a fourth, read-only, on a screen where the fact belongs to a row that may not exist
yet seemed worse than leaving it. **If Rajeev wants it on the library screens, the honest version
shows it on both kinds of recipe, which means a field on `RecipeIngredientView` in the reserved
`api.ts` and a change to the recipe page — a task, not a line.**

**2. I used the seeding team's converter instead of writing one.** Covered above. The brief said none
exists; `tools/seed/02b-build-catalogue.mjs` does, it round-trips every field before it writes, and
proving the loader against a converter I wrote myself would have proved less.
