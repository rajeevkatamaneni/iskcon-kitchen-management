# T-428 — a staff record opens as a record, and carries its papers and its past jobs

The register now opens a person by their name. Their record leads with their name and their
photograph, carries Edit, reads the PAN behind an eye that makes the audited request when it is
pressed, holds scans of the PAN and Aadhaar cards, and lists where they worked before. Notes is gone
from the screens, the DTOs and the view; the column is still there, holding three rows of text.

## What protection the Aadhaar scan actually has, in plain sentences

Rajeev asked for this knowing what it is. So, exactly:

- **Who can open it.** Anyone holding `MANAGE_STAFF` — today, a Temple Admin. The same permission that
  already lets them read the person's date of birth, address, salary and PAN. No new permission was
  added, because that is what he asked for.
- **Every open is recorded.** `STAFF_DOCUMENT_VIEWED`, naming who read it, whose record it was on and
  which kind of document. Nothing from inside the file, no filename, no storage key. Uploading and
  removing are recorded too.
- **There is no URL.** No public URL and no signed URL, here or anywhere in this application. The
  bytes only ever come back from `GET /api/v1/staff/members/{id}/documents/{documentId}`, with the
  sign-in token in a header and the permission checked before anything is read. There is nothing to
  paste into a WhatsApp message. The response is `Cache-Control: no-store, private`, so it is not kept
  by a proxy or written to the browser's disk cache.
- **Another temple cannot see it.** Row-level security on `staff_documents`, enforced by PostgreSQL
  against the unprivileged application role, and tested as such.
- **What it does NOT have: encryption at rest by us.** The PAN *number* is AES-encrypted by
  `PanCipher` before it is stored (`V57:61-64`). A scan is not. It is an opaque blob written to
  Google Cloud Storage and streamed back out; at rest it has whatever the bucket gives it, which is
  Google-managed encryption, and nothing more. I did not invent cryptography for it, because that is
  not a decision for a build task. If the scan should get the same treatment as the number, say so and
  it can be a task of its own — it means key management, a decision about what happens to old objects,
  and the fact that a file cannot be decrypted for a thumbnail without decrypting the whole thing.
- **A removed or replaced file's bytes stay in the bucket.** `DocumentStorage` has no delete.
  Nothing points at the object any more, so nothing can reach it — waste, not a leak, and the same
  waste `V144` already accepts for an abandoned upload. Worth a sweeping job one day.

## Decisions I made, and why

**A real single-record read, not more fields on `StaffProfileView`.** `GET /api/v1/staff/members/{id}`
behind `MANAGE_STAFF`, returning `StaffRecordView` (profile, banned, documents, previous employment).
The four screens about one person used to read the whole register and filter it in the browser.
`StaffProfileView` is also served to the roster and to somebody reading their own schedule, and is
deliberately lean; `GET /staff/profiles/{id}` could not be used because it sits behind
`MANAGE_STAFF_SCHEDULE`, and leaning on it would have quietly undone the split that lets a kitchen
manager hold the roster without holding hiring. The cost of this decision was updating the
`useAuthedQuery` stub in six test files.

**A table of its own for the documents, sharing the storage.** `V144`'s own header argues it —
"The storage service is shared; the table is not." The bytes go through the same `DocumentStorage`
under the same tenant prefix, the type is decided by the same `AttachmentFileType` from the bytes
(which I made public rather than copying the signatures), the ceiling is the same
`AttachmentService.MAX_BYTES`, and the refusals are the same two codes. No second upload mechanism
exists.

**The documents live on the record, not inside the Edit form.** An upload takes effect the moment it
finishes — the record already exists, so there is nothing to claim on Save. Putting the boxes inside
the form would have put them beside a Cancel that cannot undo them. `ConductNotes` already sits on
this screen for the same reason.

**A stored scan's thumbnail is not fetched to draw it.** `AttachmentThumb` fetches an image eagerly so
it can draw the picture — which for a staff document would mean opening a PAN card and an Aadhaar card
on every page load, and recording two reads nobody made. It now takes `preview`, and the staff boxes
pass `preview={false} openable`: the thumbnail is a file-type icon until it is pressed, and pressing
it is the read. Asserted both ways in `staff-papers.test.tsx`.

**The photograph *is* fetched on load**, and that read *is* audited — one `STAFF_DOCUMENT_VIEWED` row
per open of a record that has a photograph. That is what acceptance 5 asks for ("every open writes an
audit row") and it is honest, but it is worth knowing before the log fills up. Flagged below.

**Three Aadhaar columns already existed and still nothing writes them.** `staff_profiles.aadhaar_name`,
`aadhaar_date_of_birth`, `aadhaar_last4` (`V65:326-337`), added so a ban record would have somewhere to
copy the triple from the day the signed-QR capture is built. I left them alone. Capturing a verified
Aadhaar triple is a different feature from filing a photograph of the card, and starting to write them
from a scan nobody has verified would make the ban check believe something it should not. It should be
its own task.

**No fourth audit action for a change to the past-employment list.** `STAFF_UPDATED` already records
that the record was edited, and the before/after shape does not carry the address or the emergency
contact either. Adding a count of past jobs to it would have been the first of a series.

# Appendix — the browser measurement pass (added after the first report)

The first report said "not verified in a browser" for acceptance 9. That gap is now closed. **Both
screens were driven at 1280 and 390, and every one of the four layout decisions I had made from CSS
arithmetic has been measured against a rendered page.** One of them was wrong in a way the arithmetic
could not have shown, and it is fixed.

## Why it failed the first time, and what changed

Not an absolute obstacle. The wave-5 stack script never exported `CORS_ALLOWED_ORIGINS`, so the API
on :8093 accepted only `http://localhost:3000` while the web runs on :3003; every call died in
preflight with `403 Invalid CORS request` and the screen could only say it was unable to reach the
server. Another builder found and fixed it (`wave5-stack.sh:25`). After a restart the app signs in
and serves real data — the session is Karuna Murti Das, Temple Admin, against the seeded
`kms_wave5`.

One caution of my own, for whoever comes next: `wave5-stack.sh api` **must not be launched from a
backgrounded Bash task**. The first attempt started cleanly (`Started KmsApplication in 3.003
seconds`, served one request) and was then killed with the task's process group; `nohup` does not
save it. Launched from a foreground call it survives.

## How a true viewport was obtained

The extension pins the tab's layout viewport — `innerWidth` stayed **1421** while `outerWidth` was
**392**. So every geometric measurement below was taken inside a same-origin iframe of an exact CSS
width, with `documentElement.clientWidth` asserted before anything was read:

```
await window.__mk(1280, '/staff')  ->  clientWidth=1280
await window.__mk(390,  '/staff')  ->  clientWidth=390
```

The hand-pressing (the name link, Edit, the eye) was done with the real mouse on the top-level page,
where a click is a click whatever the width.

## The four decisions, measured

**1. The record header's `basis-64` wrap. Correct.**

| | 1280 | 390 |
|---|---|---|
| header | x 312, w 936 | x 16, w 358 |
| left block (name + subtitle) | x 312, w 767, bottom 156 | x 16, w 358, bottom 212 |
| right group (Edit + photo) | x 1095, **y 90**, w **153** | x 237, **y 224**, w 137 |
| `rightGroup.y >= leftBlock.bottom` | **false** — one row | **true** — wrapped |
| right-aligned (group right == header right) | 1248 == 1248 | 374 == 374 |

I predicted the right group at "about 150px"; measured **153**. At 1280 the two sit side by side and
the photograph is flush with the content's right edge (1248). At 390 the group drops to its own line
and `ml-auto` holds it at the right (374), which is what makes "photo top right" still true on a
phone. Edit is 61 × 44 at both widths; the photo 80 × 80 at 1280 and 62 × 62 at 390.

**2. The PAN cell going full width on a phone. Correct, and it matters more than I thought.**

```
390:  grid-template-columns: 146px 146px      cell class "col-span-2 sm:col-span-1"
      PAN cell w = 308  (2 x 146 + 16 gap)    eye 44 x 44    value span w = 234
      room for the number = 308 - 44 = 264px
1280: grid-template-columns: 284.664px x3     PAN cell w = 284.7    eye 44 x 44
```

Without the span the cell would have been 146px and the number would have had ~102px. 264 is a field;
102 is a sliver.

**3. The past-job block at two columns. Correct — four rows, no empty cell.**

At 1280, `grid-template-columns: repeat(2, minmax(0px, 1fr))`, seven cells, each 443px:

```

row 2  Manager's name    | Manager's phone
row 3  From              | To
row 4  Why they left  (spans both, w = 902)
```

`emptyCellsInLastRow: 0`. At three columns the last row would have been one box and two empty
columns. At 390 it is `repeat(1, ...)`, every cell 324px, nothing overflowing.

**4. From and To as separate grid cells rather than a nested pair. Correct, and the reason holds.**

`dateInputWidth: 443` at 1280 and `324` at 390. Nested inside one cell of the old three-column grid
they would have had roughly 150px and 155px — barely a native date picker, which is what the change
was for.
