# T-085 — attendance cannot be marked before the shift has run

`SignupService.recordAttendance` now refuses a shift whose start time is still in the future with
`SHIFT_NOT_STARTED` (KMS-400144), the mirror of the `SHIFT_ALREADY_STARTED` guard on `releaseSignup`
and off the same `TempleClock`. The roster screen withholds the ticks and the *Save attendance*
button for the same condition and says why instead.

**The second half of the review's finding — a rule that `marks` must name every active signup — was
deliberately not built.** T-079 subsumes it. Nothing in the code mentions it.

## What changed

**Backend** (`SignupService.recordAttendance`): `lockShift`'s return is now kept, and

```java
LocalDateTime start = LocalDateTime.of(shift.shiftDate(), shift.startTime());
if (start.isAfter(LocalDateTime.now(clock.zone()))) {
    throw new ApplicationException(ErrorCode.SHIFT_NOT_STARTED, Map.of("shiftId", shiftId));
}
```

placed immediately after the lock, before any write — so a refusal marks nobody. `isAfter` without
the negation is the exact mirror of `releaseSignup`'s `!start.isAfter(...)`: a shift starting at this
minute is markable and not releasable, and the two guards meet rather than leaving a gap or
overlapping.

**Frontend** (`app/volunteers/[id]/page.tsx`): `shiftHasStarted` compares
`"<shiftDate> <startTime hh:mm>"` against the temple's own now (`todayIso()` + an `Intl` h23
formatter on `templeZone()`), both fixed-width so the string comparison is chronological. It is
`&&`-ed into `canMarkAttendance`, which already gates both the per-volunteer checkbox and the *Save
attendance* button. Where the button used to be, a future shift now reads *"Attendance can be
marked once this shift has started."* — the same sentence as the error code's next step, said
before the click instead of after it.

## On counting: which assertions are of an absence

Three, all flagged as the task asked:

1. Frontend `offers no marking of a shift that has not started, and says why` — two
   `queryBy...not.toBeInTheDocument()` assertions (no checkbox, no *Save attendance*). These pass
   vacuously against a screen with no attendance feature at all, which is why the same test also
   asserts a **presence** — the sentence *"Attendance can be marked once this shift has started."* —
   and why the test beside it, `offers marking from the minute the shift starts`, asserts the
   control **is** there one minute later. Under the control, that second test passed while the first
   failed: 1 failed of 9, not 2.
2. Backend `markingAShiftThatHasNotRunIsRefused` — after the 409, `attended` and
   `attendanceRecordedAt` must not exist on either signup. That is an absence, and it is the half
   that would catch a guard placed after the UPDATE loop; the 409 itself is a presence assertion,
   so the test cannot pass vacuously.
3. Pre-existing, and now protected: `shows a released volunteer under Released, with no attendance
   tick` asserted an absent checkbox. With T-085's rule and the file's fixture date of 2026-12-06 it
   would have passed against the real clock because *no* row has a tick before December — the whole
   `taking a volunteer off a roster` block therefore pins the clock too, so the assertion is once
   again about the released row and not about the calendar.

`Object.keys` was not needed: neither new test uses `objectContaining`. The existing
`toEqual({ marks: [...] })` assertion on the payload is exact by construction.

  not deployed and I did not drive the staging app. What wants pressing on UAT: open a roster for a
  shift **later today or tomorrow** with signups on it — the ticks and *Save attendance* must be gone
  and the line *"Attendance can be marked once this shift has started."* in their place — then open a

  `coordinatorReleasesNamedVolunteer`, `releasingSomebodyNotOnTheShift` and
  `volunteerCannotReleaseSomebodyElse` — nothing to do with this change, but now three months out.
  My own new test computes its date instead. Worth a small follow-up to make `FUTURE` dynamic; I did
  not widen this task to do it.
- **The partial-`marks` route to an unrecoverable state is still open**, by the ruling in the
  dispatch row: T-079 makes a mark correctable and that is where it gets fixed. Nothing in the code
