## What was built

- **PUT /api/v1/vendors/{id}/supplies** takes optional `packSizeId` and `pricePerPack`. With a pack and a price per pack, `last_price` is derived: pricePerPack ÷ the pack's size in the ingredient's canonical unit (V144 `base_quantity` ÷ `Unit.baseFactor()` of the canonical unit). A `lastPrice` sent beside a pack price is ignored. The pack must belong to the ingredient, or the request is refused with KMS-400162; RLS hides another temple's pack, so it gets the same refusal. A pack with a per-unit `lastPrice` and no `pricePerPack` is refused with KMS-400163. A pack with no price at all is allowed. A `pricePerPack` sent with no pack is a field error (KMS-400001, "Choose what it is sold as before giving a price per pack."). Without a pack, `lastPrice` is typed per unit as before.
- **VendorPriceHistoryService.record(...)** is the only writer of `vendor_price_history`. It takes `Propagation.MANDATORY`, so it runs inside the supply write's transaction. Its parameters are the vendor, ingredient, price per unit, pack price, pack snapshot, effective date, `Source` (ONBOARDING/MANUAL/INVOICE), invoice line id and setBy. The invoice task (stage 6) calls it with `Source.INVOICE` and the line id. It writes a row only when the price differs from the newest recorded row: per-unit price, pack price or pack text, compared with `compareTo`. A null price writes nothing. setBy is required at runtime.
- **POST /api/v1/vendors/{id}/supplies/bulk** takes `{rows:[SetVendorSupplyRequest]}`. All rows save in one transaction through the same code path as the single PUT, with source ONBOARDING. One bad row refuses them all, and an empty list is refused.
- **VendorSupplyView** gains `unit` (canonical, as stored: "KG"), `packSizeId`, `packLabel`, `pricePerPack`, `previousPrice` and `previousPriceOn`. The previous price comes from the second-newest history row (effective_on DESC, created_at DESC). Both are null when there is no earlier row. `packLabel` uses the same rule as T-253's `PackSizeService.label`: `name + " = " + Quantities.exact(quantity, unit)`, or just the size when there is no name. It is written out in VendorService because that method is package-private. The method is named `chipText()`, not `label()`, so UnitLabelAgreementTest's scan passes.
- **GET /api/v1/vendors/supplies?ingredientId=…** returns a flat `IngredientSupplyView` (vendorId, vendorName and every VendorSupplyView field), ordered by vendor name. Linking from the ingredient side uses the same PUT.
- All endpoints use `hasAuthority('MANAGE_VENDORS')`.
- **V145:** adds `vendor_price_history.backfilled BOOLEAN NOT NULL DEFAULT false`, makes `set_by` nullable, and adds `CHECK (set_by IS NOT NULL OR backfilled)`. It then copies each non-null `last_price` into a history row per temple: source MANUAL, effective_on = updated_at as a date in the temple's time zone (COALESCE to current_date), set_by NULL, backfilled true. Pairs that already have history are skipped. It follows the V144 tenant-loop pattern with the loop variable `v_tenant`. It was written in the scratchpad and copied into db/migration only once complete.

## Conductor's / work manager's calls (recorded as asked)

1. A pack with a per-unit `lastPrice` and no `pricePerPack` is refused with `SUPPLY_PRICE_PER_PACK_ONLY` (KMS-400163). Price per pack only.
2. A re-save at the same price writes no history row, and neither does a cleared price. The next price is compared with the last recorded one.
3. Backfill V145: one MANUAL row per existing non-null last_price, dated from updated_at, written per temple under RLS.
4. For information, not built here: the ingredient-side dropdown will offer active vendors only (UI, later). The GET returns every supply row, including a deactivated vendor's, the same as the vendor page's table.
5. Work manager: backfilled rows are not attributed to any person. `set_by` is NULL with `backfilled = true`, enforced by the CHECK, and no temple is skipped. A screen that shows who set a price should read a backfilled row as "recorded before price history". No view in this task exposes who set a price.

## Acceptance criteria

- **60 → 64 gives two history rows; the view shows lastPrice 64, previousPrice 60 and its date.** VendorPriceHistoryIT `aChangedPriceLeavesTwoRowsAndThePreviousPrice`. It checks both rows (MANUAL, set_by = the signed-in user, backfilled false) and the JSON `lastPrice 64`, `previousPrice 60`, `previousPriceOn` = today in Asia/Kolkata.
- **A 25 Kg bag at ₹1,500 per pack derives ₹60/Kg.** `aPackPriceIsWorkedOutPerUnit` checks lastPrice 60, pricePerPack 1500, packLabel "Bag = 25 Kg", and the history row at 60 with pack price 1500 and "Bag = 25 Kg". The same test checks that 500 ml at ₹325 on ghee (L) gives ₹650 / L and reads "500 ml".
- **A bulk add of 3 ingredients with 2 prices creates 3 supplies and 2 ONBOARDING history rows.** VendorOnboardingIT `bulkAddCreatesSuppliesAndOnboardingHistory` (one of the two prices is a bag price).
- **Another temple's rows are invisible (RLS).** `anotherTemplesRowsAreInvisible` runs as the unprivileged app role adopted as temple A: it sees 1 row, and 0 rows for temple B. Temple B's pack id, sent by A, is refused KMS-400162, and B's ingredient returns an empty vendor list. ProcurementRowLevelSecurityIT still passes.
- **No change, no row:** `noChangeNoRow`. **Pack refusals (400162 / 400163 / field error), nothing written:** `packRefusals`. **Bulk is all-or-nothing:** `oneBadRowRefusesTheLot`. **Permission:** a volunteer is forbidden on both new endpoints. **V145:** `v145BackfillsExistingPrices` migrates a fresh database to V144, seeds two temples, then migrates to V145. Result: `backfill-a|Rice|58.0000|2026-08-15|MANUAL|true|nobody` and the same for b; the unpriced supply gets no row; the app role cannot insert a non-backfilled row without set_by. TenantLoopMigrationIT plans the loop body against a real temple.
- **Negative control:** 5 of 10 fail with the write removed (above).

## Addendum: last_price widened to NUMERIC(14, 4) in V145 (conductor's call, 2026-09-19)

V145 section 0 runs before the backfill: `ALTER TABLE vendor_supplies ALTER COLUMN last_price TYPE NUMERIC(14, 4)`. The conductor put this in V145 because V145 has never been applied anywhere. It is a widening only, so existing values are kept exactly (58.00 becomes 58.0000). No view or function depends on the column (grep of every `CREATE … VIEW` migration found no vendor_supplies). Nothing maps it with a fixed scale: the only JPA entities are Tenant and User, and every reader uses JDBC `getBigDecimal`.

**What reads or writes last_price, outside my files (none changed):**
- `costing/BasketCostingService.java:179-182` reads it (preferred price, else max). The basket total is `setScale(2)` at line 122, after multiplying. That is the right place to round, and the per-gram rate now reaches it unrounded.
- `ingredient/MarketRateService.java:125` (T-254) reads it for the stock-value suggestion. The suggestion may now carry 4 places; the screen formats it.
- `purchaseorder/PurchaseOrderService.java:303-306` copies it into `purchase_order_lines.expected_price`, which is **NUMERIC(12, 2) (V26)**. PostgreSQL rounds on assignment, so a gm-priced PO line's expected price becomes ₹0.07 again. **Reported, not changed:** widening expected_price is outside this contract. It matters only for gm/ml-priced lines' expected price per unit.
- `receiving/ReceivingService.java:311-314` writes it from a delivery (R-DEL-5 removes that). Its input is NUMERIC(12, 2) (V82), and it fits the wider column.
- ShoppingListService does not read the column (grep: no match).
