# T-141 — the shopping list walks the plan once and reads its recipes in one batch: 392 statements down to 43

**The headline.** One `GET /api/v1/shopping-list` sent **392** SQL statements before this task and
sends **43** after. 348 of the 392 were `RecipeService` reading one recipe at a time; 2 remain. The
whole derivation of what the plan claims ran twice per page load; it runs once.

**The brief said 404 and it is 392 on today's tree.** Measured before touching anything, with the
instruments the brief named — `ShoppingListPerformanceIT` and `StatementRecorder` — over T-139's
five-year fixture. The shape the brief described is entirely correct; only the number moved, and by
12, which is the sort of drift a wave of unrelated work produces. The recipe figure is **348, not
360**, for the same reason. Everything below quotes the numbers this tree actually produced.

Fixture both times: 146,150 stock movements, 16,963 meal plans (408 planned), 150 ingredients, 26

**The database's own counters agree, from the other side of the connection.** `pg_stat_all_tables`

**On the 70.7 ms: do not read it as the win.** The brief is right that a local Testcontainers
PostgreSQL over a loopback socket hides round-trip cost almost entirely, and that behind Cloud Run
and Cloud SQL the count is the honest measure. 349 fewer round trips at even a 1 ms round trip is
a third of a second that this laptop cannot show. The statement count is the acceptance criterion;
the milliseconds are a bonus that happens to point the same way.

## What was wrong, in two independent halves

**Half one — the plan was walked twice.** `ShoppingListService.suggestions()` asks
`SufficiencyService.shortfallFeed(onHand)` for the meal-plan shortfall and
`InventoryItemService.lowStock(onHand)` for the low-stock top-up. The first reaches
`CommittedStockService.claimsInHorizon()`, the second reaches
`CommittedStockService.committedBaseByIngredient()`. Both are projections of one private method,
`claims()`, and nothing shared the result — so one page load resolved the festival calendar twice,
read the planned dishes twice, and scaled every recipe in the buying window twice.

**Half two — one recipe at a time.** `claims()` called `recipeService.scale(recipeId, targetYield)`
per dish, memoised on the pair. `scale()` went through `get()`, which is two statements: the head
row, then the lines. The memo bounded the count without stopping it, because a temple cooking the
same dish at a different head count each day has nearly as many distinct pairs as dishes. At
staging scale: 87 distinct pairs per walk, two walks, two statements each = **348**.

## The thing the brief told me to check before collapsing `claims()`, and what I found

*"A value computed twice and used for two different questions may be two different questions."*

**They are the same question, and that is deliberate rather than lucky.** `claimsInHorizon()`
groups the claim rows by meal; `committedBaseByIngredient()` sums the same rows by ingredient. Both
are built from one `claims()` list, over one window, one `status = 'PLANNED'` filter and one
"today". `claimsInHorizon()`'s own javadoc, written by T-088, says so in as many words: *"This is
the same set of claims `committedBaseByIngredient()` sums, handed over un-summed"*, and T-088's
stated purpose was that *"a dish that is committed on the inventory screen is a dish the badge
counts, necessarily rather than by agreement."* Two walks could only ever differ by disagreeing —
which is the defect T-088 existed to remove. So computing once is not merely safe here; it is what
the class already claims to do.

## What was built, and what is in the contract

**`RecipeService.scaleAll(List<ScaleRequest>)`** — several recipe-and-yield pairs scaled in two
statements for the whole batch, over the *distinct* recipes (a `= ANY(?)` head read and a
`= ANY(?)` lines read, both still fully RLS-qualified). The scaling itself is arithmetic and stays
per request. `scale(id, yield)` now delegates to it — a batch of one, the same two statements it
always cost, and one definition of what scaling means instead of two that could drift. Yield
validation, its `VALIDATION_FAILED` details and `RESOURCE_NOT_FOUND` for an invisible recipe all
behave exactly as before, and yields are still checked before any round trip.

**`CommittedStockService`** — `claims()` splits into a memo check and `computeClaims()`; the
per-dish `scale()` loop becomes one `scaleAll` call over the distinct pairs, zipped back by
position.

### The memo: one sentence, and how each clause is enforced

> The claim list lives in the current **read-only database transaction**, for the **one temple** it
> was computed for, and is **discarded when that transaction completes**.

- **Read-only transaction.** Nothing is held unless
  `TransactionSynchronizationManager.isCurrentTransactionReadOnly()`. So no transaction that could
  itself change a meal plan can be reading claims computed before it did — the staleness question
  does not arise rather than being argued away. Every caller today is a read path
  (`ShoppingListService.list`, `InventoryItemService.list/get/lowStock`,
  `SufficiencyService.sufficiency/shortfallFeed`); one written tomorrow that is not simply
  recomputes.
- **One transaction.** Bound as a transaction resource under a private constant key and unbound by
  a `TransactionSynchronization` in `afterCompletion` — and in `suspend()`, so an inner
  `REQUIRES_NEW` starts from nothing. It is not a field, not a static, and not a bare `ThreadLocal`
  a missing `finally` could leak onto the next request borrowing this pooled thread.
- **One temple.** The memo carries the tenant it was computed for and is discarded rather than used
  if that is not the tenant asking. This should never fire — the tenant is fixed on the thread
  before the transaction opens and RLS scopes the connection for its whole life — and it is there
  because "cannot happen" is the wrong amount of care to take over one temple reading another's
  plan. `oneTemplesClaimsAreInvisibleToAnother` exercises it.

**Why this does not contradict T-140.** `ShoppingListService` says, of the stock ledger, *"a cache
with a lifetime could do worse, which is why there is no cache here."* That reasoning is intact and
points the same way. The danger it names is a figure held **across** reads, so a screen prints what
the database no longer says. What is held here is held **within** one read — which is exactly what
T-140 did when it read the ledger once and handed that one reading to both streams, arrived at from
the other end because the two collaborators needing this one are outside this task's contract.

## The negative control

A performance fix makes this harder than usual: a statement count is not a passing assertion, so
the count had to become a test first. `ShoppingListStatementCountIT` is that test, and it runs in
the **ordinary suite** rather than behind `KMS_PERF` — deliberately, and it is not tagged `perf`
either, because a guard a build script can switch off is not a guard. T-140's ledger assertion sits
in the gated class and has never run in CI. This one builds a thirty-day fixture in seconds.

Script: `control-T-141.sh` (in the shared scratchpad, named for this task because the scratchpad is
shared). It restores the two **unfixed** files from a `cp` snapshot — never `git checkout --`, the
working tree is dirty with three other builders' work this wave — asserts the revert actually took
before running anything, runs the gate, and restores the fix in a `trap` whatever happens.

Two honest notes on the control:

- **The third test passes against the unfixed code, and should.** With no memo there is nothing to
  leak, so "one temple's claims are invisible to another" is trivially true. It guards the memo
  that now exists; it is not evidence the memo was needed.
- **`theMemoDiesWithTheTransaction` fails on the unfixed tree for the wrong reason** — it reports 2
  walks because there was no memo at all, not because a memo outlived anything. On the fixed tree it
  says the thing it means: the second read finds nothing held and computes its own. It is a lifetime
  guard, and only the fixed tree gives it something to guard.

## Not done / needs Rajeev

- **No hand smoke-test.** Commandment 5 asks for one where a task adds a user-facing surface. This
  task adds none: no new screen, no new field, no new error code, no change to a single figure the
  shopping list prints — only how many statements it sends to print them. The behaviour is held by
  `ShoppingListIT` (12 tests) and `HandAddedLineIT` (9), which pass unchanged. **If you want it
  driven on staging anyway, the check is that `/shopping-list` shows the same lines and quantities
  it did before, faster.**
- **The gain is larger on Cloud SQL than these figures show, and nobody has measured it there.**
  Everything above is a local Testcontainers PostgreSQL over loopback, where a round trip is
  nearly free. 349 fewer round trips is the part of this that a laptop cannot demonstrate. Worth a
  before/after on staging if the deployed page is still slow.
- **The `perf` package now builds one Spring context in the ordinary suite** that it did not
  before — `ShoppingListStatementCountIT` shares `@Import(PerfStubVerifierConfiguration.class)`
  with the two gated classes, so it is one context, not two. Given the project's history with
  context-cache growth, flagging it rather than leaving it to be discovered.
- **`RecipeService.scale()` now routes through `scaleAll()`**, so its head query selects four
  columns rather than the whole recipe. Every consumer of `ScaledRecipeView` only ever used those
  four, and `RecipeIT`, `RecipeScalerTest`, `JobCardIT`, `RecipeDocumentE2EIT` and
  `MaterialsCostIT`'s siblings all pass — but it is a change to a method five other services call,
  so it is named here rather than buried.
- **Interference from another builder, for the record.** The first control run died at
  `compileTestJava` on `backend/.../shift/ShiftAttendanceIT.java` — another builder mid-edit in a
  file I do not hold. I did not touch it; the control script now waits for the shared checkout to
  compile before reverting anything. Nothing about that failure was mine and nothing about it is
  outstanding.
