## Layer versus screen — the four-fields rule, and what I did instead

**The rule bites, and I did not ignore it.** `DESIGN_SYSTEM.md:281` is arithmetic and says so:
*"A form of four fields or more becomes a screen. Three or fewer stays inline. … The number matters
more than the judgement."* `app/volunteers/new/page.tsx` line 14 states its own compliance in one
line — `/** Post a shift — eight fields, so a screen of its own. */` — and that is the screen the
overlay Rajeev remembers became on 2026-08-21.

So the eight-field form could not come here. **What I did instead was cut the layer to three
fields** rather than build a screen or breach the rule:

| Field | Asked or derived |
|---|---|
| Start | **asked** — the one thing nobody can derive |
| End | **asked**, offered as the meal's ready-by (crew wanted up to the moment food goes out) |
| How many volunteers | **asked**, offered as `crewRequired − rostered`, floored at 1 — the shortfall itself |
| Title | derived: `"Lunch preparation on Tuesday, 1 September 2026"`, **shown** not typed |
| Date | derived: the planner day |
| `mealDate` / `mealKind` / `mealEventName` | derived: the meal the layer was opened from (D-14) |
| Location, description, reminders | **not asked, and never blanked** — see below |

Three fields, so the layer is inside the rule rather than in breach of it, and the row's ask
(a layer, prefilled, land back where you were) is satisfied. `expect(layer.querySelectorAll("input")
.length).toBe(3)` is asserted in the test file so the count cannot drift back over the line unnoticed.

**Two consequences worth Rajeev's eye, because they are product decisions and not technical ones:**

- **`updateShift` replaces the whole shift.** A three-field save that sent empty strings would wipe
  a location or description somebody had typed on the volunteers screen. So on a correction those
  three are carried through from the loaded `ShiftView` unchanged, and on a new shift they take the
  full form's own defaults (no location, no description, one reminder a day before, 1440 minutes —
  the same default `readShiftForm` applies). There is a test asserting all three survive a save.
- **Where the other five fields live is a link, not a second form.** The layer's foot carries
  `Location, notes and reminders` → `/volunteers/[id]/edit`, offered only once there is a shift to
  open. A third copy of the shift form is the drift `shift-form.tsx`'s own docstring warns about.

**Why I did not simply reuse `app/volunteers/shift-form.tsx`'s `ShiftFields`, which would have been
the smallest diff:** it prefills only through its `shift?: ShiftView` prop, and that same prop flips
its `aria-label` to *"Edit a shift"*. Prefilling a **new** shift would therefore have announced the
form as an edit to anybody using a screen reader, and fixing that means editing `shift-form.tsx`,
which is not in my contract. I chose correct copy over the smaller diff and wrote my own three
fields. Flagging it because it is the one place this task duplicates markup that already exists.

**If Rajeev wants the rule to win outright** — the full eight-field form on its own URL, reached
from the planner and returning to it — that is a new route (`/planner/[date]/[kind]/shift`, say),
which is neither in my contract nor reserved, and it costs the thing the acceptance criterion asks
for: the reader's scroll position and everything the day's blocks hold open (the language a job card
is set to print in, a correction half typed). `MealServices` re-reads on a prop *specifically* so it
does not remount and lose that state; a navigation would throw it away. I would rather he rule on it
than widen my own paths.

**One deviation from the row's literal text, raised here rather than after:** the row's example title
is *"Lunch preparation on September 1 2026"* — month-first. Every date in this application is
day-first with the month spelled out (`longDate`, and the memory note *Date format decision*), so the
title reads **"Lunch preparation on Tuesday, 1 September 2026"**. The pattern is the row's; only the
date format is the project's. Say the word and it is one function call.

## Not done / needs Rajeev

1. **No hand smoke test.** Commandment 5 wants a new user-facing surface driven by hand, and I could
   not: this is a builder in a shared checkout with nothing deployed, and the change is not on
   staging. `next build` and the tests are what stands behind it. **The layer wants one pass on UAT
   before this item is closed** — specifically the three things a test cannot judge: whether the
   pebble row wraps sensibly on a meal that already carries an event name, a badge and a card number;
   whether the scrim over a long planner day scrolls the way the recipe layer does; and whether
   *"Ask for volunteers"* is the right words for the button (I preferred it to *"Post a shift"*
   because the planner's problem is people, not shifts — that is a copy judgement and it is his).
2. **The layer-versus-screen argument above needs his ruling.** I built the layer at three fields,
   which keeps both the row and the rule satisfied, but it means the planner path asks less than the
   volunteers path does. If he wants parity, that is the eight-field form and therefore a screen and
   a new route, which is a new contract.
3. **The title's date format** deviates from the row's literal example (day-first, not month-first).
   Deliberate; one line to change.
4. **A shift posted for the evening before a morning meal will not be found.** The day's shifts are
   read with `listShifts({from: date, to: date})`, which filters on `shiftDate`. Every shift raised
   *from this affordance* has `shiftDate === mealDate`, so it is always found; a shift posted from
   the volunteers screen for the 31st and linked to the 1st's breakfast is real, is correctly linked,
   counts correctly toward crew, and simply will not be drawn on the 1st's planner. That is a gap in
   the **read**, not in the link, and closing it means widening the range — which needs a decision
   about how far, so I have written it in the code comment and left it.
5. **A second shift for the same meal cannot be raised from here** — the button hides once one is
   linked, and the way to want more people is to open the shift and raise its capacity. If a temple
   genuinely runs a cooking shift and a serving shift against one lunch, the button should stay.
   Deliberately not designed for, per *no unnamed abstractions*; flagging it as the case I can most
   easily imagine being wrong about.
6. **`frontend/app/planner/[date]/[kind]/page.tsx` was in my contract and is untouched** — the
   shortfall is not on that screen. Nothing owed; recorded so nobody wonders.
7. **Not run:** the backend suite. This task adds no backend and T-079 is mid-migration in the same
   checkout; `git status` confirms none of its files are mine.
