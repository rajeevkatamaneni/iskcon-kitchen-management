## Every save path, and whether it clears the mark

`grep -rn "INSERT INTO ingredients\|UPDATE ingredients" --include=*.java --include=*.sql backend/src`
outside tests returns exactly four writers, and there are no others — no migration writes the table
either:

| Path | What it does | Clears the mark? |
|---|---|---|
| `RecipeImportService:199` `INSERT` | the import, writing `library_derived = true` | n/a — it is what sets it |
| `IngredientService.create:111` `INSERT` | a person typing a new ingredient. **Never names the column at all**, so the `DEFAULT false` stands | n/a — a hand-typed row is never marked |
| `IngredientService.update:146` `UPDATE` | the edit form's Save, the whole descriptive body | **Yes.** `library_derived = false` in the same statement |
| `IngredientService.setEkadashiFlag:184` `UPDATE` | the one-click Ekadashi toggle on the row | **No — deliberately. See below.** |

**The Ekadashi toggle is the second path, and I left it alone on purpose.** Rajeev's wording is
*"the mark clears when somebody edits and saves the ingredient"*, and the edit form is the only
thing that edits and saves it. The toggle writes one religious-compliance flag from a button on the
row without opening the row or showing anybody the category and unit the import guessed — the very
fields the review is about — and it *returns early when the flag is already what was asked for*, so
a click that cleared the mark and a click that did not would look identical to the person pressing
it. `IngredientIT.ekadashiFlagLeavesTheMarkAlone` asserts the current behaviour and says in its
comment that it is the test to change if Rajeev rules the other way. **This is the one judgement in
the task I would want him to confirm** — the counter-argument is real: `/recipes` tells an admin to
go and set the Ekadashi flag on imported ingredients, and an admin who does exactly that still
leaves every row labelled.

## Where the Recipes-screen message went, and why

**Directly under the existing Ekadashi warning, above the search box — and conditional on the count
being above zero.**

- *Why that spot:* `/recipes` already carries a standing `InlineNotice` about imports (D-18), placed
  there with the reasoning *"import is the act that creates the unflagged rows, and this is the
  screen it is started from"*. That reasoning is word for word this task's, so the new message goes
  beside its sibling rather than inventing a third place. Above the search box for the reason the
  existing one gives: both are about the catalogue, not about what the box just found.
- *Why under it, not over it:* the Ekadashi one is the graver of the two. An unflagged ingredient
  reaches an Ekadashi menu; an unreviewed one is merely unreviewed.
- *Why that satisfies "seen after an import rather than always":* the existing warning is
  unconditional and says the same thing on every visit. This one is gated on `count > 0`. A temple
  that has never imported never sees it. A temple that has reviewed everything stops seeing it. And
  the count is **re-fetched after every successful import on that screen**, so somebody who presses
  the plus sees the number appear or rise on the spot — which is the only moment the message is
  actually news. `recipes.test.tsx` asserts each of those three.
- *Tone `info`, not `warning`* — same ruling as the label. An import-created ingredient is not
  deficient, and `DESIGN_SYSTEM.md:115` reserves the semantic colours for something genuinely low,
  wrong, overdue or complete.
- It carries a **Review them** link to `/ingredients?show=added-by-import`, which is the filtered
  view, so the message and the queue it describes are one gesture apart.

## The filter mechanism — I followed the existing one

**The ingredients list had no filter at all.** The repo's pattern for "one list with a filter over
it" is `SegmentedControl` in the address bar, used by `/ingredient-requests`, `/donations`,
`/leave` and `/planner/reuse`. I used it verbatim: two options, **All ingredients** /
**Added by an import**, `router.replace` rather than `push` (the filter narrows one screen, so Back
should leave the screen), and the state read from `?show=added-by-import`. Being in the URL is what
lets the Recipes message link straight at it.

Two consequences worth naming: the control and the message both **hide themselves at zero**, so a
temple that has never imported sees neither and the screen is exactly what it was; and the existing
`?added=` flash-capture effect had to be taught to keep `show` when it strips `added`, or adding an
ingredient while filtered would have dumped you back into the whole catalogue. There is a test for
that.
