## Final DDL summary

Every new table has `tenant_id → tenants RESTRICT` and calls `enable_tenant_rls()`.

**ingredient_pack_sizes** (new): id, tenant_id, ingredient_id → ingredients CASCADE, name (nullable, not blank), quantity NUMERIC(14,3) > 0, unit (KG/GM/L/ML/PIECES), base_quantity (generated: quantity × 1000 for KG/L, else × 1), unit_family (generated: MASS/VOLUME/COUNT), created_at. UNIQUE (id, ingredient_id) for composite FKs. UNIQUE INDEX (ingredient_id, base_quantity), which is PROVISIONAL. AFTER INSERT/UPDATE trigger `ingredient_pack_sizes_same_family`: refuses a unit outside the ingredient's canonical-unit family, and refuses an ingredient not visible to this temple.

**ingredients** (new columns): market_rate NUMERIC(14,4) > 0, market_rate_on DATE, market_rate_source (STOCK_TAKE/INVOICE/MANUAL). All three are null or all three are set.

**ingredient_market_rate_history** (new, append-only): id, tenant_id, ingredient_id → ingredients RESTRICT, rate NUMERIC(14,4) > 0, effective_on DATE, source (STOCK_TAKE/INVOICE/MANUAL), vendor_invoice_line_id → vendor_invoice_lines RESTRICT (set exactly when source = INVOICE), set_by → users RESTRICT, created_at.

**vendor_supplies** (new columns): pack_size_id, price_per_pack NUMERIC(12,2) ≥ 0. FK (pack_size_id, ingredient_id) → ingredient_pack_sizes(id, ingredient_id) RESTRICT, DEFERRABLE INITIALLY IMMEDIATE. A pack price requires a pack.

**vendor_invoices** (new columns): sub_total, gst_amount, other_charges, other_charges_note, discount, grand_total. All nullable, and every amount is ≥ 0.

**vendor_invoice_lines** (new): id, tenant_id, invoice_id → vendor_invoices CASCADE, goods_receipt_line_id → goods_receipt_lines RESTRICT (nullable), ingredient_id → ingredients RESTRICT (nullable), description, billed_qty NUMERIC(14,3) ≥ 0, unit (5 units), pack_size_id + pack_count (both or neither; count > 0; needs an ingredient), line_amount NUMERIC(12,2) NOT NULL ≥ 0, rate NUMERIC(14,4) GENERATED = round(amount ÷ billed_qty, 4) per `unit` (null when billed_qty = 0), created_at. Every line has either an ingredient or a non-blank description, never both and never neither (the same rule V100 put on PO lines). A receipt line requires an ingredient. Composite FK to pack sizes, as on vendor_supplies.

**vendor_invoice_deliveries** (new): id, tenant_id, invoice_id → vendor_invoices CASCADE, receipt_id → goods_receipts RESTRICT, created_at, UNIQUE (invoice_id, receipt_id).

**vendor_price_history** (new, append-only): id, tenant_id, vendor_id → vendors RESTRICT, ingredient_id → ingredients RESTRICT, price_per_unit NUMERIC(14,4) ≥ 0, price_per_pack NUMERIC(12,2) + pack_description TEXT (both or neither; a snapshot, not an FK), effective_on DATE, source (ONBOARDING/MANUAL/INVOICE), vendor_invoice_line_id → vendor_invoice_lines RESTRICT (set exactly when source = INVOICE), set_by → users RESTRICT, created_at.

**invoice_payments** (new column): received_by_name TEXT (nullable, not blank).

**attachments** (new): id, tenant_id, kind (INVOICE_BILL/PAYMENT_PROOF/CASH_SIGNED_NOTE/CASH_RECEIVER_PHOTO), storage_key UNIQUE and not blank, content_type not blank, size_bytes > 0, original_name, invoice_id → vendor_invoices RESTRICT, payment_id → invoice_payments RESTRICT, uploaded_by → users RESTRICT, uploaded_at. At most one parent. A bill never goes on a payment, and payment kinds never go on an invoice. A row with no parent yet is allowed, so a file can be uploaded before the form is saved.

**recipe_ingredients** (new column): preparation_note TEXT (nullable, not blank).

**ingredient_aliases** (new): id, tenant_id, ingredient_id → ingredients CASCADE, alias, normalised_alias (both not blank), created_at, UNIQUE (tenant_id, normalised_alias). Backfilled per tenant from `ingredients.aliases` using lower(btrim()). Blanks are skipped. When two ingredients share an alias, the older ingredient keeps it and the collision count goes in a NOTICE. The array column is left in place.

## Decisions (recorded, as asked)

- **Market-rate history** has its own table (`ingredient_market_rate_history`), not rows in vendor_price_history with a null vendor. This was the conductor's ruling and is final.
- **PROVISIONAL, pending Rajeev: price history survives removing a supply.** §3 draws the link as "→ vendor_supplies". But `VendorService` deletes supply rows, and history is append-only. CASCADE and SET NULL would both be refused by the append-only trigger. RESTRICT would change today's behaviour. So I used separate FKs to vendors and ingredients. If he rules the other way, it is one `ALTER TABLE … ADD CONSTRAINT … REFERENCES vendor_supplies (vendor_id, ingredient_id) ON DELETE RESTRICT`, written out in the migration's comment.
- **PROVISIONAL, pending Rajeev: a duplicate pack size is the same canonical quantity, whatever it is called.** That is one unique index. The alternative ("same name and size") is written out beside it.
- **Pack sizes store what was entered** (a number and a unit), plus a generated base quantity and family. The canonical unit can be edited, so storing a pre-converted figure would go stale.
- **What SQL enforces for pack sizes:** positive quantity, a valid unit, no duplicates, and same family (the trigger). **Left to the service:** the limit of 8 (a count in a trigger is racy), and refusing a change to an ingredient's canonical-unit family while it has pack sizes.
- **Rate scale:** derived per-unit rates are NUMERIC(14,4), because ₹65/Kg is ₹0.065/gm. Typed money is NUMERIC(12,2), the same as the existing columns.
- **History pack is a text snapshot, not an FK.** An append-only row could never release a pack size that was later removed from the ingredient.
- **attachments rather than V12 `documents`.** `documents` records generated artifacts: a PENDING/READY/FAILED lifecycle, language, target yield and error, with the kind limited to PDFs. An upload has none of those. The storage service (`DocumentStorage`) is still the one used.
- **Composite pack FKs are DEFERRABLE**, so the merge tool (R-DUP-3) can re-point a pack and its users in one transaction.

## Acceptance criteria

- **AC-3.1:** met. `ProcurementRowLevelSecurityIT` runs through the application's DataSource as `kms_app`. For each of the 7 new tables it checks four things: each temple sees only its own rows; with no temple set, nothing is visible; an insert for another temple is refused with a row-level security error; and cross-temple update/delete touches 0 rows. The negative control shows the test fails when RLS is removed from one table.
- **AC-3.2:** met. `ProcurementDataModelMigrationIT` migrates to V143, seeds two temples and snapshots every row as jsonb. The seed covers POs, 2 receipts (one with a rejection), a PO invoice, a direct invoice, payments (including a reversal and cash), stock movements, inventory items, supplies, recipe lines and ingredients. It then runs V144 and compares byte for byte (minus the added columns). On-hand stock is compared per temple, ingredient and unit. The added columns are asserted null on the old rows.
- Aliases are backfilled per temple, with the collision and cross-temple cases asserted.
- The permission matrix rows are added and pass.
