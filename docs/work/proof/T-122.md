# T-122 — on hand stops at zero; the shortfall becomes a record of a discrepancy, not a movement of stock

T-087 shipped this morning with the shortfall **subtracting**, so an ingredient read **−40 Kg**.
Rajeev: *"That makes no sense. We should stop at 0. How does negative ingredients make any sense?"*

The consumption still draws what actually exists. The `USED_BEYOND_RECORDED_STOCK` row is unchanged
in every respect a person can see — same quantity, same meal-plan reference, same note naming the
ingredient, same place in the movement list — and it now **subtracts nothing**. Only its effect on
the total changed, which is what the brief asked for.

---

## Where the shortfall record now lives, and why

**Still a `stock_movements` row.** Both answers were defensible; here is the case for this one,
and it is not "smaller change".

Three things about the row are load-bearing, and **all three already work in this table and nowhere
else**:

1. **Reachable from the meal it came from** — it carries the same `(reference_type, reference_id)`
   pair as the draws beside it, which is exactly what `compensateAllFor` finds a meal's stock by.
2. **On a list somebody reads** — that list *is* the movement history on the ingredient's own
   screen, and `GET /api/v1/inventory/movements?type=USED_BEYOND_RECORDED_STOCK` already serves it.
3. **Names which ingredient's paperwork is behind** — in its note.

A `stock_discrepancies` table of its own would have had to rebuild all three, and one of them —
the read surface — would have needed a new endpoint, a client type and a screen, none of which was
reserved for this task. That is the weaker half of the argument. **The stronger half is the live
data.** V115 is applied to staging and staging has these rows. Moving them would mean a backfill
**out of an append-only ledger, per tenant, under RLS** — the exact shape this project has paid for
three hotfix migrations to get right. Excluding them at read time instead means **staging heals on
the next deploy with no data touched at all**, which is the right property for a correction to
something already live.

**And the contradiction the brief names is real, so it is answered rather than ignored.** A row in
`stock_movements` that moves no stock has to be legible to the next reader, so the rule is written
in three places they cannot miss: `COMMENT ON TABLE stock_movements`, `COMMENT ON COLUMN
stock_movements.quantity`, and the name of the function every reader now calls. In ledger terms it
is a **memorandum entry** — a row the book records and does not post.

**What it is not:** it is not a filter that a reader may forget. See below.

## How the exclusion is done, and whether the reader list was verified against the tree

**Verified against the tree, not taken from the brief.** `grep -rn stock_movements backend/src/main`
returns 18 files; `grep -rn "to_base_qty(" backend/src/main/java` returned **8 occurrences in 4
files**, which is the brief's six sites (`FefoAllocator`'s single query names it twice). The other
14 files are comments, reference-keyed queries or type-filtered ones, re-checked individually and
tabulated below. **The brief's list was correct and complete.**

### The mechanism: one SQL function, not six filters

`V116` adds

```sql
CREATE OR REPLACE FUNCTION to_on_hand_qty(qty NUMERIC, unit TEXT, movement_type TEXT)
RETURNS NUMERIC AS $$
    SELECT to_base_qty(qty, unit) * CASE
        WHEN movement_type = 'USED_BEYOND_RECORDED_STOCK' THEN 0
        ELSE 1
    END;
$$ LANGUAGE SQL IMMUTABLE;
```

and every ledger sum in `main/` becomes `SUM(to_on_hand_qty(quantity, unit, movement_type))`.

**Why a function rather than a filter at each site, or a view.**

- **A filter at six sites is the failure this repo has already paid for.** `V74`'s own header
  records it: the same table's unit arithmetic was written out by hand in seven places and **two of
  the copies had silently drifted**, so the tests and the application disagreed about litres and
  nothing said so. `to_on_hand_qty` is that lesson applied to the second half of the same
  expression. Six readers cannot disagree if they ask one function.
- **A view was rejected on tenancy grounds.** `CREATE VIEW` runs with the **view owner's**
  privileges unless `security_invoker = true`, and the owner here is `kms_migrator`, which owns the
  tables. A view over `stock_movements` is one missing option away from being a hole straight
  through RLS, in the one table where that matters most. A function has no such mode.
- `LANGUAGE SQL` rather than plpgsql so the planner can inline it — this sits inside `SUM()` over
  the ledger on three screens.
- `to_base_qty` is still called for every row, **including the ones multiplied by zero**. Its job is
  to raise on an unrecognised unit rather than return NULL, because `SUM` skips NULLs (V74);
  short-circuiting past it would make the discrepancy rows the one kind a corrupt unit could hide in.

### The seventh reader, caught by a test rather than by care

`StockMovementLedgerIT > no reader of the ledger computes on hand without to_on_hand_qty` walks
`src/main/java` and fails any file that contains **both** `stock_movements` and `to_base_qty(`.
Same shape as `BaseQuantityIT.noHandWrittenConversionRemains`, and for the same reason: nothing else
can catch a seventh sum — it compiles, it runs, and it returns a number. `to_base_qty` stays
correct over every other table, which is why the check is a pair rather than a ban. It currently
reports **zero offenders**; there is no `to_base_qty` left anywhere in `backend/src/main/java`.

## The trap this change laid for itself, on the write path

**`StockMovementService.compensate` reversed every movement as a `+quantity` `ADJUSTMENT`.** Once a
`USED_BEYOND_RECORDED_STOCK` row counts as zero, its reversal counted **in full** — so a temple
correcting a short meal downwards would have finished holding **forty kilos of rice nobody ever
delivered.** The same wrong figure as the defect being fixed, in the opposite direction, reached
from the end nobody was looking at: it is not among the six readers, and no amount of care about
sums would have found it.

So **a row that moves no stock is retracted in kind** — the reversal of a discrepancy is another
discrepancy row of opposite sign, carrying no `reason_category` (nobody adjusted a count). The rule
stays one sentence with no exceptions: *a `USED_BEYOND_RECORDED_STOCK` row never moves stock,
whether it is raised or withdrawn.* `compensateAllFor`, `isAlreadyCorrected` and the append-only
rule are all untouched. **Control 2 below reproduces the +40 Kg on demand.**

## The lot list

**It goes, and it goes by itself.** The shortfall is booked against a fresh batch id — an unrecorded
lot, which is what it is — and `loadBatches` groups by batch with no `HAVING`, so while the row
subtracted, the item screen listed **a bare UUID holding minus one kilo, with no arrival date and no
expiry, among the real lots.** Rajeev has seen this and it was on his list.

It now aggregates to **0**, and `InventoryItemService.get` has always dropped a batch holding
nothing (`qtyBase().signum() != 0`). **Nothing was written to remove it**; it stopped qualifying.
Asserted directly rather than argued: `InventoryConsumptionIT > the stock screens read zero, and the
shortfall's phantom lot is not among the real ones`.
