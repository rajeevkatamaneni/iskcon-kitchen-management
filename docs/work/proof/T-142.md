# T-142 — closing a part-delivered order releases what the vendor never brought, and the score at closing is shown and editable nowhere

Nothing is outstanding. Two reservations were granted mid-task and both are built and tested:
`AuditAction.PO_CLOSED`, and `PO_PART_DELIVERED_CANNOT_CANCEL` = **`KMS-400150`** (409), which closes
a hole this task exposed — **a part-delivered order can no longer be cancelled at all**, because
cancelling one erased the goods that had actually arrived from the supplier's record and let somebody
tick *"Vendor Never Delivered this Order"* against a vendor who demonstrably did deliver.

**The single most useful thing in this proof is control 1**, which came back *green* and should not
have. It passed because nothing in the fixture wanted rice anyway — so "not on the shopping list" was
true for the wrong reason, and the suppression it was meant to test was untested. **A control that
passes for the wrong reason is indistinguishable from a feature that works.** Both runs are below.

## What "released" turned out to mean, which the brief asked me to work out

**It is an absence, not a write.** T-132 derives the shopping list on every read, and exactly two
predicates in `ShoppingListService` decide whether an ingredient appears:

- `ingredientsOnLiveOrders()` — suppression. Was `status IN ('DRAFT','SENT')`.
- `poOutstandingByIngredient()` — stream 3, the short-delivery re-feed. Was
  `status = 'PARTIALLY_RECEIVED'`.

So a part-delivered order was in **neither** set: it did not suppress, and its balance was re-fed the
moment the lorry came short. That is the state D-26 reverses. The release is therefore two edits, and
they are complementary:

- `PARTIALLY_RECEIVED` **joins the suppression**. The vendor still owes the balance and the clock is
  ticking on them, so the list must not ask for rice a supplier is already bringing.
- the re-feed moves to `status = 'CLOSED'`. Closing the order is the moment the balance is nobody's
  promise any more, and it comes back on the very next read with the PO that fell short named beside
  it.

**Nothing is restored, because nothing was stored.** There is no release path in the code and there
should not be one.

### Why `shoppinglist/**` was genuinely required

The contract allows it "only if the release-on-close genuinely requires it". It does, and there was
no alternative: both predicates are private methods of `ShoppingListService`, the list is computed
and never persisted, and no other file in the tree can change what a derived read produces. Two
methods and four comment blocks changed; no signature, no other stream, no write.

### One thing I found while building it, and fixed

A closed order is terminal, so its balance would have been re-fed **for ever** — including after a
replacement order had been raised, delivered in full and received, at which point the list would ask
for 200 kg of rice the temple was standing on. The old code had the same shape, but with
`PARTIALLY_RECEIVED` it was invisible, because nothing ever moved an order out of that state; T-142
is what makes the terminal case common.

So the re-feed is bounded by **a purchase order raised for that ingredient since the close** —
raised, not delivered, because D-24a already makes creation the moment a line is answered
(*"someone else will take pity and generate another PO. Same ingredients, 2 PO's"*). One rule for
both. The edge it leaves open is the safe one: an order raised *before* the close and still live does
not count as the answer, so the balance shows once that order finishes — erring towards putting
something in front of a person rather than hiding it. Control 3 is that bound under test.

## The decisions inside it

### `CLOSED` is a new status value, where V125 argued against one

V125 refused to make `auto_cancelled` a sixth status and gave a good reason: *"Every query in this
application that groups, filters or sums on status would silently stop seeing those orders."* I took
that seriously and then found it argues the other way here, because an auto-cancellation **is** a
cancellation and must behave like one everywhere, whereas a closed order must stop being what it was
to almost every reader.

I enumerated every status predicate in the tree before deciding — `grep "po\.status\|PoStatus\."` over
`backend/src/main` — and there are ten. With `CLOSED` as a status, seven are correct with no edit at
all:

| where | what it does with a closed order | edit needed |
|---|---|---|
| `ReceivingService:104` (`SENT`/`PARTIALLY_RECEIVED` only) | refuses a receipt | none — **and this file is outside my contract** |
| `VendorPerformanceService.countOpenOrders` (`IN ('SENT','PARTIALLY_RECEIVED')`) | drops it from open and aging | none |
| `LIVE_ORDER`, `SCORED_ORDER` (`NOT IN ('DRAFT','CANCELLED')`) | goes on scoring it | none |
| `applyReceivedStatus`, `recordArrivals` | refuse it | none |
| `update`, `send` (`DRAFT` only) | refuse it | none |
| `TodayService` (`SENT` only) | not an awaited delivery | none |
| invoice screen's open list (`IN (…)`, named positively) | would have gone quiet | **one line** |
| `cancel`, WhatsApp send | would have accepted it | **two lines** |
| shopping list | the release | the task |

**The deciding line is the first one.** The alternative — keep `PARTIALLY_RECEIVED` and add a
`closed_at` flag — is correct only if `ReceivingService` is edited to know about the flag, and that
file is not this task's to touch. A design whose correctness depends on editing a file nobody is
editing is the one to reject.

### A part-delivered order can no longer be cancelled at all

This was the third flag in my first draft of this proof, granted rather than queued. It pre-dates
T-142; what T-142 gives it is a right answer.

**Why it is a defect and not untidiness.** A cancellation leaves the scorecard's `LIVE_ORDER`
predicate entirely. So cancelling a part-delivered order erased from the supplier's record the 300 kg
that had actually arrived — and, worse, `vendorAbandoned` was then offerable, so the
*"Vendor Never Delivered this Order"* tick could be put against a vendor who demonstrably **did**
deliver. That is a number this product promises is defensible becoming indefensible, which is the
same standard D-25, T-129 and `KMS-400149` were all built to hold.

`KMS-400150` says so and names the door that is right — *"Close it instead. What arrived stays on
the vendor's record, and what didn't goes back on the shopping list."* The guard sits **before** the
two claim checks, because the state is what is wrong rather than the claim: an unticked cancellation
of a part-delivered order erases the delivery just as thoroughly.

**Both halves, and the server half is the one that is the rule.** `canCancel` on the screen is
narrowed to `DRAFT` and `SENT`, and `aPartDeliveredOrderCannotBeCancelled` posts the cancellation
**straight at the endpoint**, with and without the tick — never through the screen. The lesson is
three lines above my own code in `PO_NEVER_SENT_TO_VENDOR`'s comment: *a rule that lives only in a
form is not a rule*, and it is the gap T-137 was sent back for last wave. Control 7 removes the
server guard and the endpoint answers `204` where a `409` belongs.

**The vanished control needs no sentence, and this is the one place that is true.** Everywhere else
on this screen an absent control is explained, because *"a control that disappears with no
explanation reads as a bug or as a missing permission"*. Here the replacement is structural:
`canClose` is the exact complement of the status removed from `canCancel`, so the panel that goes is
always replaced, in the same spot, by *"Close this order, part delivered"* — which says what happens
to the goods that came and to the ones that did not. `puts the closing panel where the cancel panel
was` asserts that rather than assuming it.

`cancellingWhatWasNeverDeliveredStillWorks` is the other side: a draft and a sent order cancel
exactly as they did, tick and all. Only the part-delivered case moved.

### The audit row, and why the waiver is what makes it necessary

`close` writes `AuditAction.PO_CLOSED` with the outcome and the sentence in its after-state, shaped
like `PO_CANCELLED`'s. That is not bookkeeping. **Excusing a shortfall is the single act an admin can
take that changes what a supplier's scorecard reports**, and D-26's third cost is that such a figure
must be defensible — *"an admin changed it" is not an answer to a vendor who disputes their score*.
Who waived it, when, and in what words is.

Unlike T-137's sweep there was no obstacle: closing is a human act, the actor is verified, and
`audit_events.actor_user_id` is satisfied. `closingIsAudited` asserts the actor id, the actor label,
the before-state, the outcome and the sentence. Control 8 removes the row and shows that the order's
own trail still reads perfectly without it — which is exactly why the absence needs a test rather
than an eye.

### The named outcome is a name; there is no number to move

`VENDOR_LET_US_DOWN` scores **exactly as computed**, and that is not an omission. T-124 scores on-time
by quantity, so the 200 kg that never came is already in the percentage — 300 of 500 inside the window
is 60%, with nothing to add. What the name does is make the record legible: a reader looking at a 60%
can tell an order the temple holds against the supplier from one it accepts, which is a different fact
from the arithmetic and is nowhere else. (It is arithmetically identical to `AS_COMPUTED` today; that
is deliberate and is flagged for you below, because it is the one place you might want something more.)

`SHORTFALL_EXCUSED` takes the order out of the on-time figure **and out of the fill rate**. That is
the one place I deliberately diverge from T-137's pattern, and the reason is nameable: ordering late
excuses **our** timing and not a half-empty lorry, whereas this excuses **their** shortfall, which is
precisely the question the fill rate asks. Waiving the black mark and leaving 60% standing in the
column that measures the shortfall would waive almost nothing. Control 2 is that explanation under
test — it builds the obvious implementation (copy T-137 exactly) and shows the suite catch it.

`ordersExcused` sits beside **both** percentages on the scorecard, and the caveat paragraph says what
was excused and from what. The fill-rate column has an exclusion for the first time, so it needed its
own count there — which is the standard T-137 set and the note it left open.

### The score is shown, and the absence is tested rather than asserted

`VendorPerformanceService.scoreOfOrder` is the report's own item query narrowed to one order — the SQL
was extracted into `scoreItemsWhere` so the arithmetic exists once. If the closing screen computed the
figure separately, a person would be shown one number while the scorecard printed another, and both
would be defended by somebody.

Two tests guard the "no dial" half, one on each side:

- `theScoreIsShownAndThereIsNoWayToMoveIt` posts `onTimePercent`, `score`, `fillRatePercent` and
  `deliveryScore` straight at the endpoint — the way T-129's guard is tested, never through a screen,
  because a rule that lives only in a form is not a rule — and asserts the figures are exactly what
  the receipts made them.
- `offers no way at all to change that score` enumerates every `input`/`select`/`textarea`/`button` in
  the closing form and requires exactly three radios, one text box and one submit. Control 6 puts an
  adjustment box back and shows it react, because an absence nobody breaks is an absence that proves
  nothing.

## RLS

`purchase_orders` is under `enable_tenant_rls()` (V26:53). **V126 touches no rows** — one
`DROP CONSTRAINT`, four `ADD CONSTRAINT`s and three `ADD COLUMN`s, all DDL, run as the table owner —
so there is no tenant loop and no tenant was adopted. That is a decision: no order that already exists
has been closed by anybody, so NULL in all three columns is the truthful reading for every row in
every tenant, and it is what `ADD COLUMN` writes. `ADD CONSTRAINT` genuinely validates every tenant's
existing rows rather than silently validating none of them, which is why the status CHECK is dropped
and re-added rather than left alone.

Nothing in the application writes these columns outside `PurchaseOrderService.close`, which runs on
the tenant-scoped connection like every other request.

## Acceptance criteria

**1. Closing a part-delivered order releases the undelivered remainder to the shopping list.**
`closingReleasesTheBalanceToTheShoppingList` (200 kg back, `PO-2026-0042` named),
`aLiveShortfallIsStillSuppressedWhileTheVendorOwesIt` (silent while live, even against an independent
demand), and end to end through the receiving endpoint in
`ReceivingIT.partialReceiptBooksGoodRejectsBadAndHoldsTheBalance`. **What "released" means in the
derivation is set out above** — an absence, not a write. Controls 1 and 3.

**2. Two named outcomes at closing, plus neither.** `theVendorLetUsDownIsScoredAsComputedAndSaidSo`,
`theShortfallExcusedLeavesBothFigures`, `neitherIsScoredAsComputedAndClaimsNothing`, and on the screen
`sends the name the person chose, and the sentence with it` and `says what each ending costs the
vendor before it is chosen`.

**3. Anything other than "as computed" requires a sentence.** `aNamedOutcomeNeedsASentence` — the
refusal is `KMS-400001` with `fieldErrors[0].field = namedOutcomeExplained`, blank counts as absent,
the order is still `PARTIALLY_RECEIVED` after the refusal, and `AS_COMPUTED` with no note succeeds.
On the screen, `requires a sentence for the two outcomes that say something about the supplier`.
Control 5.

**4. The computed score is shown at closing and is never editable.**
`theComputedScoreIsShownAtClosingTime` (60%, 0 of 1 items, and the same figure the report gives),
`noNeededByDateIsNothingToScore`, `theScoreIsShownAndThereIsNoWayToMoveIt` (posted at the endpoint),
and on the screen `shows the computed score with the counts behind it` and `offers no way at all to
change that score`. Control 6 proves that last one is not vacuous. **There is no column, no request
field and no control anywhere in the application that writes a score.**

**5. The exclusions are visible on the scorecard.** `ordersExcused` on the row and on the total,
rendered as *"N orders they made right — not counted"* beside **both** percentages — asserted as three
occurrences in `counts the orders the vendor made right, beside BOTH percentages` — plus the caveat
paragraph, plus `says nothing at all when nothing was excused`. It follows `ordersSentLate`'s pattern
exactly: same `Badge tone="neutral"`, same place, same caveat mechanism.

**6. The arithmetic needed nothing new.** `scoreItems` and `itemFraction` are unchanged in substance;
the SQL was extracted into `scoreItemsWhere` so one order can be scored by the same query. T-124's
60% is what every test reads.

**7. Auto-cancel never touches a part-delivered order.** Verified against the statement and asserted
in `theSweepLeavesThesePartsAlone` as well as T-137's own test. See the section above.

**8. Nothing T-137 built was undone.** Its 13 tests plus the two `VendorPerformanceIT` ones pass in
the run above, unmodified.

**9. A part-delivered order cannot be cancelled, on the server as well as on the screen.**
`aPartDeliveredOrderCannotBeCancelled` posts it straight at the endpoint, with and without the tick,
and asserts `KMS-400150`, both sentences of it verbatim, that the order is still `PARTIALLY_RECEIVED`
afterwards, that `vendor_abandoned` is still false, and that the same order closes cleanly through
the door that is right. `cancellingWhatWasNeverDeliveredStillWorks` shows a draft and a sent order
are untouched. On the screen, `is not offered on a part-delivered order` (the panel and its tick both
gone), `puts the closing panel where the cancel panel was`, and `is still offered on a %s order` for
DRAFT and SENT. Controls 7 and 9.

**10. Closing is on the audit record.** `closingIsAudited` — `PO_CLOSED`, `PURCHASE_ORDER`, the
actor's id and label, `PARTIALLY_RECEIVED` in the before-state, and the outcome and sentence in the
after-state. Control 8.
