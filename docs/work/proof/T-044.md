## Sentinel or semantics — which was fixed

**Both, and they are not the same fix.** `isPlaced()` is now
`placeId != null && isCoordinate(latitude) && isCoordinate(longitude)`.

The **semantic** half is `placeId != null`. `isPlaced()` claims "a place somebody chose from the
list, so there is nothing left to look up", and the old predicate never consulted the one field that
could support that claim. Coordinates on their own are not evidence anybody chose anything — they
could be a geocode from months ago, whose thirty-day licence `locate()` exists to enforce — and a
predicate that cannot tell a pick from a stale geocode is wrong even on inputs that contain no zero.

The **sentinel** half is `isCoordinate()`, which refuses exactly `0` on either axis. This is not a
range check on India (a temple outside it is a thing this product may one day have); it is the
observation that `0.000000` is what an empty box serialises to. It is needed because the semantic
fix alone does not stop the defect from the wire: the old composer sent a *real* place id beside the
placeholder, so `placeId != null` was satisfied and `0,0` would still have been stored. A stale
browser bundle can still send that today.

The asymmetry is what makes the sentinel safe to be blunt about: a genuine pick refused here still
carries its place id, so `place()` asks Places for the true coordinates and the event ends up
correctly pinned — one API call. A placeholder accepted here is written to the row a driver's job
card is printed from.

`fresh()` uses the same predicate, so the rows *already* poisoned in production stop counting as
fresh and are looked up again on the next read rather than being kept for thirty days. See
**Not done** for what that does and does not cover.

### C — the escape hatch itself, and a correction to the brief

**C1: annotation removed *and* the two pin fields deleted from `mealFacts()`** — the shape the defect
actually had:

```
components/planner/MealComposer.tsx(871,17): error TS2345: Argument of type '{ recipeId: string; ... }'
  is not assignable to parameter of type 'CreateMealPlanInput'.
  Type '{ ... }' is missing the following properties from type 'CreateMealPlanInput': deliveryLatitude, deliveryLongitude
components/planner/MealComposer.tsx(880,17): error TS2345: ... (the createMealPlan call, same message)
tsc exit: 2
```

**This did not compile, and that is worth being exact about.** The brief predicted the omission would
still slip through without the annotation. It does not — but not because of anything in this file:
it is the *reservation in `api.ts`* doing the work. Spread exempts **excess** properties from
checking, not **missing required** ones, so making `deliveryLatitude`/`deliveryLongitude`
required-and-nullable is what closed the hole. Had they been left optional, both C1 and the original
defect would have compiled in silence.

**C2: the same omission with the annotation restored:**

```
components/planner/MealComposer.tsx(816,5): error TS2739: Type '{ planDate: string; ... }'
  is missing the following properties from type 'MealFacts': deliveryLatitude, deliveryLongitude
tsc exit: 2
```

So what the annotation buys is not *whether* the omission is caught but *where*: one error at line
816, the builder that can fix it, instead of two at 871 and 880, the call sites that cannot — and it
keeps holding if a future caller stops passing the result straight to a typed API function. That is
a real gain and it is the one being claimed here; the reservation is what makes the omission
impossible.

## Acceptance criteria

1. **Editing a placed delivery event and saving leaves its coordinates unchanged, asserted on the
   real database.** `MealPlanIT.editingAPlacedDeliveryLeavesItsPinAlone` reads
   `delivery_latitude, delivery_longitude` straight off `meal_plans` through the admin connection
   (`pinOf()`), never through an endpoint. It edits twice: once resending the true pin (the fixed
   composer), once resending `placeId` with `0,0` (the composer as it was, and any stale bundle still
   out there). Both leave `12.856230 / 77.548110` standing. Control A shows the second one writing
   `0.000000` without the fix. There is no map service in that context, so nothing that survives can
   be surviving on a fresh lookup.
2. **`mealFacts()` carries a return-type annotation** — `function mealFacts(): MealFacts`, where
   `MealFacts = Omit<CreateMealPlanInput, "recipeId" | "targetYield" | "ekadashiAcknowledged">`.
   Verified by C2: the omission is a compile error at the builder.
3. **`isPlaced()` no longer treats `0,0` as placed.** Verified twice over: the update case above, and
   a *create* carrying `placeId` + `0,0`, which now stores `null, null` — no map service, so no pin
   is the honest answer — rather than a point in the Atlantic.
4. **`tsc --noEmit` silent; targeted tests green.** 105 frontend tests across the four contract
   files, 18 backend tests in MealPlanIT, both through the lock.

## Not done / needs Rajeev

- **No hand smoke-test.** Commandment 5 wants one for a user-facing surface and I could not do it:
  this is not on UAT, and the defect is invisible on screen by nature — the address, contact and
  serving time all render correctly while the pin is wrong. When it does go up, the check is: open a
  saved delivery event that was **picked** from the map, change nothing but the head count, save,
  reopen, and confirm the leave-by line still reads the same drive it read before.
- **Rows already poisoned in production are not backfilled.** Any delivery event edited since
  2026-09-05 may be holding `0,0` today. `fresh()` now treats those as stale, so the next travel
  estimate re-geocodes from the address text and self-heals *where a geocoder can find the address* —
  which is precisely the case the picker exists because it often cannot. A migration that nulls
  `delivery_latitude/longitude/geocoded_at` wherever both are zero would be the honest fix and is
  cheap; it was outside this contract (no migration path was reserved), so it is not written. Worth
  a look at how many rows are affected before the next deploy.
- **The `place()` javadoc dated 2026-09-05 still describes the previous incarnation of this bug.** It
  is accurate and I left it, but it is now the second such comment in that method; someone reading it
  cold gets two archaeology notes before the code. Not mine to reorganise mid-wave.
