# T-108 — "1 pieces"

## The shared label, and why one label could never be right

`frontend/lib/format.ts` holds **one** label per unit:

```ts
export const UNIT_LABEL: Record<string, string> = { KG: "Kg", GM: "gm", L: "L", ML: "ml", PIECES: "pieces" };
```

The private renderer behind `quantity()` and `cooksQuantity()` read that map directly:

```ts
function say(value: number, unit: string, maxDecimals: number): string {
  return `${value.toLocaleString("en-IN", { … })} ${UNIT_LABEL[unit] ?? unit}`;
}
```

It has the number in its hand and throws it away before choosing the word. **That is the whole
defect** — a label that has never been shown the number it is going to sit beside cannot agree with
it. One plastic stool therefore read "1 pieces" on every screen at once.

## The fix

`UNIT_SINGULAR` (one entry: `PIECES: "piece"`) and `unitLabelFor(value, unit)`, which `say()` now
calls. The count is a **required** argument, not an optional one — an optional count is a count the
next caller forgets, and the forgotten case renders the exact defect this exists to remove.

Only `PIECES` pluralises, and the tests state why: `Kg`, `gm`, `L` and `ml` are abbreviations of a
mass or a volume, and "1 Kgs" is not English. "1 Kg" is right, "1 piece" is right, and no
abbreviation the app does not already use was invented — `UNIT_LABEL` is untouched.

## The rest of `unitLabel()` is correct and stays plural

The other **22** `unitLabel()` calls across 15 files are naming a unit with no number anywhere near
it, and there "pieces" is the right word: dropdown options (`RecipeForm`, `IngredientForm`,
`IngredientRequestForm`, `PurchaseOrderEditor`, `supplies`, `ingredients`, `inventory/[id]`,
`donations/new`, `orders/new/lines`), a column that names an ingredient's stored unit, and the

## And a guard, because a fix that leaves the next instance easy to write is not a fix

`design-system.test.ts` gains a rule beside the three it already has about units. It flags any source
file where a closing interpolation is immediately followed by a bare `unitLabel(` — a number and a
label rendered as one phrase by hand:

```

```

It matched `MealServices.tsx` before the change and matches nothing now. `unitLabel()` standing on
its own is not flagged and must not be.

## ⚠ Second finding, reported and deliberately not built

`app/orders/[id]/page.tsx` builds three strings of the form *"per pieces"* — the price-paid box's
accessible name, its hint, and the expected-price hint (`per ${unitLabel(l.unit)}`). "Price paid per

singular regardless of any number, so `unitLabelFor` is the wrong tool and getting it right needs a
third idea ("the unit named after *per*"). Three strings, all of them hints or accessible names, none
of them what Rajeev saw. **Not worth a new concept in the shared formatter today** — flagging it
instead.

# T-077 — the language picker

## Which picker, and the honest answer about the reproduction

`LanguageSection`, which was at `frontend/app/settings/page.tsx:1392`:

```ts
const [language, setLanguage] = useState((initial ?? "en-IN").split("-")[0]);
```

`initial` is the temple's stored locale, passed down from the settings page. A `useState` argument is
read once, on the first render, and never again.

**I could not reproduce it, and that is a finding, not a failure to look.** The section is rendered
below the page-wide `if (!settings) return <Loading />` gate, and all six settings requests resolve
in a single `Promise.all` whose results are set in one React batch — so by the time the section
mounts, `locale` is already there, and the prop cannot change underneath it afterwards. There is no
in-app temple switch on that screen either (`TemplePicker` is the registration control, not a
switcher). **No user has hit this and none can today.** `docs/work/DISPATCH.md` says the same thing
about its own row: *"safe today only because of the page-wide `if (!settings)` gate — which is to say
it is safe by an accident of a neighbour rather than by its own construction."*

What it would cost if the gate ever moved: the picker sits on **English** permanently while the
temple's setting says Kannada, and pressing Save writes English over it — with nothing on the screen
looking wrong.

## Fixed anyway, and fixed by deriving

```ts
const [picked, setPicked] = useState<string | null>(null);
const language = picked ?? (initial ?? "en-IN").split("-")[0];
```

Not a `useEffect` copying the prop into state — that is the same bug with more steps: it renders once
with the wrong value before correcting itself, and it overwrites a choice already made the next time
the prop moves. Deriving also gives the behaviour you want for free: once somebody has picked
Kannada, nothing arriving from the server puts English back under their cursor. **This is the shape
the application's two other language pickers already use** — the job card's on the planner
(`MealServices.tsx:361`) and the work order's on an ingredient request
(`ingredient-requests/[id]/page.tsx:599`) both write `language ?? somethingFromTheServer ?? English`.

## Why it moved to its own file, since that is the largest part of the diff

The one thing worth asserting about this component is what it reads **when the prop changes after
mounting**, and a fixture that never changes the prop passes whether the bug is there or not. Inside
a 1,400-line page the section could only be reached by loading the whole screen, where the prop
cannot be made to change. So it is now `frontend/components/LanguageSection.tsx`, imported by the
settings page, and the test mounts it with `initial={null}`, then re-renders with `initial="kn-IN"`
and asserts the picker reads Kannada. **Verbatim move plus the three-line fix — no behaviour, copy or
markup changed.** Say the word if you would rather it had stayed inline and I will put it back.

## ⚠ The neighbour I did not touch

`AppearanceSection`, forty lines above it in the same file, has the identical shape —
`const [chosen, setChosen] = useState(saved)` seeded from `initial` — and is protected by the same
gate and therefore equally latent. It is not my item and another builder may be in that file, so it
is named here and left alone.
