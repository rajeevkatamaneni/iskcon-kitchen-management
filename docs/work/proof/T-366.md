## What the repair does, and why it is shaped this way

The obvious route is closed, and I confirmed that against a running backend rather than
taking it from the brief. `POST /api/v1/inventory/items/{id}/adjustments` with
`reason: COUNT_CORRECTION` is the recount door, but the request is a signed change and
`InventoryItemService.adjustStock` asks the whole-counts rule of that change. The real refusal:

```
POST /api/v1/inventory/items/57eb3f76-7402-4b03-868d-02a4af36153f/adjustments
  {"batchId": "6c0c0000-0000-4000-8000-000000000001", "quantity": -0.98,
   "unit": "PIECES", "reason": "COUNT_CORRECTION", "note": "Recount says 400."}
  -> HTTP 400
{
  "code": "KMS-400191",
  "message": "Some of these are counted one by one, so a part of one can't be entered.",
  "action": "Round the amounts marked below to a whole number and try again.",
  "fieldErrors": [
    {
      "field": "Coconut",
      "message": "Coconut is counted in whole pieces. Enter -1 or 0."
    }
  ]
}
onHand still: 400.98
```

Neither -1 nor 0 lands on 400. So the script goes through
`POST /api/v1/inventory/movements/{id}/compensate`, which appends a movement's exact reverse past
validation on purpose — `StockMovementService.compensate` says so in its own comment, and
`IngredientUnits`' class javadoc names it as how a leftover fraction comes off. Per lot: reverse the
fractional rows **somebody typed**, then post one whole `COUNT_CORRECTION` for whatever that
over-removed.

**Three judgements I made, all argued in the file's docstring:**

1. **Rounded down.** 400.98 becomes 400, never 401. Overstating stock is the expensive direction —
   the allocator commits against on hand, so an invented coconut is promised to a meal and the
   kitchen finds out while cooking. Understating costs one coconut and shows up on the shopping
   list. This does not contradict `01b` rounding reorder levels *up*: both round to the side where
   being wrong is cheap, and that side is a different direction for a warning about the future than
   for a claim about the shelf now.

2. **Typed figures may be reversed; figures the application worked out may not.** The split is the
   backend's own `StockMovementService.ENTERED_BY_A_PERSON`, not one I invented: `PO_RECEIPT`,
   `DONATION_IN_KIND`, `RETURN_TO_VENDOR`, `ADJUSTMENT`. A fractional `CONSUMPTION` is a recipe
   scaled to 12 L genuinely needing 2.4 coconuts; reversing it would say the cooking never happened
   and would put back food that was eaten. Where a lot's fraction is the application's own
   arithmetic the script **writes nothing, leaves the item exactly as found, and reports it**. This
   is the answer to the brief's "check this actually works before building on it" — it does not
   always work, and the script says which case it is in rather than mangling the ledger.

3. **The residual is settled per lot, not per item.** One residual for the whole item would move
   stock between lots that never held it. The cost, stated plainly in the docstring: an item spread
   over several fractional lots can land up to one unit below the floor of its total. Always
   downwards, never up.

**Keyed on the COUNT family, not on `== PIECES`.** The API exposes no unit metadata at all — there
is nothing to ask it — so the script reads the backend's own `Unit.java`, which is the definition of
the rule and two directories away in the same repo. Proved by adding a second COUNT unit to a
throwaway copy:

```
read from backend/.../Unit.java as it stands: ['PIECES']
with --counted-units PIECES,CRATES : ['CRATES', 'PIECES']

now add a second COUNT unit to a THROWAWAY copy of Unit.java and re-read it:
   added: ['\tCRATES("crates", "crate", Family.COUNT, 1);']
   the script now counts: ['CRATES', 'PIECES']
```

I cannot touch staging, so the condition was reproduced and repaired locally, end to end, against a
real backend and a real PostgreSQL.

**Setup, clearly separated from the repair.** Own database (`kms_t366c`, a `pg_dump` copy of
`kms_verify` — `kms_seed` and the `:8080`/`:8091`/`:8093` ports were left alone) and own port
(`8097`). A fixture SQL file wrote the pre-rule fractional rows, because the application can no
longer produce them; it lives in the scratchpad, not the repo. **No SQL appears anywhere in the
repair path** — every write the script makes is an HTTP POST, shown below with its status code.

*adds* — which R-ING-3 requires a value for. The script reads the ingredient's own stock-value
suggestion and **refuses rather than inventing a price**, as above. Setting one is an operator act,
