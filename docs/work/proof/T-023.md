## Acceptance criteria

**1 — A supply can be created, appears on the catalogue marked as a supply, and goes into inventory
and onto a purchase order exactly as food does.**

- Created: `SupplyIngredientIT.createsASupplyAndListsItWithFood` posts `supply:true` to the ordinary
  `POST /api/v1/ingredients`, then asserts `GET /api/v1/ingredients` returns **both** rows with
  `supply` true and false respectively, and reads `is_supply` back out of the database directly.
- Marked on the screen: a new **Type** column on `/ingredients` badges `Supply` and leaves food as
  plain "Food" — `supplies.test.tsx` › "marks a supply, and leaves food unmarked", which finds the
  cell by its column header rather than by index.
- Into inventory: asserted on both sides of the boundary rather than one.
  `SupplyIngredientIT.aSupplyGoesIntoInventory` posts a supply to `POST /api/v1/inventory/items` and
  finds it in `GET /api/v1/inventory/items`; `supplies.test.tsx` › "puts a supply into inventory
  through the same call food goes through" drives the real `/inventory/new` screen and asserts the
  API call carries the supply's id. Neither the endpoint nor the screen has a special case, which is
  the assertion.
- Onto a purchase order: **verified by reading, not by a test I own** — see "Not done" below.

**2 — The recipe picker does not offer it, and the API refuses it with `KMS-400127` if posted anyway;
a test asserts the second.**

- Picker: `supplies.test.tsx` › "does not offer a supply as a recipe ingredient". Queried by
  `getByRole("option", { name: … })` rather than `getByText`, deliberately — the inventory picker
  splits an option label across three text nodes, and a `queryByText` negative there would have
  passed for the wrong reason. (It did, first run; the run that caught it is in the log.)
- Server: `SupplyIngredientIT.aRecipeRefusesASupply` asserts `409` / `KMS-400127` on a create whose
  lines are *rice and leaf plates together* — so what is refused is demonstrably the supply and not
  the request shape, since the same call without the plates comes back `201` in the same test. It
  also asserts nothing was written. `editingARecipeOntoASupplyIsRefused` does the same for `PUT`,
  and checks the recipe still holds its original rice line afterwards.
- The refusal lives in `RecipeService.resolveIngredients`, which is on the create *and* the update
  path, so both are covered by one guard.

**3 — Existing ingredients are all food after the migration.**
`SupplyIngredientIT.everyExistingIngredientIsFood` inserts through an `INSERT` that never names the
column — which is how every pre-V99 row, and every row recipe import writes, was written — in **two
tenants**, one of which nobody ever signs in as, and asserts both read false plus
`SELECT count(*) FROM ingredients WHERE is_supply` is zero. Also asserted through the API, so the
false crosses the JSON boundary and is not merely a column reading.

**4 — Builds green.** `./gradlew test` on the three affected classes: 32/32, `BUILD SUCCESSFUL`.
`npx tsc --noEmit`: exit 0, no output. The seven vitest files: 69/69.

## Where the brief was wrong, and one claim of its own it told me to test

**The three "verified" facts held.** No `Ingredient` entity or repository (the module is raw
`JdbcTemplate`); `new IngredientView(` really does appear at exactly one site, `VIEW_MAPPER`; no
ingredient flag was used as a query filter; the frontend never calls `/ingredients/search`; and
`sattvicProhibited` is indeed gone, so the plan's note about it was stale as the brief said.

**The residual-`tsc` claim is now wrong, in our favour.** The brief said `tsc --noEmit` would stay red
in `frontend/__tests__/order-detail.test.tsx` and `frontend/app/orders/[id]/page.tsx` and that I
should say so. It is not: **`tsc` is exit 0 with no errors anywhere.** T-024 has already repaired both
files — they show as modified in `git status` and type-check clean. I did not touch either. Worth
knowing that a clean type-check is now the expected state for the rest of this wave, not a surprise.

**"An integration test asserts the backfill ran per tenant under RLS" is vacuous on this column shape,
and I did not manufacture one.** `ALTER TABLE … ADD COLUMN … NOT NULL DEFAULT false` is DDL run as
the table owner; PostgreSQL fills the default into every existing row itself, catalogue-only, without
a row-level policy ever being consulted. There is no backfill statement, so there is nothing per
tenant to test. I said so out loud in three places rather than leaving it implicit — in V99's header,
in `SupplyIngredientIT`'s class javadoc, and in the test that replaces it — and asserted instead the
fact the criterion was actually reaching for: rows that predate the column read as food, *including a
row in a tenant nobody adopted*, which is precisely the row that DML-under-RLS would have missed.

I considered the alternative shape (nullable column → per-tenant `UPDATE` → `SET NOT NULL`) purely so
there would be a backfill to test, and rejected it: three statements and a window where the column
means nothing, to reach a state one DDL statement reaches atomically. That would be writing a defect
in order to have something to prove.

**I did not take the `listIngredients` filter-argument the brief offered to let me refuse.** I agree
with the brief's reasoning and confirmed it from the far side myself: `grep -rn listIngredients app
components lib __tests__` shows five bare function references passed to `useAuthedQuery`
(`vendors/[id]`, `donations/new`, `inventory/new`, `ingredients`, `RecipeForm`) and two wrapped
closures (`orders/[id]`, `IngredientRequestForm`) against a `(token?: string)` signature. A leading
parameter binds the token wrongly at all seven, five of which are outside this contract. The recipe
picker filters client-side on the flag it now receives, and the server refusal is the actual guard.

## Decisions worth flagging

**The D-18 guard in `ingredient-new.test.tsx` was amended, not weakened.** It read
`expect(screen.getAllByRole("checkbox")).toHaveLength(1)` — every checkbox on the form. A supply box
makes that two. Changing the number to 2 would have destroyed the guard, because the count would then
say nothing about *which* flags were on the form. It now counts the checkboxes whose accessible name
matches `/prohibited/i`, still asserts the Ekadashi box is that one, and adds a line asserting the
supply box **is** present — so the filter is doing work rather than matching everything. The
`/prohibited/i` payload-key assertion below it is untouched, exactly as the brief predicted, because
the field is named `supply`.

**`ingredients.test.tsx`'s "offers one dietary flag and no second one" needed its header list
extended** to include `Type`. The load-bearing half of that test — exactly one allowed/prohibited
toggle in the row — is unchanged and still passes; a comment now says why `Type` is on the list and
is not a dietary flag.

**The Type column is read-only on the row; the flag is edited through Edit.** Unlike Ekadashi beside
it, `supply` has no endpoint of its own — it goes up on the update body with the name and the
category — so a one-click toggle would have had to send the whole row and would have been a different
act from the one it looked like. The edit row grew a `Supply` checkbox in the Type cell, which also
keeps the editing row's cell count equal to the header count (the existing test that counts them
still passes).

**Only supplies are badged.** Food is the overwhelming majority of any catalogue and badging every
row of it would say nothing; the eye wants the exception.

**One line of copy changed on `/ingredients` that was not asked for.** The post-add banner said "It
can go into a recipe now, and be tracked in your inventory." That is now false for half the
catalogue — a leaf plate is the one thing a recipe will not take. It reads "It can be ordered and
stocked now, and — if it is food — put into a recipe." The banner only knows the name, which travels
in the URL from `/ingredients/new` (a file outside my contract), so it says what is true of both
rather than branching.

**A supply flag is not an observance flag, and the form says so by ordering.** The supply box sits
*above* the Ekadashi box: what a thing IS comes before what a rule says about it, and the answer
changes whether the box below is even meaningful. The supply box is not behind `isAdmin`.

**`IngredientSummary` gained the flag too**, though nothing reads it yet — it is the shape a *recipe*
typeahead would consume, and a picker that cannot see the flag cannot honour it. Asserted by
`SupplyIngredientIT.typeaheadCarriesTheFlag` so it does not rot.

**One known edge case, handled by the server rather than by more UI.** If an ingredient already on a
saved recipe is later flagged a supply, the recipe's edit screen renders that line's select with
nothing chosen — the option is filtered away, but the id stays in component state, so nothing is
silently dropped. Pressing Save asks the server, which answers `KMS-400127`: *"That's a supply, not
something you can cook with. Choose a food ingredient, or add this one to the catalogue as food."*
That is the correct message for exactly that situation, so I did not invent a extra badge or a
"no longer a food ingredient" option for it. Flagged here because it is a judgement call, not a
certainty — if Rajeev would rather the stale line be shown explicitly, that is a small follow-up.
