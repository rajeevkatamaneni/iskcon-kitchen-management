## Acceptance criteria

1. **Admin saves, `/whoami` returns it as a nested object, in the order saved** —
   `theArrangementReachesEverybodyAsAnObject`, read as the Kitchen Staff cook who may not open
   Settings at all. It asserts `$.menuLayout.version`, `$.menuLayout.groups[0].id`,
   `$.menuLayout.groups[1].title`, and each of `groups[1].items[0..2]` individually, which a set or
   a re-ordered list could not satisfy. A path like `$.menuLayout.groups[0].id` cannot be satisfied
   by a JSON string, which is the point — control B below proves it.
2. **Never saved reads null** — `nullUntilArranged`, plus `settingsRowWithoutAnArrangement` for the
   second shape of "never saved": a settings row written for some *other* preference, with a null
   in this column. That is the exact state that took the theme down on 2026-08-30, so `menuLayout()`
   reads off the list and never `stream().findFirst()`.
3. **Saving twice replaces** — `savingTwiceReplaces`: one row in `tenant_settings`, one group left,
   and the first arrangement's `dashboard` and `kitchen` are gone from the stored text.
4. **Reset** — `resetIsAlwaysAnAnswer` (204, column back to NULL, 204 again on a second call) and
   `resetWithNoSettingsRowAtAll` (204 for a temple with no settings row, and no row written to
   record it). A plain `UPDATE` matching zero rows, not an upsert.
5. **Tenant isolation** — `perTemple`. Temple A saves, temple B reads null, temple B saves its own,
   temple A is untouched. Read through the application's `kms_app` role, which
   `AbstractIntegrationTest` creates `NOSUPERUSER NOBYPASSRLS`; the superuser template is used only
   to seed fixtures and to read the raw column.
6. **403 for a role without the permission** — `onlyTheTempleAdminMayArrange`, Kitchen Manager and
   Kitchen Staff, on both `PUT` and `DELETE`, and nothing was written.
7. **Same item in two groups → 409 `KMS-400190`** — `oneDestinationCannotBeInTwoGroups` asserts the
   code and the message, not only the status, and that nothing was stored.
   `oneDestinationCannotBeInOneGroupTwice` covers the same id twice inside one group.
8. **Malformed → 400 `KMS-400189`** — `anUnreadableArrangementIsRefused`, asserting the code on each
   of: five bad group ids (`Kitchen`, `the kitchen`, `-kitchen`, `kitchen_area`, 65 characters), two
   bad item ids (`Meals`, empty), two groups sharing an id, and `"version": 2`.
9. **Blank heading, 41-character heading, 21 groups → field errors** —
   `theBoundsAPersonCanSeeComeBackAgainstTheBox` asserts `KMS-400001` with a non-empty `fieldErrors`
   array, and also covers zero groups. `theBoundsAreInclusive` proves the bounds are not off by one:
   20 groups with 40-character headings save and read back.
10. **`PermissionBeforeValidationIT`** — both endpoints added to the hand-written list, both
    parameterised checks passing on them (output above), and the class's own
    `everyProcurementWriteEndpointIsListed` still green.

## Who else reads `tenant_settings`

Grepped for every reader before adding the column, because a `SELECT` goes on compiling when the
meaning of a row changes underneath it.

- Every named reader asks for its own columns — `TenantWhatsAppSettingsService`,
  `TenantPaymentSettingsService`, `PaymentGatewayResolver`, `TenantEmailIdentityService`,
  `WishlistService`, `WhatsAppTemplateComparison` and this service. There is **no `SELECT *` on
  `tenant_settings`** anywhere in `backend/src/main/java`, so nothing widens.
- **One reader does take every column**, and it is right that it does:
  `TenantExportService.writeSheet` runs `SELECT * FROM <table> WHERE tenant_id = ?` over every table
  carrying a `tenant_id`. So the temple's data export now carries its menu arrangement, which is
  correct — it is the temple's own data — and `TenantExportWorkbook` writes an unrecognised value
  through `String.valueOf`, the same path `whatsapp_refused_templates` (V128, also JSONB) has taken
  since it was added. `TenantExportIT` discovers those tables dynamically and passed (6/6).
- Nothing sums or counts this table, so there is no aggregate to break. The upserts in the other
  settings services name their own columns in both the `INSERT` list and the `DO UPDATE SET`, so
  none of them can null this one out by saving something else; `settingsRowWithoutAnArrangement`
  exercises that through the broadcast-limit endpoint.
- `RowLevelSecurityIT` (30/30) asks `pg_class` which tables carry `tenant_id` and asserts each has
  RLS forced. `tenant_settings` has carried `enable_tenant_rls()` since V36 and a column is not a
  new table, so there was nothing to add and the guard confirms it.

## Decided differently from the brief

**`version` is refused with `KMS-400189`, not as a bean-validation field error.** The brief listed
"`version` must be exactly `1`" under the field-error rules and then asked, in acceptance criterion
8, for `version: 2` to answer `400 KMS-400189`. Those two cannot both hold. I took the code, for
three reasons: a field error points at a box the person can fix, and no screen anywhere has a
version box; `KMS-400189`'s next step — arrange it again and save — is the thing that actually works,
while "check the highlighted fields" is advice nobody can follow; and the comment the work manager
wrote above these two codes in `ErrorCode.java` says a code is minted "where the refusal is about
the arrangement as a whole and there is no one field to point at", which a version is. So
`UpdateMenuLayoutRequest.version` carries no constraint and `TenantSettingsService` refuses anything
that is not `1`. Both directions are asserted in `anUnreadableArrangementIsRefused`.

Smaller calls, all inside the brief:

- **The service is given the arrangement as JSON and reads it again before writing**, rather than
  taking the bound record. What is checked is then exactly what is stored, and what is stored is
  rebuilt from the check — version, then each group's id, trimmed title and items, and nothing else.
  A document that reached the write by any route lands in one canonical shape.
- **Two `@AssertTrue` accessors carry the heading rules** (`isHeadingWrittenOrAbsent`,
  `isHeadingShortEnough`) rather than `@Size`, because the brief asks for "non-blank and at most 40
  characters *after trimming*" and `@Size` can express neither. They follow the naming of the two
  cross-field rules already in the tree (`ClosePoRequest.isNamedOutcomeExplained`,
  `UpdatePreferenceRequest.isExactlyOneThing`).
- **`PermissionBeforeValidationIT` gained a three-line `codeOf` helper.** Every probe on that list
  used to answer with an error body, so the code was read straight off it with
  `json.readTree(response.getBody())`. The menu-layout reset is the first probe whose permitted
  answer is a success: 204, no body, and `readTree(null)` throws. `codeOf` returns `""` for an empty
  body. The alternative was to leave the reset off the list, which would leave the endpoint the
  brief specifically wanted guarded unguarded.
- **`SettingsController` was not added to `WHOLE_CONTROLLERS`** in that class. That set is the
  procurement build's controllers and drives `everyProcurementWriteEndpointIsListed`; adding
  `SettingsController` would require listing every settings endpoint, most of which predate T-301
  and are outside this task. The two new endpoints are in `everyProbe()` and are exercised by both
  parameterised checks, which is what criterion 10 asked for.
- **A stored arrangement that cannot be parsed logs a warning and reads as null** rather than
  failing `/whoami`. Only this application writes the column and it writes a document it has just
  rebuilt, so this needs somebody in the database by hand — but a menu preference must not be able
  to stop a temple signing in.
