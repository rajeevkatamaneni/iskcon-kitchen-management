Each asserts no item, no movement, market rate still ₹50 MANUAL, no rate history and no audit row of any kind. Each refusal happens after the item row and its audit row were inserted, so these tests show a rollback. The control shows 6 of 7 fail when the count is ignored.
- Happy path: one item, one ADJUSTMENT / COUNT_CORRECTION movement with the exact note and its own batch, market rate 62 STOCK_TAKE with 1 history row, and INVENTORY_ITEM_ADDED + STOCK_ADJUSTED audit rows.
- Reuses the adjust path: `create()` calls `adjust()`, and there is no copied rule.
- The page sends one request: `inventory-new` asserts `createInventoryItem` gets `openingCount: {quantity: 40, unit: "KG", pricePerUnit: 62}` and `adjustStock` is never called. A refusal (KMS-400161) now arrives on that one call and the page stays put. This passes, and fails under the control.

One caution: `LOCAL-STACK.md` says the API recompiles and restarts by itself about 6 seconds after a Java file is saved, so my edits may already have restarted it. I didn't check.
- **A consequence to know about.** Only the Temple Admin holds the permission to approve a large stock adjustment, and a first count is always a large one. So a Kitchen Manager or Kitchen Staff who adds an item with a count is now refused outright (KMS-400025), and nothing is saved. Before, they got an item with no stock, which is the half-save this task fixes. They can still add the item with no count and let an admin count it. The rule itself is unchanged. The server has always refused their count; now it refuses the whole add.
- **Layout choice (per the Q-18 answer: follow the rule's logic, pick the lesser evil):** one column below 768 wide, two from 768 up. At 640–767 the form is one full-width column. That hides nothing and leaves no half-empty row. Splitting at 640 cut off a real ingredient name and put the rows out of line.
