**Why 9 and not 15, which is the part worth reading.** Six of these tests assert an *absence* or a
*fallback*, and with the feature gone both are true for the wrong reason, so they pass vacuously —
that is correct rather than a hole:

- *cannot grant*, *cannot take away*, *leaves the operator five destinations*: these say an
  arrangement changes nobody's access. With the merge patched out no arrangement is applied at all,
  so of course nobody's access changed. These three are the acceptance criteria (8) and (9), and a
  negative control cannot demonstrate them — what demonstrates them is that they fail if the role
  filter is moved in front of the merge, which is why the filter's position is written into
  `navForRole`'s doc comment. Each of them also asserts the destinations that *should* be there, so
  they cannot pass on an empty menu.
- the three *fallback* tests say an odd arrangement yields the standard menu. Patching the merge out
  makes every arrangement yield the standard menu, so they pass. That is criterion (12), and it is
  the one criterion whose failure mode is "the feature does too much", not "too little".

## Acceptance criteria, one by one

1. **Permanent `id` on every item and group.** 42 item ids and 7 group ids, written as literals in
   `nav.ts`; the doc comment on `NavItem.id` says the href-derivation was how the first set was
   chosen and is not a rule for deriving another. Verified by `nav.test.ts > the menu's permanent ids`
   (the full 42-id list frozen in order, the 7 group ids, all distinct, carried through `navForRole`).
2. **`/notices` disambiguated** — `notices-operator` / `notices`; and the whole file checked for other
   duplicate hrefs (there are none). Verified by the id test and by control B.
3. **`applyMenuLayout` merges at render, never migrates.** Verified by the 15 tests in
   `menu-layout.test.ts`, mapped to the brief's list below.
4. **`navForRole` arranges, then filters, then drops empties**, arrangement optional and defaulting to
   none. Verified: every pre-existing `nav.test.ts` assertion still passes untouched (29 tests), and
   the access tests in `menu-layout.test.ts`.
5. **Sidebar passes the session's arrangement, makes no request, and the drawer gets it.** Verified by
   the new `phone-menu.test.tsx` test, which opens the drawer and reads its links — and by control C.
   The sidebar still has no `api.` call in it.

The twelve cases the brief asked `menu-layout.test.ts` to cover, and the test that covers each:

1. reorder within a group → *puts the items of a group in the order the temple put them*
2. move between groups → *moves a destination from one group to another…*
3. reorder groups → *puts whole groups in the temple's order*
4. renamed heading, and an unplaced item still lands in it → *honours a renamed heading…*
5. standard group deleted → bottom, under "New", not stored → *sends an unplaced destination to the bottom under New…*
6. unknown id passed over → *passes over an id it has never heard of…*
7. emptied group survives the merge, dropped by `navForRole` → *keeps a group the temple emptied…*
8. an arrangement cannot grant access → *cannot grant a destination to a role that may not reach it*
9. an arrangement cannot remove access → *cannot take a destination away from a role that may reach it*
10. the meal-planner rule over an arrangement → *does not hand the planner to somebody whose kitchen does not plan here*
11. the operator's five destinations → *leaves the platform operator exactly the five…*
12. null, empty and garbage all fall back → the three tests under *an odd arrangement falls back…*

Plus one the brief did not ask for: *offers a destination once even if the arrangement lists it

## Decided differently from the brief, and why

**One rule added: an arrangement that recognises nothing is treated as no arrangement.** The brief
asks that "a garbage-but-well-typed arrangement" fall back to the standard menu. Followed literally,
the other rules would not do that: a row naming groups we do not have and ids we do not have would
produce those empty groups plus all 42 destinations in one heap headed "New" — not empty, but not a
menu either. So `applyMenuLayout` first asks whether the arrangement names *any* group id or *any*
item id this menu has; if it names none, it is not an arrangement of this menu and is ignored. An
arrangement that names even one thing we recognise is honoured in full, so nothing legitimate is
caught by it — including the case of an arrangement whose groups are all empty, which still reorders
and renames the headings as the temple asked.

**Two React keys changed in `Sidebar.tsx`**, beyond the one-line change the brief described. The group
key was `group.title ?? "main"`. Headings are now something an admin types, so two groups can share a
title, and two can be unheaded — either would collide. It is now `group.id`. The item key was
`item.href`, and `/notices` is two items at one address, so that is now `item.id` too. Both are inside
the contract and both are the same fix as the rest of the task: key on the thing that is unique and
permanent.

**`standardMenu()` returns copies.** The Settings screen's whole job is to splice this list about, and
`GROUPS` is module state shared with every menu on the page. A test asserts a caller cannot move
everybody's menu by mutating what it was handed.
