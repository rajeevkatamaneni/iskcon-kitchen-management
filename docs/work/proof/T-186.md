# T-186 — a counter gift's phone is saved in +91 form when it can only be an Indian mobile; the counter page carries the saved form to the confirmation

**State: proven.** Every acceptance criterion is met, including "Saved as +91 98765 43210" on screen.

**Contract widened by the dispatcher on 2026-09-13**, after my first report: `frontend/app/donations/page.tsx` was granted, only for the banner that confirms a recorded gift. It checked ownership first: no live builder held that file. Nothing else on that page was changed.

## The rule

1. Trim.
2. Remove T-157's separators (`[\s\p{Z}\p{Pd}\p{Cf}]`).
3. If what is left is `(+91 | 91 | 0)?` followed by ten digits starting 6–9, save `+91` and those ten digits.
4. Anything else is saved as typed, trimmed. Blank is null.

**The Bengaluru landline, settled by the dispatcher.** `080 2345 6789` is "0 plus ten digits starting 8", so the rule saves it as `+918023456789`. That is the line's correct international form, not a guess: every Indian number is written internationally by dropping the trunk 0 and adding +91. It can never match a verified volunteer on My donations, because Firebase verifies mobiles only. The brief listed it as "kept as typed"; the dispatcher confirmed that example was its mistake and the rule stays as decided. The kept-as-typed landline example is `022 2345 6789` (Mumbai).

The one real wrong reading the rule allows: a foreign ten-digit number typed without its country code that starts 6–9, e.g. American `617 555 0100` becomes `+916175550100`. It is in the class comment.

`DonationLedgerService.donorHistory` groups by `donor_phone IS NOT DISTINCT FROM ?` (and email). A new gift saved as `+919876543210` and the same donor's older gift typed `98765 43210` are different strings, so **the donor's history splits in two at the day T-186 ships.** Asking for the history of the old gift shows only old gifts; asking for the new one shows only new ones.

`DonationLedgerIT` › "T-186: a new counter gift saved as +919876543210 does not group with the donor's older gift typed 98765 43210":
- two old gifts typed `98765 43210` group with each other, not with the new ones;
- a new gift from `98765 43210` and a new gift from `09876543210` now group with each other. Before T-186 those two would not have grouped either.

I did not change the ledger's matching. A backfill would rejoin the halves; so would the ledger comparing the normalised form.

## Backfill sizing query (read-only), for Rajeev

Per temple:
- **(a) `would_change`:** counter gifts (`provider IS NULL`, no account) whose stored phone the rule would rewrite.
- **(b) `would_newly_match`:** how many of those are listable (completed, not struck, not anonymous), do not match today, and would match the phone on an active Volunteer's `users` row at that temple afterwards.

**Two limits on (b), stated plainly:**
- The database has no verified phones. My donations matches the phone in the Firebase token, and T-179 proved the `users` row's phone is not proof. So (b) uses `users.phone` as a stand-in. It can overcount (an admin typed a phone the person never verified) and undercount (a volunteer signed in by phone whose row carries a different number). The exact figure needs each volunteer's Firebase `phone_number`.
- **The real numbers need staging data. This query has not been run anywhere but the test database.** It needs a role that can read every temple, because RLS limits the app role to one.

The separator list is spelled out code point by code point because PostgreSQL has no `\p{…}` and its `\s` depends on locale.

```sql
WITH counter AS (
    SELECT d.tenant_id, d.donor_phone, d.status, d.voided_at, d.is_anonymous,
           regexp_replace(d.donor_phone, '[\u0009-\u000D\u0020\u002D\u00A0\u00AD\u058A\u05BE\u0600-\u0605\u061C\u06DD\u070F\u0890-\u0891\u08E2\u1400\u1680\u1806\u180E\u2000-\u2015\u2028-\u202F\u205F-\u2064\u2066-\u206F\u2E17\u2E1A\u2E3A-\u2E3B\u2E40\u2E5D\u3000\u301C\u3030\u30A0\uFE31-\uFE32\uFE58\uFE63\uFEFF\uFF0D\uFFF9-\uFFFB\U00010EAD\U000110BD\U000110CD\U00013430-\U0001343F\U0001BCA0-\U0001BCA3\U0001D173-\U0001D17A\U000E0001\U000E0020-\U000E007F]', '', 'g') AS bare
    FROM donations d
    WHERE d.provider IS NULL
      AND d.donor_account_user_id IS NULL
      AND d.donor_phone IS NOT NULL
),
rewritten AS (
    SELECT c.*, '+91' || right(c.bare, 10) AS saved
    FROM counter c
    WHERE c.bare ~ '^(\+91|91|0)?[6-9][0-9]{9}$'
      AND '+91' || right(c.bare, 10) <> c.donor_phone
)
SELECT t.id AS tenant_id, t.name AS temple,
       count(r.donor_phone) AS would_change,
       count(r.donor_phone) FILTER (
           WHERE r.status = 'COMPLETED' AND r.voided_at IS NULL AND r.is_anonymous = false
             AND r.bare <> r.saved
             AND EXISTS (SELECT 1 FROM users u
                         WHERE u.tenant_id = r.tenant_id AND u.role = 'VOLUNTEER'
                           AND u.status = 'ACTIVE' AND u.phone = r.saved)
       ) AS would_newly_match
FROM tenants t
LEFT JOIN rewritten r ON r.tenant_id = t.id
GROUP BY t.id, t.name
ORDER BY t.name
```

**Proof against fixtures** (`DonationIntakeIT`):
- "the backfill count query's separators are exactly T-157's, code point for code point": every code point from 1 to U+10FFFF (surrogates skipped) is run through the SQL class in PostgreSQL. The result equals Java's `[\s\p{Z}\p{Pd}\p{Cf}]` set, 220 code points.
- "the backfill count query counts, per temple, the rows the rule would change and those that would newly match". Temple A has volunteer Gopal `+919876543210` and a Temple Admin `+919811122233`.
  - `98765 43210` changes and newly matches.
  - `98765`–`43210` (en dash) changes and newly matches.
  - `+91 98765 43210` changes but already matches today.
  - `+919876543210`: no change.
  - `022 2345 6789`: no change.
  - `+91 (0) 98765 43210`: no change.
  - `09812345678` changes and matches nobody.
  - `98111 22233` changes; it is only the admin's phone.
  - `98765 43210`, struck: changes, never listed.
  - An online gift `98765 43210` is excluded.
  - **Expected A: would_change 6, would_newly_match 2.**
  - Temple B has `98765 43210` but no Gopal. **Expected B: 1 and 0**, which proves the match is per temple.
  - Then (a) is recomputed row by row with `CounterPhone.normalise` in Java for both temples, and it agrees.
