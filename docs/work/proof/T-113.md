## Precedent followed, not invented

There is a clear precedent in this repo and I followed it rather than setting a new one:

- **Story withdrawal** — `E7-S1` (2026-08-29) and `E2-S4` (D-18, 2026-09-08): heading struck through,
  `· WITHDRAWN <date>` appended, a **Status** block saying what was withdrawn and why, a *"do not
  build this story and do not run its script"* line, a *"the text below is left exactly as written"*
  paragraph explaining that deleting it would lose the fact that it was scoped and deferred on
  purpose, a *"what is true now"* paragraph, and the id kept because other documents cite it.
- **`github-import` body** — `bodies/e7-s1.md`: a `## WITHDRAWN <date> — …, kept because other
  documents cite <id> by id` heading directly under the story's source line.
- **`import.sh`** — the E7-S1 line appends `(WITHDRAWN <date>)` to the issue title.
- **UAT script withdrawal** — `UAT-014` and `UAT-018` (D-18): struck-through H1 with `· WITHDRAWN
  <date>`, then a `> ## ⛔ WITHDRAWN <date> — do not run this script` blockquote covering what went,
  what is true now, and why the script below is kept.
- **UAT index and traceability** — the struck-through row shape used for UAT-014/UAT-018, and the
  `~~…~~ **CLOSED <date>.**` shape used for gaps G1, G2 and G10.
- **Locked-document amendment** — the REQUIREMENTS v1.5 / SYSTEM_DESIGN v1.4 pair, which put the
  sign-off first, stated the live-promise-vs-record rule explicitly, and named what it was *not*
  editing and why.

## Judgement calls, stated rather than made silently

**`UAT-059` is amended, not withdrawn — the only script where the brief left the call open.** The
ledger is a Phase 1 feature that survives; only one of its four gift types goes. Its recurring parts
are *live instructions to a tester*, not a record of a test that was run — the defects table is
empty, so this script has not been run — and leaving them would send a tester hunting a filter that
no longer exists. So: an amendment blockquote at the top, and **step 6 struck in place with its
number kept**, so numbering a tester reports against does not shift. Step 2 was turned from *"look at
the type filter"* into a positive check that **no *Recurring* option exists** — a filter for a kind of
gift the product cannot take is a promise on a screen, and this is now the cheapest place to catch it
if T-112 misses one.

**`TECH_STACK.md` §5 — the exact wording used.** The two rows were **not edited at all**. The note
sits directly under the `## 5. Payment Gateway — Razorpay` heading, *before* the table, so no reader
reaches the Razorpay row without it. Its three paragraphs say, in order: that the requirement moved
to Phase 2 and release 1 registers no mandate, creates no subscription and handles no cycle charge;
that **"Razorpay remains the pick and the evaluation below is not reopened"** because recurring is
deferred rather than cancelled and re-running a provider comparison for a feature nobody is building
would be churn, with the instruction to **"read the two rows below as the Stage 3 record of a
2026-08-03 evaluation, not as a live Phase 1 dependency"**; and that **"the rows are left exactly as
written, deliberately"** because they record what was decided on 2026-08-03 when donor-chosen
frequency genuinely *was* a Phase 1 requirement, so editing them *"would falsify the evaluation
rather than update it"* — naming the Cashfree row in particular, whose narrow rejection turned on
precisely the requirement that moved, and whose own advice to re-quote both providers is now advice
for whoever starts the Phase 2 engagement.

**Gap G4 is closed *by withdrawal*, and the row says so in those words.** It complained that
recurring giving was half-present — a ledger filter and a plan API with no donor surface. The
resolution is that all of it goes together, which is the complaint answered, not dodged; recording it
as merely "closed" would let a future reader think the screen was built.
