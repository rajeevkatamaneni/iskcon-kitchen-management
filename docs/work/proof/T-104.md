# T-104 — the send's compare-and-swap now has one test that notices if it is deleted

The predicate `WHERE id = ? AND status = 'DRAFT'` on `CommunicationService.recordSend`'s UPDATE was
guarded by nothing that runs. `lockCommunication` stands in front of it, so no request can reach that
UPDATE holding a stale DRAFT, and the statement-level test T-102 added runs its **own copy** of the
SQL. A green suite was therefore consistent with the predicate being present *and* with its having
been deleted. This adds the one assertion that can tell those apart, as a **named, argued exception**
to the rule against asserting on the text of SQL — not a quiet breach of it.

## What it asserts, and why not a literal string match

A grep for `status = 'DRAFT'` would break on the first re-wrap of the text block, and — worse — would
pass against a predicate that had been moved somewhere it guards nothing. `CommunicationRetryIT`
contains a live example of that hazard: a fixture at the bottom of the file deliberately runs
`UPDATE communications SET status = 'SENT' ... WHERE id = ?` with no predicate at all. A file-wide
grep on either file can read the wrong statement.

So the statement is **located first, then read**:

1. **Exactly one statement in `CommunicationService` moves a communication to `SENT`, and it sits
   inside `recordSend`.** A second, unguarded transition added elsewhere fails here rather than being
   found by a devotee receiving the letter twice. Located by anchoring on `SET status = 'SENT'` and
   closing on the text block's `"""`, with whitespace collapsed, so re-indenting or re-wrapping the
   SQL changes nothing.
2. **That statement's WHERE clause is the same clause `CommunicationRetryIT.transitionToSent` runs**
   — the clause whose refusal is proved against two real unprivileged connections. This is the
   assertion worth having: the tie between the proof and the shipped statement was previously made by
   review alone, and this makes it mechanical. It survives reformatting on either side, and does not
   survive the predicate being deleted, weakened, or relocated. The failure message names the test
   whose proof has come untied.
3. A one-line coarse net (the clause still constrains `status` to `'DRAFT'`) for the case where
   somebody edits *both* sides together. That case is also caught from the other side — with the
   predicate gone from `transitionToSent`, the statement-level test's second transition would update
   a row and go red — so the two tests close each other's gap and neither is redundant.

It refuses to guess rather than guessing: if the method is renamed, if the SQL stops being a text
block, or if the statement grows a second `WHERE` (a subquery would make "the WHERE clause"
ambiguous), it fails with a message saying which of those happened and that the test must be rewritten
deliberately.

**Why a separate class, not a method in `CommunicationRetryIT`:** it is a plain JUnit test — no Spring
context, no Testcontainers, no Docker — because it asserts a property of the tree, not of a run. Put
inside the IT it would have needed a whole application context to compare two strings, and would only
have run when Docker was up. It is named `...SourceTest`, its two `@DisplayName`s both begin
`SOURCE ASSERTION, not behaviour:`, and its class comment carries the argument for the exception so
that a reader who finds it cannot conclude that asserting on SQL is normal here. A paragraph in
`CommunicationRetryIT`'s class javadoc points at it from the other direction.

## Why not the test-only seam

I considered it and rejected it, and would have said so rather than building this if I had thought it
better. A seam in `recordSend` letting a test reach the UPDATE without the lock *would* make the
refusal behaviourally reachable — that is a real merit. The costs beat it:

- It puts a **lock-free path into the one method where a lock-free path writes to four hundred
  devotees twice.** That hazard is permanent and lives in production code; the gap it closes is a
  test-access gap, not a production race.
- It buys a re-proof of something already proved twice: that the clause refuses a second transition
  (the statement-level test, two real connections) and that the endpoint refuses a second admin
  (`two admins pressing Send at once send one copy each, not two`). The **only** fact missing was
  whether the shipped method still carries the clause.
- That fact is a property of the source, not of any run. A source assertion is the honest instrument
  for it and costs nothing to run.
- The contract forbids production changes, and T-102's builder declined the seam on its own authority
  for the same reason. Having read it, I agree with that call rather than merely inheriting it.

| It says in its own text that it is an exception and why | Class javadoc opens with "A deliberate, named exception… Read this before copying anything out of it", states the rule it departs from, why behaviour cannot reach this guard, and why the seam was rejected. `CommunicationRetryIT`'s javadoc points at it and repeats that it is not a licence. |
| Specific enough to be worth having — not a literal grep | Statement located by anchor and method, whitespace collapsed, WHERE clause compared against the clause the statement-level test proves. ## Not done / needs Rajeev

- **No hand smoke-test, and none is possible here.** This task adds no user-facing surface — it adds a
  test. There is nothing to press.
- **The exception should be visible where the rule is stated.** The rule "make no assertion about the
  text of the SQL" lives in the wave 10–12 briefs in `docs/work/DISPATCH.md` (the rule it belongs to —
  *do not accept evidence that would look identical if the thing were broken* — is `README.md` line
  398), not in the code. I did not touch either file; both are outside my contract.
  Somebody should add a one-line pointer to `CommunicationSendGuardSourceTest` as the one sanctioned
  exception, or the next brief will restate the rule flatly and the next builder will read this class
  as a mistake. **That is the one loose end.**
- The source assertion is tied to two method names (`recordSend`, `transitionToSent`) and to the SQL
  being a text block. All three are asserted explicitly with messages saying "rename it here too — do
  not delete the assertion", so a rename fails loudly rather than silently passing. It is still a
  coupling worth knowing about.
