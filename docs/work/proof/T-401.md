# T-401 — a library recipe line carries its preparation, from the book to the temple's recipe

Rajeev's 45 curated recipes put the preparation in a `prep` key instead of after a comma in the
name. The library path dropped it and the import's fallback (re-splitting the name) found nothing,
so all 84 of his notes imported empty. `prep` is now stored, served, editable without being erased,
printed on both library screens, and preferred over the split at import.

## Things I decided differently from the brief, and why

**1. `recipe_ingredients.preparation_note` does not carry a 200 limit.** The brief said to use
`@Size(max = 200)` "the same limit `recipe_ingredients.preparation_note` carries". The column is
`TEXT` with only a not-blank check (V144:767). I kept 200 — but sourced it from the real precedent,
`MergeGroupInput.Member.preparationNote`, which is `@Size(max = 200, message = "That preparation note
is too long.")` and writes onto the very same recipe lines. Same limit, same message, so the two
fields cannot accept what the other refuses. The javadoc says the column is TEXT rather than
repeating the brief's claim.

**2. `leftOver` still runs on a curated line. The answer is usually "nothing", and that is the
point.** `leftOver` asks a different question from `split`: not "which word is a preparation" but
"which words are not the ingredient the person just chose". On a curated line the name is normally
the bare ingredient, so it finds nothing and the note is simply the `prep`. Where a curated name
still carries a comma because the comma names what the temple *buys* — "Rice, basmati" — and the
person answers "Use Rice", "basmati" is as much part of the note as it ever was, and losing it is the
exact fault A-N5 was raised to fix. Suppressing `leftOver` on the curated path would reintroduce it.
Tested: `a stated preparation joins what is left of the name when the person says "Use Rice"` expects
`basmati, Soaked`. The order falls out of `combineNotes`, which reads the raw name to decide: the
prep is not in the name at all, so it sorts last, which is the order a person would write.

**3. A package-private `LibraryLoader.load(String books)`, added as a test seam.** The AC wants a
load that reads `prep` out of a book, and **no vendored book has a `prep` key** (`grep -l '"prep"'
backend/src/main/resources/recipe-library/*.json` → 0 of 32). The books are `classpath:` (single
colon), so a fixture placed under `src/test/resources/recipe-library/` would *replace* the real
directory on the test classpath and break `RecipeLibraryIT`'s 5,376. The overload is four lines,
documented with the reason, and `load()` still loads `BOOKS` and nothing else. `RecipeLibraryIT`'s
class comment argues against fixtures on principle; I think that principle is about *what a real book
says*, and there is nothing real to read here — I said so in the new class's comment rather than
quietly contradicting it. If a reviewer prefers, the alternative is to add `prep` to one vendored
book, which changes production data to serve a test and seemed worse.

**4. Wording.** The one string I added is `"That preparation note is too long."`, copied verbatim
from `MergeGroupInput`. Checked against the installed `ux-writing` skill: 6 words, sentence case,
names the field, no blame, no jargon. The skill would prefer a validation error that states the
requirement ("Keep the preparation note under 200 characters"); I kept the existing wording because
all nine other `@Size` messages in `MasterRecipeInput` read "That X is too long." and one odd one out
is worse than one imperfect one. Worth changing as a set, not one at a time. The separator and the
notes themselves are the book's own words and went through no rewriting.
