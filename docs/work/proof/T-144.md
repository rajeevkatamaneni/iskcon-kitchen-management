## Indian-English usage, and the app's own conventions

**No abbreviation and no plural the product does not already use was invented.** The five labels are
untouched: `Kg`, `gm`, `L`, `ml`, `pieces`. The only new word anywhere is **"piece"**, the ordinary
singular of a word the product already prints.

Only `PIECES` pluralises. `Kg`, `gm`, `L` and `ml` are abbreviations of a mass or a volume, and an
abbreviation takes no "s" in Indian English any more than in British: one kilo of rice is written
"1 Kg", never "1 Kgs". That is not my reading imposed on the codebase — it is what the enum and
`frontend/lib/format.ts` have both written for a year, and T-108 states the same reason. `PIECES` is
the one unit in the vocabulary that names the things themselves rather than how much of something
there is, and one of those is a piece.

Asserted in both directions, because fixing a plural by making everything singular is the same defect
facing the other way: `exact(1, KG|GM|L|ML)` still reads "1 Kg", "1 gm", "1 L", "1 ml", and so do the
two figures that reach one by being promoted into it (`1000 GM` → "1 Kg").

## ⚠ The check you asked for specifically — does `Unit.java` change anything but printed text?

**No. The change is additive and `label()` is untouched.** I checked who writes the value as well as
who reads it, because a grep of one layer is not evidence about another.

- **Stored as the enum name, never the label.** The class comment says so and the tree agrees: 56
  sites use `unit.name()` / `Unit.valueOf(...)`. No column, no CHECK and no request carries "pieces".
- **No reverse lookup exists.** `grep` for `fromLabel|byLabel|labelOf|.label().equals` across all of
  `src/` returns nothing, so no parser can be confused by a second word.
- **Nothing serialises the label.** No `@JsonValue`, no `@JsonCreator`, no `AttributeConverter`
  anywhere near `Unit`, and no `@JsonFormat(shape = OBJECT)` on it — so Jackson writes the enum as
  `name()` and never introspects a getter. Adding `label(BigDecimal)` cannot appear in an API
  response.
- **The one place a label does reach a wire type** is `RecipeScaler` → `ScaledQuantity.displayUnit`,
  and I deliberately did **not** touch it (see above). It calls the no-arg `label()`, whose return
  value is byte-for-byte what it was before this change.
- **`label()` itself is unchanged.** I added an overload and a field, and the three existing callers
  compile and behave identically. The negative control's arm B proves the singular is load-bearing
  rather than incidental.

## The fix

`Unit` gains a second word and a way to ask for the right one:

```java
PIECES("pieces", "piece", Family.COUNT, 1);

public String label(BigDecimal count) {
    if (count == null) {
        return label;
    }
    return count.abs().compareTo(BigDecimal.ONE) == 0 ? singular : label;
}
```

Three things in that are deliberate and each has a test:

- **The count is required, not optional**, matching T-108 exactly. An optional count is a count the
  next caller forgets, and the forgotten case renders the defect this removes.
- **`compareTo`, not `equals`.** A quantity arrives from JDBC scaled to its column, so a genuine one
  stool is `1.000`, and `BigDecimal.equals` compares the scale as well as the value — it would answer
  false and print "1 pieces" for every row that had ever been near a database. This project has been
  caught in that exact spot before; `Quantities.displayUnit` four files along carries the same note
  about `signum()`.
- **Absolute value**, so taking one stool back out reads "-1 piece".

Units with no distinct singular declare one word and go through the three-argument constructor
unchanged, so the next counted unit somebody adds — crates, sacks, bundles — is one extra word on one
line rather than a second place to remember a rule.

Then the funnel, `Quantities.say()`:

```java
return format.format(value) + " " + unit.label(value);
```

`value` there is the figure **as it will be shown** — already rounded by `roundAsAPersonWould` and
already promoted between gm and Kg. That is why the word is chosen at this line and not by any of the
twelve callers: it is the last place holding the number the reader actually sees. A job card asking
for 1.2 stools prints "1 piece" because the cook's form made it whole first; a ledger row prints
"1.2 pieces" because it does not round. Both are right, and both are asserted.

## The guard — yes, but not the shape you sketched, and here is why

You asked for a reasoned answer either way. **Mine is yes**, and the reason it is worth having is not
theoretical: `RecipeScaler` is live proof that a Java caller with a count in hand reads the plural
label, and nothing on either side of the app catches it today.

**But the frontend's guard cannot be translated.** T-108's rule works because JSX has a distinctive
tell — `}` followed by `{unitLabel(` is visibly a number and a word glued together. Java has no
equivalent. The two shapes that actually produce this bug here are

```java
"%s %s".formatted(n, u.label())
new ScaledQuantity(raw, name, value, u.label())
```

and no regex recognises either as "a number next to a word". A guard that tries would be exactly the
noise you said you would rather refuse.

**So `UnitLabelAgreementTest` inverts it.** Rather than hunting the bad composition, it enumerates
every call site of the no-arg `Unit.label()` and holds that list fixed, with a sentence per entry
saying why there is no count beside it. Four lines in the whole of `src/main`. A fifth appearing is
one thing for a person to look at once, and a person looking at it once is all this defect has ever
needed.

**The one measurement that decides whether this is precise or noise**, and I measured rather than
assumed it: **twelve** unrelated enums in this codebase expose a `label()` — `BanCategory`,
`LeaveType`, `JobTitle`, `PaymentMode` and the rest — so a tree-wide `.label()` scan matches twenty-odd
innocent lines and proves nothing. Narrowed to files that mention `Unit` at all, it matches **exactly
four, all four genuinely `Unit.label()`, with no false positives**:

```
recipe/RecipeScaler.java:57            unit.label()
recipe/RecipeScaler.java:67            displayUnit.label()
document/DocumentGenerationService.java:224   Unit.valueOf(l.unit()).label()
ingredient/IngredientUnits.java:69     ref.canonical().label(), given.label()
```

The second test in that class asserts the funnel line itself, so if `say()` ever goes back to
`label()` the failure names the one line that matters instead of leaving somebody to infer it from
four broken strings.

**The two `RecipeScaler` entries are listed as a defect, not an approval**, with the reasoning in the
file and a note that fixing them will fail this test and require deleting the entries. A guard that
records an outstanding bug where the build runs beats a comment nobody executes.

**No abbreviation or plural the product does not already use was invented.** Five labels unchanged;
