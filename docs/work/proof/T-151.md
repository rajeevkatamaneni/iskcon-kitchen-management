# T-151 — the WhatsApp Test button asks for a phone number and sends a real message to it

Rajeev, 2026-09-12: *"Ask the use for a phone number to send a test message."*

## What was built, in one paragraph

On /settings, the WhatsApp section's button is now **Send a test message**. Pressing it opens one
phone box with Send and Cancel, in place where the button was. Send calls
`POST /api/v1/settings/whatsapp/test` with `{ "phoneNumber": "..." }` (new record
`SendWhatsAppTestRequest`, still `MANAGE_TEMPLE_SETTINGS`). The service sends the new
`NotificationTemplate.WHATSAPP_TEST` (Meta name `connection_test`, language `en`, one parameter: the
temple's name) through `MetaWhatsAppClient.sendTemplate`. On a returned message id it calls the existing
`markMessageSent()`, which is still the only UPDATE of `whatsapp_last_sent_at`. It also refreshes
`whatsapp_verified_at`, writes an audit entry and answers with the settings view. The screen then says
"Test message sent to +91…. Check WhatsApp on that phone." A malformed number is `KMS-400003`. Any Meta
refusal or failure is `KMS-500007`, with Meta's own words going only to the log.

**`verified_at` / `display_number`, my call:** a successful send refreshes `whatsapp_verified_at`,
because Meta accepting a send under the token proves the credentials. Without that, "Last checked" would
never move again, since Test no longer calls `verifyNumber`. `whatsapp_display_number` is left alone: a
send does not return it, and Save refreshes it.

## Meta's constraints, with sources

1. **Can a business-initiated message be free text? No.**
   - Meta, *Template fundamentals*
     (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview):
     "Template messages are the only type of message that can be sent to WhatsApp users outside of a
     customer service window."
   - Meta, *About the WhatsApp Business Platform*
     (https://developers.facebook.com/documentation/business-messaging/whatsapp/about-the-platform),
     the same sentence: "They are also the only type of message that can be sent to WhatsApp users
     outside of a customer service window."
   - Meta, *Pricing* (https://developers.facebook.com/docs/whatsapp/pricing): non-template messages "can
     only be sent within an open customer service window". *Get Started* says the window is 24 hours:
     "This 24-hour window allows you to send non-template messages to users on WhatsApp."
   - Meta error 131047: "More than 24 hours have passed since the recipient last replied to the sender
     number." Action: "Send the recipient a template message instead." Source:
     https://developers.facebook.com/docs/whatsapp/cloud-api/support/error-codes
   - The code's own comment agrees. `MetaWhatsAppClient.sendTemplate` javadoc: "Meta only allows free
     text inside the twenty-four hours after that person last wrote to the temple."
   - An admin typing a colleague's number has no open window with them, so free text is out.

2. **Must a new template be approved before it can be sent? Yes, and review can take up to a day.**
   - Meta, *Template fundamentals*: "Templates must have a status of `APPROVED` before they can be sent
     in template messages." And: "Templates are automatically reviewed upon creation or after editing."
     And: "Review can take up to 24 hours."
   - Meta error 132001: "The template does not exist in the specified language or the template has not
     been approved."
   - In our code, `submitTemplates` registers every `NotificationTemplate` only inside `save()`, which is
     Connect or Save. So a temple connected before this change (staging) has **not** registered
     `connection_test`. Someone must press **Save** once in Settings → WhatsApp, with the secrets left
     blank so the stored ones are kept. Re-running is safe: an existing template comes back
     `ALREADY_EXISTS`. Then Meta must approve `connection_test`, which can take up to 24 hours. Until
     then the test answers KMS-500007.

3. **Does a test or unpublished setup only deliver to registered test recipients? Probably yes, but not
   confirmed from Meta's own pages.**
   - Meta confirms test resources exist and are relaxed. *About the platform*: "When you get started
     with Cloud API a test WhatsApp Business account and test business phone number are automatically
     created for you. Test WhatsApp Business accounts and test phone numbers are useful for testing
     purposes as they have relaxed messaging limits and don't require a payment method on file in order
     to send template messages." *Get Started*: "Add a **To** phone number that will receive the test
     message."
   - Meta's current pages do **not** say a test number can message only its registered recipients, or
     that the limit is five. I searched *Get Started*, *Business phone numbers*, *Messaging limits* and
     *Error codes*. Error 131030 ("Recipient phone number not in allowed list") is **not** on Meta's
     current error-codes page.
   - Third-party sources state both. WANotifier help
     (https://help.wanotifier.com/en/article/test-phone-number-limitations-in-direct-setup-kt0ly2/ and
     https://help.wanotifier.com/en/article/fix-error-message-not-sent-recipient-phone-number-not-in-allowed-list-add-recipient-phone-number-to-recipient-list-and-try-again-13xu4d1/),
     respond.io (https://respond.io/help/whatsapp/whatsapp-cloud-api), and chatwoot issue #13932
     (https://github.com/chatwoot/chatwoot/issues/13932), where 131030 appears in development mode.
   - The code already assumes it. `WhatsAppChannelAdapter` names "a number outside Meta's test list" as
     a known refusal.
   - For a real (non-test) number, Meta's *Messaging limits* page says: "Newly created business
     portfolios have a messaging limit of 250".

4. **Is a sample template (`hello_world`) on every WhatsApp Business Account? Not established, so not
   relied on.**
   - Meta's documentation names `hello_world` only inside the Get Started walkthrough, whose account is
     the automatically created test one: "The temporary access token you created to send the
     `hello_world` template message expires quickly".
   - Neither *Template fundamentals* nor *Business phone numbers* says a production account has it.
     Third-party search summaries say it comes with a test account at setup; I did not treat that as
     proof.

**What that decided:**
- Free text is ruled out by (1).
- `hello_world` is ruled out by (4): it would work on a developer's test account and might fail on a
  temple's real one.
- Sending an existing template with invented values would put a false shift reminder or purchase order
  on a real person's phone.
- That leaves a dedicated `NotificationTemplate`: UTILITY and OPERATIONAL like the rest, one parameter
  (the temple's name), with the placeholder mid-sentence. It is registered for every temple the same way
  as every other message. The cost is (2): approval before it works, and one Save on already-connected
  temples. The in-place hint on the number box says "Meta must approve the test message first, which can
  take up to a day after you connect."

## Recommended KMS-500007 wording

The provisional text names only a wrong number or a test recipient. From (2), the most common refusal on
a newly connected temple, and on staging right after its Save, is the template still in review. I
recommend:

```java
WHATSAPP_TEST_NOT_DELIVERED(500007, 502,
        "WhatsApp didn't send the test message to that number.",
        "Check the number has its country code. If you connected in the last day, Meta may still be "
                + "approving the message, so try again later. On a test account, add the number as a "
                + "recipient in your Meta account first."),
```

"Didn't send" rather than "didn't accept for that number", because the refusal is often not about the
number. I did not open `ErrorCode.java`; the coordinator edits it.

**Mock or effect, and why:** the mock was the defect. The real `getToken` in
`frontend/lib/auth-context.tsx` is `useCallback(async () => …, [user])`, so on a real screen it is the
same function on every render and `SettingsView`'s load effect runs once. The old mock built a new
function inside every `useAuth()` call. Each render gave the effect a new dependency, so it refetched
and overwrote the just-saved settings with the stub. The effect itself is right to re-run when the
token source really changes, which happens at sign-in. The fix is a `vi.hoisted` `getToken` shared for
the whole file. The connect test now asserts the connected panel: "We can send as Temple Kitchen", the
"Connected, and Meta accepted…" line, "Tell Meta where to reach us", the Replace button, "Your message
templates went to Meta on", and an enabled "Send a test message". The tooltip assertion it used to lean
on is gone.
