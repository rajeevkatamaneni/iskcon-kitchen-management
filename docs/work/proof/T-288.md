## The shared formatter: `readableRate` in `frontend/lib/format.ts`

`readableRate(price, perUnit, pack?)` returns `string | null`.

- `readableRate(0.3, "GM")` gives "₹300 / Kg".
- `readableRate(0.25, "ML")` gives "₹250 / L".
- `readableRate(4, "PIECES")` gives "₹4 / piece".
- `readableRate(60, "KG", { label: "Bag (25 Kg)", quantity: 25 })` gives "₹1,500 / bag · ₹60 / Kg".
- A price of null gives null, never "₹0".
- Figures are rounded to paise, with Indian grouping.

The doc comment names it as the one rate formatter for the merge screen, the invoice page and the ingredient page to move onto. The server has the same rule in `DocumentGenerationService.rateUnit`.

## Rulings and judgement calls

1. **How a line is sent** (clarifier, then conductor, 2026-09-19). The brief contradicted itself: "3000 gm sent" against "reuse the shopping list's convention". The conductor ruled to follow the shopping list, so a plain line goes as `{quantity: 3, unit: "KG", expectedPrice: 60}`. The acceptance check's "(3000 gm sent)" is read as the stock amount, which is 3,000 gm either way. Pack lines are sent exactly as the shopping list sends them: `{quantity: 100, unit: "KG", expectedPrice: 60, packSizeId, packCount: 4}`, with the price per the stock unit. No server change was needed.
2. **The rate is always per Kg or L, not per the unit the quantity is printed in** (the conductor's rule). T-260's sheet followed the printed quantity, so a lone 500 gm pack read "₹0.50 / gm". Now it reads "₹250 / 500 gm · ₹500 / Kg", and a plain 450 gm line reads "₹60 / Kg".
3. **Readable unit on the form:** Kg for a gm-stocked item and L for an ml-stocked item, always, even below 1,000 (0.25 Kg). This is the same rule the type-ahead's "₹60/Kg" already used, so the box and the list price never disagree.
4. **Packs sit in the Unit column** as a select: the plain unit, then each of the ingredient's packs ("× Bag (25 Kg)"). One-off lines already had a unit select in that column.
   - The line starts in the vendor's own "Sells it as" pack, at the vendor's pack price. With no pack price, it is the list price × the pack size, as the shopping list works it out.
   - The price box then holds the price per pack.
   - Switching the select converts a typed price (₹1,450/bag ↔ ₹58/Kg). It is never re-read from the vendor.
   - A pack line's box has `step="1"`, so `Form` refuses part of a bag.
5. **The rate in words under each price box** ("₹60 / Kg", "₹1,500 / bag · ₹60 / Kg"). This is not in the mock. It is how D-8's wording reaches the form.
6. **Layout at 1024: two deviations from the mock, the lesser evil.** Before this change the page had 680px for the table:
   - one plain line (the committed code) made the table 775px wide
   - my pack select made it 891px
   - in both cases, Remove and the form's right edge were cut off
   The fixes:
   - The empty type-ahead row now spans the Item, Quantity and Unit cells (`colSpan={3}`), which were always empty. It is held at `max-w-xs`, so it looks as it did in the Item cell.
   - The quantity box is `min-w-20` (80px), not the mock's 112. The price box keeps 112.
   Result: 680 wide in 680. The item column is 90px at 1024, so names wrap onto 2–3 lines. No word is cut and nothing overflows. That is the remaining cost.
