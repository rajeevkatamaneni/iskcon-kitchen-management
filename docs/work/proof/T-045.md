## The stop, and how it resolved

The create form is `frontend/components/IngredientForm.tsx`. `frontend/app/ingredients/new/page.tsx`
— which was in the original contract — only *hosts* it; it does not build the payload. The literal
that had to carry the new field lives at `IngredientForm.tsx:36-42`, and the checkbox it mirrors at
`:82-87`. **That file was not on the original paths list, so I stopped and reported instead of
widening the contract myself.**

The stop was structural, not a matter of effort: `onSubmit` is typed
`(input: CreateIngredientInput) => void` *inside* `IngredientForm.tsx`, so the type error was
internal to that file and nothing writable from `app/ingredients/new/page.tsx` could silence it. Two
workarounds were considered and rejected:

- **Inlining a second form in the page** — would duplicate a shared component and invent a parallel
  pattern for the same shape of decision. **D-3 forbids exactly that by name.**
- **An `<input form="add-ingredient">` rendered outside the form** — would reach `FormData`, but
  `IngredientForm`'s own `submit` would never read it. Green build, wrong design.

Deliberately **no test was written for the create path while it was blocked**: a test asserting a
control that did not exist would have sat red in the tree and broken the release agent's full-suite
run.

**Resolution.** The coordinator (`ad54108e492c91783`) checked ownership across the ledger — the only
other claim on the file is T-023 in wave 5, weeks away, a cross-wave serialisation rather than a
collision; none of T-042/T-047/T-048 names it; `git status` showed it clean — and granted exactly
that one file. The coordinator also recorded the undercount as a planning error of theirs: the brief
was built by checking which *test files* named `IngredientView`, and never which *components*
construct `CreateIngredientInput`, so the reservation written into `lib/api.ts` had already broken
`IngredientForm.tsx` before this task started. **Six files were named; it was seven.**

## Acceptance criteria

**1. An ingredient can be marked Ekadashi-prohibited and un-marked, from the screen, and the change
persists — asserted through the wrapper, not by eye.** ✅ Two tests, both asserting on
`api.setIngredientEkadashiFlag` rather than on rendering:

- `lets an admin mark an ingredient Ekadashi-prohibited` — clicking *Allowed* calls
  `("i1", true, "test-token")`, and additionally asserts `setIngredientSattvicFlag` was **not**
  called, so one rule can never be written through the other's endpoint.
- `lets an admin un-mark one, so a mistake is recoverable` — a fixture with the flag already set
  renders *Prohibited*; clicking calls `("i1", false, "test-token")`.

Both fail with the fix patched out (control 4).

**2. A newly created ingredient can carry the flag from the create form.** ✅ Two tests:

- `carries the Ekadashi flag from the create form` — ticking the box and submitting sends
  `ekadashiProhibited: true`, and asserts `sattvicProhibited: false` in the same payload so ticking
  one rule cannot set the other.
- `says so out loud when the flag is not ticked, rather than leaving the key out` — **the heart of
  the defect, in one assertion.** It deliberately does *not* use `objectContaining`, because a
  missing property and an explicit `false` read identically to it. It inspects the payload's own
  keys: `expect(Object.keys(payload)).toContain("ekadashiProhibited")` and then
  `expect(payload.ekadashiProhibited).toBe(false)`. That is exactly the silence that caused this bug
  — an absent JSON key deserialising into a primitive `boolean` as the permissive answer — pinned
  so it cannot come back.

**3. The screen shows the current state of the flag, so somebody can see which ingredients are
prohibited without changing anything.** ✅ `shows the state of both flags independently, changing
neither` renders an ingredient that is Ekadashi-prohibited but sattvic-allowed, asserts the Ekadashi
cell reads *Prohibited* and the Sattvic cell reads *Allowed* — proving the two columns are not wired
to the same field — and asserts neither wrapper was called. `shows kitchen staff the Ekadashi state
but gives them no way to change it` covers the read-only path.

**4. The five borrowed fixture files have one line added each and nothing else.** ✅ `git diff --stat`

## Design notes

**Both controls mirror their sattvic twin exactly, per D-3.** The list toggle: same control, same
two words (*Prohibited* / *Allowed*), same `bg-warning-bg text-warning` vs
`bg-sunken text-ink-secondary`, same admin-only rule, same failure string *"We couldn't change that
flag."*, same read-only fallback. The create checkbox: same `col-span-2` label, same input classes,
same `isAdmin` gate, same *"X-prohibited (examples…)"* sentence shape. Nothing was invented, and the
sattvic controls were not modified.

**Wording.** *Prohibited* / *Allowed* under a column headed **Ekadashi**, and
*"Ekadashi-prohibited (rice, wheat, dal, chickpeas…)"* on the form — the same register as
**Sattvic** and *"Sattvic-prohibited (onion, garlic, mushroom, egg…)"*. It states a rule, not a
preference, uses concrete ingredients a temple kitchen names rather than abstract categories, and is
the vocabulary already on these screens, so nobody has to learn a second one.

**The edit row.** `EditRow` had exactly as many cells as the display row. A sixth column would have
left it one short and pulled *Actions* out of line with every row above it, so the aliases cell takes
`colSpan={2}`. Neither flag is edited in that row — each is a one-click toggle on the row itself — so
no editing affordance was lost.

**Test scoping.** `flagCell()` in `ingredients.test.tsx` finds a column by its **header text**, not
by a fixed index, so a query cannot silently assert against the neighbouring flag, and inserting a
column later moves the tests with it. One pre-existing sattvic test was re-scoped through it, because
`getByRole("button", { name: /allowed/i })` became ambiguous the moment a second identical-looking
toggle joined the row.
