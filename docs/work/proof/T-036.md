## Finding 2 — the lowercasing

### Before and after, the exact sentence

The fixture is Rajeev's own: an `ADJUSTMENT` of `+1.8` KG at `2026-08-23T06:15:00Z`, which the
table above the dialog prints as **`+1.8 Kg`** on **`23 Aug 2026`**.

```
before:  The adjustment of +1.8 kg on 23 aug 2026, 11:45 stays in the ledger exactly as it is.
after:   The adjustment of +1.8 Kg on 23 Aug 2026, 11:45 stays in the ledger exactly as it is.
```

And the same in the refusal dialog's third paragraph:

```
before:  It is in the list behind this, marked as a correction of the adjustment of +1.8 kg on 23 aug 2026, 11:45.
after:   It is in the list behind this, marked as a correction of the adjustment of +1.8 Kg on 23 Aug 2026, 11:45.
```

The leading label still reads mid-sentence — "The **adjustment** of…", never "The Adjustment of…"
— which is asserted, not assumed.

### How, and why there

Fixed at construction, as directed. `summary` (now `:523-542`) lower-cases the type label alone:

```ts
const summary =
  `${(TYPE_LABEL[movement.type] ?? movement.type).toLowerCase()} of ` +
  `${movement.quantity > 0 ? "+" : ""}${quantity(movement.quantity, movement.unit)} ` +
  `on ${moment(movement.createdAt)}`;
```

and both call sites now interpolate `{summary}` with no `.toLowerCase()` on it. `quantity()`,
`unitLabel()` and `moment()` in `lib/format.ts` were read and not touched; `:423`, which lower-cases
a `TYPE_LABEL` with the date outside the call, was left exactly as it was.

### The note left about the MealComposer precedent

Quoted in the doc comment on `summary`, so the third occurrence has something to find, and again in
the test that covers the litre case:

> Units are not decoration — `Kg`, `gm`, `L` and `ml` name different amounts of the same thing —
> and this codebase has been bitten by exactly this before: the note at
> `components/planner/MealComposer.tsx:1362` records `toLowerCase()` rendering a litre's "L" as the
> digit-like "l", which is why unit labels there are printed through `unitLabel()` and left in the
> case it gives them. Same lesson, second place: decide the case where the string is built, so a
> call site cannot flatten a formatter's output on its way to the screen.

## Finding 3 — the control that was offered and then refused

`{!reversedBy && <Button …>Correct</Button>}` in the actions cell (`:438-464`). `reversedBy` is the
value already computed at `:402` and already drawing the *Corrected* badge three lines above, so no
new state, no new field, and nothing added to `api.ts`.

### The judgement you asked me to state: nothing, not a disabled control

**A corrected row shows an empty actions cell.** No disabled button, no replacement text.

**The T-002 precedent I copied, and why.** T-002 shipped five withdrawals and did the same thing in
every one of them: *remove the affordance, leave the explanation in words.* The work-order card is
not rendered at all for a non-issuer, and the `InlineNotice` that already said "Approved, and
waiting on the store." carries the reason. The "Working today" tile keeps its figure and its
per-meal note and merely loses its `href` — the information stays, the affordance goes. The
`/staff-schedule` and `/my-shifts` empty states had their links and their instructions removed and
replaced with a sentence saying what actually happens. **Not one of the five is a disabled control.**

This row is the closest analogue to the tile: the explanation is already on screen, one column to
the left, in the *Corrected* badge. Adding a disabled "Correct" button beside it would say the same
thing twice in two registers, and a control that is disabled and can never become enabled just asks
the reader to work out what would enable it. So: badge stays, button goes. That reasoning is in a
comment at the guard, alongside the reason the server-refusal branch stays.

### The refusal branch stays, and is said so in a comment

The guard comment says it in as many words ("What is removed is the *ordinary* way of reaching that
refusal, not the refusal… Deleting it would trade a rude screen for a broken one"), and the
`CorrectMovement` doc comment — which previously argued the control *should* be unconditional — was
rewritten rather than left to contradict the code:

> **The refusal branch below is for the race, and only the race.** … The row now withholds the
> control when it holds the reversal, so the only way left to this branch is the one it was written
> for: two people on two tabs, where whoever presses second is looking at a screen that was right
> when it loaded.
