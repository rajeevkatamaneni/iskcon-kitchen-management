## Tables and what counts as successful

Every gift is one row in `donations`: online money (V38), cash at the counter and goods (V17). Receipts live on the same row (`receipt_number`, `receipt_issued_at`, V117). The PDF is a `documents` row with `kind = 'DONATION_RECEIPT_PDF'` and `donation_id`, one per gift by unique index. `DocumentService.receiptFor(donationId)` finds it by that pair.

Successful means all three:
- `status = 'COMPLETED'`. The other V38 values are `PENDING`, `FAILED` and `EXPIRED`. Counter and in-kind gifts take the default `COMPLETED`.
- `voided_at IS NULL` (V104). A struck gift keeps `COMPLETED`, so status alone is not enough.
- `is_anonymous = false`. Online gifts are never anonymous (MonetaryDonationService writes `false`), but a counter gift can be.

## Verified contacts

- **Phone:** the token's `phone_number` claim. Firebase sets it only after phone sign-in, which needs the one-time code, so its presence is the proof. It is always E.164. I also require it to match `^\+[1-9][0-9]{7,14}$`, otherwise it is ignored.
- **Email:** the token's `email`, and only when `email_verified` is true. Firebase puts an unconfirmed address on an email-and-password account that never clicked the link. `FirebaseTokenVerifier.toSubject` reads `token.isEmailVerified()`.

This is the same rule as `PendingAccountClaim.verifiedContact`.

**How the verified subject reaches the service.** Today it doesn't. `AuthenticationFilter` verifies the token and keeps only the uid. The principal (`AuthenticatedUser`) carries the email and phone from the `users` row, which an administrator typed, and no `emailVerified`. The subject is used at request time only by the first-sign-in claim.

I carry it by verifying the same bearer token again, inside `MyDonationsController`, through the same `TokenVerifier` bean. Its uid must equal the principal's `firebaseUid`, or the contacts are ignored. If the second verification fails, the caller is matched by account only. No path outside the contract was needed. The cost is a second verification on these two endpoints; with Firebase that includes the revocation lookup. The IT proves the users-row contacts match nothing (test 6 below).

## The matching query and comparison

`MyDonationsService.candidates` selects, at this temple (`d.tenant_id = current tenant`, plus RLS): `COMPLETED`, not voided, not anonymous, and one of:
- `donor_account_user_id = caller`, or
- the stored phone with everything but digits and `+` removed equals the verified phone, or
- `lower(btrim(donor_email))` equals the verified email.

That SQL is a wider net for phone. `owns()` in Java then applies the exact rule:
- **Email:** the stored value trimmed and lower-cased (`Locale.ROOT`) must equal the token email, also lower-cased.
- **Phone:** the stored value with T-157's separators removed must be identical to the token number. The separators are `[\s\p{Z}\p{Pd}\p{Cf}]`, the same pattern as `PhoneNumberDeserializer`. So `+91 98765 43210` matches `+919876543210`. `98765 43210` does not, and nor does `+449876543210`: no assumed +91, no last-ten-digits comparison.

Name and PAN are never read by the rule.

## The stranger answer

404 with `KMS-400030` ("We couldn't find what you were looking for."). It is the same answer as for a gift id that never existed, which the IT asserts code-for-code and message-for-message. The same 404 covers:
- not yours
- an unverified email
- struck, anonymous or not completed
- another temple
- no receipt issued
- a receipt not yet READY

**Why 404:** a 403 would confirm the gift id is real, and this is already what RLS gives for another temple's gift on the admin path. Ownership is checked before the document is looked up.

## The screen

- **Money:** the amount (`money(amount, "INR")`), with the description underneath.
- **Goods:** the description ("Rice, 25 Kg"), with no amount.

Below that is the date (`dateWithYear`), plus " · Receipt R-…" where one exists. A **Download receipt** button appears only where `receiptNumber` is set. ## Not done, and follow-ups

- **Hand smoke test not performed.** I did not drive the page in a browser, and staging was off-limits.
- **Second token verification.** Carrying `emailVerified` and the token's phone on `AuthenticatedUser` (`AuthenticationFilter` and `AuthenticatedUser`, both outside this contract) would remove the second verification and its extra Firebase revocation call.
- **The phone separator pattern is copied** from `config/PhoneNumberDeserializer`, whose `normalise` is package-private. Making it public, and using it here, would stop the two drifting.
- **Counter gifts rarely carry E.164.** `RecordDonationRequest.donorPhone` has no pattern and no `PhoneNumberDeserializer`, and the counter form's placeholder is only "+91…". A number typed as `98765 43210` will never match a verified phone. That is correct by the no-loose-matching rule, but it means many counter gifts won't appear until the counter form requires E.164 (T-172's screens and a request record outside this contract).
- **A receipt whose PDF FAILED to render** shows its number, but the download gets 404. Only the admin's Send receipt re-queues it. The volunteer sees "We couldn't find what you were looking for."
- **No audit entry on a donor downloading their own receipt.** The PAN in it is their own, and `AuditAction.java` was not in the contract.
- **Dependency:** the `donation_receipt` WhatsApp wording ("Please ask at the temple office for a copy.") should later point to this page. That belongs to the template batch, and `NotificationTemplate` was not touched.
