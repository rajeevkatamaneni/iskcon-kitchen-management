## Blocker B — there is no next charge date anywhere in the stack

**Acceptance criterion 1 is "An active plan is listed with its amount and its next charge date."
That date does not exist.** Not in the table, not in the view, not in the service, not in the
TypeScript type. It is not a missing wrapper; it is a value the product has never held.

The table (`V42__recurring_donations.sql`, plus `V43` which adds only `pan_fingerprint`):

And a whole-tree search for any next-charge concept, under any of the six spellings the codebase or
Razorpay might use, returns nothing at all:

```
$ grep -rn "next_charge\|nextCharge\|charge_at\|chargeAt\|current_end\|currentEnd" backend/src frontend/lib frontend/app
--- exit 0 (empty above = no match) ---
```

Razorpay holds the real schedule (`charge_at` / `current_end` on the subscription). We never read
it, never store it, and never serve it.

**Why I did not compute it on the client and move on.** I could derive a date from `createdAt` plus
one period of `frequency` — it would typecheck, the test would pass, and the screen would look
finished. It would also be a **fabricated date about a live financial mandate**. It goes wrong the
first time a cycle fails (`notifyFailedCycle`), the first time the provider halts the plan
(`status = 'HALTED'`), and any time Razorpay's own anniversary differs from our insert timestamp —
and it would be wrong *silently*, which is the exact failure mode the brief singled out this task
for. A donor reading "next charge 15 October" off a screen and planning around it is worse served
than a donor who is told nothing.

Closing this properly needs a migration (a `next_charge_at` column fed from the subscription
webhook, which is where the provider tells us), a backend change to `RecurringPlanView` and
`myPlans`, and an `api.ts` type change. My brief says: *"No migration, no error code, no
permission. If you conclude you need one of those, that is a signal the task was mis-scoped: stop
and report it rather than inventing one."* So I stopped.

## A third finding, not a blocker — a second cancel is not refused by the server

Acceptance criterion 2 says a second cancel must be *refused readably*. The server does not refuse
it. `cancelPlan` re-cancels a `CANCELLED` plan without complaint:

```java
// RecurringDonationService.cancelPlan
String subscriptionId = requireOwned(planId, actor.getUserId());   // no status filter
if (subscriptionId != null) {
    gateways.forCurrentTenant().cancelSubscription(subscriptionId);
}
jdbc.update("UPDATE recurring_plans SET status = 'CANCELLED', updated_at = now() WHERE id = ?", planId);
```

`requireOwned` selects on `id` and `donor_account_user_id` only, so a cancelled plan is still found;
the UPDATE is idempotent and returns `204`. What the gateway does splits by environment:

```
$ sed -n '127,135p' backend/src/main/java/org/iskcon/kms/payment/RazorpayPaymentGateway.java
	public void cancelSubscription(String subscriptionId) {
		try {
			client.subscriptions.cancel(subscriptionId);
		} catch (RazorpayException e) {
			throw new ApplicationException(ErrorCode.PAYMENT_GATEWAY_ERROR, Map.of(), e);
		}
	}

$ sed -n '56,60p' backend/src/main/java/org/iskcon/kms/payment/StubPaymentGateway.java
	public void cancelSubscription(String subscriptionId) {
		// no-op for the stub
	}
```

So on Razorpay a duplicate cancel surfaces as `PAYMENT_GATEWAY_ERROR` — readable, but it names the
gateway rather than the truth ("this gift has already been stopped"); on the stub it silently
succeeds. **This one I judged buildable inside the contract** — the screen stops offering cancel on
a plan it has already cancelled, and surfaces the server's `ApiError` message if a stale click
still fires — so it is recorded here as context for whoever picks the task up, not as a reason for
the stop.

## Acceptance criteria

| # | Criterion | Status |
|---|---|---|
| 1 | An active plan is listed with its amount and its next charge date | **Blocked.** Amount is available (`amountInr`); the next charge date does not exist in the database, the view, the service or the TS type — see Blocker B |
| 2 | Cancelling removes it from the list; a second cancel refused readably | Buildable, not built. The refusal has to come from the screen; the server does not refuse — see the third finding |
| 3 | A donor with no plans sees an empty state, not an error | Buildable, not built. `myPlans` returns `[]`, never a 404 |
| 4 | `RequireRole` guard matches who the endpoints admit, noting D-8 / D-10 | Determined, not applied. See below |
| 5 | `tsc` clean, vitest passes, `npm run build` succeeds | Not run — nothing was changed |

**On criterion 4, since the answer is settled and shouldn't be re-derived by whoever picks this up.**
All four endpoints are `@PreAuthorize("isAuthenticated()")` — the server admits any signed-in user.
The guard should nonetheless be `VOLUNTEER` alone. `DECISIONS.md` D-10 says so in terms: *"Giving
stays on `isAuthenticated()` per D-8 — a staff member who insists on donating through the API harms
nobody, and minting a permission to stop them is ceremony."* The narrowing is deliberately a page
guard, not a permission, because the reason is tone rather than authority: *"a tone-deaf screen
reached by typing the URL is still tone-deaf."* So `<RequireRole roles={["VOLUNTEER"]}>`.

Worth flagging while it is in view: `frontend/app/donate/page.tsx:13` still reads
`roles={["TEMPLE_ADMIN", "KITCHEN_MANAGER", "KITCHEN_STAFF", "VOLUNTEER"]}`, which is what D-8
reverses. That file is **not in my contract** and I have not touched it, but if no task in this
batch owns that narrowing, D-8 is unimplemented and a new `/donate/recurring` built to `VOLUNTEER`
would be stricter than the giving page that links to it.
