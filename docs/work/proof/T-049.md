# T-049 — The planner has no way back to today: one Today control, inside the shared stepper, opted into by the two screens that need it

**The answer is a shared component both screens must take.** Saying so plainly because the next
person will otherwise solve it locally again, which is how it broke the first four times. The way
back to today is now a control inside `components/ds/PeriodNav.tsx`, beside the arrows. The calendar
no longer has a copy of its own in its page header; there is one implementation and both screens
take it whole.

---

## What was decided, and why

**The brief's suggested approach was confirmed, not rejected.** `PeriodNav` has five consumers, and
the opt-in mechanism the brief pointed at — `current` being optional and passed by only one caller —
is exactly the right model. The Today control is opt-in through a new optional `onToday` prop: the
planner and the calendar pass it, the three report screens do not, and nothing appeared on a report
screen as a side effect of fixing the planner.

**Placement: inside `PeriodNav`, not in `PageHeader`'s `actions` slot.** N2 says follow the
calendar's placement; I did not, and the reasoning is the one the brief anticipated. The planner's
top right is shaped differently, so `actions` is the one place the two screens *cannot* share — which
is precisely how the calendar ended up with a Today and the planner with none. Beside the stepper,
both screens have identical structure.

Placing it there also settles an objection that would otherwise have re-opened. Rajeev, 2026-08-23:
*"No Today button on the planner in any view — the screen is one accent action, and the arrows are
how you move."* That objection is about a **page action** competing with the primary. This is not a
page action: it is a quiet `ghost` button in the stepper's own group, the third arrow. The planner's
header still carries nothing, and the calendar's still carries exactly one primary.

**One thing I found that the brief did not anticipate, and it changed the design.** The calendar has
**two cursors** — the period it steps through (`date`) and the day it has open (`day`) — and its
Today resets both. So `isCurrentPeriod(...)` is *not* the same fact as "the reader already stands
where Today leads". On the 15th with the 23rd of *this* month open, the month on screen is the
current month (pill lit) and there is still somewhere to go. Wiring the control's inertness to
`current` alone would have **disabled the calendar's Today for every day of the current month you
clicked on** — a new defect introduced while fixing an old one, and one no acceptance criterion
would have caught. Hence a second optional prop, `atToday`, which **defaults to `current`** so the
planner and any future screen whose whole position is the anchor say nothing extra, and which the
calendar overrides with `isCurrentPeriod(...) && selected === today`.

**Inert rather than absent.** The brief allows either. Absent would make the calendar's `<Legend />`
— which sits after the stepper in the same flex row — shuffle sideways every time you stepped on and
off today. The control is rendered and `disabled`, so the row does not reflow.

### Why the count is 12 and not 16 — the arithmetic

**Sixteen tests touch this feature. Twelve fail without the fix. Four pass, and all four are
explained.**

| Where | Tests touching the feature | Fail under the control | Pass, and why |
|---|---|---|---|
| `planner.test.tsx` | 9 (8 new, 1 inverted) | **9** | — |
| `calendar.test.tsx` | 4 (3 new, 1 adjusted) | **3** | 1 |
| the three report tests | 3 (1 each) | **0** | 3 |
| | **16** | **12** | **4** |

The three report tests **pass vacuously**, exactly as the brief predicted. They assert that
`issued-from-store`, `vendor-performance` and `cost-per-serving` render the stepper *and* zero Today
buttons. Remove the feature and there are still zero Today buttons, so they cannot fail. They are not
holes — they are the guard against a *future* change putting a control on a report screen, and that
is a direction the control cannot travel in. (Each one also asserts the tablist and the Next-month
arrow *are* present, so a zero produced by the page failing to render would be caught rather than
read as a pass.)

The fourth pass is more interesting, and it is the strongest single thing this control says. The
calendar's pre-existing test **`moves a month at a time, and comes back to today` passes against
`HEAD`** — because at `HEAD` the calendar has its own Today in the page header, always enabled. That
test has been green throughout the entire life of the defect. It asserts a *presence* on one screen,
and a presence assertion is worth nothing against a control that goes missing from the other screen
and worth nothing against a second copy appearing beside it. That is why every test I added asserts a
**count**, on all five consumers, rather than a presence on one.

## Acceptance criteria

**1. From the planner, moved two days forward, one control returns to today in every view — day,
week and month.** `planner.test.tsx` → `comes back to today in the %s view, whatever it stepped away
by`, an `it.each` over day/week/month. Each steps **twice** with the view's own Next arrow (so the
arrows are no longer the obvious way home, which is the journey N2 describes), asserts the date has
moved off today, presses Today, then asserts `date` is back to `todayIso()` **and** that `view` is
unchanged — because "today" is a different anchor in each view and one date has to answer all three.
Failed 3/3 without the fix.

**2. The same control works on `/calendar`.** `calendar.test.tsx` → `refuses the journey only when
both cursors are already home` presses it and asserts `push("/calendar")`; the pre-existing `moves a
month at a time, and comes back to today` asserts the same through the stepper. Both pass.

**3. Exactly one Today control per screen, asserted by test on all five consumers.**
- planner: `offers exactly one of them in the %s view — not none, and not two` —
  `queryAllByRole("button", {name: /^today$/i})` has length **1**, in all three views. It also
  asserts the sidebar's Today is still there and is a **link** (a different destination — the Today
  dashboard) so it is provably not what the count found.
- calendar: `keeps exactly one way back to today, in the stepper rather than the header` — same
  count, plus `back.parentElement` is asserted to be the same node as the Previous-month arrow's
  parent, which pins the *placement* decision rather than just the existence.
- the three reports: `takes the shared stepper without taking its way back to today` — the tablist
  and the Next arrow present, Today count **0**.

**4. Absent or inert when the anchor already is the current period.** Chose inert.
- planner: `refuses the journey when the reader already stands at the end of it` — `toBeDisabled()`
  on load, `toBeEnabled()` a day forward, `toBeDisabled()` a day back. And `is inert on this week and
  this month too, not only on today itself`, because "the current period" is not only today.
- calendar: `refuses the journey only when both cursors are already home` — disabled with today
  open, and **enabled** with the 23rd of the current month open, which is the two-cursor case above.

**5. `npx tsc --noEmit && npm test` green.** `tsc` silent, 82/82 on the five files, `next build` ✓
Compiled successfully. See output above. I did not run the full `npm test` suite — the brief forbids
it; that is the release agent's run on the merged tree.

## Visible changes, flagged rather than slipped in

Three of these change a screen that is currently correct. None of them reads worse to me, but they
are decisions rather than mechanics and they should be looked at.

1. **The calendar's header Today button is gone.** It was
   `app/calendar/page.tsx:125-127`, a `<Button variant="secondary">` beside "Open the meal planner".
   Its replacement sits in the stepper. This is the deletion N2 is actually asking for when it says
   the defect has come back "for the third or fourth time" — with the control in one place it cannot
   diverge a fifth.
2. **The calendar's Today changed weight**, from `secondary` (accent text in an accent hairline) to a
   quiet `ghost` at `size="sm"`. Two reasons: it now sits directly beside the accent-tinted "current
   period" pill, where a second accent element reads as competition; and a neutral control is what
   keeps the planner's 2026-08-23 objection answered.
3. **The calendar now draws the current-period pill**, because it now passes `current`. This is not
   gratuitous — acceptance criterion 4 needs the screen to know whether the period on show is the
   current one, and the pill is that fact's existing rendering. The calendar previously had no way of
   saying whether the month on screen was this month.
4. **The calendar's Today now refuses** when the current period is on screen *and* today is the open
   day. It used to be pressable always (a no-op).

And two test-level changes worth naming:

5. **An existing planner assertion was inverted.** `planner.test.tsx` carried
   `expect(screen.queryByRole("button", { name: /^today$/i })).not.toBeInTheDocument()` with the
   comment *"No Today button on the planner in any view (Rajeev, 2026-08-23)"*. N2, re-verified on
   staging 2026-09-07, is the later instruction and says the opposite. I read the 2026-08-23
   objection as being about a competing **page action** rather than about a way back existing at all
   — see *What was decided* — and the new placement honours it. **If that reading is wrong, this is
   the line to argue about.** The half of the old assertion that still holds is kept: the middle of
   the stepper is still asserted not to be a button.
6. **`calendar.test.tsx`'s `moves a month at a time…` now calls `cleanup()`** between its two
   renders. It rendered twice into one document and then reached for `getAllByRole("button", {name:
   "Today"})[0]` — which after this change is the *first* render's control, correctly inert. Rather
   than index past it, the stale render is now torn down. Same for the deep-link half of the pill
   test.
