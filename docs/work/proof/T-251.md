## What it does

**Backend**, on `create`, and on `update` only when the stored name changes (compared trimmed):
1. **The literal same name** (case-insensitive, matching the DB index `ingredients_name_per_tenant`) still gets **KMS-400034, and `confirmDifferent` does not get past it**. The new check does NOT replace the old one: the database would refuse two rows called "Curd" whatever anyone confirms, so offering "It's a different ingredient" there would only lead to a second refusal.
2. **Otherwise**, `IngredientNameMatcher.findMatch` runs over every other ingredient in the temple, by name, by the `aliases` array and by `ingredient_aliases` rows. The row being renamed is excluded, so it can never match itself.
   - An EXACT or CLOSE match returns **409 KMS-400156**, with `fieldErrors` `existingIngredientId` and `existingIngredientName`.
   - With `confirmDifferent: true` the save goes ahead. The existing `INGREDIENT_ADDED` / `INGREDIENT_UPDATED` audit event then gets:
     - reason: `Added although it looks like “Curd”: confirmed as a different ingredient.` ("Renamed …" for a rename)
     - `after_state.confirmedDifferentFrom` = {id, name, matchedName, kind}
   - I added no new AuditAction, because `AuditAction.java` is not in my contract.
3. **`ingredient_aliases` is kept in step** on create and update:
   - one row per `IngredientNameMatcher.normalise(alias)`; two aliases that normalise the same become one row
   - rows the ingredient no longer has are deleted
   - the `aliases` array is untouched
   - A **newly typed** alias that another ingredient already holds is refused with KMS-400034, and the save rolls back.
   - An alias the row **already had** before this save, but which the V144 backfill gave to another ingredient, is let through without a row. Otherwise that ingredient could never be saved again.

**RLS**: every read is tenant-scoped by the database. No tenant id is taken from the request. Alias rows take `tenant_id` from `app.tenant_id`.

**Frontend**, one prompt component, styled like the app's `ConfirmLayer`: an `alertdialog` with the same scrim and `modal` card, and neutral colours, because it is a question. Behaviour:
- Step 1 is the spec's words: heading "Did you mean Curd?", then "Use Curd, or add a preparation note instead." Its buttons are "Use Curd" and "It’s a different ingredient", both `Button variant="secondary"` (style E, `.btn` press).
- "It’s a different ingredient" does not save. It opens step 2:
  - heading: "Keep “Curd sour” separate from Curd?"
  - body: "It will have its own stock, prices and orders. Your choice is recorded in the audit log."
  - buttons: "Go back" (secondary, and it takes focus) and "Keep it separate" (primary), which re-sends with `confirmDifferent: true`.
- Escape goes back one step at a time.
- Any other error still shows the normal ErrorNotice.

**What "Use Curd" does (my choice):**
- On `/ingredients/new` and `/supplies/new`: nothing is added, and it goes to `/ingredients?edit=<id>`. That page opens Curd's editing row and scrolls to it, so the person can add their spelling as an alias. It then strips the parameter. If the lookalike is a supply, the page sends them on to `/supplies` instead, because I could not touch `/supplies/page.tsx`.
- On the inline rename: the rename is dropped (nothing saved) and Curd's own editing row opens.

**Apostrophe:** the button reads "It’s" with a curly apostrophe, matching the rest of the app's copy ("couldn’t"). The spec wrote it with a straight one.

## Acceptance criteria

- **"Tomatos" is stopped when "Tomato, ripe" exists.** Proved by the IT (409, KMS-400156, details naming Tomato, ripe, nothing saved) and by vitest (the prompt reads "Did you mean Tomato, ripe?"). Not proved on the live screen, because the local API is down (above).
- **"Curd sour" is stopped when "Curd" exists.** Proved the same way, by the IT and by vitest on all three screens.
- **`confirmDifferent` saves and is audited.** The IT checks the row, the audit reason text and `after_state.confirmedDifferentFrom`, for both create and rename.
- **Another temple's "Curd" never matches.** The IT puts Curd, "Tomato, ripe" and the alias "Tamatar" in temple B. From temple A, creating "Curd sour", "Tomatos" and "Tamatar" is saved with no override. The same test then shows temple A's own Curd does stop "Curds".
- **An unchanged name never trips the check, and a row never matches itself.** Both have their own IT.
- **The existing KMS-400034 stays.** It is kept for the literal same name and cannot be overridden (see "What it does").
- **The negative control fails without the check.** 7 of 14 fail (above).
