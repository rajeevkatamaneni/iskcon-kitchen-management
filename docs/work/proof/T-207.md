# T-207 — Counter cash stops being a reconciliation mismatch, and a voided bill shows no variance

Phase B item 8, Rajeev's decision, which overrides T-072's old acceptance line.

**Files changed:** (all four are inside the contract)

- `backend/src/main/java/org/iskcon/kms/donation/DonationReconciliationService.java`. The query adds
  `AND provider_payment_id IS NOT NULL`, so a gift with no payment id is never selected and the
  gateway is never asked about it. The class comment explains why.
- `backend/src/main/java/org/iskcon/kms/invoice/VendorInvoiceService.java`. In `withVariance`, a bill
  whose status is `VOIDED` gets `expected = null`, which makes `variance` null too. Nothing else
  changed: the order link, amount and credits stay on the view, and a live bill is computed as
  before. I did not touch T-206's refusal in `voidInvoice` (its diff was already in the file and is
  still there).
- `backend/src/test/java/org/iskcon/kms/donation/OneTimeDonationIT.java`. Adds the test
  `reconciliationSkipsCashTheGatewayNeverSaw` and the helper `seedCash()`. The helper writes the row
  in the same shape `DonationRecorder.insertDonation` does: ONE_TIME, default status COMPLETED,
  payment_mode CASH, recorded_by set, no provider, no provider_payment_id.
- `backend/src/test/java/org/iskcon/kms/invoice/VendorInvoiceIT.java`. Adds the test
  `aVoidedBillHasNoVariance`.
- `docs/work/proof/T-207.md` (this file).

**No existing test asserted T-072's old behaviour.** The only test that calls `reconcile` is in
OneTimeDonationIT, and every gift those tests seed carries a provider_payment_id. None of them
seeds cash, so nothing needed changing. Nothing outside the contract needed a change either.

**One naming note.** The task says `expectedReceivedValue`. That is the name of the private method.
The field on the view and in the JSON is `expectedValue`, so the test asserts `expectedValue` and
`variance`.

## Acceptance criteria

- **A recorded cash gift produces no mismatch, and the gateway stub is not called for it.** Covered
  by `reconciliationSkipsCashTheGatewayNeverSaw`. It seeds a cash gift and asserts the mismatch
  list is exactly `[pay_bogus_card]`. It also checks, with Mockito, that `fetchPaymentStatus` was
  `never()` called with a null id. Green in run 1. Red in run 2 with the fix removed, when the list
  was `[null, pay_bogus_card]`.
- **A card or UPI gift the gateway does not show as captured still produces a mismatch.** Checked in
  the same test: the unrecognised gateway gift `pay_bogus_card` is still named, and the gateway was
  asked about it exactly once. The existing `reconciliationCatchesMismatch` also still passes.
- **A voided bill with a purchase order shows expectedValue null and variance null.** Covered by
  `aVoidedBillHasNoVariance`. Before the void it asserts variance 50.0, so the check cannot pass on
  a bill that never had a variance. After the void, both the single-bill read and the list filtered
  to VOIDED return neither field. The single-bill read also still shows the order link and the
  amount. Green in run 1. Red in run 2, which found `expectedValue` 1350.0.
- **A live bill's variance is unchanged.** Checked in the same test: a second bill on an identically
  priced order still lists expectedValue 1350.0 and variance 50.0. All the other variance tests
  still pass (plain, net of credits, partial credit, the order actually on the invoice).
- **Negative control for each half.** Section 2 above.
