## Sweep — every request-time read of `users`

Only `users` lets a person see their own rows at other temples. Every policy mentioning `app.auth_uid` (grep below) is either the `users` read policy (V2, V4), or uses the users row only to check who the caller is on platform tables: V9 platform audit (super-admin), V65 ban-check audit insert, V66 notices, notice dismissals (which also check the tenant) and platform audit, V68 master recipes. None of those tables holds a person's own rows at another temple. There are no views (`CREATE VIEW` grep exit=1). There is no memberships table. JPA reads on `User`: only `UserRepository` methods and `findById` in MembershipService:196 (an id just inserted at this temple) and PendingAccountClaim:109 (the pending row being claimed). No JPQL on `User`.

## RowLevelSecurityIT decision

Added `ownAccountsAtOtherTemplesAreReadableAndNotWritable`. This visibility is the design, not a policy bug:
- V2 says the escape lets sign-in find the person's row.
- V52 made it several rows on purpose.
- WhoAmIController `temples()` reads memberships through it.
- V66 says outright "a person's auth_uid may now span several memberships (V52)".

So I did not stop, and changed no policy or migration. The test pins exactly that: own rows only (a stranger at B stays invisible), readable only, and gone once the uid is cleared.

## Option not built: clear the lookup uid once the temple is chosen

`AuthenticationFilter` could drop the uid right after `TenantContext.set(...)`. Every one of these holes would close centrally, but it would break the following:
- WhoAmIController `temples()`: the switcher would show only the current temple.
- `DocumentService.requesterHere()`: it finds the author by `app.auth_uid`; zero rows would throw.
- Every policy that identifies the caller through the uid while a temple is set: V68 `master_recipes_read` (the library disappears for signed-in users), V66 `platform_notices_read`, `_raise`, `_withdraw` and `platform_notice_dismissal_own`, V65 ban-check audit insert, V66 notice audit insert.

Doing it properly needs a second, narrower setting that means "this membership" rather than "this person". That is an auth and migration change, far bigger than T-190.

- **Sweep of request-time reads.** Listed above with file:line and reason. Only `users` has the own-uid branch, and there are no views (grep).

- **Negative control.** Run 3: the patch was proven applied (cmp differ, anchor 1→0), the test went red, and the restore was proven (cmp identical, anchor back to 1).
