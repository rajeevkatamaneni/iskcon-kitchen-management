The rule:

```css
input[aria-invalid="true"],
select[aria-invalid="true"],
textarea[aria-invalid="true"] { border-color: rgb(var(--kms-danger) / 1); }
```

**The token used:** `--kms-danger`. Tailwind compiles `border-danger` to
`--tw-border-opacity:1; border-color:rgb(var(--kms-danger) / var(--tw-border-opacity))`. I checked
this by compiling globals.css with the Tailwind CLI into the scratchpad. The rule resolves to the
same value.

One correction to the scoping note. It said a rule on the hex `--danger` would ignore a temple's pack.
It would not: `applyPalette` in `lib/theme.ts` writes both `--kms-<token>` and `--<token>` from the
same pack. Both follow the pack. I used `--kms-danger` anyway, as asked, so that "the same colour as
`border-danger`" holds by construction.

**What the rule does and doesn't touch:**

- It sets only `border-color`. Width and style stay with the box: the base `1px solid`, or a
  `border` utility. A `Field` in error gets the same colour from two places. There is no double
  border and no width change.
- Its specificity is 0,1,1. That beats a single colour utility (0,1,0) such as
  `border-hairline-strong` in any layer order, which is what makes it reach hand-rolled boxes.
- A box that isn't refused doesn't change. `Field` writes `aria-invalid="false"` and unmarked boxes
  have no attribute, so neither matches.
- A focused refused box keeps its red 1px edge. The `:focus-visible` outline (2px `--focus-ring`, 2px
  offset) draws outside the red edge. The rule sets no outline and no shadow.
- One exception, outside my contract, left alone. The WhatsApp composer textarea
  (`app/communications/composer.tsx:240`) has `outline-none focus:border-accent-border`, which is
  0,2,0. While focused, that box shows its accent border instead of red, and returns to red on blur.
  That is the box's own focus style winning, and it stays visible.

**Acceptance criteria:**

1. **A test that fails without the rule.** `invalid-border.test.ts` strips comments from
   globals.css, parses every innermost `selectors { declarations }` block, and asserts four things:
   - `input`, `select` and `textarea` are each covered by an `[aria-invalid="true"]` selector.
   - Each one's `border-color` equals the `danger.DEFAULT` value read from `tailwind.config.ts`, with
     `<alpha-value>` set to 1. That value is `rgb(var(--kms-danger) / 1)`.
   - The rule declares nothing but `border-color`: no width, outline or shadow.
   - No `aria-invalid` selector anywhere matches anything but `"true"`.

   Why a source test is enough: jsdom never applies globals.css, so a rendered check would prove
   nothing. The ways this can break are all visible in the source: the rule deleted, an element
   dropped, the token changed, or the rule touching width or focus. The cascade itself is browser
   behaviour. The Tailwind compile above shows the rule reaches the built CSS.
2. **Negative control.** Done as specified. It went red (3 of 5), and the restore was proven with
   `cmp`. The log is quoted above.
3. **Runs through the lock.** tsc, the test file, the full vitest run and eslint all pass.
4. **Browser.** Not driven. I had no local app running with a signed-in form, and staging was off
   limits. Not smoke-tested by hand.
