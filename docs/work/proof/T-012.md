together, behind `VOID_DONATION` (Temple Admin alone, D-4).

## Acceptance criteria

**1. Void reverses the stock and marks the donation in one transaction; a failure in either half
rolls back both. Real database, under RLS.**
`DonationVoidIT.voidsTheGiftAndTheStockTogether` records 5 Kg of rice through the real intake
endpoint, voids it, and asserts the mark (`voided_at`, `voided_by` = the admin's own user id,
`void_reason`), that `SUM(to_base_qty(...))` for the ingredient is back to `0`, and that exactly one
`CORRECTION` movement points at the original `DONATION` movement.

`bothHalvesRollBackTogether` is the atomicity proof. A `@SpyBean` on `StockMovementService` makes
`compensate` throw; the request answers 5xx and the donation is **not** marked (`voided_at` null,
`void_reason` null), the stock is still 5000, there is no correction row and no `DONATION_VOIDED`
audit entry. This test is only meaningful because the service marks the donation **first** and
reverses stock **after** — written the other way round the mark would never have been attempted and
the test would pass proving nothing. That ordering is commented in the service as the reason it is
that way round.

**2. The voided gift is excluded from the 80G period summary and stays in the ledger, marked.**
`leavesTheFiguresAndStaysInTheLedger` asserts `$.byCategory.IN_KIND.total = 2500` **before** the
void and `$.byCategory.IN_KIND` `doesNotExist()` after — before *and* after, because an empty tile on
its own is the same answer a temple that received nothing would get. The same test then reads the
ledger and finds the gift still there with `voided: true`, its `voidReason`, and `status` still
`COMPLETED` (status is deliberately untouched: it says how the payment went, and a gift can complete
and then be voided).

Two further places the same rule had to be applied, both inside the contract and neither in the
brief:
- **`MonetaryDonationService.form10bdRows()`** — the literal Form 10BD dataset, the 80G filing the
  tiles are only a preview of. It filtered on `status = 'COMPLETED'` alone, so a struck gift would
  have gone to the tax authority with the donor's name and PAN against it. Now `AND voided_at IS NULL`.
- **the CSV export** — where the figures leave the application. A struck row stays in the file (so
  the export and the screen agree row for row) but now carries `Voided` = `Yes` and a `Void reason`
  column beside it. A spreadsheet has no badges, and a row reading like every other one while the
  tiles say a different total is how a wrong number gets filed. Asserted in the same test.

`earliestGift()` deliberately does **not** filter voided gifts, and says so in a comment: it answers
"do this temple's books reach back that far", not "how much did it receive". Excluding a struck gift
there would tell a temple with three years of books that it had nothing to compare against, on the
strength of one correction.

**3. A second void returns KMS-400134.**
`aSecondVoidIsRefused` — `409`, `$.code = KMS-400134`, and then the assertions that say why the
refusal matters: still exactly one correction, stock still `0`, one `DONATION_VOIDED` entry. Note the
deliberate divergence from `StaffPayService.voidPayment`, which returns quietly on a second call:
this one moves goods, and a silent success would leave somebody believing a second reversal happened.

**4. Temple Admin only.**
`onlyATempleAdminMayVoid` — Kitchen Manager `403`, Kitchen Staff `403`, and after both refusals the
donation is still unmarked and the stock still 5000; the same admin then succeeds with `204`.
`RolePermissionsTest` gains the five-row block (admin allowed; manager, staff, volunteer and
super-admin denied) — the test file only; `RolePermissions.java` was not opened.

**5. Audited under `DONATION_VOIDED`, and the stock half under `STOCK_MOVEMENT_CORRECTED`.**
Asserted as exactly one of each in `voidsTheGiftAndTheStockTogether`. Two entries for one act, which
is what `AuditAction`'s own doc comment asks for.

On the audit snapshot: the **after-state is read back out of the row** after the UPDATE, never
rebuilt from the request — the wave-4b lesson, and it is commented as such in
`DonationVoidService.after(...)`. The before-state likewise comes from the `SELECT ... FOR UPDATE`,
not from anything the caller sent. Money is stringified with `toPlainString()` so a scale difference
cannot make the trail claim a figure moved when it did not.

## Decisions I made, and the one the brief asked for

**A donation carrying equipment lines: the gift is voided, the food reversed, and the equipment is
left standing in the register.** Asserted as a test —
`equipmentStaysInTheRegister` — so it is a decision on the record rather than something a later
reader discovers.

Why not refuse such a donation, which was the other option offered: **refusing needs an error code
and I have exactly one**, `DONATION_ALREADY_VOIDED`, which does not mean this. Reusing
`VALIDATION_FAILED` would put a refusal on screen with no plain-language sentence and no next step,
against Commandment 4 — and the only honest next step would be "there is no door", which is exactly
the failure `StaffPayService`'s own comment records having to undo ("an error message pointing at a
door that does not exist"). Refusing would also leave the 80G figure permanently wrong to protect a
register entry a Temple Admin can already correct by hand, which is the wrong trade for the defect
this task exists to fix. So the screen names the consequence in words before the button is pressed —
"Anything it brought that was registered as equipment stays in the register — take it out there if it
was never given" — and the equipment row keeps its `donation_id`, still pointing at a donation the
ledger now shows as voided, so the two are reconcilable by anybody who looks.

**The endpoint is not restricted to hand-recorded gifts, and this is worth Rajeev's eye.** The task
is written about hand-recorded gifts, but a provider-recorded (Razorpay) donation can also be voided
by this endpoint. I did not restrict it because restricting requires refusing, refusing requires a
code, and I have none — and because a gateway gift duplicated by a webhook glitch is a real case with
no other cure. The act is Temple-Admin-only, demands a written reason and is audited, so nothing is
silent about it. If Rajeev wants it narrowed to `provider IS NULL`, that is one clause plus one new
error code, and it should be his call rather than mine.

**Not idempotent, unlike the staff-payment void.** Stated above and commented in the service.

**Reason required in three places**, deepest first: a CHECK on the column, `@NotBlank` on the
request, and a commit button that stays refused until there are words in the box. The last is the
kindest and the first is the one that cannot be got round.

**The Void control is withheld on a row already marked, rather than offered and refused.** Same call
and the same reasoning as the Correct control on the inventory ledger (Rajeev, 2026-09-07): the
screen is holding the server's answer already, and making somebody write out a reason before being
told it was already done is work asked for and thrown away. The 409 path is still reachable and still
tested — server-side by `aSecondVoidIsRefused`, and on screen by the test that puts the server's own
sentence in the dialog for the two-tabs race.

## Not done / needs Rajeev

outside my contract.** `WishlistService.java:141-142` and `:182-183` compute an item's progress as

is for the UAT pass.

**5. Two things a reviewer should look at with fresh eyes**, because they are judgement rather than
mechanism: the CSV gaining two columns (`Voided`, `Void reason`) changes a file an accountant may
already have a template for; and the decision to skip, rather than refuse, a stock movement somebody
had already corrected by hand before the donation was voided. The second is commented at length in
`DonationVoidService.reverseGoods` — the shelf is already where it should be, and letting
`MOVEMENT_ALREADY_CORRECTED` out would leave the 80G figure permanently inflated while explaining why
in terms of a stock movement to somebody who was striking a donation.
