# T-041 — the temple edit screen narrows to name, address and 80G, and the calendar-rebuild path goes with it

D-17 applied end to end: latitude, longitude, timezone and currency are displayed and not offered
on `/tenants/[id]/edit`, refused at the service if a caller changes them anyway, and the
`CalendarPrecomputeScheduler` re-queue that existed only to make an editable timezone safe is gone.

## What was built

**Frontend.** `TIMEZONES`, `CURRENCIES` and `optionsFor(...)` are deleted with the pickers they fed.
The four frozen fields, plus the web address that was already read-only, are rendered as a `<dl>` of
label/value pairs in a new "Fixed when the temple was created" section — the same presentation the
temple's own page uses for its details, so what cannot be edited does not read as a field somebody
greyed out. **There are no disabled inputs**: a disabled control submits nothing, which would have
sent four nulls to an endpoint that requires all seven fields.

The payload still carries all seven. The frozen four are **read off the loaded `temple` record**
rather than carried in hidden inputs, and the reason is written into the code: a hidden input would
put the values back into the form only for the handler to take them out again through `FormData`,
with two failure modes worth avoiding — `latitude` would round-trip through `Number()` so a lost
value would arrive as `0` rather than as an error, and a hidden field is editable from a devtools
panel, which is exactly the offer this screen has just stopped making.

Layout note, since there was no mockup for this and D-17 rules on fields rather than on sections:
the 80G tick moved out of "Where it's located" (where it had been sitting for want of anywhere else)
into the first section, now headed "What can be changed", so the screen reads as three editable
things followed by five fixed ones. Raising it here rather than after the fact, per Commandment 6.

**Backend.** `TenantUpdateService` loses `reprecomputeCalendar`, the `CalendarPrecomputeScheduler`
field, its constructor parameter, its import and the doc paragraphs describing the rebuild; the class
javadoc is rewritten around what the endpoint is now for. In its place `rejectFrozenFieldChanges`
mirrors `rejectSlugChange`: the four fields stay declared on `UpdateTenantRequest` and are refused
only when they **differ** from what is stored. Both the service and the DTO say in prose why they are
declared rather than removed (Jackson drops an unknown property in silence and tells the caller the
save worked) and why each field is frozen (a building does not move; a currency changed after money
is recorded shows invoices, payments and donations in a currency they were never in; a temple that
cannot move cannot change timezone either).

Every offending field is collected before throwing, so a caller sending a wholly stale record is told
about all four at once rather than discovering them one save at a time.

**The `BigDecimal` trap** is handled with `compareTo(...) == 0` in `numberChanged(...)`, comparing the
stringified stored value (`"12.971600"`, from `loadSnapshot`) against the request's `BigDecimal`
(`12.9716`). `equals` would have called those different and made the screen unsaveable. Proved by
`savingTheRecordBackUnchangedSucceeds`, which sends latitude at a *third* scale again
(`12.97160000`) so the assertion is about the value and not about two renderings happening to match
— and by the whole file, since `validUpdate()`'s latitude is deliberately shorter-scaled than the
column.

`validateTimezone` was kept, ahead of the freeze check, so a zone that is not a zone at all is still
refused for what it is rather than for differing from a value it could never have matched. It is now
belt-and-braces rather than the primary gate.

**Ordering matters and is deliberate**: slug first (its presence alone is the fault), then
`loadSnapshot` (so a temple that does not exist is a 404, not a refusal listing fields nobody can
compare), then the frozen-field check, then the write.

## Acceptance criteria

**1. The four frozen fields are visible, with no control offering to change them.** Verified by
`shows the location, timezone and currency, and offers no way to change them`, which asserts the four
values are present as text and then that they are absent as controls three ways over — by label, and
by `queryAllByRole("combobox")` / `queryAllByRole("spinbutton")` across the whole screen, which is
what would catch a disabled `<select>` or number input left behind.

**2. A `PATCH` changing any of the four is refused with a field-level message.** `refusesAChangedTimezone`,
`refusesAChangedLatitude` and `refusesAChangedCurrency` each assert `KMS-400001`,
`$.fieldErrors[0].field`, a message containing "can't be changed", and that the column did not move.
`refusesAChangedLatitude` also asserts the name is untouched — a refused request writes nothing at
all, not the fields it happened to like. `refusesEveryFrozenFieldItWasSent` asserts all four come
back in one response.

**3. A `PATCH` repeating the stored values, including a differently-scaled latitude, succeeds.**
`savingTheRecordBackUnchangedSucceeds` (`12.97160000` against a stored `12.971600`), plus every other
passing test in the file, all of which send `validUpdate()`'s shorter-scaled `12.9716`.

**4. Name, address and 80G still save and are still audited.** `correctsEveryEditableField` asserts
all three columns, asserts the four frozen columns came out unchanged, and asserts the *other* temple's
name is untouched — a `WHERE` clause lost from that `UPDATE` would rename every temple on the platform
and nothing else here would notice. `writesAnAuditEvent` asserts `TENANT_UPDATED` on the temple's own
log, actor `SUPER_ADMIN`, before/after states, and that the untouched latitude still reads
`"12.971600"` on both sides.

**5. No reference to `CalendarPrecomputeScheduler` in the tenant package or its tests** — with one
exception I could not and should not remove. `grep -rn CalendarPrecomputeScheduler backend/.../tenant/`
returns only `TenantProvisioningService.java:34,40`. That is **provisioning**, not update: a brand-new
temple has no calendar at all until it is enqueued, so that call must stay. It is also outside my
contract. Nothing in `TenantUpdateService` or `TenantUpdateIT` refers to it.

**6. `tsc --noEmit` silent, targeted tests green.** Output above.

## The typo hole, stated plainly

**A provisioning typo in a temple's coordinates can no longer be corrected through this screen or
through this API.** Neither can the timezone or the currency. This is a decision, not an oversight:
D-17 rules that a coordinate error big enough to change the calendar — wrong city, transposed digits,
wrong hemisphere — is big enough to be obvious immediately, that an error small enough to go unnoticed
shifts sunrise by seconds and moves no tithi, and that a typo caught during onboarding costs nothing
because the temple has no data yet: delete it and create it again. The reasoning is written into
`TenantUpdateService`'s class javadoc and into the edit page's, so a future reader meets it where they
would meet the restriction.

D-17 also records the better fix Rajeev asked for and it is **not** built here: geocode the address at
provisioning and confirm the pin on a map, using the `GeocodingProvider` / `NominatimGeocodingProvider`
already in the tree. That belongs to `/tenants/new`, which another builder is in this wave.
