## The negative control — inverted, because this wave removes a guard

### (a) The garlic control: a recipe naming garlic now saves, and imports, and gets ordered

**`RecipeIT` › "a recipe naming garlic saves like any other, with no reason and no override (D-18)"** — new.
Signs in as **kitchen staff** (the role the block bit hardest, having no override at all), creates an
ingredient literally called Garlic, and `POST /api/v1/recipes` with it. Before D-18 that call was
`409 KMS-400037` for anyone without `OVERRIDE_SATTVIC_ENFORCEMENT` and a written reason. It now
returns `201`, the recipe reads back unbadged, and no override audit event exists. Passes.

Corroborated from the log of the same run: `RecipeIT` emitted `KMS-400001`, `KMS-400030` and
`KMS-400036` from its other cases and **no `KMS-400037` anywhere in the suite** — the code is retired
and nothing throws it.

**`ShoppingListIT` › "what used to be a sattvic-prohibited ingredient now enters via the threshold
stream"** — the exact inverse of the deleted assertion. Garlic has an inventory row with a reorder
threshold of 5 KG and 1 KG on hand; regeneration now produces a line for it —
`thresholdTopUp = 5` (5 × 1.2 safety = 6, less 1 on hand), `shortfall = 0` (no meal plan asks for
it). It asserts presence, so it is **not** vacuous.

This rippled into three sibling tests and I want that on the record rather than buried: the list is
`ORDER BY i.name`, so Garlic now sits at index 0 ahead of Rice, and `mergesStreamsWithProvenance`,
`editsSurviveRegeneration` and `editWithoutVendorKeepsTheSuggestedVendor` all had to move their Rice
assertions from `$[0]` to `$[1]`. Each now asserts `$[1].ingredientName == "Rice"` first, so a
future reordering fails loudly instead of silently checking the wrong row. `mergesStreamsWithProvenance`
also went from `$.lines == 1` to `$.lines == 2` — **which is itself the strongest evidence here**:
the pre-change test asserted exactly one line and would fail against this code.

**`RecipeLibraryIT` › "an import naming an ingredient the temple already holds no longer has a
refusal to make"** — the inverse of `refusesProhibited`. With `Curd, fresh` in the catalogue,
importing Majjige used to be `409 KMS-400104` with nothing written; it is now `201`, one recipe
exists, the pre-existing row was matched on `lower(name)` rather than duplicated, and the rest of
the recipe's ingredients were created around it — **all of them with `is_ekadashi_prohibited` false**,
which is the coverage gap D-18 chose to warn about rather than close.

One honest limit: the shared library contains **no ingredient named garlic, onion, mushroom or egg**
— I checked all 33 state files; the only matches are prose ("no onion, no garlic") and the two
ingredient names "Onion-free chaat masala" and "Garlic-free panch phoron", both describing an
absence. So the import control uses `Curd, fresh` as the old test did, for the same reason the old
test did. The direct "recipe naming garlic" case is the `RecipeIT` one above, which is the same
service-layer block from the other door.

**`IngredientIT` › "the sattvic-flag endpoint is gone, not merely inert (D-18)"** — new, and the
piece the other three cannot show: `PATCH /api/v1/ingredients/{id}/sattvic-flag` returns **404**.
Nothing can put an ingredient back into the state the deleted enforcement read. An endpoint left in
place as a no-op would have answered `204` and changed nothing, which is the outcome this asserts
against.
