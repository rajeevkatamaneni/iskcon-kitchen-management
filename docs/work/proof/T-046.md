# T-046 — a refused attempt to end your own employment is recorded

`StaffEmploymentService.endEmployment`'s self-guard now writes a `STAFF_EMPLOYMENT_END_REJECTED`
event through `AuditService.recordSeparately` before it throws `CANNOT_DISABLE_SELF`, so the record
of the attempt outlives the rollback the 403 causes. This was the second of `requireNotSelf`'s two
call sites; T-039 closed the first and reported this one as a finding.

## What was built

**1. The refusal is recorded.** `requireNotSelf(actor, before, ErrorCode.CANNOT_DISABLE_SELF)` in
`endEmployment` is replaced by a new private `requireNotEndingOwnEmployment(actor, before, request)`,
which runs the same self-test and, when it fires, writes through `AuditService.recordSeparately` —
on its own transaction — before throwing the identical
`ApplicationException(CANNOT_DISABLE_SELF, Map.of("staffId", …))`. The error code, its detail map,
the 403 and the order of the guards relative to the `isFormer` validation are all byte-for-byte what
they were, so nothing about the refusal a caller can see has changed.

The event mirrors the act it refused rather than the sibling guard: action
`STAFF_EMPLOYMENT_END_REJECTED`, entity type **`STAFF_MEMBER`** and entity id the **staff profile**,
exactly as `STAFF_EMPLOYMENT_ENDED` is filed, with the same before/after shape
(`employmentStatus`, and on the after side `lastWorkingDay` and `signInRevoked`). That differs from
T-039's `ROLE_CHANGE_REJECTED`, which is filed against the `USER` because `ROLE_CHANGED` is — each
refusal sits where a reader would look for the act it refused. The whole `EndEmploymentRequest` is
passed in rather than loose fields so the record carries `signInRevoked`: an attempted resignation
and an attempt to take one's own login away are not the same attempt.

`entity_id` is `NOT NULL` (`V3__audit_events.sql:85`) and the staff profile id is non-null on every
path that reaches the guard, so unlike T-039's `ROLE_CHANGED` write this one has nothing to rely on.

**2. `requireNotSelf` is gone, deliberately, and this is the one thing to look at in review.**
T-039's proof says "still takes an `ErrorCode` parameter although it now has one caller. That is on
purpose … Do not 'simplify' it away", and gives the reason in the same breath: the remaining caller
refuses ending one's own employment and *that refusal is not yet recorded*. This task records it, so
that caller is gone too and the method had **zero** callers left. I removed it rather than leave an
unreachable private static whose javadoc describes a gap that no longer exists — that javadoc would
have actively misled the next person in the file. The two live guards,
`requireNotChangingOwnAccess` and `requireNotEndingOwnEmployment`, are kept as two named methods
rather than merged behind a shared helper: they refuse different acts, file them under different
actions against different entities, and a single guard could only serve both by being handed
everything either might need. The cross-references in `requireNotChangingOwnAccess`'s javadoc were
updated to point at the new sibling instead of the deleted method (a `{@link}` to a method that no
longer exists is a doclint break, not just a stale comment).

**3. One frontend line.** `ACTION_LABELS` gains
`STAFF_EMPLOYMENT_END_REJECTED: "Employment end refused"`, placed under its closest sibling
`ROLE_CHANGE_REJECTED: "Role change refused"` and matching its register, so the entry reads as a
label rather than as `STAFF_EMPLOYMENT_END_REJECTED` in capitals through the
`ACTION_LABELS[action] ?? action` fallback. No other change to that file. Note for the reviewer, in
case it is a deviation somebody wants back: "Employment end refused" keeps the sibling's
noun-phrase-plus-refused shape at a small cost in fluency — "Ending employment refused" reads better
in isolation but breaks the parallelism of the filter list. I took the brief's instruction to match
the register literally; it is a one-word change if Rajeev prefers otherwise.

## Acceptance criteria

1. **An integration test attempts to end one's own employment through the endpoint, asserts the
   refusal, and asserts the audit row exists after the 403, on the real database under RLS.** —
   `StaffEmploymentIT.refusedSelfEmploymentEndIsRecorded`, PASSED. It goes through
   `POST /api/v1/staff/members/{id}/end-employment` via MockMvc, not through a service call, so
   there is a real committed transaction to roll back. The admin hires their own record at
   `TEMPLE_ADMIN`, then submits `{"status":"RESIGNED","lastWorkingDay":"2026-06-30",
   "revokeSignIn":true}` against it — the full locked-out-of-itself case. Asserts 403 with
   `KMS-400024`; that `users.role` is still `TEMPLE_ADMIN` and `users.status` still `ACTIVE`; that
   `staff_profiles.employment_status` is still `ACTIVE`; and then reads the surviving row for
   `entity_type = 'STAFF_MEMBER'`, `entity_id` = the staff record, `actor_user_id` = the admin,
   `before_state->>'employmentStatus' = 'ACTIVE'`, `after_state->>'employmentStatus' = 'RESIGNED'`,
   `after_state->>'signInRevoked' = 'true'`, and a reason containing both "their own employment" and
   the staff record's id.
2. **Both counts, not either alone.** — same test: `countOf("STAFF_EMPLOYMENT_ENDED")` is **zero**
   (the request's own transaction really did roll back) and `countOf("STAFF_EMPLOYMENT_END_REJECTED")`
   is **one** (the refusal survived it). One write gone and one write kept, out of the same request;
   either number on its own would also be produced by a transaction that never rolled back.
3. **Ending somebody else's employment still works and still audits as `STAFF_EMPLOYMENT_ENDED`,
   with no refusal row.** — `StaffEmploymentIT.endingEmploymentKeepsThePerson`, PASSED, which now
   also asserts `STAFF_EMPLOYMENT_ENDED` = 1 and `STAFF_EMPLOYMENT_END_REJECTED` = 0 immediately
   after the 204. Its existing assertions (the person drops back to `VOLUNTEER` and stays `ACTIVE`,
   the register moves them to `former`, the record is no longer editable) are untouched and still
   pass.
4. **The 15 tests T-039 left green stay green.** — all 15 PASSED, unmodified except for the two
   added count assertions in `endingEmploymentKeepsThePerson`. 16 total, 16 passed, 0 failed.
