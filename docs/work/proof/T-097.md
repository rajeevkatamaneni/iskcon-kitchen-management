# T-097 and T-063 — a send stops asking the temple's name once a head (1,833 statements → 1,287); and the six-decimal promise moves into the port, where a provider that does nothing still keeps it

**Both headlines, first.**

**T-097.** A 40-person send sent **1,833** SQL statements and now sends **1,287**. The temple's name
cost **560** of those and now costs **14**. **The ledger's "400 identical queries" was wrong in
mechanism as well as in magnitude: it is fourteen statements per recipient, not one** — every call
borrowed its own pooled connection and paid `TenantAwareDataSource`'s eight `set_config` plus five
`RESET` on top of the query. A 400-person send spent about **5,600 statements** learning a name that
cannot change while the loop runs; it now spends 14. The fix is a local variable and one parameter
on `queueFor`. **No memo, no cache, no `TransactionSynchronization`.**

**T-063.** The six-decimal rounding moved out of two identical private methods and into
`GeocodingProvider.Coordinates`'s compact constructor. The acceptance criterion is demonstrated in
both directions: a deliberately naive provider that does nothing about precision gets `12.285518` on
the fixed tree and `12.285518000000001` on the reverted one — **while all six of T-059's original
tests pass on both.** That is precisely the statement *"the old arrangement was never broken, it was
unenforceable."*

## What was wrong, and the mechanism, because the mechanism is the part that gets under-estimated

The ledger's row reads: *"`templeName()` runs inside `queueFor`, so a 400-person send makes 400
identical queries, each now costing a connection checkout because the tenant `set_config` runs on
checkout."* It has the clue and stops one step short of following it through.

`templeName()` was a bare `jdbc.queryForObject` called from the line that builds each recipient's
message parameters. `send()` **deliberately holds no transaction across its loop** — T-094 split it
that way so that one devotee the relay refuses does not abandon the other 399 — so nothing was
holding a connection and **every call checked one out of the pool**. `TenantAwareDataSource` stamps
every checkout with **eight `set_config`** and clears it on return with **five `RESET`**. So one
lookup was **fourteen statements, not one**, and the recorder shows it directly:

## What was built

`queueFor` takes the name as a parameter; `send()`, `retryWithin()` and `sendTest()` each read it
once and hand it over. Three call sites, one parameter. `templeName()` itself is unchanged.

### Why there is no memo, stated once and enforced by there being nothing to enforce

> The name lives in a **local variable**, from the line that reads it to the end of the loop that
> uses it, and there is nothing to discard because nothing outlives the send that computed it.

- **Not a field, not a static, not a `ThreadLocal`, not a transaction resource.** Nothing is bound
  anywhere, so nothing can leak onto the next request borrowing this pooled thread, and no temple
  can be handed a value computed for another. The tenant-isolation question this project asks of
  every cache **does not arise**, rather than being argued away.
- **A transaction-scoped memo would have been actively wrong here**, and not merely
  over-engineering. T-141's pattern binds to the current read-only transaction; `send()`
  deliberately holds no transaction across its loop, so there is nothing to bind to. Copying that
  pattern into this place would be cargo-culting the wrong half of it.
- **Staleness is not a question either.** The value is read after `recordSend` has committed and
  used within the same loop; the temple's own name cannot change inside it.

`templeName()` now carries a javadoc saying **never call this inside a loop over recipients**, with
the fourteen-statement reason written out, so the next person to reach for it in a loop is told why
not at the point of reaching.

## The pinning tests, and which side of the fix they are on

`CommunicationSendStatementCountIT` was written first as a **measurement**, pinning the defect's own
figures — correct while nobody could fix it, wrong the moment I became the person fixing it. It now
pins the fixed behaviour, and its class comment says so in as many words, because **a test that pins
a number is worthless unless a reader can tell whether the number is the thing being kept or the
thing being removed.** The comment carries the before-figures too, so the history is not lost.

- `theTempleNameIsLookedUpOnce` — 1 real lookup, 14 statements, 1,287 for the whole send. Three soft
  assertions, so a failure reports all three.
- `theCostDoesNotScaleWithTheAudience` — **kept, and it is the control that matters.** It halves the
  audience and requires the count **not to move**. Before the fix it read 280 against the other
  test's 560: a straight line through the origin. A fix that merely made the per-recipient lookup
  cheaper would pass the first test's spirit and fail this one.

**Forty recipients and not one, deliberately.** At one recipient a hoisted lookup and a
per-recipient one are the same single query — the wave-D false green in its exact shape.

# T-063 — the precision promise belongs to the port

## First: the brief called this "payment providers". It is not. Naming the packages, as asked.

**There is no rounding promise in any payment provider.** `org.iskcon.kms.payment` holds
`PaymentGateway`, `RazorpayPaymentGateway`, `StubPaymentGateway`, `RazorpayGatewayFactory` and the
webhook machinery; **none of them rounds anything**, and money here is `BigDecimal` at a scale the
column fixes.

**The real package is `org.iskcon.kms.geo`**, which the ledger's own row for T-063 says; the
coordinator has confirmed the "payment" framing was a paraphrase of that row going wrong. The
providers are:

- `GeocodingProvider` — the port, carrying `record Coordinates(double latitude, double longitude)`.
- `GoogleGeocodingProvider`, `GooglePlaceSuggestionProvider` — the two implementations that each
  held a private `sixDecimals(double)`.
- `NoGeocodingProvider`, `NoPlaceSuggestionProvider` — the deployments with no map service.

## The promise, quoted, from where it is written down

`docs/CHANGELOG.md`, the entry for the release that carried T-059:

> **Separately, a coordinate picked from Google is cut to six decimals** where the reply becomes a
> `Coordinates`, in both providers behind the port … Six is not a preference: `tenants.latitude` has
> been `NUMERIC(9,6)` since V1 and `meal_plans.delivery_latitude` since V88, so six decimals is what
> the database was always going to keep, and the cut makes the number an operator confirms and the
> number a row holds the same number.

And T-059's own proof records the defect this task closes, in its author's words:

> **One thing I could not avoid duplicating.** `sixDecimals` is a five-line private static in each
> [provider].

## What each provider did before, checked rather than assumed

Both held **character-for-character identical** four-line methods:

```java
private static double sixDecimals(double degrees) {
    if (!Double.isFinite(degrees)) {
        return degrees;
    }
    return BigDecimal.valueOf(degrees).setScale(6, RoundingMode.HALF_UP).doubleValue();
}
```

`GooglePlaceSuggestionProvider` called it at `:138–139`, `GoogleGeocodingProvider` at `:203–204`.
Both were correct. **The risk was never that a provider was wrong; it was that the promise lived
nowhere, so a third provider would keep it only by remembering to.** That is why this is not the
"drop it, the risk is theoretical" case the brief offered: the criterion is about the future, and
the future is a `NoGeocodingProvider` that already exists and a third service wired in later.

## What was built

**A compact constructor on `GeocodingProvider.Coordinates`** that rounds both degrees to six
decimals and hands back anything non-finite untouched, so the record never raises — every provider in
the package promises that a bad reply from a map service is an empty answer and never an exception,
and that promise would otherwise have been broken from inside the record they answer with. The two
private copies are deleted and both call sites hand the raw `asDouble()` straight in.

**A compact constructor, not a static factory, and the ledger is right that this is the decision.** A
factory leaves `new Coordinates(...)` reachable and therefore enforces nothing — the arrangement
being replaced, wearing a different hat.

### The four-package behaviour change, and the claim the ledger asked me to test rather than assume

| Construction site outside `geo/` | Built from | Rounding is |
|---|---|---|
| `meal/MealPlanService.java:1042` | request parameters (`travelEstimateFor`) | **a real change** — see below |
| `meal/MealPlanService.java:1122` | `meal_plans.delivery_latitude/longitude`, `NUMERIC(9,6)` | a no-op |
| `meal/MealPlanService.java:1134` | the same columns, after a re-geocode | a no-op |
| `meal/MealPlanService.java:1256` | `tenants.latitude/longitude`, `NUMERIC(9,6)` | a no-op |

**Two ledger errors, both found by grepping the tree rather than reading the row.**

1. **There are four construction sites, not three.** The row names `:1042`, `:1122` and `:1134` and
   misses `templeCoordinates()` at `:1256` — which is the origin of every delivery estimate the
   application makes.
2. **`tenant/` and `document/` do not construct a `Coordinates`; they only read one.**
   `MembershipService:87`, `TenantController:107`, `TenantUpdateService:298` and
   `JobCardService:509` all take one somebody else built, so nothing in either package changes at
   all. The row's "readers in `tenant/` and `document/`" is right about them being readers and wrong
   about that mattering.

`:1042` is the one the row said to check hardest, and rightly — it is the only site building from a
parameter rather than a column. What it does with the result is hand it to
`travelTimeProvider.drive()` and throw it away; **nothing built there is ever stored.** Its
coordinates come from a suggestion the picker resolved, already six decimals before this change. The
worst case is a hand-made request carrying more precision getting a route for a point eleven
centimetres away.

The no-op claim is tested rather than asserted — `aCoordinateFromAColumnIsUntouched` runs eight
values a `NUMERIC(9,6)` column can hold through the constructor and requires them back unchanged.
**Honest note: that test passes on the unfixed tree too**, because it is a claim that nothing
changed. It is evidence the change is safe, not evidence it was needed.
