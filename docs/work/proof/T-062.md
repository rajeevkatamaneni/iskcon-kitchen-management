# T-062 — CI's intermittent backend OOM measured, explained, and given a floor it cannot fall through

The test JVM had no `-Xmx`, so it ran on Gradle's built-in **512 MB** test-worker default. The
suite's live set is **446 MB compacted / 886 MB uncompacted** and climbs across the run. It was
passing with ~66 MB of headroom on a good day. That is the whole condition.

`backend/build.gradle.kts` now states a **2 GB** ceiling, prints it on every run, and names heap
exhaustion in the summary when it happens instead of leaving it disguised as a code failure.

## Two corrections to the brief

1. **The task named `backend/build.gradle`; it is `backend/build.gradle.kts`.** Already caught by
   the dispatcher. Confirmed: no `maxHeapSize`, `forkEvery`, `maxParallelForks` or `jvmArgs`
   anywhere in it before this change.

2. **"A GitHub-hosted runner has a hard ceiling you do not control" is not what was capping this,
   and the trade the brief warned about does not exist here.** The 512 MB was *Gradle's own
   default for a test worker*, not the machine's. Proved three ways: the DSL property reads
   `null`; there is no `gradle.properties` and no `GRADLE_OPTS`; and the JVM's own ergonomic
   default on a 16 GB host is 4 GB, yet the heap never went past 512 MB.

   ```
   PROBE :test: maxHeapSize=null minHeapSize=null forkEvery=0 maxParallelForks=1 jvmArgs=[]
   PROBE :test allJvmArgs=[-Dfile.encoding=UTF-8, -Duser.country=US, -Duser.language=en, -Duser.variant, -ea]

   $ java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
      size_t MaxHeapSize    = 4294967296     {product} {ergonomic}
   ```

   The repo is **public**, so `ubuntu-latest` is a 4-vCPU/16 GB runner. Raising the worker to 2 GB
   leaves ~14 GB for the Gradle process, Docker and one Postgres container. There is no container
   limit being traded for a kernel kill.

## What is actually accumulating, with the numbers

### It is context proliferation — and worse, the contexts are never released

87 of the 88 integration classes that declare a nested `StubVerifierConfiguration` declare a
**byte-for-byte identical** one, and `@Import` their own copy:

```
$ grep -rl 'class StubVerifierConfiguration' backend/src/test/java | wc -l
      88
$ # normalised body of each nested config, counted:

$ grep -rho '@Import([^)]*)' backend/src/test/java | sort -u | wc -l

```

An imported configuration class is part of Spring's context cache key, so each of those classes
asks for a context of its own. The failing CI job says so in its own words:

Committed pinned at 512 MB for the whole run against a 4 GB ergonomic default — that is the proof
the cap is Gradle's. The floor ends at **434 MB of 512 MB: 78 MB of headroom, 85% full**, in a

**The 886 MB and the 434 MB are both real and not in conflict.** Squeezed, the JVM discards the
soft-referenced caches visible in the histogram — AspectJ shadow matches and reflection metadata,
over a million instances each — and compacts to ~446 MB. So 446 MB is the floor the suite cannot
go below and 886 MB is what it wants. Gradle's 512 MB default sat *on the floor*: the suite only
ever passed by running in permanent emergency collection, which is also why the failing CI run
took 12m45s against 9m53s green.

## What changed, and that it moved the peak

`backend/build.gradle.kts`, three things:

1. **`maxHeapSize = "2g"`**, with the measurement written into the comment above it.
2. **The ceiling is printed on every run**, passing or failing. Its absence is why this cost three
   investigations across two releases — the log said a context failed to load and never said how
   much heap it had to load it into.
3. **Heap exhaustion is named in the summary.** The listener watches the exception chain of every
   test *and* every suite for `OutOfMemoryError` (matching the rendered text too, since the
   failure is serialised out of the worker and may arrive as a placeholder), and separately
   catches the second face of it — `Result: FAILURE` with `failedTestCount == 0`, which is exactly
   what the 448 MB run produced and what my first draft of the listener would have missed.

### The banner was tested, not merely written

An untested legibility path is worth nothing, so I forced it: temporarily set the file's own
`maxHeapSize` to `192m`, asserted the tree had actually changed before running, and restored
through a trapped `EXIT`.

```
temporarily lowered to 192m
--- the tree must actually differ from the fixed version, or this test proves nothing:
146c146
< 	maxHeapSize = "2g"
---
> 	maxHeapSize = "192m"
...
Test JVM heap ceiling: 192m (Gradle's default, when unset, is 512m)
```

and the summary said, in place of a mystery:

```
────────────────────────────────────────────────────────
  THE TEST JVM RAN OUT OF HEAP. THIS IS NOT A CODE FAILURE.
────────────────────────────────────────────────────────
  The test worker ran out of memory, or died. Any failure
  above reading "Failed to load ApplicationContext" is that
  one OutOfMemoryError seen from JUnit's side; no assertion
  is broken. Re-running will very likely be green, and that
  reflex is exactly what this message exists to stop.

  This suite creates about a hundred Spring application
  contexts and keeps 81 of them reachable at once. It needs
  446 MB of heap at the very least and wants 886 MB. It was
  given 192m. Raise maxHeapSize in backend/build.gradle.kts,
  or cut the number of distinct test contexts. Do not simply
  run it again.
────────────────────────────────────────────────────────

```

Restored cleanly; `diff` against the intended version is empty and the tree reads
`maxHeapSize = "2g"`.

### Guarding against the hazard the last builder hit

Every run above went through `tools/work-lock.sh run verify` (lock taken even though I was alone),
used `--rerun` so no task could report UP-TO-DATE, printed `git diff --stat` on the target file
before starting, and **aborted** rather than proceeded if the tree was not in the state the run
required (`exit 9`). The patch scripts assert each anchor matches **exactly once** and `sys.exit`
otherwise; the one time an anchor was wrong (`java.util...` is unresolvable in a Kotlin DSL script,
where `java` is the plugin accessor) the build failed loudly at configuration time rather than
silently doing nothing.

floor. I deliberately did **not** go higher: a much larger ceiling would hide the retention in (2)

runway now, `3g` is still under 20% of a 16 GB runner. Your call.

observation, for whoever owns that file: the job's "Upload test report" step uploads only
`build/reports/tests/test/` and `build/test-results/test/`, so if you ever want a heap dump on OOM
it would need a path under one of those, or another upload step.
