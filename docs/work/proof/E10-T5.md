**Acceptance criteria:**

- Mint/verify, HS256, 5-minute expiry, claims `sub tenant conv scope iat exp`. Covered by
  `AgentTokenServiceTest`. One test asserts the claim set is exactly those six and the lifetime is
  exactly 5 minutes.
- Refused cases:
  - expired: refused at exactly `exp`, accepted 1 s before
  - signed with the wrong key
  - payload tampered (tenant swapped, original signature kept)
  - signature tampered
  - `alg: none`
  - HS512 signed with the right key
  - each of the six claims missing
  - claims present but not UUIDs
  - unknown scope
  - `iat` in the future
  - garbage tokens
  - key under 256 bits, or not base64, stops start-up

  An unknown scope is refused at both mint and verify, because scopes become Spring authorities. A
  token naming `MANAGE_VENDOR_PAYMENTS` as a "scope" must not grant that permission.
- Tenant mismatch: `AgentTokenFilterIT.tenantMismatch` covers it against real RLS: user at temple A,
  token names temple B, result 401. `AgentTokenFilterTest.tenantMismatch` covers the filter's explicit
  comparison. It gives the filter a row that RLS would have hidden, which only a mock can do.
- Separate chain for `/mcp/**`, ordered first, stateless, CSRF off, requires `agent:read`. CORS is
  off as well, because no browser should call it.
- `AgentTokenFilterIT` covers these cases:
  - no token: 401
  - Firebase token: 401 at `/mcp/test-echo`. The same token gets 200 at `/api/v1/whoami` in the same
    test, so the 401 is about the path.
  - Firebase token at `/mcp` itself: 401, so the mount point is inside the agent chain
  - valid agent token: 200, with:
    - `TenantContext` equal to the token's tenant
    - the database session's `app.tenant_id` equal to the token's tenant. This was read through the
      app's own DataSource, so RLS applies.
    - principal is an `AgentPrincipal` with the right user and conversation
    - authorities exactly equal to {agent:read, agent:propose} ∪ `RolePermissions.forRole(KITCHEN_MANAGER)`, with no `ROLE_`
  - disabled user: 401. The same token got 200 before the `UPDATE ... DISABLED`.
  - unknown user: 401
  - expired token: 401
  - wrong key: 401
  - token without `agent:read`: 403
  - a Kitchen Staff agent at an endpoint that needs `MANAGE_VENDOR_PAYMENTS`: 403, so the agent can do no more than the person
  - agent token at `/api/v1/whoami`: 401, so an agent token is worthless outside `/mcp`
- Firebase chain unchanged for other paths: all 13 existing `auth`/`testsupport` classes are green
  (see above).
- Thread-locals are cleared after the request: `AgentTokenFilterTest.clearedAfterwards`.

**Decisions made inside the contract, worth knowing:**

- **The user lookup is scoped by the token's own tenant claim.** That claim is signed by us. I did
  *not* use the `setAuthLookupUid` escape the Firebase path uses, and so it is not left set for the
  request. That escape widens `users` reads to the person's accounts at other temples, and the
  assistant needs none of that. This is the one deliberate difference from "exactly as
  AuthenticationFilter". Tenant set/clear, MDC tagging, and the disabled-user check all mirror it.
- **`AgentTokenFilter` is not a Spring bean.** If it were, Boot would install it as a servlet filter
  on every path.
- **Spring Boot was also auto-registering `AuthenticationFilter` (a `@Component`) as a plain servlet
  filter.** Before `/mcp` that copy was inert, because the chain had already run it. On `/mcp` it
  would have run after the agent chain and handed the agent token to Firebase on every tool call.
  `SecurityConfiguration` now disables that duplicate registration only. The in-chain filter is
  untouched, and the 13 existing security classes are green.
- **What happens when the key is unset.** A random in-memory key is used and a WARN is logged. Tokens
  then verify only on the instance that minted them, so this fails closed.
