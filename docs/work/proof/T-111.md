## What I found about `V43`

**It stays entirely, and the brief's suspicion was right.** `V43__donation_pan_fingerprint.sql` is a
PAN-fingerprint migration with three statements, of which exactly one mentions recurring donations:

```sql
ALTER TABLE donations ADD COLUMN pan_fingerprint TEXT;
ALTER TABLE recurring_plans ADD COLUMN pan_fingerprint TEXT;   -- the only line
CREATE INDEX donations_pan_fingerprint ON donations (tenant_id, pan_fingerprint) ...
```

Two reasons it is untouched. It is **applied on staging**, so editing or deleting it fails Flyway
validation and the API does not boot. And the other two statements are load-bearing for the donor
drill-down (`DonationLedgerService.donorHistory` matches donors across gifts by PAN fingerprint),
which is very much still in the product. `DROP TABLE recurring_plans` takes its column with it.

## What I found about foreign keys into `recurring_plans`

**Exactly one, and I checked twice — statically and at runtime.**

Statically: `grep -rn recurring_plans backend/src/main/resources/db/migration/*.sql` returns only
V42, V43 and my V114. The single inbound key is `donations_recurring_plan_fk`, added by V42 line 47
(`donations.recurring_plan_id → recurring_plans.id ON DELETE SET NULL`). `recurring_plans`'s *own*
outbound keys go to `tenants` and `users` and are irrelevant to a drop.

At runtime: **V114's `DROP TABLE` is deliberately written WITHOUT `CASCADE`.** If a dependency
existed that the reading missed, Flyway fails loudly on the deploy rather than silently taking a
stranger's constraint down. It applied clean against a fresh Testcontainers PostgreSQL under the
unprivileged migration role in every run below — which is the check, not a formality.

`delete_tenant_cascade` needs no change: V44 discovers tenant-owned tables dynamically from
`pg_attribute` rather than hardcoding a list, so a dropped table simply stops appearing.

## Decisions I made, which are the ones to argue with

**1. `'RECURRING'` stays a legal value of `donations.type`, and I did not rewrite or delete any
donation row.** This is the only real judgement in the task and the brief did not settle it.

Narrowing the CHECK to `('IN_KIND', 'ONE_TIME')` would have meant one of two things: the migration
fails on any database holding such a row, or the migration rewrites that row's account of what it
was. A donation row is the temple's record of money it actually received. Neither price is worth
paying to tidy a constraint, and Phase 2 will want the value back. So the value is a tombstone —
unreachable, because nothing writes it — in the same spirit as the error codes, which are never
reused because someone may quote one from an old screenshot.

There is almost certainly nothing to preserve: a `RECURRING` donation could only be written by a
`subscription.charged` webhook from a real Razorpay account, and the recurring screen was never
built. But "almost certainly" is not a reason to write a destructive migration.

**The consequence is real and I did not hide it.** With the ledger's `RECURRING` category gone, an
old row of that type is labelled **ONE_TIME**. So that the label and the filter cannot disagree — the
thing `categoryClause`'s own javadoc exists to prevent — the money arms are now written
`type <> 'IN_KIND'` rather than `type = 'ONE_TIME'`. Written the other way, such a row would carry a
label no filter matched and an accountant reconciling by category would come up short by its value
with nothing on screen saying why. Pinned by
`DonationLedgerIT.aWithdrawnRecurringGiftIsStillOnTheLedger`.

**2. I edited six files the brief did not name.** Each was a comment or a test assertion that named
the deleted feature as a present fact, in the same packages, with no other builder in them:

- `LedgerRow.java` and `PeriodSummary.java` — javadoc listing the ledger's categories.
- `PaymentEventHandler.java` — javadoc using "the recurring handler" as its live example of
  `handles()` being broader than `subscription()`.
- `WebhookSubscription.java` — its whole rationale was written around the only non-essential group,
  which this task deletes. I kept the grouping mechanism (it is not a recurring identifier, and the
  next optional feature will want it) and said in the javadoc that there is one group now and why.
- `TenantPaymentSettingsService.java` and `TenantSettingsController.java` — two sentences of history
  naming `subscription.*`.
- `TenantPaymentSettingsIT.java` — **two assertions that would otherwise have failed**:
  `registered.events().contains("subscription.charged")` and the `$[1]` non-essential group. With
  the recurring handler gone there is exactly one `PaymentEventHandler` bean, so the list has one
  entry. Now asserted as `$.length() == 1`, with the deleted assertion's reasoning kept as a comment.

If any of that was outside what you wanted, say so and it comes back out; none of it changes
behaviour.
