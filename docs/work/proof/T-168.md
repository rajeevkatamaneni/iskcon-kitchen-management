## The codes Meta documents

- **Already exists: documented.** Code `100`, subcode `2388024`, message "Content in This Language Already Exists". Source: https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-management ("Creating a template with a name that already exists for the same language returns error code 100, subcode 2388024, with message 'Content in This Language Already Exists'"). I read this from the page's raw HTML with curl, not from a summary.
- **Category mismatch: not documented.** It is not on the error codes page (https://developers.facebook.com/documentation/business-messaging/whatsapp/support/error-codes), the template management page, or the categorization page (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-categorization). The management page says only that "Invalid categories … return error code 100". I have not guessed a subcode.
- For reference, the error codes page does document two of the rule refusals: `2388293` "Parameters words ratio exceeds limit" and `2388299` "Leading or trailing parameters not allowed". Their descriptions match staging's refusals word for word.

## Which classification is used

Both, in this order, in `MetaWhatsAppClient.classify`:

1. **Category mismatch: fallback only**, on Meta's sentence "The category X doesn't match the one that's already associated with this template, Y". Marked STOPGAP in the code. It goes first because Meta does not say whether this answer also carries `2388024`. If it did, checking the code first would hide the mismatch.
2. **Already exists: by code**, `error_subcode == 2388024`.
3. **Already exists: fallback**, marked STOPGAP. Matches "there is already … content for this template" (staging's sentence, any language) or T-159's "already exists".
4. Anything else is REFUSED.

A test proves the code alone is enough: a Spanish sentence with no "already" in it still comes back ALREADY_EXISTS. Another proves the fallback alone is enough, with no subcode and no title. A third proves the fallback is not greedy: "New English (US) content can't be added while the existing English (US) content is being deleted" stays REFUSED.

**DEBUG log.** Every non-2xx answer logs:
`Meta answered template <name> with HTTP <status>: error.code=<..> error.error_subcode=<..> error_user_title=<..>`
A missing field prints `absent`. A test pins the exact line.

## Outcome kinds and stored reasons

Stored in `whatsapp_refused_templates` as `{name, reason, kind}`:

- `REFUSED`: T-159's reasons, unchanged.
- `NOT_REACHED`: T-159's "Meta could not be reached …", unchanged.
- `HELD_UNDER_ANOTHER_CATEGORY`, new:
  - Marketing: "Meta holds this message as marketing, which some countries do not deliver." That is 12 words with no semicolon. I added the full stop to match the other stored reasons. It is true: Meta's per-user limits page says WhatsApp "does not currently deliver marketing template messages to WhatsApp users with United States phone numbers" (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/marketing-templates/per-user-limits).
  - Any other category: "Meta holds this message under a different category from the app's."
- ALREADY_EXISTS is not stored at all. It is a clean result.

Entries written before T-168 have no `kind`. They read back as `REFUSED`, which is what they were written as. A test covers this.

`api.ts` is untouched. The GET answer now carries `kind` on each entry, which the frontend can ignore until it shows the list.

## The date decision

**A template Meta holds under another category counts toward "templates submitted".** The date means Meta holds at least one of our templates, and it holds these two. If they didn't count, a save where Meta held two as marketing and refused the other eighteen would write no date, saying nothing went to Meta when two plainly had. Already-held templates still count, as in T-159. Tests: "a template Meta holds under another category counts toward the date on its own" and "a save where Meta already holds every template stores nothing and sets the date".

## Known limit, now confirmed by staging

A second Save does not send an existing template back to Meta's review. "Already exists" is final, so changed wording under an existing name never reaches Meta. T-159 recorded this, and staging's 2026-09-13 save showed it: all 13 previously registered templates came back "already exists". The same goes for categories: Save cannot move `donation_thank_you` or `wishlist_gift_split` back to utility. That needs a category review in Meta's WhatsApp Manager, or a new template name.
