# T-258 — R-VEN-2: one preferred vendor per ingredient, and the row says "Preferred (replaces A)" before saving

## The finding that changed the task: V146 was not written

The database has enforced one preferred vendor per ingredient since **V24**:
`CREATE UNIQUE INDEX vendor_supplies_one_preferred ON vendor_supplies (tenant_id, ingredient_id) WHERE preferred;`
(`V24__vendors.sql:63`). It is present in the local database:

```
docker exec kms-postgres psql -U kms -d kms -c "select indexname, indexdef from pg_indexes where tablename='vendor_supplies';"
 vendor_supplies_one_preferred     | CREATE UNIQUE INDEX vendor_supplies_one_preferred ON public.vendor_supplies USING btree (tenant_id, ingredient_id) WHERE preferred
```

`VendorService.writeSupply` has also cleared the other vendor's preference in the same transaction
since before T-252 (it is in HEAD). So no temple can hold two preferred vendors for one ingredient,
and the duplicate count is zero by construction. Counted anyway (read-only):

```
docker exec kms-postgres psql -U kms -d kms -c "select tenant_id, ingredient_id, count(*) from vendor_supplies where preferred group by 1,2 having count(*)>1;" -c "select count(*) total, count(*) filter (where preferred) pref from vendor_supplies;"
(0 rows)
 total | pref
   147 |  144
```

Staging: not queried. It is migrated through V24 like every database, so the index makes duplicates
impossible there too (reasoned, not measured).

A V146 that de-duplicates would always find nothing, and a second identical partial unique index would
be dead weight. **V146 is unused and free to hand back.** A gap in Flyway versions is harmless. The
migration AC ("de-duplicates and then enforces") is met by the enforcement test below, against V24's
index; there is nothing to de-duplicate.

## What was built

- **Backend.** Ticking Preferred at B runs `UPDATE vendor_supplies SET preferred = false … WHERE ingredient_id = ? AND preferred`
  before B's row is written, in the same transaction. The single PUT and the bulk add share this path.
  A's price is not touched and **no price-history row is written** for A. `GET /vendors/preferred`
  lists every preferred pair in the temple, including a deactivated vendor's, because it is still the
  preferred source until someone moves it.
- **Frontend.** In the supplies table's edit row, the checkbox label reads "Preferred (replaces Anand Stores)"
  once ticked, when another vendor holds the preference. In an Other ingredients row, the same text
  appears beside the box and is linked with `aria-describedby`. The text is `text-ink-secondary`
  (neutral), `whitespace-normal`, `max-w-56` (wraps, never an ellipsis). It shows nothing when this vendor
  already holds the preference, when nobody holds it, or when the list couldn't be read. In that case
  the tick still saves.

- `receiving/ReceivingService.java:311` writes supplies with `preferred` deliberately not touched. It cannot create a second preferred row.

## Acceptance criteria

- **Ticking Preferred at B, for an ingredient preferred at A, leaves B preferred and A not.** Covered by the IT `tickingPreferredAtBReplacesA` (single PUT) and `bulkAddReplacesA` (bulk). Both also assert that A's `last_price` is still 58 and that A has exactly 1 history row, so no row was written for the move. The negative control fails both.
- **The row shows "Preferred (replaces A)" before saving.** Covered in vitest for the edit row and for the Other ingredients row. Each asserts the text is present while no write mock has been called, that it goes when the box is unticked, and that the Other ingredients box's `aria-describedby` points at the text. It is not shown for this vendor's own preference or for an ingredient nobody holds. After a save the list is read again. The colour is neutral (`text-ink-secondary`, and no warning, danger or success class).
- **The migration de-duplicates and then enforces.** Enforcement: `theDatabaseRefusesTwo` shows a second preferred row is refused by `vendor_supplies_one_preferred`. De-duplication: not built, because there is nothing to de-duplicate (see the top of this file). TenantLoopMigrationIT passes.
- **RLS.** `anotherTemplesPreferenceIsUntouched`: the other temple's preferred row survives, `GET /preferred` lists only this temple's row, and the un-prefer statement, run as the app role adopted as this temple and aimed at the other temple's ingredient, updates 0 rows. RowLevelSecurityIT passes.
- **Nothing truncated at 390: NOT VERIFIED ON SCREEN.** The local API is down (curl exit 7). The only evidence is the classes: the text wraps (`whitespace-normal`, `max-w-56`, no ellipsis).
