**Acceptance criteria:**

- 600 × 350 ML on an L recipe = 210: meal-composer test "plans 600 people at 350 ml on a recipe in litres as 210 L, not 210,000" checks the box shows 210 and the saved `targetYield` is 210. format test checks `600 * convertQuantity(350, "ML", "L")` ≈ 210.
- GM on KG: 600 × 150 gm = 90 on a KG recipe (composer test).
- Incompatible families (ML portion on a KG recipe): box empty (composer test); `convertQuantity` returns null for ML→KG, PIECES→KG, GM→L (format test).
- Same unit unchanged: existing composer tests (KG on KG, 200 → 200, 208 with seniors) still pass.
- Backend refuses > 50,000 on that dish's field: MealSaveIT POST with a second dish at 210000 → 400, KMS-400001, one field error `dishes[1].targetYield`, "Amount can be at most 50,000.", no meal or dish rows. PUT at 50000.01 → 400 on `dishes[0].targetYield`, stored amount unchanged. Exactly 50000 saves.
- Composer shows red under the box before sending: composer test types 60000, presses save, finds "How much Bisi Bele Bath to make can be at most 50000" with `aria-invalid="true"`, and `saveMeal` is not called; 50000 then saves. This reuses the `Form` component's own `max` handling and `formMessages.atMost`, which is the existing field-error pattern. It is deliberately not added to `firstBlocker`, because that disables the button and the red sentence would never appear.

**Other places that compute people × portion:** none besides `targetFor`. Checked by grepping `perHeadQty|perHeadUnit|per_head` across frontend and backend main code:
- Festival default servings (`mealDayContext.suggestedServings`) and "last time's menu" both go through `applyCount`/`targetFor`, so they get the fix.
- Backend reuse/copy of a plan (`MealPlanService` ~line 1026) copies stored `targetYield`s; no multiplication.
- `library/BookParser.perHead` / `LibraryLoader` parse the portion text; no multiplication.
- `donation/GivingPageController` (~line 130) does the reverse, plates = target_yield / per_head_qty, and only when `per_head_unit = base_yield_unit`. So an ML portion on an L recipe gives no plate count (undercount to nothing, not an overcount). Not changed: not people × portion, and outside this task. If it should convert too, `InventoryUnits.toBase` / `Unit.baseFactor()` would be the thing to reuse.
- No backend code multiplies people by the portion, so no backend conversion was added.

**Recipe form:** `frontend/components/RecipeForm.tsx` line ~201 offers the portion unit from `FOOD_UNITS` (all five: KG, GM, L, ML, PIECES), independent of the yield unit. So it is not restricted: a volume portion on a mass recipe can be saved, which is why the planner needs the null case. Not changed.
