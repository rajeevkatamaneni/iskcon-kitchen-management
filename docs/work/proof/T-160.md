## The component

```tsx
import { Form } from "@/components/ds/Form";
<Form id="…" className="…" aria-label="…" onSubmit={handler}>…</Form>
```

It takes every attribute a `<form>` takes, except `noValidate`, which it always sets. It also
forwards a ref. `onSubmit` is called only when every control passes.

On submit, it reads every control in `form.elements`. That includes controls outside the tag that
name the form with `form="…"`, and a submit from an outside button fires the same event. A control is
refused when `willValidate && !validity.valid`. That is exactly what `checkValidity()` computes. I read
`validity` instead because it fires no `invalid` events, and because tests can then simulate
`badInput`, which jsdom cannot produce. The browser skips disabled, read-only and hidden controls. No
check is reimplemented.

When a control is refused, the component calls `preventDefault`, does not call `onSubmit`, puts a
sentence in red after each refused box, and sets `aria-invalid="true"` on the box plus an
`aria-describedby` pointing at the sentence. Once the sentences are on the page, focus moves to the
first refused box. While a sentence is showing, every keystroke or change re-reads the boxes that have
one. A valid box loses its sentence and gets its original `aria-invalid` back. A box that is wrong in a
new way gets the new sentence.

The name comes from `aria-label`, then the text of `labels[0]` with any nested controls removed, then
`name`, then "This field". `Field`'s trailing "(required)" is dropped.

### Mechanism: a slot plus a portal, and why

For each refused control the component creates one empty `<span data-form-error-slot>` and places it
straight after the box. If the box is wrapped in a `<label>`, the slot goes after the label, because
inside the label the sentence would become part of the box's accessible name. React renders the
sentence into that slot through `createPortal`. No text or element is built by hand.

Why React doesn't fight it: React never re-reads the DOM, and it only inserts, moves and removes nodes
it created. The slot is not in React's tree, so React cannot duplicate it and has no reason to remove
it. Two things can still disturb it. React can insert its own node between the box and the slot, or
unmount the box. React can also overwrite `aria-invalid` or `aria-describedby` when a prop changes.
While any sentence shows, a `MutationObserver` on the form puts the slot back in place, re-applies the
two attributes, and drops the sentence of a box that has gone. The test "keeps exactly one sentence
beside its box while the form re-renders around it" proves all three. It inserts React nodes on both
sides of a refused box, re-renders twice and checks for exactly one sentence. Then it unmounts the box
and checks the sentence is gone.

I rejected having `Field` read an error from context. `Field.tsx` is read-only, and that approach would
only cover `Field` boxes, which are the minority. Both kinds are proved in the first test: a `Field`
box, a hand-rolled box named by `aria-label`, and a hand-rolled box in a wrapping `<label>`.

## Every sentence the component can produce

All live in `formMessages.ts`. `{Name}` is the field's label as written.

- `{Name} is required`
- `{Name} must be at least {min}`
- `{Name} can be at most {max}`
- `{Name} must be on or after {date}`: date box, for example "Start date must be on or after 13 Sept 2026"
- `{Name} must be on or before {date}`
- `{Name} must be {HH:mm} or later`: time box
- `{Name} must be {HH:mm} or earlier`
- `{Name} must be a whole number`: `step="1"`, or a number box with no step, whose default step is 1
- `{Name} can have at most 2 decimal places`: `step="0.01"` (and "1 decimal place" for 0.1)
- `{Name} must go up in steps of {step}`: any other step. No form uses one.
- `{Name} must be a number`: half-typed number
- `{Name} must be a complete date`: half-typed date
- `{Name} must be a complete time`: half-typed time
- `{Name} can be at most {n} characters`: too long
- `Enter an email address like name@example.com`
- `{Name} is not valid`: catch-all. Nothing in the 46 forms reaches it today.
- "This field" stands in for `{Name}` when a box has no label at all.

Dates go through `dateWithYear` in `lib/format.ts` (en-GB). In this Node it prints "13 Sept 2026", and
the test accepts "Sep" or "Sept".

## Server wording for the same rule, field by field

None of them agree in wording. The server's are full sentences ending in a full stop, and they don't
name the field.

Meal kinds:
- Name, blank. Server: "Enter the meal's name." Client: "Name is required".
- Name, over 80 characters. Server: "That name is too long." Client: "Name can be at most 80 characters". The browser stops typing at 80, so the client sentence practically never shows.
- Usually ready by, and Order in the day. The server has no message for either, so there is nothing to compare. Client for order: "Order in the day must be at least 0" and "… must be a whole number".

Occasions:
- Name, blank. Server: "Enter the occasion's name." Client: "Name is required".
- Name, over 200 characters. Server: "That name is too long." Client: "Name can be at most 200 characters".
- Wording in the calendar, blank. The server has no sentence of its own. `OccasionService` throws the generic `VALIDATION_FAILED` with field `matchText`. Client: "Wording in the calendar is required".
- Wording, over 200 characters. Server: "That wording is too long." Client: "Wording in the calendar can be at most 200 characters".
- Day, 0. Server: "A day is a number from 1 to 31." Client: "Day must be at least 1".
- Day, too high. Server allows up to 31 whatever the month. Client uses the month's own length: "Day can be at most 30" in November. So the client is stricter here.
- Month. Server: "A month is a number from 1 to 12." The client control is a `<select>` with no `required`, so it never refuses and has no sentence.
- Usual servings, below 0. Server: "A servings figure cannot be less than nothing." Client: "Usual servings must be at least 0".
- Notes, over 1000 characters. Server: "That note is too long." Client: "Notes can be at most 1000 characters".

Whether to bring the server messages into the same shape is Rajeev's call. I changed nothing on the
server.

## How a slice adopts it (for the next six builders)

Import `Form` from `@/components/ds/Form` and change `<form …>` to `<Form …>` and `</form>` to
`</Form>`, keeping every attribute as it is. Don't add `noValidate`, because `Form` sets it. The
`required`, `min`, `max`, `step` and `maxLength` already on the controls are the rules. Leave them
alone, and don't write checks of your own. A header button with `form="…"` works unchanged. Your
`onSubmit` now runs only when every box passes. In the slice's tests, click the submit button rather
than calling `fireEvent.submit`. Enter step-checked values with `fireEvent.change`, not
`defaultValue`, because jsdom never step-checks a `defaultValue`. Add one blank-submit test per form
asserting "<Label> is required" and no API call, and read the sentence to check the label makes a
sensible name.

- Only boxes that already have a sentence are re-checked while someone types. A new problem shows on the next submit.
