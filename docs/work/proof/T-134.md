## The decision the brief asked me to make, and where I disagreed with it

**The brief said the tile could generate through `POST /purchase-orders/generate` with that vendor's
`ingredientIds`. I verified that endpoint and did not use it, and I think the brief was wrong here.**

`PurchaseOrderController:69` does take an optional `GeneratePosRequest` — confirmed in the tree, and
`PurchaseOrderService.generateFromShoppingList` filters the list by those ids. But it raises the
order **from the list as the server last computed it**. It cannot carry an adjusted quantity, a line
somebody removed, an uncatalogued item, or the date typed in the box — which is everything the panel
exists to let a person do. Generating first and correcting afterwards with a PUT would mean the
order existed *before* Save, with a number, which is exactly what Rajeev ruled against: *"The Cancel
this PO control must not appear in that panel… because no order exists yet."*

So the panel posts to **`POST /api/v1/purchase-orders`** — the manual-create endpoint, which already
takes a vendor, a needed-by date and a list of lines of both kinds. **The brief's substantive point
still holds: no new endpoint was needed.** It is a different existing one.

**The PO number: returned, not fetched.** `create` now answers `{"id": …, "poNumber": "PO-2026-0041"}`.
The number is allocated inside the same transaction that writes the order, so it is already in hand;
a second request to read one string is a round trip spent on a fact the first response knew. That is
the brief's own preference and I agree with it.

**One thing the brief did not mention that the switch would have broken.** Generation looked up
`vendor_supplies.last_price` for every line; manual creation sent nulls (`/orders/new/lines` says so
in a comment: "there is nothing honest to put here"). Moving the temple's ordinary ordering path onto
the manual endpoint would therefore have **silently dropped the price column off every purchase
order** — the figure the sheet prints, and the one the delivery and the vendor's bill are checked
against. So `createPo` now fills a blank price from the vendor's last-known one, for catalogue lines
only, leaving a price the caller sent alone and a described line null. `/orders/new/lines` gets the
same fill, which I judged an improvement rather than a deviation — it is the same figure generation
has always used, from the same column — **but it is a behaviour change on a screen whose comment
argued the other way, so it is flagged for Rajeev below.**

**The comment on that screen has been rewritten** (`frontend/app/orders/new/lines/page.tsx`, the
block above the `lines:` literal), because the file was left asserting something the code no longer
does. It now says where the figure comes from, that the server fills it in when the client leaves it
blank, that it is the same snapshot the generated path always took, and what stays null. The
paragraph above it about `description` being required-and-nullable on `PoLineInput` is untouched: it
is still exactly right and still load-bearing.

**Does the vendor sheet now print a price where it used to print a dash, for an order raised by
hand? It prints more than that, and Rajeev should know before he sees a PDF.** The sheet's price
column exists at all only when at least one line carries a price (`DocumentGenerationService:204`,
`PurchaseOrderSheetTemplate:11`). A hand-raised order used to carry none, so the sheet had **no rate
column and no total**. One raised against a vendor with recorded prices now prints a rate per line —
"₹45.00 / Kg" — **and an estimated total at the foot**, which a vendor reading the sheet could
reasonably take as an agreed price rather than the temple's own last-paid figure. Unchanged for
orders generated from the shopping list, which have always printed both. A line whose vendor has no
recorded price still prints a dash.

## The extraction, and how I know it is faithful

The predecessor's description was accurate: inline JSX closing over eight pieces of parent state and
`useParams()`. What it became:

- **The component owns the working copy.** `initialLines` / `initialNeededBy` seed `useState` once;
  hosts mount it when editing starts and unmount it when editing ends, so there is no second copy of
  the draft in the parent to fall out of step with the one being typed into. The order page's state
  went from `draftLines: DraftLine[] | null` + `draftNeededBy: string` to `editing: boolean`.
- **What the host still knows is passed as behaviour, not as a mode.** `onSave(draft)` — the order
  page PUTs, the shopping list POSTs; `onCancel`; `onRefuse(message)`, so a client-side refusal
  lands in whichever error surface the host owns (above the form on the order screen, *inside* the
  panel on the shopping list, where a notice on the page behind the covering would be invisible).
- **`words` carries the five strings that can only be the host's** — heading, form label, intro, and
  the two refusals that name a way out that differs by screen ("cancel the order at the foot of the
  page" / "close this panel"). Grouped into one prop so a reader comparing the two call sites sees
  all of the difference at once.
- **There is deliberately no `mode` prop.** The moment the component can ask which screen it is on,
  the two screens can be made to differ.
- `AddLine` moved as-is, as predicted. `subjectOf` is exported from the component and imported by the
  order page, which prints the same subject in three other tables — two copies of that rule is how
  one of them comes to print an empty cell for a described line.

**"Cancel this PO" is not in the component, and that is the right place for the line.** It is shown
in *view* mode too, so it is not part of the edit form; it stays on `/orders/[id]` at the foot of the
page where T-135 put it, still gated on `hasPoNumber`. The panel renders no cancel block because
there is no order — and `offers no way to cancel a purchase order that does not exist yet` proves it
from the shopping-list side, without that file asking for the behaviour.

**The evidence it is the same form:** `order-detail.test.tsx` (26 tests) and
`described-po-line.test.tsx` (15) drive this form by label, by role and by the form's accessible name
— quantities, the picker, the described adder, the needed-by refusals, the lead-time warning, Remove,
the empty-order refusal. **All 41 passed with no edit to either file.**

## The duplicate the coordinator found — and what the sweep turned up

**It is not a Wave A regression.** `git show 68d4cf4~1` and `git show 316cf33` (T-024) both show the
`<section className="table-wrap …">` holding "What was ordered" rendered unconditionally, with
`{draftLines && canEdit && (` — the edit form — opening above it. The lines have been on that screen
twice in edit mode since the edit form existed. What Wave A changed is that the bank of buttons no
longer sits between the two, which is what made it visible.

Fixed by gating that section on `!editing`. Rajeev's own question settles it: in edit mode the lines
are the thing being edited, and a second uneditable copy showing the *saved* figure while the box
shows the typed one is not context, it is the screen disagreeing with itself.

**The sweep for anything else rendered in both modes** — every top-level section on the page:

| Header identity (number, vendor, status, "Generated", sent/not sent) | yes | Correct. It says which order you are editing; the form offers none of it. |
| Header "Needed by \<date\>" readout | **was yes** | **The second duplicate, and I fixed it.** The form carries a "Needed by" box; the readout showed the saved date beside the typed one. |

## Acceptance criteria

**1. A tile per vendor, holding that vendor's ingredients.** `groupByVendor` groups the list by
`suggestedVendorId`, vendor name as the tile's heading, the vendor column gone from the table
(the tile *is* the vendor). Lines with no preferred supplier get a tile of their own, last, with no
button and a sentence saying why. Verified by `puts each vendor's ingredients in their own tile, with
a button each` — which asserts, per tile, that the other vendor's ingredient is *not* in it — and by
`gives lines with no vendor a tile with no button`.

**2. Each tile has its own Generate Purchase Order button, and there is no button tied to several
vendors at once.** Verified by the same test: `getAllByRole(…/generate purchase order$/i)` is 2 for
two vendors, and `queryByRole(…/generate purchase orders/i)` — the plural, the old one — is absent.
The button is *refused* (not hidden) when every line in a tile is unticked, because the tile is still
worth reading: `refuses the button when every line in the tile is unticked`.

**3. Pressing it opens the purchase-order edit screen as a panel over the shopping list.** A
`role="dialog"` covering, the same component the order screen mounts inside it. Verified by `opens the
purchase-order editor as a panel holding only that vendor's lines`: that vendor's quantities are in
the boxes, the *other* vendor's line is not in the panel at all, and both adders — the catalogue
picker and "An item not in the catalogue" — are there, because it is that screen.

**4. Set the needed-by date for the whole order, adjust quantities, add a catalogued ingredient, add
an uncatalogued item.** All of it is the extracted component, so it is the same code the order screen
runs and the same 41 tests cover it. The panel's date opens on the **earliest** of that vendor's
lines, which is the rule generation has always used (the order is only useful if it arrives for the
first meal that wants any of it); a tile of lines nothing demanded opens with the box empty.

**5. On save, the order is created.** One `POST`, and nothing exists before that press. Verified by
`creates one order for that vendor on save, and says so by name`, which asserts the request body:
`vendorId` is the tile's, `neededBy` is the date in the box, and `lines` carries the **edited**
quantity (6, typed over the suggested 4). And by `creates nothing when the panel is cancelled`.

**6. A green confirmation naming the PO number appears and fades, and the user is back on the
shopping list.** `InlineNotice tone="success" autoDismiss` — the design system's confirmation that
clears itself after five seconds — titled `PO-2026-0041 raised for Heritage Fresh Dairy.` No link on
it, deliberately: the next thing to do is the next tile, and an action would argue with a notice
about to disappear. Same test: the dialog is gone, the text is on the screen, the list reloads.

**7. The "Cancel this PO" control must not appear in the panel, gated on there being a PO number.**
Nothing in the shopping list asks for this — the gate is `hasPoNumber` on the order screen, and the
panel's order has no number because it has no existence. Verified from the panel's side by `offers no
way to cancel a purchase order that does not exist yet`: no "Cancel this purchase order" heading, no
"Cancel order" button, no Reason box, no never-delivered tick — and the one Cancel that *is* there
cancels the panel.

**8. Built once, mounted twice.** `frontend/components/PurchaseOrderEditor.tsx`. The 41 order-screen
tests passed unchanged.

**9. (Added mid-task) The order's lines render once in edit mode.** Verified by `shows the order's
lines once while editing, and brings the readout back after`, which asserts all three states —
before, during, after — because an assertion that the table is absent in edit mode would pass just as
happily on a screen that had lost the table altogether.

## Not done / needs Rajeev

**1. No hand smoke test.** Commandment 5 wants one and I could not do it: the change is not deployed,
and there is no local run harness that starts this app against a backend in the sandbox. Everything
above is automated-test evidence. **The tiles, the panel and the green confirmation are visual and
were asked for by eye, so they should be looked at by eye on staging.**

**2. A behaviour change Rajeev should know about before he tests it: a needed-by date that has already
passed is now refused in the panel.** The list's date is the first meal that wants the ingredient, and
that day can already have gone. The old bulk button generated such an order anyway — deliberately:
`requireNeededByOnOrAfter` skips generation, because "generation is not a person typing". The panel
*is* a person typing, so the server measures it against today and refuses (KMS-400014); the panel says
so first, leaves the date in the box, and the person picks a new one. I think this is right — asking a
vendor for something yesterday is not a request — but it is a door that used to be open. Covered by
`refuses a date that has already gone, and leaves the panel open to fix it`, which also asserts the
existing warning "That day has already gone" is on screen before anybody presses anything.

**3. A manual order now carries the vendor's last-known price, where before it carried none — and its
printed sheet now carries a rate column and an estimated total where it used to carry neither.** The
reason for the fill is in "the decision" above: without it the temple's main ordering path would have
lost the price column altogether. The side effect lands on `/orders/new/lines`, an order somebody
types by hand. **The one part with an outside audience is the sheet**: a vendor holding a printed
order that now shows "₹45.00 / Kg" and a total may read it as a price we have agreed to, when it is
the temple's record of what it last paid them. That is already true of every order generated from the
shopping list, so this makes the two paths agree rather than introducing something new — but it is
new for hand-raised orders and you should decide with your eyes open. **If you would rather it did
not, it is a two-line change to restrict the fill to orders raised from the shopping list**, at the
cost of the two paths printing differently again.

**4. `POST /purchase-orders/generate` now has no caller in the application.** The bulk button was its
only one. I left the endpoint, its tests and `api.generatePurchaseOrders` alone — removing a public
endpoint is not a builder's call, and D-24 §2 (a message naming how many orders were created, on the
purchase-order list) may yet want it. **Somebody should decide whether it is retired or kept.**

**5. The panel is a dialog with focus and Escape, but no focus trap.** It takes focus on open and
Escape closes it; tabbing past the last control walks into the list behind the covering. The
application has no focus-trap helper anywhere (`VendorStatusDialog` has the same gap), so building
one here would have been a new shared thing inside this task. Worth one small task for both.

**6. `lib/format.leadTimeWarning` compares against a hard-coded two-day buffer**, which D-25 says is
per vendor and per ingredient (`vendor_supplies.lead_time_days`). The panel shows that warning, so it
will be as wrong as the order screen already is until D-25 is built. Not mine, not changed, named
here because the panel is a new place a reader will see it.

**7. `PurchaseOrderService.generateFromShoppingList`'s javadoc says "Stamping that lead time onto the
order is T-134's, not this method's."** It is not in my brief and it needs a column to stamp it into,
which needs a migration I was not allocated. **Left undone deliberately; it belongs with D-25.**
